## 장애를 어떻게 알아보고 복구했는가

배포 성공·HTTP 200·테스트 초록만으로 서비스가 정상이라고 판정할 수 없었다. 아래 사례는 원문 티켓·워크플로·기존 연구 노트에서 **영향 범위 → 증거 → 원인 → 조치 → 검증과 남은 일**을 이어 읽는 진입점이다. prod 사고와 dev·CI 문제를 구분하며, 운영 호스트를 새로 실측한 보고서는 아니다.

| 사례 | 환경 | 핵심 판정 신호 |
| --- | --- | --- |
| 필수 시드 누락 | prod | 빈 배열 200·마스터 0행 |
| 마이그레이션 순서 역전 | dev | 502·Flyway 적용 이력 |
| 배포 성공 단절 | dev CI/CD | timeout 시점의 부팅 로그 |
| 리뷰 잡 미실행 | CI | 실제 요청 run의 cancelled |

### prod — 필수 마스터 데이터 누락

**영향·근거:** GROMO-910에서 Flyway V1~V15 success와 Hibernate validate가 통과했는데도 온보딩 직업·상점 등은 빈 배열 200, 직업 설정은 4xx였다. 마스터 데이터가 없어 5xx만으로는 서비스 이상을 검출하지 못했다.

**복구·남은 일:** dev 값을 수동 복사해 임시 복구했다. 원문은 시드 코드화와 빈 DB 검증을 근본 대책으로 남겼다. 후속 구현 완료와 복구 시각은 별도 확인이 필요하다. [사고 2 — 빈 배열 200](/research/migration-incidents#사고-2--에러-로그-없이-빈-배열-200-gromo-910) · [GROMO-910](https://romance.atlassian.net/browse/GROMO-910)

### dev — 전 경로 502와 CD 6연속 실패

**영향·근거:** GROMO-1050→1063→1065는 V21이 V20보다 53초 먼저 병합·배포된 사고다. 적용 이력에 V20이 빠져 Flyway validation이 앱 기동을 막았고, nginx는 전 경로에 502를 반환했다.

**복구·남은 일:** dev 전용 out-of-order로 기동을 회복한 뒤 이미 적용된 V20을 수정해 checksum mismatch가 발생했다. 수습 2회 실패까지 기록했다. 재배포 전 적용 이력·체크섬을 확인해야 한다. [사고 3 — 머지 순서 역전](/research/migration-incidents#사고-3--53초-차이가-만든-3연쇄-gromo-1050) · [GROMO-1050](https://romance.atlassian.net/browse/GROMO-1050)

### dev CI/CD — 실배포 성공 단절

**영향·근거:** 최근 40회 중 성공 12회가 전부 7/24 이전이었다. 마지막 성공도 55초·12번째 시도였고, 실패 컷오프 때 앱은 에러 없이 Hibernate 초기화 중이었다.

**조치·남은 일:** PR #451에서 대기를 60→150초로, APM 부착 후 #524에서 300초로 조정했다. 준비되면 즉시 통과한다. 대기 상향은 진짜 장애 탐지도 늦추므로 readiness와 부팅 분포를 함께 봐야 한다. 복구율 수치는 원문에 없다. [CI/CD — 대기 창의 근거](/research/cicd-infra#724-이후-dev-배포-성공-0건) · [PR #451](https://github.com/OneOrThree/phone/pull/451)

### CI — Spot 러너의 리뷰 잡 미실행

**영향·근거:** GROMO-862 연계 사례에서 skipped 대부분은 정상 if 분기였다. 실제 요청 run은 Set up job에서 cancelled됐고 OAuth 사용 전에 종료돼 키 교체로 풀리지 않았다. 원문은 배정 러너 소멸을 근거로 Spot 선점을 원인으로 판정했다.

**대책·남은 일:** 대화형 잡만 hosted로 복귀하고 이벤트 분기를 고치는 방안을 제안했다. 당시 쿼터 리셋 후 적용 예정으로, 적용·재검증 완료는 미확인이다. [Spot 러너 선점 사례](/operations/02-spot-runner-preemption)

## 운영 판단으로 이어진 변화

**서비스 정상성은 응답 내용과 DB 상태까지 본다.** 시드 누락은 빈 목록이 정상 200이라 상태 코드 기반 관측에서 빠졌다. 필수 데이터의 개수·불변식과 실제 사용 흐름을 검사해야 한다. 시드 코드화와 부팅 검증은 원문의 후속 대책이며 이 페이지에서 적용 완료로 바꾸지 않는다.

**앱 재배포와 DB 복구는 다른 작업이다.** 실패한 배포도 이미 DB를 바꿨을 수 있다. Flyway 적용 이력·체크섬·현재 이미지 SHA를 확인한 뒤 다음 조치를 정한다. 과거 파일을 고쳐 다시 배포하는 방식이 수습 실패를 늘린 이유는 [마이그레이션 기록](/research/migration-incidents)에 남겼다.

**원인은 실패한 단계와 시간 분포로 좁힌다.** 초기화 중 timeout, Set up job의 cancel, 실제 예외로 인한 기동 실패를 같은 “배포 안 됨”으로 취급하지 않는다. [관측 스택](/research/observability-evolution)과 [초록인데 깨진 사례](/research/green-but-broken)는 판정 신호의 사각지대를 연결한다.

**다음 경계는 켜기 전에 검증한다.** Kafka는 main 코드가 있어도 기본 OFF다. lag·DLT·oldest-pending·relay 실패율 기준선, 중복 재처리, Redis ACL·재구축의 운영 검증은 [현재 아키텍처](/spec/architecture)와 [회고](/retrospective/02-kafka-redis-boundaries)에 후속으로 남긴다. 장애 대응 경험과 아직 검증하지 않은 설계는 별도로 읽는다.

## 기록의 범위와 출처

발생·복구 시각이 없는 사례의 MTTR, 영향 사용자 수, 재발률은 계산하지 않았다. 원문에 수동 복구·대책 제안만 있는 것을 “자동 복구 완료”로 바꾸지 않는다. 티켓의 완료 상태만으로 운영 적용을 입증하지 않고 배포·검증 근거를 연결한다.
