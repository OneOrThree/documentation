## 영향과 증상

2026-09-17 04:21(KST) 이후 main의 Dev CD가 전부 실패했고 dev 서버에 새 코드가 올라가지 않았다. 애플리케이션은 기동 자체가 막혔다 — Flyway `validate`가 부팅 단계에서 끊었기 때문이다.

```text
Migration checksum mismatch for migration version 38
```

영향 범위는 **dev 환경의 배포 파이프라인**이며 prod API 장애가 아니다. 다만 그 시점 이후 main에 들어간 모든 변경이 dev에 반영되지 않았으므로, 실패는 한 커밋에 머물지 않고 뒤따르는 커밋마다 반복됐다. [run 35168718059](https://github.com/OneOrThree/phone/actions/runs/35168718059)은 원인 커밋이 아니라 그 뒤의 다른 작업(#775)에서 같은 이유로 깨진 실행이다.

## 원인 — 주석도 파일이다

바꾼 것은 SQL 한 줄, 그것도 주석이었다.

```diff
- -- (docs/prd/challenge/prd.md L5 · policy.md B3).
+ -- (docs/prd/gromo/challenge/prd.md L5 · policy.md B3).
```

[#773(GROMO-1891)](https://github.com/OneOrThree/phone/pull/773)은 앱 구조와 PRD를 제품별로 재배치하면서 문서 경로를 일괄 치환했다. 그 치환이 `V38__screen_time_nullable_kst.sql` 안의 참조 주석까지 함께 바꿨다. `V38`은 이미 dev와 prod에 적용된 마이그레이션이다.

Flyway의 체크섬은 DDL의 해시가 아니라 **파일의 해시**다. 실행 결과가 같아도, 주석 한 글자가 다르면 값이 달라지고 `validate`는 기동을 거부한다. 일괄 치환 도구에는 "이 디렉터리 아래 파일은 이미 적용돼 불변"이라는 사실이 보이지 않는다.

<Callout label="같은 함정을 이미 문서에 적어 뒀었다" tone="warn">
[마이그레이션 사고 3연발](/research/migration-incidents)은 2026-08-02에 "**적용된 파일은 주석도 불변이다**"를 재발 방지 규칙으로 적었다. 그 글은 수습 중에 "주석은 안전하겠지"라고 판단해 장애를 한 번 더 만든 경험에서 나온 것이다. 규칙을 문서에 적어 굳혔다고 생각했지만 6주 뒤 같은 부류로 재발했고, 이번에는 사람이 마이그레이션을 편집한 것도 아니었다 — 문서 정리 도구가 지나갔을 뿐이다. 사람의 주의로 지키는 규칙은 사람이 그 파일을 보고 있을 때만 작동한다.
</Callout>

## 복구

`V38` 주석을 #773 이전 문자열로 되돌려 파일이 `30a7a280b^` 시점과 바이트 단위로 같아지게 했다([#779](https://github.com/OneOrThree/phone/pull/779)). 체크섬이 원래 값으로 돌아오므로 `flyway repair`나 이력 조작 없이 기동이 회복된다.

**되돌리는 쪽을 택한 이유:** 반대 방향(운영 DB의 `flyway_schema_history` 체크섬을 새 값으로 갱신)도 가능하지만, 그러면 dev·prod 양쪽 이력을 손대야 하고 "적용된 마이그레이션은 불변"이라는 규칙 자체를 깨는 선례가 남는다. 틀린 것은 주석이 아니라 주석을 바꾼 치환이었다.

## 재발 방지 — 검사를 사람에서 CI로 옮겼다

같은 PR이 `migration-immutable` 워크플로를 추가했다. PR에서 base와 비교해 `db/migration/` 아래 파일이 **수정·삭제·개명**되면 실패하고, **추가는 통과**한다. forward-only 원칙을 그대로 옮긴 것이다.

가드 자체가 조용히 무력해지는 경로도 두 군데 막혀 있다.

| 막은 것 | 방법 |
| --- | --- |
| 검사 패턴이 깨져 아무것도 안 보는 상태 | 추적 중인 마이그레이션 파일 수를 세어 0이면 실패시킨다 |
| base 계산 실패를 통과로 읽는 것 | `merge-base`를 못 구하면 "검사를 신뢰할 수 없다"며 명시적으로 실패시킨다 |

## 가드가 처음 잡은 것은 복구 커밋 자신이었다

도입 직후 오탐이 났고, [#781](https://github.com/OneOrThree/phone/pull/781)이 이를 고쳤다. 원인은 base를 무엇으로 잡느냐였다.

`github.event.pull_request.base.sha`는 **PR이 열린 시점**의 base tip에 고정된다. 그 뒤 통합 브랜치가 앞서 나가도 갱신되지 않는다. 반면 `actions/checkout`이 받는 것은 최신 base를 품은 머지 ref다. 둘을 비교하면 PR의 변경이 아니라 **통합 브랜치 자신의 변경**까지 diff에 섞인다.

그 사이 구간에 들어 있던 것이 바로 `V38` 되돌림이었다. 즉 이 가드의 첫 실패 사례는, 이 가드를 만들게 한 사고를 복구한 커밋이었다. 수정은 base를 실행 시점에 직접 구하는 것이다.

```bash
BASE_SHA=$(git merge-base FETCH_HEAD HEAD || true)
```

남은 이론상 구멍 하나는 워크플로 주석에 그대로 적혀 있다 — base가 force-push되면 `merge-base`가 옮겨가 그 구간의 변경을 보지 못한다. 막지 않고 적어 두는 쪽을 택했다.

## 재발 방지로 남긴 기준

- **적용된 마이그레이션은 주석까지 불변이다.** 오류는 다음 번호로 보정한다(forward-only). 이 규칙은 이제 사람이 아니라 CI가 지킨다.
- **경로 일괄 치환은 적용 이력이 있는 디렉터리를 제외하고 돌린다.** `server/data-api/src/main/resources/db/migration/`이 그 대상이다. 문서 정리처럼 "안전해 보이는" 작업이 가장 위험하다 — 리뷰가 SQL 쪽을 보지 않는다.
- **가드를 넣을 때 base를 무엇으로 잡는지 확인한다.** PR 이벤트 페이로드의 고정 SHA는 통합 브랜치가 움직이는 순간 오탐을 만든다.
- **가드는 자기가 죽었는지 스스로 말하게 만든다.** 패턴이 아무것도 못 찾거나 base 계산이 실패하면 통과가 아니라 실패다.
