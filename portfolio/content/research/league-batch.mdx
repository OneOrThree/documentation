리그는 그로모에서 가장 여러 번 넘어진 도메인입니다. 4주 동안 실측한 버그 네 건과 재편 스택 하나, 그리고 정산 배치의 멱등 재실행 경로를 여기 모아 둡니다. 결론부터 말하면 네 건 모두 새로운 종류의 버그가 아니었습니다. **집계가 수렴하는 지점을 하나로 유지하지 못했거나, 그 지점에서 원천의 정밀도·필터·쿼리 단위를 한 겹 잃어버린 것**입니다.

| 사건 | 증상 | 진짜 원인 | 티켓 |
| --- | --- | --- | --- |
| 리그 집중시간이 0 | 세션을 완료해도 리그 누적이 안 오름 | `recordCompletion`이 새 파생 통계를 안 건드림 | GROMO-646 |
| 랭킹 정밀도 손실 | 60초 미만 세션이 통째로 사라짐 | 분 단위 내림 근사 — 세션당 최대 59초 유실 | GROMO-665 |
| 알림 조용한 스킵 | 특정 티어 유저만 알림이 안 감 | `findAll()`에 `deletedAt` 필터 없음 | GROMO-840 |
| 메모리 폭증 | 정산 전원이 영속성 컨텍스트로 | 루프는 200개씩, 쿼리는 전량 조회 | GROMO-839 |

## 실패 1 — 점수 소스를 늘렸는데 수렴 지점을 안 봤다

집중 세션을 완료해도 리그 탭·랭킹·주간 승강 계산의 누적 집중시간이 0 그대로였습니다. 앱은 정상이고 `DailyFocusStat`도 정상이었습니다.

원인은 단순했습니다. 세션 완료가 지나가는 `recordCompletion`이 `DailyFocusStat`과 스트릭만 갱신하고, 새로 생긴 파생 통계인 `LeagueArenaUser.totalFocusMinutes`는 건드리지 않았습니다. 리그라는 소비처가 나중에 붙었는데 집계 지점을 갱신하지 않은 것입니다.

고친 방식이 이 사건의 교훈입니다. 세션 완료 경로는 두 개(POST 즉시완료 / 라이브 종료)인데 둘 다 `recordCompletion`으로 수렴하고 있었습니다. 그래서 한 곳만 고쳐도 두 경로가 함께 커버됐습니다.

- 현재 ACTIVE 아레나 멤버면 세션 시간 누적, 미배정 유저는 스킵
- `addFocusMinutes` 도메인 메서드로 더티체킹에 태움
- `findByUserAndArenaStatusForUpdate` 비관적 락으로 동시 세션 lost update 차단 (기존 `DailyFocusStat` 락과 동일 패턴)

회귀 테스트는 두 줄로 요약됩니다 — ACTIVE면 누적, 미배정이면 스킵. 이후 점수 소스를 늘릴 때마다 "수렴 지점이 여전히 하나인가"를 먼저 확인하게 됐습니다.

## 실패 2 — "랭킹용이니 분이면 충분하다"는 가정의 비용

같은 코드를 5일 뒤에 다시 열었습니다. 60초 미만 세션이 리그 누적에서 통째로 사라지고 있었습니다.

```java
// GROMO-646에서 이렇게 설계했다
long addedMinutes = addedSeconds / 60;   // 내림 — 세션당 최대 59초 유실
```

원천인 `DailyFocusStat`은 초 단위인데 리그 누적만 분 단위였습니다. 짧은 세션을 여러 번 하는 유저는 실제 집중시간의 상당 부분을 잃고, 원천과 파생이 어긋나니 순위·동점 판정까지 왜곡될 여지가 있었습니다. "랭킹용이니 분이면 충분"이라는 가정이 정밀도 손실의 누적으로 되돌아온 셈입니다.

수정은 `addFocusSeconds(addedSeconds)`로 초를 직접 누적하는 것이었지만, 단위 하나를 바꾸는 일이 어디까지 번지는지가 이 사건의 실질입니다.

| 바꿔야 했던 곳 | 내용 |
| --- | --- |
| 엔티티 필드 | `totalFocusMinutes` → `totalFocusSeconds` |
| 응답 DTO | 초 단위 필드로 전환 |
| 파생 쿼리·JPQL | `ORDER BY` 정렬 키까지 초 기준 |
| 배치·로그 키 | 초 단위로 일괄 전환 |
| 마이그레이션 | V8에서 컬럼 RENAME + 기존 분값 `×60` 환산 |

```sql
-- V8: 이름만 바꾸면 기존 행의 의미가 조용히 60배 틀어진다
ALTER TABLE league_arena_users
  RENAME COLUMN total_focus_minutes TO total_focus_seconds;
UPDATE league_arena_users SET total_focus_seconds = total_focus_seconds * 60;
```

데이터가 없어도 환산문을 넣었습니다. 마이그레이션이 "돌려도 무해"한 것과 "데이터가 있으면 틀리는" 것은 다르고, 후자는 나중에 어느 환경에서 터질지 알 수 없습니다.

여기서 굳힌 규칙은 두 개입니다. **저장은 원천 정밀도 그대로, 변환은 표시 단계에서만.** 그리고 **필드·컬럼명에 단위를 박아둔다**(`…Seconds`). 이름에 단위가 없었으면 애초에 분/초 이원화를 눈치채지 못했을 겁니다.

## 실패 3 — 개수를 검증했지 존재를 검증하지 않았다

위기 알림 배치(`sendCrisisReminders`)가 티어 설정을 `findAll()`로 로드하고 있었습니다. 소프트 삭제를 쓰는 테이블인데 `deletedAt` 필터가 없었으니, 삭제된 티어의 임계값이 알림 판정에 쓰일 수 있었습니다. 코드리뷰에서 잡힌 건입니다.

1차 수정으로 "티어 설정 5개인지 개수 검증"을 넣었는데, 이게 불충분했습니다.

```text
삭제된 T5 + 잘못 활성화된 티어6  →  개수는 5개  →  검증 통과
그런데 T5 유저는 config == null  →  예외 없이 조용히 스킵
```

개수는 제약이 아니라 우연히 맞을 수 있는 값이었습니다. 최종 수정은 `loadTierConfigs`에서 `deletedAt == null`을 걸고 **티어 1~5 각각의 존재를 개별 검증**하는 것으로, 위반 시 침묵 스킵 대신 예외로 드러냅니다. 같은 설정을 읽는 `LeagueBatchService`와 로드 정책을 맞춰 두 서비스가 다른 답을 낼 수 없게 했습니다.

부수적으로 나온 것 두 가지도 기록해 둡니다.

- 크론 주석에 남아 있던 옛 조용한 시간(21–09시)을 실제 값(23–07시)으로 정정했습니다. 주석이 낡으면 다음 사람이 잘못된 전제로 판단합니다.
- 위기(09시)·강등 재발송(18시)·마감 2시간 전(22시) 잡을 수동 트리거 API로 노출했습니다. QA가 크론 시각까지 기다리지 않고 온디맨드로 검증할 수 있어야 이런 버그가 다음에는 리뷰가 아니라 테스트에서 잡힙니다.

## 실패 4 — 루프가 있다 ≠ 페이지네이션이다

주간 결과 알림 발송에서 메모리 사용이 유저 수에 비례해 폭증했습니다. 코드에는 200개 단위 루프가 분명히 있었습니다.

```java
// 겉보기: 200개씩 나눠 처리한다
List<LeagueWeeklyResult> targets =
    repository.findByWeekStartAtAndResultIn(weekStartAt, WEEKLY_RESULT_TYPES);
for (int i = 0; i < targets.size(); i += 200) {
    process(targets.subList(i, Math.min(i + 200, targets.size())));
}
```

루프는 이미 메모리에 올라온 `List`를 슬라이스만 하고 있었습니다. 쿼리는 한 번, 전량입니다. 게다가 STAY(잔류)를 결과 타입에 통합하면서 대상이 "승격·강등한 소수"에서 "정산된 전원(대다수가 잔류)"으로 커진 정책 변경이 있었습니다. 대상 집합이 커진 순간, 모양만 페이지네이션이던 코드가 실제 문제가 된 것입니다.

전량 조회 메서드를 지우고 id keyset 조회로 바꿨습니다.

```java
// cursorId nullable — 첫 페이지는 null
@Query("""
    select r from LeagueWeeklyResult r
     where r.weekStartAt = :weekStartAt
       and r.result in :types
       and (:cursorId is null or r.id > :cursorId)
     order by r.id asc
    """)
List<LeagueWeeklyResult> findResultPageAfter(...);
```

서비스는 while keyset 루프로 전환하고 페이지마다 flush/clear로 영속성 컨텍스트를 비웁니다. 대상 타입은 `WEEKLY_RESULT_TYPES` 상수로 뽑아 알림·정산이 같은 집합을 보게 했습니다. 테스트는 리포지토리 keyset 통합 테스트 + 커서 기반 서비스 테스트로 다시 썼습니다.

배운 것 세 줄:

1. 루프가 있는지 보지 말고 **쿼리가 페이지 단위로 나가는지** 본다.
2. 대량 배치는 offset이 아니라 id keyset(커서) + 페이지마다 flush/clear.
3. 대상 집합을 키우는 정책 변경(STAY 통합 등)은 조회 경로 부하 재점검을 동반해야 한다.

## 재편 — 점수 원천을 아예 옮겼다 (#240~243)

버그를 네 번 고치는 동안 드러난 공통 원인은 "리그가 자체 누적값을 들고 있다"는 것이었습니다. 그래서 아레나 기반 리그를 4개 PR 스택으로 다시 설계했습니다.

| PR | 티켓 | 한 일 |
| --- | --- | --- |
| #240 | GROMO-814 | `users.tier_level`을 티어 단일 원천으로 두는 모델 토대. V12에서 1~5 CHECK 제약, `league_weekly_results`(유저·주차 UNIQUE) 추가 |
| #241 | GROMO-815 | 리그 티어 시간 임계값 전환 |
| #242 | GROMO-816 | 랭킹 점수 원천을 `league_arena_users` 누적값 → `DailyFocusStat` 주간 합계로 |
| #243 | GROMO-817 | 전역 주간 티어 정산, 레거시 아레나 멤버십 제거(V14) |

#242가 핵심입니다. 점수를 별도 컬럼에 누적하지 않고 원천을 매번 집계하니, 실패 1(수렴 누락)과 실패 2(정밀도 이원화)가 구조적으로 재발할 수 없게 됩니다. `FocusService`의 `league_arena_users` 이중 쓰기도 이때 제거했습니다. 초 단위로 애써 바꿔둔 그 컬럼은 결국 V14에서 사라졌지만, 규칙("원천 정밀도로 저장")은 남아서 새 설계의 전제가 됐습니다.

구현에서 신경 쓴 지점:

- 탈퇴하지 않은 전원을 LEFT JOIN으로 집계해 **0초 유저도 랭킹에 포함**
- 정렬 계약을 `totalFocusSeconds DESC, PostgreSQL UUID ASC`로 통일 — 전역·직군·내 순위가 같은 규칙을 쓰므로 동점 순위가 요청마다 흔들리지 않음
- 정산은 user.id UUID cursor 기반 100명 단위 (앞의 실패 4와 같은 keyset 원칙)
- `LeagueWeek` KST 주차 경계 유틸을 분리해 주차 계산을 한 곳에 모음

**알려진 제한을 남긴 것도 결정입니다.** `DailyFocusStat.date`는 사용자 country 로컬 날짜인데 리그는 KST 날짜 창으로 집계하므로, 해외 유저는 주차 경계에서 최대 1일 버킷 차이가 날 수 있습니다. 정확한 전역 KST 주차가 필요하면 instant 기반 원천이나 리그 전용 rollup이 필요합니다 — MVP 범위에서는 감수하고 PR 본문에 명시했습니다.

검증은 PostgreSQL 16 Testcontainers 통합 테스트로 0초 유저 포함, occupation 필터, 합계 내림차순과 UUID 동률 규칙, 내 전역 순위, 정산 cursor 페이지, 그리고 위 1일 버킷 제한까지 케이스로 고정했습니다.

배포 직후에 대가도 치렀습니다. V14가 프로덕션에서 `constraint ... does not exist`로 실패해 CD를 막았습니다. 프로덕션은 Flyway 도입 전 레거시 스크립트로 만들어져 유니크 제약의 실제 이름이 베이스라인과 달랐기 때문입니다. #251에서 고정 이름 DROP을 제거하고 **유니크 제약 제거를 `arena_id` 컬럼 DROP에 위임**했습니다 — PostgreSQL은 컬럼을 지우면 그 컬럼을 포함한 유니크 제약·인덱스를 이름과 무관하게 함께 제거합니다. 최종 스키마는 동일하고 제거 방식만 다릅니다.

## 멱등 재실행 — 신규 테이블 0개로 (#517 → #534)

재편 이후 정산 배치는 두 단계로 더 단단해졌습니다.

**1단계(#517)**: 주간 정산이 전 유저 단일 트랜잭션이라, 정산 도중 커밋된 회원탈퇴 1건이 배치 전체 롤백으로 번졌습니다. 조사에서 확정한 충돌이 4중이었습니다.

| # | 충돌 |
| --- | --- |
| ① | 집계 조회~재조회 사이 탈퇴 커밋 → `requireUser` throw → 전체 롤백 |
| ② | 승급자 지갑이 탈퇴로 삭제 → credit NOT_FOUND → 전체 롤백 |
| ③ | users 행 락을 배치 끝까지 보유 → 탈퇴 HTTP 무한 대기 |
| ④ | User에 `@Version` 없는 full-row UPDATE → 탈퇴가 파기한 PII 부활(lost update) |

구조를 세 빈으로 쪼갰습니다. `LeagueBatchService`는 무트랜잭션 오케스트레이터, `LeagueAnchorRotator`가 anchor 가드·마감·생성을 선커밋, `LeagueUserSettler`가 유저 1명 정산을 `@Transactional`로 맡습니다(자기 호출은 프록시를 안 타므로 빈 분리가 필수였습니다). 건 안에서 `findActiveByIdForUpdate` 배타 락으로 재조회하니 탈퇴 선커밋이면 예외 없이 skip, 락을 쥐면 탈퇴가 직렬화되어 지갑 생존이 보장되고 PII lost update 창도 닫힙니다. 잠금 순서가 유저→지갑으로 양쪽 동일해 교착도 없습니다. 검증은 배치↔탈퇴 `CyclicBarrier` 동시 실행 테스트를 3회 반복 그린으로 확인했습니다.

이때 **트레이드오프를 PR 본문에 적어두고 넘겼습니다**: anchor 선커밋 구조라 정산 루프가 크래시로 중단되면 재실행이 `BATCH_ALREADY_RUN`에 막힌다. 지라 티켓으로도 남겼고, 이게 다음 단계가 됩니다.

**2단계(#534)**: 그 잔여를 풀었습니다. 위험은 두 겹이었습니다 — 기본 run은 anchor 가드에 막히고, 가드를 뚫으면 라이브 tier 재독으로 성공 유저가 **연쇄 승급(래칫)** 되거나 유니크 위반으로 전원 failed 집계됩니다. 돈 경로라 "재실행 시 중복 정산 불가능함을 증명하는 통합 테스트"를 완료 조건으로 먼저 못박았습니다.

완료 마커를 새로 만들지 않은 것이 이 PR의 핵심입니다. `league_weekly_results`는 STAY도 INSERT하므로 **행의 존재 자체가 "그 주차 정산 완료"** 를 의미하고, 유저·주차 UNIQUE 제약도 이미 있었습니다. 신규 테이블도, 마이그레이션도 0개입니다.

```text
settle(user, week)
  → 유저 행 배타 락 취득
  → (락 안에서) existsByUserIdAndWeekStartAt 재확인
      존재하면  → ALREADY_SETTLED 로 skip, mutation 0건
      없으면    → 정산 후 결과 행 INSERT
  → 유니크 제약은 최후 방어로 유지
```

락 안에서 재확인하기 때문에 동시 재실행에도 정확히 한 번만 정산됩니다. 반환형은 boolean에서 `SettleOutcome`(SETTLED / SKIPPED_WITHDRAWN / ALREADY_SETTLED)으로 바꿔 summary에 `alreadySettledMemberCount`를 신설했습니다 — 기존 skipped가 뜻하던 "탈퇴"는 의미를 그대로 두었습니다.

진입점도 기존 계약을 건드리지 않는 쪽으로 만들었습니다.

- `rotateIfAbsent` 신설 — anchor 있으면 회전 skip, 없으면 회전. 기존 `rotate()`의 409 계약은 바이트 단위 불변이라 스케줄러와 기존 run 경로는 무변경(기존 재실행 테스트가 무수정 그린)
- 정산 루프는 페이지(100명)당 완료 마커를 일괄 선조회해 N+1을 피하되, **정본은 락 안 단건 재확인**이고 이건 빠른 경로일 뿐
- 선택적 `userIds` 표적 재실행 지원 — 실패한 유저만 다시 돌림
- `POST /api/v1/league/batch/resume`은 프로파일 제한 + `X-Batch-Admin-Key` 상수시간 비교(`MessageDigest.isEqual`)
- 기존 `/league/batch/run`은 무키 유지 — anchor 409 가드로 주차당 1회만 실효라 위험도가 다르고, 키를 소급하면 dev 운영 절차가 깨집니다. 이 판단을 테스트(`legacyRunStaysKeyless`)로 고정했습니다

증명은 실제 실패 경로를 유도해서 했습니다. 지갑 없는 유저를 만들어 승급 보너스 credit을 실패시킨 뒤, 1차 run에서 A 성공·B 실패 → 원인 복구 → resume. 확인한 것은 **A가 완전히 불변**(tier 래칫 없음·결과 1행·보너스 트랜잭션 1건)이고 B만 정산되며, 한 번 더 돌리면 전원 already로 변화가 없다는 것입니다. 전체 스위트는 1,379 tests / 0 failures로 끝났습니다.

## 지금 남은 판단

- 정산에 분산 락은 아직 없습니다. 건별 배타 락 + (user, weekStartAt) 유니크 + 보너스 멱등키로 이중 반영은 차단되어 있고, 분산 락은 별도 티켓의 TODO로 남겨두었습니다.
- 해외 유저의 최대 1일 버킷 차이는 여전히 알려진 제한입니다. 리그 전용 rollup을 만들 만큼 규모가 크지 않다는 판단이고, 규모가 커지면 다시 열 결정입니다.
- 아레나 시절 얻은 규칙 세 개는 재편 이후에도 그대로 씁니다. 집계는 한 지점으로 수렴시킨다, 저장은 원천 정밀도로 한다, 배치는 keyset으로 돈다.
