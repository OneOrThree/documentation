세션당 최대 59초가 리그 랭킹에서 사라지고 있었습니다. 4주 동안 리그 도메인에서 같은 종류의 실패가 네 번 났고(셋은 실제 동작에서, 하나는 리뷰에서 잡혔습니다), 원인은 전부 **집계가 수렴하는 지점을 하나로 유지하지 못했거나, 그 지점에서 원천의 정밀도·필터·쿼리 단위를 한 겹 잃어버린 것**이었습니다. 앞의 두 건을 고친 뒤 점수 원천을 `DailyFocusStat` 주간 합계로 되돌리는 재편(#240~243)으로 갔고, 재편이 만든 모델 위에서 다시 두 건(GROMO-840·839)이 났습니다. 주간 정산의 멱등 재실행은 그 재편이 남긴 `league_weekly_results`의 유니크 행을 완료 마커로 재사용해, 신규 테이블·마이그레이션 0개로 끝냈습니다(#534). 재실행해도 성공 유저가 완전히 불변임을 통합 테스트로 못박았고, 전체 스위트는 1,379 tests / 0 failures였습니다.

실패 1~4는 원인 유형별 묶음입니다. 발생 시점은 각 절 첫 문장에 적었습니다.

| 사건 | 어떻게 드러났나 | 진짜 원인 | 티켓 |
| --- | --- | --- | --- |
| 리그 집중시간이 0 | 세션을 완료해도 리그 누적이 안 오름 | `recordCompletion`이 새 파생 통계를 안 건드림 | GROMO-646 |
| 랭킹 정밀도 손실 | 60초 미만 세션이 통째로 사라짐 | 분 단위 내림 근사 — 세션당 최대 59초 유실 | GROMO-665 |
| 알림 조용한 스킵 | 리뷰에서 차단 — 삭제된 티어 임계값이 알림 판정에 쓰일 수 있었음 | `findAll()`에 `deletedAt` 필터 없음 | GROMO-840 |
| 메모리 폭증 | 주간 결과 알림 발송에서 메모리가 유저 수에 비례해 폭증 | 루프는 200개씩인데 쿼리는 정산 결과 전량 조회 | GROMO-839 |

## 실패 1 — 점수 소스를 늘렸는데 수렴 지점을 안 봤다

집중 세션을 완료해도 리그 탭·랭킹·주간 승강 계산의 누적 집중시간이 0 그대로였습니다. 앱은 정상이고 `DailyFocusStat`도 정상이었습니다.

세션 완료가 지나가는 `recordCompletion`이 `DailyFocusStat`과 스트릭만 갱신하고, 새로 생긴 파생 통계인 `LeagueArenaUser.totalFocusMinutes`는 건드리지 않았습니다. 리그라는 소비처가 나중에 붙었는데 집계 지점을 갱신하지 않은 것입니다.

세션 완료 경로는 두 개(POST 즉시완료 / 라이브 종료)인데 둘 다 `recordCompletion`으로 수렴하고 있었습니다. 그래서 한 곳만 고쳐도 두 경로가 함께 커버됐습니다.

- 현재 ACTIVE 아레나 멤버면 세션 시간 누적, 미배정 유저는 스킵
- `addFocusMinutes` 도메인 메서드로 더티체킹에 태움
- `findByUserAndArenaStatusForUpdate` 비관적 락으로 동시 세션 lost update 차단 (기존 `DailyFocusStat` 락과 동일 패턴)

회귀 테스트는 두 줄입니다. ACTIVE면 누적, 미배정이면 스킵. 이후 점수 소스를 늘릴 때는 수렴 지점이 하나인지부터 확인합니다.

## 실패 2 — "랭킹용이니 분이면 충분하다"는 가정의 비용

같은 코드를 5일 뒤에 다시 열었습니다. 실패 1을 막으려고 넣은 누적 한 줄이 그대로 다음 버그였습니다.

```java
// GROMO-646에서 이렇게 설계했다
long addedMinutes = addedSeconds / 60;   // 내림 — 세션당 최대 59초 유실
```

원천인 `DailyFocusStat`은 초 단위인데 리그 누적만 분 단위였습니다. 짧은 세션을 여러 번 하는 유저는 실제 집중시간의 상당 부분을 잃고, 원천과 파생이 어긋나니 순위·동점 판정까지 왜곡될 여지가 있었습니다.

수정은 `addFocusSeconds(addedSeconds)`로 초를 직접 누적하는 한 줄이었지만, 단위 하나를 바꾸는 일이 다섯 곳으로 번졌습니다.

| 바꿔야 했던 곳 | 내용 |
| --- | --- |
| 엔티티 필드 | `totalFocusMinutes` → `totalFocusSeconds` |
| 응답 DTO | 초 단위 필드로 전환 |
| 파생 쿼리·JPQL | `ORDER BY` 정렬 키까지 초 기준 |
| 배치·로그 키 | 초 단위로 일괄 전환 |
| 마이그레이션 | V8에서 컬럼 RENAME + 기존 분값 `×60` 환산 |

```sql
-- V8: 이름만 바꾸면 기존 행의 의미가 조용히 60배 틀어진다
ALTER TABLE league_arena_users
  RENAME COLUMN total_focus_minutes TO total_focus_seconds;
UPDATE league_arena_users SET total_focus_seconds = total_focus_seconds * 60;
```

데이터가 없어도 환산문을 넣었습니다. 마이그레이션이 "돌려도 무해"한 것과 "데이터가 있으면 틀리는" 것은 다르고, 후자는 나중에 어느 환경에서 터질지 알 수 없습니다.

같은 시기 통계 쪽에서도 이름이 같은 전환이 있었지만 대상 테이블이 다릅니다. 그쪽은 통계 원천 쪽이고 경위는 [타임존 버킷 전쟁](/research/timezone-wars)에 있습니다. 여기서 바꾼 것은 `league_arena_users`입니다.

여기서 굳힌 규칙은 두 개입니다. **저장은 원천 정밀도 그대로, 변환은 표시 단계에서만.** 그리고 **필드·컬럼명에 단위를 박아둔다**(`…Seconds`). 이름에 단위가 없었으면 애초에 분/초 이원화를 눈치채지 못했을 겁니다.

## 실패 3 — 개수를 검증했지 존재를 검증하지 않았다

재편으로 티어가 `users.tier_level` 단일 원천이 된 뒤에 들어온 건이고, 배치가 한 번 돌기 전에 리뷰어가 잡았습니다. 위기 알림 배치(`sendCrisisReminders`)가 티어 설정을 `findAll()`로 로드하는데, 소프트 삭제를 쓰는 테이블에 `deletedAt` 필터가 없었습니다.

1차 수정으로 "티어 설정 5개인지 개수 검증"을 넣었는데, 이게 불충분했습니다.

```text
삭제된 T5 + 잘못 활성화된 티어6  →  개수는 5개  →  검증 통과
그런데 T5 유저는 config == null  →  예외 없이 조용히 스킵
```

티어 설정이 5개라는 사실은 1~5가 각각 있다는 뜻이 아니었습니다. 최종 수정은 `loadTierConfigs`에서 `deletedAt == null`을 걸고 **티어 1~5 각각의 존재를 개별 검증**하는 것으로, 위반 시 예외를 던집니다. 같은 설정을 읽는 `LeagueBatchService`와 로드 정책을 맞춰 두 서비스가 다른 답을 낼 수 없게 했습니다.

같은 PR에서 두 가지를 함께 정리했습니다.

- 크론 주석에 남아 있던 옛 조용한 시간(21–09시)을 실제 값(23–07시)으로 정정했습니다. 주석이 낡으면 다음 사람이 잘못된 전제로 판단합니다.
- 위기(09시)·강등 재발송(18시)·마감 2시간 전(22시) 잡을 수동 트리거 API로 노출했습니다. QA는 크론 시각을 기다리지 않고 온디맨드로 검증합니다.

## 실패 4 — 루프가 있다 ≠ 페이지네이션이다

재편으로 STAY까지 `league_weekly_results`에 들어온 뒤에 난 건입니다. 코드에는 200개 단위 루프가 멀쩡히 있었는데도, 주간 결과 알림 발송의 메모리 사용이 유저 수를 따라 올라갔습니다.

```java
// 겉보기: 200개씩 나눠 처리한다
List<LeagueWeeklyResult> targets =
    repository.findByWeekStartAtAndResultIn(weekStartAt, WEEKLY_RESULT_TYPES);
for (int i = 0; i < targets.size(); i += 200) {
    process(targets.subList(i, Math.min(i + 200, targets.size())));
}
```

루프는 이미 메모리에 올라온 `List`를 슬라이스만 하고 있었습니다. 쿼리는 한 번, 전량입니다. 게다가 STAY(잔류)를 결과 타입에 통합하면서 대상이 "승격·강등한 소수"에서 "정산된 전원(대다수가 잔류)"으로 커졌습니다. 대상 집합이 커지면서, 페이지 모양만 갖춘 이 루프가 메모리 부하로 이어졌습니다.

전량 조회 메서드를 지우고 id keyset 조회로 바꿨습니다.

```java
// cursorId nullable — 첫 페이지는 null
@Query("""
    select r from LeagueWeeklyResult r
     where r.weekStartAt = :weekStartAt
       and r.result in :types
       and (:cursorId is null or r.id > :cursorId)
     order by r.id asc
    """)
List<LeagueWeeklyResult> findResultPageAfter(...);
```

서비스는 while keyset 루프로 전환하고 페이지마다 flush/clear로 영속성 컨텍스트를 비웁니다. 대상 타입은 `WEEKLY_RESULT_TYPES` 상수로 뽑아 알림·정산이 같은 집합을 보게 했습니다. 테스트는 리포지토리 keyset 통합 테스트 + 커서 기반 서비스 테스트로 다시 썼습니다.

이후 배치 리뷰 체크리스트에는 "루프가 있는가" 대신 "쿼리가 몇 번 나가는가"가 항목으로 들어갔고, 대상 집합을 키우는 정책 변경(STAY 통합 등)에는 조회 경로 부하 재점검이 함께 붙었습니다.

## 재편 — 점수 원천을 아예 옮겼다 (#240~243)

앞의 두 건을 고치는 동안 드러난 공통 원인은 "리그가 자체 누적값을 들고 있다"는 것이었습니다. 그래서 아레나 기반 리그를 4개 PR 스택으로 다시 설계했습니다.

| PR | 티켓 | 한 일 |
| --- | --- | --- |
| #240 | GROMO-814 | `users.tier_level`을 티어 단일 원천으로 두는 모델 토대. V12에서 1~5 CHECK 제약, `league_weekly_results`(유저·주차 UNIQUE) 추가 |
| #241 | GROMO-815 | 리그 티어 시간 임계값 전환 |
| #242 | GROMO-816 | 랭킹 점수 원천을 `league_arena_users` 누적값 → `DailyFocusStat` 주간 합계로 |
| #243 | GROMO-817 | 전역 주간 티어 정산, 레거시 아레나 멤버십 제거(V14) |

점수를 별도 컬럼에 누적하지 않고 원천을 매번 집계하도록 #242에서 뒤집었습니다. 그러면 실패 1(수렴 누락)과 실패 2(정밀도 이원화)가 구조적으로 재발할 수 없습니다. `FocusService`의 `league_arena_users` 이중 쓰기도 이때 제거했습니다. 초 단위로 애써 바꿔둔 그 컬럼은 결국 V14에서 사라졌지만, 규칙("원천 정밀도로 저장")은 남아서 새 설계의 전제가 됐습니다.

구현에서 신경 쓴 지점:

- 탈퇴하지 않은 전원을 LEFT JOIN으로 집계해 **0초 유저도 랭킹에 포함**
- 정렬 계약을 주간 합계 별칭 `totalFocusSeconds DESC, PostgreSQL UUID ASC`로 통일 — 전역·직군·내 순위가 같은 규칙을 쓰므로 동점 순위가 요청마다 흔들리지 않음
- 정산은 user.id UUID cursor 기반 100명 단위 (앞의 실패 4와 같은 keyset 원칙)
- `LeagueWeek` KST 주차 경계 유틸을 분리해 주차 계산을 한 곳에 모음

알려진 제한 하나는 고치지 않고 남겼습니다. `DailyFocusStat.date`는 사용자 country 로컬 날짜인데 리그는 KST 날짜 창으로 집계하므로, 해외 유저는 주차 경계에서 최대 1일 버킷 차이가 날 수 있습니다. 정확한 전역 KST 주차가 필요하면 instant 기반 원천이나 리그 전용 rollup이 필요합니다. MVP 범위에서는 감수하고 PR 본문에 명시했습니다.

검증은 PostgreSQL 16 Testcontainers 통합 테스트로 0초 유저 포함, occupation 필터, 합계 내림차순과 UUID 동률 규칙, 내 전역 순위, 정산 cursor 페이지, 그리고 위 1일 버킷 제한까지 케이스로 고정했습니다.

배포 직후에 대가도 치렀습니다. V14가 프로덕션에서 `constraint ... does not exist`로 실패하면서 CD가 멈췄습니다. 프로덕션은 Flyway 도입 전 레거시 스크립트로 만들어져 유니크 제약의 실제 이름이 베이스라인과 달랐기 때문입니다. #251에서 고정 이름 DROP을 제거하고 **유니크 제약 제거를 `arena_id` 컬럼 DROP에 위임**했습니다. PostgreSQL은 컬럼을 지우면 그 컬럼을 포함한 유니크 제약·인덱스를 이름과 무관하게 함께 제거합니다. 최종 스키마는 동일하고 제거 방식만 다릅니다.

## 멱등 재실행 — 신규 테이블 0개로 (#517 → #534)

재편 이후 정산 배치를 두 단계에 걸쳐 다시 손봤습니다.

**1단계(#517)**: 주간 정산이 전 유저 단일 트랜잭션이라, 정산 도중 커밋된 회원탈퇴 1건이 배치 전체 롤백으로 번졌습니다. 여기서 정산 경계를 유저 1명 단위로 쪼갰습니다. 탈퇴 레이스 4중 충돌(재조회 실패·지갑 삭제·행 락 점유·PII lost update)과 세 빈 분리, 배타 락 재조회의 내역은 [재화·정산 무결성의 돈 경로](/research/money-integrity)에 있습니다. 검증은 배치↔탈퇴 `CyclicBarrier` 동시 실행 테스트를 3회 반복 그린으로 확인했습니다.

이때 남은 트레이드오프는 PR 본문에 적어두고 넘겼습니다. anchor 선커밋 구조라 정산 루프가 크래시로 중단되면 재실행이 `BATCH_ALREADY_RUN`에 막힙니다. 지라 티켓으로도 남겼습니다.

**2단계(#534)**: 그 잔여를 풀었습니다. 기본 run은 anchor 가드에 막히고, 가드를 뚫으면 라이브 tier 재독으로 성공 유저가 **연쇄 승급(래칫)** 되거나 유니크 위반으로 전원 failed 집계됩니다. 돈 경로라 "재실행 시 중복 정산 불가능함을 증명하는 통합 테스트"를 완료 조건으로 먼저 못박았습니다.

완료 마커는 새로 만들지 않았습니다. `league_weekly_results`는 STAY도 INSERT하므로 **행의 존재 자체가 "그 주차 정산 완료"**를 의미하고, 유저·주차 UNIQUE 제약도 이미 있었습니다. 신규 테이블도, 마이그레이션도 0개입니다.

```text
settle(user, week)
  → 유저 행 배타 락 취득
  → (락 안에서) existsByUserIdAndWeekStartAt 재확인
      존재하면  → ALREADY_SETTLED 로 skip, mutation 0건
      없으면    → 정산 후 결과 행 INSERT
  → 유니크 제약은 최후 방어로 유지
```

락 안에서 재확인하기 때문에 동시 재실행에도 정확히 한 번만 정산됩니다. 반환형은 boolean에서 `SettleOutcome`(SETTLED / SKIPPED_WITHDRAWN / ALREADY_SETTLED)으로 바꿔 summary에 `alreadySettledMemberCount`를 신설했습니다. 기존 skipped가 뜻하던 "탈퇴"는 의미를 그대로 두었습니다.

진입점도 기존 계약을 건드리지 않는 쪽으로 만들었습니다.

- `rotateIfAbsent` 신설 — anchor 있으면 회전 skip, 없으면 회전. 기존 `rotate()`의 409 계약은 손대지 않아 스케줄러와 기존 run 경로는 무변경이고, 기존 재실행 테스트가 무수정으로 그린이었습니다
- 정산 루프는 페이지(100명)당 완료 마커를 일괄 선조회해 N+1을 피합니다. 판정의 **정본은 락 안 단건 재확인**이고, 선조회는 그 앞의 빠른 경로입니다
- 실패한 유저만 다시 돌리도록 선택적 `userIds` 표적 재실행을 지원합니다
- `POST /api/v1/league/batch/resume`은 프로파일 제한 + `X-Batch-Admin-Key` 상수시간 비교(`MessageDigest.isEqual`)
- 기존 `/league/batch/run`은 무키로 뒀습니다. anchor 409 가드 덕에 주차당 1회만 실효라 위험도가 다르고, 키를 소급하면 dev 운영 절차가 깨집니다. 이 판단을 테스트(`legacyRunStaysKeyless`)로 고정했습니다

증명은 실제 실패 경로를 유도해서 했습니다. 지갑 없는 유저를 만들어 승급 보너스 credit을 실패시킨 뒤, 1차 run에서 A 성공·B 실패 → 원인 복구 → resume. 확인한 것은 **A가 완전히 불변**(tier 래칫 없음·결과 1행·보너스 트랜잭션 1건)이고 B만 정산되며, 한 번 더 돌리면 전원 already로 변화가 없다는 것입니다. 전체 스위트는 1,379 tests / 0 failures로 끝났습니다.
