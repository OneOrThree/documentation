`@LoginUser` 리졸버를 등록하는 한 줄을 빠뜨리면 예외 없이 사칭 경로가 열립니다. 컨트롤러 76곳에 반복되던 `(UUID) getAttribute` 캐스팅을 어노테이션 하나로 접기 전에 스펙을 뽑아 보니, 66개 오퍼레이션이 `userId`를 required 쿼리 파라미터로 노출하고 있었습니다. 소셜 로그인 5종 분기와 스케줄러 12곳의 빈 `trace_id`도 배선(wiring)이라는 같은 자리에서 나온 문제였습니다.

## 파라미터는 스스로 채워지지 않는다 — 커스텀 리졸버

**어디서 나왔나**: `(UUID) request.getAttribute("userId")` 캐스팅이 컨트롤러 76곳에 반복되고 있었고, 이걸 `@LoginUser UUID userId` 한 줄로 바꾸는 티켓(GROMO-363)이 열렸습니다.

중복 제거로 열린 티켓이었지만, 착수 전에 springdoc 스펙을 뽑아 보고 실제 문제가 인가 부재라는 걸 알았습니다. 로그인한 사용자가 쿼리의 UUID만 바꾸면 남의 장비를 조회·장착할 수 있었습니다. userId를 얻는 경로가 제각각이라 일부 엔드포인트가 클라이언트가 준 값을 그대로 신뢰한 결과였습니다.

| 출처 | 예 | 안전한가 |
| --- | --- | --- |
| `getAttribute("userId")` | 대부분의 컨트롤러 | 예 — JWT에서 나옵니다 |
| `?userId=` 쿼리 파라미터 | 스펙상 66개 오퍼레이션 | 아니오 — 조작 가능 |
| 요청 바디의 `userId` | `POST /equipment/equip` | 아니오 — 조작 가능 |
| `@PathVariable UUID userId` | `GET /equipment/{userId}` 형태 | 아니오 — 남의 것 조회 가능 |

인증은 통과하지만 인가가 없는 상태였습니다. `@LoginUser`로 통일하면 "userId는 JWT에서만 온다"가 구조적으로 강제됩니다.

배선은 두 곳뿐입니다. 부팅 때 한 번 등록하고, 요청마다 값을 꺼냅니다. `JwtFilter`가 `setAttribute`하는 코드는 그대로 두고, 그 값을 누가 꺼내오는지만 바꿉니다.

```java
// 부팅 1회 — 리졸버 등록
@Override
public void addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers) {
    resolvers.add(loginUserArgumentResolver);
}
```

### 등록을 빠뜨리면 에러가 아니라 사칭이 됩니다

`HandlerMethodArgumentResolverComposite`는 목록을 위에서부터 훑고, 처음 `true`를 반환한 리졸버가 그 파라미터를 처리합니다. 커스텀 리졸버는 어노테이션 기반·타입 기반 다음, catch-all보다 앞에 꽂힙니다.

| 등록을 빠뜨린 뒤 | 무슨 일이 일어나나 |
| --- | --- |
| 쿼리 파라미터 없이 호출 | `userId = null` 주입 → 서비스단 NPE 또는 엉뚱한 전체 조회 |
| 쿼리에 남의 UUID를 실어 호출 | 그 값이 그대로 주입 → **막으려던 사칭 경로가 다시 열림** |

같은 이유로 `supportsParameter`에서 타입 검사를 하려던 초안을 리뷰에서 되돌렸습니다. `@LoginUser`가 붙었는데 타입이 `UUID`가 아닐 때 `false`를 반환하면 그 파라미터가 catch-all로 흘러가 `?userId=`로 바인딩되기 때문입니다. 그래서 어노테이션이 붙었으면 타입과 무관하게 claim하고, 타입 불일치와 attribute 부재는 `resolveArgument`에서 예외로 끊었습니다.

null일 때 401이 아니라 500인 이유도 경우의 수를 세어 정했습니다. 토큰이 없거나 틀린 경우는 필터가 이미 401로 끊어 리졸버까지 도달하지 못합니다. 남는 건 "필터를 안 타는 경로에 어노테이션을 붙였다"는 서버 배선 오류뿐이므로, 클라이언트에게 "인증하세요"라고 말하면 거짓말이 됩니다.

### 3건 통과가 3건 검증이 아니었던 이유

첫 치환 직후 컨트롤러 테스트 4건 중 3건이 통과하고 1건만 실패했습니다. "대체로 괜찮다"고 읽으면 안 되는 결과였습니다.

| 테스트 | 결과 | 이유 |
| --- | --- | --- |
| 저장 성공 → 204 | 실패 | 리졸버까지 도달해 `IllegalStateException` |
| 필수값 null → 400 | 통과 | 바디 검증에서 끊겨 리졸버가 아예 안 돎 |
| 음수값 → 400 | 통과 | 같음 |
| 시각 null → 400 | 통과 | 같음 |

파라미터는 선언 순서대로 resolve되므로, 첫 파라미터에서 400이 나면 두 번째 파라미터는 시도조차 되지 않습니다. 통과한 3건은 변경 지점에 닿지도 못한 테스트였습니다.

실패한 1건의 원인은 슬라이스의 비대칭이었습니다. `@WebMvcTest`는 `HandlerMethodArgumentResolver`와 `WebMvcConfigurer`를 화이트리스트로 싣지만, 이 프로젝트의 `JwtFilter`는 `@Component` 없이 `FilterConfig`(`@Configuration`) 안에서 등록됩니다. `@Configuration`은 화이트리스트에 없으니 필터가 안 실립니다. 읽는 쪽만 실리고 심는 쪽은 안 실린 상태, 즉 계약의 절반만 있는 슬라이스였습니다. 필터를 억지로 넣는 대신 요청 빌더의 `.requestAttr(...)`로 "필터가 한 일"을 테스트가 선언하게 고쳤고, 이왕 손대는 김에 `verify`의 첫 인자를 주입한 UUID로 좁혔습니다. 그전까지는 userId가 null이어도 통과하던 테스트였습니다.

도달하지 못한 테스트의 극단을 그날 하나 더 만났습니다. 전체 테스트가 초록으로 보였지만 Gradle이 태스크를 건너뛴 0건 실행이었습니다. 판별법은 `> Task :test`의 `UP-TO-DATE` 표시, `build/test-results` XML 개수, `cleanTest test` 강제 실행 셋입니다. 초록을 위조하는 나머지 종은 [커버리지의 착시](/research/testing-notes)에 모아 뒀습니다.

## yml 값은 누가 넣는가 — Binder와 env 변환 규칙

**어디서 나왔나**: 로그 아카이브 설정 클래스(GROMO-924)를 만들다가, 초기값이 없는 필드에 어떻게 값이 도착하는지를 설명할 수 없다는 걸 깨달았습니다.

필드에 값을 넣는 주체는 Binder, 통로는 setter, 시점은 기동 중 1회입니다.

```java
@Getter @Setter
@ConfigurationProperties(prefix = "s3.log")
public class S3LogConfig {
    private String region;   // Binder가 setRegion()을 호출해 채웁니다
}
```

첫 함정이 여기 있습니다. `@Setter`를 지우면 에러 없이 전부 null이 됩니다. Binder는 호출할 setter가 없는 필드를 그냥 건너뜁니다.

두 번째는 relaxed binding입니다. setter 하나에 케밥·카멜·스네이크 표기와 대문자 환경변수가 모두 매칭됩니다.

```text
s3.log.local-dir      ← yml 권장
s3.log.localDir
s3.log.local_dir
S3_LOG_LOCAL_DIR      ← 환경변수. 이 줄이 실무의 핵심
```

환경변수는 `.`과 `-`를 못 쓰기 때문에 Spring이 `_`를 변환해 줍니다. 그래서 `application.yml`이 gitignore라 배포 이미지에 없어도 환경변수만으로 설정을 채울 수 있습니다.

이 규칙을 어긴 적이 있습니다. FCM 푸시 파이프라인(GROMO-528)에서 `@Value` 키를 `fcm.service-account-json-base64`로 잡았는데, env 자동 변환은 `FCM_SERVICE_ACCOUNT_JSON_BASE64`를 기대합니다. 그런데 배포 파이프라인이 넘기는 이름은 `FCM_SERVICE_ACCOUNT_JSON`이었습니다. 중간의 `application.yml` 매핑이 그 차이를 메우고 있었는데, 그 파일은 gitignore라 이미지에 들어 있다는 보장이 없었습니다. 없으면 플레이스홀더가 해석되지 않아 기동이 실패합니다. 리뷰에서 지적받아 키 자체를 변환 규칙에 정렬(`fcm.service-account-json`)하고, 기본값 `:`을 붙여 미설정 시 플레이스홀더 crash 대신 생성자 검증 메시지가 보이게 고쳤습니다(PR #108).

세 번째는 우선순위입니다. 커맨드라인 인자 → OS 환경변수 → 프로파일별 yml → `application.yml` 순으로 위가 아래를 이깁니다. 운영에서 값어치가 큰 건 환경변수가 yml보다 위에 있다는 점입니다. yml에 값을 박아 넣어도 시크릿 하나 추가로 이미지 재빌드 없이 덮을 수 있습니다.

그래서 기본값을 어디에 둘지도 정해야 했습니다. 처음에는 자바 필드 초기값으로 뒀다가 지적받고 걷어냈습니다.

| | 필드 초기화 | `@DefaultValue` | yml 정본 |
| --- | --- | --- | --- |
| Spring이 기본값으로 인지 | 아니오 | 예 | — |
| 값이 사는 곳 | **두 곳** | 자바 | yml |
| yml 누락 시 | 조용히 기본값 | 조용히 기본값 | null → 곧 드러남 |

같은 값이 자바와 yml 두 곳에 사는 이중 장부는 한쪽만 고쳐도 아무 일이 안 일어나고, 어긋난 뒤에도 조용합니다. 교과서적 정답은 생성자 바인딩이지만 불변 객체로 구조가 바뀌어야 하고, 다른 설정 블록이 전부 프로파일마다 명시하는 관례였으므로 yml 정본을 택했습니다.

마지막 함정이 비대칭입니다. **스칼라는 교체지만 Map은 병합입니다.** Binder가 Map을 새로 만들지 않고 getter로 기존 Map을 꺼내 거기에 put하기 때문에, yml에서 항목을 지워도 자바 쪽 기본 항목이 살아남습니다. 그래서 Map 필드에는 빈 컬렉션만 둡니다. 널 가드 목적이고, 기본 항목을 담는 자리로는 쓰지 않습니다.

## 끄는 것과 안 만드는 것 — 조건부 등록과 생성자 fail-fast

**어디서 나왔나**: 같은 티켓에서 매일 새벽 로그를 S3로 올리는 아카이브 작업을 만들며 "S3 버킷이 설정되지 않은 local/ci에서도 앱이 떠야 한다"를 구현하다가, `@ConditionalOnProperty`가 정반대로 동작하는 걸 만났습니다.

```java
@ConditionalOnProperty(name = "s3.log.bucket")
```

읽을 때는 "버킷 값이 있으면 켠다"로 읽힙니다. 틀렸습니다. `havingValue`를 생략하면 판정 기준은 "키가 존재하고 값이 `false`가 아니냐"입니다. 그리고 우리 yml은 환경변수가 없으면 빈 문자열이 되는 `${S3_LOG_BUCKET:}` 형태였습니다. **빈 문자열도 "존재"입니다.** 그래서 시크릿을 넣지 않아도 빈이 뜨고, 하루 뒤 새벽에 빈 버킷 이름으로 업로드를 시도해 조용히 실패합니다.

`havingValue`는 특정 값과의 일치만 보므로 매번 달라지는 버킷 이름에는 쓸 수 없었습니다. 값 자체를 보려면 SpEL이 필요합니다.

```java
@ConditionalOnExpression("!'${s3.log.bucket:}'.trim().isEmpty()")
```

읽는 순서가 중요합니다. 플레이스홀더 치환이 SpEL 평가보다 먼저 일어나므로, 치환된 문자열이 SpEL 리터럴이 되도록 작은따옴표가 필수이고, 키가 아예 없을 때 치환이 실패하지 않도록 `:` 기본값도 필수입니다.

조건은 클래스마다 흩지 않고 `@Configuration` 한 곳에 걸었습니다. 조건이 거짓이면 프로퍼티 빈도, 무거운 클라이언트 객체도, 서비스 빈도 만들어지지 않습니다. 빈이 없으면 그 안의 `@Scheduled`도 함께 사라지는데, 이것이 `if`로 거르는 방식과의 결정적 차이입니다. 스케줄러 스레드가 매일 쓸데없이 깨지 않고, `if`를 빠뜨리는 실수 자체가 불가능해집니다.

부수 효과가 하나 더 있었습니다. 등록을 `@Bean` 메서드가 하니 서비스 클래스에 `@Service`를 붙일 필요가 없어졌고, 그러면 테스트에서 생성자로 직접 만들 수 있습니다. 컴포넌트 스캔에 걸리지 않으니 의도치 않게 다른 프로파일에서 살아나는 일도 없습니다. 조건 평가 결과는 `--debug` 기동의 CONDITIONS EVALUATION REPORT에서 확인했고, 컨텍스트를 통째로 띄우지 않는 `ApplicationContextRunner`로 "빈 문자열이면 빈이 없다"를 테스트로 못 박았습니다.

### 조건은 통과했는데 설정이 반쪽일 때

필드 기본값을 걷어냈더니 "버킷은 넣었는데 스트림 매핑을 빠뜨린" 반쪽 설정이 가능해졌습니다. 생성자에서 던져야 할까요? 코드베이스에 정반대 선례가 있었습니다. FCM 클라이언트는 같은 상황에서 예외를 던져 기동을 죽입니다.

| | FCM 발송 | 로그 아카이브 |
| --- | --- | --- |
| 성격 | 핵심 기능 | 부가 기능 |
| 없으면 | 알림 미발송 = 서비스 결함 | 장기 보관만 안 됨 |
| 기동을 죽여도 되나 | 예 — 배포 때 잡는 게 이득 | 아니오 — API 전체가 못 뜸 |
| 선택 | `throw IllegalStateException` | `log.warn` |

기준은 하나입니다. 핵심 기능이면 던지고, 부가 기능이면 WARN으로 드러냅니다. 둘 다 하지 않으면 조용한 무동작이 남습니다. 빈 컬렉션을 순회하면 예외 없이 아무 일도 안 일어나고, 운영자는 매일 잘 올라간다고 믿다가 몇 달 뒤 로그를 찾을 때 처음 알게 됩니다.

조건부 빈은 비활성일 때 로그가 아예 없으므로, 활성 로그 한 줄의 유무 자체가 판정 근거가 됩니다. 그 한 줄에는 상대경로 설정을 해석된 절대경로로 남깁니다. 설정에 적힌 `logs`만 찍으면 컨테이너에서 실제 어디인지 알 수 없지만, 절대경로로 찍으면 호스트 볼륨 바인딩이 제대로 걸렸는지 기동 로그만으로 확인됩니다. 반대로 자격증명은 어떤 형태로도 남기지 않습니다. "어떤 인증 체인이 선택됐는지"조차 힌트가 됩니다.

생성자에서 하지 않기로 정한 것도 둘 있습니다. 네트워크 검증은 최소권한 원칙과 충돌합니다. 업로드 권한만 부여한 IAM으로 버킷 존재 확인을 호출하면 권한이 없어 실패하고, 기동이 외부 네트워크에 의존하게 됩니다. 파일시스템 검증은 오탐이 됩니다. 기동 시점에는 로깅 프레임워크가 아직 파일을 만들지 않았을 수 있습니다. 원칙으로 정리하면 생성자는 내가 받은 것만 검사하고, 바깥 세계 상태는 사용 시점에 확인합니다.

### 같은 조건이 안 쓰는 스타터도 켠다

이 조건 어노테이션들을 이해하고 나서야 별개로 보였던 지적 하나가 같은 이야기로 읽혔습니다. 내가 조건식을 쓸 때 쓴 `@ConditionalOnClass`와 `@ConditionalOnMissingBean`이, 남이 쓴 자동설정 조건에도 그대로 적용되고 있었습니다. 스타터는 의존성 묶음이면서 자동설정 트리거입니다. 그래서 안 쓰는 스타터도 빈과 엔드포인트를 켜고 공격 표면을 넓힙니다. 빌드 스크립트에서 실제로 걸린 중복 선언과 사용 코드 0건인 스타터 사례는 [Spring Boot 4 마이그레이션](/research/springboot4-migration)에 있습니다.

원칙은 "사용 시점에 추가"로 정리했습니다. 다만 Gradle의 미사용 의존성 탐지 도구는 리플렉션과 자동설정으로 켜지는 것을 잡지 못하므로, 자동 탐지에만 의존할 수는 없습니다.

## 분기를 없애는 주입 — List로 받아 Map으로

**어디서 나왔나**: 소셜 로그인을 5종(카카오·애플·구글·라인·인스타그램)으로 확장하면서(GROMO-399, PR #52), provider가 늘 때마다 `AuthService`의 if/else를 고치는 구조를 없애야 했습니다.

여기서 오해 하나를 걷어냈습니다. `private final`은 주입과 무관합니다. `final`은 자바 문법일 뿐이고, 주입은 항상 생성자가 합니다. 평소 `@RequiredArgsConstructor`로 주입되던 것의 실체는 Lombok이 생성자를 만들고 Spring이 그 생성자를 호출한 것입니다.

Spring은 생성자 파라미터로 `List<인터페이스>`를 요구하면 그 인터페이스를 구현한 빈을 전부 모아 넣어줍니다. 그런데 저장하고 싶은 타입은 Map이었습니다.

| | 타입 |
| --- | --- |
| 저장할 필드 | `Map<Provider, SocialLoginClient>` |
| Spring이 줄 수 있는 것 | `List<SocialLoginClient>` |

`@RequiredArgsConstructor`는 필드 타입 그대로 1:1 대입 생성자를 만들기 때문에 Map을 통째로 주입하려 들고, 가공 단계가 들어갈 자리가 없습니다. 그래서 명시 생성자를 씁니다.

```java
private final Map<Provider, SocialLoginClient> clients;

public AuthService(List<SocialLoginClient> clientList /* 다른 의존성들 */) {
    this.clients = clientList.stream()
        .collect(Collectors.toMap(SocialLoginClient::provider, c -> c));
}
```

호출부에서는 분기가 사라집니다. provider를 키로 클라이언트를 찾아 바로 부릅니다. provider를 추가할 때 구현체 하나만 만들면 Map에 자동 등록되고 `AuthService`는 한 줄도 고치지 않습니다.

주의점은 둘입니다. Spring이 지원하는 `Map` 주입은 키가 빈 이름(String)으로 고정되므로 enum 키로는 만들 수 없습니다. 그래서 List로 받아 직접 변환합니다. 그리고 같은 키를 반환하는 구현체가 둘이면 `toMap`이 중복 키 예외로 터지는데, 의도치 않은 중복 빈을 기동 시점에 잡아 줘서 오히려 유용했습니다.

## 호출부가 모르게 감싸기 — AOP와 NoOp 어댑터

**어디서 나왔나**: 스케줄러 로그에 `trace_id`가 비어 있었습니다. 이 프로젝트에는 `@Async`가 0건이고 `@Scheduled`가 12곳(알림 10 · 리그 1 · 세션 정리 1)이었습니다. 버킷이 설정된 환경에서만 등록되는 로그 아카이브 스케줄러는 이 집계에서 빠져 있습니다. 스케줄러 메서드는 타이머가 부르므로 `TraceIdFilter`를 거치지 않습니다.

```text
[   ] [   ] ERROR 주간 리그 결과 알림 실패
[   ] [   ] ERROR   ↳ FCM 전송 실패        ← 위 실패의 일부인가, 다른 배치인가
[   ] [   ] ERROR 오늘 미집중 푸시 실패     ← 같은 시각 다른 배치와 뒤섞임
```

스케줄러 스레드에는 옮겨올 컨텍스트가 처음부터 없으므로, 유실을 막는 대신 새로 발급해야 합니다. 12곳에 같은 코드를 반복하는 대신 한 곳에서 감싸는 것이 AOP인데, 정리하다 보니 `@Transactional`이라는 이름으로 이미 쓰고 있었습니다.

| 용어 | 뜻 | 이 문제에서는 |
| --- | --- | --- |
| JoinPoint | 끼어들 수 **있는** 지점 | 모든 메서드 호출 |
| Pointcut | 그중 실제로 **고른** 지점 | `@Scheduled`가 붙은 것만 |
| Advice | 거기서 할 일 | MDC를 넣고 → 실행하고 → 지우기 |
| Aspect | 둘을 담은 클래스 | 스케줄러 MDC Aspect |
| Weaving | 실제로 끼워 넣는 과정 | 기동 시 프록시 생성 |

전후를 모두 잡아야 하므로 `@Around`입니다.

```java
@Around("@annotation(org.springframework.scheduling.annotation.Scheduled)")
public Object withMdc(ProceedingJoinPoint pjp) throws Throwable {
    MDC.put("trace_id", UUID.randomUUID().toString());
    MDC.put("job", pjp.getSignature().getName());
    try {
        return pjp.proceed();
    } finally {
        MDC.clear();   // 스케줄러 스레드도 재사용됩니다. 필수
    }
}
```

더 큰 소득은 프록시 방식이라서 생기는 제약을 이해한 것이었습니다. 주입받는 빈은 내 클래스를 상속·구현한 대역입니다. 그래서 **자기 호출(`this.method()`)에는 Advice가 걸리지 않고**, `private`·`final`·`static`에도 걸리지 않습니다. "같은 클래스 안에서 부르면 `@Transactional`이 안 걸린다"는 유명한 함정의 정체가 이것이고, `@Transactional`·`@Cacheable`·`@Retryable`이 전부 같은 프록시 위에서 도니 함정도 전부 공유합니다.

층을 고르는 기준도 같이 정리했습니다. Filter는 모든 HTTP 요청, Interceptor는 컨트롤러 호출, AOP는 임의의 메서드입니다. 스케줄러는 HTTP가 아니어서 앞의 둘이 닿지 않으므로 AOP가 유일한 답입니다. 적용 전 확인 목록도 남겼습니다. AOP 스타터 의존성 유무, 스케줄러 메서드가 `public`인지, 그리고 붙인 뒤 실제로 값이 찍히는지를 매번 확인합니다.

### 아무것도 안 하는 구현체를 왜 만드나

푸시 파이프라인(GROMO-528, PR #107)에서 발송 포트에 구현이 둘 생겼습니다. 실제 FCM 발송 클라이언트는 dev·staging·prod에, 로그만 찍고 성공을 반환하는 NoOp은 local·ci에 `@Profile`로 갈라 등록했습니다. 이유는 네 가지였습니다.

1. 환경 격리. 로컬 개발이나 CI 중 실제 유저 폰으로 푸시가 나가면 사고입니다.
2. 의존성 없이 기동. FCM 구현은 시크릿이 없으면 fail-fast로 죽으므로, NoOp이 없으면 로컬 개발자 전원이 키를 받아야 서버가 뜹니다.
3. 호출부 무지. 필터 체인은 자기가 FCM을 쓰는지 NoOp을 쓰는지 모르고, 그래서 환경 분기가 비즈니스 코드에 스며들지 않습니다.
4. null 체크 제거. 포트가 "항상 있되 안 할 수도 있는" 것이 되므로 호출부의 방어 코드가 사라집니다.

갈아끼우는 방법 셋 중 `@Profile`을 택한 근거는 환경이 곧 선택 기준이었기 때문입니다. `@ConditionalOnMissingBean`은 라이브러리가 기본값을 제공하는 방식이고, `@Primary`/`@Qualifier`는 런타임에 둘 다 필요할 때라 과했습니다. 다만 `@Profile` 게이팅은 어느 프로파일도 매칭되지 않으면 빈이 아예 없어 기동이 실패하므로, 프로파일 목록이 전체 환경을 커버하는지 전수로 확인해야 합니다.

이 패턴의 대가도 함께 적었습니다. NoOp이 꽂힌 환경에서는 발송하지 않았다는 흔적이 어디에도 남지 않습니다. "왜 푸시가 안 오지"를 한참 디버깅할 미래의 내가 있으므로, NoOp에 로그를 남기고 기동 시 활성 구현체를 찍는 관례가 필요합니다.

## 조각들이 같은 이야기였던 이유

모아 놓고 보니 조용한 실패가 여덟 가지였습니다.

- 리졸버 미등록 → catch-all이 쿼리값을 주입
- 슬라이스 비대칭 → 3건 통과는 변경 지점 미도달
- `@Setter` 삭제 → 전 필드 null
- 기본값 이중 장부(자바 · yml) → 한쪽만 고치면 무변화
- 빈 문자열이 조건 통과 → 새벽에 빈 버킷 업로드
- 반쪽 설정의 빈 컬렉션 순회 → 무동작
- 안 쓰는 스타터 → 빈과 엔드포인트 자동 활성
- NoOp 프로파일 → 미발송 흔적 없음

그래서 배선 작업의 기본기는 틀렸을 때 시끄럽게 만드는 쪽이었습니다. 리졸버는 attribute가 없으면 예외를 던지고, 조건부 빈은 활성 로그 한 줄로 존재를 알리고, 반쪽 설정은 어느 프로퍼티를 채워야 하는지까지 WARN에 적습니다. 이 세 가지가 없으면 배선 실수는 배포 뒤까지 살아남고, 다음 사람은 그 동작을 사양으로 읽습니다.
