## 1. "경고 100건"은 실제 개수가 아니라 천장이었다

GROMO-1626(#700) 에서 `./gradlew javadoc` 을 main 에서 처음 돌렸을 때 doclint 에러 5건을 고치고 "경고 100건 유지" 라고 PR 본문에 적었습니다. 그날 밤 `@param`·`@return` 이 하나도 안 채워져 있지 않느냐는 질문을 받고 `-private` 로 다시 돌렸더니 경고가 **정확히 100에서** 멈췄습니다. javadoc 의 `-Xmaxwarns` 기본값이 100 이고, 넘치는 경고는 세지 않고 버립니다. 제가 인용해 온 100건은 총량이 아니라 출력이 잘린 자리였습니다.

일주일 뒤 GROMO-1654 리팩토링 PR(#711) 안에서 같은 숫자를 근거로 "이 PR 에서 채운다" 는 선택지를 드렸고, 그 결정이 내려진 뒤에야 `-Xmaxwarns 10000` 으로 재측정했습니다.

| 경고 종류 | 건수 |
| --- | --- |
| `no @param` | 762 |
| `no comment` | 754 |
| `no @return` | 317 |
| **합계** | **1,833건 · 321파일** (main 470개 중 68%) |

단일 파일 최대는 `GroupChallengeBetSessionRepository` 115건, 25건 이상인 파일이 15개였습니다. **잘못된 전제 위에서 결정을 받았으니 다시 여쭤야 했습니다.** 1,833건은 리팩토링 PR 안에 파묻힐 규모가 아니었습니다. `no comment` 754건을 뜯어보니 doclint 가 `public` 요소를 전수 검사해 커진 숫자였습니다 — 메서드 310 · **enum 상수 200** · 클래스·인터페이스 선언 177 · 생성자 37 · 기타 30. 나머지 1,079건은 본문 산문은 있고 태그만 빠진 경우가 대부분이었습니다.

다시 받은 결정은 "enum 상수는 제외, 그 외는 전부" 였고 도메인별 서브에이전트 6개가 워크트리에서 나눠 채웠습니다(1,633건·321파일, 병합 충돌 0). `-Xmaxwarns 10000` 은 `build.gradle` 에 커밋(`c3c5d0589`)해 다음 사람이 같은 천장에 속지 않게 했습니다. 09-07 기준 남은 경고 98건은 전부 에러코드 enum 상수, 즉 의도된 제외이고 신규 0건입니다. PR 본문에는 이렇게 적었습니다 — **저장소 부채의 94.5% 가 도구에 가려져 있었다.**

<Callout label="숫자가 딱 떨어지면 의심한다" tone="warn">
경고·에러·결과 행이 100·1,000·10,000 같은 정확한 값에서 멈추면 그것은 측정값이 아니라 도구의 상한일 가능성이 큽니다. 상한을 풀고 한 번 더 세기 전에는 그 숫자로 결정을 받지 않습니다.
</Callout>

## 2. 패키지를 옮기자 `{@link}` 8건이 끊겼다 — CI 는 javadoc 을 돌리지 않는다

#711 의 배치 정리에서 같은 패키지에 있던 클래스들이 갈라졌습니다. 짧은 이름으로 걸려 있던 `{@link}` 가 전부 끊겼는데 `compileJava`·`checkstyleMain`·테스트 1,881개는 전부 초록이었습니다. Javadoc 참조는 컴파일러가 검사하지 않는 세 번째 참조 유형이고(첫째가 JPQL 문자열, 둘째가 설정 파일), `./gradlew javadoc` 을 돌려야만 드러나는데 **CI 는 이 태스크를 돌리지 않습니다.** 앞서 JPQL FQCN 은 제가 찾아 놓고 이건 이동 후 확인 목록에서 빠뜨렸습니다. 리뷰 지적을 받고서야 돌렸고 에러 8 → 0 으로 고쳤습니다(`984cb1b1b`).

해소 방법은 javadoc 전용 import 였습니다. 여기서 제 짐작 하나가 뒤집혔습니다. 08-25 #700 에서 `StatsService` 의 `{@link UserStreak}` 를 고칠 때는 "import 를 추가하면 Checkstyle 미사용 import 에 걸린다" 고 보고 FQN 링크로 피해 갔는데, 09-01 실험에서 **Checkstyle `UnusedImports` 는 Javadoc 안의 참조를 사용으로 친다**는 것을 확인했습니다. 걸릴 거라 짐작하고 우회한 것이었습니다.

#700 의 doclint 에러 5건도 같은 부류였습니다. main 에서 `./gradlew javadoc` 이 이미 실패하고 있었는데 CI 에 없어 아무도 몰랐습니다.

| 에러 | 건수 | 원인 |
| --- | --- | --- |
| `unknown tag` | 2 | Javadoc 안에서 줄 앞의 `@EnableScheduling` 은 애노테이션이 아니라 태그로 파싱됨 |
| `malformed HTML` | 1 | 부등식의 맨 `<` 가 HTML 여는 태그로 읽힘 |
| `reference not found` | 2 | Lombok `@Getter` 가 만드는 게터는 소스에 없어 `{@link X#getY()}` 가 영영 안 풀림 · 미import 클래스 |

Lombok 건은 앞으로도 반복됩니다. 이 저장소에서 `{@link X#getY()}` 형태는 전부 깨집니다.

## 3. 인터페이스로 옮긴 `@Parameter` 는 스펙에서 사라진다

GROMO-1621(#696) 은 컨트롤러 30개 3,397줄 중 `@Operation` 133개·`@ApiResponse` 371줄을 `<domain>/api/docs/XxxControllerDocs` 인터페이스로 분리한 리팩토링입니다. 엔드포인트 2개 이상인 22개만 옮기고 단일 엔드포인트 8개는 껍데기가 본문보다 길어져 제외했습니다. 증명은 산출물로 했습니다 — `generateOpenApiDocs` 로 뜬 `openapi.json` 을 `jq -S` 로 정규화해 전후 **MD5 동일**(`ci` 프로파일 paths 110·operations 128, `@Profile` 게이팅된 배치 엔드포인트 5개는 `ci,local` 로 한 번 더). 이관 메서드에는 전부 `@Override` 를 붙였습니다. 시그니처가 어긋나면 오버라이드가 아니라 새 메서드가 되고 그 엔드포인트의 문서만 조용히 사라지는데, `@Override` 가 그 실수를 컴파일 에러로 바꿉니다.

그 PR 본문에 제가 직접 적은 규칙이 있었습니다 — **`@Parameter` 는 컨트롤러에 남긴다. 자바는 파라미터 애노테이션을 상속하지 않아 인터페이스에 붙이면 Springdoc 이 못 읽는다.** `UserController.checkNickname`·`LeagueBatchController.resumeWeeklyBatch` 2곳이 그래서 구현체에 남았습니다.

일주일 뒤 #711 에서 나머지 8개 컨트롤러를 마저 분리하면서 저는 이 `@Parameter` 3건을 "1621 때 빠뜨린 것" 으로 읽고 인터페이스로 옮겼습니다. codex 가 잡았고, 세 갈래로 확인했습니다. ① `UserControllerDocs`·`LeagueBatchControllerDocs` 의 클래스 Javadoc 에 제약이 이미 적혀 있었고 저는 그 주석을 그대로 둔 채 애노테이션만 옮겼습니다. ② 기존 22개 인터페이스에 `@Parameter` 는 0개 — 빠뜨린 게 아니라 의도였습니다. ③ Springdoc 은 구체 `HandlerMethod` 의 `getParameterAnnotations()` 를 읽습니다. 되돌렸습니다(`4d8f7b8ae`). 컴파일도 기동도 통과하고 스펙 항목 하나가 빠질 뿐이라, 이런 회귀는 산출물을 전후 대조하지 않으면 잡히지 않습니다.

## 4. 디렉토리 개편 #708 — rename 이 아니라 문자열 경로였다

GROMO-1638 은 `back/` → `server/data-api/`, `app/` → `app/app-dev/` 로 옮기는 개편입니다. git 은 워크플로 8종의 rename 을 정상 감지했고(`ci.yml→dev-ci.yml` 88%, `cd.yml→dev-cd.yml` 95%), 충돌은 rename 때문이 아니라 그 사이 main 에 들어간 #698(GROMO-1622) 이 같은 두 파일의 **내용을 재설계**했기 때문이었습니다 — `cd.yml` 을 트리거 없는 `workflow_call` 전용으로, CI 가 main push 에서 이미지를 빌드해 digest 를 CD 에 넘기는 구조로. 한쪽은 rename+경로 수정, 다른 쪽은 같은 자리 대수술이라 3-way 머지가 손을 들었고, #698 을 정본으로 삼아 개편 델타를 그 위에 얹었습니다.

후속 커밋 42파일로 경로를 현행화하고 Lint·Test 가 초록이 된 뒤에도 리뷰가 다섯 곳을 더 건졌습니다. 전부 **컴파일러도 테스트도 보지 않는 문자열** 안에 있었습니다.

| 지적 | 어디 | 놓친 이유 |
| --- | --- | --- |
| compose S3 업로드가 루트의 `docker-compose.prod.yml` 참조 — release 후 첫 prod 배포가 이 스텝에서 죽음 | `prod-cd.yml:74` | prod-cd 를 "compose 미참조" 로 잘못 분류 |
| `cache-dependency-path` 한 줄 미갱신 → setup-node 실패 | `app-android-build.yml` | 따옴표 경로만 일괄 치환 |
| `docker build ../back` · `seed.sh` 마이그레이션 경로 — 하네스 전멸 | `loadtest/Makefile` | "loadtest 는 개편 대상 아님" 으로 넘김 |
| `RNReanimated` 4.5.3 → 4.5.0 이 lock 에만 (package.json 은 4.5.3, hermes 체크섬 불일치) | `Podfile.lock` | 개편 커밋에 제 로컬의 낡은 pod 상태가 딸려 들어감 |
| 추적 중인 `app/app-dev/.claude/` 를 `.claude/*` 규칙이 잘못 겨냥 | `app/.gitignore` | 계층별 gitignore 중복 |

Podfile.lock 은 `pod install` 을 다시 돌리는 대신 개편 직전 원본으로 통째 복원해 main 과 바이트 동일한 rename 순수 상태로 되돌렸습니다(`fac534e15`). 팀원 머신에서 JS 4.5.3/네이티브 4.5.0 혼합 빌드가 날 뻔한 자리였습니다. 브랜치 훅 변경은 거절(푸시 전 `ls-remote` 이중 가드로 오탐 창이 없음), env 템플릿 복원은 보류했습니다.

Lint 실패 1건은 반대로 **우리 변경이 아니라고** 판정했습니다. ESLint 가 아니라 jest `UsageDetailScreen.test.tsx:74` 가 5초 타임아웃, 나머지 2,358개 통과(188 스위트 중 1 실패). 이 파일은 rename 만 됐고 main 에서 초록이던 테스트이며, 실패 시각에 같은 VM(러너 슬롯 3개 공유)에서 backend checkstyle·spotbugs 가 동시에 돌고 있었습니다. 재실행으로 초록을 확인했고, 재발하면 타임아웃 보정은 별도 대응으로 남겼습니다. 마지막 체크가 의미가 컸습니다 — #698 병합 후 처음 돈 빌드 잡이 `./server/data-api` 컨텍스트로 통과해 워크플로 재배선이 PR 단계에서 실증됐습니다.

## 5. Apidog 동기화 — exit 0 인데 반영 0

`Generate OpenAPI Docs` 워크플로가 7분 뒤 빨개졌습니다(08-25 14:16). 원인은 `openapi.json`(약 251 KB) 을 `jq --argjson` 의 **셸 인자**로 넘긴 것이었습니다. 리눅스의 개별 인자 상한 `MAX_ARG_STRLEN` 은 131,072 B 이고 스펙은 그 196% 라 `Argument list too long` 이 찍히고 **빈 바디**가 POST 됐습니다. 그런데 Apidog 는 빈 요청에 HTTP 200 과 `createCount:0` 을 돌려줬고 `curl --fail` 은 4xx 가 아니면 통과합니다. 그래서 스텝은 초록이었고, **최소 2026-08-14 이후 스펙이 한 번도 반영되지 않았습니다.** 08-25 에 처음 빨개진 것은 코드가 바뀌어서가 아니라 Apidog 가 빈 입력에 422 를 주기 시작했기 때문입니다. macOS 는 인자 상한이 훨씬 커서 로컬에서는 재현되지 않았습니다.

GROMO-1623(#697) 에서 jq·curl 양쪽을 파일 경유로 바꾸고(`--slurpfile`, `--data @file` — 생성된 payload 162,858 B 도 같은 상한에 걸립니다) 판정을 `apidog-import.sh` 로 분리해 관문 3개를 세웠습니다: payload 최소 10 KB · HTTP 400 미만 · 응답 `success == true` + `errorCount == 0`. 리뷰에서 직전 버전이 exit 0 으로 통과했음을 재확인했습니다.

머지 직후 main 런에서 관문 ③ 이 **실물 정상 응답을 막았습니다.** 엔드포인트 14 생성·38 수정, 스키마 23 생성·26 수정, 전 항목 `Failed:0` — 11일 만에 처음 반영된 응답이었는데 exit 1 이 났고, `set -e` 로 스텝이 죽으면서 뒤의 동기화 2건이 스킵됐습니다. 원인은 픽스처의 출처였습니다. 관문을 짤 때 쓴 응답 형태(`success:true`, `errorCount` × 33)는 08-19 로그에서 떠 온 것인데 **그때 우리가 보낸 건 빈 바디**였습니다. 정상 요청의 응답은 `data.counters` 평면에 `*Failed` × 6 이고 `success` 필드 자체가 없었습니다. 목 서버 케이스 10개가 전부 통과하고도 실물에서 틀린 이유는 지어낸 형태로만 검증했기 때문입니다. 메모리에 남긴 한 줄이 그대로 교훈입니다 — **깨진 경로에서 딴 픽스처는 무가치하다.**

GROMO-1625(#699) 는 두 스키마를 모두 이해하되 **인정은 좁게, 추출은 넓게** 로 짰습니다. 인정이 헐거우면 모르는 응답이 성공으로 통과해 관문이 열리고, 추출이 헐거우면 0 이어야 할 카운터가 늘 뿐 열리지는 않습니다. 리뷰 2라운드에서 고치는 과정에 낸 반대 방향 구멍 5개를 닫았는데, 그중 하나가 **빈 응답 바디**였습니다 — 이 스크립트의 존재 이유가 빈 바디를 막는 것인데 정작 빈 응답에는 열려 있었습니다. 픽스처는 워크플로 로그의 실물 응답(런 `32813844074`·`32203467444`)을 그대로 떠 왔고, 로그 시점 11 케이스에서 최종 24 케이스로 늘렸으며, 되돌린 스크립트에서 새 케이스 7건이 정확히 실패하는 것까지 확인했습니다. 남는 리스크는 한 줄입니다 — 응답 스키마가 또 바뀌면 CI 는 못 잡고 런이 빨개지는 것으로 알게 되지만, 방향이 fail-closed 라 조용히 통과하지는 않습니다.

곁가지 하나. 이 워크플로는 `push` 이벤트라 워크플로 파일을 **푸시된 브랜치에서** 읽습니다. #699 이전(`f77c4fee`)에서 갈라진 `bfix/GROMO-1626-javadoc-build` 는 구형 관문을 그대로 들고 실패했습니다(런 `32818405396`). 관문을 고쳐도 rebase 하지 않은 브랜치는 옛 관문으로 돕니다.

## 6. 빨라진 테스트를 의심하라

테스트 컨텍스트를 하나로 합치던 08-01 새벽, 전체 스위트가 **12초**에 끝났습니다. 성능 개선이 아니었습니다. 141개만 돌고 77개 실패, Testcontainers 컨테이너 0개 — 컨테이너 기반 테스트에 도달조차 못 한 것입니다. `NoClassDefFoundError` 가 프로덕션 클래스 전반에 나고 Spring 이 `ClassPathResource` 를 못 찾았는데, 제가 중간에 죽인 Gradle 실행이 데몬 3개를 어중간하게 남겨 산출물이 반만 만들어진 상태였습니다. `./gradlew --stop` 으로 데몬을 전부 내리고 `rm -rf build` 뒤 다시 돌렸습니다.

같은 결의 사례가 그 전에 넷 있었습니다.

| 날짜 | 초록의 모양 | 실제 | 조치 |
| --- | --- | --- | --- |
| 07-13 | `BUILD SUCCESSFUL` 16초 | `test` 가 UP-TO-DATE 로 스킵됐을 가능성 | 총 개수 확인 |
| 07-31 | 리뷰 반영 후 테스트 통과 | UP-TO-DATE 스킵으로 **오래된 결과**가 남아 있었음 | `--rerun-tasks` |
| 07-15 | 로컬 `/back-check` 통과, CI `test` PASS(2m49s) | CI 의 checkstyle·spotbugs·generate-docs 가 2~3초 만에 FAIL — 로컬에서 `checkstyleTest` 가 SKIP 이라 테스트 파일 위반을 못 잡음 | 로컬 게이트에 `checkstyleTest` 포함 |
| 07-15 · 07-19 | 테스트 실패 63건 | `DockerClientProviderStrategy`/`ExceptionInInitializerError` — Docker 미기동, 코드 무결 | Docker 기동 후 재실행 |

UP-TO-DATE 는 [테스트 전략 노트](/research/testing-notes)의 "거짓 초록 다섯 종" 표에 이미 있어 여기서는 사례만 보탭니다. 반대 방향도 있습니다 — 09-01 PR #711 의 CI 세 잡이 **8초** 만에 빨개졌는데 코드가 아니라 셀프호스티드 러너 `gromo-dev-build` 의 디스크가 찬 것이었습니다(`No space left on device`). 너무 빠른 초록도, 너무 빠른 빨강도 결과가 아니라 환경입니다.

## 7. JPQL 문자열 안의 FQCN 39건

#711 착수 직전 HEAD 가 기동조차 안 됐던 이유는 엔티티 이동 후 `@Query` JPQL 문자열 안의 FQCN 39건이 옛 경로로 남아서였고, 테스트 1,881개 중 434개가 연쇄로 무너졌습니다. [리팩토링 에픽 노트 §0](/research/backend-layering-refactor) 에 적어 두었으므로 여기서는 목록의 첫 줄로만 둡니다.

## 컴파일러·CI 가 안 보는 자리

일곱 사례를 자리별로 접으면 이렇습니다. 오른쪽 열이 실제로 잡아 준 검사입니다.

| 자리 | 사례 | 잡는 검사 |
| --- | --- | --- |
| `@Query` JPQL 문자열의 FQCN·enum 리터럴 | 39건, 기동 실패 | ApplicationContext 로딩 테스트, 이동 후 옛 경로 grep |
| Javadoc `{@link}`·doclint | 8건 + 5건, CI 에 태스크 없음 | `./gradlew javadoc` — 로컬 게이트에 포함, `-Xmaxwarns` 상한 해제 |
| 파라미터 애노테이션 상속 | `@Parameter` 3건 스펙 증발 | OpenAPI 산출물 전후 `jq -S` + md5 대조 |
| 워크플로·Makefile·스크립트의 문자열 경로 | `prod-cd.yml` S3 경로, `docker build ../back`, `cache-dependency-path` | 리뷰의 전수 grep, 첫 실배포 |
| lock 파일 | `Podfile.lock` 4.5.3→4.5.0 | main 과 바이트 대조 |
| 픽스처의 출처 | 빈 바디 시절 응답으로 짠 관문 | 실물 로그에서 뜬 픽스처, 되돌린 코드에서 실패 확인 |
| 빌드 산출물의 상태 | 데몬이 남긴 반쪽 클래스, UP-TO-DATE 캐시 | 컨테이너 수·총 테스트 수 확인, `--rerun-tasks`, `--stop` |

`logback-spring.xml` 의 `converterClass`, `@Value`, `@ComponentScan(basePackages)`, `application-*.yml` 도 같은 부류이며 [팀 규약](/spec/conventions)의 "패키지를 옮길 때 컴파일러가 안 잡는 곳" 절에 목록으로 있습니다. 이 노트는 그 목록의 근거 사례입니다.

## 초록을 의심하는 신호 셋

1. **너무 빠르다.** 12초 스위트, 16초 `BUILD SUCCESSFUL`, 8초 CI 실패. 결과가 아니라 환경입니다. 컨테이너 수와 총 테스트 수를 함께 봅니다.
2. **숫자가 딱 떨어진다.** 경고 정확히 100건. 도구의 상한부터 확인합니다. `-Xmaxwarns`, `--max-warnings`, 페이지 크기.
3. **exit 0 인데 결과가 없다.** `createCount:0` 이 11일째, Swagger UI 의 `paths: {}`. 성공의 증거를 종료 코드가 아니라 **반영 건수·산출물 diff** 에서 찾습니다. 그리고 그 판정이 모르는 응답을 만나면 열리지 않고 닫히는지(fail-closed) 되돌려 확인합니다.
