## 링크는 있었지만 착지할 곳이 없었습니다

초대 링크를 카톡에서 누르면 `oneorthree.github.io/phone/join.html` 의 GitHub Pages 404가 떴습니다. 그 페이지는 한 번도 만들어진 적이 없습니다. 발급·랜딩·deferred 매치·claim·AASA 다섯 구간이 통째로 비어 있었고, 이 다섯을 병렬로 새로 만들었습니다. 서버 쪽은 신규 테스트 49건으로 검증했습니다. 그룹 실기능 전환(#382)에서 앱이 링크 문자열을 로컬에서 조립하고 랜딩은 빈칸으로 남아 있던 결과입니다([그룹, Fakedoor에서 실기능까지](/research/group-fakedoor)).

| 구간 | 없던 것 |
| --- | --- |
| 발급 | 서버가 슬러그를 발급하는 API. 앱이 링크를 직접 조립하고 있었습니다 |
| 랜딩 | 링크가 실제로 착지하는 HTML |
| deferred 매치 | 앱이 없는 사람이 설치한 뒤 "무슨 초대였는지" 되살리는 경로 |
| claim | 되살린 초대를 가입한 유저에게 붙이는 어트리뷰션 |
| AASA | Universal Links가 앱으로 넘어가려면 필요한 도메인 연결 파일 |

이 다섯 구간을 워크스트림 4개로 쪼개 병렬로 갔고, 백엔드 코어(#412)가 나머지가 붙을 **계약과 스키마를 먼저 동결**하는 순서를 택했습니다. 앱(#413)과 GA4 어트리뷰션(#410)과 프로덕션 랜딩(#411)이 그 계약 위에 각각 올라왔습니다.

## 계약을 먼저 고정했습니다

코어 PR에서는 코드보다 표를 먼저 썼습니다. 엔드포인트 5종의 인증 여부와 응답 규칙을 못박고, 그 표를 나머지 워크스트림 3개에 배포했습니다.

| 엔드포인트 | 인증 | 규칙 |
| --- | --- | --- |
| `POST /api/v1/groups/{groupId}/invite-link` | JWT | (그룹, 초대자)당 1링크 멱등 재사용. 비멤버 403, 없는 그룹 404 |
| `GET /l/{slug}` | 무인증 | **항상 200 HTML.** 만료·미존재·그룹 삭제도 200 만료 변형(302 금지) |
| `POST /l/match` | 무인증 | 매칭 실패도 200 |
| `POST /api/v1/invite-links/claim` | JWT | 멱등 no-op, 없는 슬러그만 404 |
| `GET /.well-known/apple-app-site-association` | 무인증 | JSON 상수, 리다이렉트 없음 |

무인증 경로가 필요했는데, 우리 백엔드는 이걸 화이트리스트 문자열로 처리하지 않아도 됐습니다. `JwtFilter` 와 `TraceIdFilter` 가 `addUrlPatterns("/api/*")` 로만 등록돼 있어서, `/l/*` 과 `/.well-known/*` 은 애초에 필터 밖입니다. 인증 화이트리스트는 항목이 늘 때마다 구멍이 생기는 자리라, 경로 접두어 자체로 갈라지는 편이 훨씬 안전했습니다.

랜딩이 절대 302를 내지 않고 항상 200을 주는 것도 계약으로 박았습니다. 만료된 링크에 302를 주면 카톡 스크레이퍼가 미리보기를 못 만들고, 유저는 왜 아무 일도 안 일어나는지 알 수 없습니다. 클릭 기록과 GA4 전송 실패는 `try/catch` 로 격리해, 부가 기능이 화면 노출을 막지 못하게 했습니다.

## 미설치 유저 복원 — 지문과 SKIP LOCKED

가장 어려운 조각은 세 번째였습니다. 앱이 깔려 있으면 Universal Links가 슬러그를 그대로 넘겨주지만, 앱이 없으면 스토어를 다녀오는 사이에 어떤 초대였는지가 사라집니다. 서버가 붙일 수 있는 단서는 클릭 시점의 흔적뿐이라, 클릭을 지문으로 남겼습니다.

```text
invite_link_clicks
  link_id, ip_hash, os, user_agent, clicked_at,
  matched / matched_at / matched_device_id / app_instance_id,
  claimed_user_id / claimed_at

  idx_invite_clicks_match  (ip_hash, os, clicked_at DESC) WHERE matched = FALSE
  idx_invite_clicks_device (matched_device_id, matched_at DESC) WHERE matched = TRUE
```

원본 IP는 어떤 컬럼·로그·이벤트 파라미터에도 남기지 않고 `SHA-256(ip + LINK_IP_SALT)` 의 hex만 저장했습니다. IPv4 주소 공간은 40억 개 남짓이라 salt 없는 해시는 전수 계산으로 되돌릴 수 있습니다. prod는 이 salt를 Secrets Manager에서 필수 주입받고, 미설정이면 기동을 실패합니다.

설치 후 첫 실행에서 앱이 `POST /l/match` 를 때리면, 서버는 같은 지문의 미소진 클릭을 최신순으로 하나 골라 원자적으로 소진합니다. 여기서 락 힌트 하나가 결정적이었습니다.

```sql
-- 실제 생성된 SQL (Hibernate)
... order by clicked_at desc
    fetch first ? rows only
    for no key update of ilc1_0 skip locked
```

락을 걸지 않으면 동시 요청 둘이 한 클릭을 같이 소진해 **한 클릭이 두 기기에 매치**됩니다. 그건 `PESSIMISTIC_WRITE` 가 막습니다. `SKIP LOCKED` 를 굳이 붙인 이유는 그것과 별개였습니다. PostgreSQL은 `FOR UPDATE` 와 `LIMIT` 을 함께 쓸 때, 잠금이 풀린 뒤 조건에서 탈락한 행을 만나면 **다음 후보를 다시 찾지 않고 빈 결과를 돌려줍니다**. 공유 Wi-Fi처럼 같은 지문의 후보가 여러 개 쌓인 상황이 정확히 그 조건이고, 그때 매칭은 조용히 실패합니다. `SKIP LOCKED` 가 없으면 후보가 많을수록 복원이 더 안 되는, 직관과 반대되는 동작이 됩니다.

이 매칭은 근본적으로 **확률적**입니다. 지문이 IP 해시와 OS와 시간창이므로 같은 카페의 다른 사람이 겹칠 수 있습니다. 그래서 매치가 성공해도 자동 가입은 하지 않고, 앱이 초대 시트를 띄워 그룹명을 보여준 뒤 유저가 확인해야 참여가 일어납니다. 정확도가 100%가 아닌 신호로는 계정 상태를 바꾸지 않기로 정했습니다.

같은 원칙으로 나머지 경계도 정리했습니다.

- **claim은 최초 1회 + 셀프 초대 제외** — 뒤늦은 다른 유저가 앞사람을 덮으면 어트리뷰션이 뒤집힙니다. 후보 조회도 매치와 같은 `PESSIMISTIC_WRITE` + `SKIP LOCKED` 라 동시 claim의 lost update가 구조적으로 막힙니다.
- 매치는 재시도에 멱등합니다. 응답이 유실돼 앱이 재시도해도 같은 기기의 창 내 기존 매치를 재반환하고, 클릭을 추가로 소진하지 않습니다.
- **봇은 클릭으로 세지 않습니다** — 카톡에 링크를 붙이면 사람보다 스크레이퍼가 먼저 랜딩을 때립니다. 이걸 클릭으로 남기면 수치가 부풀 뿐 아니라, 스크레이퍼 IP의 미소진 클릭이 매치 후보가 돼 엉뚱한 설치에 붙습니다. 반대로 카톡 인앱브라우저는 주 유입 경로라 봇으로 걸러선 안 됩니다. 이 구분을 UA 분류에 넣었습니다.
- **종료된 그룹은 만료로 취급** — 마지막 멤버가 나가면 그룹은 삭제되지 않고 `status=ENDED` 로만 전이합니다. 발급·랜딩·매치 세 곳이 `deletedAt` 과 `ENDED` 를 같은 기준으로 보게 맞췄습니다.

검증은 통합 31건 + 단위 18건 = 신규 49건입니다. 그중 두 개가 코어 PR(#412)의 핵심 주장이었습니다. **동시 매치 2건 중 정확히 1건만 성공**, **동시 claim 중 정확히 1명만 기록**.

마이그레이션 검증에는 함정이 하나 더 있었습니다. `ci` 프로파일은 `flyway.enabled: false` + `ddl-auto: create-drop` 이라 **CI는 이 SQL을 한 번도 실행하지 않습니다**(스키마를 엔티티에서 만듭니다). 그래서 `postgres:16-alpine` 컨테이너에 V1부터 순서대로 직접 적용하고 `\d` 로 부분 인덱스·유니크·FK 생성을 대조했습니다. 그럼에도 dev 기동이 이 SQL의 첫 실전 검증이라는 사실은 주의사항에 그대로 적어 뒀습니다. 병렬 워크스트림의 부수 비용도 여기서 나왔습니다. Flyway 버전 번호가 다른 PR과 겹쳐 V20에서 V21로 개번했습니다.

## 카톡 인앱브라우저에서 왕복 1회

랜딩(#411)의 성능 목표는 카톡 인앱브라우저에서 왕복 1회로 끝내는 것 하나였습니다. 인앱브라우저는 캐시도 네트워크도 기대할 수 없고, 초대 링크를 누른 사람은 앱을 아직 모르는 사람이라 첫 화면이 늦으면 그대로 이탈합니다.

그래서 사람이 받는 경로는 HTML 한 장으로 끝냅니다. OG 이미지는 스크레이퍼만 따로 가져갑니다.

| 항목 | 값 |
| --- | --- |
| 외부 CDN·웹폰트 요청 | 0회 |
| 빌드 도구 | 없음 (순수 HTML/CSS/JS) |
| CSS | 전량 인라인, 18.3KB 비압축 |
| 폰트 | `-apple-system` 계열만 |
| 기준 뷰포트 | 390px |

파일을 나누면 인앱브라우저에서 요청이 한 번 더 늘어서, 18.3KB를 한 응답에 실었습니다.

만료 변형은 처음에 JS로 분기하려 했는데, JS가 막힌 환경과 스크레이퍼에서 만료 화면이 다르게 나왔습니다. 그래서 서버가 `data-expired` 속성을 한 번만 심고 CSS 속성 선택자로만 분기하도록 바꿨고, JS에는 "점프" 한 가지만 남겼습니다.

이스케이프에서도 경계가 갈렸습니다. 치환 토큰 네 개가 전부 **속성 컨텍스트**에 들어갑니다. 그룹명은 `content="..."` 안에, 스킴과 스토어 URL은 `href="..."` 안에 놓입니다. 텍스트 전용 이스케이프로는 따옴표 하나에 속성이 닫히고 임의 속성이 주입됩니다. 파싱 시점 주입은 클라이언트에서 되돌릴 수 없으므로 서버에서 막아야 하고, 템플릿은 방어 가능한 범위만 맡았습니다.

- 점프 전에 스킴을 화이트리스트로 검사 — `javascript:` 와 `data:` 자동 실행 차단
- 검증 실패한 CTA는 `href` 를 제거하고 `aria-disabled` — 눌러도 실행되지 않음
- 스토어 링크가 `http(s)` 가 아니면 링크 자체를 무력화

검증은 브라우저를 띄우지 않고도 할 수 있는 만큼 했습니다. 치환 토큰을 `grep` 으로 세어 계약 외 토큰 0건을 확인하고, 인라인 스크립트를 최소 DOM 스텁 위에서 실제로 실행해 상태 머신 12종(정상 점프 / 1.5초 폴백 / 스토어 탭 복귀 / 타임아웃 후 수동 탭 / 만료 / 스킴 미치환 등)을 전수 통과시켰습니다. 그리고 390×844 뷰포트에서 네 가지 상태를 스크린샷으로 찍고, OG 이미지는 카톡의 정사각 크롭과 가로형 축소본에서 판독되는지 따로 확인했습니다.

정적 리소스 경로는 플랜에 `/static/link/og-invite.png` 로 적혀 있었습니다. Spring Boot 기본값에서 `classpath:/static/link/x.png` 는 **`/link/x.png` 로 서빙되고 `/static/...` 은 404입니다.** OG 이미지는 스크레이퍼가 읽어야 해서 절대 URL이 필수인데, 플랜의 경로를 그대로 뒀다면 미리보기가 빈 채로 나갔을 것입니다.

## 실기기로 써 보고 자동 점프를 걷어냈습니다

여기까지는 전부 스펙대로 만들었습니다. 그런데 실기기로 직접 써 보고 스펙이 틀렸다고 판단했습니다.

랜딩은 로드 즉시 커스텀 스킴으로 자동 점프했습니다. 기술적으로는 최단 경로라, 앱이 있으면 한 박자도 안 기다리고 앱이 열립니다. 실사용 확인에서 나온 피드백은 정반대였습니다. 어느 그룹의 초대인지 확인할 틈도 없이 화면이 넘어간다는 것이었습니다.

초대 링크의 가치는 "누가 나를 어디로 부르는지"를 아는 데 있습니다. 자동 점프가 걸린 화면에서 유저는 그룹명을 읽을 틈이 없었습니다. #453에서 자동 점프를 제거하고, 점프는 그룹명을 확인한 뒤 '앱에서 열기'를 탭했을 때만 시작하도록 바꿨습니다.

구현은 상태 하나를 뒤집는 일이었습니다. `settled` 초기값을 `true`(감지 주기 없음)로 두고, 탭이 발생한 시점에 1.5초 무이탈 감지를 걸어 미설치를 판정하고 스토어 CTA를 승격합니다. 미설치 판정 후 재탭도 같은 주기로 다시 판정하고, 스토어를 다녀온 bfcache 복원 폴백은 그대로 남겼습니다.

같은 PR에서 dev 미리보기 이미지가 안 뜨는 문제도 잡았습니다. `og:image` 가 prod 도메인으로 **하드코딩**돼 있어서, dev에서 발급한 링크의 미리보기가 아직 배포되지 않은 prod 이미지(404)를 가리켰습니다. 절대 URL은 설정값으로도 조립할 수 있어서, `link.base-url` 기반 치환 변수로 교체해 환경별로 자기 도메인의 절대 URL을 만들게 했습니다.

## 전 프로파일이 플레이스홀더였습니다

마지막 발견(#465)이 가장 뼈아팠습니다. 미설치 유저가 'App Store에서 받기'를 누르면 스토어가 아니라 **"현재 국가나 지역에서 사용할 수 없는 앱"** 이 떴습니다.

코드는 정상이었습니다. `link.store-ios-url` 의 값이 dev·prod·loadtest·ci·local 예시까지 **전 프로파일에서 `id0000000000` 플레이스홀더**였습니다. 코어 PR을 쓸 때 App Store 숫자 ID가 아직 없어서 자리표시자를 넣고 주의사항에 적어 뒀는데, 그 메모를 실제 값으로 바꾸지 않은 상태로 랜딩을 열었습니다. 문서에 적어 둔 TODO는 배포를 막지 않습니다.

특히 `application-ci.yml` 은 하드코딩이라 환경변수로 덮이지 않아 함께 고쳐야 했습니다. 프로파일마다 오버라이드 가능성이 다르다는 걸 놓치면 "고쳤는데 테스트만 옛 값"인 상태가 남기 때문입니다.

값을 실제 출시 링크로 교체하는 건 한 줄이지만, 그것만으로 끝내면 같은 사고가 다시 조용히 납니다. `${ENV:기본값}` 구조는 값을 빼먹어도 예외를 던지지 않고 깨진 링크를 정상 서빙하는데, 이번 사고가 정확히 그 모양이었습니다. 그래서 렌더러에 감지 로직을 넣었습니다.

| 조건 | 동작 |
| --- | --- |
| 플레이스홀더 App ID / 비 http(s) / 빈 값 | `storeState=unset` 을 내리고 기동 시 WARN |
| `unset` 인 정상 랜딩 | 스토어 버튼 대신 검색 안내 문구 |
| `unset` 인 만료 랜딩 | 문구를 반드시 노출 — 버튼만 감추면 액션 0개의 막다른 화면이 됩니다 |

기동을 실패시킬지 한참 고민했고 하지 않기로 했습니다. 랜딩은 스토어 링크가 없어도 초대를 열어야 하고, 임의 값으로 뜨는 로컬·테스트를 깨뜨릴 이유가 없습니다.

## 대비 1.1:1과 초대자 한 줄

같은 PR(#465)에서 브랜드 정합과 초대자 노출도 정리했습니다. 페이지 배경의 인디고 그라데이션을 앱 토큰(`#F4F5F8`)으로 통일하자 흰 글씨 푸터의 대비가 **1.1:1** 이 됐습니다. 회색 계열 후보의 대비를 하나씩 쟀습니다. `--ink-muted` 는 2.4:1이라 못 쓰고, 4.56:1로 12px AA를 통과하는 `--ink-sub` 를 골랐습니다.

앞선 환경별 절대 URL 치환에 초대자 닉네임 관련 변수가 더해져, 치환 변수는 최종 9개가 됐습니다. 닉네임은 사용자 입력이라 그룹명과 같은 속성 안전 이스케이프를 적용하고, 자르기 순서에도 규칙을 뒀습니다. **자르기는 이스케이프 전**(엔티티 중간 절단 방지), **말줄임표는 이스케이프 후**(`&hellip;` 로 새어 나가는 것 방지)입니다. 처음엔 코드포인트 20자로 잘랐는데 리뷰에서 확장 grapheme 경계 지적을 받아 정규식 `\X` 기준으로 바꿨습니다. 그리고 탈퇴했거나 닉네임이 없는 초대자는 줄째로 접어, "님이 초대했어요"만 남는 화면이 나오지 않게 했습니다.

랜딩에서 가장 큰 글자는 끝까지 그룹명으로 뒀습니다. 다만 `og:title` 은 초대자로 시작하게 했습니다. 카톡 미리보기에서 가장 먼저 읽히는 줄이고, "누가 불렀나"가 링크를 누를지를 가르기 때문입니다. CSS로 분기할 수 없는 한 줄이라 서버가 완성해 넘깁니다.

## 남겨 둔 것들

앞의 플레이스홀더 사고가 주의사항에만 적어 둔 미결에서 나왔으니, 닫지 않은 항목은 이번에 목록으로 못박아 뒀습니다.

- **신뢰 헤더 전제** — 프록시 헤더를 IP 근거로 쓰는 건 "오리진에 프록시를 거치지 않고는 도달할 수 없다"가 참일 때만 안전합니다. 이 전제가 깨진 환경을 위해 신뢰 헤더 목록을 설정으로 뺐고, 비우면 `remoteAddr` 만 씁니다. 시트 확인을 강제하므로 피해는 어트리뷰션 오염에 그칩니다.
- **claim 기기 매핑** — claim 요청은 계약상 슬러그만 받아서, 같은 링크에서 여러 기기가 매치된 뒤 claim 순서가 매치 순서와 다르면 기기 필드와 유저 결합이 어긋날 수 있습니다. 초대자 어트리뷰션은 같은 링크라 영향이 없어 계약 확장은 후속으로 뒀습니다.
- **무인증 경로 스로틀** — `/l/{slug}` 와 `/l/match` 의 반복 호출 제한은 엣지 전제로 남겼습니다. UA를 안 보내는 스크립트는 봇 판정으로 걸립니다.
- **안드로이드** — `intent://` 와 `S.browser_fallback_url` 대응은 별도 티켓입니다. 현재 랜딩은 iOS 전제입니다.
- **스토어 빌드 배선** — 수신 배선(#413)은 병합됐지만 스토어에 올라가 있는 빌드는 그 이전 버전이라, 설치까지는 되지만 그룹 참여로 이어지지는 않습니다. 새 버전 배포로 풀 문제입니다.
- **gzip 확인** — 랜딩 응답의 압축 설정 확인은 인프라 쪽에 별도로 요청해 뒀습니다.

돌아보면 이 작업의 난도는 링크 하나가 카톡 스크레이퍼 → 인앱브라우저 → 스토어 → 앱 첫 실행 → 가입 → 참여까지 여섯 번 주인이 바뀌는 동안 컨텍스트를 잃지 않게 하는 데 있었고, 실제로 깨진 곳은 언제나 그 경계였습니다. 존재하지 않는 페이지를 가리킨 URL, prod로 하드코딩된 이미지 도메인, 전 프로파일의 플레이스홀더 App ID. 세 사고 모두 코드 로직이 아니라 **경계를 넘는 값**이 원인이었습니다.
