## 0. 한눈에

테스트 이야기는 보통 "무엇을 얼마나 덮었나"로 시작한다. gromo에서는 그게 두 번째 질문이었다. 첫 번째는 **"무엇을 덮을 수 없는가"**다. 이 앱의 핵심 기능(스크린타임)은 시뮬레이터에서 아예 동작하지 않고, 화면의 상당수는 네이티브 모듈이 없으면 불러오는 것조차 안 된다. 그래서 자동 검증의 모양이 **제약에 눌려서** 결정됐다.

| 값 | 무엇 (08-11, 1.x 앱 기준) |
| --- | --- |
| **145** | 테스트 파일 · 1,763 케이스 |
| **10.1초** | 전체 실행 (웜 캐시) |
| **3개** | E2E 플로 · 100초 |
| **28** | 어떤 검사도 안 거치는 네이티브 파일 |
| **없음** | 측정된 커버리지 — 안 켰다 |
| **0건** | 최근 앱 PR의 테스트 결과 |

<Callout label="08-11 기준 기록이다 — 이후 크게 바뀌었다" tone="warn">

1~4장은 기록 당일(08-11)의 상태다. 가장 급했던 A1(CI에서 테스트가 안 돈다)은 **같은 날 #619로 해소됐고**, A2(네이티브 무검사)는 08-22 #689로 안드로이드 쪽만 일부 바뀌었다. 그리고 09-16에 1.x 앱이 `app/legacy/app-dev`로 옮겨져 동결되면서 **1.x는 CI 검사 대상에서 통째로 빠졌다.** 지금 CI(`app-lint.yml`)가 검사하는 것은 2.0 앱(`app/app-dev`)뿐이다. 이 흐름은 5장에 따로 적었다.

</Callout>

<Callout label="이 문서가 다루는 것">

1장은 자동 검증이 어떤 모양이고 왜 그 모양인지, 2장은 그 체계가 부러진 자리 14건과 제품 사고를 테스트로 옮긴 3건이다. 출처 표시에서 `사고`는 실제로 깨진 뒤 안 것, `실측`은 직접 확인하다 발견한 것, `리뷰`는 코드 리뷰가 잡은 것, `플랫폼 제약`은 도구나 OS가 원리적으로 막아 둔 것이다.

</Callout>

## 1. 설계

### 1.1 도구는 둘뿐

자동 검증에 쓰는 도구는 **jest 하나와 Maestro 하나**다. jest는 JS 코드를 화면 없이 돌려 보는 테스트 러너이고, Maestro는 시뮬레이터에 앱을 띄워 사람처럼 누르는 E2E(End-to-End) 도구다. 설정 파일은 셋 — jest 설정 14줄, jest 준비 27줄, E2E 실행 스크립트 86줄. 그게 전부다. 스냅샷 도구도, 비주얼 회귀 도구도, 별도 E2E 프레임워크도 없다. Maestro를 고른 이유와 기각한 대안은 [ADR-026](/adr/adr-026-e2e-maestro)에 있다.

<Callout label="적은 게 나쁜 건 아니다">

이 앱에서 스냅샷(결과물을 통째로 저장해 두고 달라지면 알리는 방식)은 거의 무용하다. 화면의 상당수가 네이티브 뷰거나 애니메이션이라 스냅샷이 잡을 게 별로 없다. 대신 고른 전략은 **"잠글 규칙만 골라 단언"**이다. 화면이 어떻게 보이는지가 아니라, 깨지면 안 되는 계약을 문장으로 못 박는다.

</Callout>

### 1.2 4계층과 그 경계

```text
┌─ 한 번의 jest 실행 — 물리적 구분이 없다 ──────────────────────────┐
│  순수 유닛          모킹 유닛              컴포넌트                  │
│  시계·네트워크 없음  145개 중 98개가 목 사용  71개 (.test.tsx)         │
│  폴더로도 파일명으로도 안 나뉜다 — 각 파일 첫 줄 주석의                │
│  "이 파일이 잠그는 규칙"이 유일한 구분                               │
└──────────────────────── CI 관문의 5번째 단계 ─────────────────────┘
                          (3번째인 타입 검사가 죽으면 여기까지 안 온다)

┌─ E2E — Maestro ─────────────────────────────┐
│  플로 3개 · 시뮬레이터용 Release 빌드         │
│  CI 밖 · 로컬 전용 · 사람이 손으로 돌린다      │
└─────────────────────────────────────────────┘
```

앞의 세 계층은 **같은 실행에 섞여 있다.** 이건 관리 실패가 아니라 선택이다 — 계층을 나누는 순간 "이건 어느 계층이지"를 매번 판단해야 하고, 전체 실행이 10초라 나눠서 얻을 이득이 없다.

### 1.3 jest가 손댄 세 가지

| 손댄 것 | 왜 |
| --- | --- |
| **시간대를 KST로 못 박음** | "오늘"의 정의가 앱 전역에 흩어져 있어, 테스트를 돌리는 컴퓨터의 시간대에 따라 결과가 흔들린다. 고정하지 않으면 통과 여부가 지역에 달린다 |
| **애니메이션 워클릿 처리** | 애니메이션 라이브러리(Reanimated)가 UI 스레드용 함수(워클릿)를 쓰는데, 테스트 환경에는 그 스레드가 없다 |
| **탐색 범위를 `src/`로 좁힘** | 안 그러면 iOS 의존성 폴더를 통째로 뒤져 실행 시간이 몇 배로 는다 |

전역 가짜 구현(목, mock)은 **세 개뿐**이고, 셋 다 "네이티브가 없어서 파일을 읽는 것조차 실패하는" 것들이다 — 로컬 저장소, 유리 효과 UI, 오디오. 편의를 위한 목이 아니라 **없으면 테스트가 아예 안 켜지는** 것만 막았다.

### 1.4 E2E 한 바퀴

```text
e2e.sh
  ① 시뮬레이터용 Release 빌드 (개발 서버 주소 주입 · 서명 보정)
  ② 앱 삭제 → 설치        ← 권한 상태와 이전 OTA 번들 잔재를 같이 치운다
  ③ 플로 3개 순서 고정 실행 (하나라도 실패하면 중단)
  ④ 실행이 만든 게스트 계정을 탈퇴 API로 정리

플로 01  게스트로 온보딩 완주      → 계정을 만든다
플로 02  집중 세션 기록            → 01이 만든 계정에 데이터를 쌓는다
플로 03  통계 탭 조회              → 02가 쌓은 데이터를 확인한다
```

세 플로가 **체인**이라 순서가 고정이다. 앞이 뒤의 준비 과정이라 따로 돌릴 수 없다. 화면 요소는 전부 전용 식별자(testID)로 찾는다 — 글자로 찾으면 문구를 다듬는 순간 대본이 깨지니까. **딱 한 군데만 예외**로 글자를 매칭하는데, 우리가 식별자를 못 붙이는 시스템 권한 알림이다.

### 1.5 밀도 지도

테스트가 고르게 깔려 있지 않다. 어디가 두껍고 어디가 얇은지가 곧 **어디서 사고가 났는지**의 지도다. 비율은 파일 수 기준 어림치다(커버리지를 안 켰으므로).

| 영역 | 소스 | 테스트 | 비율 | 메모 |
| --- | --- | --- | --- | --- |
| 훅 | 5 | 7 | 1.40 | 가장 두껍다 |
| 그룹 | 57 | 45 | 0.79 | 돈이 걸린 판정이 여기 있다 |
| 전역 상태 | 8 | 6 | 0.75 | |
| 유틸 | 13 | 9 | 0.69 | |
| 집중 | 33 | 17 | 0.52 | |
| 서비스 | 35 | 18 | 0.51 | 스크린타임 동기화가 여기 |
| 통계 | 23 | 10 | 0.43 | |
| 리그 | 24 | 5 | 0.21 | |
| **설정** | 16 | 2 | 0.13 | |
| **온보딩** | 26 | 3 | 0.12 | **가장 얇다** — 그런데 E2E가 전부 여기를 지난다 |

<Callout label="가장 얇은 곳을 가장 불안한 그물이 받치고 있다" tone="warn">

온보딩은 단위 테스트가 거의 없고, 검증을 사실상 **E2E 첫 번째 플로에 위임**했다. 그런데 그 E2E는 CI에 없고 사람이 손으로 돌린다(2장 C·D). 실제로 E2E 대본이 세 번 수정됐는데 **세 번 다 온보딩이 바뀌어서**였다. 결합이 그만큼 강하다는 뜻이다.

</Callout>

## 2. 결함 기록

### A. 관문이 안 열린다

#### A1. 테스트가 CI에 걸려 있는데 결과가 안 나온다

**출처** 사고 · GROMO-1513 · 기록 당일 #619로 해소

**증상** — 앱 PR **3건이 연달아**(#606·#612·#616) CI에서 실패한다. 그런데 실패한 건 테스트가 아니라 그 앞의 타입 검사였고, 테스트는 **아예 실행되지 않았다.**

**원인** — CI를 자체 호스팅 러너(메모리 4GB)로 옮겼는데, Node가 자동으로 정한 힙 상한이 타입 검사기(`tsc`)가 쓰는 양보다 낮아 V8 힙 부족으로 죽었다. 진짜 문제는 그다음이다. CI 단계가 **린트 → 서식 → 타입 검사 → 테스트 → 코드 생성** 순서인데, 앞이 죽으면 뒤는 통째로 건너뛴다. **"테스트를 CI에 걸어 놨다"는 사실이 "테스트가 돌고 있다"를 보장하지 않는다.**

**해결** — 기록 시점엔 메모리 상한을 명시하는 수정이 병합 전이었고, 그동안 앱 PR들은 테스트 결과를 못 받은 채 지나갔다. 같은 날 #619(`NODE_OPTIONS=--max-old-space-size=2048`)가 병합돼 풀렸다. 숫자의 근거(`tsc` peak RSS 880MB)와 경위는 [CI/CD 트러블슈팅](/research/cicd-infra)에 있다.

구조적인 원인은 따로 남는다. 린트와 테스트는 서로 의존하지 않는데 **독립적인 검사를 하나의 순차 단계로 묶어서**, 하나가 죽으면 다른 하나도 안 돈다. 관문은 가장 약한 앞 단계만큼만 강하다.

#### A2. 네이티브 코드는 아무도 안 본다

**출처** 실측

**증상** — Swift 24파일, Kotlin 4파일 — **총 28개가 어떤 자동 검사도 거치지 않는다.** 린트도, 서식 검사도, 타입 검사도, 테스트도 없다.

**원인** — 네 도구(ESLint·Prettier·tsc·jest)가 **각자** 네이티브 폴더를 제외 목록에 넣고 있다. 하나씩 보면 다 합리적인 설정인데(JS 도구가 Swift를 볼 이유는 없다), **합치면 사각지대가 된다.** 그런데 앱에서 가장 고치기 어렵고 가장 자주 부러지는 코드가 바로 거기다.

**해결** — 부분적으로만. iOS는 테스트를 붙여도 **돌릴 서버가 없다**(맥이 필요한데 CI 러너는 리눅스다). 안드로이드 사용량 계산 로직은 순수 계산이라 몇 줄이면 덮이는데 **테스트 소스 폴더 자체가 없다** — 이건 못 한 게 아니라 안 한 것에 가깝다.

### B. 네이티브가 없는 세계

#### B1. 라이브러리 하나가 테스트 전체를 죽였다

**출처** 사고 · GROMO-1488 · #601 · 08-11

**증상** — 탭 바에 유리 표면 효과를 붙이는 작업 중, **관련 없는 테스트 묶음이 통째로** 실행조차 안 된다.

**원인** — 그 라이브러리는 **파일을 읽어 들이는 순간** 네이티브 모듈을 찾는다. 테스트 환경에는 없으니 거기서 끝이다. 게다가 최신 모듈 형식(ESM)만 배포해서 **변환 설정을 뚫어 줘도 로드가 안 된다.** 이 패키지를 간접적으로 끌어오는 파일이면 전부 같이 죽는다.

**해결** — 전역 목으로 통째로 끊었다. 처음엔 파일마다 막다가 30분 뒤 전역으로 옮겼다 — **같은 것을 여러 곳에서 막으면 하나 빠뜨린다**는 걸 그 30분에 배웠다.

#### B2. "실제로 움직였는가"는 단언할 수 없다

**출처** 플랫폼 제약

**증상** — 애니메이션이 제대로 도는지 테스트로 확인할 방법이 없다.

**원인** — 애니메이션은 별도 스레드에서 계산되는데 테스트 환경에는 그 스레드가 없다. 화면에 그려지는 최종 픽셀도 없다. 근본적으로 **확인할 대상이 존재하지 않는다.**

**해결** — 질문을 바꿨다. "움직였는가" 대신 **"움직이라는 지시가 붙었는가"**를 확인한다. 2단계로 진입하는 연출은 시간을 강제로 흘려보내 각 단계를 확인한다. 완전하진 않지만 지시를 붙이는 걸 잊은 실수는 잡는다.

#### B3. 눈으로 봐야 아는 것은 도구가 없다

**출처** 플랫폼 제약

**증상** — 레이아웃이 무너지거나 색이 틀린 것을 자동으로 못 잡는다.

**원인** — 시각 회귀 도구가 하나도 없다. 스냅샷도 0건이다.

**해결** — **시각 문제를 산술 문제로 번역**했다. 예를 들어 랭킹 한 줄이 화면 밖으로 삐져나오는 문제는 "각 칸의 폭을 합치면 정해 둔 예산을 넘지 않는다"는 계산으로 못 박았다. 픽셀은 못 보지만 **넘치는지는 셀 수 있다.** 물론 이건 이미 터진 유형만 덮는다. 안 터져 본 시각 문제는 여전히 못 잡는다.

### C. 시뮬레이터의 배신

#### C1. 핵심 기능의 정상 경로에 자동 테스트가 도달할 수 없다

**출처** 플랫폼 제약

**증상** — E2E 대본이 스크린타임 권한을 **일부러 거부**하고 지나간다. 허용했을 때의 흐름은 자동으로 확인할 방법이 없다.

**원인** — 스크린타임 API(FamilyControls·DeviceActivity)가 **시뮬레이터에서 아예 동작하지 않는다.** 실기기 전용이다. 그래서 앱 이름값을 하는 기능 — 측정·목표·실드·잠금화면 위젯 — 의 **정상 경로가 원리적으로 자동화 불가**다. 오직 사람이 실기기로 확인하는 수밖에 없다. 그 기능이 얼마나 자주 부러졌는지는 [스크린타임 노트](/research/screentime)에 있다.

**해결** — 없다. 대본은 거부 경로를 **확정 상태로** 밟고 지나간다. 이건 우회가 아니라 포기의 문서화다 — 적어도 대본을 읽으면 "여기는 자동으로 못 본다"가 드러난다.

#### C2. 좀비 알림 — 실패한 뒤 다시 돌릴 수가 없다

**출처** 사고 · 미해결

**증상** — 시스템 알림이 뜬 상태에서 테스트가 실패하면, **앱을 지워도 그 알림이 남아** 다음 실행의 화면을 덮는다.

**원인** — 시스템 알림은 앱이 아니라 **OS의 홈 화면 프로세스**가 들고 있다. 앱 삭제로는 안 치워진다.

**해결** — **시뮬레이터를 재부팅해야만** 치워진다. 이게 자동화의 진짜 걸림돌이다 — **"실패하면 다시 돌린다"가 성립하지 않는** 테스트는 CI에 올릴 수 없다. 재시도가 이전 실행의 잔재에 오염되기 때문이다. 여러 번 해도 결과가 같은 성질을 멱등(idempotent)이라고 하는데, 이 E2E의 재시도는 멱등하지 않다.

#### C3. 시뮬레이터가 안 뜬다던 알림을 띄웠다

**출처** 사고

**증상** — "시뮬레이터에서는 스크린타임 권한 창이 안 뜬다"는 전제로 짠 대본이, 새 iOS 버전 시뮬레이터에서 **실제로 권한 창이 뜨면서** 멈췄다.

**원인** — OS 버전이 올라가면서 동작이 바뀌었다. **"안 뜬다"는 전제 자체가 버전에 묶인 사실**이었는데 영구 진리처럼 적어 뒀다.

**해결** — 대본이 그 알림의 버튼 글자를 매칭해서 눌러 넘긴다. 전체 대본에서 **글자로 찾는 유일한 예외**다.

#### C4. 증분 빌드가 서명을 빼먹는다

**출처** 사고

**증상** — 빌드는 성공했는데 앱이 **실행을 거부**당한다.

**원인** — Release 설정으로 증분 빌드를 하면 **간혹** 메인 실행 파일의 서명이 빠진다. 간헐적이라 재현이 안 되고, 매번 클린 빌드를 하기엔 너무 느리다.

**해결** — 실행 스크립트가 서명을 검사하고, 빠졌으면 **임시(ad-hoc) 서명을 다시 붙인다.** 원인을 못 고치는 대신 증상이 나타날 수 없게 했다.

#### C5. 성공했는데 실패로 판정됐다

**출처** 실측

**증상** — 검사 조건이 실제로 맞았는데도 스크립트가 실패로 끝난다.

**원인** — "찾으면 즉시 종료"하는 옵션(`grep -q`)을 썼는데, 그러면 **앞 단계가 아직 쓰는 중인 파이프가 끊긴다.** 앞 단계(`strings`)가 SIGPIPE로 죽고, `pipefail`을 켠 셸이 그걸 오류로 센다. 매치에 성공했기 때문에 실패한 셈이다.

**해결** — 조기 종료 옵션을 쓰지 않고 출력만 버린다. 스크립트에 **"`grep -q` 금지" 주석을 남겨** 다음 사람이 되돌리지 못하게 했다.

#### C6. 빌드 실패를 못 보고 옛 번들로 몇 시간을 헤맸다

**출처** 사고

**증상** — 고친 코드가 반영되지 않는다. 원인을 한참 찾았는데 **빌드가 실패하고 있었다.**

**원인** — 빌드 출력을 파이프로 넘겨 마지막 몇 줄만 보고 있었다. 그러면 **빌드의 실패 여부가 파이프에 가려진다** — 셸은 파이프의 마지막 명령이 성공했는지만 본다.

**해결** — 파이프가 앞 단계의 실패를 가리지 않게 설정했다. 로그를 줄이려고 한 일이 실패를 숨기고 있었다.

### D. 대본이 검증하는 앱

#### D1. E2E가 실제 제품과 다른 앱을 확인한다

**출처** 실측

**증상** — 테스트 전용 플래그가 앱의 동작을 **네 군데**에서 바꾼다. 그중 둘은 단순 우회가 아니라 **분기 자체를 바꾼다.**

**원인** — 자동화가 불가능한 조작이 있다. 드럼처럼 굴리는 시간 선택기는 대본으로 못 돌리고(GROMO-1080), 사진 선택은 시스템 화면이라 못 건드린다. 그래서 플래그가 켜지면 **목표가 미리 채워져 버튼이 열리고, 사진 없이도 다음으로 넘어간다.** 그 결과 "두 목표를 다 정해야 진행된다"와 "사진을 골라야 진행된다"는 제품의 실제 규칙을 **E2E는 영원히 검증하지 못한다.** 나머지 둘(OTA 게이트·푸시 권한)은 순수한 우회라 무해하다. OTA 게이트를 끈 사정은 [OTA 노트](/research/ota-release-pipeline) B3에 있다.

**해결** — 분기를 바꾸는 두 곳은 남겨 뒀다. 대신 이 문서가 그 사실을 기록한다 — **E2E가 초록불이어도 그 두 규칙은 확인된 적이 없다.**

#### D2. 대본이 스텝을 조용히 건너뛰었다

**출처** 리뷰

**증상** — 조건부로 뜨는 화면을 처리하는 부분에서, 그 화면이 뜨기도 전에 조건을 평가해 **없는 것으로 치고 지나간다.** 실패가 아니라 통과로 끝나서 더 위험하다.

**원인** — 화면은 서버 응답을 받은 뒤에 뜨는데, 조건 검사가 그보다 빨랐다. **조건부 스텝은 "없다"와 "아직 안 왔다"를 구분하지 못한다.**

**해결** — 조건을 보기 전에 **먼저 기다린다.** 기다려도 안 나오면 그때 없는 것으로 친다.

#### D3. 탭이 안 바뀌어도 통과하던 대본

**출처** 리뷰

**증상** — 통계 탭 전환이 고장 나도 E2E가 초록불이다.

**원인** — 대본이 "카드가 있는가"만 확인했는데, **그 카드는 모든 탭에 있다.** 탭을 안 눌러도 통과한다. 존재 확인은 변화를 검증하지 못한다.

**해결** — "어느 탭이 선택된 상태인가"를 확인하도록 바꿨다.

### E. 사고를 테스트로 번역

<Callout label="여기 셋은 성격이 다르다">

앞의 14건은 "테스트 체계 자체의 고장"인데, 이 셋은 **제품에서 사고가 난 뒤 그 사고를 다시는 못 나게 문장으로 못 박은** 사례다. 이 앱에서 테스트가 실제로 한 일의 대부분이 이 모양이다 — 미리 잡은 게 아니라, 터진 걸 굳혔다.

</Callout>

#### E1. 버전이 4곳에 흩어져 있고 2곳만 올라갔다

**출처** 사고

**증상** — 릴리즈 버전이 앱 설정·패키지·iOS·안드로이드 **네 곳**에 각각 적혀 있는데 둘만 올라간 상태가 됐다. 이러면 OTA가 **구 바이너리에 신 번들을 배달**해 앱이 죽는다.

**원인** — OTA가 버전으로만 구·신을 가르는데, 그 버전이 한 군데가 아니다. iOS는 배포 도구가 자동으로 올려 주지만 **안드로이드는 올려 주는 장치가 없다.** 새 네이티브 모듈(오디오)을 쓰기 시작한 뒤라, 그 모듈이 없는 구 바이너리에 새 번들이 내려가면 크래시한다.

**해결** — "네 곳이 같아야 한다"를 **테스트로 못 박았다.** 기록 시점에 이 테스트는 의도대로 실패하고 있었다 — 버전을 올리는 중이라 두 곳만 올라간 상태였기 때문이다. **실패가 곧 그물이 작동한다는 증거**다.

#### E2. 세션 저장을 동시에 보내 전부 롤백됐다

**출처** 리뷰

**증상** — 집중 세션 저장 요청이 동시에 나가면 서버에서 충돌이 나고, **세션·통계·보상이 통째로 취소**된다.

**원인** — 같은 지갑을 두 요청이 동시에 건드린다. 클라이언트가 순서를 보장하지 않았다.

**해결** — 요청을 줄 세우고, 그 규칙을 테스트로 잠갔다.

#### E3. 레이아웃 붕괴를 숫자로 잡았다

**출처** 실측

**증상** — 작은 기기에서 랭킹 한 줄이 화면 밖으로 밀린다.

**원인** — 각 칸의 폭이 따로 정해져 있어서, 합이 화면을 넘는지 아무도 안 셌다.

**해결** — B3의 방식 그대로 — **"합이 예산을 넘지 않는다"**를 계산으로 못 박았다. 이 앱에서 시각 회귀를 잡는 유일한 방법이다.

### A1은 풀렸지만 구조는 남았다

#619로 타입 검사가 다시 통과하면서 테스트도 CI에서 돌기 시작했다. 다만 4장에서 적은 "독립 검사를 병렬 잡으로 분리"는 하지 않았다. 지금 `app-lint.yml`도 한 잡 안에서 린트 → 서식 → 타입 검사 → 테스트를 순서대로 돈다. 앞 단계가 죽으면 테스트가 건너뛰어지는 구조는 그대로다.

### 커버리지는 켰고, 기준선이 생겼다

08-13에 1.x의 jest 설정에 커버리지 측정 대상이 들어갔다. 테스트가 없는 파일도 0%로 분모에 잡히도록 대상 목록을 명시했고, 그날 기준선은 statements 59.6% · branches 57.3% · functions 52.8% · lines 61.0%다. 임계값은 "지금 걸면 CI가 바로 빨개진다"는 이유로 걸지 않았다. 4장의 "모른다"가 "안다, 다만 관문으로 쓰지 않는다"로 바뀐 것이다.

### jest가 증명할 수 없는 것이 하나 더 드러났다

B2의 "스레드가 없다"는 제약은 애니메이션 확인에서 끝나지 않았다. jest에서는 워클릿이 **평범한 JS 함수로 돈다.** 그래서 워클릿을 UI 스레드로 넘길 때 클로저가 캡처한 객체를 직렬화하다 실패하는 문제는 jest에서 절대 재현되지 않는다.

리그 4위 이하 행에만 붙은 워클릿이 모션 토큰 객체 전체를 캡처하고 있었고, 목록이 채워지기 전에는 한 번도 실행된 적이 없었다. 목록이 차자 흰 화면으로 터졌다(GROMO-1570, #657). 닷새 뒤 축하 컨페티에서 같은 함정이 재발했을 때(GROMO-1601, #679) 두 가지를 더했다 — 워클릿 안에서 그 토큰을 읽으면 ESLint 에러로 막는 규칙, 그리고 워클릿의 `__closure`에 그 토큰이 없음을 잠그는 회귀 테스트(수정을 되돌리면 실패하는 것까지 확인). PR 본문은 스스로 한계를 적었다 — "워클릿 직렬화는 네이티브 런타임 동작이라 jest로는 증명할 수 없다. 시뮬레이터에서 노출 확인은 별도로 필요하다." B2처럼 **질문을 증명 가능한 대리물로 바꾼** 사례다.

### 1.x는 CI 밖으로 나갔다

09-16 이관 PR은 먼저 CI 경로를 새 위치로 돌려, 옮긴 1.x 앱이 거기서도 통과하는지 한 번 검증했다(ESLint·Prettier·타입 검사 통과, jest 2,407개 중 2,406개 통과 — 남은 1건은 느린 러너에서 컴포넌트 렌더 테스트가 5초 제한에 걸린 타임아웃이었고 로컬에서는 통과했다). 그 뒤 "동결이라 CI가 볼 이유가 없다"는 판단으로 경로를 `app/app-dev`로 되돌렸다. 08-11의 1,763케이스는 동결 직전 2,407케이스까지 늘었지만, 이제 그 테스트를 CI가 돌려 주지 않는다.

<Callout label="동결된 1.x 앱에는 CI가 없다" tone="warn">

지금 `app-lint.yml`(ESLint·Prettier·tsc·jest)과 `app-android-build.yml`(안드로이드 네이티브 검사)은 2.0 앱(`app/app-dev`)만 본다. 1.x에 핫픽스를 내려면 `app/legacy/app-dev`에서 `npm ci && npm run lint && npm run format:check && npm run typecheck && npm test && npm run gen:palette:check`를 직접 돌려야 한다. 마지막 팔레트 코드젠 검사를 빼먹으면, 테마 파일을 고치고 코드젠을 안 돌렸을 때 나머지가 전부 통과해도 iOS 네이티브 팔레트가 옛 색으로 남는다 — 전에는 CI가 잡아 주던 것이다. 안드로이드 네이티브를 건드렸다면 XML 정합 검사와 Gradle 컴파일도 손으로 돌려야 한다. iOS 빌드는 처음부터 CI에 없었다. 결국 A1의 교훈이 1.x에서는 더 강한 형태로 돌아왔다 — **검사를 걸어 두는 것조차 사람의 기억에 달렸다.**

</Callout>

동결 시점까지 끝내 바뀌지 않은 것도 있다. 안드로이드 사용량 계산 모듈에는 테스트 소스 폴더가 여전히 없고(A2), E2E는 여전히 사람이 로컬에서 돌린다(C2). Maestro 플로는 1.x에만 있고 2.0 앱에는 아직 들어가지 않았다.

## 6. 용어

| 용어 | 뜻 |
| --- | --- |
| 유닛 테스트 | 함수 하나처럼 작은 단위가 규칙대로 동작하는지 확인하는 것. 화면 없이 돌아 빠르다 |
| 컴포넌트 테스트 | 화면 조각을 가짜 화면에 그려 놓고 눌러 보는 것. 진짜 기기는 아니다 |
| E2E (End-to-End) | 실제 앱을 켜서 사람처럼 눌러 보는 것. 가장 진짜에 가깝지만 가장 느리고 잘 깨진다 |
| 목 (mock) | 진짜 대신 세워 두는 가짜. 여기서는 **없으면 아예 안 켜지는 것**만 가짜로 세웠다 |
| 스냅샷 | 결과물을 통째로 저장해 두고 달라지면 알려 주는 방식. 이 앱에선 안 쓴다 |
| 커버리지 | 코드 중 테스트가 지나간 비율. 기록 시점엔 측정을 안 켰다 |
| testID | 화면 요소에 붙이는 전용 이름표. 글자로 찾으면 문구를 다듬을 때마다 대본이 깨진다 |
| 워클릿 (worklet) | 애니메이션을 JS 스레드가 아니라 UI 스레드에서 돌리려고 따로 떼어 내는 함수. 넘길 때 캡처한 값이 직렬화된다 |
| 멱등 (idempotent) | 여러 번 해도 결과가 같은 성질. E2E 재시도가 이걸 못 지켜서 CI에 못 올린다 |
| 관문 (CI gate) | 병합 전에 통과해야 하는 검사. **가장 약한 앞 단계만큼만 강하다** |
| 플레이키 (flaky) | 같은 코드인데 됐다 안 됐다 하는 테스트. 신뢰를 갉아먹어서 결국 아무도 안 본다 |
