KST 유저는 로컬 00:00~08:59, **하루의 3/8을 전날 버킷에 잃었습니다.** 아침에 앱을 열면 오늘 집중이 0이었습니다. 7월 2일부터 8월 12일까지 타임존·날짜 축을 건드린 PR 17개를 거쳐, 지금 서버 코드에 `LocalDate.now` 호출은 0건입니다. 한 번 고칠 때마다 아직 손대지 않은 경로에서 새 불일치가 나왔고, 기준이 정착하기까지 일곱 단계가 걸렸습니다.

결론부터 세 개 적습니다.

1. **"시각은 UTC로 저장한다"는 원칙은 옳고, "오늘"에는 적용되지 않습니다.** 시각(instant)은 위치와 무관한 절대량이지만, 날짜(civil date)는 타임존이 있어야만 결정되는 달력 개념입니다. 원칙을 후자까지 확장한 것이 첫 버그의 근원이었습니다.
2. **날짜 기준은 데이터의 소비자에 따라 달라야 합니다.** 유저 화면에 보여줄 집계는 로컬 날짜 버킷, 서버 배치의 판정은 절대시각 윈도우입니다. 같은 테이블을 두 기준으로 읽는 것이 정답인 구간이 실제로 있었습니다.
3. **스키마 문서를 권위로 삼아 정합했더니 사흘 전에 고친 버그가 나흘간 되돌아왔습니다.** 정본이 계약보다 낡아 있었습니다.

## 하루의 3/8이 전날로 갔다

시작은 `/stats/today`(오늘 요약)였습니다. 처음 구현은 유저의 `country_code`로 `ZoneId`를 파생해 서버가 로컬 날짜를 계산하는 방식이었는데, 코드리뷰에서 **읽는 쪽마다 기준이 제각각**이라는 게 드러났습니다.

| 경로 | 당시 날짜 기준 |
| --- | --- |
| `FriendService` · `GroupService`의 오늘 집중 | `LocalDate.now(ZoneOffset.UTC)` |
| `/stats/today` (신규) | `country_code` 파생 zone |
| `daily_screen_time_stats.date` 저장 | `country_code` 파생 zone |
| `daily_focus_stats` | writer 자체가 없어 조회하면 항상 0 |

그래서 **조회 기준**을 하나로 통일했습니다. **"서버가 계산하는 오늘은 UTC 날짜로 두고, 로컬 변환은 클라가 한다."** `/stats/today`도 `LocalDate.now(ZoneOffset.UTC)`로 고정했습니다. `daily_screen_time_stats`의 저장 존(`country_code` 파생)은 이때 손대지 않아, 저장과 조회의 기준이 서로 다른 채로 남았습니다.

`daily_focus_stats`의 writer를 새로 붙일 때 문제가 나왔습니다.

```java
// recordCompletion — 당시 버킷 산정
LocalDate statDate = endedAt.atOffset(ZoneOffset.UTC).toLocalDate();
```

KST 7/20 08:30에 끝난 세션은 UTC로 7/19 23:30, 즉 **7/19 버킷**입니다. 조회도 UTC라서 쓰기와 읽기가 서로 어긋나지는 않았습니다. 다만 **둘 다 유저의 달력과 어긋났습니다.** UTC+9 유저에게는 로컬 00:00~08:59, 즉 하루의 3/8이 전날로 귀속됩니다. 증상은 이렇게 보고됐습니다.

- KST 00:00~08:59에 완료한 세션이 `/stats/today`에 안 잡힘.
- 같은 세션이 히트맵·기간 통계에서는 **전날**에 얹혀 보임.

같은 자리에서 두 번째 손실도 함께 발견했습니다. 집계가 세션별로 `toMinutes()` 내림을 하고 있어서 **30초 세션 10번이 0분**이었습니다. 1분 미만 세션의 시간이 통째로 사라진 겁니다.

## 날짜를 클라에게 묻는 계약 (PR #149)

두 버그(GROMO-642 분 내림, GROMO-643 UTC 경계)는 같은 집계 경로에 얽혀 있어서 한 PR로 함께 고쳤습니다.

**쓰기 — 클라가 로컬 날짜를 준다.** `FocusSessionRequest`·`FocusSessionEndRequest`에 `localDate`를 필수 필드로 추가하고, `recordCompletion`의 statDate를 `endedAt` UTC 산정 대신 클라가 준 로컬 날짜로 버킷했습니다.

**읽기 — 서버는 오늘을 계산하지 않는다.** `date` 쿼리 파라미터를 필수로 추가했습니다. 대상은 `/stats/today`·`/stats/focus`·`/stats/by-category`·`/stats/screen-time`·`/users/{id}/stats`·`/pins`·`/groups/{id}`. 서버는 받은 날짜를 변환 없이 그대로 매칭합니다. 친구·그룹의 오늘 집중분도 같은 기준으로 통일하면서 `LocalDate.now(ZoneOffset.UTC)` 호출을 전면 제거했습니다.

**분 내림은 컬럼부터 바꿨습니다.** `total_focus_minutes`를 `total_focus_seconds`로 바꾸고(기존값 ×60 백필) 목표 비교(`goal * 60`)도 초 단위로 옮긴 뒤, 내림은 응답에서 **1회만** 하도록 했습니다. 응답 DTO 계약은 분 그대로라 앱이 볼 표면은 변하지 않았습니다. 원천 정밀도 규칙이 리그 쪽에서 다시 문제가 된 경위는 [리그 배치 노트](/research/league-batch)에 있습니다.

회귀 테스트는 두 개를 못박았습니다.

```text
30초 세션 2건        → 60초 (과거: 0 + 0 = 0)
endedAt UTC date ≠ localDate → localDate 로 귀속
```

필수 파라미터는 **회귀 방지 장치**로도 작동했습니다. `date`가 없으면 400이므로, 나중에 누군가 "서버가 몰래 `now()`로 폴백"하는 코드를 넣는 회귀가 구조적으로 불가능해집니다. 시간 로직의 테스트 불가 문제(`now()` 직접 호출)도 같이 사라졌습니다. 기준 날짜 주입이 계약 그 자체가 되었으니까요.

같은 PR의 리뷰에서 P2 두 건이 잡혔습니다. **카테고리 통계만 여전히 `endedAt` UTC 윈도우로 세션을 긁고 있었습니다.** KST 오전 세션이 `/stats/focus`에는 있는데 `/stats/by-category`에는 없는, 절반만 고친 상태였습니다. 후속 커밋에서 `focus_sessions.local_date` 컬럼을 신설(완료 시점에 확정, 라이브 세션은 null)하고 카테고리 조회를 `local_date BETWEEN`으로 전환해 버킷 기준을 통일했습니다. 카테고리 합계도 태그별 분 내림 후 합산에서 **전체 초합 1회 내림**으로 바꿔, 30초+30초가 카테고리에서는 0분인데 `/stats/focus`에서는 1분으로 갈라지던 손실을 없앴습니다.

이 커밋에서 "클라 로컬 귀속 날짜"는 요청 파라미터에서 **세션 데이터의 속성**이 됐습니다. 쓰기 시점에 확정된 civil date를 이후 모든 조회가 그대로 읽습니다.

기존 UTC 버킷 데이터는 마이그레이션하지 않고 방치했습니다. 신규부터 정확하면 된다는 판단이었고, 이 트레이드오프를 커밋 메시지에 남겼습니다.

## 정본이 낡으면 정합이 회귀가 된다

사흘 뒤, 공통 컬럼 전면 정합 작업(V2)이 있었습니다. `schema.dbml`을 target으로 두고 실제 스키마를 문서에 맞추는 작업이었습니다. 그 과정의 "기능 제거" 파트에서 우리는 두 가지를 지웠습니다.

- `focus_sessions.local_date` 컬럼 DROP
- 요청 본문의 `localDate` 필드 제거

`schema.dbml`이 아직 사흘 전 계약을 반영하지 않은 상태였고, 문서를 권위로 삼았으니 **문서에 없는 컬럼과 필드는 군더더기로 보였습니다.** 결과는 쓰기 버킷이 `endedAt` UTC로 회귀한 것입니다. 조회는 클라 `date` 관례를 유지하고 있었으니, 이제는 쓰기(UTC)와 읽기(클라 로컬)가 **서로도** 어긋났습니다. 이 상태가 나흘간 지속됐습니다.

**정본 갱신은 계약 변경과 원자적이어야 합니다.** 이 사건 이후 우리는 스키마 문서 갱신을 계약 변경 PR 안으로 끌어들이는 규칙을 논의했습니다.

부수적으로 하나 더 확인됐습니다. 통계 API 전체 리팩토링(GROMO-779)에서 코드를 전수 조사했더니, 날짜 기준이 **3종으로 갈라져** 있었습니다 — UTC 버킷 / `country_code` 존 로컬 / 클라 전달 로컬. 주석은 "클라 로컬"이라고 적혀 있는데 실제 코드는 이미 UTC 버킷이었습니다. 주석도 정본의 일종이어서, 낡은 주석을 읽은 사람은 낡은 문서를 읽은 사람과 똑같이 잘못된 전제로 판단합니다.

## 다시 서버 산정으로, 다른 좌표에서

회귀를 수리할 때 선택지는 두 개였습니다. (가) 클라 계약을 다시 깨서 `localDate`를 되살린다. (나) 서버가 유저 존으로 환산해 버킷한다.

(나)를 택해 서버측에서만 수리했습니다. 계약 파괴 변경은 앱과 동시 배포가 필요하고, 구버전 앱은 400을 맞습니다. 이미 한 번 원샷 전환을 했는데 일주일 만에 또 계약을 깨는 건 과했습니다.

```java
// FocusService — GROMO-803 이후
private LocalDate statDate(Instant endedAt, ZoneId zone) {
    return endedAt.atZone(zone).toLocalDate();
}
```

- 쓰기 버킷: 유저 `country_code` 파생 존의 로컬 날짜로. 스트릭 산정도 동일 기준.
- 카테고리 조회 윈도우: UTC에서 유저 존 `[from 00:00, to+1 00:00)` 반열림으로.
- 그 결과 스크린타임 저장 존과 **같은 기준**이 됐습니다. 정합 테스트를 별도 티켓으로 두어 고정했습니다.

맨 처음 구현으로 돌아온 것처럼 보이지만 좌표가 다릅니다. 그때는 "읽는 곳마다 제각각"의 한 갈래였고, 지금은 **조회가 클라 date로 이미 통일된 위에서 쓰기 버킷만** 서버 존으로 일원화한 것입니다.

수용한 한계도 명시했습니다.

| 항목 | 결정 |
| --- | --- |
| 국가→존 매핑 | KR·JP·GB만, 그 외와 null은 UTC 폴백 |
| 다중 타임존 국가(US) | 단일 매핑 원리적으로 불가 — 주석으로 명시 |
| 여행·국가 변경 | 하루 중복/누락을 package-info로 문서 수용 |
| 과거 데이터 | forward-only, 백필 없음 |
| 경계 테스트 | KST 00~09시 시나리오로 고정 |

미지원 국가의 유저는 수정 이전의 "아침에 0" 버그를 그대로 겪습니다. 이건 고친 게 아니라 **범위를 좁혀 수용한 것**이고, 글로벌 확장 시 기기 tz(IANA 문자열)를 직접 받는 방식으로 갈아탈 지점으로 남겨뒀습니다. 국가 코드로는 유저가 실제로 어느 존에 있는지 알 수 없기 때문입니다.

## 역교훈 셋 — 배치 판정, 자정 경계, 기기 로컬 축

**하나. 서버 배치의 판정은 로컬 버킷을 쓰면 안 됩니다.** 리그 재참여 알림 배치는 "이 유저가 오늘 집중했나"를 판정해야 하는데, 배치에는 클라가 `date`를 줄 상대가 없습니다. `DailyFocusStat.date`(로컬 버킷)로 판정했더니 비-KST 유저의 오늘(KST) 세션이 다른 날짜로 버킷돼 오판이 났습니다. `FocusSession.endedAt`(절대시각)의 KST 윈도우 판정으로 전환했습니다.

이 분류 원칙은 한동안 PR 본문에만 존재해서 매번 재발견됐습니다. 저장소 전체 grep으로 문서에 한 줄도 없다는 것을 확인한 뒤 `docs/date-axis.md` 정본으로 승격했습니다(PR #638).

**둘. 자정을 넘는 창은 "같은 날 선형 비교"로 판정되지 않습니다.** 시간대 챌린지의 창 겹침 검사는 23:50~23:59와 00:00~00:10을 서로 다른 날의 인접 구간으로 판정하지 못하고 그대로 통과시켰습니다. 실제로는 자정에서 맞닿은 연속 구간입니다. 8월 11일에는 "자정 인접은 막지 않는다"로 결정했다가, 다음 날 그 근거가 무너져 요일 마스크를 회전시키는 판정식으로 막았습니다. 창의 시간 모델 정본은 [챌린지 재정의 노트](/research/challenge-rebuild)에 있습니다.

결정 로그에 근거를 함께 적어둔 덕분에, 근거가 깨졌을 때 결정도 같이 되돌릴 수 있었습니다.

같은 창(window) 계열에서 저장 표현 문제도 한 번 크게 밟았습니다. 앱은 진짜 KST instant로 보내는데, 우리는 서버에서 저장된 instant의 **UTC time-of-day를 KST 벽시계로 읽고 있었습니다.** 그래서 정확히 9시간이 밀려 09:00~12:00 선택이 00:00~03:00으로 집계됐습니다. 고친 곳은 단일 변환점 하나였고, 그것만으로 7개 소비처(생성 검증·정산·푸시 등)가 한 번에 정합됐습니다.

**셋. 기기 로컬 축은 앱 안에서도 절반만 고칠 수 있습니다.** 창 사용분 측정에서, 앞선 작업이 앱의 창 계산 축(경계·보고 date)만 KST로 맞췄는데 네이티브 타임라인의 적재 키와 버킷 리셋은 여전히 기기 로컬 축이었습니다. 비KST 기기에서 KST 날짜로 조회하면 로컬 날짜 키와 어긋나 창 구간 이벤트가 누락되고, 이건 **과소 측정**입니다.

스크린타임 창 내기에서 과소 측정은 곧 허위 달성 판정으로 이어지고, 그 끝은 오정산입니다. 그래서 돈 경로 리스크로 분류하고, 네이티브를 건드리지 않는 쪽으로 해결했습니다. KST 창과 **교차하는 로컬 날짜를 모두 조회**한 뒤, 로컬 자정 리셋 시계열을 로컬 일 경계로 쪼개 세그먼트별 delta를 합산합니다. 두 축이 공존하는 상태를 그대로 두고, 한쪽 축의 질의를 다른 축의 조각으로 재구성했습니다.

## 지금의 기준 지도와 남은 판단

일곱 단계는 이렇게 이어졌습니다. 경로별 제각각 → UTC 일원화 → UTC 버킷 writer → 클라 `localDate` 계약 → `local_date` 컬럼 승격 → 정본 회귀 → 서버 존 산정.

정착한 형태는 **하이브리드**입니다. 시각은 UTC, 쓰기 날짜 버킷은 서버가 유저 존으로 환산, 조회 기준일은 클라가 계약으로 전달.

| 데이터 | 타입 | 기준 |
| --- | --- | --- |
| `focus_sessions.startedAt` · `endedAt` | Instant | UTC |
| `daily_focus_stats.date` · 스트릭 버킷 | DATE | country-zone 산정 (endedAt@존) |
| `daily_screen_time_stats.date` | DATE | country-zone 산정 |
| 조회 기준일 (date 필수 API 11개) | LocalDate | 클라 date 계약 |
| 카테고리 조회 윈도우 | Instant | endedAt이 유저 존 `[from, to+1)` 안 |
| 재참여 알림 판정 | Instant 윈도우 (endedAt, KST) | 서버 배치 |

`date`를 필수로 받는 조회 API는 계속 늘어 현재 11개입니다(통계 6종 + `/users/{id}/stats` + `/pins` + `/friends` + `/groups/{id}` + `/league/me/ranking`). 그 부산물로 **서버 코드에 `LocalDate.now` 호출이 0건**입니다. 클라가 `date`를 줄 상대가 없는 배치도 예외가 아닙니다. 오늘 여부를 `endedAt`(절대시각)의 KST 윈도우로 판정하므로, 서버가 civil date를 만들어내는 지점 자체가 없습니다. 서버가 "오늘"을 판단하지 않으면 틀릴 여지도 없다는 뜻이라, 이게 지금 이 도메인에서 가장 마음에 드는 숫자입니다.

아직 열려 있는 것들:

- **country-zone 근사의 수용 한계.** 매핑을 넓힐지, 기기 tz를 직접 받을지, 어느 쪽이 먼저인가.
- **forward-only의 잔흔.** 전환일 이전 히트맵·주간 통계의 오차는 백필하지 않았습니다. 사용자 문의로 돌아올지.
- **서비스 기준 시간대의 정체.** 리그 주차 경계는 KST 고정이라 해외 유저에게 최대 1일 버킷 차가 남습니다([리그 배치 노트](/research/league-batch)에 제한과 감수 근거). 글로벌 확장 시 유저별로 바꿀지, 서비스 정책 시간대로 유지할지.
- **정본 신선도 프로세스.** 스키마 문서 갱신을 계약 변경 PR에 원자적으로 묶는 규칙을 강제할지.

**범위를 적어두지 않은 원칙은 언젠가 자기 범위 밖에서 쓰입니다.**
