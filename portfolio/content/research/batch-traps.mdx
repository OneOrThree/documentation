배치는 실시간 API와 같은 코드로 쓰지만 같은 함정을 갖지 않습니다. 방아쇠가 사용자 요청이 아니라 시각이라서, 실패해도 아무도 화면에서 보지 못합니다. 릴리즈 준비기에 그로모 백엔드에 배치가 폭증했고, 2026-07-20에 크론 전체를 한 번 훑어 감사했습니다. 결론부터 적습니다. 개별 함정은 대부분 막아뒀는데, 남은 문제는 함정이 아니라 **구조**였습니다.

## 크론 11종이 한 스레드 풀에서 직렬로 돌고 있었다

스택은 Spring의 `@EnableScheduling` + `@Scheduled(cron = "...", zone = "Asia/Seoul")` 뿐입니다. Spring Batch도 Quartz도 넣지 않았습니다. 주 1회~일 1회에 수백~수천 건 규모라 청크·재시작·메타테이블은 과설계라고 판단했고, 그 판단 자체는 지금도 유효하다고 봅니다.

문제는 판단의 부작용이었습니다. `@Scheduled`의 기본 태스크 스케줄러는 스레드 1개짜리라, 크론 11종이 사실상 한 줄로 서서 돕니다.

```text
스케줄러 층 — 기본 풀 스레드 1 (직렬)
  LeagueScheduler                월 00:00 주간 정산
  NotificationScheduler          크론 9종 (리그 5 + 리텐션 4)
  FocusSessionOrphanScheduler    매시 고아 세션 스윕
        |
        +-- LeagueBatchService   단일 @Transactional 전 유저 정산
        +-- 알림 서비스 4종       @Transactional(REPEATABLE_READ) 루프
                                   └ 유저당 1건 동기 POST → FCM 클라이언트
```

주요 배치의 발화 시각과 역할은 이렇습니다.

| 배치 | cron (KST) | 하는 일 | 티켓 |
| --- | --- | --- | --- |
| 주간 리그 마감 | `0 0 0 * * MON` | 아레나 순위 확정·승강등 판정·다음 주 재배정 | GROMO-412 |
| 리그 승격/강등 알림 | `0 0 9 * * MON` | 직전 주차 ENDED 결과 재조회 후 발송 | GROMO-528 |
| 리그 마감 임박 알림 | `0 0 20 * * SUN` | ACTIVE 아레나 전원에 현재 순위 발송 | GROMO-528 |
| 미접속 복귀 알림 | `0 0 10 * * *` | `last_active_at` 기준 D+3/7/14 유저 발송 | GROMO-578 |
| 순위 추월 알림 | `0 0 19 * * *` | 어제 스냅샷과 오늘 실시간 순위 비교 | GROMO-579 |
| 고아 라이브 세션 정리 | 매시 | `ended_at IS NULL`인 오래된 세션 마감 | GROMO-610 |

설계의 중심은 **상태 재조회**(state-refetch)입니다. 월 00:00 정산이 결과를 영속화하면, 09:00 알림 배치가 그 결과 테이블을 다시 조회해서 발송합니다. 별도 발송 큐가 없어 단순한데, 대가가 분명합니다. "이미 보냈는지"를 저장하는 곳이 없습니다.

## 2026-07-20 감사: 개별 함정이 아니라 구조가 걸렸다

감사에서 나온 것 세 가지입니다. 세 가지 다 평시에는 아무 증상이 없고, 조건이 겹치는 순간에만 나타납니다.

**① 정산이 단일 거대 트랜잭션입니다.** `LeagueBatchService`가 전 유저 정산을 하나의 `@Transactional` 안에서 끝냅니다. 중간에 한 건이 터지면 전량 롤백이고, 재시작 지점이 없어 처음부터 다시 돌려야 합니다. 실제로 감사에서 잡힌 시나리오는 정산 도중 유저 1명이 탈퇴하면 `settlement user disappeared`로 전체가 롤백되는 레이스였습니다. 수천 명의 정산이 1명 때문에 무효가 됩니다.

**② 알림이 트랜잭션을 연 채로 FCM에 동기 POST를 합니다.** 알림 서비스 4종이 `@Transactional(isolation = REPEATABLE_READ)` 루프 안에서 유저당 푸시 1건을 단건 POST로 보냅니다. 두 가지가 동시에 나빠집니다.

- DB 커넥션을 외부 HTTP 왕복이 끝날 때까지 붙잡습니다. 롱 트랜잭션 + 커넥션 점유입니다.
- 발송 처리량이 스케줄러 스레드 1개에 묶입니다. 대상이 늘면 늘어난 만큼 선형으로 길어집니다.

트랜잭션 안에서 외부 I/O를 하는 것은 교과서적 안티패턴인데, 배치 루프 안에 있으면 "한 유저씩 처리하는 평범한 코드"로 보여서 눈에 잘 안 걸립니다.

**③ ShedLock이 없습니다.** 크론 전체가 단일 인스턴스 가정 위에 서 있습니다. 코드에는 `// TODO 분산 락`만 있습니다. 스케일아웃하는 순간 파드 수만큼 같은 배치가 동시 발화해서 중복 푸시가 나갑니다. 여기에 dev/staging용 수동 트리거 컨트롤러(`@Profile` 게이팅)가 있어서, 크론 발화 시각과 수동 트리거가 겹칠 수도 있습니다.

정리하면 감사 결과는 "버그 3개"가 아니라 "단순 스케줄러 층에 머문 대가 3개"였습니다.

## 이미 막아둔 함정들 — 무엇을 어떻게 막았나

반대로, 겪고 나서 고친 것들도 기록해둡니다. 대부분 값비싼 인프라 없이 쿼리 한 줄로 막혔습니다.

**TOCTOU 이중 반영 → 원자적 조건부 UPDATE.** 세션 종료 PATCH가 동시에 2건 들어오면 둘 다 `ended_at IS NULL`을 읽고 각자 갱신해서, 통계·스트릭·이벤트가 두 번 반영됐습니다(GROMO-610). `SELECT` 후 검사하는 형태를 버리고 조건을 UPDATE 안으로 밀어넣었습니다.

```sql
UPDATE focus_sessions
   SET ended_at = :now
 WHERE id = :id
   AND ended_at IS NULL;
```

영향 row가 1이면 경쟁 승자라 후처리를 진행하고, 0이면 이미 처리된 것이라 조용히 스킵합니다. 락도 버전 컬럼도 없이, 검사와 갱신을 한 문장으로 합치는 것만으로 레이스가 사라졌습니다.

**매 인증 요청마다 UPDATE 트랜잭션 → WHERE 가드로 1일 1 write.** 미접속 복귀 알림(GROMO-578)이 `last_active_at`을 필요로 해서 인증 필터에서 갱신했더니, 전 인증 트래픽에 쓰기 트랜잭션이 붙었습니다. 리뷰에서 지적받고 갱신 조건을 컬럼 값으로 가드했습니다.

```sql
UPDATE users
   SET last_active_at = :now
 WHERE id = :id
   AND last_active_at < :todayStartKst;
```

유저당 하루 1회만 실제 write가 발생합니다. 쿼리 왕복 자체는 남아서, 인메모리 스로틀은 후속(GROMO-903)으로 남겼습니다.

나머지는 표로 남깁니다.

| 함정 | 대처 |
| --- | --- |
| 대상 조회 풀스캔 | 부분 인덱스 `(last_active_at) WHERE is_guest = false AND deleted_at IS NULL` — 배치 대상만 인덱싱 |
| 유저별 설정 N+1 | `findAllById(userIds)` 일괄 로드, 아레나별 순위는 `JOIN FETCH` 1쿼리 |
| 루프 중 1건 예외로 전체 중단 | 건별 `try/catch` 예외 격리 — warn 로그 후 계속 |
| cron 타임존 혼동 | 전 배치 `zone = "Asia/Seoul"` 고정, 하루 경계는 `atStartOfDay(KST)`, 주 경계는 공용 `resolveWeekStart` 재사용 |
| 알림 폭탄 | 순위 추월에 `notification_sent_logs` 기반 48시간 쿨다운·주 2회 상한 |
| 시각 민감 문구의 지연 발송 | 지연 발송하지 않고 폐기 — "마감까지 4시간"이 늦게 도착하면 오정보가 됩니다 |

수용한 리스크도 명시해둡니다. 배치가 못 돈 회차는 소급하지 않습니다(no catch-up). D+3 윈도우를 놓치면 다음 날엔 이미 D+4라서 대상이 아니고, 리텐션 발송이 조용히 샙니다. 발화 시각에 프로세스가 죽으면 그 회차는 재실행되지 않습니다. 주 1회 규모라 로그 감시로 버티기로 하고, 코드 주석과 PR에 알려진 한계로 적었습니다. 정석은 발송 이력 + 워터마크(마지막 성공 시각) 기반 소급 처리입니다.

## enum 컬럼 마이그레이션에서 두 번 넘어졌다

배치가 새 컬럼에 의존하면 마이그레이션이 함께 가야 하는데, 여기서 두 가지에 걸렸습니다.

첫째, `@Enumerated(EnumType.STRING)`은 네이티브 enum 타입이 아니라 **varchar 저장**입니다. 마이그레이션에서 친절하게 네이티브 enum 타입으로 컬럼을 만들면 부팅 시 이렇게 터집니다.

```text
type "occupation" does not exist
```

JPA가 기대하는 것은 `varchar`입니다. 어노테이션 이름이 `STRING`인 이유가 그것입니다.

둘째, 마이그레이션 스크립트를 두던 `docs/`가 gitignore 대상이라 diff에 나타나지 않았습니다. `ddl-auto=validate`인 dev/staging에서는 배포 전에 `run-migration-v*.sh`를 반드시 선적용해야 하고, 안 하면 부팅이 실패합니다. 부작용도 있었습니다. 코드 리뷰 도구가 diff만 보고 "마이그레이션이 없다"고 오판했습니다. 스키마 변경은 리뷰 가능한 자리에 두어야 한다는 걸, 리뷰가 틀리는 방식으로 배웠습니다.

## 다음 단계는 함정 땜질이 아니라 층을 올리는 것

감사 결과가 개별 함정이 아니라 구조였으니, 대응도 구조로 잡았습니다.

| 티켓 | 내용 | 얻는 것 |
| --- | --- | --- |
| GROMO-892 | 정산을 Spring Batch Step으로 이관 (reader = keyset 커서, processor = `settleUser`, writer = `saveAll`) | 청크 커밋 + JobRepository 재시작성 |
| GROMO-893 / GROMO-900 | 알림 트랜잭션 경계를 페이지 단위로 축소, FCM 발송은 트랜잭션 밖으로 + `sendEach` 다건화 | 커넥션 점유 해소, 처리량이 스레드 1에서 분리 |
| GROMO-894 | 크론 전체에 ShedLock (`lockAtMostFor`) | 스케일아웃·수동 트리거 중복 발화 차단 |
| GROMO-901 | 미접속 복귀 잡의 전량 메모리 적재를 keyset 페이징으로 | 대상 수와 무관한 메모리 |

트레이드오프는 분명합니다. 메타테이블과 설정 복잡도가 올라가는 대신, 재시작성·부분 커밋·실행 이력을 직접 만들지 않고 표준으로 얻습니다. 지금 규모에서는 과설계였던 것이, 실패 모드를 실측한 뒤에는 정당해졌습니다.

발송 이력 테이블(아웃박스, GROMO-622)은 아직 미도입입니다. 상태 재조회로 버티는 중이고, 크로스 dedup이나 지연 발송·catch-up이 필요해지는 순간에 필연적으로 들어옵니다. 배치 성공/실패·발송 건수 메트릭을 관측 스택에 붙이는 것도 남았습니다. 지금은 배치가 조용히 실패하면 로그를 뒤져야만 압니다.

돌아보면 배치의 교훈은 하나로 모입니다. 배치는 실패해도 화면이 빨개지지 않으므로, **관측과 재시작성이 기능보다 먼저** 필요합니다. 크론 11종을 하나의 스레드로 돌리면서도 1년을 버틸 수는 있습니다. 다만 그건 문제가 없다는 뜻이 아니라, 아직 아무도 보지 못했다는 뜻입니다.
