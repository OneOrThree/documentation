챌린지 문서 세트를 정본 5종으로 이관한 PR은 코드 0줄이었습니다. 그런데 리뷰를 거치며 결정 로그가 N1~N51까지 쌓이는 사이에 조기 정산 데드패스, 24시간 자동 환불 우회 3종, 삭제 IDOR을 잡았습니다. 이후 구현 배치에서 정본과 코드가 갈린 8건을 원인별로 판정했고, 그다음 배치에서는 상위 정본의 세 줄이 거짓이라는 걸 찾았습니다. 그중 「폐기되는 코드」 목록을 믿었으면 지금도 던져지는 `throw` 경로를 지울 뻔했습니다.

코드 PR과 문서 PR이 따로 움직이면 그 틈에서 다음 구현자가 낡은 문서를 근거로 코드를 고치고, 방금 고친 동작을 되돌립니다.

## 기능 하나 = 5종 세트, 그리고 policy가 이긴다

기획 문서가 각자 로컬에 흩어져 있으면 "정본"이라는 말 자체가 성립하지 않으니, 먼저 저장 위치를 갈랐습니다.

- 개인 기획 스크래치는 `.docs/`로 내리고 gitignore 대상으로 둡니다.
- 팀이 공유하는 기능 문서는 `docs/prd/<기능>/` 아래에 두고 git 추적 대상으로 올립니다.
- 기능에 담을 수 없는 팀 전체 규약(예: 날짜 축)은 `docs/` 최상위에 둡니다.
- 문서 변경에도 브랜치 규칙을 둡니다. 신규는 `doc/prd-<기능>`, 수정은 `doc/fix-prd-<기능>`입니다.

루트·app·back의 `CLAUDE.md`와 티켓 구현·동기화 커맨드가 PRD를 찾는 경로도 전부 `docs/prd/<기능>/` 우선으로 동기화했습니다. 문서를 옮기는 작업에는 **문서를 가리키는 참조를 옮기는 작업**이 그대로 따라붙었습니다.

그 위에서 굳어진 패턴이 PRD·policy·IA·HLD·LLD 5종 세트입니다.

| 파일 | 역할 |
| --- | --- |
| `prd.md` | to-be 요구사항(FR), 조건 한눈에, 미해결 항목 목록 |
| `policy.md` | **정책 정본** — 결정 로그, 기존 정책 처분, 알려진 한계 |
| `information-architecture.md` | 화면·정보 구조, 응답 필드 계약, 로컬 저장소 키 |
| `high-level-design.md` | 컴포넌트·주요 흐름·시간 모델·동시성·운영 |
| `low-level-design.md` | ERD·엔드포인트 계약·판정 커널·마이그레이션 계획 |

**문서 간 충돌 시 policy가 이깁니다.** 결정 로그의 N번호가 정책의 정본이고, 나머지 문서는 그것을 펼친 것입니다. 이 우선순위를 명문화하지 않으면 구현자마다 근거로 드는 문서가 달라지고, 같은 기능에 다섯 개의 답이 공존합니다.

이 구조로 이관하는 동안 코드 리뷰 8라운드(봇 66건)와 팀 리뷰 4건을 거쳤고, 거기서 잡힌 결함은 세 갈래였습니다.

- 돈 경로: 보고와 정산의 경합, 탈퇴자 보고 경로 부재, 조기 정산 데드패스, 24시간 자동 환불 우회 3종, 삭제 IDOR
- 동시성: 생성·종료·삭제 직렬화, 지갑 잠금 순서, write-skew 2종
- 계약 정합: 알림 중복 제거 아이덴티티, 구앱 호환 브리지, 스키마 마이그레이션 누락

문서 PR을 코드 PR과 같은 리뷰 게이트에 올린 덕에, 이 결함들이 전부 구현 착수 전에 나왔습니다.

문서를 코드보다 앞세운 두 번째 자리는 모션 시스템이었습니다. duration이 8개 파일에 하드코딩되고 오버슛 커브가 두 파일에 복붙돼 있었습니다. 이걸 코드로 고치는 대신 문서로 duration 6단을 먼저 확정했습니다. 6단 전부 **기존에 쓰이던 값을 승격**한 것이라 새로 발명한 값이 없다는 점을 문서에 못박고 다음 날 구현에 들어갔습니다.

## 정본과 코드가 갈렸을 때, 고치기 전에 원인을 가른다

구현 배치를 돌리며 정본과 구현이 갈린 8건을 찾았습니다. 고칠 것을 정하기 전에 **왜 갈렸나를 먼저 가렸습니다.** 판정 축은 문서 오류, 구현 오류, 문서 낡음, 둘 다 성립 네 가지이고, 8건은 문서 쪽 6건과 구현 쪽 2건이었습니다.

| 사례 | 대표 상황 | 처분 |
| --- | --- | --- |
| 정본이 영문 이름을 안 정함 | policy가 사유를 한국어로만 정하고 영문 이름을 안 정해서 LLD와 서버가 각자 이름을 붙였다 | 문서를 코드 이름으로 정정 |
| 문서 안에서만 이름이 둘 | 같은 개념이 PRD와 LLD에서 다른 상수명 | 하나로 통일 |
| 원리적으로 실행 불가한 규칙 | 로컬 마커 키에 날짜 성분이 없는데 "60일 지나면 정리"라고 적음 | 값 스펙 자체를 정정 |
| 문면대로 구현하면 기능이 죽음 | 보고 게이트를 참가자 조건으로 묶으면 진행률이 통째로 죽는다 | 돈 갈래와 표시 갈래로 분리 |
| policy 내부 모순 | 같은 문서 안에서 사일런트 푸시 시점이 "정산 직전"과 "창 종료 직후"로 갈림 | 다수 문서·구현과 같은 쪽으로 정정 |
| 결정 반영 누락 | 사유 축이 넓어졌는데 LLD 본문이 옛 주석으로 굳어 있음 | 사유 표 신설 |

이 PR은 **문서가 틀렸거나 낡은 것만** 고쳤습니다. 구현이 틀렸던 2건은 코드 PR에서 이미 고쳤고 문서는 그 결과에 맞췄습니다. 결정 로그의 N항목 자체는 손대지 않았습니다. 그건 결정의 **역사**여서, N항목은 그대로 두고 본문·표·예시만 현행화했습니다.

표의 처분 중 값이 가장 컸던 건 **개명 철회**, 곧 문서를 코드 이름으로 정정한 쪽이었습니다. 문서에만 적혀 있던 더 예쁜 에러코드 이름으로 통일하려다 멈췄습니다. 배포된 앱이 그 문자열로 분기하고 있었기 때문입니다.

```ts
// BetSheet.tsx — BET_CLOSED 를 받으면 내일 날짜로 자동 재시도
// GroupBetHistoryScreen.tsx — BET_NOT_FOUND 를 받으면 페이지네이션을 접는다
```

에러코드 enum에는 "앱이 응답의 code 문자열로 분기한다 — 이름 변경 금지"라는 규약이 **이미 명문화돼 있었습니다.** 개명을 밀어붙이면서도 구코드 처분과 브리지는 문서에 한 줄도 없었습니다. 즉 이 케이스는 문서가 코드보다 틀렸을 뿐 아니라, **정본을 쓰면서 코드의 규약을 읽지 않았다**는 증거였습니다.

## 위험한 방향으로 서 있는 거짓말

다음 배치에서 상위 정본의 세 줄이 거짓이라는 걸 발견했습니다. 셋 다 **틀린 방향이 위험한 쪽**이었습니다.

| 자리 | 무엇이 거짓이었나 | 믿었으면 |
| --- | --- | --- |
| LLD 응답 계약 | "이 필드에 null 없음" — 실제 구현은 비활성 상태에서 null을 내고 서버 DTO·앱 타입도 그 계약 | 끝난 챌린지에 서지도 않을 회차 시각을 채운다 |
| LLD 폐기 코드 목록 | 「폐기되는 코드」 4개 중 **셋이 지금도 던져진다** | 살아 있는 `throw` 경로를 지운다 |
| policy 한계 절 | 이미 철회된 정리 계획을 아직 유효한 것처럼 서술 | 되살아난 값을 다시 좀비로 취급한다 |

두 번째가 특히 아팠습니다. 죽었다고 적힌 코드를 믿고 살아 있는 예외 경로를 지우는 방향인데, 이건 원래 티켓이 막으려던 사고("죽은 코드를 살아 있다고 광고")의 **정반대**입니다. 그래서 이 배치부터 문서 오류를 개수 대신 **방향**으로 분류했고, 잡을 때는 grep 두 줄을 썼습니다.

```bash
# "폐기됐다"는 서술을 믿지 않고 코드별로 발급 경로를 직접 센다
grep -rn "BET_ALREADY_EXISTS" back/src/main/java | grep -v test
# 문구 복사본이 다른 문서에 번졌는지 확인
grep -rn "null 없음" docs/
```

검산은 코드 단위로 돌렸습니다. 폐기 목록의 4개 중 셋은 발급 경로가 그대로 남아 있었고, `BET_ALREADY_EXISTS` 하나만 해도 지금도 던지는 자리가 3곳이었습니다. 두 번째 grep으로는 문제 문구가 한 곳뿐임을 확인했습니다. 이후 정본을 고칠 때는 같은 문구의 복사본까지 grep으로 셉니다.

같은 PR에서 사전 게이트를 돌리다 이 PR **자신의 자기모순**도 찾았습니다. 상위 정본을 고쳐놓고, 같은 PR의 델타 문서가 고치기 **전** 문면을 그대로 인용하고 있었습니다. 후속 구현자가 그 인용을 따르면 살아 있는 코드를 지웁니다. 마침 CI 러너가 5/5 offline이라 자동 체크가 붙지 않던 시기여서, 독립 검증은 사람과 사전 게이트 2라운드가 전부였습니다.

## 코드가 정본이라고 가리키는 주소가 실재하지 않았다

계측 이벤트 코드 세 곳의 주석이 정본 문서 주소를 가리키고 있었는데, 그 경로의 상위 디렉터리가 **gitignore 대상인 개인 스크래치**였습니다. 즉 저장소에는 그 문서가 없고, 팀원이 그 주석을 따라가면 빈손으로 돌아옵니다. 게다가 그룹 공통 분석 계약은 "챌린지·내기 이벤트의 정본은 챌린지 문서가 소유한다"고 소유권을 넘겨놨는데, **받은 쪽에 계측 절이 없었습니다.**

그래서 범위를 챌린지·내기 이벤트 11종 전체로 넓혀 계측 정본을 신설했습니다. 이 PR도 코드 0줄입니다. 사전 게이트 3라운드에서 10건이 나왔고 전부 반영했습니다. 그중 8건은 원인이 셋으로 갈렸습니다.

- 다섯은 **내가 쓴 문장이 실제보다 강한 보장을 약속한 경우**였습니다.
- 둘은 **코드 주석을 믿어서 생긴 사실 오류**였습니다. 카드 컴포넌트 주석에는 "마지막 참가자가 철회하면 서버가 내기를 `CANCELED`로 닫는다"고 적혀 있었는데, 상태 enum에 `CANCELED`는 없습니다. 실제 서비스는 마지막 참가자가 빠지면 회차 행을 `delete`합니다. 게이트가 없었으면 **틀린 상태 전이를 정본에 박제**할 뻔했습니다.
- 하나는 지표 자체가 성립하지 않는 경우였습니다. "미노출률"의 분모 후보는 상세 로드 성공 후에만 나가는 이벤트여서, 상세와 결과 조회가 함께 실패하면 분자만 생깁니다. 두 실패는 상관이 높아 **실패가 몰릴수록 어긋남이 커집니다.** 분모만 빠지므로 이 비율은 과대 추정이고, 1을 넘는 값도 나올 수 있습니다. "이 비율은 하한"이라던 초안의 서술은 성립하지 않습니다. 비율을 버리고 절대 건수로 계약을 바꿨습니다.

측정할 수 없는 것 7건은 갭 표로 남겼습니다. PRD에 측정 소스로 적힌 이벤트 이름 하나는 앱 코드 grep 0건, 존재하지 않는 이름이었습니다. 이름을 확정하는 건 이 문서의 권한 밖이라, 확정 주체를 적어 갭으로 열어 뒀습니다.

## 지도가 없으면 정합도 없다 — 날짜 기준 3종 혼재

통계 API 리팩토링 티켓(GROMO-779)에서 날짜 기준이 세 갈래로 갈라져 있었고, 주석과 구현도 어긋나 있었습니다(유래와 전수 조사는 [타임존 버킷 전쟁](/research/timezone-wars)).

이 티켓에서 한 선택이 지금도 유효하다고 봅니다. **동작 보존을 전제로 서비스 분해와 문서 정합화만 이번 범위로 하고**, 날짜 기준 통일·집계 소스 통일·목표 판정 통일은 각각 별도 후속 티켓으로 분리했습니다. 같은 검토에서 조회 API 중 하나만 실시간 집계라 고아 세션 포함 여부가 달라 총합이 어긋날 수 있다는 것도 확인했지만, 그것 역시 후속으로 넘겼습니다. 분해와 기준 변경을 한 PR에 섞었다면, 회귀가 났을 때 원인이 어느 쪽인지 가릴 수 없었을 것입니다.

같은 교훈의 다른 판이 날짜 축 규약이었습니다. PR 본문에만 남아 있던 분류 원칙을 `docs/date-axis.md` 정본으로 세우면서, 원리·유틸 카탈로그·전수 분류표·판정 근거·테스트 관행·갭 목록을 담았습니다. 그런데 이 문서 자체를 처음엔 **반대로 썼습니다.** 이미 폐지된 서버 클래스를 정본처럼 서술한 앱 주석을 그대로 믿고 서버를 확인하지 않았습니다. 그래서 문서에 오판 자체를 기록으로 남겼습니다.

- "이 절은 한 번 반대로 쓰였다. 앱 주석만 읽고 서버 정본을 확인하지 않으면 같은 실수를 반복한다."
- "날짜 축 문서는 계산이 근거다. 계산을 안 하고 쓰면 정본이 오히려 위험해진다."
- "범위·경계는 양끝을 검산해 예시로 남긴다."

## 남은 규칙 다섯 줄

정본화를 몇 주 돌리고 남은 실무 규칙입니다.

1. **정본 갱신은 계약 변경과 원자적으로.** 낡은 문서를 권위로 삼은 정합 작업은 롤백이 됩니다([타임존 버킷 전쟁](/research/timezone-wars)의 `schema.dbml` 회귀가 그 사례입니다). 갈릴 수밖에 없다면 문서 쪽에 "구현 PR과 범위가 겹친다 — 착수 전 대조" 같은 경고를 남깁니다.
2. **충돌 시 policy가 이긴다를 명문화한다.**
3. **결정 로그는 현행화하지 않는다.** 본문은 고치고 N항목은 남깁니다.
4. **문서를 고치기 전에 원인을 가른다.**
5. **grep으로 검산하고, 못 검산한 건 갭으로 적는다.** "폐기됐다"·"없다"·"항상 그렇다"는 전부 확인 대상입니다.
