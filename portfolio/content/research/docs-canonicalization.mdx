문서는 오래 "있으면 좋은 것"이었습니다. 그런데 구현이 붙기 시작하자 성격이 달라졌습니다. 문서가 낡으면 다음 구현자가 그 문서를 근거로 코드를 고치고, 그러면 문서가 코드를 회귀시킵니다. 이 노트는 정본을 만든 기록이 아니라, **정본을 만들고 나서 그것이 어떻게 틀리기 시작했는지**의 기록입니다.

한 줄로 요약하면: 정본 갱신은 계약 변경과 **원자적**이어야 합니다. 코드를 바꾸는 PR과 문서를 바꾸는 PR이 갈리는 순간, 그 사이의 틈이 다음 사고의 재료가 됩니다.

## 개인 스크래치와 팀 공유를 분리하는 것부터

시작은 구조였습니다. 기획 문서가 각자 로컬에 흩어져 있으면 "정본"이라는 말 자체가 성립하지 않습니다.

- 개인 기획 스크래치는 `.docs/`로 내리고 gitignore 대상으로 둡니다.
- 팀이 공유하는 기능 문서는 `docs/prd/<기능>/` 아래에 두고 git 추적 대상으로 올립니다.
- 기능에 담을 수 없는 팀 전체 규약(예: 날짜 축)은 `docs/` 최상위에 둡니다.
- 문서 변경도 브랜치 규칙을 갖습니다 — 신규는 `doc/prd-<기능>`, 수정은 `doc/fix-prd-<기능>`.

동시에 하네스 쪽 경로 참조를 전부 새 체계로 동기화했습니다. 루트·app·back의 `CLAUDE.md`, 티켓 구현·동기화 커맨드가 PRD를 찾는 경로가 모두 `docs/prd/<기능>/` 우선으로 바뀌었습니다. 문서를 옮기는 일의 절반은 **문서를 가리키는 것들을 옮기는 일**이었습니다.

## 기능 하나 = 5종 세트, 그리고 policy가 이긴다

여기서 굳어진 패턴이 PRD·policy·IA·HLD·LLD 5종 세트입니다.

| 파일 | 역할 |
| --- | --- |
| `prd.md` | to-be 요구사항(FR), 조건 한눈에, 미해결 항목 목록 |
| `policy.md` | **정책 정본** — 결정 로그, 기존 정책 처분, 알려진 한계 |
| `information-architecture.md` | 화면·정보 구조, 응답 필드 계약, 로컬 저장소 키 |
| `high-level-design.md` | 컴포넌트·주요 흐름·시간 모델·동시성·운영 |
| `low-level-design.md` | ERD·엔드포인트 계약·판정 커널·마이그레이션 계획 |

핵심 규칙은 하나입니다. **문서 간 충돌 시 policy가 이깁니다.** 결정 로그의 N번호가 정책의 정본이고, 나머지 문서는 그것을 펼친 것입니다. 이 우선순위를 명문화하지 않으면 다섯 문서가 서로를 인용하며 다섯 개의 진실을 만듭니다.

챌린지 문서 세트를 이 구조로 이관한 PR은 **코드 0줄**이었는데도 가장 많은 설계 결함을 잡은 PR이 됐습니다. 이관 후 코드 리뷰 8라운드(봇 66건)와 팀 리뷰 4건을 반영하며 결정 로그가 N1~N51까지 쌓였고, 초기 이관본과 최종본은 내용이 상당히 달라졌습니다. 잡힌 것들은 문서 오탈자가 아니었습니다.

- 돈 경로: 조기 정산 데드패스, 24시간 자동 환불 우회 3종, 삭제 IDOR, 보고와 정산의 경합, 탈퇴자 보고 경로 부재
- 동시성: 생성·종료·삭제 직렬화, 지갑 잠금 순서, write-skew 2종
- 계약 정합: 알림 중복 제거 아이덴티티, 구앱 호환 브리지, 스키마 마이그레이션 누락

같은 패턴을 모션 시스템에도 적용했습니다. duration이 8개 파일에 하드코딩되고 오버슛 커브가 두 파일에 복붙된 상태를 코드로 고치는 대신, 문서로 기준을 먼저 확정하고 다음 날 구현에 들어갔습니다. 이때 확정한 duration 6단은 전부 **기존에 쓰이던 값을 승격**한 것이라 새로 발명한 값이 없다는 점을 문서에 못박았습니다.

배운 것: 문서 PR을 코드 PR과 같은 리뷰 게이트에 올리면, 구현 착수 전에 돈 경로 결함이 나옵니다. 문서 리뷰가 싼 게 아니라, **문서 단계에서 잡는 결함이 싼 것**입니다.

## 정본과 코드가 갈렸을 때, 고치기 전에 원인을 가른다

구현 배치를 돌리며 정본과 구현이 갈린 8건을 찾았습니다. 이때 가장 중요했던 판단은 "무엇을 고칠까"가 아니라 **"왜 갈렸나"를 먼저 가른 것**입니다. 판정 축은 네 가지였습니다 — 문서 오류 / 구현 오류 / 문서 낡음 / 둘 다 성립.

| 유형 | 대표 사례 | 처분 |
| --- | --- | --- |
| 문서가 이름을 지어냄 | policy가 사유를 한국어로만 정하고 영문 이름을 안 정해서 LLD와 서버가 각자 이름을 붙였다 | 문서를 코드 이름으로 정정 |
| 문서 안에서만 이름이 둘 | 같은 개념이 PRD와 LLD에서 다른 상수명 | 하나로 통일 |
| 원리적으로 실행 불가한 규칙 | 로컬 마커 키에 날짜 성분이 없는데 "60일 지나면 정리"라고 적음 | 값 스펙 자체를 정정 |
| 문면대로 구현하면 기능이 죽음 | 보고 게이트를 참가자 조건으로 묶으면 진행률이 통째로 죽는다 | 돈 갈래와 표시 갈래로 분리 |
| policy 내부 모순 | 같은 문서 안에서 사일런트 푸시 시점이 "정산 직전"과 "창 종료 직후"로 갈림 | 다수 문서·구현과 같은 쪽으로 정정 |
| 결정 반영 누락 | 사유 축이 넓어졌는데 LLD 본문이 옛 주석으로 굳어 있음 | 사유 표 신설 |

이 PR은 **문서가 틀렸거나 낡은 것만** 고쳤습니다. 구현이 틀렸던 2건은 코드 PR에서 이미 고쳤고 문서는 그 결과에 맞췄습니다. 그리고 결정 로그의 N항목 자체는 손대지 않았습니다 — 그건 결정의 **역사**이고, 역사를 현행화하면 왜 그렇게 정했는지가 사라집니다. 본문·표·예시만 현행화했습니다.

가장 배운 게 많았던 건 **개명을 철회한 사례**입니다. 문서가 지은 더 예쁜 에러코드 이름으로 통일하려다 멈췄습니다. 배포된 앱이 그 문자열로 분기하고 있었기 때문입니다.

```ts
// BetSheet.tsx — BET_CLOSED 를 받으면 내일 날짜로 자동 재시도
// GroupBetHistoryScreen.tsx — BET_NOT_FOUND 를 받으면 페이지네이션을 접는다
```

에러코드 enum에는 "앱이 응답의 code 문자열로 분기한다 — 이름 변경 금지"라는 규약이 **이미 명문화돼 있었습니다.** 문서는 개명을 시도하면서 구코드 처분과 브리지를 한 줄도 적지 않았습니다. 즉 이 케이스는 문서가 코드보다 틀렸을 뿐 아니라, **문서가 코드의 규약을 읽지 않고 쓰였다**는 증거였습니다.

## 위험한 방향으로 서 있는 거짓말

다음 배치에서 상위 정본의 세 줄이 거짓이라는 걸 발견했습니다. 셋 다 공통점이 있었습니다 — **틀린 방향이 위험한 쪽**이었습니다.

| 자리 | 무엇이 거짓이었나 | 믿었으면 |
| --- | --- | --- |
| LLD 응답 계약 | "이 필드에 null 없음" — 실제 구현은 비활성 상태에서 null을 내고 서버 DTO·앱 타입도 그 계약 | 끝난 챌린지에 서지도 않을 회차 시각을 채운다 |
| LLD 폐기 코드 목록 | 「폐기되는 코드」 4개 중 **셋이 지금도 던져진다** | 살아 있는 `throw` 경로를 지운다 |
| policy 한계 절 | 이미 철회된 정리 계획을 아직 광고 | 되살아난 값을 다시 좀비로 취급한다 |

두 번째가 특히 아팠습니다. 죽었다고 적힌 코드를 믿고 살아 있는 예외 경로를 지우는 방향인데, 이건 원래 티켓이 막으려던 사고("죽은 코드를 살아 있다고 광고")의 **정반대**입니다. 문서 오류의 위험도는 오류의 개수가 아니라 **방향**으로 재야 한다는 걸 여기서 배웠습니다. 잡은 방법은 단순했습니다.

```bash
# "폐기됐다"는 서술을 믿지 않고 발급 경로를 직접 센다
grep -rn "BET_ALREADY_EXISTS" back/src/main/java | grep -v test
# 문구 복사본이 다른 문서에 번졌는지 확인
grep -rn "null 없음" docs/
```

첫 grep은 지금도 던지는 자리 3곳을 짚었고, 두 번째 grep으로 문제 문구가 한 곳뿐임을 확인했습니다. 정본을 고칠 때 **복사본을 세는 습관**이 여기서 붙었습니다.

같은 PR에서 하나 더 배웠습니다. 사전 게이트가 이 PR **자신의 자기모순**을 잡았습니다. 상위 정본을 고쳐놓고, 같은 PR의 델타 문서가 고치기 **전** 문면을 그대로 인용하고 있었습니다. 후속 구현자가 그 인용을 따르면 결국 살아 있는 코드를 지웁니다. 마침 CI 러너가 5/5 offline이라 자동 체크가 붙지 않던 시기여서, 독립 검증은 사람과 사전 게이트 2라운드가 전부였습니다.

## 코드가 정본이라고 가리키는 주소가 실재하지 않았다

가장 조용한 결함은 여기였습니다. 계측 이벤트 코드가 세 곳에서 정본 문서 주소를 주석으로 인용하고 있었는데, 그 경로의 상위 디렉터리가 **gitignore 대상인 개인 스크래치**였습니다. 즉 저장소에는 그 문서가 존재하지 않습니다. 팀원이 그 주석을 따라가면 아무것도 없습니다. 게다가 그룹 공통 분석 계약은 "챌린지·내기 이벤트의 정본은 챌린지 문서가 소유한다"고 소유권을 넘겨놨는데, **받은 쪽에 계측 절이 없었습니다.**

그래서 범위를 결과 이벤트 2종이 아니라 챌린지·내기 이벤트 11종 전체로 잡고 계측 정본을 신설했습니다. 이 PR도 코드 0줄입니다. 사전 게이트 3라운드에서 10건이 나왔고 전부 반영했는데, 그 구성이 시사적이었습니다.

- 절반은 **내가 쓴 문장이 실제보다 강한 보장을 약속한 경우**였습니다.
- 둘은 **코드 주석을 믿어서 생긴 사실 오류**였습니다. 카드 컴포넌트 주석이 "마지막 참가자가 철회하면 서버가 내기를 `CANCELED`로 닫는다"고 적었는데, 상태 enum에 `CANCELED`는 없습니다. 실제 서비스는 마지막 참가자가 빠지면 회차 행을 `delete`합니다. 게이트가 없었으면 **틀린 상태 전이가 정본에 박제**될 뻔했습니다.
- 하나는 지표 자체가 성립하지 않는 경우였습니다. "미노출률"의 분모 후보는 상세 로드 성공 후에만 나가는 이벤트여서, 상세와 결과 조회가 함께 실패하면 분자만 생깁니다. 두 실패는 상관이 높아 **실패가 몰릴수록 어긋남이 커집니다.** 초안이 "이 비율은 하한"이라고 쓴 건 틀렸습니다 — 1을 넘을 수 있습니다. 비율을 버리고 절대 건수로 계약을 바꿨습니다.

그리고 측정할 수 없는 것 7건을 갭 표로 남겼습니다. PRD가 측정 소스로 적어둔 이벤트 이름 하나는 앱 코드에 grep 0건 — 존재하지 않았습니다. 이름을 확정하는 건 이 문서의 권한 밖이라 갭으로 열어 뒀습니다. **모르는 것을 모른다고 적는 칸이 정본에 있어야 합니다.**

## 지도가 없으면 정합도 없다 — 날짜 기준 3종 혼재

통계 API 리팩토링 티켓(GROMO-779)에서는 다른 종류의 정본 문제를 만났습니다. 12개 넘는 티켓이 누적되며 날짜 기준이 세 갈래로 갈라져 있었습니다.

| 기준 | 어디서 왔나 |
| --- | --- |
| UTC 버킷 | 서버 집계 저장 축 |
| country_code 파생 존 로컬 | 유저 국가에서 존을 파생시키던 시기의 잔재 |
| 클라가 전달한 로컬 | 앱이 계산해 보내던 초기 계약 |

여기서도 문서·주석이 코드와 어긋나 있었습니다. 주석은 "클라 로컬"이라고 적었지만 실제 구현은 이미 UTC 버킷으로 바뀐 상태였습니다. 조회 API 중 하나만 실시간 집계라 고아 세션 포함 여부가 달라 총합이 어긋날 수 있다는 것까지 함께 짚였습니다.

이 티켓에서 한 선택이 지금도 유효하다고 봅니다. **동작 보존을 전제로 서비스 분해와 문서 정합화만 이번 범위로 하고**, 날짜 기준 통일·집계 소스 통일·목표 판정 통일은 각각 별도 후속 티켓으로 명시적으로 분리했습니다. 지도를 그리는 작업과 지형을 바꾸는 작업을 한 PR에 섞으면, 실패했을 때 무엇이 원인인지 알 수 없습니다.

같은 교훈의 다른 판이 날짜 축 규약이었습니다. "데이터 결합은 서버 축, 측정·저장은 로컬 축"이라는 분류 원칙이 **PR 본문에만 남아 저장소 어디에도 없어서**(`docs/` 대상 grep 0건) 매번 다시 발견해야 했습니다. 이를 `docs/date-axis.md` 정본으로 세우고, 원리·유틸 카탈로그·전수 분류표·판정 근거·테스트 관행·갭 목록을 담았습니다. 그런데 이 문서 자체가 처음엔 **반대로 쓰였습니다** — 앱 주석이 이미 폐지된 서버 클래스를 정본처럼 서술하는 걸 그대로 믿고 서버를 확인하지 않았습니다. 그래서 문서에 오판 자체를 기록으로 남겼습니다.

- "이 절은 한 번 반대로 쓰였다. 앱 주석만 읽고 서버 정본을 확인하지 않으면 같은 실수를 반복한다."
- "날짜 축 문서는 계산이 근거다. 계산을 안 하고 쓰면 정본이 오히려 위험해진다."
- 범위·경계는 양끝을 검산해 예시로 남깁니다.

## 남은 규칙 다섯 줄

정본화를 몇 주 돌리고 남은 실무 규칙입니다.

1. **정본 갱신은 계약 변경과 원자적으로.** 코드 PR과 문서 PR이 갈리면 그 틈이 다음 사고의 입력입니다. 갈릴 수밖에 없다면 문서 쪽에 "구현 PR과 범위가 겹친다 — 착수 전 대조" 같은 경고를 남깁니다.
2. **정본에 우선순위를 명문화.** 충돌 시 어느 문서가 이기는지 없으면 다섯 문서가 다섯 진실이 됩니다.
3. **결정 로그는 현행화하지 않는다.** 본문은 고치고 N항목은 남깁니다. 역사와 현재 상태는 다른 물건입니다.
4. **문서를 고치기 전에 원인을 가른다.** 문서 오류인지 구현 오류인지 낡음인지 판정하지 않고 고치면, 코드가 맞았던 곳을 문서로 회귀시킵니다.
5. **grep으로 검산하고, 못 검산한 건 갭으로 적는다.** "폐기됐다"·"없다"·"항상 그렇다" 같은 단정은 전부 확인 대상입니다. 확인 못 했으면 단정하지 않습니다.
