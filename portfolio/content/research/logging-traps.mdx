PII를 로그로 흘릴 뻔했고, 로깅 인자 하나 때문에 그룹 탈퇴 트랜잭션이 단위테스트에서 실패했고, MDC를 `doFilter` 뒤에 넣어 `trace_id`·`user_id`가 전부 빈칸이었습니다. user-activity 전용 로거를 붙이는 PR 한 건에서 나온 함정 5건입니다. "로깅 실패는 비즈니스에 영향 없다"는 보장은 함정 2에서 인자 평가 단계에 뚫렸고, 함정 3·4는 로깅 코드를 추가하는 행위 자체가 남의 단위테스트와 컴파일을 깨뜨린 경우였습니다.

## 왜 스트림을 둘로 갈랐나

그때까지 로그는 한 갈래였습니다. `@Slf4j`로 찍는 시스템 로그와, "누가 무엇을 했다"는 유저 행동 기록이 같은 파일에 섞여 있었습니다. 목적이 다른 두 로그가 섞이면 둘 다 못 씁니다. 시스템 로그는 사람이 장애 때 읽는 것이고, 유저 행동 로그는 기계가 집계·조인하는 것이기 때문입니다. 그래서 스트림을 갈랐습니다.

| | 시스템 로그 | 유저 행동 로그 |
| --- | --- | --- |
| 로거 | `@Slf4j` → root | 이름 로거 `user-activity` |
| 파일 | `logs/app.log` | `logs/user-activity.log` |
| 포맷 | 텍스트 (PatternLayout) | 구조화 JSON (logstash 인코더) |
| 보관 | `maxHistory` 7일 | `maxHistory` 30일 |
| 프로파일 | dev/staging/prod만 파일 | 모든 프로파일에서 파일 |

## 다섯 함정

### 1. `Map.of("is_new_user", user)` — 엔티티를 통째로 넣어 PII를 흘릴 뻔했다

payload 값으로 JPA `User` 엔티티를 통째로 넣었습니다. logstash JSON 인코더는 넘어온 객체를 그대로 직렬화하므로, refreshToken·닉네임 같은 필드가 전부 로그 파일에 찍힙니다. 게다가 lazy 연관관계를 건드리면서 추가 쿼리·순환참조·`LazyInitializationException` 위험도 함께 생깁니다.

```java
// 잘못된 payload — 엔티티가 통째로 직렬화된다
logger.log(event, Map.of("is_new_user", user));

// 올바른 payload — 원시값만
logger.log(event, Map.of("is_new_user", isNewUser, "method", "kakao"));
```

여기서 정한 규칙은 **민감 객체를 payload에 아예 넣지 않는 필드 통제**입니다. 파일에 쓰인 PII는 지우려면 파일을 뒤져야 하고, 수집기로 흘러간 뒤엔 회수가 어렵습니다. 그래서 이 항목은 코드리뷰 체크리스트로 올렸습니다.

### 2. 로깅 인자 하나가 단위테스트의 그룹 탈퇴를 실패시켰다

`UserActivityEventLogger`는 내부를 try-catch로 감싸 "로깅 실패는 비즈니스에 영향 없음"을 보장하도록 만들었습니다. 그런데 단위테스트에서 `withdrawGroup` 자체가 실패했습니다.

```java
// joinedAt이 null이면 여기서 NPE — log() 안으로 들어가기도 전이다
logger.log(event, Map.of("joined_at", groupMember.getJoinedAt().toString()));
```

테스트의 `GroupMember`는 빌더로 만들어 영속되지 않았으니 `@CreationTimestamp`가 찍히지 않았고, `joinedAt`은 null이었습니다. 문제는 이 NPE가 `log()` **호출 전 인자 평가 단계**에서 터진다는 점입니다. 메서드 안의 try-catch는 메서드 안에서만 유효합니다. `log()` 내부의 직렬화·출력 실패는 try-catch가 삼키지만, 인자 평가 중의 예외는 호출 전이라 걸러지지 않습니다.

해결은 nullable 값을 payload에서 빼는 것(`joined_at`을 버리고 `group_id`만 남김)이었습니다. 규칙으로 정리하면 **payload 값은 항상 non-null이 보장되는 것만**입니다. 영속 전 엔티티라는 트리거는 테스트 전용이었지만, 단위테스트가 아니었다면 이 구조를 볼 기회도 없었습니다.

규칙은 정했지만 이미 배포된 호출부의 구조는 그대로라, 프로덕션에도 같은 지뢰가 남아 있습니다. payload 값에 null이 들어올 경로가 하나라도 있으면 비즈니스 트랜잭션까지 터집니다. 같은 함정이 한 군데 더 있습니다. `log.debug("u=" + toJson())` 처럼 문자열을 연결하면 레벨에 막혀도 인자는 먼저 평가됩니다. `{}` 파라미터화가 필수인 이유가 같습니다.

### 3. 횡단 의존성을 넣으면 남의 테스트가 깨진다

서비스에 `UserActivityEventLogger` 필드를 주입하자, 관련 없어 보이던 `@InjectMocks` 단위테스트들이 NPE로 줄줄이 실패했습니다. 주입할 mock이 없어 필드가 null이었기 때문입니다. `@Mock UserActivityEventLogger`를 추가하면 no-op mock이 들어가 해결됩니다. 사소하지만, **횡단 관심사를 추가하는 PR은 기존 단위테스트의 mock 목록도 함께 갱신해야 한다**는 걸 이때 배웠습니다. mock을 채운 뒤 단위테스트 186건이 전부 통과해 게이트가 GREEN으로 돌아왔습니다.

### 4. static import가 멤버 메서드에 가려졌다

`UserActivityEventLogger`에 `mask()` 메서드를 추가했더니 `import static MaskingConverter.mask`가 미사용·충돌로 잡혔습니다. 같은 이름의 멤버 메서드가 static import를 가리기(shadow) 때문입니다. 게다가 같은 패키지라 import 자체가 불필요했습니다. static import를 지우고 `MaskingConverter.mask()`로 정규 호출하는 것으로 끝났지만, "이름이 겹치면 가까운 쪽이 이긴다"를 로깅 코드에서 처음 밟았습니다.

### 5. MDC를 `doFilter` 뒤에 넣어 전부 빈칸이었다

가장 조용했던 버그입니다. 로그는 정상적으로 찍히는데 `trace_id`·`user_id` 자리만 계속 비어 있었습니다.

```java
// 잘못된 순서 — 컨트롤러가 도는 동안 MDC는 비어 있다
filterChain.doFilter(request, response);
MDC.put("trace_id", traceId);

// 올바른 순서
MDC.put("trace_id", traceId);
try {
    filterChain.doFilter(request, response);
} finally {
    MDC.clear();
}
```

`doFilter` **앞이 전처리, 뒤가 후처리**입니다. 뒤에 넣으면 요청 처리가 끝난 뒤에 값을 채우는 셈이니 의미가 없습니다. 그리고 `%X{trace_id}`는 값이 없으면 예외도 경고도 없이 **빈 문자열**이 됩니다. 그래서 이 실수는 누군가 로그 파일을 직접 열어 볼 때까지 아무 신호도 내지 않습니다.

여기 얽힌 순서 제약이 하나 더 있었습니다. `user_id`는 JwtFilter가 request attribute로 심어둔 값을 읽어야 하므로, `TraceIdFilter`는 JwtFilter 뒤여야 합니다(order 1 → 2). 그리고 attribute 키는 `userId`, MDC 키는 `user_id`로 표기가 다릅니다. 케이스 하나 때문에 값이 안 붙는 걸 잠깐 헤맸습니다.

## 그 다음에 파고든 것들

다섯 함정을 정리하고 나서 "왜 이렇게 동작하는가"를 층별로 파고들었습니다. 구조화 로깅 파이프라인은 네 층으로 나뉘고, 문제가 어느 층의 일인지부터 가려야 설명이 맞아떨어졌습니다. 파고든 순서도 표를 그대로 따랐습니다. Appender(비동기 큐와 롤링), Encoder/Converter(JSON 경로 마스킹), 층 바깥의 스레드 경계(MDC), 그리고 그렇게 쌓인 파일의 수명(S3).

| 층 | 질문 | 대표 설정 |
| --- | --- | --- |
| Logger | 찍을까? | 레벨 상속(조상 하나) |
| Appender | 어디로? | `additivity`로 스트림 분리 |
| Encoder | 어떤 모양? | PatternLayout ↔ JSON 인코더 |
| Converter / Provider | 필드 하나를? | `%mask`, `%X` |

앞의 두 층부터가 함정입니다. 스트림 격리를 실제로 만드는 건 `additivity=false`인데, 로거 이름만 나누면 로그가 조상 로거의 appender까지 **누적으로** 타서 양쪽 파일에 중복으로 찍힙니다. Logback에서 레벨은 가장 가까운 조상 하나를 찾고 멈추지만, appender는 조상 것까지 전부 누적합니다. 이 두 규칙이 독립이라는 게 실무 혼선의 최대 원인이었습니다.

스트림 표의 마지막 줄(프로파일)이 그 대가입니다. `additivity=false`라 root를 안 타니, 프로파일 분기(`springProfile`)도 root에만 걸려 있어서 유저 행동 로그는 로컬에서도 파일로 남습니다. 비즈 이벤트는 로컬에서도 보존하자는 판단이었지만, 이 값은 구조에서 따라온 결과여서 PR에 그 사실을 명시해 뒀습니다.

### 비동기 appender — 요청 지연 0의 대가

두 appender 모두 `AsyncAppender`로 감쌌습니다. 요청 스레드는 큐에 이벤트만 넣고 즉시 반환하고, 워커 스레드 하나가 파일에 씁니다. 우리 값은 이렇습니다.

```xml
<queueSize>512</queueSize>
<discardingThreshold>0</discardingThreshold>
<neverBlock>true</neverBlock>
```

읽으면 "버스트를 512개까지 흡수하고, 넘으면 레벨을 가리지 않고 버린다. 요청 지연은 절대 만들지 않는다"입니다. 문제는 `discardingThreshold=0`이 **레벨 기반 조기 폐기를 끄는 스위치**라는 점입니다. 아무것도 안 버린다는 뜻이 아닙니다. 기본값(20%)은 여유가 줄면 INFO 이하부터 버려 WARN·ERROR 자리를 남겨 둡니다. 그걸 껐으니 큐가 끝까지 차고, ERROR가 폭주하는 바로 그 순간에 ERROR가 버려질 수 있습니다.

설정이 틀렸다기보다, "ERROR 유실 가능"을 알고 고른 것인지가 핵심이었습니다. AsyncAppender는 폐기 시 카운터도 경고도 내지 않으므로, 확인하려면 부하 구간에서 **로그 줄 수와 요청 수를 대조**하는 방법뿐입니다. 당시 우리는 그 트레이드오프를 모른 채 이 값을 넣었습니다.

롤링 쪽에서도 같은 종류의 착각을 하나 걷어냈습니다. `maxHistory` 30일과 `totalSizeCap` 1GB 중 **먼저 걸리는 조건에서 파일이 지워집니다.** 1GB를 30일로 나누면 하루 약 34MB이니, user-activity가 그 선을 넘으면 "30일 보관"은 지켜지지 않습니다. 그리고 롤링을 촉발하는 건 로그 이벤트입니다. 새벽에 트래픽이 없으면 아침 첫 요청에서 롤링되니, 파일 타임스탬프가 자정이 아니어도 정상입니다.

### JSON 경로 마스킹 — 문이 둘인데 경비원은 하나

텍스트 로그는 패턴에 `%mask`가 박혀 있어 프레임워크가 자동으로 마스킹합니다. JSON 로그는 그렇지 않습니다. Converter는 PatternLayout **안에서만 도는 부품**이고, JSON 인코더는 PatternLayout을 아예 안 쓰기 때문입니다. 그래서 우리 코드가 `MaskingConverter.mask()`를 직접 호출해 2차 방어를 합니다.

인과관계도 하나 정정했습니다. 처음에는 우리가 만든 래퍼라서 자동 마스킹이 빠졌다고 봤지만, **마스킹 적용 여부는 인코더가 결정하고** 호출부가 누구인지는 그 판단에 들어가지 않습니다. 반증도 간단합니다. `user-activity` 로거에 텍스트 패턴과 `%mask`를 붙이면 래퍼를 그대로 두고도 자동 마스킹됩니다.

가장 크게 배운 건 정규식 마스킹의 한계입니다. 정규식은 값의 형식만 매칭하고 의미는 판별하지 않습니다.

| 패턴 | 정밀도 | 충돌 예시 |
| --- | --- | --- |
| 주민번호 | 높음 — 하이픈 위치가 고유 | 거의 없음 |
| 이메일 | 높음 — `@`와 TLD 구조 | 파일명 정도 |
| 전화번호 | 높음 — 접두어 고정 | 거의 없음 |
| 카드번호(16자리) | 중간 — 길이만 조건 | 16자리 주문번호·트랜잭션 ID |
| GPS 좌표(소수 4자리+) | 낮음 | 가격·환율·응답시간·버전 등 모든 실수 |
| 한글 이름(2~4자) | 낮음 | "결제", "실패", "사용자"까지 마스킹됨 |

미탐(PII 유출)과 오탐(정상 데이터 훼손)은 **둘 다 되돌릴 수 없습니다.** 오탐은 원본이 없어져 디버깅이 불가능해지고, 보통 장애 조사 중에야 그 사실을 알아차립니다. 그래서 GPS·이름 패턴은 뺐습니다. 정규식만으로는 미탐과 오탐을 동시에 잡을 수 없다고 판단했습니다. 덧붙여 마스킹 자체가 핫패스라, 패턴을 늘릴수록 모든 로그 줄이 그만큼 느려집니다.

근본 방향은 "모양 추측"에서 "이름표 확정"으로 옮기는 것입니다. 블랙리스트가 놓치면 PII가 조용히 나가고, 화이트리스트가 놓치면 값이 눈에 띄게 비니, 실패 방향이 반대입니다. 가장 멀리 가면 "로그엔 참조 ID만 남기고, 이메일이 필요하면 그때 DB를 본다"까지 갑니다.

### MDC는 왜 비동기 appender에서는 안 끊기나

같은 스레드 경계 문제인데 결과가 갈리는 이유를 이해하는 데 오래 걸렸습니다. `AsyncAppender`의 워커 스레드는 남의 스레드인데도 `trace_id`가 살아 있고, `@Async` 비즈니스 코드에서는 사라집니다.

답은 **복사 시점**이었습니다. MDC는 `log.info()` 호출 순간 이벤트 객체 안으로 스냅샷됩니다. 큐에 들어가는 이벤트는 MDC를 참조하지 않고 그 시점 값을 복사해 담습니다. 그래서 워커의 ThreadLocal이 비어 있어도 무관합니다. `%thread`가 워커 이름이 아니라 원래 요청 스레드 이름으로 찍히는 것도 같은 이유입니다.

| | AsyncAppender | `@Async` 비즈니스 코드 |
| --- | --- | --- |
| MDC | 유지 — Logback이 복사해준다 | 유실 — 아무도 복사하지 않는다 |
| 해결 | 필요 없음 | `TaskDecorator`로 직접 복사 |

즉 "스레드가 바뀌면 MDC가 끊긴다"의 정확한 형태는 **"복사해주는 사람이 없으면 끊긴다"**입니다. 순서는 하나뿐입니다. 제출 스레드에서 ①복사 → 풀 스레드에서 ②심기 → ③`finally`에서 clear. 실수는 ①을 람다 **안에서** 하는 쪽입니다. 코드가 그럴듯한데 값이 계속 비어 나옵니다.

그런데 백엔드를 전수로 훑고 나서 결론을 뒤집었습니다.

| 항목 | 실제 |
| --- | --- |
| 요청 스레드 MDC 주입 | 적용됨 (`TraceIdFilter`) |
| `finally` clear | 적용됨 |
| `@Async`·`@EnableAsync`·`CompletableFuture`·`ThreadPoolTaskExecutor` | `back/src/main`에 0건 |
| `ExecutorService` | 동시성 테스트 2개에만 존재 |

**`TaskDecorator`는 지금 붙일 데가 없었습니다.** 대신 다른 걸 발견했습니다. `@Scheduled`가 12곳(알림 스케줄러 10, 리그 1, 집중 세션 고아 정리 1)이고, 스케줄러는 HTTP 요청이 아니니 `TraceIdFilter`를 안 거칩니다. 여러 배치의 실패 로그가 같은 시각에 `trace_id` 없이 뒤섞여 나옵니다.

이건 성격이 다른 문제였습니다. `@Async`는 있던 값이 **유실**되는 것이라 복사하면 되지만, 스케줄러는 **애초에 없는** 것이라 복사할 원본이 없습니다. `TaskDecorator`로는 못 풀고 새로 발급해야 하며, 12곳에 반복하지 않으려면 AOP로 감싸는 게 정석입니다. 그리고 `MDC.clear()`의 목적이 두 개(다음 요청 오염 방지 + ThreadLocal 누수 방지)라는 것도 여기서 알았습니다. 스레드풀의 스레드는 죽지 않으니 그 스레드의 Map도 죽지 않습니다.

### 7일 뒤 사라지는 로그 — S3와 조회 비용

`maxHistory`는 **삭제 시점을 정하는 값**입니다. 지금 우리 시스템 로그는 7일 뒤 영영 사라집니다. 이 PR 범위 밖(GROMO-385+ TODO)이라 설계만 남겼고, 판단이 갈린 건 셋이었습니다.

올리는 건 롤링된 파일만입니다. 쓰는 중인 `app.log`는 어디까지 담았는지 알 수 없고 어제 파일은 아무도 안 건드리니, 자정 롤링 뒤 한 시간 여유를 둬 cron을 새벽 1시에 뒀습니다. 다중 인스턴스가 같은 키로 올리면 덮어써서 로그가 사라지는데, 반사적으로 떠올린 분산 락은 오답이었습니다. 한 대로 줄여도 그 한 대는 자기 로컬 파일만 보므로, 답은 키에 인스턴스 식별자를 넣는 **키 분리**입니다. 남은 하나는 컨테이너입니다. 새벽 1시까지 파일이 살아 있어야 올라가는데 저녁 배포 한 번이면 그날 로그가 증발하니, 볼륨이냐 수집기냐를 먼저 정해야 합니다. 이 선택은 이후 [헬스체크 하나뿐이던 관측이 APM까지](/research/observability-evolution)에서 stdout 수집으로 정리됩니다.

## 지금 아는 것

- **"로깅 실패는 비즈니스에 영향 없게"는 인자 평가 단계까지 지켜야 진짜입니다.** payload 값을 만드는 표현식은 이미 비즈니스 트랜잭션의 일부입니다.
- **PII 방어의 1차선은 필드 통제입니다.** payload에는 원시값만, 엔티티는 금지. 마스킹은 그 뒤를 받는 2차 방어입니다.
- **정규식 마스킹의 정밀도는 그 형식이 얼마나 고유한가에 비례합니다.** 잡는 것보다 부수는 게 많으면 빼는 게 옳습니다.
- **격리를 만드는 건 `additivity=false` 한 줄입니다.** 레벨 상속과 appender 누적은 독립된 규칙입니다.
- **조용히 깨지는 것들이 제일 비쌉니다.** 빈 MDC, 버려진 ERROR, 오탐으로 훼손된 값 — 모두 예외도 경고도 없습니다.
