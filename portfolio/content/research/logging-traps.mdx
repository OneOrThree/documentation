로깅은 "곁다리 작업"으로 분류되기 쉽습니다. 실패해도 비즈니스에는 영향이 없다고 가정하니까요. 유저 행동 로그를 붙이면서 그 가정이 세 번 틀렸습니다. 하나는 PII를 로그로 흘릴 뻔했고, 하나는 로깅 인자 때문에 그룹 탈퇴 자체가 실패했고, 하나는 필터 순서를 잘못 잡아 로그가 전부 빈칸이었습니다. 여기 남기는 건 그 다섯 건과, 그걸 계기로 Logback 파이프라인을 층별로 파고들며 알아낸 것들입니다.

## 왜 스트림을 둘로 갈랐나

그때까지 로그는 한 갈래였습니다. `@Slf4j`로 찍는 시스템 로그와, "누가 무엇을 했다"는 유저 행동 기록이 같은 파일에 섞여 있었습니다. 목적이 다른 두 로그가 섞이면 둘 다 못 씁니다. 시스템 로그는 사람이 장애 때 읽는 것이고, 유저 행동 로그는 기계가 집계·조인하는 것이기 때문입니다.

그래서 스트림을 갈랐습니다.

| | 시스템 로그 | 유저 행동 로그 |
| --- | --- | --- |
| 로거 | `@Slf4j` → root | 이름 로거 `user-activity` |
| 파일 | `logs/app.log` | `logs/user-activity.log` |
| 포맷 | 텍스트 (PatternLayout) | 구조화 JSON (logstash 인코더) |
| 보관 | `maxHistory` 7일 | `maxHistory` 30일 |
| 프로파일 | dev/staging/prod만 파일 | 모든 프로파일에서 파일 |

격리를 실제로 만드는 건 로거 이름이 아니라 `additivity=false`입니다. 이름만 나누면 로그가 조상 로거의 appender까지 **누적으로** 타서 양쪽 파일에 중복으로 찍힙니다. Logback에서 레벨은 가장 가까운 조상 하나를 찾고 멈추지만, appender는 조상 것까지 전부 누적합니다. 이 두 규칙이 독립이라는 게 실무 혼선의 최대 원인이었습니다.

표의 마지막 줄이 그 대가입니다. `additivity=false`라 root를 안 타니, 프로파일 분기(`springProfile`)도 root에만 걸려 있어서 유저 행동 로그는 로컬에서도 파일로 남습니다. 비즈 이벤트는 로컬에서도 보존하자는 판단이었지만, 이건 "설정한 것"이 아니라 "구조상 그렇게 된 것"이라 PR에 명시해 뒀습니다.

## 다섯 함정

### 1. `Map.of("is_new_user", user)` — PII를 막으려다 흘릴 뻔했다

payload 값으로 JPA `User` 엔티티를 통째로 넣었습니다. logstash JSON 인코더는 넘어온 객체를 그대로 직렬화하므로, refreshToken·닉네임 같은 필드가 전부 로그 파일에 찍힙니다. 게다가 lazy 연관관계를 건드리면서 추가 쿼리·순환참조·`LazyInitializationException` 위험까지 같이 옵니다.

```java
// 잘못된 payload — 엔티티가 통째로 직렬화된다
logger.log(event, Map.of("is_new_user", user));

// 올바른 payload — 원시값만
logger.log(event, Map.of("is_new_user", isNewUser, "method", "kakao"));
```

교훈은 "마스킹을 더 촘촘히 하자"가 아니었습니다. **마스킹은 2차 방어이고, 1차 방어는 애초에 민감 객체를 넣지 않는 필드 통제**라는 것입니다. 로그는 되돌릴 수 없습니다. 파일에 쓰인 PII는 지우려면 파일을 뒤져야 하고, 수집기로 흘러간 뒤엔 사실상 회수가 불가능합니다. 그래서 이 항목은 코드리뷰 체크리스트로 올렸습니다.

### 2. 로깅 인자 하나가 그룹 탈퇴를 실패시켰다

`UserActivityEventLogger`는 내부를 try-catch로 감싸 "로깅 실패는 비즈니스에 영향 없음"을 보장하도록 만들었습니다. 그런데 단위테스트에서 `withdrawGroup` 자체가 실패했습니다.

```java
// joinedAt이 null이면 여기서 NPE — log() 안으로 들어가기도 전이다
logger.log(event, Map.of("joined_at", groupMember.getJoinedAt().toString()));
```

테스트의 `GroupMember`는 빌더로 만들어 영속되지 않았으니 `@CreationTimestamp`가 찍히지 않았고, `joinedAt`은 null이었습니다. 문제는 이 NPE가 `log()` **호출 전 인자 평가 단계**에서 터진다는 점입니다. 메서드 안의 try-catch는 메서드 안에서만 유효하므로 아무 방어가 되지 않습니다.

| | 방어됨? |
| --- | --- |
| `log()` 메서드 내부의 직렬화·출력 실패 | 예 — try-catch가 삼킨다 |
| 인자 평가 중의 예외 (`.toString()`, 계산, 조회) | 아니오 — 호출 전이라 못 막는다 |

해결은 nullable 값을 payload에서 빼는 것(`joined_at`을 버리고 `group_id`만 남김)이었습니다. 규칙으로 정리하면 **payload 값은 항상 non-null이 보장되는 것만**입니다. 덧붙여, 이건 프로덕션에서는 잘 드러나지 않을 케이스(영속 전 엔티티)를 단위테스트가 잡아준 사례이기도 했습니다. 로깅에는 이 대칭이 하나 더 있습니다. `log.debug("u=" + toJson())` 처럼 문자열을 연결하면 레벨에 막혀도 인자는 먼저 평가됩니다. `{}` 파라미터화가 필수인 이유가 같습니다.

### 3. 횡단 의존성을 넣으면 남의 테스트가 깨진다

서비스에 `UserActivityEventLogger` 필드를 주입하자, 관련 없어 보이던 `@InjectMocks` 단위테스트들이 NPE로 무너졌습니다. 주입할 mock이 없어 필드가 null이었기 때문입니다. `@Mock UserActivityEventLogger`를 추가하면 no-op mock이 들어가 해결됩니다. 사소하지만, **횡단 관심사를 추가하는 PR은 기존 단위테스트의 mock 목록도 함께 갱신해야 한다**는 걸 여기서 배웠습니다. 최종적으로 게이트는 GREEN이었고, 그 시점 테스트는 186건이었습니다.

### 4. static import가 멤버 메서드에 가려졌다

`UserActivityEventLogger`에 `mask()` 메서드를 추가했더니 `import static MaskingConverter.mask`가 미사용·충돌로 잡혔습니다. 같은 이름의 멤버 메서드가 static import를 가리기(shadow) 때문입니다. 게다가 같은 패키지라 import 자체가 불필요했습니다. static import를 지우고 `MaskingConverter.mask()`로 정규 호출하는 것으로 끝났지만, "이름이 겹치면 가까운 쪽이 이긴다"를 로깅 코드에서 처음 밟았습니다.

### 5. MDC를 `doFilter` 뒤에 넣어 전부 빈칸이었다

가장 조용했던 버그입니다. 로그는 정상적으로 찍히는데 `trace_id`·`user_id` 자리만 계속 비어 있었습니다.

```java
// 잘못된 순서 — 컨트롤러가 도는 동안 MDC는 비어 있다
filterChain.doFilter(request, response);
MDC.put("trace_id", traceId);

// 올바른 순서
MDC.put("trace_id", traceId);
try {
    filterChain.doFilter(request, response);
} finally {
    MDC.clear();
}
```

`doFilter` **앞이 전처리, 뒤가 후처리**입니다. 뒤에 넣으면 요청 처리가 끝난 뒤에 값을 채우는 셈이니 의미가 없습니다. 그리고 `%X{trace_id}`는 값이 없으면 예외도 경고도 없이 **빈 문자열**이 됩니다. 그래서 이 실수는 로그를 눈으로 보고서야 발견됩니다.

여기 얽힌 순서 제약이 하나 더 있었습니다. `user_id`는 JwtFilter가 request attribute로 심어둔 값을 읽어야 하므로, `TraceIdFilter`는 JwtFilter 뒤여야 합니다(order 1 → 2). 그리고 attribute 키는 `userId`, MDC 키는 `user_id`로 표기가 다릅니다 — 케이스 하나 때문에 값이 안 붙는 걸 잠깐 헤맸습니다.

## 그 다음에 파고든 것들

다섯 함정을 정리하고 나서 "왜 이렇게 동작하는가"를 층별로 파고들었습니다. 구조화 로깅 파이프라인은 네 층으로 나뉘고, 문제가 어느 층의 일인지 아는 게 이해의 열쇠였습니다.

| 층 | 질문 | 대표 설정 |
| --- | --- | --- |
| Logger | 찍을까? | 레벨 상속(조상 하나) |
| Appender | 어디로? | `additivity`로 스트림 분리 |
| Encoder | 어떤 모양? | PatternLayout ↔ JSON 인코더 |
| Converter / Provider | 필드 하나를? | `%mask`, `%X` |

### 비동기 appender — 요청 지연 0의 대가

두 appender 모두 `AsyncAppender`로 감쌌습니다. 요청 스레드는 큐에 이벤트만 넣고 즉시 반환하고, 워커 스레드 하나가 파일에 씁니다. 우리 값은 이렇습니다.

```xml
<queueSize>512</queueSize>
<discardingThreshold>0</discardingThreshold>
<neverBlock>true</neverBlock>
```

읽으면 "버스트를 512개까지 흡수하고, 넘으면 레벨을 가리지 않고 버린다. 요청 지연은 절대 만들지 않는다"입니다. 문제는 `discardingThreshold=0`이 "아무것도 안 버린다"가 아니라 **레벨 기반 조기 폐기를 끈다**는 뜻이라는 것입니다. 기본값(20%)은 여유가 줄면 INFO 이하부터 버려 WARN·ERROR 자리를 남겨 둡니다. 그걸 껐으니 큐가 끝까지 차고, **ERROR가 폭주하는 바로 그 순간에 ERROR가 버려질 수 있습니다.** 가장 필요할 때 사라지는 쪽으로 설정한 셈입니다.

설정이 틀렸다기보다, "ERROR 유실 가능"을 알고 고른 것인지가 핵심이었습니다. 당시는 모르고 고른 쪽에 가까웠습니다. 그리고 AsyncAppender는 폐기 시 카운터도 경고도 내지 않으므로, 실측 방법은 부하 구간에서 **로그 줄 수와 요청 수를 대조**하는 것뿐이었습니다.

롤링 쪽에서도 같은 종류의 착각을 하나 걷어냈습니다. `maxHistory` 30일과 `totalSizeCap` 1GB는 **먼저 걸리는 쪽이 이깁니다.** user-activity가 하루 40MB를 넘으면 "30일 보관"은 사실상 거짓말이 됩니다. 그리고 롤링은 타이머가 아니라 로그 이벤트가 촉발하므로, 새벽에 트래픽이 없으면 아침 첫 요청 때 롤링됩니다 — 파일 타임스탬프가 자정이 아니어도 정상입니다.

### JSON 경로 마스킹 — 문이 둘인데 경비원은 하나

텍스트 로그는 패턴에 `%mask`가 박혀 있어 프레임워크가 자동으로 마스킹합니다. JSON 로그는 그렇지 않습니다. Converter는 PatternLayout **안에 사는 부품**이고, JSON 인코더는 PatternLayout을 아예 안 쓰기 때문입니다. 그래서 우리 코드가 `MaskingConverter.mask()`를 직접 호출해 2차 방어를 합니다.

여기서 인과관계를 하나 정정했습니다. "우리가 만든 래퍼라서 자동 마스킹이 안 된다"가 아닙니다. `%mask`는 호출부가 누구인지 모릅니다. **결정하는 건 인코더이고 호출부가 아닙니다.** 반증도 간단합니다. `user-activity` 로거에 텍스트 패턴과 `%mask`를 붙이면 래퍼를 그대로 두고도 자동 마스킹됩니다.

그리고 정규식 마스킹의 한계가 이 노트에서 가장 값진 발견이었습니다. 정규식은 "모양"만 보고 "의미"를 모릅니다.

| 패턴 | 정밀도 | 충돌 예시 |
| --- | --- | --- |
| 주민번호 | 높음 — 하이픈 위치가 고유 | 거의 없음 |
| 이메일 | 높음 — `@`와 TLD 구조 | 파일명 정도 |
| 전화번호 | 높음 — 접두어 고정 | 거의 없음 |
| 카드번호(16자리) | 중간 — 길이만 조건 | 16자리 주문번호·트랜잭션 ID |
| GPS 좌표(소수 4자리+) | 낮음 | 가격·환율·응답시간·버전 등 모든 실수 |
| 한글 이름(2~4자) | 낮음 | "결제", "실패", "사용자"까지 마스킹됨 |

미탐(PII 유출)과 오탐(정상 데이터 훼손)은 **둘 다 되돌릴 수 없습니다.** 오탐은 원본이 없어져 디버깅이 불가능해지고, 그 사실은 보통 장애 조사 중에 발견됩니다. 그래서 GPS·이름 패턴은 뺐습니다. 보안을 포기한 게 아니라 **정규식이라는 도구로는 이 둘을 못 잡는다**는 판단이었습니다. 덧붙여 마스킹 자체가 핫패스라, 패턴을 늘릴수록 모든 로그 줄이 그만큼 느려집니다.

근본 방향은 "모양 추측"에서 "이름표 확정"으로 옮기는 것입니다. 블랙리스트는 실패하면 조용히 유출되고, 화이트리스트는 실패하면 눈에 띄게 값이 빕니다 — 실패 방향이 반대입니다. 그 계보의 끝은 "로그엔 참조 ID만 남기고, 이메일이 필요하면 그때 DB를 본다"입니다. 로그에 PII가 없으면 마스킹도 필요 없습니다.

### MDC는 왜 비동기 appender에서는 안 끊기나

같은 스레드 경계 문제인데 결과가 갈리는 게 오래 걸렸습니다. `AsyncAppender`의 워커 스레드는 남의 스레드인데도 `trace_id`가 살아 있고, `@Async` 비즈니스 코드에서는 사라집니다.

답은 **복사 시점**이었습니다. MDC는 `log.info()` 호출 순간 이벤트 객체 안으로 스냅샷됩니다. 큐에 들어가는 건 "MDC를 참조하는 이벤트"가 아니라 "MDC 값이 복사된 이벤트"입니다. 그래서 워커의 ThreadLocal이 비어 있어도 무관합니다. `%thread`가 워커 이름이 아니라 원래 요청 스레드 이름으로 찍히는 것도 같은 이유입니다.

| | AsyncAppender | `@Async` 비즈니스 코드 |
| --- | --- | --- |
| MDC | 유지 — Logback이 복사해준다 | 유실 — 아무도 복사하지 않는다 |
| 해결 | 필요 없음 | `TaskDecorator`로 직접 복사 |

즉 "스레드가 바뀌면 MDC가 끊긴다"의 정확한 형태는 **"복사해주는 사람이 없으면 끊긴다"**입니다. 원리도 하나뿐입니다. 제출 스레드에서 ①복사 → 풀 스레드에서 ②심기 → ③`finally`에서 clear. 여기서도 함정이 세 개인데, 그중 잡기 어려운 건 복사를 람다 **안에서** 하는 것입니다. 코드가 그럴듯한데 값이 계속 비어 나옵니다.

그런데 백엔드를 전수로 훑고 나서 결론이 뒤집혔습니다.

| 항목 | 실제 |
| --- | --- |
| 요청 스레드 MDC 주입 | 적용됨 (`TraceIdFilter`) |
| `finally` clear | 적용됨 |
| `@Async`·`@EnableAsync`·`CompletableFuture`·`ThreadPoolTaskExecutor` | `back/src/main`에 0건 |
| `ExecutorService` | 동시성 테스트 2개에만 존재 |

**`TaskDecorator`는 지금 붙일 데가 없었습니다.** 대신 다른 걸 발견했습니다. `@Scheduled`가 12곳(알림 스케줄러 10, 리그 1, 집중 세션 고아 정리 1)이고, 스케줄러는 HTTP 요청이 아니니 `TraceIdFilter`를 안 거칩니다. 여러 배치의 실패 로그가 같은 시각에 `trace_id` 없이 뒤섞여 나옵니다.

이건 성격이 다른 문제였습니다. `@Async`는 있던 값이 **유실**되는 것이라 복사하면 되지만, 스케줄러는 **애초에 없는** 것이라 복사할 원본이 없습니다. `TaskDecorator`로는 못 풀고 새로 발급해야 하며, 12곳에 반복하지 않으려면 AOP로 감싸는 게 정석입니다. 그리고 `MDC.clear()`의 목적이 두 개(다음 요청 오염 방지 + ThreadLocal 누수 방지)라는 것도 여기서 알았습니다. 스레드풀의 스레드는 죽지 않으니 그 스레드의 Map도 죽지 않습니다.

### 7일 뒤 사라지는 로그 — S3와 조회 비용

`maxHistory`는 보관 장치가 아니라 **삭제 장치**입니다. 지금 우리 시스템 로그는 7일 뒤 영영 사라집니다. 다음 단계를 설계하면서 정리한 것들입니다.

- **올리는 건 롤링된 파일만.** 쓰는 중인 `app.log`는 계속 늘어나므로 어디까지 담았는지 알 수 없습니다. 어제 파일은 아무도 안 건드리는 불변 파일이라 안전합니다. 그래서 cron이 새벽 1시입니다 — 자정 롤링 뒤 1시간 여유.
- **Spring cron은 6필드(초 포함).** 리눅스 감각으로 5필드를 쓰면 "매시 1분 0초"로 해석돼 하루 24번 돕니다.
- **다중 인스턴스에서 같은 키로 올리면 덮어써서 로그가 사라집니다.** 반사적으로 분산 락을 떠올렸는데 여기선 오답이었습니다. 한 대로 줄여도 그 한 대는 자기 로컬 파일만 봅니다. 답은 락이 아니라 키에 인스턴스 식별자를 넣는 **키 분리**입니다.
- **컨테이너에서는 저녁 배포 한 번에 그날 로그가 증발합니다.** 새벽 1시까지 파일이 살아 있어야 올라가니까요. 볼륨이냐 수집기냐를 먼저 정해야 하는 문제입니다.
- **`.gz` 한 줄이 저장·전송·조회 비용을 동시에 줄입니다.** 롤링 파일명이 `.gz`로 끝나면 Logback이 롤링 시 자동 압축합니다(대신 `contentType`은 gzip으로).
- **키 설계는 처음에 정해야 합니다.** 날짜 파티션(`dt=YYYY-MM-DD`)과 인스턴스 분리를 처음부터 넣어야 나중에 조회할 때 파티션 프루닝이 먹습니다. 나중에 바꾸면 이미 올라간 객체는 그대로라 두 체계가 섞입니다.

## 지금 아는 것

- **"로깅 실패는 비즈니스에 영향 없게"는 인자 평가 단계까지 지켜야 진짜입니다.** try-catch는 메서드 안에서만 유효합니다.
- **PII 방어의 1차선은 마스킹이 아니라 필드 통제입니다.** payload에는 원시값만, 엔티티는 금지.
- **정규식 마스킹의 정밀도는 그 형식이 얼마나 고유한가에 비례합니다.** 잡는 것보다 부수는 게 많으면 빼는 게 옳습니다.
- **격리는 로거 이름이 아니라 `additivity=false`가 만듭니다.** 레벨 상속과 appender 누적은 독립된 규칙입니다.
- **조용히 깨지는 것들이 제일 비쌉니다.** 빈 MDC, 버려진 ERROR, 오탐으로 훼손된 값 — 모두 예외도 경고도 없습니다. 로그는 쓰는 순간이 유일한 기회입니다.
