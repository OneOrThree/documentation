## 구성 — 막는 단위는 메시지가 아니라 접속

채팅은 같은 섬(그룹) 안에서만 되고, 집중 중에는 **접속 자체**가 막힙니다. 막는 단위가 메시지가 아니라 접속이라 CONNECT·SUBSCRIBE·SEND·REST 가 전부 같은 관문을 지납니다. 서버는 관문에서만 막고 강제 disconnect 는 하지 않습니다 — 집중을 시작하면 앱이 스스로 구독을 끊는 쪽입니다. 채팅은 푸시를 보내지 않으므로 막혀도 놓치는 것이 없고, 안 읽음은 읽음 커서로 셉니다.

인스턴스 간 전파는 Kafka 가 아니라 Redis Pub/Sub 입니다. 팬아웃·멤버십 캐시·프레즌스가 전부 Redis 라 Redis 는 채팅의 하드 의존성이고, 그래서 Redis 응답 시간이 이 PR 의 결함 대부분에 등장합니다. 6월 브랜치(`bfeat/chat-server`)는 리베이스하지 않고 재이식했습니다 — 그 사이 userId 가 Long 에서 UUID 로 바뀌어 그대로 쓸 수 없었습니다.

집중 상태는 [ADR-007](/adr/adr-007-focus-session-liveness) 의 하트비트/리스 위에 얹었습니다. data-api 가 집중 시작 커밋 뒤 `presence:focus:{userId}` 를 놓고 종료 시 지우며, 리스 TTL 은 시작 기준 13시간 — 고아 스윕 상한 12시간에 1시간을 더한 백스톱입니다. 채팅은 이 키의 존재만 봅니다.

## 리스 하나가 겪는 일 — 재구축을 넣기까지

리스는 "놓고 지운다" 두 연산인데, 리뷰 초반 세 라운드가 전부 이 두 연산의 순서와 실패에 대한 것이었습니다.

| 라운드 | 지적 | 조치 |
| --- | --- | --- |
| 3R · codex (`07e9bb49f`) | 커밋 이후 콜백이 트랜잭션마다 다른 스레드라 종료·시작이 겹치면 SET/DEL 순서가 뒤집힘 → 끝난 집중의 SET 이 되살아나 13h 차단 | 세션 id 를 값으로 싣고 Lua 조건부(더 새로울 때만 쓰기 / 그 세션일 때만 해제) + 종료 표식 `:closed`(5분) |
| 5R (`ff34b4f09`) | 회전 시 새 세션의 SET 이 한 번 실패하면 이미 닫힌 이전 세션 id 가 남고, 해제가 엄격 동일 비교라 **아무도 못 지움** | 해제 조건을 「나보다 새롭지 않으면 지운다」로, 회전 시 방금 닫은 마커 해제도 함께 등록 |
| 6R (`ec53684de`) | A19 규칙 「Redis 는 사본, 소유자가 DB 정본에서 재구축할 수 있어야 한다」 미이행 — 플래그를 켜는 순간 이미 집중 중이던 사람들은 세션 끝까지 채팅이 열림 | `FocusPresenceReconciler` 신설(기동 시 미종료 마커 재적재) |
| 7R (`5bcbf857e`) | 재구축이 코어 기동을 붙잡음 — 고아 창 없이 전부 되살림(12시간 넘긴 세션까지), `@Transactional` 이 catch 를 지나쳐 기동 실패, Redis 드롭 시 동기 대기 | 모수를 `now − ORPHAN_TIMEOUT` 이후로, 트랜잭션 경계를 메서드 안으로, 전용 스레드 |
| 8R (`2808a09d3`) | 재구축이 기동 한 번뿐 — 그 순간 Redis 가 흔들리면 끝 | **주기 재구축(5분·ShedLock)**, 쓰기는 「비어 있을 때만」(`restoreLeaseIfMissing` + Lua `SET_IF_ABSENT`) |

7라운드에서 진짜로 배운 것 하나. 재구축을 전용 스레드로 빼면서 공용 실행기에 얹으려 했는데 **이 앱엔 그 빈이 없습니다** — `ga4Executor`·`pushExecutor` 가 `Executor` 빈으로 있어 Boot 의 `applicationTaskExecutor` 자동 구성이 물러나 있었습니다. 플래그를 켜면 기동이 깨지는 상태였는데 스위트는 전부 초록이었습니다. 프레즌스가 통째로 `focus.presence.enabled` 뒤에 있고 기본값이 꺼짐이라 **어떤 테스트도 켜진 형상을 띄우지 않았기 때문**입니다. `FocusPresenceWiringIntegrationTest`(`focus.presence.enabled=true`) 를 두고 나서야 잡혔습니다. 플래그 뒤에 통째로 들어가는 기능은 켠 형상을 부팅하는 테스트가 하나는 있어야 합니다.

8라운드에서 「지연 재시도」 대신 주기 실행을 고른 이유는 백오프가 「몇 번까지·얼마나 오래」를 정해야 하고 그 답이 항상 틀리기 때문이었습니다. 주기 실행은 실패를 감지할 필요가 없습니다. 대신 **매 회차가 잘못 쓸 기회를 갖습니다** — 그게 다음 절입니다.

## 내가 넣은 주기 재구축이 스스로 만든 고장

11라운드(`8c745caef`)에서 codex 가 잡은 것은 8라운드의 제 수정이 만든 구멍이었습니다.

```
t0  재구축이 진행 중 목록을 읽는다        (Redis 장애 중)
t1  유저가 종료 — DB 는 커밋, focusEnded 의 Redis 쓰기는 실패 → 「끝났다」 표식이 없다
t2  Redis 복구
t3  루프가 그 항목에 도달 → 막을 표식이 없으니 리스가 새로 13시간 놓인다
t4  다음 회차 조회는 endedAt 이 찬 행을 제외 → 아무도 그 리스를 치우지 않는다
```

결과가 이 PR 이 도처에서 막으려 한 바로 그 실패 — 끝난 집중이 13시간 채팅을 막음 — 라 더 나빴습니다. 여기서부터 같은 축에 겹이 쌓입니다. 매번 「자가 치유가 실패했을 때 누가 만회하는가」라는 같은 질문의 다른 층이었고, 매번 한 층만 보고 닫았다고 여겼습니다.

| 겹 | 커밋 | 잡은 쪽 | 구멍 | 조치 |
| --- | --- | --- | --- | --- |
| 1 | `8c745caef` | codex 11R | 위 타임라인 | 놓아 준 직후 그 id 들로 정본에 **되묻고** 그 사이 끝난 것의 리스를 회수. 모수가 방금 쓴 목록이라 IN 조회 한 번, 회수는 조건부 삭제 |
| 2 | `f0334b1ba` | claude 최종 | 되묻기 자체가 실패하면 그 세션은 `endedAt` 이 차서 진행 중 조회에 다시는 안 잡힘 → 후보에서 영영 탈락, 백스톱이 TTL 하나(13h) | 실패한 후보를 인스턴스 안에 **기억**했다가 다음 회차에 함께 실음. 상한 1000 |
| 3 | `81b8bfc4e` | codex 16R | **조회 성공을 해제 성공으로 쳤다** — 해제는 별개 Redis 연산이고 `focusEnded` 는 실패를 삼키고 아무것도 돌려주지 않음 | 재구축 전용 해제 `boolean releaseLeaseNow(userId, sessionId)` |
| 4 | `7d22fa317` | Codex 별도 세션 | 복구 쓰기가 실패를 돌려주면 후보에 넣기 전에 중단하는데, **Redis 쓰기는 성공하고 응답만 유실**될 수 있음 → 종료와 경합하면 이후 조회에서도 빠짐 | 실패에서 멈추더라도 쓰기를 **시도한** 세션은 회수 후보로 보존 |

겹 2 에서 claude 가 제안한 「최근 N분 내 종료 전부를 매 회차 훑기」는 안 골랐습니다. `ended_at` 인덱스가 없어 5분마다 전수 스캔이 되고, 창을 장애 길이만큼 넓혀야 하는데 그 비용이 하필 장애 중에 가장 큽니다. 기억은 조회를 한 건도 안 늘리고 같은 창을 닫습니다. 상한 1000 은 DB 가 오래 흔들릴 때 무한히 자라면 이 컴포넌트가 **장애를 메모리 누수로 번역하는** 셈이라 둔 것이고, 넘으면 TTL 에 맡깁니다. 겹 1 에서 「Redis 를 SCAN 해 회수」를 안 고른 이유도 적어 둡니다 — `presence:*` 는 채팅과 공유하는 네임스페이스라 SCAN 주체를 두고 싶지 않았습니다.

겹 3 에서 `focusEnded` 자체에 반환값을 달지 않은 이유가 있습니다. 그쪽은 커밋 콜백으로 미뤄질 수 있어, 반환값을 달면 **부르는 위치에 따라 의미가 달라지는 계약**이 됩니다(트랜잭션 안 = 아직 모르는 값 / 밖 = 진짜 결과). 다음 사람이 반드시 밟는 함정이라, 커밋을 기다리지 않는 재구축 경로에만 결과를 말하는 메서드를 갈라 뒀습니다. 「지울 것이 없는」 경우는 성공입니다 — 그 사이 새 집중이 주인이 된 것이라 안 지우는 것이 옳고, 실패로 치면 대기 목록이 영영 안 빕니다.

| 되묻기 조회 결과 | 처리 |
| --- | --- |
| 아직 진행 중 | 뺀다(다음 회차 재구축이 다시 싣는다) |
| 끝났고 해제 성공 | 뺀다 |
| 끝났는데 해제 실패 | **남긴다** |
| 유저가 끊긴 행 | 뺀다(누구의 리스인지 몰라 재시도 무의미) |

겹 4 는 제가 아니라 Codex 가 별도 세션에서 찾았습니다. 머지 직전 최종 검토를 맡겼더니 `FocusPresenceReconciler.java:231` 을 짚으며 **실제 Redis 에 쓰기를 성공시킨 뒤 타임아웃 예외를 주입해** 재현했고, 제가 고쳐 보라고 넘기자 회귀 테스트 3건과 함께 수정했습니다. 16라운드 장부에 「이 축에서만 네 겹」이라고 적었는데 그 세는 것마저 한 겹 모자랐던 셈입니다.

<Callout label="교훈" tone="warn">
자가 치유를 넣으면 그 치유의 각 단계가 따로 실패한다는 것을 세어야 합니다. 읽기·쓰기·되묻기·해제·응답 수신이 전부 독립적으로 실패할 수 있고, 계약상 삼켜지는 실패는 특히 그렇습니다. 주기 실행은 실패를 감지할 필요를 없애 주지만 매 회차가 잘못 쓸 기회를 갖습니다.
</Callout>

### 곁에 있던 같은 구멍 — 시작 기준인가 놓은 시점 기준인가

12라운드(`92b123f7e`)는 재구축이 새로 놓는 리스에 전체 수명을 준 것이었습니다. 11시간 59분 된 집중의 리스를 그때 처음 놓으면 만료가 지금부터 13시간 → 시작 기준 **25시간**. 8라운드에 「채우기만 하고 손대지 않으면 그 창은 원래대로다」라고 제가 직접 적었는데, 그건 이미 있는 리스에만 해당했고 「없어서 새로 놓는」 경로 — 재구축의 본래 경로 — 에 같은 구멍이 그대로 있었습니다. 한 곳만 고치는 대신 규칙을 하나로 했습니다: 리스는 언제나 `startedAt + LEASE_TTL` 에 만료하고, 백스톱을 넘긴 마커는 아예 쓰지 않습니다. 규칙을 통일하니 지적이 짚지 않은 `focusStarted` 의 순서 역전 방어 분기(오래됐을 수 있는 기존 마커 id 를 싣던 것)도 같이 닫혔습니다.

| ③ | 17R (`3ab5ec06b`) | A19·CLAUDE.md·`RedisKeys` javadoc — 「배포가 `%R~presence:*` 로만 준다」 | 그 ACL 을 적용하는 배포가 없음. dev redis 는 ACL 파일도 비밀번호도 없는 기본 이미지고 두 서비스가 기본 유저를 공유 → **채팅이 `presence:focus:*` 를 지울 수 있다** |

③ 은 「집중 중엔 채팅 불가」를 채팅이 스스로 해제할 수 있다는 뜻입니다. ACL 배선은 인프라 작업이고 채팅은 prod 배포 자체가 없어 GROMO-1744 로 넘겼지만, 문장은 사실대로 고쳤고 티켓에 「`presence:*` 쓰기가 실제로 거부되는지 확인하는 검증을 남길 것」까지 적었습니다 — 안 그러면 그 티켓도 문서만 고치는 일이 됩니다. 규칙 하나가 남았습니다. **코드 주석이 런타임 보증을 말할 때는 그 보증을 누가 강제하는지를 같이 적는다.** 강제 주체가 없으면 「지금은 이 주석뿐이다」라고 씁니다.

| 지적 | 그대로 적용하니 | 최종 |

## 최종 검토 — CONNECT 에서만 검사하던 만료

Codex 별도 세션의 최종 검토는 `5b2a246d6` 기준 P1 2건이었습니다. 하나는 위의 겹 4, 다른 하나는 `StompAuthChannelInterceptor.java:225` — **JWT 만료를 CONNECT 에서만 검사**해서, 같은 사용자의 다른 기기가 유효한 토큰으로 멤버십 캐시를 채우면 만료된 소켓도 그 캐시로 계속 구독·발신할 수 있었습니다. 실제 소켓으로 재현했고, SEND·SUBSCRIBE 에서도 만료를 확인하도록 고쳤습니다. STOMP 세션이 CONNECT 때 토큰을 들고 오래 산다는 사실은 13라운드에서 이미 401 분류로 한 번 다뤘는데, 그때는 「캐시 미스」 경로만 보고 「캐시 히트」 경로를 안 본 것입니다. 같은 축의 모든 발현을 세지 않으면 반쪽만 닫고 닫았다고 적습니다.

## PK 생성기 하나가 data-api 전체를 흔들다

프레즌스 순서 판정은 세션 id(UUID v7)의 시간 순서에 서 있는데, 그 id 를 만드는 data-api 의 `UuidV7Generator` 가 호출마다 새 생성기를 만드는 형태였습니다. UUID v7 은 공유 생성기에서만 같은 ms 안에서 단조이고, 호출마다 새 인스턴스면 20,000건 중 9,993건이 역전됩니다 — 이 PR 본문이 실측해 적은 바로 그 패턴인데 채팅엔 전용 클래스를 만들면서 정작 id 생산자는 안 고쳤습니다. claude 가 더 아픈 걸 짚었습니다. **테스트는 공유 생성기를 쓴다고 주석에 적어 놨는데 프로덕션은 아니어서 이 비일관성이 테스트로 절대 안 드러났습니다.** `common/id/UuidV7` 을 공유 인스턴스로 두고 회귀 테스트(20,000건 역전 0 · 8스레드 40,000건 고유)를 붙였습니다. PK 생성기가 바뀌면 data-api 전체가 영향을 받으므로 이후 라운드마다 전체 스위트(2105건 이상)를 돌렸습니다. 남는 한계는 JVM 하나 안에서만 단조라는 것 — 1743 의 이유입니다.

## 남은 규칙

1. **자가 치유를 넣으면 그 치유가 만들 수 있는 고장을 같이 본다.** 각 단계(읽기·쓰기·되묻기·해제·응답)가 따로 실패한다.
2. **결과를 말하는 메서드와 커밋을 기다리는 메서드를 가른다.** 반환값의 의미가 부르는 위치에 따라 달라지면 그건 계약이 아니다.
3. **백스톱은 「시작한 지」기준이지 「놓은 지」기준이 아니다.** 새로 놓는 경로와 갱신하는 경로를 둘 다 센다.
4. **주석이 런타임 보증을 말하면 강제 주체를 같이 적는다.** 없으면 「지금은 이 주석뿐이다」.
5. **플래그 뒤의 기능은 켠 형상을 부팅하는 테스트가 하나는 있어야 한다.**
6. **리뷰가 켜라는 플래그는 켜고 스위트를 돌려 본 뒤 답한다.**
7. **지적 하나당 티켓 하나가 기본값이 되면 안 된다.**

머지 승인은 아직 남아 있습니다. 09-12 에 이 워크스페이스의 상태·맥락·후속 티켓 3건·미확인 검증을 `HANDOFF-GROMO-292-chat-server.md` 한 장으로 적어 다음 세션에 넘겼습니다.
