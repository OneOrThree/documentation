dev 배포는 7/24를 마지막으로 실배포 성공 0건이었고, 원인은 헬스체크 대기 창 60초였습니다. 마지막 성공조차 12번째 시도 55초 턱걸이였습니다. 같은 여름에 앱 PR 세 건이 3/3으로 같은 Typecheck 스텝에서 죽어 앱 PR이 초록을 받을 방법이 아예 없어졌고, OpenAPI 문서 생성은 브랜치와 무관하게 전부 실패했습니다. 세 건 다 원인은 같은 모양이었습니다. **우리가 정해둔 대기 시간이나 상한이 현실보다 작았고, 코드는 멀쩡했습니다.**

## 세 건 모두 표면 에러가 원인을 가리고 있었다

| 사건 | 표면 에러 | 실제 원인 | 근거로 쓴 실측 | PR |
| --- | --- | --- | --- | --- |
| dev 배포 성공률 0% | 헬스체크 타임아웃 | 대기 창 60초가 부팅보다 짧음 | 마지막 성공도 55초·12번째 시도 | #451 |
| 앱 CI 전면 차단 | `JavaScript heap out of memory` | V8 기본 힙 상한 | 로컬 `tsc --noEmit` peak RSS 880MB | #619 |
| OpenAPI 생성 실패 | `Connection refused` | 앱은 살아 있고 **아직 부팅 중** | 경합 시 부팅 40.008초 실측 | #622 |

세 건은 각각 `cd.yml`, `lint.yml`, 문서 생성 워크플로에서 따로 났고, 겹치는 건 우리가 박아둔 상수뿐이었습니다.

## 7/24 이후 dev 배포 성공 0건

7월 하순부터 dev 실배포가 계속 실패했습니다. 처음엔 급성 사고들이 원인으로 보였습니다. 같은 시기에 Flyway V20 번호 충돌로 3연쇄 장애가 있었고, 그게 CD를 막고 있었으니까요. 그 사고를 별도 티켓으로 정리하고 나서도 배포는 여전히 실패했습니다. 그래서 최근 실행 이력을 통계로 먼저 봤습니다.

| 구분 | 최근 40회 |
| --- | --- |
| 성공 | 12 |
| 실패 | 14 |
| 취소 | 14 |

숫자만 보면 성공 12건이 있으니 "간헐적 실패"로 읽힙니다. 그런데 그 12건이 전부 7/24 이전이었고, 그 뒤로는 실배포 성공이 0건입니다. 어느 날짜를 기점으로 끊긴 분포라, 코드보다 경계를 넘어간 값을 먼저 의심했습니다.

경계를 찾으려고 마지막 성공 런의 로그를 열었습니다. `cd.yml`의 헬스체크는 5초 간격으로 최대 12번, 즉 최대 60초를 기다립니다.

```bash
# 당시 cd.yml 헬스체크 대기 루프 (요약)
for i in $(seq 1 12); do
  curl -fsS http://localhost:8080/health && exit 0
  sleep 5
done
exit 1
```

마지막 성공은 **12번째 시도, 55초**, 루프의 마지막 한 칸에서 통과했습니다. 그리고 실패 런에서 60초 컷오프 시점의 앱 로그를 보니 에러가 하나도 없었습니다. Hibernate 초기화가 진행 중이었을 뿐입니다. 같은 런에서 Flyway는 25개 마이그레이션 검증과 V25 적용을 정상적으로 끝냈습니다.

부팅이 끝나기 전에 워크플로가 대기를 끊었습니다. 대기 루프를 12회에서 30회(최대 150초)로 올렸고, 통과하는 즉시 `exit 0`이라 정상일 때 배포 시간은 늘지 않습니다.

8월에 Datadog APM 오버레이가 배포에서 보존되면서 `-javaagent`가 붙은 부팅이 다시 150초를 넘겨 300초로 재확장했습니다(경위는 [관측 스택 진화 기록](/research/observability-evolution)).

| 시점 | 대기 창 | 확장 근거 |
| --- | --- | --- |
| 초기 | 60초 (5초×12) | — |
| 7/24 실측 후 (#451) | 150초 (5초×30) | 마지막 성공 55초 턱걸이, 실패 시점 앱은 초기화 중 |
| APM 부착 후 (#524) | 300초 (5초×60) | 컷오프 시점 JPA 초기화 중, dev VM 총 부팅 약 3분 |

배포 잡 자체의 타임아웃도 20분에서 40분으로 올렸습니다(#450). 다만 성격이 다른 변경입니다. 상한을 올리면 진짜 고장을 인지하기까지 걸리는 시간도 같이 늘어나서, 그 트레이드오프는 PR에 명시해뒀습니다.

## 결정적 OOM은 flake가 아니다

앱 PR이 CI 초록을 받을 방법이 없어졌습니다. 전부 `lint.yml`의 Typecheck 스텝에서 죽었습니다.

```text
FATAL ERROR: Ineffective mark-compacts near heap limit
Allocation failed - JavaScript heap out of memory
```

세 PR을 나란히 놓고 보니 **3/3**이었습니다. 이 비율이면 결정적 실패입니다. 그리고 이 스텝이 막히면 뒤의 테스트 실행과 codegen 검증이 전부 `skipped`가 되므로, 앱 쪽 검증이 통째로 사라집니다. 상한을 올리기 전에 두 가지를 먼저 확인했습니다.

첫째, 코드 문제가 아님을 확정했습니다. 같은 커밋 세 개를 로컬에서 돌렸습니다.

| 브랜치 | typecheck | 테스트 |
| --- | --- | --- |
| A | 통과 | 1,578개 / 124 스위트 |
| B | 통과 | 1,578개 / 125 스위트 |
| C | 통과 | 1,760개 / 142 스위트 |

타입 에러는 하나도 없었습니다. CI에 남은 실패 메시지는 힙 고갈이었습니다.

둘째, 처방할 숫자의 근거를 만들었습니다. 로컬에서 `tsc --noEmit`의 peak RSS를 재보니 880MB였습니다. 당시 러너는 `e2-medium`(2 vCPU / 4GB)이었습니다(뒤에 `e2-custom-4-8192`로 상향됩니다). 그래서 2048MB로 정했습니다. 880MB에 성장 여유를 얹기엔 충분하고, 4GB 박스에서 OS·npm·러너 에이전트 몫을 남겨야 하니 3072MB는 스왑 위험이 있어 피했습니다.

```yaml
# lint 잡에 잡 레벨 env 한 줄
env:
  NODE_OPTIONS: --max-old-space-size=2048
```

한 줄짜리 변경이지만, PR에는 이걸로 안 풀릴 경우의 다음 수까지 적어뒀습니다. 에러가 `Ineffective mark-compacts near heap limit`이라는 건 V8 자체 상한에 부딪혔다는 뜻으로 읽었는데, 물리 메모리가 실제로 부족한 것이라면 상한만 올려도 OOM killer로 바뀔 뿐입니다. 그 경우엔 머신타입 상향, 이 잡을 GitHub 호스티드 러너로 이관, `tsc` 프로젝트 참조 분할 중 하나가 필요합니다.

이 PR을 먼저 넣는 게 판정으로도 가장 저렴하다고 판단했습니다. 통과하면 V8 상한 문제였음이 확정되고, 실패하면 위 세 가지로 바로 넘어가면 됩니다.

## 앱이 죽은 게 아니라 아직 부팅 중이었다

세 번째는 `Generate OpenAPI Docs`입니다. 특정 시각 이후 `main`을 포함한 모든 브랜치에서 실패했고, 한 브랜치는 4회 연속으로 죽었습니다. 분포만 봐도 파이프라인 문제였습니다. 로컬에서 같은 태스크가 gitignored config 누락으로 죽던 건은 원인이 다른 별개 사건입니다([부하테스트 하네스 구축기](/research/loadtest-harness)).

표면 메시지는 `Connection refused`라 "앱이 안 뜬다"로 읽힙니다. 실패 런의 앱 로그를 열어보니 상황이 달랐습니다.

```text
12:29:33  Starting PhoneApplication
12:29:48  Tomcat initialized with port 8080      (15초)
12:29:53  HikariPool-1 - Starting...
12:29:54  HikariPool-1 - Start completed         (21초 — DB 연결 완료)
12:29:59  Unable to connect ... waited for 30 seconds
```

`Started PhoneApplication`이 끝내 안 찍힙니다. 21초에 겨우 DataSource를 열었고, 남은 Hibernate SessionFactory와 엔티티 메타데이터 구축이 30초 창 안에 못 끝났습니다. 플러그인의 30초는 앱 로그 첫 줄보다 이른 JVM fork 시점부터 셉니다. 서비스 컨테이너(postgres)는 healthy였고 포트 매핑도 정상이라 DB 문제가 아니었습니다. 같은 앱이 개발 머신에서는 3.5초에 뜹니다. 결국 걸린 값은 `back/build.gradle`의 `waitTimeInSeconds` 30이었습니다.

하필 그날 머지가 몰렸습니다. 두 시간 남짓한 창에 알림 재편·내기 2계층 재편·챌린지 테이블 v2·참가자 스코프 API를 한꺼번에 넣었습니다. 빈이 늘어 부팅이 30초를 넘겼고, 원래 아슬아슬하던 값이 넘어가면서 백엔드를 건드리는 모든 PR이 한꺼번에 깨졌습니다. 앞의 헬스체크 60초와 같은 구조입니다.

앞의 lint OOM 이후 러너가 4 vCPU / 8GB로 상향되면서 한 VM 위에 러너 프로세스가 3개 돌게 바뀌었습니다. "스펙업했으니 30초로도 되지 않을까"를 확인하려고, 수정이 없는 `main`과 수정이 있는 브랜치를 같은 날 나란히 돌려 부팅 시간을 직접 쟀습니다.

| 런 | 수정 | 동시 실행 | `Started PhoneApplication` | 30초 판정 |
| --- | --- | --- | --- | --- |
| `main` | 없음 | 단독 | 16.065초 | 통과 |
| 이 브랜치 | 있음 | 러너 3개 경합 | 40.008초 | 초과 |

여기서 '수정'은 대기 시간과 `paths` 필터 변경이라 앱 부팅 자체에는 영향이 없습니다. 두 런을 갈라놓은 변수는 러너 경합 하나뿐입니다.

러너가 한가하면 16초에 뜨니 스펙업만으로도 그때는 통과합니다. 그러나 **러너 3개가 겹치면 40초**이고, 4 vCPU 한 대에 러너 셋을 얹었으니 백엔드 테스트·Lint·Docker 빌드가 상시 겹칩니다. 즉 30초는 러너가 놀 때만 통과하는 값이라, 대기를 180초로 올렸습니다.

대가도 있습니다. 앱이 진짜로 못 뜨는 경우 실패 판정이 30초에서 180초로 늦어집니다. 다만 그 경우에도 job 로그에 앱 스택트레이스가 그대로 남고, 실제로 이 티켓의 원인도 같은 아침 dev를 내려앉힌 스키마 불일치도 그 로그로 찾았습니다. 상시 빨간 것보다 3분 대기가 낫다고 판단했습니다.

### 같은 조사에서 나온 2차 장애 — 호스트 포트 :5432

재측정 도중 `test` 잡이 15초 만에 죽는 새 실패가 나왔습니다. 컨테이너 초기화 단계에서 끝나 테스트가 시작되지도 못했습니다.

```text
Bind for 0.0.0.0:5432 failed: port is already allocated
Docker start fail with exit code 1
```

러너 프로세스는 3개지만 VM은 한 대라 호스트 네트워크를 공유합니다. 그런데 두 워크플로가 postgres를 호스트 포트 고정으로 발행하고 있었습니다.

| 잡 | 러너 | 시작 | 호스트 5432 |
| --- | --- | --- | --- |
| `generate-docs` | 러너 2 | 13:27:15 | 13:34:13까지 점유 |
| `test` | 러너 1 | 13:27:22 (7초 뒤) | 바인드 실패 |

**러너가 1대였을 땐 큐가 직렬이라 겹칠 수 없었습니다.** 3중화하면서 동시 실행이 생기자마자 터진 겁니다. 다른 브랜치에서도 같은 에러로 `test`가 죽은 걸 확인했고, 백엔드 PR은 `test`와 `generate-docs`가 함께 트리거되므로 앞으로 거의 매번 부딪힐 구조였습니다. 호스트 포트를 도커에 맡기고, 실제 매핑 포트를 잡 컨텍스트에서 읽어 `SPRING_DATASOURCE_URL`로 주입하는 방식으로 풀었습니다. Testcontainers를 쓰는 테스트들은 `@DynamicPropertySource`가 env보다 우선하므로 영향이 없습니다.

여기에 한 가지 더 걸렸습니다. 워크플로의 `paths` 필터가 `back/src/main/java/**`뿐이라 `build.gradle`만 고치면 그 워크플로가 아예 안 돕니다. 다른 워크플로도 `back/**`뿐이라 워크플로만 고치는 PR에서는 `test`가 안 돕니다. 머지해봐야 맞는지 아는 구조였다는 뜻입니다. 그래서 `paths`에 워크플로 자신과 호출 대상, `back/build.gradle`을 함께 추가했고, 그 덕분에 이 PR 안에서 `generate-docs`가 실제로 돌아 `Started PhoneApplication in 40.008 seconds`와 문서 생성까지 로그로 확인할 수 있었습니다.

## 러너 인프라를 알아야 로그가 읽힌다

위 세 건은 전부 GCP 위의 self-hosted 러너에서 났고, 러너가 어떻게 생겼는지 모르는 채로는 로그 해석이 안 됐습니다. CI 러너는 상시 켜둔 `e2-custom-4-8192` 한 대에 프로세스 3개입니다. 부하테스트 러너는 별도 MIG에 올려 `make runner-up`/`make runner-down`으로만 켜고 끄는 온디맨드 풀로 뒀습니다(구성은 [부하테스트 하네스 구축기](/research/loadtest-harness)).

**러너 등록은 WIF와 방향이 반대입니다.** 대시보드에서 버튼을 눌렀더니 GitHub Actions에 job은 뜨는데 GCP에서는 아무 일도 일어나지 않았습니다. `runs-on`의 라벨을 가진 러너가 하나도 없으면 job은 생성만 되고 큐에서 스텝 0개로 무기한 대기합니다. WIF는 job이 GCP 서비스 어카운트를 사칭하는 방향(job → GCP)이고, 러너 등록은 VM이 자기를 GitHub에 올리는 방향(VM → GitHub)이라, WIF가 있어도 러너 VM이 GitHub 크리덴셜로 등록 토큰을 받아 `config.sh`를 돌려야 합니다. 여기서 조용한 실패를 하나 겪었습니다. `config.sh --name`에 FQDN을 넘기면 이름이 64자를 넘겨 등록이 거부되는데, 도구 설치와 인증이 다 끝난 뒤 마지막 이름에서 실패하니 로그만 보면 원인이 안 보였습니다. `hostname -s`로 바꿔 해결했습니다.

## 남은 부채와 규칙화

- **앱이 쓰는 호스트 포트 8080은 아직 고정입니다.** 문서 생성 잡이 두 개 동시에 뜨면 postgres와 같은 방식으로 부딪힐 수 있습니다. 앱이 직접 바인드하는 포트라 `apiDocsUrl` 파라미터화가 필요합니다.
- **4 vCPU 한 대에 러너 3개**라는 구성 자체가 경합의 원인입니다. 180초도 부팅이 더 느려지면 언젠가 넘고, 상향 전 같은 러너에서 앱 lint 힙 부족도 났습니다. VM 증설이나 일부 잡의 호스티드 이관이 남은 과제입니다.
- **타임아웃 상향은 인지 지연과 맞바꾸는 선택**입니다. 배포 잡 20분→40분, 리뷰 잡 10분→40분 모두 같은 대가를 지불했습니다.

정리하면서 규칙으로 만든 게 세 개입니다.

1. **실패한 시점의 앱 로그를 연다.** `Connection refused`와 "부팅 중"은 로그를 열기 전까지 구분되지 않습니다.
2. **실패 분포를 먼저 본다.** 3/3은 결정적 실패고, 성공 12건이 전부 7/24 이전이면 특정 시점부터 끊긴 분포입니다. 이 판정 하나로 조사 방향을 절반 이상 좁혔습니다.
3. **숫자를 바꿀 땐 실측 근거를 워크플로 주석으로 같이 커밋한다.** 880MB, 55초, 16초 대 40.008초. 근거 없는 상한은 다음 사람이 이유를 몰라 못 건드립니다.
