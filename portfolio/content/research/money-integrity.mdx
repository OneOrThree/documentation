철회 후 재참여하면 참가비가 0원이었습니다. 차감 함수는 중복 멱등키에도 예외를 던지지 않고 INFO 로그 한 줄만 남겼고, 호출부는 그 반환값을 버렸습니다. 6월 초부터 8월 10일까지 재화·정산 워크스트림 18개 PR에서 잡은 돈 결함은 P0 3종을 포함해 대부분 같은 세 자리로 수렴했고, 나머지 하나는 실패한 정산에 처분이 없다는 문제였습니다.

1. 금액과 사유는 서버가 계산해야 합니다. 클라가 보낸 `amount`를 그대로 더하는 API는 재화 발행기입니다.
2. 멱등키를 유저 축으로 잡으면 "행을 지우고 다시 만드는" 모든 동선이 무임승차가 됩니다.
3. 유저 행을 바꾸는 경로는 처음부터 배타 락으로 쥐어야 합니다. 공유 락으로 읽고 뒤늦게 쓰는 경로가 하나라도 남으면 그 틈으로 환불이 두 번 나가고, PII가 되살아납니다.

검증 수단은 하나였습니다. 돈 경로의 동시성 결함은 강제 인터리빙 테스트로만 존재를 증명할 수 있고, 수정 전 코드로 3/3 실패를 먼저 확인해야 무엇을 고쳤는지 말할 수 있습니다.

## 금액의 출처를 서버로 옮기다

초기 인게임 재화는 `POST /currency/earn`이었습니다. 클라가 금액과 사유를 body에 담아 fire-and-forget으로 던지고, 서버는 지갑 잔액을 그만큼 올렸습니다. 집중 세션 보상을 앱에서 계산하던 시절에는 자연스러운 설계였습니다. 내기 시스템이 붙어 코인이 판돈이 되자, `earn`은 클라가 부르는 금액을 그대로 찍어 주는 엔드포인트가 됐습니다.

지급 지점을 세션 저장 트랜잭션 안으로 옮겨, 서버가 보상을 계산하고 원장에 기입하도록 바꿨습니다.

```java
// 세션 저장 트랜잭션 안에서 지급 — 멱등키가 같은 세션의 이중 지급을 차단
credit(user, SESSION_COMPLETE, reward, "focus:" + sessionId + ":reward");
```

보상 공식은 앱이 쓰던 `floor(집중초 / 10)`을 그대로 포팅했습니다. 서버가 보는 집중초는 `(endedAt − startedAt) − totalDistractionSeconds`이고, 음수 방어를 넣은 뒤 경계값 12종을 diff 단위 테스트로 고정했습니다. 공식이 앱과 어긋나면 유저 화면의 숫자와 지갑 잔액이 달라집니다.

이관하면서 신경 쓴 것은 **구앱과 신앱이 동시에 붙어 있는 기간**이었습니다. `earn`을 없애면 구앱이 500을 받고, 그냥 두면 구앱은 두 번 지급받습니다. 그래서 `earn`을 잔액·원장 무변화 no-op으로 만들고 204를 유지했습니다.

| 앱 버전 | 세션 저장 시 | `/currency/earn` | 총 지급 |
| --- | --- | --- | --- |
| 구앱 | 서버 지급 1회 | 호출하지만 no-op | 정확히 1회 |
| 신앱 | 서버 지급 1회 | 호출 안 함 | 정확히 1회 |

어느 조합에서도 1회임을 확인하고 나서 버전 게이팅과 배포 순서 제약을 둘 다 걷어냈습니다. `earn` 호출이 언제 0이 되는지 보려고 no-op 경로에 로그만 남겼습니다. 차감 쪽 `/currency/spend`는 사유 화이트리스트와 양수 검증이 이미 있어 그대로 뒀습니다. 차감은 유저가 자기에게 불리한 방향으로만 조작할 수 있어서 위험의 결이 다르기 때문입니다.

## 멱등키의 축이 구멍의 크기를 정한다

내기 참가비 차감의 멱등키는 처음에 `bet:{betId}:stake:{userId}`였습니다. 유저 축입니다. 여기에 "시작 전까지는 철회 후 재참여가 가능해야 한다"는 요구가 들어왔습니다.

철회는 참가 행을 물리 삭제합니다. 그러면 다음이 성립합니다.

```text
참가   → debit(bet:{betId}:stake:{userId})  기입 생성, 참가비 차감
철회   → 참가 행 DELETE (원장 기입은 남는다)
재참여 → debit(같은 키) → 이미 있으니 조용히 skip, false 반환
       → 참가 행만 생성. 참가비 0원.
```

여기에 앞서 말한 **버려진 반환값**이 겹칩니다. 정산 판돈은 `참가비 × 참가자 수`로 계산하므로, 걷히지 않은 코인이 승자에게 지급됩니다. 서비스 레이어에도 DB 유니크 제약에도 이걸 잡을 장치가 없었습니다.

그래서 축을 옮겼습니다. 참가 행은 참가마다 새로 만들어지는 UUID v7이라, 키에 참가 행 id를 넣으면 회차가 키 수준에서 갈립니다.

| 용도 | 옛 키 | 새 키 |
| --- | --- | --- |
| 참가비 차감 | `bet:{betId}:stake:{userId}` | `bet:{betId}:stake:{participantId}` |
| 철회 환불 | 정산 환불 키를 공용 | `bet:{betId}:leave-refund:{participantId}` |

축을 바꾸면서 **알지도 못했던 버그 하나를 덤으로 닫았습니다.** 종전에는 철회 환불이 정산 환불 키를 미리 소진해서, "참가 → 철회 → 재참여 → 그룹 탈퇴" 경로를 탄 유저만 환불이 조용히 스킵됐습니다. 이번엔 유저 손해 쪽이었습니다. 환불 키 하나를 두 경로가 공유해서, 같은 키가 유저 이득 쪽과 손해 쪽으로 각각 한 번씩 새고 있었습니다.

그리고 반환값 검사를 넣었습니다. 키에 참가 행 id가 들어간 뒤로 중복 선점은 도달 불가지만, 그래도 `false`가 오면 id 생성이나 키 규약이 깨진 것이므로 그냥 넘기는 대신 트랜잭션 전체를 되돌리게 했습니다. 차감 없는 참가 행이 남는 것보다 요청 실패가 안전합니다.

이 PR의 핵심 산출물은 회귀 락 테스트였습니다. 실제 `joinBet → leaveBet → joinBet` 경로를 타면서 최종 잔액, 차감 기입 2건, 멱등키 중복 없음, 옛 키 포맷 부재를 단언합니다. 기존 테스트들은 참가 행을 헬퍼로 직접 삽입해서 **이 경로를 한 번도 타지 않았습니다.** "철회 후 재참여 시 코인이 실제로 다시 차감되는가"를 검증하는 테스트가 백엔드와 앱 어디에도 없었다는 것이, 이 결함이 프로덕션까지 간 이유였습니다.

## P0 3종을 강제 인터리빙으로 3/3 재현하다

8월 8일 챌린지 정책을 백지에서 다시 쓰면서, 정책 문장과 코드를 한 줄씩 대조했더니 P0 등급 돈 결함 세 개가 나왔습니다. 셋 다 같은 파일군을 건드려서 쪼개면 서로 충돌하므로 한 PR(#544 · GROMO-1258)로 묶었습니다.

**① 이중 환불.** 내기 취소와 그룹 탈퇴가 겹치면 같은 참가비가 두 번 나갔습니다. 네 조건이 겹쳐야 열리는 창이었습니다.

- 탈퇴 경로가 대상 내기를 **잠금 전 평문 SELECT**로 뽑음 (TOCTOU)
- 잠금 후 재검증이 "내기가 열려 있는가"뿐이고, "이 유저가 아직 참가자인가"는 안 봄
- 환불 멱등키 축이 경로별로 갈림 — 철회는 참가 행 축, 탈퇴는 유저 축 → 원장 유니크가 교차 경로를 못 막음
- 취소와 그룹 탈퇴 두 경로가 모두 공유 락으로 유저를 읽음. 같은 자리를 계정 탈퇴는 배타 락으로 쥐고 있어 창이 닫혀 있었고, 그룹 탈퇴만 뚫려 있었음

수정은 잠금 후 참가 행 실재를 재검증하고, 취소·철회·탈퇴·무산의 환불 키를 전부 `bet:{betId}:refund:{participantId}` 하나로 통일한 것입니다. 위 표에 새 키로 적어 둔 leave-refund 키도 이때 이 하나로 흡수했습니다. 차감 키와 1:1로 대응하니 "한 번 걷힌 참가 행은 어떤 경로로든 정확히 한 번만 돌아온다"를 원장 유니크가 보장합니다.

**② 탈퇴가 '시작 후 취소 금지'를 우회.** 시작 가드가 철회 경로에만 있고 탈퇴 경로에는 아예 없었습니다. 지는 판이 시작된 뒤 그룹을 나가면 전액 환불됐습니다. 판정부를 추출해 두 경로가 공유하게 했는데, 탈퇴 쪽은 예외를 던지지 않고 **스킵**으로 처리했습니다. 던지면 "지는 판이 하나라도 있으면 그룹을 못 나간다"가 되고, 계정 탈퇴가 통째로 실패합니다. 시작된 회차는 참가 행과 판돈을 보존해 정산 대상으로 남깁니다. 목표 해석에 실패하면 "시작됨"으로 판정합니다. 모르는 채로 환불하기보다 에스크로에 남겨 두는 편이 낫다고 보고 기본값을 그렇게 잡았습니다.

**③ 판돈 무기한 동결.** 정산 실패에 재시도가 없어서, 영구 실패 3종(참가자 유실·목표 유실·불변식 위반)은 매일 같은 지점에서 터졌습니다. 동결 감지는 error 로그만 남기고 처분이 없었고, prod에는 수동 트리거조차 없었습니다. 감지에 처분을 붙여 24시간 넘긴 회차를 환불 상태로 닫고 전원 환불하게 했고, 생성 코드가 없어 죽어 있던 환불 상태 enum을 현역으로 되살렸습니다. "정산은 불가역"이라는 원칙과 충돌하지 않습니다. 닫는 대상은 **정산 자체가 영원히 불가능해진 회차**이고, 이미 정산된 건은 그대로 둡니다.

저장소 전체에 취소×탈퇴 조합의 동시성 테스트가 하나도 없어서 이 결함이 프로덕션까지 갔습니다. 그래서 `CyclicBarrier`로 두 경로를 강제 인터리빙하는 테스트를 쓰고, **옛 동작을 임시로 복원해 3회 돌려 3/3 실패**(`expected: 1L but was: 2L`)를 확인한 뒤 임시 코드를 되돌렸습니다. 이 순서를 밟지 않으면 테스트가 그린인 이유가 "고쳤기 때문"인지 "애초에 그 경로를 안 타기 때문"인지 구별할 수 없습니다.

기존 탈퇴 테스트 3건은 기대값을 뒤집었습니다. 시작된 회차는 탈퇴해도 환불되지 않는 것이 새 정답입니다. 날짜 기준은 UTC CI에서 어긋나지 않도록 전부 KST로 못박았습니다.

```text
SPRING_PROFILES_ACTIVE=ci ./gradlew test checkstyleMain spotbugsMain
classes 140  tests 1414  failures 0  errors 0  skipped 7
spotbugs BugInstance count = 0
```

## 전체 롤백에서 건별 격리로

리그 주간 정산은 전 유저를 단일 트랜잭션으로 처리했습니다. 정산 도중 회원 탈퇴 1건이 커밋되면 배치 전체가 롤백됐습니다. anchor 미생성, 전원 미정산, 승급 보너스 소실입니다. 조사해보니 탈퇴 커밋이 정산 배치와 네 지점에서 부딪혔습니다.

| 충돌 | 메커니즘 | 결과 |
| --- | --- | --- |
| 재조회 실패 | 집계 조회~재조회 사이 탈퇴 커밋 | 유저 조회 예외 → 전체 롤백 |
| 지갑 삭제 | 승급자 지갑이 탈퇴로 삭제 | 지급 시 NOT_FOUND → 전체 롤백 |
| 행 락 점유 | 유저 행 락을 배치 끝까지 보유 | 탈퇴 HTTP 요청 무한 대기 |
| lost update | 버전 없는 full-row UPDATE | 탈퇴가 파기한 PII 부활 |

구조를 셋으로 쪼갰습니다. 오케스트레이터는 트랜잭션을 갖지 않고, anchor 회전(가드·마감·생성)만 먼저 커밋하고, 유저 1명 정산이 하나의 트랜잭션 경계가 됩니다. 자기 호출은 프록시를 타지 않으므로 빈을 분리해야 했습니다.

건 안에서는 유저를 **배타 락으로 재조회**합니다. 탈퇴가 선커밋된 상태면 예외 없이 결정론적으로 스킵되고, 락을 먼저 쥐면 탈퇴가 직렬화되어 지갑 생존이 보장됩니다. 잠금 순서를 유저→지갑으로 양쪽에서 동일하게 맞춰 교착을 피했고, PII lost update 창도 같이 닫았습니다. 유저 행을 바꾸는 경로는 처음부터 배타 락으로 쥔다는 규율을 이 배치에서 확정했습니다.

부수적으로 티어 설정 검증을 anchor 선커밋 **앞으로** 당겼습니다. 깨진 설정으로 anchor만 커밋되면 재실행이 "이미 실행됨" 가드에 막혀 그 주차 정산이 통째로 유실됩니다. 정산 루프가 프로세스 크래시로 중단되면 여전히 같은 가드에 막히는데, 그 잔여 트레이드오프와 이후 resume 진입점으로 푼 과정은 [리그 배치 노트](/research/league-batch)에 적었습니다.

## 멱등키를 구조에 흡수시키다

내기를 설정(챌린지와 1:1)과 회차(참가·판정·정산의 단위) 2계층으로 쪼개면서, 앞서 봉합한 P0 3종을 **새 수정 없이 설계로 흡수**하도록 만들었습니다. 돈 경로에서 남길 것은 두 가지입니다.

첫째, 환불 멱등키의 축을 회차로 옮겨 `session:{sid}:refund:{participantId}` 단일 키로 못박았습니다. 앞 절에서 통일한 `bet:{betId}:refund:{participantId}`를 대체한 키이고, 취소·철회·탈퇴·무산이 하나의 키를 공유한다는 성질은 그대로 승계됩니다. 잠금 순서도 유저→멤버십→회차→지갑으로 확장해 고정했고, 참여는 멤버십 행 공유 락, 탈퇴 정리는 배타 락 선점입니다.

둘째, 회차 id로 구 내기 행 id를 재사용했습니다. 원장 멱등키와 알림 dedup이 참조하는 id가 불변으로 유지되니, 스키마를 바꾸면서도 멱등성 불변식이 마이그레이션을 통과합니다. 참가비 상한은 DB CHECK로 못박았습니다. 철회×탈퇴와 참가×탈퇴 두 조합은 새 구조에서 다시 인터리빙으로 확인했습니다. 그 결과와 상태 어휘 분리, 구앱 응답 형태 유지, 크론 재설계 같은 도메인 재편 쪽 결정은 [챌린지 백지 재정의 노트](/research/challenge-rebuild)로 넘겼습니다.

판정 단일화에서도 돈에 직결된 결정이 하나 나왔습니다. **스크린타임 권한을 철회한 유저를 미계측(=미달성)으로 확정**한 것입니다. 스크린타임은 작을수록 이기는 지표라서, 오전 9시에 권한을 끄면 그 시점의 부분 측정값으로 "하루 2시간 이하"를 완승합니다. 반대로 판정하면 측정을 끄는 행위가 곧 승리 조건이 됩니다. 원장에서 보면 참가비는 회차 시작 시점에 이미 걷혀 기입돼 있고, 정산이 그 판돈을 승자 지갑으로 지급 기입하면 회차가 닫힙니다. 정정 수단인 역분개는 아직 설계 단계여서, 잘못 나간 지급을 원장에서 되돌릴 방법이 없습니다. 판정 커널 통합과 이 규칙이 참가 자격 검사에 남긴 구멍은 [챌린지 백지 재정의 노트](/research/challenge-rebuild)에 있습니다.

## 아직 증명하지 못한 것

여기까지가 사고 대응이고, 설계 목표는 따로 있습니다. 지금 잔액은 여전히 mutable 컬럼이고, 거래 기록 테이블은 원장의 씨앗일 뿐입니다. 지향점은 이중부기 원장입니다. 모든 변동을 차변·대변 쌍으로 append하고, 잔액은 원장의 파생값(프로젝션)으로 두고, 원장 UPDATE와 DELETE를 DB 권한으로 봉쇄하고, 정정은 역분개만 허용하는 구조입니다. 그러면 "합이 0이 아니다"라는 자기 검증이 가능해집니다.

단계는 이렇게 잡아 뒀습니다.

| 단계 | 무엇 | 지금 상태 |
| --- | --- | --- |
| 1 | 잔액 컬럼 + 클라 신뢰 | 벗어남 |
| 2 | server-authoritative + 원자적 구매 | 지급은 이관 완료, 구매 원자성은 남음 |
| 3 | 이중부기 원장 + 멱등 키 | 멱등키만 확보, 원장은 설계 |
| 4 | 정산 엔진(라운딩 잔여 규칙·분배 합 검증) | 부분 |
| 5 | 대사 배치 + Outbox | 미착수 |

증명 쪽 숙제도 목록으로 남겼습니다. 잔액 차감의 낙관적 락은 엔티티에 버전 컬럼이 있는데 **재시도 로직이 없어서** 동시 요청 시 하나는 예외로 실패합니다. 이중 차감은 막히지만 "충돌 시 하나만 성공"이 UX상 허용되는지는 아직 판단하지 못했습니다. 낙관적 락, 비관적 락, 유니크 제약을 같은 부하 프로파일에서 재보고 변곡점을 숫자로 남기는 것이 다음 목표입니다. 세 기법의 선택 기준 자체는 [동시성 방어선 노트](/research/concurrency-defense)에 정리해 뒀습니다.

```java
// check-then-act — 잔액 검사와 차감이 단일 스레드 가정.
// 커밋 시점 버전 충돌로 이중 차감은 막히지만, 재시도가 없어 진 요청은 예외로 끝난다
if (this.currency < amount) throw new CurrencyException(INSUFFICIENT_CURRENCY);
this.currency -= amount;
```

그 위로 crash-point 테스트(원장 INSERT 후 / outbox 기록 전 / 커밋 후 응답 전에서 강제 종료 → 재시도 → 불변식 검증), 같은 멱등키 동시 2요청의 in-flight 처리, 속성 기반 테스트로 무작위 인터리빙 수천 회, 그리고 일 1회 3중 대사(원장 합=0 / 원장 SUM vs 잔액 / 원장 vs 비즈니스 이벤트)가 남아 있습니다.

세 달 동안 배운 가장 큰 것은, 정합성은 지키는 게 아니라 **매일 검증하는** 것이라는 점입니다. 그동안 잡은 결함은 전부 사람이 정책 문장과 코드를 대조하다 찾은 것이고, 원장의 합을 자동으로 검증하는 절차는 아직 없습니다. 위 목록의 일 1회 3중 대사가 그 첫 칸입니다.
