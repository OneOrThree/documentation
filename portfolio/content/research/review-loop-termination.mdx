결론부터 적습니다. 리뷰 루프의 종료 조건은 3개월 동안 여섯 번 바뀌었고, 마지막 형태는 **"CI 초록 · 미답변 스레드 0 · codex 👍(또는 "didn't find major issues") · claude 종결 판정" 4부를 통과하면 오너가 머지한다**입니다. 👍는 정식 APPROVE가 아닙니다 — 이 레포는 브랜치 보호가 없어 `reviewDecision`이 빈 값이고, Claude Code Action은 보안 정책상 approve를 제출하지 않습니다. 그래서 봇 둘이 무엇을 말하든 머지 버튼은 사람 몫입니다.

루프가 헛돈 시간의 대부분은 리뷰어 쪽이 아니라 **제가 만든 감시 장치**에서 났습니다. 코멘트 개수만 세기, `claude[bot]` 로그인 불일치, comment id 순서 필터로 7건 누락, 존재하지 않는 `updatedAt` 필드, `--paginate` 누락, 9자 SHA와 40자 commit_id 비교, 자기 답변을 새 리뷰로 오탐 — 여덟 가지가 차례로 나왔고 전부 "리뷰가 안 왔다"는 거짓 결론을 냈습니다. 아래는 정의의 변천, 감시 장치의 결함, 재트리거와 한도, 라운드 수 실측, 로컬 게이트의 한계, 그리고 도구 필터가 판정을 가린 사례입니다.

## 1. 루프 정의는 여섯 번 바뀌었다

👍가 도착하는 속도는 빠릅니다. 08-19 13:50 #683에서 수정 커밋 `04:43:40Z` → codex 👍 `04:46:28Z`, 3분이었습니다. 반응 시각이 마지막 커밋보다 뒤여야 최종 상태를 본 판정이라는 것도 이때 규칙이 됐습니다(09-11 #734 판정문에 같은 논리).

08-01 22:29의 자체 관찰이 이 표의 요약입니다. "대장 규칙 덕에 기결정 재론은 차단되고 있습니다 … 심각도가 P2·UX급으로 내려왔고". 라운드가 늘수록 지적의 심각도는 내려가지만 0이 되지는 않았고, 그래서 "언제 끝나는가"는 리뷰어가 아니라 판정 규칙이 정해야 했습니다.

<Callout label="자기 급식" tone="warn">
푸시가 다음 라운드를 부르는 구조라, 지적을 반영한 커밋 자체가 새 리뷰를 트리거합니다. 08-14 05:28 "여기서부터는 @claude를 더 부르지 않습니다 — 푸시가 다음 라운드를 부르는 구조라 의도적으로 닫습니다." 09-10 17:30에는 제 답변 코멘트가 `@codex review`로 시작해 스스로 2라운드를 트리거했고, 21:19에는 push만으로도 라운드가 돈다는 것을 메모리에 정정했습니다.
</Callout>

## 2. 감시 장치는 여덟 번 틀렸다

리뷰어가 침묵한 게 아니라 제 워처가 못 본 경우가 대부분이었습니다. 전부 "리뷰 없음"이라는 **false negative**로 나타났기 때문에 루프가 조용히 멈췄습니다.

| 날짜 | 결함 | 결과 | 수정 |
| --- | --- | --- | --- |
| 07-10 15:39 | @claude가 "분석 중" 플레이스홀더를 먼저 게시 | 폴링이 10분 타임아웃으로 종료 | 재폴링 |
| 08-07 12:52 | 코멘트 **개수**만 셈 | claude가 진행 중 체크리스트를 제자리 수정으로 최종 리뷰로 바꾼 것을 놓침(18분) | 내용 비교 |
| 08-07 12:53 | REST 로그인이 `claude[bot]`인데 `== "claude"` 매칭 | 0건 | 접미 허용 |
| 08-09 21:25 | comment **id**로 필터 | 제 답글(11:08) id가 3차 코멘트(11:00) id보다 커서 7건 통째로 걸러짐 | `created_at` 기준 |

가장 아픈 건 09-10 18:39 두 번째 사고입니다. 반영 적용 스크립트가 중간 assert로 죽었는데 그걸 읽지 않고 **커밋 없이 "반영했습니다" 답변 10건이 먼저 나갔습니다.** 직후 실제 반영으로 수습했지만 "했다"고 말하기 전에 반영 결과를 조회한다는 원칙을 다시 어긴 것이었습니다. 감시 스크립트의 결함은 리뷰를 못 보는 쪽으로만 나지 않습니다 — 반대 방향으로는 하지 않은 일을 했다고 말하게 만듭니다.

## 3. 재트리거와 한도 — 봇도 죽고 에이전트도 죽는다

codex는 푸시에만 반응합니다. 그래서 리뷰를 다시 부르는 표준 수단이 **빈 커밋**이 됐습니다. 08-18 19:10 `git commit-tree`로 "codex 자동 리뷰 재트리거용 빈 커밋"을 만들어 푸시한 것이 처음이고, 09-12 16:36에는 PR 5건에 한 번씩, 09-13에는 #740에 두 번 썼습니다. 09-13 00:48에는 반대 방향의 정정도 있었습니다 — 제가 수동으로 `@codex review`를 부르는 게 아니라 푸시하면 자동으로 붙으니 기다리라는 것.

그런데 빈 커밋으로도 안 깨어나는 경우가 있었습니다.

- **09-11 21:04** #735 재리뷰 요청에 codex가 "code review 사용량 한도 초과" 코멘트를 반환. 최신 커밋 `97c2d7aa7`, 👍 없이 대기.
- **09-12 16:10** 5건 빈 푸시 뒤 "codex가 트리거는 됐는데 사용 한도에 걸렸다." 한도가 소진되면 푸시는 👀만 남깁니다.
- **09-13** #740에서 9라운드 반영(`f51df67ca`) 뒤 60분 무반응 → 빈 푸시 `16a5eabe6` → 10라운드 즉시 재개. 14라운드 반영(`0be6b07bb`) 뒤에는 👀만 61분 → 이번엔 빈 푸시를 반복하지 않고 보고. **60분 룰**: 한 번은 빈 푸시, 두 번째는 사람에게.
- **08-02 07:05** @claude 리뷰 봇 러너 장애로 3회 즉시 실패 → 10분 간격 자동 재시도. 08-01 14:26에는 리뷰 잡이 `cancelled`로 끝나 발견 사항을 남기지 못했습니다.

에이전트 쪽 한도는 더 거칠게 왔습니다. 07-10 23:04 세션 한도로 **에이전트 10개가 전부 같은 오류로 죽어** 멀티에이전트를 버리고 메인 루프에서 직접 처리했고, 08-02 06:43에는 워커 3개(B2a·A4·A2)와 스크립트 1개가 같은 시각에 "session limit · resets 7:30am"으로 멈춰 09:29부터 코디네이터가 하나씩 재개시켰습니다. 09-01 17:47에는 서브에이전트 4개가 ENOTFOUND 2건·스톨 2건으로 전부 죽어 제가 직접 완주했습니다. 09-13 13:16에는 감시 2개와 서브에이전트가 매분 GitHub API를 여러 번 불러 3연속 실패 — 한도 소진 의심으로 끝났습니다. 루프를 무인으로 돌리려면 리뷰어 한도·에이전트 한도·API 한도 셋을 다 세어야 합니다.

## 5. 로컬 게이트는 원격을 대체하지 못했다 — 그러나 한 번은 유일한 안전망이었다

08-11 codex-plugin-cc를 로컬 게이트로 붙였습니다. 결과는 양면이었습니다.

**대체하지 못한 쪽.** 08-11 17:18 "리뷰는 다 끝난건가?"에 표를 만들어 보니 배치 5건(#606·#607·#612·#616·#617)은 GitHub 상 리뷰가 **0건**이었습니다. 제가 돌린 codex 게이트는 로컬 실행이라 GitHub에 남지 않습니다 — 지적이 없어서 스레드가 0인 게 아니라 리뷰 객체 자체가 없었습니다. "게이트 통과"라고 보고했던 것과 GitHub 상태가 달랐습니다. 09-12 23:31 `$code-review` 3라운드 뒤에도 원격 👍는 오지 않았습니다. 팀이 보는 증거는 GitHub에 있는 것뿐입니다.

**유일한 안전망이었던 쪽.** 08-11 05:53 러너 이전으로 `@claude`와 CI가 둘 다 offline인 상태에서 codex 게이트가 17건을 잡았고, 그중 **구현 불가 명세 3건**이 컸습니다 — 2열 FlatList에 `itemLayoutAnimation`을 쓸 수 없어 티켓 1493이 지정한 기법 자체가 불가능했고, 누끼·저장은 연속 3단계가 아니라 사이에 사용자 입력 대기가 있었으며(제 지시가 틀린 건), §A5 자정 경계는 정책 자체의 구멍이었습니다. 문서를 그대로 따랐으면 세 티켓이 헛돌 뻔했습니다.

두 사실은 모순이 아닙니다. 로컬 게이트는 **리뷰의 품질**을 대체할 수 있어도 **리뷰의 기록**을 대체하지 못합니다. 08-22 19:22가 같은 교훈의 다른 얼굴입니다 — 반영한 23건이 전부 로컬에만 있어(12·13·20·22 커밋 미푸시) codex가 옛 코드를 보고 있었습니다. "승인이 안 난 게 아니라, 볼 게 안 올라간 겁니다."

## 6. rtk 출력 필터가 게이트 판정을 가린 세 번

토큰을 아끼려고 명령 출력을 요약하는 `rtk` 프록시를 쓰는데, 요약이 판정을 가린 사례가 셋 있었습니다.

| 날짜 | 명령 | 가려진 것 | 대응 |
| --- | --- | --- | --- |
| 08-08 01:53 | `prettier --check` | exit 1이 요약에서 사라져 "통과"로 읽음 — "rtk 요약이 또 거짓말" | `rtk proxy`로 원문 + `echo "PRETTIER=$?"` |
| 08-18 19:10 | `git push origin achore/…` | refspec이 잘려 푸시 실패 | `rtk proxy`로 원본 푸시 |
| 09-06 14:41 | `git diff` | 변경 규모 오판 → merge-base 기준 재측정 57파일 / +1,288 −955 | 백그라운드 분할 |

첫 기록은 그보다 앞선 08-01 16:12, 리뷰 반영 워커가 남긴 메모리 `rtk-filters-gcloud-output.md`였습니다. 알고도 세 번 더 났다는 뜻입니다. 게이트 판정에 쓰는 명령은 요약을 거치면 안 됩니다 — exit code와 `Tests:` 라인은 원문에서 읽어야 합니다.

## 남은 규칙 여섯 줄

1. **종료는 4부 판정이다.** CI 초록 · 미답변 스레드 0(`--paginate`) · codex 👍 또는 "didn't find major issues" · claude 종결. 👍는 APPROVE가 아니고 머지는 사람이 누른다.
2. **워처는 개수·id·꼬리 줄이 아니라 `created_at`과 상태 전이를 본다.** 필드는 실제 JSON 키 목록으로 확인하고, SHA는 접두 매칭, 페이지는 `jq -s 'add'`.
3. **PR은 ready로 연다.** draft엔 codex가 붙지 않는다. 열린 PR은 곧 루프를 걸어야 할 PR이다(09-13 09:48 #757 미감시).
4. **재트리거는 빈 커밋 한 번, 60분 무응답이면 사람에게.** 한도 초과 코멘트가 있으면 푸시를 반복하지 않는다.
5. **로컬 게이트는 기록이 아니다.** 통과했으면 푸시하고, 원격 리뷰 객체가 생겼는지 확인한 뒤에 "게이트 통과"라고 말한다.
6. **판정 명령은 원문으로.** `rtk proxy`, exit code, `Tests:` 라인. "반영했습니다"는 반영 조회 뒤에.

하드 스톱은 없습니다. 08-12에 만들고 08-25에 지웠고, 그 사이에도 20·24라운드를 돌렸습니다. 대신 남은 것은 "라운드마다 직전 반영이 만든 빈틈이 섞인다"는 관찰이고, 그 비율이 올라가면 라운드를 더 돌리는 대신 사람에게 넘기는 것이 4부 판정 밖의 유일한 종료 조건입니다.
