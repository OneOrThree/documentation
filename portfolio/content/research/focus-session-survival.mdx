## 0. 한눈에

집중 세션은 화면 세 개짜리 기능처럼 보이지만 본체는 **생명주기**다. 사용자는 타이머를 켜 놓고 앱을 떠나고, iOS는 그 사이 앱을 멈추거나 죽인다. 그래도 돌아왔을 때 시간은 맞아야 하고, 죽어 있던 동안의 기록도 남아야 하며, 같은 기록이 두 번 들어가서도 안 된다. 이 문서의 대부분은 그 세 가지를 동시에 만족시키려다 부러진 자리에 대한 것이다.

| 값 | 무엇 |
| --- | --- |
| **34시간** | 통계 일 탭에 찍힌 "오늘 총 집중" 최고 기록 (GROMO-1253) |
| **3중** | 세션 생존 그물 — 라이브 기록 · 고아 정산 · 업로드 대기열 |
| **3중** | 서버 중복 가드 — 마커 선점 · 마커 행 잠금 · 구간 완전일치 검사 |
| **5초** | 라이브 기록 저장 주기. 앱이 죽어도 최대 5초만 잃는다 |
| **50건** | 업로드 대기열 상한 |
| **124 / 37** | 집중 코어 커밋 수 / 그중 `[FIX]` |

<Callout label="이 문서가 다루는 것">

1장은 지금 도는 구조, 2장은 거기 도달하기까지 부러진 지점을 증상·원인·해결로 적은 기록이다. **앱 쪽 그물**이 중심이다. 서버가 "이 세션이 아직 살아 있는가"를 어떻게 판정하는지는 [집중 세션 동기화](/research/focus-session-sync)와 [ADR-007](/adr/adr-007-focus-session-liveness)이 다루고, 날짜 축·리그 누적·재화 지급처럼 이미 다른 노트가 깊게 쓴 사건은 요약과 링크만 남겼다.

</Callout>

<Callout label="기준 시점" tone="warn">

1.x 앱(`app/legacy/app-dev`)의 2026-05-16~08-11 기록이다. 1.x는 이후 동결됐다. 코드 경로는 지금 저장소 구조로 고쳐 적었고, 08-11 이후 바뀐 것은 본문에 따로 표시했다.

</Callout>

## 1. 설계

### 1.1 문제는 화면이 아니다

집중 타이머의 어려움은 "1초마다 숫자를 줄이는 것"이 아니다. 어려운 건 이 셋이다.

- **앱이 멈춘다** — iOS는 백그라운드에서 JS 실행을 정지시킨다. 타이머가 안 돈다.
- **앱이 죽는다** — 메모리 압박이나 사용자의 강제 종료로 프로세스가 사라진다. 그동안 쌓인 시간은 어디에도 없다.
- **같은 걸 두 번 보낼 수 있다** — 복구 로직이 있으면 정상 종료와 복구가 겹쳐 한 세션이 두 번 저장될 수 있다.

세 번째가 특히 고약하다. 1·2번을 막으려고 그물을 겹칠수록 3번 위험이 커진다. **안전망을 늘리는 것 자체가 새 결함의 원인이 되는 구조**다.

### 1.2 3중 안전망

```text
진행 중 세션 (1초 틱 · 블록 정산)
   │
   ├─ ① 라이브 기록 ── 5초마다 기기에 저장 (앱이 죽었을 때 복구의 근거)
   │
   ├─ 서버 업로드 ──── 블록마다 전송
   │      └─ 실패 ─▶ ③ 업로드 대기열 (상한 50) ─▶ 앱 시작·포그라운드 복귀마다 재전송
   │
   └─ 앱이 죽는다 (강제 종료 · OS 회수)
          └─▶ ② 고아 정산 ── 다음 실행 때 남은 라이브 기록을 정산해 업로드

그물이 겹칠수록 "같은 세션을 두 번 저장할" 위험이 커진다 → 서버 중복 가드 (1.5)
```

<Callout label="명시적으로 고른 트레이드오프 — 미적립보다 중복이 낫다">

코드 주석에 한 줄로 적혀 있는 원칙이다. 사용자가 집중한 시간을 잃는 것보다, 두 번 세어져서 서버가 걸러내는 쪽이 낫다. 이 선택이 서버의 중복 가드를 필수로 만들었다.

</Callout>

### 1.3 시간을 세는 법

화면이 켜져 있을 때는 1초마다 센다. 문제는 백그라운드 구간이다. 그때는 틱이 안 돌기 때문에, 돌아오면 **"떠난 시각과 지금 시각의 차이"를 벽시계로 재서 그 구간을 되감는다**(벽시계 리플레이). 그리고 세션이 끝날 때 한꺼번에 보내지 않고 **블록 단위로 끊어** 로컬에 적립하고 서버로 올린다. 세션이 통째로 날아가는 걸 막기 위해서다. 이 "블록"이라는 개념이 나중에 여러 결함의 무대가 된다(B1·B2).

### 1.4 실드가 규칙을 바꾼다

집중 세션은 실드(다른 앱을 막는 가림막)를 켤 수 있고, 실드 여부에 따라 "자리를 비운 시간"의 취급이 정반대다.

| 상황 | 자리를 비우면 | 왜 |
| --- | --- | --- |
| 실드 켬 | 집중으로 인정 (세션 누적 상한 8시간) | 다른 앱이 막혀 있으니 딴짓을 할 수 없다. 폰을 내려놓고 공부하는 게 오히려 정상이다 |
| 실드 끔 | 15초 뒤 자동 종료 | 막는 게 없으니 나간 건 딴짓으로 본다 |

<Callout label='여기가 "서버 권위 시간"을 포기한 지점이다' tone="warn">

실드를 켜면 앱이 안 보고 있는 시간을 집중으로 인정한다. 서버는 그게 진짜인지 확인할 방법이 없다 — 스크린타임 원본을 서버가 볼 수 없기 때문이다([스크린타임 노트](/research/screentime) 1.1). 이 기능은 클라이언트가 보고한 시간을 믿는 구조 위에 서 있고, 그 신뢰가 2장 E의 배경이다.

</Callout>

### 1.5 서버의 3중 중복 가드

같은 세션이 두 번 들어오는 걸 막는 보통의 방법은 DB 유니크 제약이다. 여기서는 그걸 쓰지 않고 서비스 코드에서 세 겹으로 막는다.

1. **마커 조건부 선점** — 세션을 시작할 때 서버에 남긴 표식(라이브 마커)을 조건부 UPDATE로 한 번만 가져간다
2. **마커 행 잠금** — 선점에 실패하면 그 마커 행을 잠그고 상태를 확인해, 같은 마커를 둘러싼 요청들이 줄을 선다
3. **구간 완전일치 검사** — 시작·종료 시각이 똑같은 완료 세션이 이미 있으면 저장·통계·지급을 전부 건너뛴다

세션 저장 한 트랜잭션에 코인 지급·일별 통계·스트릭·그룹 내기 확정이 전부 묶여 있어 하나라도 실패하면 전부 취소된다. 안전하지만, 트랜잭션이 커진 만큼 충돌 지점도 넓어졌다(2장 E2).

## 2. 결함 기록

원본 기록의 결함 42건 중 이 문서에 맞는 것을 골랐다. 시간순이 아니라 **고장 성격별**로 묶었다. `사고`는 실제로 뭔가 깨진 뒤에 알게 된 것, `실측`은 코드를 직접 확인하다 발견한 것이다.

### A. 증거를 지우고 보고한다

#### A1. 복구용 기록을 먼저 지우고 나서 업로드했다

`사고` · GROMO-613 · PR #128 · 07-07

**증상** — 오프라인이거나 서버가 불안정할 때, 강제 종료된 세션이 서버에서 영구히 사라진다.

**원인** — 고아 정산기가 업로드하기 **전에** 로컬 라이브 기록을 지우고, 업로드 실패는 조용히 무시했다. 증거를 폐기한 다음 보고를 시도하는 순서였다. 실패하면 되살릴 근거가 이미 없다.

**해결** — 순서를 뒤집었다. 로컬 적립은 한 번만 했다고 표시해 두고, 라이브 기록 삭제는 업로드 성공 이후로 옮겼다.

#### A2. 업로드 실패를 통째로 삼키고 있었다

`사고` · GROMO-614 · PR #129 · 07-07

**증상** — 기기에는 집중 시간이 쌓였는데 서버에는 없다.

**원인** — 업로드 실패를 잡아서 아무것도 안 했다. 재시도할 곳도, 남겨 둘 곳도 없었다.

**해결** — 실패한 업로드를 대기열에 넣고 앱 시작·포그라운드 복귀마다 다시 보낸다. 상한은 50건이다.

#### A3. 정상 종료인데 적립이 통째로 스킵됐다

`사고` · GROMO-615 · PR #130 · 07-07

**증상** — 세션을 정상적으로 끝냈는데 시간도, 코인도, 업로드도 안 됐다.

**원인** — 종료 처리에서 로컬 기록 삭제와 정산이 같은 예외 처리 묶음 안에 있었다. 삭제가 실패하면 그 예외가 정산까지 같이 날려 버린다. **부수적인 일이 본체를 끌고 죽은 것이다.**

**해결** — 삭제를 따로 떼어내 실패해도 정산은 무조건 실행되게 했다. 이때 남긴 주석이 이 기능 전체의 원칙이 됐다 — "미적립보다 중복이 낫다."

<Callout label="A1~A3은 한 문장으로 요약된다">

복구 경로에서 **되돌릴 수 없는 일(삭제)은 되돌릴 수 있는 일(업로드)이 성공한 뒤에** 한다. 그리고 부수 작업의 실패가 본 작업을 끌고 가지 않게 떼어 둔다. 세 수정은 같은 날(07-07) 연달아 들어갔다.

</Callout>

#### A4. 계정을 바꿨는데 이전 계정 기록이 보였다

`사고` · GROMO-677 · PR #188 · #200 · 07-10

**증상** — 다른 계정으로 로그인했는데 이전 계정의 과목과 오늘 집중 시간이 그대로 뜬다.

**원인** — 로그아웃할 때 지우는 키 목록에 집중 관련 키가 빠져 있었다. 게다가 복원 함수는 **호출하는 곳이 한 군데도 없었다** — 만들어만 놓고 배선을 안 했다.

**해결** — 키를 추가하고 복원을 배선했다. 후속 리뷰에서 더 미묘한 게 나왔다. 편집 작업을 취소하는 호출이 새 토큰을 저장한 **뒤에** 있어서, 이전 계정의 편집이 새 계정 권한으로 실행될 수 있었다. 취소를 토큰 교체 직전으로 옮기고 계정 세대 가드를 넣었다.

### B. 시간이 어긋난다

#### B1. 백그라운드에서 넘어간 경계가 한 블록에 다 삼켜졌다

`사고` · GROMO-873 · PR #312 · #314 · 07-20

**증상** — 뽀모도로를 켜 놓고 앱을 떠났다 돌아오면, 첫 블록이 전체 시간을 다 먹고 나머지 블록은 0초가 된다. 서버 통계가 오염된다.

**원인** — 백그라운드 구간을 되감을 때 각 블록의 정산 시각을 전부 **"돌아온 순간"**으로 찍고 있었다. 실제로는 30분에 걸쳐 일어난 일이 한 시점에 몰린 것처럼 기록된다.

**해결** — 정산 시각을 넘겨받도록 바꿔, 되감을 때 "떠난 시각 + 경과 초"로 실제 벽시계를 복원한다.

#### B2. 하루 집중 시간이 34시간으로 찍혔다

`사고` · GROMO-1253 · PR #538 · 08-09

**증상** — 통계 일 탭의 "오늘 총 집중"이 34시간. 앱을 완전히 종료했다 켜도 그대로다. 같은 시점 서버의 일별 집계는 8시간이었다 — **화면만 틀렸다.**

**원인** — 두 개가 겹쳤다.

① 실드 세션의 자리 비움 인정 상한 8시간이 **"복귀 1회당"**으로 걸려 있었고 횟수 제한이 없었다. 나갔다 들어오기를 네 번 하면 32시간이 인정된다.

② 카운트업 모드는 되감기 루프에 종료 조건이 없어 **상한 검사에 닿지도 않았다.** 정산도 종료 시 1회뿐이라 누적분 전체가 '오늘'에 꽂혔다. 상한이 있는데 도달하지 못하는 구조였다.

로컬 값은 틱 기반으로, 서버 값은 "종료 − 시작" 벽시계로 쌓이니 둘이 갈라질 수 있는 통로가 바로 여기였다.

**해결** — 상한을 **세션 누적** 기준으로 바꾸고, 하루 총합에 24시간 클램프를 적립·저장분 로드·서버 복원 세 지점에 넣었다. 로드 시점에도 걸었기 때문에 **이미 부푼 값이 저장된 기기도 앱을 다시 켜면 정리된다**(별도 마이그레이션 없음). 코드 리뷰가 두 번 더 파고들었다.

| 라운드 | 지적 | 대응 |
| --- | --- | --- |
| 1차 | 기기 시계가 뒤로 가면 "자리 비운 시간"이 음수가 되고, 카운트다운은 남은 시간이 되레 늘어난다 | 계산 지점에 하한 0 — 소비처 네 곳이 한 번에 닫힘 |
| 1차 | 총합만 막으면 과목별 누적이 부푼 채 남는다 | 과목 스토어도 같은 하루 상한 공유 |
| 2차 | 부패가 여러 과목에 나뉘면(20시간 + 14시간) **과목별 클램프를 전부 통과**하는데 합은 34시간. 도넛 차트 중앙 34:00:00, 바로 위 총계 카드 24:00:00이 한 화면에 뜬다 | 과목 합계 기준 **비례 축소** — 합이 정확히 24시간이 되게 |

<Callout label='"1회당 상한"은 반복 호출에 뚫린다' tone="warn">

상한은 호출 단위가 아니라 **누적 단위**로 건다. 그리고 불변식을 먼저 적는다 — "세션의 경과 시간은 세션 시작 이후 실제로 흐른 벽시계 시간을 넘을 수 없다." 이 한 줄이 있었다면 34시간은 들어올 자리가 없었다. 서버 과거 값은 건드리지 않았다(forward-only).

</Callout>

#### B3. 자정을 넘긴 세션이 종료일에 통째로 적립됐다

`사고` · GROMO-1252 · PR #539 · 08-09

**증상** — 밤 11시에 시작해 새벽 1시에 끝낸 세션의 2시간이 전부 다음 날로 기록된다. 전날 몫이 사라지고 다음 날이 부푼다. 같은 날짜를 쓰는 스트릭·목표 달성·보상도 함께 밀린다. 운영 DB를 실측해 실제로 잘못된 날짜에 붙은 세션이 있음을 확인했다.

**원인** — 세션을 날짜별로 쪼개는 로직이 **서버에도 앱에도** 없었다. 둘 다 "종료 시각의 날짜" 하나에 전체 구간을 넣었다. 일 탭은 기기 로컬 값만 쓰므로, **서버만 고쳤다면 일 탭은 그대로 틀렸을 것이다.**

**해결** — 세션 구간을 로컬 자정 경계로 잘라 날짜별로 배분하되, 서버와 앱이 **같은 분할 규칙**을 쓴다. 무엇을 쪼개고 무엇을 안 쪼개는지가 이 수정의 핵심이다.

| 날짜별로 쪼갠다 | 쪼개지 않는다 |
| --- | --- |
| 하루 집중 시간 | 세션 원본 행 — 1건 유지. 그래야 재업로드 중복 검사가 그대로 동작한다 |
| 목표 달성 판정·지급 (날짜별 멱등키) | 세션 보상 코인 — 멱등키가 세션 기준 |
| 스트릭 (그 날짜 누적 10분 이상인 날만) | 세션 횟수·방해 시간 — 시작한 날에만 |

세 가지를 곁들였다. ① 분할이 엉뚱한 곳에서 일어나지 않게 서버의 시간대 폴백을 UTC에서 한국 시간으로 먼저 바꿨다 — 국가 코드가 비어 있는 유저의 "하루"가 한국 오전 9시에 바뀌고 있었다. 시간대 축의 전체 이력은 [타임존 버킷 전쟁](/research/timezone-wars)에 있다. ② 서버는 시작 시각을 클라가 보낸 값으로 믿으므로, 시작 시각을 몇 년 전으로 조작한 세션 하나가 날짜 수만큼 잠금과 INSERT를 만들 수 있었다. 분할을 최대 32일로 자르고 초과분은 마지막 조각에 합쳐 총합을 보존했다. ③ 앱의 "오늘 겹침" 계산은 다음 자정을 `setDate(+1)`로 구해 서머타임 전환일(23·25시간)에도 맞게 했다.

#### B4. 같은 질문을 네 번 물어 네 번 다르게 답했다

`사고` · GROMO-920 · PR #341 · 07-24

**증상** — 자정 무렵 홈 화면의 "오늘 집중" 총합과 과목별 합계가 안 맞는다.

**원인** — 복원 조회가 최대 네 번 일어나는데, 각자 **자기가 실행되는 시점에** "오늘"을 판정했다. 자정을 사이에 두면 답이 갈린다.

**해결** — 조회를 한 번으로 합치고 진행 중인 요청을 두 스토어가 공유하게 했다. **"오늘"을 여러 번 계산하지 않는 것 자체가 해결**이다.

#### B5. 일시정지한 시간이 전부 집중으로 계산됐다

`실측` · GROMO-1214 리뷰 중 발견 · PR #540 · 08-09

**증상** — 1시간 집중 → 30분 일시정지 → 30분 집중이면 실제 집중은 1.5시간인데, 서버 통계는 2시간, 코인은 90개가 아니라 120개다. 리그 순위·통계·스트릭이 전부 이 값을 본다.

**원인** — 앱이 방해 시간 필드에 **항상 0을 박아** 보내고 있었다. 서버는 "종료 − 시작 − 방해 시간"으로 계산하니, 일시정지가 통째로 집중이 됐다.

**해결** — 블록 단위 일시정지 카운터를 만들고, 블록 시작 시각을 옮기는 다섯 곳을 전부 한 헬퍼로 통과시켜 "새 블록 = 카운터 리셋"을 구조로 보장했다. **방해로 세는 것은 수동 일시정지뿐**이다 — 뽀모도로 휴식·실드 이탈 인정분은 이미 정산 구간 밖이라 또 빼면 이중 차감이 된다. 서버는 날짜별 조각 길이에 비례해 방해 시간을 배분한다. 뒤이은 리뷰에서 24시간 넘는 일시정지가 상한만 잘리고 구간은 그대로라 초과분이 집중이 되는 구멍도 찾아, 상한을 넘으면 정지 시작 시각에서 블록을 끊게 했다.

### C. 실드와 화면

실드에서 사파리가 뚫리던 문제(GROMO-866)는 [스크린타임 노트](/research/screentime) B5에 있다. 여기서는 집중 화면에만 있는 두 건을 적는다.

#### C1. 캐릭터가 잠금화면에서 과하게 줄어들었다

`사고` · GROMO-1081 · PR #459 · 08-02

**증상** — 잠금화면과 다이나믹 아일랜드의 캐릭터가 작게 찌그러지거나 잘린다.

**원인** — 캐릭터 스냅샷이 정사각형으로 캡처돼 실제 그림 주변에 투명한 여백이 잔뜩 있다. 좁은 공간에 맞추면 여백까지 같이 줄어 그림이 작아진다.

**해결** — 투명한 가장자리를 잘라내고 최대 크기 상자를 씌웠다. 저장본 자체를 고치지 않은 이유가 있다 — 같은 이미지를 실드 화면이 아이콘으로 공유해서, 저장본을 바꾸면 그쪽이 깨진다.

#### C2. iPad 멀티태스킹에서 정지 버튼 없는 화면에 갇혔다

`사고` · GROMO-973 · PR #419 · #420 · 08-02

**증상** — iPad에서 화면을 분할해 쓰면 세션을 끝낼 방법이 없는 가로 화면에 갇힌다.

**원인** — 멀티태스킹 상태에서는 앱이 지정한 화면 방향 잠금이 무시된다.

**해결** — iPad 분할 화면 지원을 포기하고 전체 화면만 허용해, 이 상태가 **만들어질 수 없게** 했다. 같은 리뷰에서 시계 표시가 100시간을 넘으면 자릿수가 밀리는 것도 나왔다.

### D. 판정 축이 갈렸다

<Callout label="이 그룹은 한 뿌리에서 나왔다">

"오늘 집중했나"라는 하나의 질문에 서비스마다 다른 답을 내고 있었다. 어떤 곳은 시작 시각만 봤고, 어떤 곳은 완료된 세션만 봤고, 어떤 곳은 취소된 세션까지 셌다. 기준이 코드에 흩어져 있으면 반드시 갈라진다. 날짜 축이 세 번 흔들린 이력(분 내림 → UTC 대 로컬 → 자정 분할, GROMO-642·803·1252)은 [타임존 버킷 전쟁](/research/timezone-wars)에, 리그 누적 갱신이 아예 없었다가 분 내림으로 30초 세션이 사라진 사건(GROMO-646 → 665 → 829)은 [리그 배치 노트](/research/league-batch)에 있다.

</Callout>

#### D1. 알고도 미룬 것이 2주 뒤 정확히 그 자리에서 터졌다

`사고` · GROMO-841 → 851 · PR #269(07-16) → #360(07-31)

**증상** — 세션을 버려둔 사용자에게 재참여 알림이 안 가고, 집중 중인 사람에게 방해 알림이 간다. 고치고 2주 뒤 순위 추월 알림에서 같은 증상이 났다.

**원인** — "오늘 집중했나"를 **세션 시작 시각만으로** 판정했다. 강제 종료로 서버가 자동 마감한 세션이나 사용자가 취소한 세션은 실제 집중이 0분인데도 "오늘 집중함"이 된다.

첫 수정 PR #269의 주의사항에는 이렇게 적혀 있었다 — 순위 추월 서비스도 같은 방식이라 같은 오검출 소지가 있으나, 리뷰 범위 밖이라 이번 PR에서 제외한다. 그리고 정확히 거기서 터졌다.

**해결** — 판정 기준을 "완료 세션 ∪ 진행 중 세션"으로 통일하고, 이번에는 **같은 실수를 반복할 옛 조회 경로 자체를 지웠다.** 남겨 두면 "오늘 집중 판정" 방식이 둘로 보여 다음 사람이 틀린 쪽을 다시 쓸 수 있기 때문이다. 범위 밖으로 미룬 것은 미룬 게 아니라 **예약된 사고**다.

#### D2. 취소한 세션이 리그 순위에 들어갔다

`사고` · GROMO-872 · PR #307 · 07-19

**증상** — 취소한 세션이 리그 "내 시간"과 통계 타임라인에 집계된다.

**원인** — 세션 목록 조회 쿼리에만 상태 필터가 빠져 있었다. 같은 리포지토리의 다른 쿼리에는 다 있었다. 앱이 이 목록을 직접 합산하니 취소분이 그대로 더해졌다.

**해결** — 취소 세션만 뺐다. 앱이 끝맺지 못해 서버가 자동 마감한 세션은 **일부러 포함**한다 — 사용자가 취소한 것과 앱이 못 끝낸 것은 다르게 다뤄야 한다. (PR 제목은 둘 다 뺀 것처럼 읽히지만, 본문과 코드는 취소만 뺐다.)

#### D3. 과목 이름을 바꿨더니 과거 기록이 미분류가 됐다

`사고` · GROMO-754 · PR #274 · 07-16

**증상** — 과목 이름을 수정하자 과거 세션이 전부 "미분류"로 강등되고 오늘 총합이 사라진다.

**원인** — 서버에서 이름 변경은 **기존 태그를 지우고 새로 만드는** 방식인데, 세션들은 지워진 옛 태그를 가리키고 있었다.

**해결** — 이름을 바꿀 때 과거 세션의 참조를 새 태그로 일괄 옮긴다. 이 수정 이전에 깨진 데이터는 복구할 수 없다 — 어느 세션이 어느 과목이었는지 알 근거가 DB에 남아 있지 않다.

### E. 신뢰의 바닥

#### E1. 증거를 스스로 폐기하고 나서 결과를 보고하고 있었다

`실측` · GROMO-1214 · PR #540 · 08-09

**증상** — 변조된 앱이 아무 세션이나 만들어 보내면 그대로 코인이 지급된다.

**원인** — 세션을 시작할 때 서버에 라이브 마커를 남기고(친구·리그의 "집중 중" 표시가 여기서 나온다), 끝날 때 **그 마커를 취소한 뒤** 별개의 저장 요청을 새로 보냈다. 저장 요청 입장에서는 "정말 그 세션이 있었는지" 확인할 근거가 방금 스스로 지워진 셈이다. A1과 같은 모양의 실수가 서버 계약 층위에서 반복된 것이다.

**해결** — 종료를 **마커를 이어받는 PATCH**로 바꿔, 지급이 서버가 발급한 마커를 거쳐야만 이뤄지게 했다. 결정의 근거와 기각안은 [ADR-029](/adr/adr-029-focus-payout-server-marker)에 있다. 여기서는 앱 쪽에서 배운 두 가지만 남긴다.

- **티켓의 작업량 추정이 틀렸다는 것을 PR이 정정했다.** 티켓에는 "서버 신규 코드 0줄"이라고 적혀 있었지만, 기존 PATCH 경로에는 세션 보상 지급이 통째로 빠져 있어 앱만 바꾸면 집중 코인이 0이 됐다. 서버 작업이 같은 PR에 들어간 이유다.
- **같은 409(충돌)에 서로 다른 뜻이 섞여 있었다.** ① 앞선 PATCH가 이미 커밋된 경우 ② 서버가 자동 마감해 통계에 반영하지 않은 경우 ③ 지갑 갱신 경합에서 져서 롤백된 경우. ①에서 새 저장 요청으로 폴백하면 코인·통계가 두 번 들어가고, ②·③을 ①처럼 종결 처리하면 집중 시간이 사라진다. 리뷰 두 라운드를 거쳐 서버가 ②를 별도 에러 코드로 구분해 주게 됐고, 앱은 코드별로 셋을 다르게 처리한다 — ①은 종결, ②는 새 저장 요청으로 폴백, ③은 네트워크 실패와 같은 재시도.

<Callout label="모르는 응답은 성공도 실패도 아니다" tone="warn">

고아 정산과 대기열 재전송이 있는 한 앱은 같은 세션을 여러 번 보낸다. 그때 앱이 응답을 **"이미 끝났다"와 "다시 보내도 된다"로 정확히 나눌 수 있어야** 그물이 중복을 만들지 않는다. 응답 코드 하나에 뜻이 둘 이상 섞이면, 어느 쪽으로 읽어도 한쪽이 틀린다.

</Callout>

#### E2. 코인 사고 다섯 번의 원인이 결국 하나였다

`사고` · GROMO-1036 ~ 1049 · PR #417 · #489 · #499 · #500 · #504 · 08-02~08-07

**증상** — 다섯 번에 걸쳐 다른 증상이 났다 — 앱이 코인을 임의로 만들 수 있음 → 차액이 안 맞음 → 0초 세션이 목표 달성으로 처리됨 → 앱이 잔액을 못 맞춤 → 축하 표시가 두 번 뜸.

**원인** — 첫 번째는 앱이 금액을 정해 적립을 요청하던 구조 자체였다. 이것을 서버 지급으로 옮긴 이야기는 [재화·정산 무결성 노트](/research/money-integrity)에 있다. 나머지 넷은 다섯 번째 수정에서 뿌리가 나왔다 — **지급 응답이 오기 전에 화면 잔액을 미리 올리는 낙관적 처리**였다. 앱은 늘 "미리 올린 값"과 "서버가 준 값"을 맞춰야 했는데, 진행 중이던 잔액 조회 응답이 지급 전 스냅샷인지 후인지 알 수 없어서 어느 쪽으로 보정해도 반대편이 틀렸다.

| 시도 | 결과 |
| --- | --- |
| 조회 응답 폐기 | 콜드 스타트에서 기준 잔액 손실 |
| 응답 + 낙관 델타 | 지급 후 스냅샷이면 이중 가산 |
| 확정 재조회 + 미확정 합 | 대기열 경로에서 미확정분 영구 누수 |
| 서버가 저장 응답에 최종 잔액 제공 | 구매 등 다른 잔액 변동과의 순서 미해결 |

**해결** — 다섯 번째 수정은 무엇을 더하지 않고 **추적부터 했다.** 낙관값이 사용자 눈에 닿는 화면이 있는가? 집중 세션 화면과 결과 화면에는 잔액 칩이 없었고, 잔액이 보이는 홈·메뉴는 진입할 때마다 서버 잔액을 다시 받고 있었다. 미리 올린 값을 보여 줄 화면이 처음부터 없었던 것이다. 그래서 규칙을 하나로 줄였다 — **잔액이 바뀔 만한 일이 끝나면 서버에서 한 번 다시 받는다.** 이 PR은 172줄을 더하고 550줄을 지웠다. 네 번의 수정이 붙인 것을 다섯 번째가 걷어낸 셈이다. 증상마다 대응하면 대응이 결함이 된다.

#### E3. 후일담 — 지급은 맞는데 표시가 틀렸다

`실측` · GROMO-1193 · PR #492 · 08-07

E2를 정리하면서 지급 경로 네 개(세션 완료·집중 목표·스크린타임 목표·리그 승급)를 진입점부터 표시까지 코드로 따라가는 검증을 했다. 중복 지급은 서버의 멱등키 선조회와 유니크 제약으로 닫혀 있었고, 클라이언트는 멱등키를 만들지도 보내지도 않는다(설계상 서버 담당). 대신 **표시**에서 세 건이 나왔다.

| 결함 | 무엇이 틀렸나 | 수정 |
| --- | --- | --- |
| 보상 이중 표기 | 결과 화면 배지가 "세션 보상 + 목표 보너스" 합계인데, 홈 축하 모달이 그 목표 보너스를 또 보여 줬다. 잔액은 정상, 사용자 눈에는 더 받은 것처럼 보임 | 배지는 세션 보상만, 목표 보너스는 축하 모달이 단독 표시 |
| 낡은 내역 | 잔액은 화면 진입마다 갱신하는데 거래 내역은 마운트 1회만 로드. "갱신된 잔액 + 낡은 내역"이 나란히 뜸 | 내역도 화면 포커스마다 재조회 |
| 유령 배지 | 리그 승급 보너스를 서버가 **0**으로 내려도 앱이 공식으로 다시 계산해 배지를 띄웠다. "백엔드 머지 전 임시 폴백"이라는 주석이 붙어 있었지만 서버는 이미 값을 내리고 있었다 | 서버 값만 신뢰. 폴백이 쓰던 계산 함수도 함께 삭제 — 남겨 두면 같은 폴백으로 다시 쓰이기 쉽다 |

<Callout label='"임시"라는 주석에는 만료일이 없다'>

유령 배지는 E2와 같은 뿌리다 — 서버가 준 값보다 앱이 계산한 값을 앞세웠다. 임시 폴백은 그 이유가 사라지는 순간(서버가 값을 내리기 시작한 순간) 지워야 하는데, 그 순간을 알려 주는 장치가 없다. 앱에 남은 지급 공식은 서버 공식의 **표시 전용 미러**로 남기고, 두 값이 갈리지 않게 테스트로 고정했다.

</Callout>

## 5. 용어

| 용어 | 뜻 |
| --- | --- |
| 세션 | 집중을 시작해서 끝낼 때까지의 한 덩어리. 카운트다운·뽀모도로·카운트업 세 모드가 있다 |
| 실드 (shield) | 집중하는 동안 다른 앱을 막는 가림막. 켜면 자리 비움 규칙이 통째로 바뀐다 |
| Live Activity | 잠금화면과 다이나믹 아일랜드에 뜨는 실시간 표시. 앱이 정지돼도 별도 프로세스가 그린다 |
| 라이브 기록 | 진행 중인 세션을 5초마다 기기에 적어 두는 것. 앱이 죽었을 때 복구의 근거가 된다 |
| 라이브 마커 | 세션을 시작할 때 서버에 남기는 표식. 친구·리그의 "집중 중" 표시와 지급 경로가 여기서 나온다 |
| 고아 세션 (orphan) | 끝맺지 못하고 남은 세션. 다음 실행 때 정산해서 살린다 |
| 블록 정산 | 세션이 끝날 때 한꺼번에 보내지 않고 구간마다 끊어서 적립·전송하는 방식 |
| 벽시계 리플레이 | 백그라운드에서 못 센 구간을 "떠난 시각과 지금 시각의 차이"로 되감는 것 |
| 자리 비움 인정 (away-credit) | 실드가 켜진 세션에서 앱을 안 보고 있던 시간도 집중으로 세는 것 |
| 멱등 (idempotent) | 같은 요청이 여러 번 와도 결과가 한 번과 같은 성질. 안전망이 겹칠수록 필수가 된다 |
| 낙관적 처리 (optimistic) | 서버 응답을 기다리지 않고 화면을 먼저 바꾸는 것. 빠르지만 어긋나면 보정 코드가 쌓인다 |
| 스트릭 (streak) | 연속 달성 일수. 여기서는 하루 누적 10분이 기준이다 |
| forward-only | 고친 시점 이후만 정상이고 과거 데이터는 손대지 않는 방식. 날짜 축 수정이 모두 그랬다 |
