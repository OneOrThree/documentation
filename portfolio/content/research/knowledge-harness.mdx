결론부터 적습니다. 흩어진 지식을 모으는 일은 "전부 한곳에 합치기"로는 풀리지 않았습니다. 세 번의 시도 끝에 남은 규칙은 두 줄입니다. **출처는 origin별로 쪼개고, 가공물은 예외 없이 한 층으로 모은다.** 그리고 그 층을 신뢰하려면 lint가 필요했고, lint를 신뢰하려면 lint가 세는 숫자부터 의심해야 했습니다.

이 노트가 다루는 것은 코드가 아니라 제 작업 환경입니다. 다만 이 사이트의 연구 노트 대부분이 그 환경의 산출물이므로, 여기 적힌 실패들은 결국 다른 모든 노트의 전제 조건입니다.

## 무엇이 문제였나

소프트웨어 마에스트로를 진행하는 동안 자료가 빠르게 쌓였습니다. 멘토링 노트가 200개를 넘겼고, 백엔드 프로젝트 리포가 따로 돌아가고, 책과 강의로 공부한 내용이 또 따로 있었고, 취업용 블로그 초안이 그 위에 얹혀 있었습니다.

문제는 양이 아니라 **연결이 끊긴 섬**이라는 구조였습니다. 증상은 세 가지로 반복됐습니다.

| 증상 | 실제로 일어난 일 |
| --- | --- |
| 배운 걸 다시 못 찾는다 | 멘토링에서 "Kafka 파티션으로 순서를 보장한다"고 배웠는데, 채팅 서버를 설계할 때 그 노트를 찾지 못했다 |
| 진도 관리가 안 된다 | 뭘 알고 뭘 모르는지가 머릿속에만 있어 다음에 공부할 것을 매번 새로 고민했다 |
| 산출이 매번 수작업 | 글 하나 쓰려면 멘토링 노트·공부 내용·코드를 손으로 긁어모아야 했다 |

"폴더를 잘 나누자"로는 부족했습니다. 원하는 것은 지식이 **출처 → 가공 → 산출** 로 흐르고, 그 흐름 자체가 가능한 한 자동으로 돌아가는 상태였습니다.

## 1차: 전부 한곳에 통합 → 독립성이 무너졌다

처음 떠올린 방식은 가장 단순한 쪽이었습니다. 루트에 규칙 파일 하나를 두고 멘토링 위키, 프로젝트, 공부 노트를 전부 흡수해 단일 규칙으로 관리하는 것.

- **왜 그렇게 했나**: 멘탈 모델이 하나라 단순합니다. 규칙 파일도 하나뿐이니 관리 지점도 하나입니다.
- **왜 깨졌나**: 멘토링 폴더는 이미 자체 하네스를 갖고 있었습니다. raw에서 위키로 가는 파이프라인, 원본은 읽기 전용이라는 규칙이 이미 돌고 있었습니다. 그리고 프로젝트 리포와 일정관리 폴더는 **각자 독립된 git 저장소**였습니다.

즉 루트로 빨아들이는 순간, 잘 돌던 구조 두 개를 동시에 깨뜨리게 됩니다. 통합의 이득보다 파괴가 컸습니다. 여기서 방향을 바꿨습니다. 필요한 건 전부를 삼키는 층이 아니라 **얇은 층**이었습니다.

## 2차: 얇은 오케스트레이션 층 — 보충성 원칙

각 섬의 자율성을 그대로 두고, 그 위에 지도와 라우팅과 지식 흐름만 담당하는 얇은 루트 층을 얹었습니다. 행정학의 보충성 원칙과 같은 발상입니다. **하위가 할 수 있는 일은 하위에 맡긴다.**

| 층 | 역할 | 불가침 여부 |
| --- | --- | --- |
| 루트 규칙 파일 | 섬 지도 + 라우팅 규칙 | 이 층만 새로 만든다 |
| 루트 스킬 4종 | 섬을 넘나드는 작업 | 이 층만 새로 만든다 |
| 멘토링 폴더 | 자체 raw→위키 파이프라인 | 건드리지 않음 |
| 프로젝트 리포 / 일정관리 | 자체 git·자체 규칙 | 건드리지 않음 |

이 전환으로 기존 구조를 깨지 않고 통합 효과를 얻었습니다. 하지만 한계가 하나 남았습니다. **가공된 지식, 즉 개념 노트를 어디에 둘 것인가**가 여전히 미정이었습니다. 라우팅만 있고 목적지가 없었던 셈입니다.

## 3차: "개념은 출처가 달라도 하나다" — 원칙을 뒤집은 순간

처음 설계는 가공 층도 출처별로 나누는 쪽이었습니다. 멘토링에서 배운 개념은 멘토링 위키에, 공부한 개념은 공부 위키에, 고수준 주제는 또 별도 폴더에. 출처와 가공을 나란히 3분할하는 그림입니다.

그런데 개념 노트를 몇 개 쓰다가 막혔습니다. SSE라는 개념은 멘토에게 들었든 책으로 봤든 **하나**입니다. 가공 층을 출처별로 쪼개면 같은 개념이 두세 곳에 중복 생성되고, 링크 그래프가 그만큼 갈라집니다. 그래프가 갈라지면 "이미 아는 것"을 검색으로 찾을 수 없게 되는데, 그게 애초에 해결하려던 첫 번째 증상이었습니다.

그래서 원칙을 뒤집었습니다.

- **출처(raw)는 origin별로 분리한다.** 멘토링 raw와 공부 raw는 끝까지 섞지 않습니다. 출처의 신뢰도와 인용 방식이 다르기 때문입니다.
- **가공은 유일한 한 층으로 통일한다.** 원자 개념과 고수준 주제, 둘만 둡니다. 출처가 어디였는지는 개념 노트 안에서 소스 링크로만 표현합니다.

```text
출처 (origin별 분리)            가공 (단일 층)              산출
  멘토링/raw  ─┐
               ├─→  knowledge/concepts ─→ knowledge/topics ─┬─→ blog-drafts
  study/raw   ─┘            ↑                              └─→ 프로젝트 코드
                            │
                     study/gap (갭 체크리스트)
                     topics의 requires와 대조
```

이 결정 하나로 "이건 어디에 정리하지?"라는 판단이 사라졌습니다. 답이 항상 같기 때문입니다. **가공물은 무조건 knowledge로.** 하루에 열 번씩 하던 결정이 규칙 한 줄로 상수가 됐습니다.

다만 트레이드오프가 있었습니다. 멘토링 위키에 이미 있는 개념들을 한 번에 옮기면 멘토링 그래프의 내부 링크가 통째로 깨집니다. 그래서 **온디맨드 승격**으로 절충했습니다. 어떤 주제가 그 개념을 실제로 필요로 할 때만 knowledge로 끌어올립니다. 대량 이관을 하지 않으니 깨지는 링크도 없고, 승격된 개념은 항상 쓰임이 검증된 것들만 남습니다.

## 미참조 160개의 실체 — 숫자부터 의심하기

구조가 잡히자 검증이 필요했습니다. 멘토링 raw 209개 중 위키로 들어오지 않은 것이 얼마나 되는지 lint를 돌렸습니다.

결과는 **미참조 160개**였습니다. 209개 중 160개가 반영되지 않았다는 뜻이니, 사실상 시스템이 작동하지 않았다는 판정으로 읽혔습니다.

그런데 목록을 하나씩 열어봤더니 대부분이 멘토가 첨부한 **코드 레포의 부수 파일**이었습니다. README, 차트, 소스 파일이 raw 폴더에 통째로 딸려 들어와 분모와 분자를 동시에 부풀리고 있었습니다. 경로 패턴으로 코드 레포 노이즈를 걷어내자 진짜 미반영 멘토링 노트는 **29개**였습니다. 이건 하루에 처리할 수 있는 양이었고, source 페이지와 개념으로 ingest해 미참조를 0으로 만들었습니다.

| 지표 | 첫 측정 | 노이즈 필터 후 | 처리 후 |
| --- | --- | --- | --- |
| raw 노트 총계 | 209 | — | — |
| 미참조 | 160 | 29 | 0 |

배운 것은 하나입니다. **수치는 항상 "무엇을 세고 있는가"부터 의심해야 합니다.** 160이라는 숫자는 거짓이 아니었지만, 측정 대상이 제가 생각한 것과 달랐습니다. 부하테스트에서 오류율 96%를 보고 인증을 의심했던 것과 정확히 같은 종류의 실수입니다. 도구는 정직하게 답했고, 질문이 틀렸습니다.

## macOS 한글 파일명이 lint를 속인 방식

같은 lint에서 더 고약한 오탐이 있었습니다. 멘토링 source 노트에 위키링크를 분명히 넣었는데도 lint가 계속 미참조로 잡았습니다. 볼트에서 링크를 클릭하면 정상적으로 열립니다. 그래프도 멀쩡합니다. 그런데 스크립트만 못 봅니다.

원인은 **macOS의 파일명 유니코드 정규화**였습니다. 파일 시스템에 저장된 한글 파일명은 자모가 분해된 NFD 형태이고, 제가 에디터에서 타이핑해 넣은 링크 문자열은 결합된 NFC 형태입니다. 사람 눈에는 같은 글자, 바이트로는 다른 문자열이라 단순 비교가 전부 실패합니다.

```python
import unicodedata

def norm(name: str) -> str:
    return unicodedata.normalize("NFC", name)

# 비교 양쪽을 모두 정규화해야 한다
linked = norm(link_target)
actual = norm(path.name)
```

수정은 비교 직전에 양쪽을 `unicodedata.normalize("NFC", ...)`로 통과시키는 것으로 끝났습니다. Obsidian 자체는 내부에서 NFC로 처리하기 때문에 실제 그래프는 처음부터 정상이었습니다. 즉 **버그는 데이터가 아니라 검증기에 있었습니다.**

여기서 얻은 규칙: macOS에서 한글 파일명을 프로그램으로 비교할 일이 생기면 NFC/NFD를 가장 먼저 의심합니다.

곁가지로 하나 더 걸렸습니다. 파일명 자체에 대괄호가 들어간 노트를 위키링크로 걸면 링크 문법과 파일명의 대괄호가 겹쳐 파싱이 깨집니다. 이건 우회가 정답이라 판단해 그 파일만 일반 마크다운 경로 링크로 처리했습니다. 같은 원본이 다른 경로로 이미 참조되고 있어 그래프 완결성은 유지됐습니다.

## 자동화는 마지막에 붙였다

여기까지는 제가 시켜야 돌아가는 반자동이었습니다. 흐름이 수동으로 한 바퀴 검증된 뒤에야 손이 가는 지점에 훅을 붙였습니다. 순서가 중요합니다. 검증 안 된 흐름을 자동화하면 잘못된 결과가 자동으로 쌓입니다.

| 자동화 | 트리거 | 없애준 수작업 |
| --- | --- | --- |
| 세션 시작 스캔 | 에이전트 세션 시작 훅 | 지금 쓸 수 있는 글감·남은 공부 갭·미처리 트러블슈팅을 매번 손으로 확인하던 일 |
| 갭 대시보드 | 볼트 쿼리 플러그인의 체크박스 집계 | 주제별 체크리스트를 돌아다니며 진도를 세던 일 |
| 트러블슈팅 인박스 자동 적재 | 프로젝트 리포의 post-commit 훅 | 사건이 끝난 뒤 기억으로 복원하던 일 |

세 번째가 실제로 가장 큰 차이를 만들었습니다. 프로젝트 리포에서 `fix:` 계열 커밋이나 버그 관련 커밋을 하면 post-commit 훅이 트러블슈팅 인박스에 항목을 자동으로 적재합니다.

사건이 벌어진 그 순간에 기록이 생기기 때문에, 며칠 지나 "그때 왜 그렇게 고쳤지"를 복원하지 않아도 됩니다. **디버깅의 맥락은 커밋을 찍는 순간이 가장 진하고, 그 뒤로는 단조 감소합니다.** 그 시점을 훅으로 낚아채는 것이 요점이었습니다.

## 네 단계를 한 표로

| 단계 | 접근 | 해결한 것 | 남은 한계 → 다음 |
| --- | --- | --- | --- |
| 1 | 단일 통합 | 단순한 멘탈 모델 | 기존 하네스·독립 git 붕괴 → 얇은 층 |
| 2 | 얇은 오케스트레이션 층 | 독립성 보존 + 통합 효과 | 가공 지식의 저장 위치 모호 → 구조 재설계 |
| 3 | 출처/가공 분리 | 개념 중복 제거, 단일 그래프 | 멘토링 그래프 보호 → 온디맨드 승격 |
| 4 | 자동화 훅 | 수동 트리거 제거 | 외부 발행은 의존성 때문에 수동 유지 |

## 배운 것

- **좋은 시스템은 통합이 아니라 경계 설정에서 나옵니다.** 무엇을 합칠지보다 무엇을 합치지 않을지, 어디를 불가침으로 둘지를 정하는 것이 전환점이었습니다.
- **중복을 없애는 규칙 하나가 수십 개의 결정을 없앱니다.** "가공물은 무조건 한 층으로"가 "이건 어디에 두지?"라는 반복 판단을 제거했습니다.
- **검증기를 먼저 검증합니다.** 미참조 160개도, NFC/NFD 오탐도, 데이터가 아니라 측정 도구의 문제였습니다.
- **자동화는 흐름을 수동으로 한 바퀴 돌린 뒤에.** 검증 순서를 뒤집으면 잘못된 결과가 자동으로 축적됩니다.
