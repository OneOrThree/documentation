API 전체를 무너뜨린 범인은 하나였습니다. 가장 뜨거운 테이블 `focus_sessions`(3,000만 행)에 **보조 인덱스가 0개**였고, 그 위를 도는 쿼리가 100초 가까이 커넥션을 쥐고 있었습니다. 커넥션 풀은 기본값 10개였고, 밀린 요청은 HikariCP `connectionTimeout` 기본값인 30초에서 잘려 나갔습니다. 그래서 붕괴 run의 p99가 정확히 30,000ms였습니다.

문제는 그 결론에 도달하기까지 **가짜 범인을 셋이나 거쳤다**는 점입니다. 셋 다 측정 도구와 절차 쪽 결함이었습니다.

## 측정 조건

유저 10만 · 집중세션 3,000만 행 위에서 API **72종을 한 믹스에 넣어 일괄 측정**했습니다. recipe 자동 생성으로 전체 API 93종 중 86종이 실행 가능해졌고, 그중 72종이 이날의 믹스입니다.

| 축 | 구성 |
| --- | --- |
| 부하 모델 | k6 · open model(`constant-arrival-rate`) — 서버가 느려져도 유입을 유지해 coordinated omission을 피합니다 |
| 데이터 | 프로드 스케일 golden DB, 동결 시점 실적재 약 6,500만 건(22GB, 설계 목표는 7,000만 건), run마다 `CREATE DATABASE ... TEMPLATE golden`으로 복제 |
| 관측 | micrometer + node-exporter + `pg_stat_statements`를 Prometheus가 수집, 워밍업 2분은 본측정에서 분리 |
| SUT | 2vCPU VM + Cloud SQL PostgreSQL 16(2vCPU), HikariCP 기본 풀 10 |
| 인증 | 부하 전에 JWT를 대량 사전 발급해 k6 유저 풀로 사용 |

run마다 DB를 템플릿에서 다시 만드는 이유와 그 비용 계산은 [설계 노트](/research/loadtest-design)에 있습니다.

## 1차 — 에러율 95.7%, 그런데 성공한 게 딱 두 개였습니다

72종을 한 믹스에 넣고 smoke(5rps × 1분)부터 쐈습니다. 넓게 훑는 게 목표였으니 얕게 시작해 깨진 곳부터 찾았습니다.

에러율은 95.7%였습니다. 이상한 건 **성공한 엔드포인트가 단 2개**였다는 점입니다. `/health`와 게스트 로그인, 둘 다 인증이 필요 없는 엔드포인트였습니다. 지연은 1ms대였고, 그 속도는 서버가 요청을 처리하지 않고 문턱에서 곧바로 거부했다는 신호였습니다.

원인은 시드 산출물이었습니다. 얼마 전 토큰 하드닝 작업에서 JWT에 `type` 클레임을 넣었고, 필터도 클레임이 없으면 fail-closed로 401을 반환하도록 고쳤습니다. 그런데 시드 단계에서 미리 발급해 둔 부하용 토큰은 `{sub, iat, exp}`만 갖고 있었습니다.

```text
발급 시점의 시드 토큰 : {sub, iat, exp}
현재 필터가 요구하는 것 : {sub, iat, exp, type: "access"}
→ 클레임 없음 = fail-closed 401 (1ms 만에)
```

토큰 75,232장을 `type: "access"` 포함으로 재서명하고, curl로 200을 확인한 뒤 재실행했습니다. 컴파일러도 테스트도 이 드리프트는 잡아주지 못했습니다. 시드 토큰이 코드 밖에 데이터로 남아 있었기 때문입니다.

## 2차 — 토큰을 고쳤는데 이번엔 500이 쏟아졌습니다

에러율 86%. 이번 주력은 **500**이었고, 인증이 필요 없는 게스트 로그인까지 실패했습니다.

`pg_stat_statements`를 열어 보니 인증 필터가 내는 쿼리는 285회 **성공**했는데, 컨트롤러 단의 쿼리가 거의 없었습니다. 요청이 필터는 통과하고 서비스 계층에서 죽고 있다는 뜻입니다.

범인은 재실행 절차였습니다. run마다 DB는 `DROP DATABASE` → `CREATE ... TEMPLATE golden`으로 갈아엎는데, 앱 컨테이너는 `docker compose up -d`로 띄웁니다. compose는 이미지와 설정이 같으면 아무 일도 하지 않습니다.

```bash
# 리셋 절차 (문제 있던 버전)
psql -c 'DROP DATABASE gromo'
psql -c 'CREATE DATABASE gromo TEMPLATE golden'
docker compose up -d          # 이미지 동일 → no-op → 이전 run의 JVM이 그대로 생존
```

즉 **DB가 통째로 갈리는 동안 이전 run의 앱 프로세스가 살아남아** 오염된 상태로 500을 뱉고 있었습니다. 같은 요청을 새 JVM에서 단건으로 보내니 전부 200이었습니다(부하 상황의 게스트 로그인 500은 이와 별개로 남았고, 다음 과제에 있습니다). 리셋 전에 앱을 명시적으로 정지시키는 단계를 파이프라인에 넣어 해결했습니다.

이 갭이 그동안 드러나지 않은 이유는 CI 경로에 있었습니다. 커밋마다 이미지 태그가 바뀌니 컨테이너는 늘 재생성됩니다. "같은 이미지로 재실행"은 사람이 손으로 반복 측정할 때만 밟는 경로였고, 그 경로는 첫 실행과 다르게 동작했습니다. 멱등성을 확인하려면 재실행도 따로 한 번 돌려봐야 했습니다.

## 3차 — 이제 진짜 숫자가 나오는데, 절반이 4xx였습니다

에러율 45.9%. 실패의 성격이 달라졌고, 정체는 **계약성 오류**였습니다. 원인을 분류하려고 k6 스크립트에 (엔드포인트 × 상태코드 × 응답 본문) 로깅을 심고 같은 믹스를 5rps로 다시 돌렸습니다. 로깅을 심은 뒤로는 실패를 전부 남겼고, 4차 붕괴 run까지 포함해 이날 쌓인 실패 로그는 43,855건입니다. 그중 이 3차 재실행 몫은 이렇게 갈렸습니다.

| 상태 | 대표 코드 | 정체 |
| --- | --- | --- |
| 403 | 그룹 API 전반 | 랜덤 유저 × 랜덤 그룹 조합은 대부분 비멤버 — 부하 스크립트 설계의 한계 |
| 400 | `UNSUPPORTED_EVENT`, `INVALID_PARAMETER(from)` | 스크립트가 만든 요청이 최신 API 검증과 어긋남(계약 드리프트) |
| 400 | `SELF_REQUEST`, `SELF_PIN` | 랜덤 페어링이 자기 자신을 뽑는 엣지 |
| 409 | 중복 충돌 | 랜덤 쓰기의 정상 거부 — 서버가 옳게 동작한 결과 |

5rps에서 에러 0%인 31종만 clean set으로 추렸습니다. 이 분리를 건너뛰었다면 이후의 지연 지표는 "정상적으로 거부된 요청"의 1ms와 섞여 희석됐을 겁니다.

## 4차 — 50rps에서 전면 붕괴, 그리고 라운드 넘버

clean set으로 부하를 50rps까지 올리자 에러율 96.1%가 나왔습니다. 전 엔드포인트가 동반 붕괴했고, 지표에서 **p99 = 30,000.0ms**를 봤습니다.

이건 응답 시간이 아니라 HikariCP `connectionTimeout` 기본값 30초입니다. 요청들이 DB 커넥션을 30초 기다리다 죽고 있었습니다. 지연 지표가 라운드 넘버에 정확히 걸리면, 그 숫자가 어떤 설정의 기본값인지부터 의심하는 게 빠릅니다. 병목은 **커넥션을 오래 쥔 쿼리** 쪽입니다.

붕괴 순간의 `pg_stat_statements` 상위 쿼리는 전부 같은 테이블을 향하고 있었습니다.

| 쿼리 | 평균 실행시간 |
| --- | --- |
| `FocusSession WHERE user = ? AND startedAt BETWEEN ...` | 99~111초 |
| `FocusSession WHERE user IN (...) AND endedAt IS NULL` (isFocusing) | 63~146초 |
| `FocusSession LEFT JOIN FETCH focusTag ...` | 90~107초 |

`focus_sessions`는 3,000만 행, 이 앱에서 가장 뜨거운 테이블입니다. 설계 단계 스키마 조사에서 이미 1순위 표적으로 지목해 둔 곳이기도 합니다([설계 노트](/research/loadtest-design)). 이날 실측으로 그 표적이 전면 장애까지 가는 경로를 확인했습니다. 스키마의 보조 인덱스는 0개, PK와 FK 제약뿐이었고, PostgreSQL의 FK는 인덱스를 자동 생성하지 않습니다(MySQL은 만듭니다). 그래서 `WHERE user_id = ?`가 매번 3,000만 행 시퀀셜 스캔이었습니다. dev DB에서는 같은 쿼리가 수백 건 위에서 0ms로 끝나니 아무도 몰랐습니다.

### 단일 쿼리 지연이 전면 장애가 되는 경로

1. **점유** — 100초짜리 쿼리는 그 100초 동안 커넥션을 반납하지 않습니다. 총 50rps를 clean set 31종에 분산하니 킬러 쿼리 하나당 2rps 안팎입니다. 리틀의 법칙으로 2rps × 100초 = 동시 200 커넥션 수요, 풀은 10개입니다.
2. **대기** — 인덱스와 아무 상관없는 요청까지 같은 커넥션 대기열에 균일하게 밀립니다. 그래서 "전부 느려" 보입니다.
3. **위장** — 30초 타임아웃이 터지면 인증 필터가 유저 조회 실패로 판단해 fail-closed 401을 반환합니다. 모니터링에는 인증 장애로 보입니다. 3차에서 심어 둔 로깅 덕분에 이 붕괴 run의 응답도 그대로 남았는데, 최다 상태코드가 401이었습니다.

이 위장 때문에 운영에서는 오진이 나기 쉽습니다. 단건 curl은 200을 주니, "부하 걸면 로그인이 깨진다"는 잘못된 가설을 붙잡고 시간을 태우게 됩니다.

## 5차 — 격리 실증: 그 테이블 하나가 범인인가

"전부 느리다"와 "하나가 다 막고 있다"는 지표만으로는 구분되지 않습니다. 가설이 맞다면 세 가지 예측이 성립해야 합니다. 격리 run 셋으로 하나씩 확인했습니다.

| run | 구성 | 예측 | 실측 |
| --- | --- | --- | --- |
| 격리 A | 킬러 7종만 × 2rps | 저부하에서도 붕괴해야 함 | 에러 87.5%, p95 60s — 붕괴 |
| 격리 B | 코어 24종(킬러 1종 잔류) × 30rps | 1종만 남아도 전파돼야 함 | 에러 83.9% — 독살 전파 |
| 격리 C | 코어 23종(킬러 완전 제거) × 30rps | 회복돼야 함 | 에러 8.1% — 붕괴 해소(단 p95는 4.5초) |

격리 A의 2rps는 어떤 기준으로도 저부하인데, 거기서 이미 붕괴했습니다. 즉 이건 용량 문제가 아니라 **쿼리 하나의 문제**입니다. 격리 B에서는 킬러를 딱 1종만 남겼는데도 무관한 23종이 같이 죽었습니다. 커넥션 풀이 공유 자원이라 격리가 없기 때문입니다.

격리 C에서 결정적인 대조가 하나 더 나왔습니다. DB를 타지 않는 `/health`는 p95 1ms인데, DB를 타는 나머지는 전부 균일하게 약 4.5초였습니다. **모두가 같은 대기열에 서 있다**는 뜻입니다. 남은 4.5초는 다음 병목의 몫이고, 그 후보들(친구 관계 역방향 조회, 리그 랭킹 집계 등)도 같은 종류의 문제로 보입니다.

## 남긴 것

하루 동안 잡은 범인 넷과 그 순서입니다.

| 단계 | 증상 | 범인 | 교훈 |
| --- | --- | --- | --- |
| 1차 | 인증 API 전멸(401), 95.7% | 시드 JWT에 `type` 클레임 없음 | 시드 산출물도 코드와 함께 진화해야 합니다 |
| 2차 | 500 폭발, 필터만 통과, 86% | compose no-op이 만든 좀비 JVM | 재실행은 별도의 실행 경로입니다 |
| 3차 | 4xx 45.9% | 측정 도구와 API의 계약 드리프트 | 성능을 묻기 전에 성공 집합을 분리합니다 |
| 4차 | 50rps 전면 붕괴, p99 30s, 96.1% | `focus_sessions` 보조 인덱스 0개 | FK는 인덱스가 아닙니다. 스케일 데이터에서만 보입니다 |
| 5차 | — | 격리 3-run으로 단일 원인 실증 | 가설은 예측을 세우고 격리로 검증합니다 |

이날 잡은 범인 4개 중 3개는 서버 밖, 하네스와 절차에 있었습니다. **측정 시스템 자체도 소프트웨어**라는 사실을 값을 치르고 배웠습니다.

### 부수적으로 드러난 두 가지

- **관측 없는 fail-closed는 블랙박스입니다.** fail-closed로 401을 주는 판단 자체는 맞습니다. 다만 인프라 실패와 인증 실패가 같은 코드·같은 로그로 나오면 운영에서 오진합니다. 덤으로 logback에 부하테스트 프로파일용 appender가 없어 스택트레이스가 통째로 유실되고 있었습니다.
- **클라이언트가 포기해도 서버 쿼리는 살아 있습니다.** k6와 HikariCP는 30~60초에 포기하지만 PostgreSQL의 시퀀셜 스캔은 취소되지 않고 계속 돕니다. 그동안 유령 쿼리가 CPU와 I/O를 그대로 먹습니다. DB는 run마다 갈아엎어도 Cloud SQL 인스턴스는 그대로라, 이전 run의 스캔이 아직 도는 동안 시작한 다음 run은 워밍업부터 오염된 자원 위에서 출발했습니다. 후속 run이 원인 불명으로 느렸던 이유가 이것입니다. 앱 커넥션에 `statement_timeout` 상한(5~10초)을 걸어 클라이언트 포기가 서버 취소가 되도록 해야 합니다.

### 다음 과제

병목의 대부분이 `CREATE INDEX` 다섯 줄 거리였습니다. 하지만 **프로드 스케일 데이터 + 커넥션 풀 + 타임아웃의 상호작용**을 실측하기 전에는 그 다섯 줄이 P0라는 걸 증명할 수 없었습니다. 하네스를 만든 값은 여기서 회수했습니다.

- P0 인덱스 5종을 Flyway 마이그레이션으로 반영: `focus_sessions(user_id, started_at)` · `focus_sessions(user_id) WHERE ended_at IS NULL`(부분 인덱스) · `friendships(to_user_id, status)` · `group_members(group_id)` · `currency_transactions(user_id, created_at DESC)`
