## 결론 — 셋 다 git 파일 목록에는 안 보이고 실제 DB 상태에서만 드러났다

가장 큰 것은 53초 차이의 머지 순서 역전입니다. dev 전 엔드포인트가 502가 되고 CD가 6연속 실패했습니다. 증상은 전부 달랐지만 원인 구조는 하나였습니다.

| 사고 | 티켓 | 증상 | 실제 원인 |
| --- | --- | --- | --- |
| 제약 이름 의존 | GROMO-817 | prod CD만 실패, 앱 기동 차단 | prod는 Flyway 도입 전 이력이라 제약 이름이 베이스라인과 다름 |
| 마스터 데이터 누락 | GROMO-910 | 에러 없이 빈 목록·기능 거부 | 스키마는 코드화, 시드는 사람 손에만 있었음 |
| 머지 순서 역전 | GROMO-1050 → 1063 → 1065 | dev 전 엔드포인트 502, CD 6연속 실패 | 배포 순서가 파일 번호 순서와 어긋남 |

근거는 사고마다 달랐습니다. 사고 1과 3은 환경마다 다른 제약 이름과 적용 이력, 사고 2는 전부 success인 `flyway_schema_history`. 세 경우 모두 그 상태를 보는 자동 검사가 없었습니다.

## 사고 1 — prod만 제약 이름이 달랐다 (GROMO-817)

dev에서 통과한 `V14__remove_legacy_league_arena_membership.sql`이 프로덕션 배포에서 실패했습니다.

```text
constraint "uq_league_rank_snapshots_arena_user_day" ... does not exist
```

마이그레이션이 실패하면 Flyway 초기화가 실패하고 앱이 아예 뜨지 않으므로, 스키마 한 줄 때문에 배포 전체가 막힙니다.

원인은 환경의 나이 차이였습니다. 프로덕션은 Flyway를 도입(GROMO-670, PR #166)하기 전에 레거시 셸 스크립트로 만들어진 DB입니다. `league_rank_snapshots`의 유니크 제약 이름이 베이스라인 스냅샷과 달랐습니다. Hibernate가 자동으로 붙인 이름이 남아 있었던 것으로 보입니다. V14는 그 제약을 고정 이름으로 지목해서 DROP하고 있었습니다.

수정은 이름 지목을 버리는 것이었습니다.

```sql
-- 이전: 베이스라인의 고정 이름에 의존
ALTER TABLE league_rank_snapshots
  DROP CONSTRAINT uq_league_rank_snapshots_arena_user_day;

-- 이후: 컬럼 DROP에 제거를 위임
ALTER TABLE league_rank_snapshots DROP COLUMN arena_id;
```

PostgreSQL은 컬럼을 지우면 그 컬럼을 포함한 유니크 제약과 인덱스를 이름과 무관하게 함께 제거합니다. 운영 DB의 실제 이름이 무엇이든 통과합니다. 이름이 맞는 dev 리셋 경로만 `DROP CONSTRAINT IF EXISTS`로 정리했습니다. 최종 스키마와 엔티티 매핑은 그대로였고, 달라진 것은 제거 방식 하나뿐이었습니다(`fa74a955`).

검증은 로컬 PostgreSQL 16에서 두 시나리오를 각각 재현했습니다. 프로덕션식(다른 이름 제약이 존재)과 dev식(베이스라인 이름이 존재). 그리고 수동 검증으로 끝내지 않고 `LeagueLegacyMigrationTest`에 회귀 테스트를 넣었습니다(`38abae3a`). V13까지 올린 뒤 제약을 Hibernate 자동 생성명 흉내로 rename하고 V14를 돌려, 이름 무관 전환이 성립하는지를 CI가 매번 확인합니다.

PostgreSQL은 DDL이 트랜잭셔널이라, 마이그레이션 실행문과 `flyway_schema_history` INSERT가 같은 트랜잭션에 묶여 함께 롤백됩니다. 그래서 이 실패는 FAILED 행 자체를 남기지 않는 것이 일반적입니다. 재배포 시 `flyway repair`를 먼저 돌릴 필요가 없다는 뜻이고, 예외적으로 실패 마커가 남았을 때만 1회 필요합니다. 사고 수습 절차에 "일단 repair"를 반사적으로 넣지 않게 된 근거입니다.

## 사고 2 — 에러 로그 없이 빈 배열 200 (GROMO-910)

새 프로덕션 환경을 세우고 빈 DB에 앱을 붙였습니다. Flyway는 정상 동작해 `flyway_schema_history`에 V1부터 V15까지 전부 success로 찍혔고, Hibernate `validate`도 통과했습니다. 스키마 쪽은 문제가 없었습니다.

그런데 서비스는 반쯤 죽어 있었습니다. 온보딩 직업 목록(`GET /api/v1/occupations`)·상점·인벤토리·추천 태그·뽀모도로 프리셋이 모두 빈 배열 200으로 내려갔고, 직업 설정 요청만 `OCCUPATION_NOT_AVAILABLE` 4xx였습니다.

에러 로그는 거의 없었습니다. 조회 경로 대부분이 빈 결과를 정상 응답으로 내려주기 때문입니다. 모니터링에서 5xx도 예외도 안 보이는데 앱은 쓸 수 없는 상태였습니다.

마이그레이션을 전수 조사해서 "이 값들은 대체 어디서 오는가"를 물었습니다. 답은 "아무 데서도 오지 않는다"였습니다.

| 주입 경로 | 실제 |
| --- | --- |
| Flyway 시드 마이그레이션 | `V13`(리그 티어 5행) 단 1개 |
| 나머지 INSERT 7개 (V3·V4·V5) | 전부 `INSERT ... SELECT` 형태의 backfill → 빈 DB에서 0행 |
| `data.sql` / `init.sql` / `import.sql` | 없음 |
| `ApplicationRunner` / `CommandLineRunner` / `@PostConstruct` | grep 0건 |
| `@Profile("dev")` 시더 빈 | 없음 |

dev DB의 마스터 값은 과거에 사람이 손으로 넣은 것이 누적된 상태였습니다. 코드 어디에도 그것을 재현할 방법이 없었지만, dev가 오래 살아 있는 동안에는 부재가 드러날 일이 없었습니다.

가장 뼈아팠던 증거는 `V6__add_pomodoro_tables.sql` 5번째 줄의 주석입니다. "뽀모도로 프리셋(서버 관리 시드, 하드코딩 대체)"이라고 써놓고 그 파일에 INSERT가 한 줄도 없습니다. 의도만 주석에 남고 구현이 따라가지 않은 것을, 빈 DB가 처음 세워질 때까지 아무도 몰랐습니다.

### 왜 테스트가 이걸 못 잡았나

사각지대가 두 개 겹쳐 있었습니다.

| 프로파일 | 시드 결과 |
| --- | --- |
| base / `local` (기본) | 0건 |
| `ci` | 0건 (테스트가 직접 세팅) |
| `dev` / `staging` / `prod` / `loadtest` | V13만 |

첫째, `ci` 프로파일은 Flyway가 꺼져 있고 `create-drop`입니다. 리그 테스트들은 `leagueTierConfigRepository.save(...)`로 티어 설정을 직접 만들어 씁니다. 그래서 테스트는 100% 통과하면서 시드 부재는 원천적으로 검출될 수 없습니다. 픽스처를 테스트가 직접 만들어 쓰니 "프로덕션에서 이 데이터는 어디서 오는가"라는 질문이 나올 자리가 없었습니다.

둘째, dev 리셋 스크립트가 정본 경로를 우회합니다. `DROP SCHEMA public CASCADE` 후 `ddl-auto=update`로 스키마만 재생성하기 때문에 Flyway를 타지 않고, 유일하게 코드화돼 있던 V13 시드조차 들어가지 않습니다. 이걸로 dev를 리셋하면 `league_tier_configs`가 0행이 되고, 그 주 월요일 00시 KST 리그 배치가 티어 설정을 못 찾아 예외로 중단됩니다. Flyway를 정본으로 선언해 뒀지만, 정작 개발자가 매일 돌리는 리셋 툴은 그 정본을 한 번도 거치지 않았습니다. 프로파일을 이렇게 갈라놓은 설계의 근거는 [flyway-core를 넣었는데 왜 안 켜질까](/research/flyway-adoption)에 있습니다.

수습은 임시였습니다. DB 클라이언트로 prod에 붙어 dev 값을 수동 복사했습니다. 서비스는 복구됐지만 재현 불가·이력 없음이라 근본 해결이 아니고, prod를 다시 세우면 그대로 재발합니다. 근본 방향은 V13 패턴(리터럴 INSERT + `ON CONFLICT DO UPDATE` + 검증 `DO` 블록)을 나머지 마스터 테이블로 확장하는 것으로 잡았습니다.

한 가지는 명확히 기각했습니다. `spring.sql.init` + `data.sql`은 채택하지 않았습니다. Flyway와 실행 순서가 얽히고 프로파일별 on/off 스위치가 하나 더 늘어납니다. 스키마 정본이 이미 Flyway인데 데이터 정본을 다른 곳에 두면 이번 사고를 고치는 대가로 다음 사고의 원인을 하나 늘리게 됩니다.

시드 정본을 찾는 과정에서 오답 하나를 걸렀습니다. 부하테스트 시드 스크립트가 전 마스터 테이블을 채우는 유일한 스크립트여서 "여기서 값을 가져오면 되겠다" 싶었지만, 값이 전부 합성 더미였습니다. 직군 표시명이 `직군-LABOR_ATTORNEY` 꼴이고 아이템이 `아이템0`부터 순번입니다. 부하테스트는 행 수와 문자열 분포만 맞으면 되니 값이 진짜일 이유가 없고, 그래서 같은 테이블을 다 채우는 스크립트라도 목적이 다르면 시드 정본으로는 못 씁니다.

## 사고 3 — 53초 차이가 만든 3연쇄 (GROMO-1050)

앱의 그룹 화면이 안 뜬다는 제보로 시작했는데, 실제로는 `/actuator/health`·`/swagger-ui`·리그·유저까지 전 엔드포인트가 nginx 502였습니다. 그룹 기능 코드는 무관했습니다.

같은 그룹 챌린지 작업을 병렬 워크트리로 돌리다 두 PR이 1분 안에 연속 머지된 것이 원인이었습니다.

| 시각 (KST) | 일 |
| --- | --- |
| 06:19:38 | V21 초대 링크(#412) 머지 → CD 배포 |
| 06:20:31 | V20 그룹 챌린지 스키마(#414) 머지 — 53초 늦음 |

원인은 V21 배포의 Flyway 로그에 그대로 남아 있었습니다.

```text
Current version of schema "public": 19
Migrating schema "public" to version "21 - group invite links"
Successfully applied 1 migration to schema "public", now at version v21
```

그 빌드의 클래스패스에는 V20이 아직 없었고, Flyway는 V19 다음에 곧장 V21을 적용했습니다. dev DB의 버전은 20을 빈칸으로 둔 채 21이 됐습니다. 53초 뒤 V20이 main에 머지되자, 그 다음부터 모든 배포가 부팅 시점에 죽었습니다.

```text
FlywayValidateException: Validate failed: Migrations have failed validation
Detected resolved migration not applied to database: 20.
```

`flywayInitializer` 빈 생성 실패가 `entityManagerFactory`로, 다시 리포지토리 빈으로 연쇄해 컨텍스트 기동이 실패합니다. 컨테이너는 뜨지만 앱이 없으니 nginx가 업스트림을 못 잡고 전 경로가 502입니다. V20 머지 이후 시작된 배포 6건은 전부 이 한 원인으로 실패했습니다.

### 수습이 두 번 더 실패한 순서

1차 조치를 하면서 전제가 깨졌고, 그 탓에 2차·3차 수습이 연달아 실패했습니다(#437 → #444 → #447의 3연쇄).

| 순서 | 조치 | 결과 |
| --- | --- | --- |
| 1차 (#437) | `application-dev.yml`에 `spring.flyway.out-of-order: true` (dev 전용 4줄) | dev 기동 회복. 이 배포로 원본 V20이 dev DB에 소급 적용됨 |
| 2차 (#444) | 그 사실을 모른 채 `V20__...sql` → `V24__...sql`로 번호 이동 | `Detected applied migration not resolved locally: 20` — 역방향 실패 (실패 1) |
| 3차 (#447) | 파일명을 V20으로 복원 | `Migration checksum mismatch for migration version 20` (실패 2) |
| 4차 (#449) | 파일 내용을 최초 적용 커밋과 바이트 단위로 일치시켜 복원 | 통과 |

3차와 4차의 차이가 6줄입니다. #444가 번호를 옮길 때 헤더 주석에 "V24로 옮긴 사유" 6줄을 함께 적었고, #447이 파일명만 되돌렸기 때문에 내용이 적용본과 달라졌습니다. Flyway가 체크섬으로 잡아낸 것은 그 주석 6줄이었고, DDL은 한 글자도 다르지 않았습니다. 4차 수습은 `git diff`가 0줄임을 확인하는 작업이었습니다.

**체크섬은 DDL의 해시가 아니라 파일의 해시입니다.** 이미 적용된 마이그레이션 파일은 주석조차 건드릴 수 없습니다. 머리로는 알고 있었지만, 수습이 급한 상황에서 "주석은 안전하겠지"라고 판단해 장애를 한 번 더 만들었습니다.

### 번호 이동이 왜 안전했나 (그리고 왜 그것만으로 안 끝났나)

2차 조치가 틀린 판단은 아니었습니다. 번호를 뒤로 미뤄도 안전하다는 근거는 대상 객체가 완전히 분리돼 있다는 것이었습니다.

| 마이그레이션 (#444가 상정한 번호) | 대상 |
| --- | --- |
| V24 (당시 V20 파일) | `group_challenge_bets` · `group_challenge_windows` · `group_challenge_members` · `group_challenges` |
| V21 | `group_invite_links` · `invite_link_clicks` |
| V22 | `currency_transactions` |
| V23 | `character_generation` |

교집합이 없으니 적용 순서와 무관하게 최종 스키마가 같습니다. 검증도 했습니다. 로컬 `postgres:16-alpine`에 dev와 같은 상태(V1~V19 → V21 → V22 → V23, V20 생략)를 재현한 뒤 V24로 번호를 바꾼 파일을 얹어, 의도한 변경 4종이 전부 생기는 것을 확인했습니다.

```bash
# 확인한 것: 내기 status CHECK 확장 · windows.duration_minutes
#            members.usage_date · uq_group_challenges_active_cat_type
```

논리도 검증도 맞았지만 전제가 틀렸습니다. "V20은 적용된 적 없는 파일"이라는 전제는 1차 조치의 배포 한 번으로 이미 깨져 있었습니다. 이 번호 이동은 3차·4차에서 되돌려졌고, V24는 지금도 빈 번호입니다.

### failure로 끝난 런이 이미 커밋해 둔 것

V21을 배포한 CD 런은 "failure"로 끝났습니다. 겉보기엔 "배포 실패 → DB는 안 건드려졌다"입니다. 실제 로그 순서는 이랬습니다.

| 로그 시각 (UTC) | 일 |
| --- | --- |
| 21:27:51 | Flyway가 V21을 커밋 완료 |
| 21:28:17 | JPA 초기화 진행 중 |
| 21:28:33 | CD가 헬스체크 대기 시간을 넘겨 런을 failure로 기록 |

머지가 06:19:38 KST(21:19:38 UTC)였으니, Flyway 커밋(06:27:51 KST)까지의 8분은 빌드·배포 시간입니다. 이 런의 failure는 CD 6연속 실패와 원인이 다릅니다. Flyway는 성공했고 실패한 것은 그 뒤의 헬스체크 대기였으니, 6연속에는 들어가지 않습니다. 1차 조치(#437)의 배포도 워크플로는 cancelled였지만 서버 컨테이너는 마이그레이션을 이미 수행했습니다.

마이그레이션은 앱 부팅 시퀀스의 앞쪽에 있고, **배포가 실패해도 그 시점까지의 스키마 변경은 이미 확정입니다.** 그래서 2차·3차 수습이 헛돌았고, 우리는 이제 롤백이든 재수습이든 판단하기 전에 `flyway_schema_history`를 먼저 조회합니다.

한 가지 판단은 지금도 같습니다. `out-of-order: true`는 dev를 살리지만 검증 완화가 영구히 남아 이후의 진짜 순서 의존 버그를 가립니다. 그래서 prod에는 넣지 않았고, dev만 병렬 브랜치 개발의 현실을 받아들여 상시 허용으로 뒀습니다.

## 남은 규칙과 아직 없는 것

세 사고에서 규칙으로 굳힌 것들입니다.

- **마이그레이션은 이름에 의존하지 않는다.** 제약·인덱스 이름은 환경의 나이에 따라 다릅니다. 컬럼 DROP처럼 이름과 무관한 수단이 있으면 그것을 씁니다.
- **적용된 파일은 주석도 불변이다.** 오류는 다음 번호로 보정합니다(forward-only).
- **번호는 예약되지 않는다.** 브랜치에서 "다음은 VN"이라고 잡아도 먼저 머지한 쪽이 가져갑니다. GROMO-910이 예약해 둔 V16은 다른 티켓을 먼저 머지하면서 그쪽 몫이 됐고, GROMO-1050은 순서 역전으로 터졌습니다.
- **조용한 빈 배열보다 기동 실패가 낫다.** 마스터 데이터가 없으면 부팅 시점에 fail-fast하는 것이 정답입니다. GROMO-910은 5xx도 예외도 없어서 모니터링이 잡을 신호 자체가 없었습니다.

아직 없는 검사도 분명합니다. Flyway는 같은 번호 충돌은 잡지만 빈 번호(순서 역전)는 잡지 못합니다. main의 번호가 연속인지, PR의 새 번호가 현재 main 최대값 + 1인지 검사하는 CI가 필요한데 없습니다.

기각하거나 보류한 것도 있습니다. 흔히 대안으로 꼽히는 "빈 DB에 전 마이그레이션 재생" 잡은 이 사고를 막지 못합니다. 신선 체인은 V20을 포함해 멀쩡히 통과하고, 검사 대상에 실제 dev DB의 `flyway_schema_history`가 들어 있지 않기 때문입니다. 번호를 순번 대신 타임스탬프로 가면 순서 역전과 번호 선점 실패가 한 번에 없어지지만, 이미 20번대까지 순번으로 쌓아둔 상태의 전환 비용은 아직 따져보지 않았습니다.

이 노트를 쓰다가 하나를 더 찾았습니다. 사내 정본 문서에는 사고 직후 상태 그대로 "V20은 결번, 다음 번호는 V25"라고 적혀 있었습니다. 실제로는 #447과 #449가 V20을 되살렸으므로 결번은 없고 다음 번호는 V24입니다. 사고를 기록해 두는 것만으로는 부족하고, 수습이 여러 PR로 이어질 때는 마지막 PR이 정본을 갱신해야 합니다.
