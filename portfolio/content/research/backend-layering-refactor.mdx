알림 서버·초대 링크 서버·API/데이터 서버 분리(GROMO-1658~1661)를 앞두고, 잘라낼 대상인 `server/data-api` 가 **잘라낼 수 있는 모양인지**부터 확인했습니다. 결론은 "아니다"였습니다. 도메인 17개가 같은 성격의 클래스를 서로 다른 자리에 두고 있었고, 서비스 44개가 남의 리포지토리 ~120건을 직접 주입받고 있었으며, 도메인 사이의 순환은 티켓이 추정한 2개가 아니라 **238개**였습니다. 이 상태로 프로세스 경계를 그으면 컴파일 단위가 갈라지지 않습니다.

그래서 에픽 GROMO-1643 을 네 단계로 잘랐습니다. 순서가 곧 의존입니다 — 배치가 정해져야 조회 계층을 둘 자리가 생기고, 조회 계층이 있어야 도메인 사이 의존을 셀 수 있고, 방향이 고정돼야 에러 계약을 공통으로 묶을 때 `common → group` 같은 역참조를 잡을 수 있습니다.

| 1. 배치 규약 | 1654 | #711 | `docs/conventions/backend-layering.md` 정본, 16개 도메인 정렬, 기동 불가 회귀 수리 |
| 2. 조회 계층 | 1655 | #715~#720 | `<Domain>QueryService` 5개, id 조회 직행 0건, 리포지토리 `@Transactional` 10→1 |

기능 변경 0 이 원칙이었고, 앱 계약이 바뀌는 항목은 전부 마지막 티켓(1725)으로 몰아 앱 티켓(1726)과 배포 순서를 묶었습니다. 아래는 단계마다 무엇을 왜 그렇게 했는지, 그리고 리뷰가 잡아 준 제 실수입니다.

## 0. 착수 전에 발견한 것 — HEAD 가 기동조차 안 됐다

배치 정리를 시작하려고 HEAD 를 띄우니 애플리케이션이 뜨지 않았습니다. 직전 커밋이 엔티티를 `<domain>/domain/` 에서 `<domain>/repository/domain/` 으로 옮기면서 `@Query` JPQL **문자열 안의 FQCN 39건**을 갱신하지 않은 것입니다. 컴파일러는 문자열을 보지 않으니 빌드는 초록이고, ApplicationContext 로딩에서 터집니다. 테스트 1,881개 중 434개가 실패했는데 실패 4건이 컨텍스트 로딩이고 나머지 430건은 임계치 초과로 연쇄 스킵된 것이었습니다.

이걸 별도 커밋(`[FIX]`)으로 먼저 고치고 시작했습니다. 이 에픽 내내 반복될 교훈 하나가 여기서 나왔습니다 — **패키지를 옮기면 컴파일러가 못 잡는 자리를 grep 해야 한다.** JPQL 문자열, `@Value`, `@ComponentScan(basePackages)`, logback 설정, `application-*.yml`. 규약 문서 §6 에 이 목록을 그대로 적었습니다.

## 1. 배치 규약 — 다수파를 정본으로, 이름이 아니라 의존성으로

티켓 본문은 컨트롤러를 `api/`, 엔티티를 최상위 `domain/` 에 두는 것을 목표로 적고 있었습니다. 전수 조사를 해 보니 이미 **15/16 도메인이 컨트롤러를 도메인 루트에, 14/16 이 엔티티를 `repository/domain/` 에** 두고 있었습니다. 티켓이 소수파를 목표로 적은 것입니다. 다수파를 정본으로 삼으면 이동량이 최소가 되므로 티켓 본문을 고쳤습니다.

`service/` 와 `support/` 를 가르는 기준을 **이름이 아니라 의존성**으로 잡았습니다 — repository 나 다른 service 를 주입받으면 `service/`, 입력만 받아 계산하면 `support/`. 이름만 보고 고른 이동 후보 13개 중 이 기준으로 실측하니 **8개만 실제 이동 대상**이었습니다. `GroupBetJudge` 는 이름이 판정기지만 리포지토리 5개를 주입받으므로 `service/` 에 남습니다.

`server/data-api/CLAUDE.md` 의 Layout 절은 현재 코드와 정면으로 모순돼 있었습니다(도메인 목록에 `bot`·`character`·`invitelink` 누락, 컨트롤러 수 19 → 실제 30). 정본 문서를 하나 정하고 CLAUDE.md 는 "둘이 어긋나면 문서가 맞다"는 한 줄과 요약만 남겼습니다.

순수 이동이 아닌 변경은 3건뿐이고 전부 커밋을 분리했습니다. 그중 하나가 `invitelink` 랜딩 응답에서 엔티티를 내보내던 자리(`LandingView` 가 `GroupInviteLink` 를 감쌈)를 `InviteLinkRef` DTO 로 바꾼 것입니다 — 컨트롤러가 엔티티를 주고받던 유일한 곳이었습니다.

## 2. 조회 계층 — 같은 유저를 네 가지로 조회하고 있었다

`UserQueryService` 를 먼저 만들었습니다. 31개 service 에 흩어진 User 조회 66건을 접었고 25개 파일에서 `userRepository` 필드가 사라졌습니다. 이유는 보일러플레이트가 아니라 **갈림**이었습니다. 같은 "활성 유저 한 명"을 쿼리로 거르기(`findByIdAndIsDeletedFalse`), 본문에서 `isDeleted()` 로 거르기, `Optional.filter` 로 거르기, 아예 안 거르기(`findById`) 네 가지로 조회하고 있었습니다.

계층을 만들 때 지킨 것 둘입니다.

- **락을 감추지 않는다.** `ForShare`·`ForUpdate` 를 시그니처에 남겼습니다. "그 트랜잭션이 users 행을 변경하면 처음부터 배타 락, 공유 락으로 읽고 나중에 UPDATE 하면 락 승급 교착"(GROMO-1230, Postgres EvalPlanQual)이라는 규칙을 계층이 지우면 안 됩니다.
- **예외 두 갈래를 합치지 않는다.** `getTarget*`(요청이 지목한 대상 부재)와 `getCaller*`(요청자 본인 부재)는 앱이 code 문자열로 다르게 분기하므로(GROMO-1247) 시그니처로 갈라 뒀습니다. 이 구분이 4단계에서 다시 문제가 됩니다.

두 번째 도메인 `group` 에서 규약이 실제로 검증됐습니다. 그룹 조회 23건은 전부 `NOT_FOUND` 로 균일했지만 **멤버십 조회 24건은 같은 쿼리인데 부재의 뜻이 다섯 갈래**였습니다 — `MEMBER_ONLY`(17) · `NOT_OWNER`(3) · `NOT_FOUND`(2) · `ALREADY_MEMBER`(1, 존재가 거절 사유) · 예외 없이 boolean(1). 그래서 계층은 조회만 접고 **판정은 service 에 남겼습니다.** 부재의 뜻은 영속성 관심사가 아니라 그 화면의 정책입니다.

지갑·설정 36건, 내기 회차 20건, 나머지 도메인 13건을 차례로 옮겨 **조회 계층 밖의 id 조회는 0건**이 됐습니다. 여기서도 측정이 설계를 정했습니다. `findByIdForUpdate` 7건 중 5건이 `ifPresent`/`filter` 패턴 — 락은 잡되 **부재가 정상**인 자리였습니다. 탈퇴 환불·챌린지 삭제 무효화는 여러 회차를 id 오름차순으로 잠그며 열린 것만 모으는 루프라, 여기서 던지면 이미 정산된 회차 하나 때문에 나머지 환불이 통째로 죽어 돈이 묶입니다. 그래서 같은 배타 락에 `get`(던짐)과 `find`(Optional)를 둘 다 뒀습니다.

### 리포지토리 `@Transactional` 30건 중 10건 — 습관이었나 규칙이었나

Spring Data 리포지토리의 `@Modifying` 메서드 30개 중 10개에만 `@Transactional` 이 붙어 있었습니다. 다음 사람은 붙은 것과 안 붙은 것의 차이를 추론하다 없는 규칙을 만들어냅니다. 그래서 **10건을 전부 떼고 전체 스위트를 돌렸습니다.** 16건이 깨졌고 원인은 둘이었습니다.

- 9건은 **테스트가 지탱**하고 있었습니다. 무트랜잭션 `IntegrationTestBase` 를 상속한 통합 테스트 2개가 리포지토리를 직접 두드리고 있었고, 프로덕션 호출부는 전부 이미 `@Transactional` 이라 런타임 기여가 없었습니다. 떼고, 두 테스트가 픽스처 준비·정리만 `transactionTemplate` 으로 감쌌습니다.
- 1건은 **진짜**였습니다. `GroupBetScheduler` 는 건별 격리를 위해 의도적으로 무트랜잭션인 `@Scheduled` 진입점인데 `recordFailure` 를 직접 부릅니다. 떼면 정산 실패를 기록할 때마다 `InvalidDataAccessApiUsageException` 이 catch 블록 안에서 터져 그 틱의 남은 회차가 유실되고 백오프가 전진하지 못해 5분마다 무한 재시도합니다. **전체 테스트 1,904건이 초록인 상태에서도 그렇습니다** — 그 경로를 타는 테스트가 없었습니다.

남긴 1건은 규약 §5 "인정된 예외"에 근거와 함께 적었고, 그 경로를 잡는 테스트를 새로 세웠습니다.

## 3. 도메인 방향 — 순환을 세지 말고 끊어야 할 간선을 세라

기존 규약은 "도메인 간 접근은 service 를 통한다"고 **누구를 통할지만** 말하고 **어느 쪽으로 갈지**를 말하지 않았습니다. A→B, B→A 가 둘 다 규약을 지키면서 순환이었습니다. 실측 순환 238개는 전부 **역행 간선 15쌍(import 49건)** 에서 파생된 것이라, 순환을 하나씩 세는 대신 도메인에 높이를 주고 그 높이를 어기는 간선만 세기로 했습니다.

### 왜 이벤트가 아니라 오케스트레이터인가

회원 탈퇴는 계정·그룹·집중·통계·스크린타임·친구를 정리하는 일인데, 전부가 `UserService.withdraw` 90줄 안에 있어 가장 아래 도메인이 자기 위의 다섯을 참조했습니다. 이벤트로 뒤집는 게 정석처럼 보이지만 이 절차엔 순서 제약이 셋 있습니다 — 그룹 정리(내기 환불) 뒤에 지갑 삭제, 판정 근거 박제 뒤에 집중·통계 익명화, PII 파기·소셜 삭제는 맨 끝(소셜 벌크 DELETE 가 영속성 컨텍스트를 비워 그 뒤의 엔티티 변경은 예외도 실패도 없이 커밋만 안 됩니다). 이벤트로 가면 이 순서가 **리스너 등록 순서에 숨습니다.**

그래서 `withdrawal/AccountWithdrawalService` 가 여섯 호출을 차례로 부르게 하고, 정리하는 **방법**은 각 도메인이 갖게 했습니다. 순서에는 증인을 세웠습니다 — `InOrder` 테스트를 두고 실제로 지갑 삭제를 그룹 정리 앞으로 옮겨 그 2건만 실패하는 것을 확인했습니다. 반대로 `group → notification` 은 순서 제약이 없어 이벤트로 끊었습니다. 단, 발행 트랜잭션 안에서 처리돼야 하는 결과 확인 억제는 `@TransactionalEventListener(AFTER_COMMIT)` 가 아니라 **동기 `@EventListener`** 로 두었습니다. 같은 "이벤트"라도 언제 도는지가 계약입니다.

### 측정 스크립트가 두 번 거짓말했다 — 그래서 ArchUnit 규칙 ③

역행 간선을 세던 제 스크립트가 새로 만든 `profile`·`withdrawal` 을 **조용히 건너뛰어** 「위반 0」을 두 번 잘못 보고했습니다. 레이어 표에 없는 도메인을 「검사 대상 아님」으로 넘긴 것입니다. 미등록은 침묵이 아니라 실패여야 합니다.

`DomainLayerRulesTest`(#724) 의 규칙 셋 중 ③ **"모든 도메인 패키지가 레이어 표에 등록돼 있다"** 가 그 자리를 메웁니다. 없으면 ①(역행 금지)·②(순환 금지)가 있으나 마나입니다. 규칙이 실제로 잡는지도 되돌려 확인했습니다 — `user`(L0) 에 `group`(L5) 참조를 주입하니 ①②가 함께 실패했고, 표에 없는 패키지를 만드니 ③이 이름을 지목하며 실패했습니다. 작성 중 결함도 둘 있었는데 이 검증으로 드러났습니다: 자기 도메인 내부 참조를 위반으로 세어 6,462건이 나왔고, `common` 을 슬라이스에 넣으니 전 도메인 예외를 아는 `GlobalExceptionHandler` 때문에 모든 도메인이 서로 순환하는 것처럼 잡혔습니다.

## 4. 에러 계약 — 봉투는 하나였는데 들어가는 길이 열한 개였다

에러 봉투 `{code, message}` 는 이미 하나였습니다. 문제는 **봉투에 들어가는 길**이었습니다. 도메인 `ErrorCode` enum 11개가 전부 `(HttpStatus, String)` 같은 모양인데 공통 타입이 없어서 `GlobalExceptionHandler` 가 글자 그대로 같은 핸들러를 11개 들고 있었고, 새 도메인이 한 줄을 빠뜨리면 그 예외는 스프링 기본 `/error` 바디(`code` 없음)로 새어 나갔습니다. 그 11개를 직접 검증하는 테스트는 0건이었습니다.

`common/exception/ErrorCode`(인터페이스)·`DomainException`(추상 베이스)를 두고 핸들러를 `handleDomain` 하나로 접었습니다(#725). 핸들러는 판단하지 않습니다 — `code.getStatus()` 를 상태로, `code.name()` 을 `code` 로 옮길 뿐입니다. **응답을 바꾸려면 핸들러가 아니라 그 도메인의 enum 을 고칩니다.** 계약 테스트 `ErrorContractTest` 는 목록을 손으로 적지 않고 `ErrorCode` 를 구현한 enum 을 클래스패스에서 찾아 상수마다 `(status, code, message)` 를 단언합니다. 손으로 적으면 새 도메인이 빠져도 초록이라, 찾은 enum 이 팩토리 표에 없으면 그것 자체가 실패입니다. 처음 100건, 지금 120건입니다.

그 다음 일회용 `@WebMvcTest` 프로브로 **봉투 밖으로 새는 경로**를 실측했습니다(#726). 일곱이었습니다 — `@Valid` 실패(컨트롤러 26곳) · 깨진 JSON · 파라미터 누락 · 405 · 404 · item 의 `EntityNotFound`(**500**) · 그 외 전부. 앱은 `body.code` 만 읽으니 전부 「알 수 없는 오류」였습니다. `CommonErrorCode` 15개를 두고 catch-all 까지 봉투에 넣었습니다. 핸들러가 닿지 않는 필터 응답(`JwtFilter` 401 · `RequestSizeLimitFilter` 413)은 `@RestControllerAdvice` 가 구조적으로 볼 수 없는 자리라 같은 봉투를 직접 씁니다. 종전에 낙관락 코드를 `GroupErrorCode` 에서 **빌려** 쓰던 `common → group` 참조도 이때 없어졌습니다 — 3단계 규칙이 검사하지 않는 방향이었습니다.

### 앱 계약이 바뀌는 것만 따로 — 1725

1657 의 원칙은 "앱 호환이 깨지는 항목은 그 티켓에서 바꾸지 않는다"였습니다. 실측에서 나온 계약 변경 항목을 1725 로 모았습니다.

**`NOT_FOUND` 가 두 도메인에 있었습니다.** `GroupErrorCode.NOT_FOUND`(그룹 없음)와 `UserErrorCode.NOT_FOUND`(지목한 유저 없음)가 같은 문자열로 나가서, 앱 그룹 화면 17곳이 유저 부재 404 에도 「그룹이 사라졌다」를 띄웠습니다. 서버 enum 이름이 곧 앱 분기 문자열이라 한쪽만 못 바꿉니다. 앱이 이미 `USER_NOT_FOUND` 를 신구 병기로 받고 있던 선례(GROMO-1247)를 따라 **A안** — 서버는 `GROUP_NOT_FOUND`·`CHALLENGE_NOT_FOUND`·`TARGET_USER_NOT_FOUND` 를 새로 내고 `NOT_FOUND` 는 그룹 안의 것(공지·멤버십)에만 남기며, 앱은 `case` 를 병기한다(1726). 배포 순서는 **앱 → 서버**입니다. 서버가 먼저 나가면 구앱은 새 코드에 분기가 없어 안내 없이 실패합니다. 그래서 #729 는 리뷰가 끝난 뒤에도 `main`(dev) 까지만 들어갔고 release(prod) 컷은 1726 배포 뒤입니다.

**`IllegalArgumentException` 그물이 409 였습니다.** 잘못된 입력에 「충돌」이라 답해 앱이 재시도로 오해할 수 있었습니다. 400 으로 바꾸기 전에 앱의 `status === 409` 분기를 실측했더니 8곳/7파일 전부 도메인 코드(닉네임 중복·이미 친구·마지막 소셜 연동)가 원천이라 영향이 없었고, IAE 가 앱까지 닿던 3경로(집중 세션 시각·친구 검색 수단·소셜 제공자)는 도메인 코드로 치환했습니다(#730).

### 리뷰가 잡은 제 실수 — 전부 「이 userId 가 누구 것인가」

#729 는 codex 4라운드·claude 3라운드를 거쳤고 지적 7건 중 6건이 한 종류였습니다. **`userId` 파라미터를 요청자라고 가정한 것.**

- `InventoryService.grantItem` 의 `userId` 는 `@LoginUser` 가 아니라 요청 본문의 지급 대상(관리자 용도)이었습니다. 요청자 축으로 옮기면 없는 대상에 지급하려던 관리자에게 「다시 로그인하라」고 답합니다.
- 지갑 접근자는 요청자(구매·집중 보상·잔액)와 참가자(회차 환불·정산 지급·리그 보너스) 두 경로를 다 지납니다. 접근자 하나에 축 하나로는 안 되고, 결국 원장 API 에 `WalletOwner {CALLER, TARGET}` 을 호출자가 명시하게 했습니다.
- 공개 프로필·통계는 `friends` 를 생략하면 본인입니다. `callerId.equals(targetId)` 면 `getCaller`, 아니면 `getTarget` — `getTargetOf(callerId, targetId)` 로 갈랐습니다.

세 번 다 제 1차 실측이 틀린 원인은 grep 이었습니다. `getX(userId)` 처럼 **인자 이름으로 호출처를 세면** `getX(user.getId())` 를 놓치고, `throw new X(` 만 세면 **람다형** `orElseThrow(() -> new X(` 을 놓치고, `grep -v` 배제 필터는 한 줄에 여러 항목이 있으면 진짜를 지웁니다. 축 판단은 컨트롤러 시그니처(`@LoginUser` 인지 경로·본문 id 인지)까지 추적해야 합니다. 같은 파일의 주석이 세 번 뒤집힌 것도 같은 원인이라, 동작을 바꾼 커밋 전에 옛 코드명을 grep 하는 것을 체크리스트에 넣었습니다.

## 곁가지 둘 — 매일 1시간 빨갛던 CI, 앱이 쓸 언어 컬럼

**GROMO-1723.** `FocusServiceTest` 가 매일 KST 00~01시에 2~3건 실패했습니다. 테스트가 `Instant.now()` 기준 「지금 − 1시간」 세션을 만들어 자정을 걸치면 날짜 분할(GROMO-1252)이 정상 동작하면서 단언이 깨진 것으로, 제품 코드는 정상이었습니다. 우회 대신 `FocusService` 가 `java.time.Clock` 을 주입받게 해 테스트가 시계를 고정합니다(#728). 증명은 벽시계를 기다리지 않고 시계를 바꿔 했습니다 — `NOW` 를 12:00 KST 로 두면 145건 초록, 00:30 KST 로 바꾸면 티켓의 그 3건만 정확히 실패. 리뷰가 하나 더 잡았습니다: 고정 시계에서 `isAfterOrEqualTo(before)` 하한 단언은 서비스가 다시 벽시계를 읽어도 영원히 통과하므로 `isEqualTo(NOW)` 로 바꿨고, 시계 한 곳을 되돌리면 5건이 실패하는 것을 확인했습니다.

**GROMO-1659 P0.** 알림 서버가 푸시를 사용자 언어로 렌더링하려면 서버가 언어를 알아야 합니다. `users.language`(V50) 와 `PATCH /users/me {language}` 를 추가했습니다(#727). 설계 문서는 `users.locale` 이라 불렀지만 앱 계약이 이미 `language` 로 적혀 있어 그쪽을 따랐고, CI 는 Flyway 를 돌리지 않으므로 V1~V50 을 로컬 Postgres 에 실제 적용한 뒤 `ddl-auto=validate` 로 부팅해 확인했습니다. 리뷰가 잡은 누락 하나 — 프로필 필드를 추가하면 탈퇴 시 파기(`erasePersonalData`)도 같은 PR 에서 따라가야 합니다.

## 남은 규칙 여섯 줄

1. **패키지를 옮기면 컴파일러가 못 잡는 자리를 grep 한다.** JPQL 문자열·`@Value`·`basePackages`·logback·yml.
2. **배치는 이름이 아니라 의존성으로 가른다.** 주입이 있으면 `service/`, 없으면 `support/`.
3. **계층은 조회만 접고 판정은 남긴다.** 부재의 뜻은 화면의 정책이다. 락 등급과 예외 축은 시그니처에 남긴다.
4. **순환은 세지 말고 높이를 준다.** 역행 간선만 세면 장부가 짧아지고, 미등록 도메인은 침묵이 아니라 실패다.
5. **순서 제약이 있으면 오케스트레이터, 없으면 이벤트.** 이벤트로 가면 순서가 리스너 등록 순서에 숨는다.
6. **"전부·없음" 을 쓰기 전에 넓은 패턴으로 다시 센다.** `getX(`·`new X(`, 배제 필터 없이, 컨트롤러까지.

아직 남은 것도 적어 둡니다. 895(item·screentime 전용 예외)는 스프린트 밖이고, 1658(Kafka)·1659 P1~·1660·1661 은 목표 아키텍처 문서가 확정되면 이 위에서 시작합니다. 이 에픽이 한 일은 그 문서가 그을 경계선이 **컴파일 단위로 갈라지게** 만든 것입니다.
