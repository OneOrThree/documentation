부하테스트를 설계하면서 가장 많이 고쳐 쓴 것은 시나리오가 아니라 **측정 도구 자체에 대한 불신**이었습니다. 이 노트는 사건 기록이 아니라 결정 기록입니다. 무엇을 왜 그렇게 정했는지, 그리고 그 근거가 어디서 무너졌는지를 남깁니다.

결론부터 말하면 이렇습니다. 멘토 세션 직후 세운 설계(v1)의 표적 가설은 3개였고, 코드와 스키마를 직접 읽어보니 **3개 전부 틀렸습니다.** 부하를 걸기도 전에 표적이 다 바뀐 경험이, 이후 모든 설계 결정의 기준이 되었습니다.

## 표적 가설 3개가 전부 틀렸다

v1은 2026-06-29 멘토 세션 직후 작성한 가설 설계였습니다. "느릴 만한 곳"을 도메인 지식으로 짚었습니다. 2026-07-02에 `back`의 스키마와 리포지토리를 전수 조사하면서 세 가설을 하나씩 대조했습니다.

| 축 | v1 가설 | 실측 결과 | 교정된 표적 |
| --- | --- | --- | --- |
| Phase 1 | `/stats/heatmap`이 `daily_focus_stats` 인덱스 부재로 느릴 것 | `(user_id, date)` UNIQUE 인덱스가 **이미 있었음** | `GET /api/v1/focus-session` — `focus_sessions` |
| Phase 2 | 리그 랭킹에 N+1이 있을 것 | 이미 `JOIN FETCH` 적용됨 | `Friendship`·`PinnedFriend`·`GroupChallengeMember`의 LAZY 경로 |
| Phase 3 | friends·groups 검색 둘 다 `LIKE '%…%'` 풀스캔일 것 | `users.nickname`은 이미 pg_trgm GIN(GROMO-460) | `GroupRepository.findByNameContainingIgnoreCase`만 남음 |

진짜 표적은 조사 중에 우연히 드러났습니다. `focus_sessions`는 **PK 외 인덱스가 0개**였고, 동시에 시드 볼륨표에서 최대 규모(3천만 건)를 차지하는 테이블이었고, 하필 방금 구현한 커서 페이지네이션 API(GROMO-517)가 그 위에서 돌고 있었습니다. PostgreSQL은 FK에 자동 인덱스를 만들어 주지 않으므로, FK 컬럼 전반이 잠재 표적이라는 사실도 이때 정리했습니다.

교훈은 한 줄로 남겼습니다. **부하를 걸기 전에 스키마와 리포지토리부터 읽어라.** 그리고 v1에서 이미 인덱스가 있던 `/stats/heatmap`은 버리지 않고 **대조군**으로 승격시켰습니다. "인덱스 있는 쪽은 안 느리다"를 같은 하네스로 실측해 두면, Phase 1의 개선 수치가 환경 탓이 아니라는 증거가 됩니다.

## closed model은 서버가 느려지면 부하도 줄인다

v1은 부하량을 VU(가상 사용자) 수로 지정했습니다. 암묵적으로 closed model입니다. closed model에서는 VU가 응답을 받은 뒤에야 다음 요청을 보내므로, **서버가 느려지면 유입 rps도 같이 줄어듭니다.** 서버가 힘들어할 때 우리가 부하를 덜어 주는 구조입니다. 그래서 꼬리 지연이 실제보다 낮게 나옵니다. coordinated omission입니다.

v2에서 기본 부하 모델을 open model(`constant-arrival-rate` / `ramping-arrival-rate`)로 바꿨습니다. 초당 N개 요청을 서버 상태와 무관하게 밀어넣고, k6가 그 rate를 못 따라가면 `dropped_iterations`가 올라갑니다. 이 값이 곧 **포화 판정 지표**가 됩니다.

executor를 정리하다 보니 "총 rps 입력"이 프로파일마다 의미가 다르다는 것도 알게 됐습니다.

| 프로파일 | executor | 총 rps 입력 | 부하를 정하는 주체 |
| --- | --- | --- | --- |
| smoke / load | `constant-arrival-rate` | 사용 | 내가 목표 rps를 지정 |
| stress | `ramping-arrival-rate` | 미사용 | 램프가 스스로 올림 |
| spike | `ramping-arrival-rate` | 미사용 | 급증 스테이지 |
| soak | `constant-vus` | 미사용 | VU 수 기반, 장시간 |

한계 탐색(stress)에 "총 rps"를 넣는 건 개념적으로 틀립니다. **램프 자체가 탐색**이기 때문입니다. 대시보드에서도 프로파일에 따라 rps 입력을 숨기는 쪽이 맞다고 판단했습니다. 반대로 soak만은 closed(VU)를 그대로 씁니다. 누수·누적 포화를 오래 보는 것이 목적이라 꼬리 지연 정확도가 1순위가 아니기 때문입니다.

합격선도 이 모델에 맞춰 코드에 박았습니다. `p95<200ms`, `p99<500ms`, 에러율 `<1%`, 그리고 `dropped_iterations=0`. 마지막 항목이 open model 때문에 새로 생긴 조건입니다.

```javascript
thresholds: {
  'http_req_duration{phase:main}': ['p(95)<200', 'p(99)<500'],
  'http_req_failed{phase:main}':   ['rate<0.01'],
  'dropped_iterations':            ['count<1'],   // rate를 못 따라감 = 포화
},
```

## 측정 도구를 못 믿게 만드는 조건들을 먼저 봉쇄한다

open model로 바꾼 것과 같은 이유로, "이 숫자를 믿을 수 있는가"를 흔드는 요인을 하나씩 결정으로 못박았습니다.

| 흔드는 요인 | 결정 |
| --- | --- |
| 부하기와 SUT가 자원을 다투면 숫자가 오염 | 별도 VM 분리 + **부하기 CPU가 80%를 넘은 run은 무효** |
| 같은 ID만 반복 조회하면 버퍼캐시 히트로 과대평가 | 랜덤 파라미터 + 활동량 순위 기반 Zipf 유저 풀 |
| 데이터가 RAM에 다 들어가면 I/O 병목이 안 보임 | 데이터(~15GB) `>` 인스턴스 RAM(8GB) 조건을 설계에 명시 |
| JVM JIT·커넥션풀·버퍼캐시가 덜 데워진 구간 | 앞 2분 워밍업을 별도 시나리오로 분리, 태그로 집계 제외 |
| 부하 중 쿼리 로깅이 오버헤드·로그 폭발 | P6Spy off → pg_stat_statements 델타 + auto_explain + exporter |
| e2 계열은 CPU 세대가 랜덤 배정 | SUT를 n2 계열 + min CPU platform 고정으로 확정 |

로그인 자체는 시험 대상이 아니므로 JWT를 사전에 대량 발급해 k6 `SharedArray`로 넘겼습니다. 단, 인증 필터는 그대로 태웁니다. 토큰 파싱 비용은 prod에서도 매 요청 발생하니 측정에 포함해야 맞습니다.

`pg_stat_statements`는 쿼리가 어느 API에서 왔는지 모릅니다. 이걸 도구를 추가해 풀지 않고 **테스트 설계로** 풀었습니다. 한 API만 때리는 단건 매트릭스 run이라면, reset 후의 델타가 곧 그 API의 쿼리 프로필입니다. 요청당 쿼리 몇 개, 각각 평균 몇 ms가 공짜로 표로 나옵니다. 시나리오 믹스 run에서는 `hibernate.use_sql_comments`로 JPQL 출처 주석을 붙여 식별합니다.

## golden DB — 비싼 건 한 번, 싼 건 매번

쓰기 시나리오를 돌리면 DB가 오염됩니다. 리셋 없이는 before/after 비교가 애초에 성립하지 않습니다. 그런데 3천만 건 시드는 수십 분이 걸립니다. 매 run 재시드는 불가능합니다.

PostgreSQL의 `TEMPLATE` 복제로 갈랐습니다. 시드 완료 상태를 `golden`으로 **동결**해 두고, run마다 그 복제본을 만들어 씁니다.

```sql
-- 1회, 비쌈: 시드 완료 후 golden을 동결 — 아무도 직접 못 붙는다
ALTER DATABASE golden IS_TEMPLATE true;
ALTER DATABASE golden ALLOW_CONNECTIONS false;

-- 매 run, 쌈: 같은 인스턴스 안 파일 수준 복사라 분 단위
DROP DATABASE IF EXISTS loadtest;
CREATE DATABASE loadtest TEMPLATE golden;
```

| 축 | 매번 재시드 | golden 복제 |
| --- | --- | --- |
| 소요 | 30분 이상 | 수 분 |
| 초기 상태 | 매번 미묘하게 다름 | 항상 동일 |
| 직전 run의 쓰기 | 남음 | 복제본만 더럽히고 버림 |

숨은 이득이 하나 더 있었습니다. 시드 직후 `VACUUM ANALYZE`까지 golden에 담으면 **플래너 통계도 함께 동결**됩니다. 통계 상태가 run마다 다르면 플래너가 다른 플랜을 잡아 측정 자체가 오염되는데, 그 변수가 통째로 사라집니다. golden을 다시 만드는 건 스키마 마이그레이션·시드 로직 변경·인스턴스 삭제 때뿐입니다. 실제로 동결된 golden은 22GB였습니다.

## 7천만 건을 어떻게 '재현 가능하게' 만드나

시드는 커야 하고(빈 DB에서는 병목이 안 보임), 동시에 **같은 데이터가 다시 만들어져야** 합니다. 그래서 적재 경로와 난수를 따로 결정했습니다.

적재는 애플리케이션을 쓰지 않습니다. 차원 테이블(users·groups·items 등)은 현실적인 한글 문자열이 필요해 스크립트로 CSV를 만들어 `\copy`, 팩트 테이블(`focus_sessions`·`daily_focus_stats` 등)은 분포만 맞으면 되므로 DB 안에서 `INSERT … SELECT generate_series()`로 직접 생성합니다. 최종 약 7,000만 건입니다.

재현성은 난수를 전부 결정론으로 바꿔 확보했습니다.

- 차원 UUID: `md5('user-' || n)::uuid` — 같은 `n`이면 항상 같은 UUID. FK를 조인 없이 공식으로 유도할 수 있다는 부수 효과가 큽니다.
- 문자열·비율 난수: **mulberry32 고정 시드** — 한글 닉네임·그룹명·아이템 슬롯까지 같은 순서로 재생성됩니다.
- 팩트 PK: `seed_uuid_v7(started_at)` — 상위 6바이트를 epoch ms로 채워 시간순 정렬을 보장합니다.

마지막 항목은 그냥 취향 문제가 아니었습니다. `focus_sessions`의 커서 쿼리는 `ORDER BY id DESC` + `id` 경계 비교에 의존합니다. 시드가 랜덤 v4를 넣으면 id 정렬이 시간과 무관해져서 **커서 API의 부하 특성 자체가 왜곡됩니다.** 그래서 시드 검증 단계에 "커서 정렬 위반 0건" 항목을 넣었습니다.

적재 가속은 제약을 떼고 넣는 고전적인 방법을 씁니다. 다만 제약명을 하드코딩하지 않고 `pg_get_constraintdef`로 동적 캡처해 저장 → 드롭 → 적재 → PK·UNIQUE·FK 순으로 복원합니다. 스키마 마이그레이션이 제약명을 바꿔도 시드 스크립트를 수정할 필요가 없습니다. 실제로 PRD 확정 직후 마이그레이션 여러 개가 머지되면서 이 선택이 값을 했습니다.

## 매트릭스를 손으로 쓰지 않는다 — openapi에서 자동생성

초기 k6 매트릭스는 엔드포인트당 파일 하나를 손으로 썼습니다. 표적 3종을 다루는 동안은 괜찮았지만, 이 방식은 엔드포인트가 늘어날 때마다 사람이 따라가야 합니다. 게다가 표적 가설이 틀린 경험을 한 뒤라, "느릴 만한 몇 개만 골라 쓴다"는 전제 자체를 믿지 않게 됐습니다.

`openapi.json`을 입력으로 엔드포인트별 입력 전략(path·query·body, enum·date·시드 풀·body 스키마)을 만드는 생성기를 붙였습니다. **전체 93개 중 86개가 바로 실행 가능**했고, 남은 7개는 시드에 존재하지 않는 path ID(태그·챌린지·공지 등)를 요구하는 경우였습니다. "리스트를 먼저 조회해 id를 얻는" 후속 과제로 남겼습니다.

실행 쪽은 제네릭 러너 하나로 통일했습니다. 선택한 엔드포인트를 직렬로 N번 디스패치하는 대신, **하나의 arrival-rate 안에서 랜덤 픽**해서 총 rate를 선택분에 병렬 분산합니다. 스팟 부하 VM을 여러 대 띄우는 이유가 병렬이니, 트리거도 한 번이어야 맞습니다. `endpoint` 태그로 per-endpoint 지표는 그대로 유지됩니다. 유저 시나리오도 코드가 아니라 JSON 정의로 옮겨, 새 시나리오 추가가 파일 하나 추가로 끝나게 했습니다.

## "스팟은 경매다"를 레포 전수 검색으로 반증

부하 VM을 스팟으로 쓰다 존 재고 소진에 막혔을 때, 팀 안에 이런 전언이 있었습니다. "스팟은 경매라 max price를 올리면 용량을 뺏어올 수 있고, 사내 terraform 레포에 그 세팅이 있다."

받아들이기 전에 확인했습니다. 해당 레포 전 파일을 가격·입찰 키워드로 검색한 결과 **세팅 0건**이었습니다. `bid` 매치는 전부 `AssumeRoleWithWebIdentity`의 부분 문자열(`WebId`)이었습니다. 개념도 정리했습니다.

- GCP Spot에는 **가격 파라미터가 아예 없습니다.** terraform google provider의 `scheduling` 블록에 필드가 없습니다. 무입찰이고, 선점·재고는 순수 용량 기준입니다.
- "경매·입찰"은 2017년 이전 AWS 모델이고, 현재 AWS의 max price는 지불 상한일 뿐입니다. 가격 기반 축출은 Azure Spot 이야기입니다.
- 결정적으로, 그때 막혀 있던 SUT는 **스팟도 아닌 온디맨드**였습니다. 어떤 가격으로도 새치기할 수 없습니다.
- GCP에서 돈으로 용량을 확보하는 유일한 수단은 예약(reservation)인데, 확보 순간부터 24시간 풀 과금이라 "평시 전부 중지" 모델과 충돌하고, 품절 존에서는 예약 생성도 같은 이유로 실패합니다.

여기서 얻은 규칙은 부하테스트보다 넓게 쓰입니다. **클라우드 통념은 프로바이더를 명시해야 사실이 됩니다.** 그리고 반박하든 수용하든, 그 전에 원문(레포 검색 + provider 스키마)으로 확인합니다. 표적 가설 3개가 틀렸던 것과 같은 종류의 실수를, 이번엔 남의 말에서 걸러낸 셈입니다.

무료체험 8 vCPU 상한도 같은 방식으로 처리했습니다. 설계상 부하기는 c2-standard-8이었지만, SUT 2 + 관측 2 + 부하 4로 예산을 맞춰 **c2-standard-4로 하향**했습니다. 대신 "부하기 CPU가 80%를 넘으면 그 run은 무효" 가드를 유지해, 부하기가 먼저 포화된 측정을 숫자로 쓰지 않게 막았습니다. 고rps 한계 탐색은 다중 부하기가 준비된 뒤로 미뤘습니다.
