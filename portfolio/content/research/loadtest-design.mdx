2026-07-02, `back`의 스키마와 리포지토리를 전수 조사하던 날 **v1 표적 가설 3개가 한꺼번에 무너졌습니다.** 진짜 표적은 PK 외 인덱스가 0개인 `focus_sessions`(3천만 건)였고, 며칠 전 구현해 둔 커서 페이지네이션 API(GROMO-517)가 하필 그 테이블 위에서 돌고 있었습니다. 부하를 한 번도 걸기 전에 표적이 전부 바뀌었고, 이후 설계 결정은 그 위에서 다시 짰습니다.

## 표적 가설 3개가 전부 틀렸다

v1은 2026-06-29 멘토 세션 직후 작성한 가설 설계였습니다. "느릴 만한 곳"을 도메인 지식으로만 짚어 둔 것이라, 전수 조사에서 세 가설을 코드와 하나씩 대조했습니다.

| 축 | v1 가설 | 실측 결과 | 교정된 표적 |
| --- | --- | --- | --- |
| Phase 1 | `/stats/heatmap`이 `daily_focus_stats` 인덱스 부재로 느릴 것 | `(user_id, date)` UNIQUE 인덱스가 **이미 있었음** | `GET /api/v1/focus-session` — `focus_sessions` |
| Phase 2 | 리그 랭킹에 N+1이 있을 것 | 이미 `JOIN FETCH` 적용됨 | `Friendship`·`PinnedFriend`·`GroupChallengeMember`의 LAZY 경로 |
| Phase 3 | friends·groups 검색 둘 다 `LIKE '%…%'` 풀스캔일 것 | `users.nickname`은 이미 pg_trgm GIN(GROMO-460) | `GroupRepository.findByNameContainingIgnoreCase`만 남음 |

진짜 표적은 조사 중에 우연히 걸렸습니다. `focus_sessions`는 **PK 외 인덱스가 0개**였고, 동시에 시드 볼륨표에서 최대 규모(3천만 건)를 차지하는 테이블이었습니다. FK 컬럼 전반이 잠재 표적이라는 점도 이때 정리했습니다(자동 인덱스가 없어 실제로 벌어진 일은 [에러율 96% 노트](/research/loadtest-error96)에 있습니다).

교훈은 한 줄로 남겼습니다. **부하를 걸기 전에 스키마와 리포지토리부터 읽어라.** 그리고 v1에서 이미 인덱스가 있던 `/stats/heatmap`은 버리지 않고 **대조군**으로 승격시켰습니다. "인덱스 있는 쪽은 안 느리다"를 같은 하네스로 실측해 두면, Phase 1의 개선 수치가 환경 탓이 아니라는 증거가 됩니다.

## closed model은 서버가 느려지면 부하도 줄인다

v1은 부하량을 VU(가상 사용자) 수로 지정했습니다. 암묵적으로 closed model입니다. closed model에서는 VU가 응답을 받은 뒤에야 다음 요청을 보내니, 서버가 포화될수록 부하기가 요청을 덜 보냅니다. 유입 rps가 서버 상태를 따라 내려가고, 꼬리 지연은 실제보다 낮게 나옵니다(coordinated omission).

v2에서 기본 부하 모델을 open model(`constant-arrival-rate` / `ramping-arrival-rate`)로 바꿨습니다. 초당 N개 요청을 서버 상태와 무관하게 밀어넣고, k6가 그 rate를 못 따라가면 `dropped_iterations`가 올라갑니다. 이 값을 **포화 판정 지표**로 씁니다.

executor를 정리하다 보니 "총 rps 입력"이 프로파일마다 의미가 다르다는 것도 알게 됐습니다.

| 프로파일 | executor | 총 rps 입력 |
| --- | --- | --- |
| smoke / load | `constant-arrival-rate` | 사용 |
| stress | `ramping-arrival-rate` | 미사용 |
| spike | `ramping-arrival-rate` | 미사용 |
| soak | `constant-vus` | 미사용 |

한계 탐색(stress)에 "총 rps"를 넣는 건 개념적으로 틀립니다. 램프가 하는 일을 사람이 미리 정해 버리는 셈이니까요. 대시보드에서도 프로파일에 따라 rps 입력을 숨기는 쪽이 맞다고 판단했습니다. 반대로 soak만은 closed(VU)를 그대로 씁니다. 누수·누적 포화를 오래 보는 것이 목적이라 꼬리 지연 정확도가 1순위가 아니기 때문입니다.

합격선도 이 모델에 맞춰 코드에 박았습니다. `p95<200ms`, `p99<500ms`, 에러율 `<1%`, 그리고 open model로 바꾸면서 새로 생긴 `dropped_iterations=0`.

```javascript
thresholds: {
  'http_req_duration{phase:main}': ['p(95)<200', 'p(99)<500'],
  'http_req_failed{phase:main}':   ['rate<0.01'],
  'dropped_iterations':            ['count<1'],   // rate를 못 따라감 = 포화
},
```

## 측정 도구를 못 믿게 만드는 조건들을 먼저 봉쇄한다

open model로 바꾼 것과 같은 이유로, "이 숫자를 믿을 수 있는가"를 흔드는 요인을 하나씩 결정으로 못박았습니다.

| 흔드는 요인 | 결정 |
| --- | --- |
| 부하기와 SUT가 자원을 다투면 숫자가 오염 | 별도 VM 분리 + **부하기 CPU가 80%를 넘은 run은 무효** |
| 같은 ID만 반복 조회하면 버퍼캐시 히트로 과대평가 | 랜덤 파라미터 + 활동량 순위 기반 Zipf 유저 풀 |
| 데이터가 RAM에 다 들어가면 I/O 병목이 안 보임 | 설계 시 추정 데이터(~15GB) `>` 인스턴스 RAM(8GB) 조건을 명시 |
| JVM JIT·커넥션풀·버퍼캐시가 덜 데워진 구간 | 앞 2분 워밍업을 별도 시나리오로 분리, 태그로 집계 제외 |
| 부하 중 쿼리 로깅이 오버헤드·로그 폭발 | P6Spy off → pg_stat_statements 델타 + auto_explain + exporter |
| e2 계열은 CPU 세대가 랜덤 배정 | SUT를 n2 계열 + min CPU platform 고정으로 확정 |

로그인 자체는 시험 대상이 아니므로 JWT를 사전에 대량 발급해 k6 `SharedArray`로 넘겼습니다. 단, 인증 필터는 그대로 태웁니다. 토큰 파싱 비용은 prod에서도 매 요청 발생하니 측정에 포함해야 맞습니다.

`pg_stat_statements`만으로는 쿼리가 어느 API에서 왔는지 알 수 없습니다. 출처 식별은 테스트 설계로 풀었습니다. 한 API만 때리는 단건 매트릭스 run이라면, reset 후의 델타가 곧 그 API의 쿼리 프로필입니다. 요청당 쿼리 몇 개, 각각 평균 몇 ms가 공짜로 표로 나옵니다. 시나리오 믹스 run에서는 `hibernate.use_sql_comments`로 JPQL 출처 주석을 붙여 식별합니다.

## golden DB — 비싼 건 한 번, 싼 건 매번

쓰기 시나리오를 돌리면 DB가 오염되고, 리셋 없이는 before/after 비교가 애초에 성립하지 않습니다. 그런데 7천만 건 규모의 시드(설계 목표, 그중 `focus_sessions`가 3천만)는 수십 분이 걸려서 매 run 재시드는 불가능합니다.

PostgreSQL의 `TEMPLATE` 복제로 갈랐습니다. 시드 완료 상태를 `golden`으로 **동결**해 두고, run마다 그 복제본을 만들어 씁니다.

```sql
-- 1회, 비쌈: 시드 완료 후 golden을 동결 — 아무도 직접 못 붙는다
ALTER DATABASE golden IS_TEMPLATE true;
ALTER DATABASE golden ALLOW_CONNECTIONS false;

-- 매 run, 쌈: 같은 인스턴스 안 파일 수준 복사라 분 단위
DROP DATABASE IF EXISTS loadtest;
CREATE DATABASE loadtest TEMPLATE golden;
```

재시드는 논리 데이터가 같아도 행의 물리 배치와 적재 시각이 매번 달라집니다. 복제하면 그 물리 상태까지 같은 출발선에서 시작하고, 수 분이면 끝납니다. 직전 run의 쓰기는 복제본만 더럽히고 함께 버려집니다.

숨은 이득이 하나 더 있었습니다. 시드 직후 `VACUUM ANALYZE`까지 golden에 담으면 **플래너 통계도 함께 동결**됩니다. 통계 상태가 run마다 다르면 플래너가 다른 플랜을 잡아 측정 자체가 오염되는데, 그 변수가 통째로 사라집니다. golden을 다시 만드는 건 스키마 마이그레이션·시드 로직 변경·인스턴스 삭제 때뿐입니다. 이후 실측에서 동결된 golden은 22GB로 설계 시 추정(~15GB)보다 컸고, "데이터 `>` RAM" 조건은 더 여유 있게 충족됐습니다.

## 7천만 건을 어떻게 '재현 가능하게' 만드나

시드는 커야 하고(빈 DB에서는 병목이 안 보임), 동시에 **같은 데이터가 다시 만들어져야** 합니다. 그래서 적재 경로와 난수를 따로 결정했습니다.

적재는 애플리케이션을 거치지 않습니다. 차원 테이블은 현실적인 한글 문자열이 필요해 CSV `\copy`로, 팩트 테이블은 분포만 맞으면 되므로 DB 안에서 생성합니다. 파이프라인 구현과 그때 겪은 실패는 [하네스 노트](/research/loadtest-harness)에 적었습니다. 설계 목표는 약 7,000만 건이고, 동결 시점의 실적재 건수는 [에러율 96% 노트](/research/loadtest-error96)에 있습니다.

재현성은 난수를 전부 결정론으로 바꿔 확보했습니다.

- 차원 UUID: `md5('user-' || n)::uuid` — 같은 `n`이면 항상 같은 UUID. FK를 조인 없이 공식으로 유도할 수 있다는 부수 효과가 큽니다.
- 문자열·비율 난수: **mulberry32 고정 시드** — 한글 닉네임·그룹명·아이템 슬롯까지 같은 순서로 재생성됩니다.
- 팩트 PK: `seed_uuid_v7(started_at)` — 상위 6바이트를 epoch ms로 채워 시간순 정렬을 보장합니다.

마지막 항목은 측정 정확도에 직접 걸립니다. `focus_sessions`의 커서 쿼리는 `ORDER BY id DESC` + `id` 경계 비교에 의존합니다. 시드가 랜덤 v4를 넣으면 id 정렬이 시간과 무관해져 커서 API의 부하 특성 자체가 왜곡됩니다. 그래서 시드 검증 단계에 "커서 정렬 위반 0건" 항목을 넣었습니다.

적재 가속은 제약을 떼고 넣는 고전적인 방법을 씁니다. 제약명은 `pg_get_constraintdef`로 런타임에 캡처해 저장 → 드롭 → 적재 → PK·UNIQUE·FK 순으로 복원합니다. PRD 확정 직후 마이그레이션을 여러 개 올리면서 제약명이 바뀌었지만, 시드 스크립트는 한 줄도 손대지 않아도 됐습니다.

## 매트릭스를 손으로 쓰지 않는다 — openapi에서 자동생성

처음에는 엔드포인트당 k6 파일 하나를 손으로 썼습니다. 표적 3종을 다루는 동안은 이 방식으로 버텼지만, 엔드포인트가 늘 때마다 사람이 파일을 따라 늘려야 합니다. 그래서 "느릴 만한 몇 개만 골라 쓴다"는 전제를 버리고 전수 자동생성으로 방향을 틀었습니다.

`openapi.json`을 입력으로 엔드포인트별 입력 전략(path·query·body, enum·date·시드 풀·body 스키마)을 만드는 생성기를 붙였습니다. 붙여 보니 커버리지는 **86/93**이었습니다(경계가 된 7개의 정체는 [하네스 노트](/research/loadtest-harness)).

실행은 제네릭 러너 하나로 통일했습니다. 선택분은 하나의 arrival-rate 안에서 랜덤 픽해 총 rate를 분산하고, `endpoint` 태그로 per-endpoint 지표를 유지합니다. 초기 구현은 선택한 N개를 직렬로 N번 디스패치했는데, 스팟 VM을 낭비하면서 병렬 부하까지 잃어버려 단일 run 랜덤 픽으로 바꿨습니다. 유저 시나리오는 JSON 정의로 옮겨, 새 시나리오 추가가 파일 하나로 끝나게 했습니다.

## "스팟은 경매다"를 레포 전수 검색으로 반증

부하 VM을 스팟으로 쓰다 존 재고 소진에 막혔을 때, 팀 안에는 이런 전언이 돌고 있었습니다. "스팟은 경매라 max price를 올리면 용량을 뺏어올 수 있고, 사내 terraform 레포에 그 세팅이 있다."

받아들이기 전에 확인했습니다. 해당 레포 전 파일을 가격·입찰 키워드로 검색한 결과 **세팅 0건**이었고, `bid` 매치는 전부 `AssumeRoleWithWebIdentity`의 부분 문자열(`WebId`)이었습니다.

- GCP Spot에는 **가격 파라미터가 아예 없습니다.** terraform google provider의 `scheduling` 블록에 그런 필드가 없고, 선점·재고는 순수 용량 기준입니다. "경매·입찰"은 2017년 이전 AWS 모델이며 가격 기반 축출은 Azure Spot 쪽 이야기입니다.
- 결정적으로, 그때 막혀 있던 SUT는 **스팟도 아닌 온디맨드**였습니다. 어떤 가격으로도 새치기할 수 없습니다.
- GCP에서 돈으로 용량을 확보하는 유일한 수단인 예약(reservation)은 확보 순간부터 24시간 풀 과금이라 "평시 전부 중지" 모델과 충돌하고, 품절 존에서는 생성 자체가 실패합니다.

이 규칙은 부하테스트 밖에서도 씁니다. 클라우드 통념은 프로바이더를 명시하지 않으면 검증할 수 없으니, 반박하든 수용하든 원문(레포 검색 + provider 스키마)으로 먼저 확인합니다.

무료체험 8 vCPU 상한에 맞춰 설계상 c2-standard-8이던 부하기를 **c2-standard-4로 하향**했습니다(SUT 2 + 관측 2 + 부하 4). 앞서 정한 무효 규칙 덕에 부하기가 먼저 포화된 run은 숫자로 쓰이지 않고, 고rps 한계 탐색은 다중 부하기가 준비된 뒤로 미뤘습니다. 존·세대 핀을 포함한 실제 프로비저닝은 [하네스 노트](/research/loadtest-harness)에 있습니다.
