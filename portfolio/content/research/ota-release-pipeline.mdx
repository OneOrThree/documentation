## 0. 한눈에

gromo 1.x는 앱 하나를 **서로를 모르는 두 파이프라인**으로 내보냈다. 네이티브 바이너리(앱 자체)는 로컬 맥에서 fastlane으로 빌드해 TestFlight를 거쳐 애플 심사를 받고, JS 번들(화면과 로직을 담은 자바스크립트 묶음)은 hot-updater로 올려 **심사 없이 즉시** 전 사용자에게 꽂힌다. 이렇게 스토어 심사 없이 JS 번들만 바꿔 내려보내는 업데이트를 OTA(Over-The-Air)라고 부른다.

두 축이 만나는 곳은 앱 시작 시점 딱 한 곳이고, 거기서 **번들이 바이너리를 덮어쓴다.** 그래서 "바이너리를 고쳤다"가 "사용자가 고친 코드를 본다"를 보장하지 않는다. 7월 20일 사고의 구조적 뿌리가 이것이다.

| 값 | 무엇 |
| --- | --- |
| **2축** | 바이너리(심사 거침) · 번들(심사 없음) |
| **26시간** | 옛 번들이 새 바이너리보다 "새것"으로 판정되는 창 |
| **15시간** | 07-20 사고, 첫 아카이브부터 수습까지 |
| **5 vs 0** | 축별 배포 가드 수 |
| **0건** | 파이프라인 커밋에 붙은 `[FIX]` 라벨 |
| **0개** | iOS CI 잡 (빌드·배포 전부 수동) |

<Callout label="이 문서가 다루는 것">

1장은 파이프라인이 왜 이런 모양이 됐는지, 2장은 그 위에서 실제로 부러진 14건을 증상·원인·해결로 적은 기록이다. 1~4장은 8월 초(GROMO-1234 #520 직후) 기준이고, 그 뒤 1.x가 동결될 때까지 바뀐 것은 5장에 따로 모았다. 눈여겨볼 것은 **가드의 비대칭**이다 — 심사를 거치는 축에는 방어가 다섯 겹인데, 심사 없이 즉시 나가는 축은 맨손이다.

</Callout>

<Callout label="1.x 앱의 기록이다" tone="warn">

이 문서의 파이프라인은 지금은 동결된 1.x 앱(`app/legacy/app-dev`)의 것이다. 2.0 앱(`app/app-dev`)에는 현재 hot-updater 설정이 없다. OTA 도구 선택의 기각 대안은 [ADR-023](/adr/adr-023-ota-hot-updater), 브랜치 전략의 결정 근거는 [ADR-024](/adr/adr-024-app-release-branch)에 있다.

</Callout>

## 1. 설계

### 1.1 왜 축이 둘인가

처음엔 Expo의 클라우드 빌드(EAS)를 썼는데 무료 한도 월 15회를 다 쓰면서 **로컬 fastlane으로 내려왔다**(GROMO-515, #69, 06-29). fastlane은 빌드·서명·업로드를 자동화하는 도구다. 그 뒤 "JS만 고친 수정도 애플 심사를 며칠 기다려야 한다"는 문제가 남아 번들만 갈아끼우는 OTA를 붙였다(GROMO-875, #303, 07-19).

OTA 도구는 셋을 비교했고, 관리형 서비스가 편했지만 **비용 회피와 인프라 통제**를 이유로 자체 호스팅(hot-updater)을 골랐다. 호스팅도 처음엔 Firebase로 잡았다가 같은 날 뒤집었다 — Functions를 쓰려면 카드 등록이 필요했고, 카드 없이 시작할 수 있는 Supabase로 갈아탔다.

<Callout label="비용을 아낀 대가는 맥 한 대에 묶였다">

클라우드 빌드를 버린 결과, 빌드 재현성이 **맥 한 대의 로컬 환경**(node 경로, 키체인, 인증서 파일)에 묶였다. 당장 문제는 없었지만, 비용을 사람과 기계 한 대로 치환한 선택이다.

</Callout>

### 1.2 두 축의 전체 그림

```text
[바이너리 축]  심사를 거친다 · 가드 5겹
  arelease/* 브랜치 → testflight.sh → fastlane → TestFlight → 애플 심사 → 스토어
                      (여기서 값이 박힌다)  (7타겟 수동 서명)

[번들 축]      심사를 안 거친다 · 가드 0
  같은 브랜치(JS만) → hot-updater deploy → Supabase → 업데이트 서버
                      (손으로 치는 CLI · 문서 없음)  (번들 저장 + 버전 DB)  (채널 1개)

                          ↘                         ↙
                     [앱 시작 게이트] — 두 축이 만나는 유일한 지점
                     여기서 번들이 바이너리를 덮어쓴다 (JS 한정)
```

### 1.3 만나는 지점은 한 곳

앱이 켜지면 **화면을 그리기 전에** 업데이트 서버에 묻는다. "나는 이 버전, 이 번들인데 더 새 게 있나?" 있으면 내려받아 내장 번들을 갈아끼우고, 없으면 그대로 진행한다. 이 게이트는 두 경우에 아예 걸리지 않는다 — **E2E 테스트 실행 중**(대본이 옛 번들에 오염되면 안 되니까, B3)과 **웹**(호스팅이 JS를 직접 갈아 주니까)이다.

<Callout label='비교 기준은 "마케팅 버전"뿐이다' tone="warn">

업데이트 대상 판정에는 **빌드 번호를 안 쓴다**(`updateStrategy: 'appVersion'`). 마케팅 버전은 사용자에게 보이는 `1.0.0`, 빌드 번호는 업로드마다 올리는 내부 번호다. `1.0.0`으로 올린 바이너리가 100개든 1개든 전부 같은 대상으로 묶이므로 "더 높은 빌드 번호로 다시 올렸으니 괜찮겠지"가 성립하지 않는다.

</Callout>

### 1.4 26시간의 의미

그럼 "더 새것"은 무엇으로 판단하나. 바이너리에는 **이보다 오래된 번들은 무시한다**는 기준선(minBundleId)이 박혀 있다. 문제는 그 기준선이 컴파일 시각 그대로가 아니라 **컴파일 시각 − 26시간**이라는 점이다. 전 세계 시간대 폭(UTC−12 ~ UTC+14)을 감안한 hot-updater 기본 로직의 안전 마진인데, 부작용이 크다.

```text
  기준선                                             새 바이너리
  (컴파일 − 26h)                                     컴파일 17:46
     |◀──────────────── 위험 창 26시간 ─────────────────▶|
                  03:15 dev 주소 번들 배포
                  └ 이 창 안에 올린 번들은 새 바이너리보다 "미래"로 판정돼 내려온다
```

<Callout label="탈출구가 있는데 안 쓰고 있다" tone="warn">

기준선은 앱 설정 파일에 값을 하나 넣어 **직접 지정할 수 있다.** gromo에는 그 키가 없어 26시간 기본값에 그대로 노출돼 있다. "잘못된 번들을 올렸으니 바이너리를 다시 빌드하자"는 순서로 수습하면 **같은 함정에 반드시 다시 걸린다.**

</Callout>

### 1.5 값이 박히는 순간

서버 주소나 분석 키 같은 환경 변수는 앱이 실행될 때 읽는 게 아니라 **번들을 만드는 순간 문자열로 박힌다**(인라인). 값의 우선순위는 이렇다.

`셸 export > .env.production > .env`

**셸 export가 가장 세다.** 파일을 아무리 고쳐도 스크립트가 export로 덮어쓰면 그 값이 이긴다. 이게 A1 사고의 전부다. 게다가 값이 박히는 자리가 축마다 다르다 — 바이너리 축은 빌드 스크립트(`testflight.sh`)가, 번들 축은 `deploy`를 돌린 **그 셸의 환경**이 정한다. 두 축이 서로 다른 주소를 박을 수 있고, 실제로 그랬다.

### 1.6 브랜치와 3단계

| 단계 | 무엇 | 태그 | 빈도 |
| --- | --- | --- | --- |
| ① 업로드 | TestFlight에 올려 내부 테스트 | 안 붙임 | 월 20회 이상 |
| ② 심사 제출 | 애플에 검수 요청 | **필수** | 드묾 |
| ③ 출시 | 스토어 공개 (수동 버튼) | — | 드묾 |

이 셋을 구분하지 않으면 테스트 업로드마다 태그가 쌓여 릴리즈 태그가 소음이 된다. 그래서 fastlane 레인도 둘로 나눴다 — **beta**는 아무 브랜치에서나 개발 서버로, **release**는 릴리즈 브랜치에서만 운영 서버로 나가고 태그를 자동으로 붙인다(GROMO-911, #330).

<Callout label="브랜치 이름이 arelease/인 이유">

`release/app-1.0`으로 만들려다 **push가 거부됐다.** 백엔드가 `release`라는 단독 브랜치를 이미 쓰고 있어서([ADR-021](/adr/adr-021-release-fast-forward)), git이 "같은 이름을 파일이자 폴더로 쓸 수 없다"(directory file conflict)고 막은 것이다. 앱 브랜치에 `a`를 붙이는 기존 컨벤션(`afeat/`·`afix/`)과도 맞아 `arelease/1.0`으로 굳었다.

</Callout>

## 2. 결함 기록

고장 성격별로 묶었다. 출처 표시에서 `사고`는 실제로 뭔가 깨진 뒤에 안 것, `실측`은 코드나 설정을 직접 확인하다 발견한 것이다.

### A. 박힌 값

#### A1. 심사에 제출한 빌드가 개발 서버를 보고 있었다

**출처** 사고 · GROMO-881 · 07-20

**증상** — 운영 백엔드로 전환하는 날. `.env.production`을 운영 주소로 고치고 다시 빌드했는데 앱이 계속 개발 데이터를 보여 준다. 한 번 더 빌드해도 같다. **그 상태로 심사까지 제출됐다.**

**원인** — 빌드 스크립트 `testflight.sh`가 서버 주소를 **개발 서버로 export하고 있었다.** 셸 export가 `.env.production`보다 세니까 파일 수정이 통째로 무효였다. 더 아픈 건 그 export가 **3주 전(06-30)에 넣은 안전장치**였다는 점이다. "로컬 백엔드 주소가 박혀서 테스터가 접속 못 하는" 사고를 막으려고 넣은 것이었다. 어제의 올바른 방어가 오늘 정반대 사고의 원인이 됐다.

**해결** — 기본값을 **운영 서버로 뒤집고**, 개발 서버는 별도 변수로 명시할 때만 쓰게 했다(`2d02c7b2`). 기본값이 안전한 쪽이어야 한다는 원칙을 뒤늦게 적용한 셈이다. 지금 스크립트는 레인으로 기본값을 고른다 — release는 운영, beta는 개발.

진짜 교훈은 **검증은 산출물로** 해야 한다는 것이다. 설정 파일이 아니라 아카이브 안의 `main.jsbundle`을 `strings`로 뽑아 박힌 주소를 직접 확인하는 것이 유일하게 확실한 검사였다.

#### A2. 개발 서버 푸시가 3주 동안 전멸해 있었다

**출처** 사고 · GROMO-1234 · #520 · 08-08

**증상** — 개발 환경 푸시 알림이 **전부** 실패한다(`SENDER_ID_MISMATCH`). 로그 보존 기간 내내 같은 에러였고, 3주가 지나서야 발견했다.

**원인** — **판단 축이 둘로 갈라져 있었다.** 빌드 스크립트는 레인(beta/release)을 보고 서버를 골랐는데, 푸시 설정 파일(Firebase plist)은 빌드 설정(Debug/Release)을 보고 골랐다. beta 레인은 "Release 설정 + 개발 서버" 조합이라, 개발 서버에 운영용 푸시 설정이 붙었다. 같은 것을 두 기준으로 판단하면 **언젠가 반드시 어긋난다.**

**해결** — 판단 축을 `APP_ENV` 하나로 통일했다. 이 한 값이 관측 태그와 푸시 설정을 동시에 정한다. 리뷰 지적으로 주소 비교도 **대소문자와 끝 슬래시를 정규화**하게 했다 — 주소 끝에 `/`를 하나 더 붙였다는 이유로 같은 사고가 재발하지 않도록.

#### A3. 관측 도구의 환경 태그가 개발용으로 박힐 뻔했다

**출처** 실측 · GROMO-928 · #334 · 07-24

**증상** — 에러 추적·분석 도구의 환경 태그가 **로컬 개발 설정**의 값으로 릴리즈 번들에 박히는 경로가 열려 있었다.

**원인** — A1과 같은 뿌리다. 값이 빌드 순간에 박히는데, 그 값의 출처가 개발자 개인 파일이었다. 터지면 운영 데이터와 개발 데이터가 한 대시보드에 섞인다.

**해결** — 환경 태그를 배포 대상과 **같이 묶어서 export**하고, 일부 키는 로컬 설정과 무관하게 스크립트에 직접 넣었다. 사고로 번지기 전에 잡은 건이다.

### B. 번들이 이긴다

#### B1. 고쳐서 올린 바이너리를 옛 번들이 되돌릴 뻔했다

**출처** 사고 · 07-20

**증상** — A1을 수습하고 **운영 주소가 박힌 것을 직접 확인한** 새 빌드를 올렸는데, 그 앱이 **첫 실행에 옛 번들을 내려받아 원위치될** 상황이었다.

**원인** — 1.4의 **26시간 창**이다. 그날 새벽 03:15에 올린 "개발 주소가 박힌 번들"이 저녁 17:46에 컴파일한 새 바이너리의 기준선보다 나중으로 판정된다. 빌드 번호를 아무리 올려도 소용없다 — 비교에 안 쓰이니까(1.3). 공들여 고친 바이너리를, **그 고침 이전의 번들이 덮어쓰는** 구조였다.

**진단** — 추측이 아니라 서버 응답을 재현해서 확인했다. 순서는 이렇다.

1. 활성 번들 목록을 조회한다. 번들 id가 UUIDv7이라 앞 12자리 16진수가 배포 시각(ms)이다 — 언제 올라간 번들인지 id만으로 역산된다.
2. 업데이트 서버에 새 빌드가 보낼 요청을 그대로 흉내 낸다. 경로 모양은 `/app-version/{platform}/{앱버전}/{채널}/{minBundleId}/{현재bundleId}`이고, 신규 설치는 두 id가 같다. 기준선은 "빌드 시각보다 하루쯤 이전"이면 같은 판정이 나온다.
3. 응답이 `null`이면 내려올 번들이 없다(안전). `UPDATE`면 그 번들이 새 빌드를 덮는다.
4. 서빙되는 번들을 내려받아 `strings`로 박힌 주소를 확인한다.

**해결** — 문제의 번들을 서버에서 **비활성화**하고, 응답이 `null`로 바뀐 것을 다시 확인한 뒤 번들 행과 저장 파일을 완전히 삭제했다. 그다음 재빌드해서 심사에 제출했다. 이미 그 번들을 받은 기기는 비활성화하면 내장 번들로 돌아간다.

**근본 해결은 아직 안 됐다** — 기준선을 직접 지정하는 설정이 여전히 비어 있다(1.4).

#### B2. OTA 롤백이 사용자 데이터를 지울 수 있었다

**출처** 실측 · GROMO-936 · #339 · 07-24

**증상** — 번들을 되돌리는 순간, 되돌아간 **옛 번들이 사용자의 보유 아이템과 착용 정보를 삭제**하는 경로가 있었다.

**원인** — 로컬 저장소 마이그레이션이 "버전 값이 내가 아는 값이 아니면 옛 데이터를 지운다"는 식이었다. 앞으로만 가면 맞는 로직인데, **OTA는 뒤로도 간다.** 롤백하면 옛 번들이 자기가 모르는 새 버전 값을 보고 데이터를 파괴한다.

**해결** — `storageVersion` 값을 **`'2'`로 영구히 고정**하고, 앞으로의 마이그레이션은 전용 마커 키로 따로 추적하게 계약을 바꿨다. 저장할 때 구 키에도 같이 써서(듀얼 라이트) 롤백된 번들에서도 구매·장비가 보이게 했다. 롤백 가능성이 저장소 설계의 제약 조건이 된 것이다.

#### B3. 자동 테스트가 옛 번들에 오염됐다

**출처** 사고 · GROMO-947 · #352 · 07-26

**증상** — E2E(실제 앱을 켜서 사람처럼 눌러 보는 자동 테스트) 대본을 돌리는 중 화면 요소를 못 찾는다.

**원인** — 테스트 실행 중 OTA가 **옛 번들로 갈아끼웠다.** 그 번들에는 대본이 찾는 식별자가 아직 없다. 테스트가 무엇을 검증하는지 자체가 불확실해졌다.

**해결** — E2E 전용 플래그로 **게이트 자체를 안 걸도록** 했다. 실행 전 앱을 지우고 다시 까는 절차도 넣었다 — 권한 상태와 이전 번들 잔재를 같이 치우기 위해서다. 이 결정이 E2E를 "제품과 다른 앱"으로 만드는 한 축이 된 사정은 [앱 자동 검증의 사각지대](/research/app-test-gap) D1에 있다.

### C. 빌드 도구

#### C1. 빌드 번호가 항상 0이라 업로드가 거부됐다

**출처** 사고 · GROMO-911 · #330 · 07-23

**증상** — 업로드할 때마다 "이미 쓴 빌드 번호"라며 거부된다.

**원인** — "마지막 빌드 번호"를 조회할 때 버전 값으로 **실제 숫자가 아니라 치환되지 않은 변수 문자열**을 넘기고 있었다. 그런 버전은 없으니 조회 결과가 항상 0이고, 다음 번호는 늘 1이 된다.

**해결** — 프로젝트 설정 파일에서 **실제 버전 문자열을 직접 뽑아** 넘긴다.

#### C2. 빌드가 실패하면 다음 시도가 막힌다

**출처** 실측 · GROMO-911 · #330

**증상** — 한 번 실패한 뒤 다시 돌리면 "작업 트리가 깨끗하지 않다"며 시작조차 안 된다.

**원인** — 빌드 전에 **버전 파일을 고치는데**, 빌드가 실패하면 그 수정이 그대로 남는다. 다음 실행의 안전 가드가 그 흔적에 걸린다. 가드가 재시도를 막는 구조였다.

**해결** — 실패 시 버전 파일을 **원래대로 되돌린다.**

#### C3. 뒤처진 로컬로 심사 빌드를 만들 수 있었다

**출처** 실측 · GROMO-911 · #330

**증상** — 업로드까지 다 끝난 뒤에야 마지막 push가 거부된다. 빌드 번호는 이미 소모됐다.

**원인** — 로컬이 원격보다 뒤처져 있는지 **빌드 전에 확인하지 않았다.** 심사 빌드는 되돌릴 수 없는 행위인데 그 앞에 검사가 없었다.

**해결** — 빌드 시작 전에 원격과 같은 지점인지 확인하고, 아니면 아예 시작하지 않는다.

#### C4. 태그를 하나 만들었는데 전부 밀려 나갔다

**출처** 실측

**증상** — 릴리즈 태그 하나를 붙였는데 로컬의 실험용 태그까지 전부 원격으로 올라간다.

**원인** — push 옵션이 **"태그 전부"**였다. 편의 옵션 하나가 원격 태그 목록을 오염시킨다.

**해결** — 전체 태그 push를 끄고 **방금 만든 태그 하나만** 명시해서 올린다.

#### C5. 안드로이드 릴리즈가 디버그 키로 서명되고 있었다

**출처** 실측 · GROMO-1001 · 08-01

**증상** — 릴리즈 빌드를 만들어도 스토어에 못 올린다.

**원인** — 프로젝트 생성 시 기본값 그대로였다. 릴리즈용 서명 설정이 아예 없어 디버그 키가 쓰였다. **아무도 안 봐서 오래 남아 있던 기본값**이다.

**해결** — 릴리즈 서명 설정을 추가하고, 키 파일이 없으면 경고와 함께 디버그로 물러나게 했다. 키 자체는 비밀이라 저장소에 넣지 않는다.

### D. 프로세스

#### D1. 심사 빌드가 나오는 브랜치에서 CI가 안 돈다

**출처** 실측 · 미해결

**증상** — 릴리즈 브랜치로 올리는 PR은 린트·타입 검사·테스트를 **하나도 거치지 않는다.**

**원인** — CI 설정이 `main`으로 가는 PR만 대상으로 잡혀 있다. 정작 **사용자에게 나가는 코드가 지나는 길이 검사 사각지대**다.

**해결** — **안 됐다.** 문서에 "티켓화 대상"으로만 적혀 있다. 브랜치 보호 규칙으로 강제하는 방법은 저장소 소유 조직이 **유료 플랜이어야 해서** 막혀 있다.

#### D2. 별표까지 쳐서 "필수"라고 못 박은 규칙이 실제로 밀렸다

**출처** 실측 · 미해결

**증상** — 릴리즈 브랜치에서 고친 것을 `main`으로 되가져오는 작업(머지백)이 밀려 있다. 그 결과 `main`의 빌드 번호가 **폐기된 빌드**를 가리킨다.

**원인** — 문서에 별표를 붙여 "빼먹으면 다음 버전에서 버그가 부활한다"고 적어 뒀는데, 강제 장치가 없다. **문서화는 1단계일 뿐 실행을 보장하지 않는다**는 걸 문서 스스로 증명한 셈이다.

**해결** — 아직. 머지백 PR을 열면 끝나는 일이지만, 그걸 알려 주는 장치가 없다.

#### D3. 가장 위험한 통로가 가장 문서화가 안 돼 있다

**출처** 실측 · 미해결

**증상** — OTA 배포 명령이 **저장소 어디에도 없다.** 스크립트에도, 문서에도, 예시에도.

**원인** — 바이너리 축은 스크립트 하나로 감싸고 가드를 다섯 겹 붙였는데, **심사를 안 거치고 전 사용자에게 즉시 반영되는 축**은 손으로 명령을 치는 상태로 남았다. 위험도와 방어의 크기가 정확히 반대다.

**해결** — 아직. `hot-updater deploy`를 감싸는 가드 스크립트 구상만 문서에 있다 — 배포 전(브랜치·더티 트리·env·대상 버전 검사), 배포 후(서버 응답 시뮬레이션·번들 안 주소 검증), 기록(배포 태그). A1·B1이 전부 이 축에서 나왔다는 걸 생각하면 우선순위가 낮을 이유가 없다.

#### D4. 자동 검사를 통과해도 심사는 떨어질 수 있다

**출처** 사고 · 07-20

**증상** — 메타데이터 사전 검사(fastlane `precheck`)를 통과했는데, 실제로는 운영 DB에 기초 데이터가 안 들어가 있어 온보딩 화면이 **빈 화면**으로 뜰 뻔했다.

**원인** — `precheck`는 **스토어에 적는 글자만** 본다(금칙어·플레이스홀더·깨진 URL 등). 앱이 실제로 어떻게 도는지는 검사 범위 밖이다. 도구 이름이 "사전 검사"라 다 봐 준다고 착각하기 쉽다. 서버 쪽에서 본 같은 사건은 [마이그레이션 사고 3연발](/research/migration-incidents)에 있다.

**해결** — 그 경계를 문서에 명시하고, 심사 전 확인 목록에 **운영 데이터 점검과 클린 설치 확인**을 넣었다. 도구가 못 보는 것은 사람이 보는 수밖에 없다.

| 검증이 사람 손에 | 번들 안의 주소를 눈으로 확인하는 게 유일하게 확실한 검사인데, 체크리스트에만 있다 | 배포 스크립트가 자동으로 확인하고 다르면 멈추게 한다 |
| 빌드 머신이 한 대 | 클라우드 빌드를 비용 때문에 버린 대가. 재현성이 로컬 환경에 묶임 | 사람이 늘거나 그 맥이 죽으면 그때가 전환 시점 |
| 호스팅 무료 플랜 | 전송 월 5GB · 저장 1GB · **1주 비활성이면 프로젝트 일시정지** | 일시정지가 곧 OTA 정지다. 사용자가 늘기 전에 유료 전환 |

## 5. 이후 변화 — 1.x 동결까지

| 날짜 | 무엇 | 천장에 미친 영향 |
| --- | --- | --- |
| 08-10 · 08-14 | 1.1.0을 `arelease/1.1`에서 release 레인으로 두 번 빌드(태그 `app-1.1.0-1` · `app-1.1.0-7`). 빌드 번호가 타임스탬프에서 버전별 순번으로 바뀌었다 | 바이너리 축은 설계대로 굴렀다. 앱 릴리즈 태그는 모두 3개가 됐다 |
| 08-31 | GROMO-1703(#709) — 배포 런북에 OTA 배포 장 신설. 셋업·명령·배포 전 사고 3종·검증·롤백 | D3의 "문서가 없다"는 해소. "가드가 없다"는 그대로 |
| 09-16 | GROMO-1890(#766) — 1.x 앱을 `app/legacy/app-dev`로 옮기고 동결, CI 검사 대상에서도 뺐다 | D1이 "릴리즈 브랜치만 무검사"에서 "1.x 전체 무검사"로 넓어졌다 |

#709가 문서화한 "배포 전 사고 3종" 중 하나는 이 문서 이후에 드러난 구멍이다. `testflight.sh`는 셸 export로 서버 주소를 고정하지만 **OTA 배포에는 그런 보정이 없어서**, 배포하는 사람의 개인 `.env.local`에 적힌 API 주소가 그대로 전 사용자 번들에 박힌다. 1.5의 우선순위 문제가 번들 축에서 사람마다 다른 모양으로 남아 있었던 것이다. 나머지 둘은 26시간 기준선(1.4)과 `storageVersion` `'2'` 고정 계약(B2)이다.

끝까지 남은 것도 확인했다(09-19 저장소 기준).

- **기준선 키** — 1.x의 hot-updater 설정 파일에는 동결 시점까지 minBundleId 키가 없다.
- **OTA 가드 스크립트** — 만들어지지 않았다. 1.x의 `scripts/`에는 안드로이드 릴리즈와 E2E 스크립트뿐이다.
- **머지백** — `arelease/1.0`의 빌드 번호 커밋 하나는 끝내 `main`에 머지백되지 않았다. `arelease/1.1`의 여섯 커밋도 마찬가지인데, 그중 릴리즈 아카이브 컴파일 실패를 고친 Swift 한 줄은 `main`에 따로 반영돼 있다. 머지백 PR이 아니라 사람의 기억이 옮긴 것이다.

<Callout label="1.x 핫픽스는 이제 CI가 검증해 주지 않는다" tone="warn">

동결 이후 `app-lint.yml`은 2.0 앱(`app/app-dev`)만 검사한다. 1.x에 핫픽스를 내려면 `app/legacy/app-dev`에서 린트·서식·타입 검사·테스트·팔레트 코드젠 검사를 직접 돌려야 하고, 안드로이드 네이티브를 건드렸다면 Gradle 컴파일까지 손으로 확인해야 한다. 자세한 사정은 [앱 자동 검증의 사각지대](/research/app-test-gap) 6장에 있다.

</Callout>

## 6. 용어

| 용어 | 뜻 |
| --- | --- |
| 바이너리 / 네이티브 | 앱 자체. 애플 심사를 거쳐야 바뀐다. 며칠 걸린다 |
| 번들 (JS bundle) | 화면과 로직을 담은 자바스크립트 묶음. 심사 없이 갈아끼울 수 있다 |
| OTA (Over-The-Air) | 앱을 다시 설치하지 않고 번들만 원격으로 갈아끼우는 것 |
| TestFlight | 애플이 제공하는 베타 배포 통로. 심사 전에 테스터가 먼저 써 볼 수 있다 |
| fastlane | 빌드·서명·업로드를 자동화하는 도구. 여기서는 로컬 맥에서 돈다. 레인은 그 안의 작업 묶음 하나 |
| 인라인 (inline) | 값이 실행 시점에 읽히는 게 아니라 **빌드 순간 문자열로 박히는** 것. 이 문서 사고의 절반이 여기서 나왔다 |
| 마케팅 버전 / 빌드 번호 | 앞은 사용자에게 보이는 `1.0.0`, 뒤는 업로드마다 올리는 내부 번호. **OTA 판정에는 앞만 쓴다** |
| 기준선 (minBundleId) | "이보다 오래된 번들은 무시한다"는 시점. 기본값이 컴파일 시각 − 26시간이라 위험 창이 생긴다 |
| 채널 | 번들을 나눠 배포하는 갈래. gromo는 하나뿐이라 단계 배포가 없다 |
| 가드 (guard) | 위험한 작업 전에 조건을 확인하고 아니면 멈추는 장치. 바이너리 축엔 5개, 번들 축엔 0개다 |
| 머지백 | 릴리즈 브랜치에서 급히 고친 것을 다시 `main`으로 합치는 일. 빼먹으면 다음 버전에서 버그가 되살아난다 |
| precheck | fastlane의 심사 전 메타데이터 검사. 스토어에 적는 글자만 보고 앱 동작은 보지 않는다 |
