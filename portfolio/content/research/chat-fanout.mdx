실시간 채팅은 "A가 보낸 메시지를 B에게 즉시 전달한다" 한 문장입니다. 이 문장이 쉬운 건 서버가 한 대일 때뿐입니다.

이 노트의 결론을 먼저 적습니다. 채팅 아키텍처의 발전 단계는 취향이 아니라 **제약 하나에서 파생된 필연**입니다. 그 제약은 WebSocket 연결이 stateful이라는 것 하나뿐이고, 여기서 Presence 릴레이 → Pub/Sub → 메시지 큐 + 컨슈머 팬아웃 분리가 순서대로 강제됩니다. 그리고 그 과정에서 흔히 오해되는 것 하나를 정리했습니다. **"채팅 서버를 여러 대로 늘린다"는 것은 별개 서버를 만드는 일이 아닙니다.** 같은 스프링 앱을 수평 확장하는 것이고, 진짜로 별개 배포가 정당화되는 지점은 팬아웃 워커를 떼어낼 때 딱 한 번입니다.

## 제약 하나가 모든 단계를 끌고 간다

먼저 못 박아야 하는 사실이 두 개 있습니다.

- WebSocket 연결은 **stateful**입니다. 유저가 한 번 붙으면 그 TCP 연결은 **특정 인스턴스의 로컬 메모리**에만 존재합니다.
- 따라서 서버를 수평 확장하면 A와 B가 서로 다른 인스턴스에 붙을 수 있고, **A가 붙은 서버는 B의 연결을 모릅니다.**

HTTP API를 여러 대로 늘리는 일과 결정적으로 다른 지점이 여기입니다. 무상태 HTTP는 어느 인스턴스가 받아도 같은 응답을 만들 수 있으니 로드밸런서만 붙이면 끝입니다. 반면 WebSocket은 "받는 쪽"이 특정 인스턴스에 묶여 있어서, 인스턴스를 늘리는 순간 **"수신자가 어느 서버에 붙었나"**라는 새 문제가 자동으로 생깁니다. 이 질문에 답하는 방식의 차이가 곧 아래 단계들입니다.

그래서 저는 단계를 외우는 대신 매 단계에서 같은 네 칸을 채우는 방식으로 정리했습니다. ① 무엇을 했나 ② 왜 ③ 한계 ④ 그래서 다음 선택. 한계 칸이 비면 다음 단계로 갈 이유가 없다는 뜻이고, 그때는 그 구조에 머무는 것이 맞습니다.

## 0차와 1차 — 위치를 조회해서 직접 릴레이한다

**0차는 단일 WebSocket 서버**입니다. 스프링 부트 한 대에 STOMP를 띄우고 접속 세션을 인메모리에 들고 있습니다. 가장 빠르게 동작하고, 모든 연결이 한 메모리 안에 있으니 라우팅 고민이 아예 없습니다. 한계는 명확합니다. 서버 1대의 한계이고, 재시작하면 연결과 세션이 통째로 날아가며, 동시 접속이 늘면 수평 확장이 불가능합니다.

**1차는 다중 인스턴스 + 공유 메모리(Presence)** 입니다. 여기서 제가 오래 헷갈렸던 걸 짚어둡니다. 채팅 서버 1, 2는 서로 다른 종류의 서버가 아니라 **같은 스프링 앱을 수평 확장한 인스턴스들**입니다. 각 인스턴스는 자기에게 붙은 유저의 WS 세션만 로컬에 들고 있고, "누가 어느 서버에 붙어 있는지"를 모든 인스턴스가 함께 보는 Key-Value Store(보통 Redis)에 올립니다. 이게 Presence입니다.

메시지 흐름은 이렇습니다.

```text
1. A가 서버1로 SEND (WebSocket)
2. 서버1: 자기 메모리에 B의 연결이 없다 → KV에서 "B가 붙은 서버"를 조회
3. 서버1 → 서버2로 릴레이 요청 (직접 전달)
4. 서버2: 자기 메모리의 B 연결로 push
```

수평 확장이 가능해지고 연결 상태가 중앙화됩니다. 그런데 두 개의 한계가 남습니다. 하나는 메시지를 보낼 때마다 수신자 위치를 매번 조회해야 한다는 것, 다른 하나가 훨씬 심각합니다. **대규모 단톡방이면 한 메시지를 수백~수천 명에게 릴레이해야 하고, 그 팬아웃 부하가 유저 요청을 처리하는 경로에 그대로 얹힙니다.** 한 명이 메시지를 하나 보냈을 뿐인데 그 요청 스레드가 수천 번의 릴레이를 떠안습니다.

여기서 흔히 나오는 변형이 **Redis Pub/Sub**입니다. 위치를 매번 조회하는 대신 서버가 방 채널에 publish만 하고, 그 방을 구독한 서버들이 받습니다. 위치 조회는 사라집니다. 하지만 팬아웃이 요청 경로에 얹힌다는 무게 문제는 그대로 남습니다. 이게 제가 이 단계에서 얻은 판단입니다. **Pub/Sub은 "어디로 보내나"를 해결하지만 "누가 그 무게를 지나"는 해결하지 않습니다.**

## 2차 — 팬아웃을 요청 경로에서 떼어낸다

2차에서는 메시지를 받은 서버가 직접 릴레이하지 않습니다. 대신 "이 메시지를 이 수신자 묶음에게 보내라"를 메시지 큐에 발행하고 즉시 응답합니다. 무거운 팬아웃(수신자 목록 조회, presence 조회, 릴레이)은 컨슈머가 큐에서 꺼내 비동기로 처리합니다.

```text
1. 유저 → 서버로 SEND
2. 서버: 채팅방 수신자 목록을 DB에서 조회
        → 수신자를 묶음으로 쪼개 큐에 발행 (예: 1~200번 / 201~400번)
        → 즉시 응답
3. 컨슈머: 묶음을 꺼내 KV에서 "이 유저들이 각각 어느 서버에 붙었나"를 한 번에 일괄 조회
4. 컨슈머: 해당 채팅 서버로 순차 릴레이 → 각 서버가 자기 유저에게 push
```

개선점은 세 개입니다. 첫째, 수신 서버는 발행만 하고 즉시 응답하니 **응답 지연이 팬아웃 규모와 무관해집니다.** 둘째, 팬아웃이 독립적으로 스케일됩니다(컨슈머만 늘리면 됩니다). 셋째, 큐가 버퍼 역할을 하니 버스트를 흡수합니다. 대가는 정직하게 적어둡니다. 컴포넌트가 늘어 구성 복잡도가 오르고, 비동기라 전달 지연이 늘고, 파티션과 순서, at-least-once 재전송, 멱등 처리를 직접 신경 써야 합니다.

### 여기서 비로소 '별개 서버'가 생긴다

이 단계에서도 채팅 서버 A와 B는 여전히 0차·1차와 **같은 스프링 앱 인스턴스**(WS 게이트웨이)입니다. 새로 등장한 것은 컨슈머라는 **역할** 하나뿐이고, 그 역할을 어디에 두는지는 두 갈래입니다.

| 배치 | 방법 | 별개 배포 필요? |
| --- | --- | --- |
| (a) 같은 앱 안 | `@KafkaListener`를 WS 앱에 함께 둔다 | 필요 없음 |
| (b) 떼어낸다 | 팬아웃 워커를 독립 배포로 분리 | 이 순간 처음 생긴다 |

정리하면, **수평 확장(WS 인스턴스 N대)은 전부 같은 앱**이고, **별개 서버가 정당화되는 지점은 팬아웃 컨슈머를 분리할 때**입니다. 이유도 규모가 아니라 성질입니다. 팬아웃은 무겁고 버스트성이어서, 요청 처리 경로와 자원·장애를 격리하려는 것이 분리의 목적입니다. 반대로 말하면 팬아웃이 아직 가볍다면 (a)로 두는 것이 맞고, 그때 워커를 떼는 건 과설계입니다.

### 4단계 비교

| 단계 | 구조 | 서버 간 전달 방식 | 얻는 것 | 남는 한계 |
| --- | --- | --- | --- | --- |
| 0 | 단일 WS 서버 | 불필요 | 라우팅 고민 없음 | 1대 한계·재시작 유실·확장 불가 |
| 1 | 다중 인스턴스 + KV Presence | B 위치 조회 후 직접 릴레이 | 수평 확장·상태 중앙화 | 매번 위치 조회, 팬아웃이 요청 경로 직격 |
| 1' | + Redis Pub/Sub | 채널 publish/subscribe | 위치 조회 제거 | 팬아웃 무게는 여전 |
| 2 | MQ + 컨슈머 팬아웃 | 발행 후 컨슈머가 비동기 릴레이 | 즉시 응답·독립 스케일·버스트 흡수 | 복잡도·지연 증가, 순서·멱등 관리 |

## 지금 가동 중인 구조 — persist-first, UUIDv7, 파티션 키

실제로 띄운 것은 메인 API와 분리된 **채팅 전용 서비스**(`:8081`, 채팅 전용 PostgreSQL `:5433`)입니다. 단일 인스턴스지만 MQ 경로는 미리 깔아뒀습니다. consume 후 릴레이는 로컬 구독자에게만 하는 LocalRelay 상태입니다.

메시지 한 건이 지나는 경로가 이 구조의 핵심입니다.

```text
SEND → ① DB INSERT → ② publish(key=group_id) → ③ consume(@KafkaListener) → ④ relay
```

이 순서를 **persist-first**라고 부르기로 했습니다. DB를 진실원천으로 두고 저장이 끝난 뒤에 전파합니다. 브로드캐스트를 먼저 하고 저장을 나중에 하면 전파는 성공했는데 저장이 실패하는 경우가 생기고, 그러면 클라이언트 화면에는 있지만 서버에는 없는 메시지가 만들어집니다. 순서를 뒤집는 것만으로 그 종류의 유실이 사라집니다.

나머지 결정들도 각각 하나의 문제에 대응합니다.

| 결정 | 무엇 | 어떤 문제를 막나 |
| --- | --- | --- |
| 메시지 ID = UUIDv7 (클라 생성) | 시간순 정렬 가능한 UUID | at-least-once 중복 전달을 dedup 키로 흡수, 클라 정렬 보정 |
| Redpanda 파티션 키 = `group_id` | 같은 방은 같은 파티션 | 다중 서버 환경의 방 단위 순서 역전 |
| 인증 = 메인 API와 JWT 서명 키 공유 | 채팅 서비스가 자체 검증 | 매 프레임 메인 API 왕복. 멤버십만 조회 후 Redis 캐시 |
| Presence = deviceID 단위 | 유저 단위가 아니라 기기 단위 | 멀티디바이스에서 한 기기 접속이 다른 기기를 덮는 문제 |

Redpanda를 고른 이유도 적어둡니다. Kafka 와이어 호환이라 나중에 관리형 Kafka로 옮길 때 **spring-kafka 코드는 그대로 두고 엔드포인트만 교체**할 수 있습니다. 지금 단계에서 MQ 경로를 미리 깔아둔 비용이 그 시점에 회수되는 구조입니다.

그리고 persist-first가 공짜가 아니라는 점은 분명히 해둡니다. DB INSERT와 MQ publish 사이에는 원자성이 없습니다. INSERT는 성공했는데 publish가 실패하면 저장은 됐지만 아무에게도 안 간 메시지가 남습니다. 정석은 Transactional Outbox(같은 트랜잭션에 outbox 행을 남기고 릴레이가 발행)이거나 CDC입니다. 지금 규모에서는 publish 실패 시 재시도와 폴링 보정으로 시작했고, Outbox 도입 시점은 열린 질문으로 남겨뒀습니다.

## 배선하며 걸린 것들

설계 말고 실제 코드에서 시간을 뺏긴 것 두 개를 기록합니다.

**첫째, WebSocket 인증은 두 층입니다.** 통합 테스트에서 연결이 `DeploymentException`으로 실패했는데, 범인은 HTTP 서블릿 필터였습니다. WS 연결은 2단계로 일어납니다.

```text
1) HTTP 핸드셰이크: GET /ws (Upgrade: websocket)   ← 평범한 HTTP 요청
2) STOMP CONNECT 프레임 (Authorization: Bearer …)  ← JWT는 여기에 있다
```

JWT는 ②에 실리고 ①에는 없습니다. 그런데 `JwtAuthFilter`가 ①까지 가로채서 "토큰 없음 → 401"을 내고, 핸드셰이크가 실패해 연결 자체가 안 됩니다. 해결은 `/ws`를 HTTP 필터 화이트리스트에 넣는 것입니다. 인증 책임을 층별로 나누면 이렇게 됩니다.

| 층 | 담당 | 하는 일 |
| --- | --- | --- |
| HTTP 핸드셰이크 `/ws` | `JwtAuthFilter` (화이트리스트) | 인증 안 함 |
| STOMP CONNECT | `StompAuthChannelInterceptor` | JWT 검증 후 `setUser` |
| STOMP SUBSCRIBE | 같은 인터셉터 | `getUser`로 신원 꺼내 멤버십 인가 |

STOMP 쪽 배선은 `clientInboundChannel`에 `ChannelInterceptor`를 걸어서 합니다. HTTP의 서블릿 필터와 같은 자리인데 대상이 STOMP 프레임입니다. 여기서 배운 게 하나 더 있습니다. **`accessor`는 프레임마다 새로 만들어지는 로컬 래퍼지만, `setUser`가 저장하는 곳은 WS 세션입니다.** CONNECT에서 한 번 `setUser`를 해두면 Spring이 같은 연결의 이후 프레임마다 그 Principal을 다시 실어줍니다. 그래서 **CONNECT는 인증(연결당 1회), SUBSCRIBE는 인가**로 역할이 갈립니다. HTTP 필터가 매 요청 검증하는 것과 다른 리듬입니다.

**둘째, MQ 경로만 직렬화에서 터졌습니다.** `ChatMessageEvent`(record, `Instant sentAt` 포함)를 Redpanda로 보내려는데 `InvalidDefinitionException: Java 8 date/time type java.time.Instant not supported by default`가 났습니다. 그런데 STOMP 응답 DTO는 똑같이 `Instant`를 갖는데도 멀쩡했습니다. 왜 MQ만인가.

원인은 클래스패스에 Jackson이 두 버전 있는 것이었습니다.

| 쓰는 곳 | Jackson | 네임스페이스 |
| --- | --- | --- |
| spring-kafka의 `JsonSerializer`/`JsonDeserializer` | 2.x | `com.fasterxml.jackson.*` |
| Spring Boot 4 웹·STOMP 메시지 컨버터 | 3.x | `tools.jackson.*` |

`JsonSerializer`는 Boot이 구성한 `ObjectMapper`를 쓰지 않고 자기만의 Jackson 2 `ObjectMapper`를 새로 만듭니다. 그 `ObjectMapper`는 클래스패스의 알려진 모듈을 자동 등록하는데, `java.time` 지원은 **Jackson 2용 jsr310 모듈**이 있어야 합니다. Boot 4는 Jackson 3 jsr310만 들고 오니 MQ 경로만 비어 있었던 것입니다.

선택지는 세 개였고 저는 A를 골랐습니다.

```java
// A. 페이로드에서 java.time 제거 — epoch millis(long)
public record ChatMessageEvent(UUID messageId, Long groupId, Long senderId,
                               String content, long sentAt, UUID clientMessageId) { }
// 되돌릴 때: Instant.ofEpochMilli(event.sentAt())
```

B는 Jackson 2 jsr310 의존을 하나 더 추가하는 것, C는 `ProducerFactory`에 커스텀 `ObjectMapper`를 주입하는 것입니다. A를 고른 이유는 직렬화 모듈 의존이 0이 되는 것도 있지만, **MQ 계약을 특정 JVM 시간 타입에 묶지 않는 편이 언어중립적**이기 때문입니다. 여기서 얻은 일반화는 이겁니다. **"어디서는 되고 어디서는 안 됨"은 대개 `ObjectMapper`가 서로 다른 인스턴스거나 다른 버전이라서 그렇습니다.** Boot 자동설정 `ObjectMapper`와 라이브러리 내부 `ObjectMapper`는 같은 것이 아닙니다.

## 아직 안 푼 것

미해결을 해결처럼 적지 않기 위해 남겨둡니다.

- **순서 보장**: 파티션 키를 `group_id`로 잡아 방 단위 순서의 근거는 만들었지만, 재접속·재전송이 섞였을 때 클라이언트가 보는 최종 순서까지 검증하지는 못했습니다. 지금은 UUIDv7의 시간순 성질에 정렬 보정을 의존하고 있습니다.
- **오프라인 동기화**: 재접속 시 `last_read` 기준 미수신 메시지 동기화와 FCM 푸시는 설계만 있고 구현 전입니다.
- **cross-instance 릴레이**: 현재 LocalRelay는 자기 로컬 구독자만 압니다. 인스턴스가 2대가 되는 순간 다른 서버 접속자에게 전달이 안 됩니다. 다음 단계는 `ws:instance:{id}` 채널을 쓰는 RedisRelay이고, 방 단위 채널 구독과 어느 쪽이 나은지는 아직 판단이 서지 않았습니다.
- **Outbox 도입 시점**: 지금 규모에서 publish 실패 재시도로 충분한지, 아니면 이미 Outbox가 필요한지의 경계를 못 그었습니다.

마지막으로, 이 노트를 쓰면서 가장 쓸모 있었던 습관을 적어둡니다. 단계마다 "이 구조의 한계"를 한 문장으로 쓸 수 있는지 확인하는 것입니다. 그 문장이 안 나오면 다음 단계로 갈 근거가 없다는 뜻이고, 그건 보통 아직 그 구조에 머물러야 한다는 신호였습니다.
