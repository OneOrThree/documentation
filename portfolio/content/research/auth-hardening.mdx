우리 팀의 백엔드 인증은 Spring Security 없이 **수제 `JwtFilter` 한 장 + 소셜 로그인 6종**으로 서 있습니다. 처음에는 "동작하는 인증"이었고, 그 뒤로는 계속 "구조적으로 안전한 인가"와의 거리를 좁히는 작업이었습니다. 이 노트는 그 거리를 좁히면서 실제로 밟은 함정과, 각 수선이 무엇을 얼마나 바꿨는지의 실측을 남깁니다.

먼저 결론 셋입니다.

1. 사전 검사는 동시 요청에 반드시 뚫립니다. 최종 방어선은 DB 유니크 제약이고, 위반 예외는 **의미별로** 처리해야 합니다.
2. 유니크 제약을 하나 추가하면 그 테이블에 INSERT하는 **모든 경로의 예외 처리 전제**가 바뀝니다. 이걸 몰라서 가입이 영구 차단되는 회귀를 만들었습니다.
3. 상태(DB)만으로 구분되지 않는 두 시나리오는 **발급 시점의 신호**로 구분해야 합니다.

## 출발점 — 필터 한 장 위에 쌓인 여섯 개의 발급 경로

카카오 단독 로그인에서 시작해 Google, Line, Instagram, Meta, Apple, 그리고 게스트까지 발급 경로가 늘었습니다. 소셜 클라이언트는 두 계열로 갈립니다.

| 계열 | 제공자 | 검증 방식 | 외부 왕복 |
| --- | --- | --- | --- |
| JWKS형 | Apple · Google · Facebook | `id_token`을 IdP 공개키로 **자체 검증** (서명 + iss + aud) | JWKS 조회 1회 |
| API형 | Kakao · Line · Instagram | 받은 토큰으로 IdP 프로필 API를 호출해 **위임 검증** | 프로필 API 1회 |

두 계열은 `Map<Provider, SocialLoginClient>` 전략 주입으로 갈라집니다. Apple 계열의 실제 검증 순서는 이렇습니다. 토큰 헤더에서 `kid` 추출 → JWKS 조회 후 `kid` 매칭 → `n`/`e`로 RSA 공개키 복원 → 서명 검증 → `aud`·`iss` 검증 → `sub` 반환.

여기서 발급 경로가 늘 때마다 새 구멍이 생긴 지점이 **필터의 화이트리스트**였습니다. `JwtFilter`는 `FilterRegistrationBean`으로 `/api/*`에 order 1로 걸리고, 인증 없이 통과할 경로를 `startsWith` 매칭으로 걸러냅니다. 소셜 6종 엔드포인트, `/auth/guest`, `/auth/refresh`가 화이트리스트에 들어가고 `/auth/logout`은 들어가지 않습니다(로그아웃에는 유효한 access 토큰이 필요합니다). 문제는 이 구조가 **deny-by-default가 아니라 허용이 기본에 가깝다**는 것입니다. 새 로그인 제공자를 붙일 때마다 화이트리스트를 손으로 늘려야 했고, 프리픽스만 겹치면 의도치 않은 경로가 열릴 여지가 남습니다. 인증 주체 전달도 `request.setAttribute("userId")`라는 **문자열 컨벤션**이라, 컨트롤러가 규칙을 어기고 요청 파라미터의 id를 그대로 신뢰해도 컴파일러가 잡아주지 못합니다.

## 검증은 서명만으로 끝나지 않는다

초기 JWKS 클라이언트는 **서명만 검증**했습니다. 서명이 유효하면 `sub`를 신뢰하고 넘어갔습니다. 코드 리뷰에서 지적을 받고 나서야 이게 결함이라는 걸 알았습니다. Apple이 발급한 정상 토큰이라도 **다른 앱을 audience로 발급된 토큰**이면 우리 서비스에서는 거부해야 하는데, 서명만 보면 그게 통과합니다. `iss`와 `aud`(bundle id) 검증을 추가해 닫았습니다.

이 결함의 뿌리는 프로토콜 역사에 있었습니다. OAuth 2.0은 위임 **인가** 프로토콜이라 access token으로 신원을 확인하면 audience 혼동이 생기고, OIDC가 `id_token`의 표준 클레임(`iss`/`aud`/`sub`)과 JWKS 공개키 배포로 인증을 표준화했습니다. 즉 **검증 규칙 전수를 지키는 책임이 토큰을 받는 서버 쪽에 있습니다.** 공개키로 누구나 검증할 수 있다는 편의의 대가입니다.

같은 계열에서 아직 남겨둔 것도 기록해 둡니다. JWKS 캐싱이 없어 로그인마다 IdP를 왕복하고(3사 동일), `kid` 미스는 재조회 없이 즉시 예외입니다. 키 롤테이션을 우연히 견디는 구조라, 캐싱과 `kid` 미스 시 재조회는 개선 과제로 남아 있습니다.

## 유니크 제약은 예외 계약의 변경이다

여기가 이 노트의 중심입니다. 두 개의 티켓(GROMO-581, GROMO-584)을 같은 패턴으로 함께 처리했고(PR #111), 그 조합이 만든 회귀를 리뷰가 잡았습니다.

### 문제 1 — 동시 첫 로그인이 계정을 둘로 만든다

같은 소셜 계정으로 두 요청이 동시에 최초 로그인하면, 사전 조회(`findByProviderAndProviderId`)가 **둘 다 "없음"**을 보고 각자 User와 SocialAccount 생성을 시도합니다. 조회와 생성 사이의 갭, 전형적인 TOCTOU입니다. DB 제약이 없던 시점에는 중복 계정 row가 실제로 가능했습니다.

방어선을 두 층으로 깔았습니다.

- `social_accounts(provider, provider_id)`에 **전체 유니크 제약**. 방어이면서 조회 인덱스를 겸합니다. 여기서 한 가지 결정이 있었습니다 — `deleted_at`을 포함한 부분 유니크로 만들지 않았습니다. soft-delete된 row와도 충돌해야, 로그인 시 `deletedAt`을 null로 되돌려 재활성화하는 로직이 성립하기 때문입니다.
- 위반 예외를 **트랜잭션 밖에서** 잡습니다. 유니크 위반은 flush/커밋 시점에 나므로 `@Transactional` 메서드 내부의 try-catch로는 잡을 수 없습니다. 그래서 `socialLogin`을 `@Transactional(NOT_SUPPORTED)`로 트랜잭션 밖에 두고, self 프록시(순환 주입을 피하려 `@Lazy`)로 `loginOrRegister`를 **새 트랜잭션**으로 호출했습니다.

핵심은 재시도의 형태입니다. 무한 재시도도, 500 응답도 아니라 **1회 재시도**입니다.

```java
// 개념 골격: 검증·외부 호출은 트랜잭션 밖, 쓰기만 새 트랜잭션
try {
    return self.loginOrRegister(provider, providerId, ...);
} catch (DataIntegrityViolationException e) {
    // 경쟁 승자가 이미 계정을 만들었다 → 재시도하면 present 분기로 들어간다
    return self.loginOrRegister(provider, providerId, ...);
}
```

재시도 시점에는 경쟁 승자가 만든 계정이 보이므로 "이미 있음" 분기로 들어가 **경쟁 패자도 정상 로그인**합니다. 사용자 눈에는 아무 일도 없고, 500이 나지 않습니다.

### 문제 2 — 닉네임 유니크가 재시도의 전제를 깨다

같은 PR에서 닉네임도 함께 잠갔습니다. `users.nickname` 전체 유니크 + `existsByNicknameAndIdNot` 사전 검사(본인 닉네임 재사용은 허용) → 중복이면 409, 사전 검사를 뚫은 레이스는 전역 핸들러에서 409로 폴백, 온보딩 요청에 `@NotBlank`로 닉네임 필수화. 컬럼은 nullable이지만 Postgres가 다중 NULL을 허용하므로 게스트와 온보딩 전 유저에게는 무해했습니다.

그런데 이 제약이 방금 만든 재시도 로직과 충돌했습니다. Apple 로그인에는 `fullName`을 닉네임으로 프리필하는 코드가 남아 있었습니다. 그래서 **동명이인이 첫 로그인하면** 이렇게 됩니다.

```text
가입 INSERT → nickname 유니크 위반 (DataIntegrityViolationException)
  → socialLogin이 이를 "소셜 계정 경쟁"으로 오인 → 1회 재시도
    → 이름이 같으니 또 nickname 위반 → 409
      → 그 이름을 가진 사용자는 가입이 영구 차단
```

원인은 예외 처리의 **전제**였습니다. 재시도 로직은 "이 경로에서 나는 DIVE = `(provider, provider_id)` 위반"이라고 가정했는데, 새 유니크 제약이 **같은 예외 타입의 다른 원인**을 추가하면서 그 가정이 조용히 깨졌습니다. 예외를 원인 구분 없이 잡아 복구하는 코드는 제약이 늘어날 때마다 전제를 다시 물어야 합니다.

고친 방식은 예외 분기를 정교하게 만드는 쪽이 아니었습니다. **Apple fullName 프리필을 원천 제거**했습니다. `socialLogin`/`loginOrRegister`의 nickname 파라미터와 컨트롤러의 fullName 전달을 삭제했습니다. 닉네임은 어차피 온보딩에서 필수로 받으므로 프리필은 필요가 없었고, 가입 경로가 nickname을 아예 세팅하지 않으니 **그 경로의 DIVE는 다시 `(provider, provider_id)` 위반뿐**이라는 가정이 견고해집니다. 예외의 원인을 파싱해서 갈라내는 대신, 원인이 하나만 남도록 경로를 좁힌 것입니다. 참고로 iOS의 `fullName`은 최초 로그인에서만 채워지고 이후에는 nil이라, 프리필을 남겨두는 것이 값 자체로도 신뢰할 만한 소스가 아니었습니다.

전역 핸들러의 DIVE→409 폴백에는 warn 로깅을 붙였습니다. 전역 폴백이 FK나 NOT NULL 위반 같은 실제 버그를 조용히 삼키지 않게, 모니터링에서 구분되게 만들려는 목적입니다.

검증은 JPA 바깥 층에서 고정했습니다. Testcontainers로 실제 DB에 중복 insert를 넣어 정말로 DIVE가 나는지, null 다중 허용이 성립하는지 확인했고, Apple 케이스는 "닉네임을 저장하지 않는다"를 단언으로 박아 프리필이 부활하면 테스트가 깨지게 했습니다.

한 가지 배포 함정도 남깁니다. 우리는 이 제약을 **엔티티 선언으로만** 반영했는데, 스키마 검증만 하는 환경에서는 엔티티의 유니크 선언이 실 DB를 바꾸지 않습니다. 즉 **실 DB에 제약이 없으면 위 폴백 전체가 무의미**합니다. 그리고 기존 데이터에 닉네임 중복이 있으면 제약 생성 자체가 실패합니다. 배포 전에 중복 존재 여부와 제약 존재 여부를 확인해야 합니다.

## 토큰의 유출 표면과 사용 범위를 따로 닫는다

토큰 레이어는 한동안 그대로였습니다. 두 결함이 있었고, 서로 **다른 축**이라 하나로는 닫히지 않았습니다(PR #347, GROMO-713·714).

| 결함 | 축 | 무엇이 가능했나 | 수선 |
| --- | --- | --- | --- |
| RT 평문 저장 | 유출 표면 | DB 덤프·백업·인젝션으로 읽히면 그 자체가 장기 자격증명. 쿼리 로그에도 원본이 남음 | SHA-256 해시 저장 + 해시로 조회 |
| access/refresh 무구분 | 사용 범위 | 두 토큰이 같은 키·subject로 발급되고 만료만 달라, 필터가 서명·만료만 보면 **긴 수명의 RT가 모든 `/api/*`를 직접 인증** | `type` 클레임 발급 + 검증 지점별 용도 확인 |

714만 해도 DB 유출 시 평문 RT로 refresh를 호출해 access를 무한 발급할 수 있고, 713만 해도 RT가 API를 직접 타는 건 그대로입니다. 그래서 함께 닫았습니다. 구현에서 배운 디테일들입니다.

- RT는 서버가 발급하는 고엔트로피 랜덤이므로 salt나 스트레칭 없이 단순 SHA-256으로 충분합니다. 저엔트로피인 비밀번호와 다릅니다. 저장 2곳(소셜·게스트)과 조회 2곳(refresh·logout)이 **모두 같은 변환을 경유**하게 만들었습니다.
- 테스트에서 "저장된 값이 원본이 아니라 해시인지"를 단언했습니다. 필드 이름은 `Hash`인데 값은 원본이 들어가는 유형의 버그는 컴파일러가 절대 못 잡습니다.
- 필터의 타입 가드는 상수를 왼쪽에 두어, `type` 클레임이 없는 구 토큰(null)도 NPE 없이 **fail-closed로 거부**되게 했습니다.
- 가드를 `try` 블록 **안**에 둬야 합니다. 클레임 추출이 만료·서명 오류에 던지는 예외가 밖에 있으면 500이 되고, 안에 있으면 401로 변환됩니다.
- 게스트→소셜 승격 경로의 헤더 파싱은 **의도적으로 타입 가드에서 제외**했습니다. 게스트는 자기 access 토큰을 헤더로 보내므로 refresh 타입을 요구하면 그 경로가 깨집니다.
- 컬럼은 마이그레이션으로 `refresh_token` → `refresh_token_hash`로 rename했습니다. 담는 값이 원본에서 해시로 바뀌었으니 이름도 정정해야 합니다. SHA-256 hex는 64자라 길이 변경은 불필요했습니다.

가장 큰 결정은 **컷오버 방식**이었습니다. 기존 평문 RT는 해시 조회에 매칭되지 않고, 기존 access 토큰에는 `type` 클레임이 없어 거부됩니다. 즉 배포 순간 **전 유저 세션이 무효화되어 재로그인 1회**가 필요합니다. 백필로 부드럽게 넘길 수도 있었지만, 보안 티켓에 forward-only 정책을 적용해 의도된 fail-closed 컷오버로 수용했습니다. 관련 테스트 89건으로 잠갔습니다.

이 PR은 스스로 남긴 부채도 명시했습니다. 필터에서 토큰 파싱이 유효성 검사·타입 추출·userId 추출로 3회 발생합니다. 인증 hot path인 걸 알면서도 기존 구조를 따랐고, 최적화를 별도 티켓으로 넘겼습니다.

## 인증 hot path는 왕복으로 센다

필터에는 부가 로직이 두 개 얹혀 있었습니다. 탈퇴 유저 차단(서명이 유효한 access 토큰이라도 매 요청 최종 차단)과 마지막 활동 시각 갱신입니다. 둘 다 각자 DB를 건드려 **요청당 왕복이 2회**였습니다.

원래 티켓의 안은 인메모리 캐시와 비동기 큐였습니다. 채택하지 않았습니다. 탈퇴 차단 조회가 이미 매 요청 `users`를 PK로 읽고 있으므로, **그 쿼리에 `last_active_at`을 얹으면** 스로틀 판정이 왕복을 늘리지 않고 끝납니다. 이 방식 위에서 캐시가 추가로 벌어주는 왕복은 0인데, 서버 상태(무한 성장·인스턴스 불일치·재시작 소실)만 생깁니다.

`existsByIdAndIsDeletedFalse`를 `findLastActiveAtIfActive`로 바꿨습니다. 반환이 empty인 집합(없는 유저 또는 soft delete)이 기존 exists가 false이던 집합과 **정확히 동일**하므로 401 신호는 불변입니다. 판정은 트랜잭션 없는 순수 함수로 분리하고, 갱신이 필요할 때만 트랜잭션에 진입합니다. 판정을 `@Transactional` 메서드 안에 두면 갱신이 불필요한 요청에서도 트랜잭션이 열려 절약분이 사라지고, 같은 클래스에서 내부 호출하면 self-invocation이라 프록시를 타지 않아 애초에 트랜잭션이 걸리지도 않습니다.

같은 토큰으로 연속 3요청을 던져 SQL을 세어봤습니다.

| | before | after |
| --- | --- | --- |
| 총 쿼리 | **6** | **3** |
| SELECT | 3 (exists) | 3 (단일 조회) |
| UPDATE | 3 (전부 0건 매치) | **0** |

after에서 나가는 SQL은 이 하나뿐입니다.

```sql
select u1_0.last_active_at from users u1_0 where u1_0.id=? and u1_0.is_deleted=false
```

측정 절차도 남깁니다. 던져버리는 `postgres:16-alpine`으로 로컬 프로필을 띄우고, 게스트 로그인으로 토큰을 받은 뒤 **존재하지 않는 경로**(404)로 3요청을 보냈습니다. 필터는 타면서 컨트롤러 쿼리가 섞이지 않는 지점을 고른 것입니다. 같은 절차를 기준 브랜치에서 반복해 대조했습니다. 왕복 2→1은 산술적으로 자명하므로 부하 테스트 대신 이 쿼리 카운트 증명과 회귀 테스트로 대체했습니다.

같이 바꾼 것이 하나 더 있습니다. 스로틀 경계가 **KST 자정 하드코딩**이었는데, 슬라이딩 2시간 창으로 전환했습니다. 글로벌 서비스에서 특정 국가의 자정을 전 유저의 하루 경계로 쓸 수 없고, 저장소에는 이미 "유저 존 로컬 날짜" 컨벤션이 있었는데 이 클래스만 그 밖에 남아 있었습니다. 스로틀은 "얼마나 자주 쓸까"의 문제라, "어느 날에 속하나"(소비자 관심사)와 분리했습니다.

이 변경은 인증 계약은 건드리지 않지만 **데이터 계약을 바꿉니다.** `last_active_at`이 실제 마지막 활동보다 최대 창 길이(2시간)만큼 과거일 수 있어, 자정 직후 2시간 안에 그날 첫 활동을 한 유저는 값이 전날로 남고 미접속 복귀 푸시의 "정확히 N일째" 판정이 하루 당겨집니다. 창 길이 선택이 곧 오차율 선택이라는 걸 인지하고 2시간으로 정했고, 자정을 넘겨도 창 안이면 쓰지 않는다는 동작을 테스트로 고정했습니다. 전체 794건 통과.

## 상태로 구분되지 않는 것은 발급 시점 신호로 구분한다

마지막은 리뷰가 발견한 구멍입니다(PR #518, GROMO-1229). 같은 게스트 계정으로 **두 기기가 서로 다른 소셜에 동시 로그인**하면, 진 요청이 신규 가입 폴백으로 빠져 닉네임이 null인 빈 계정을 조용히 만들었습니다. 에러는 없습니다. 응답은 신규 유저라고 알려주고 온보딩으로 진입하며, 사용자는 자기 게스트 데이터를 전부 잃은 빈 계정에 로그인됩니다.

선행 PR의 락은 정확히 걸립니다. 문제는 진 요청이 락 해제 후 조건을 재평가할 때 `is_guest=false`를 보고 빈 결과를 얻는데, **이 상태가 정식 계정 전환**(비게스트 토큰으로 새 소셜에 로그인하는 정상 시나리오)**과 DB만으로는 100% 동일**하다는 것입니다. 상태로는 구분이 불가능합니다.

그래서 **발급 시점의 신호**를 썼습니다. 게스트 발급 경로의 토큰에 `guest=true`를 탑재하고, 소셜·승격 후 발급은 false, refresh 재발급은 재발급 시점의 유저 상태를 따릅니다. 신규 가입 폴백에 진입하기 직전에 세 조건이 모두 참이면 패자로 판별하고 409(이미 다른 계정으로 승격된 게스트)를 내려 유령 계정 생성을 차단합니다.

```text
클레임 guest=true  ∧  게스트 락 조회 결과 empty  ∧  활성 비게스트로 존재
```

판별 조회는 **일부러 락을 걸지 않았습니다.** 락을 걸면 `users` 두 행을 잠그게 되어 선행 PR에서 세운 교착 방지 논증("어떤 로그인도 `users` 한 행만 잠근다")이 깨집니다.

이 판별이 기존 계약을 침해하지 않는지도 확인했습니다. 클레임이 없는 구 토큰은 null(비게스트 간주)로 기존 폴백을 유지하는데, 이건 앞서 `type` 클레임을 점진 적용한 선례와 같은 형태입니다. 탈퇴한 게스트의 유효 토큰은 그대로 신규 가입(의도된 계약), 같은 소셜로의 동시 재시도는 앞서 만든 DIVE 재시도로 승격 계정에 정상 로그인, 계정 전환은 영향 없음 — 셋 모두 기존 계약 테스트로 잠갔습니다.

증명은 동시성 통합 테스트로 했습니다. `CyclicBarrier`로 두 요청을 같은 순간에 출발시키고 **`users` 행 수 불변 · 정확히 1승 1패 · `social_accounts` 1건**을 단언했습니다. 동시성 버그는 "고쳤다"가 아니라 "동시에 실행해서 이 숫자가 나온다"로만 증명됩니다.

### 남은 것

- `refresh_tokens` 테이블 분리와 RT rotation·재사용 감지. 지금은 유저 테이블의 단일 컬럼이라 새 로그인이 이전 기기의 RT를 덮어써 멀티디바이스가 불가능하고, refresh는 access만 재발급하는 비회전입니다.
- Spring Security 필터체인 도입과 인증 주체 주입의 타입 강제. `startsWith` 화이트리스트를 정확 매칭 + "명시적으로 열지 않으면 잠금"으로 뒤집고, request attribute 컨벤션을 어노테이션 주입으로 바꾸는 일입니다. 부가 로직(탈퇴 차단·활동 갱신)을 어디로 옮길지가 결정 사항으로 남아 있습니다.
- JWKS 캐싱과 `kid` 미스 시 재조회.
