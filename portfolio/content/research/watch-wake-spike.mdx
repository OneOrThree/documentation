결론부터 적습니다. 애플워치 컴패니언 PRD 의 리스크 표에 있던 「폰 앱을 스와이프 강제종료해 두면 WCSession 이 앱을 재기동하지 못한다」는 항목은 **실측으로 반박됐고 취소선으로 남겼습니다.** 2026-08-18 실기기(Apple Watch SE 2·watchOS 10.6.2 + iPhone 16 Pro Max) 측정 결과입니다.

| 시나리오 | RTT | wake | 실패 | 해석 |
| --- | --- | --- | --- | --- |
| ① 포그라운드 | ~200ms | — | 0 | 기준선 — 채널 자체는 빠름 |
| ② 백그라운드(수 분 방치) | ~200ms | ~999,999ms(≈16분) | 0 | wake 가 크다 = **기존 프로세스가 그대로 응답**, 재기동 없이 잠든 앱이 즉시 깨어남 |
| ③ 강제종료 | ~200ms | ~178,450ms(≈3분) | 0 | **강제종료에도 iOS 가 앱을 백그라운드 재기동** — 첫 탭 때 새로 뜬 프로세스가 이후 탭까지 산 시간으로 보임 |
| JS 적재 | 「전부 미적재」 | | | **스파이크 측정 버그** — RN 0.86 브리지리스에서 구식 알림 `RCTJavaScriptDidLoad` 가 발화하지 않음. JS 부팅 시간만 미측정으로 남음 |

리스크 하나가 지워진 대신 측정 도구의 결함 하나가 드러났고, 그 미측정은 PRD 의 페이즈 0 종료 게이트(ⓔ)가 됐습니다. 아래는 PRD 가 어떻게 이 스파이크를 맨 앞에 두게 됐는지, 그리고 20라운드 리뷰에서 무엇이 뒤집혔는지입니다.

## 1. 제약 셋이 PRD 의 뼈대를 정했다

PRD 를 쓰기 전에 현행 코드를 조사했고, 08-17 22:56 에 세 가지 제약이 나왔습니다. 이 셋이 이후 결정 15건의 출발점입니다.

| 제약 | 사실 | PRD 에 미친 영향 |
| --- | --- | --- |
| ① 경과시간은 서버에 없다 | 전부 폰 로컬 틱 | 미러링은 폰↔워치 직접 채널이 필요 — 워치가 서버를 볼 이유가 없음 |
| ② 스크린타임 실드는 폰 앱 프로세스 전용 | 워치 단독 시작은 「실드 없는 세션」 문제 | 워치 발 시작은 결국 폰을 깨워야 성립 — **폰 wake 가 핵심 가설** |
| ③ 세션 로직 전체가 화면 컴포넌트 소유 | `FocusSessionScreen` 1,792줄 | 헤드리스화 선행 필요(D2) |

이 위에서 plan-ceo-review 를 3차까지 돌렸고 23:40 에 「최종 9.0/10, policy.md 착수 가능」 판정을 받았습니다. 23:48 미결을 제 의견대로 닫아 `docs/prd/apple-watch/policy.md` 에 **D1~D15 를 플랫 로그**로 확정했습니다. 각 결정에 근거와 「뒤집을 신호」를 달았는데, 이 문서에서 중요한 것은 두 개입니다.

- **D1 폰 릴레이 리모컨** — 워치는 리모컨+디스플레이, SoT 는 폰, 1차 백엔드 변경 0. 뒤집을 신호는 「워치 세션 완료율이 폰 발 대비 유의미하게 낮으면(폰 깨우기 신뢰성 한계)」.
- **D3 출시 순서** — codex 가 「순서가 거꾸로다(보급률을 재기 전에 최대 리팩토링부터 시작)」는 이견(M1)을 냈고, 절충안으로 **페이즈 0 = ⓐ 실기기 wake 스파이크 + ⓑ Live Activity 정확도 수리 + ⓒ 보급률 계측 + ⓓ 특성화·헤드리스화**를 맨 앞에 뒀습니다. 뒤집을 신호는 「ⓐ 에서 wake 성립률·지연이 수용 불가로 나오면 페이즈 1 전에 D1 재검토」.

즉 D1 이 옳은지는 D3-ⓐ 가 답합니다. 같은 턴에서 codex 의 두 번째 이견(M2)대로 홈 위젯·Siri 인텐트(R14·R15)를 `docs/prd/entry-points/prd.md` 로 분리하고 PRD 에는 취소선만 남겼습니다(D4).

## 2. 폐기 전제의 측정 도구

08-18 03:59 에 `GromoWatch` 워치 타겟과 `SpikeWatchWakeResponder.swift`(폰 쪽 응답기), `SpikeView.swift`(워치 쪽 탭 UI)를 만들었습니다. 커밋 제목에 **「(폐기 전제)」** 를 박았고, 실제로 이 커밋은 브랜치 `afeat/GROMO-1596-watch-wake-spike` 에만 있고 main 에는 들어가지 않았습니다. 워치 앱 타겟을 제품 코드로 남기면 페이즈 1 의 설계가 스파이크 코드의 모양에 끌려가기 때문입니다 — 스파이크가 답할 질문은 「폰이 깨어나는가」 하나뿐이고, 답이 나오면 도구는 버립니다.

측정은 D14(QA 는 실물 Apple Watch 로) 그대로 실기기에서 했습니다. 시뮬레이터는 WCSession wake 와 force-quit 거동을 실기기와 다르게 재현하므로 여기서는 쓸모가 없습니다.

## 3. 실측이 리스크를 지웠고, 측정 버그가 게이트를 만들었다

13:38 결과가 들어왔습니다. 앞의 표가 그것입니다. 해석에서 조심한 것 둘입니다.

첫째, **②③의 wake 값은 「재기동에 걸린 시간」이 아닙니다.** 백그라운드 ≈16분은 앱이 죽지 않고 그대로 있다가 즉시 응답했다는 뜻이고, 강제종료 ≈3분은 첫 탭 때 iOS 가 새로 띄운 프로세스가 이후 탭까지 살아 있던 시간으로 읽힙니다. 핵심은 세 상태 모두 응답이 성립했다는 것이지 숫자의 크기가 아닙니다. PRD §7 에는 리스크 항목에 취소선을 긋고 「실측으로 반박됨」을 적되, **표본이 기기 1대·1회차**라 저전력 모드·저장공간 부족 같은 변수는 남는다고 병기했고 §5 의 성립률 계측은 유지했습니다.

둘째, **JS 적재 「전부 미적재」는 앱이 아니라 도구가 틀린 것입니다.** 응답기가 `RCTJavaScriptDidLoad` 알림을 관측하고 있었는데, RN 0.86 은 브리지리스(신 아키텍처)라 이 구식 알림이 발화하지 않습니다. 폰 앱 JS 가 정상 동작 중이라는 것은 측정 중에 앱을 쓴 것 자체가 증거였습니다. 그래서 「JS 부팅 시간 미측정」으로 정직하게 남겼습니다.

이 미측정을 처음에는 페이즈 1 재측정으로 미뤄 뒀는데, codex 5차 리뷰(19:24)가 잡았습니다 — 네이티브 wake·RTT 만으로는 S-2(폰 엔진이 워치 타임아웃 안에 부팅해 실드·마커를 처리한다)를 검증하지 못하므로, 그 상태로 워치 코어에 들어가면 핵심 가설이 미검증인 채입니다. D3 를 개정해 **ⓔ 「명령 발신→JS 엔진 처리 완료」 실측을 페이즈 0 종료 게이트**로 추가했습니다. 헤드리스 엔진(ⓓ) 완성 직후 재고, 실패하면 네이티브 선실드 최적화·D1 재검토로 돌아갑니다.

<Callout label="측정이 바꾼 것" tone="primary">
리스크 표에서 한 줄이 취소선이 되고(강제종료 재기동), 페이즈 0 에 게이트가 하나 늘었습니다(ⓔ JS 기동). 둘 다 스파이크 이전의 PRD 에는 없던 문장입니다.
</Callout>

세 가지가 눈에 띕니다.

- **D13 킬스위치는 세 번 개정됐습니다.** 원안 「OTA 배포 가능한 JS 플래그」는 콜드 스타트가 매번 최신 OTA 로 뜬다는 전제 위에 있었는데, 실제로는 내장·캐시 번들로 먼저 부팅한 뒤에야 업데이트를 확인하므로 킬스위치 배포 직후 깨어난 폰은 구 번들이 첫 명령을 처리할 수 있습니다. 그래서 App Group 네이티브 플래그를 정본으로, 네이티브 인박스가 수신 시점에 평가하도록 바꿨고, 3차 개정에서 차단 대상을 `start` 로 한정했습니다 — 전체 차단은 대기 중인 `end` 까지 막아 폰 세션·실드를 못 닫게 가두는 모순이 있었습니다.
- **D10 은 없는 기능을 전제로 한 보장이었습니다.** 「잘못 붙은 과목은 완료 후 수정이 싸다」고 적었는데 완료 세션의 과목을 바꿀 UI 도 서버 API 도 저장소에 없었습니다. 보장을 철회하고 오귀속 대응은 entry-points PRD 의 미결로 넘겼습니다.
- **13·14라운드 지적은 제가 앞 라운드에서 넣은 문장끼리의 충돌이었습니다.** 라운드가 길어질수록 리뷰가 잡는 것은 원안의 결함이 아니라 반영끼리의 정합 공백이었고, 18라운드도 같은 종류였습니다. 20라운드 문서 PR 은 08-12 에 세운 5라운드 하드 스톱 규칙 밖에서 돌았는데, 문서 PR 을 예외로 둔 근거는 로그에 없습니다.

## 5. 부속 PR 과 머지, 그리고 IA 초안

페이즈 0 의 ⓑ·ⓒ 는 별도 PR 로 나갔습니다. #675(GROMO-1598, 08-18 00:01)는 워치 페어링 보급률 계측으로 `isPaired` 를 GA4 사용자 속성으로 싣는 것이고, #677(GROMO-1597, 00:32)은 Live Activity `ContentState` 를 정지·카운트다운·뽀모도로까지 표현하도록 넓힌 것입니다. `isPaired` 는 「워치 앱 설치·지원 watchOS·도달 가능」을 뜻하지 않으므로 PRD §5 에는 보급률의 상한 근사치로만 해석한다고 적었고, 이것이 D8(watchOS 최소 버전) 개정의 근거이기도 합니다 — iOS 공개 API 로는 페어링 워치의 OS 버전을 읽을 수 없어 계측은 「투자할 가치가 있는가」만 답합니다.

## 결론 — 측정 도구를 먼저 의심하되, 측정이 리스크를 반박하면 PRD 를 개정한다

이 스파이크는 부하테스트 설계 때와 같은 계열입니다(/research/loadtest-design). 그때는 표적 가설 3개가 실측으로 전부 틀렸고, 이번에는 리스크 가설 하나가 실측으로 틀렸습니다. 다른 점은 측정 결과 안에 도구의 결함이 섞여 있었다는 것입니다 — 「JS 전부 미적재」를 그대로 믿었으면 PRD 는 「폰 JS 가 백그라운드에서 부팅하지 않는다」는 더 큰 거짓 리스크를 얻었을 것입니다. 앱이 정상 동작한다는 반증이 눈앞에 있었기 때문에 도구를 의심할 수 있었습니다.

남은 규칙 셋입니다.

1. **스파이크는 폐기 전제로 만들고 브랜치에 둔다.** 답할 질문 하나에 맞춰 만들고, 답이 나오면 제품 코드에 섞지 않는다.
2. **측정값이 상식과 어긋나면 도구부터 본다.** RN 브리지리스처럼 런타임이 바뀌면 관측 지점(알림·훅)이 조용히 죽는다.
3. **반박된 리스크는 지우지 말고 취소선과 표본 크기를 남긴다.** 기기 1대·1회차라는 한계와 남은 변수(저전력·저장공간)는 계측 항목으로 이어진다.

아직 안 끝난 것도 적어 둡니다. ⓔ JS 기동 게이트는 헤드리스 엔진이 완성돼야 잴 수 있으므로 이 글의 시점에는 미측정입니다. 게이트가 실패하면 D1(폰 릴레이) 자체를 다시 봅니다.
