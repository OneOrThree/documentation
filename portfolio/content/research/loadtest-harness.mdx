목표는 단순했습니다. 대시보드 버튼 한 번(딸깍)으로 golden DB를 복제하고 부하 VM을 띄우고 k6를 돌린 뒤 판정까지 커밋하는 하네스입니다. 설계는 문서로 정리돼 있었고 코드도 순서대로 나갔습니다. 그런데 실제로 GCP에서 돌리기 시작하자 막는 것은 설계가 아니라 **아무 소리도 내지 않는 실패들**이었습니다.

결론부터 적습니다. 이 하네스를 만드는 동안 시간을 가장 많이 잡아먹은 실패는 전부 "예외도 로그도 없이, 한참 뒤에 간접적으로 발견되는" 종류였습니다. 그래서 하네스 작업의 절반은 기능을 붙이는 일이었고, 나머지 절반은 **조용한 실패를 시끄럽게 바꾸는 게이트를 심는 일**이었습니다.

## 조용한 실패 목록

| 사건 | 겉으로 보인 것 | 실제 원인 |
| --- | --- | --- |
| full seed 소멸 | `focus_sessions` INSERT 중 프로세스가 그냥 사라짐 | IAP ssh 터널 드롭 → 원격 psql이 SIGHUP |
| 검증 숫자 역전 | 포모도로 건수가 상위 테이블보다 많음 | `count(*)`가 아니라 `n_live_tup` 추정치를 읽음 |
| openapi 생성 타임아웃 | `waited for 180 seconds` | 부팅 config yml이 gitignored라 워크트리에 없음 |
| 스택 PR base 증발 | `Base ref must be a branch` | 부모 PR의 squash 머지로 브랜치·SHA 소멸 |
| 직렬 디스패치 | 워크플로가 API 수만큼 반복 실행 | "배치 = 순차"라는 오케스트레이션 편의 |
| verdict INVALID | Prometheus 9090 connection refused | envsubst가 주석 안 변수 표기까지 치환 |
| 인스턴스 생성 실패 | `ZONE_RESOURCE_POOL_EXHAUSTED` | 중지된 VM은 용량을 예약하지 않음 |

아래는 각각을 어떻게 재현하고 무엇으로 확정했는지의 기록입니다. 에러율 96% 사건은 이 하네스가 처음 관통한 뒤 나온 별개의 이야기라 [별도 노트](/research/loadtest-error96)로 넘깁니다.

## 조용히 죽는 시드 — 프로세스를 SSH 수명에서 떼어내기

시드 파이프라인(PR #179)은 차원 테이블을 CSV `\copy`로 넣고 팩트 테이블은 Cloud SQL 안에서 `INSERT ... SELECT generate_series()`로 생성합니다. Cloud SQL이 사설 IP 전용이라 모든 DB 접근은 관측 VM의 IAP ssh를 경유했습니다.

증상은 규모에 따라 갈렸습니다.

| 시드 규모 | `focus_sessions` | 결과 |
| --- | --- | --- |
| `SCALE=0.1` | 300만 | 매번 완주 |
| `SCALE=1` | 3,000만 | INSERT 도중 조용히 소멸 (스택트레이스·에러 없음) |

가설은 셋이었습니다. (a) 단일 대형 트랜잭션의 메모리·WAL 폭발, (b) statement/idle timeout, (c) 원격 SSH 터널 드롭.

먼저 Cloud SQL 서버 로그를 봤습니다. OOM도, crash도, timeout 흔적도 하나도 없었습니다. **서버는 멀쩡히 살아 있었는데 세션만 끊겼다** — 그러면 죽은 주체는 서버가 아니라 클라이언트(psql)입니다. 두 번째 단서가 결정적이었습니다. 데이터가 10배인데 실행 시간은 약 2.5배였고, 실패는 데이터 크기가 아니라 **실행 시간에 비례**했습니다. 장시간 유지되는 터널이 범인이라는 뜻입니다.

psql은 로컬 포그라운드의 `gcloud compute ssh --command=...`에 매여 있었습니다. 터널이 끊기면 원격 psql이 SIGHUP을 받고, 트랜잭션은 롤백되고, 로컬에는 아무 일도 없던 것처럼 보입니다.

해결은 프로세스 수명을 세션에서 떼어내는 것이었습니다.

```bash
# 긴 단계(팩트 생성·제약 복원)는 VM 안에서 detached 실행하고,
# 로컬은 완료 rc 파일만 폴링한다
setsid bash -c 'set -euo pipefail; psql -f 20_facts.sql; echo $? > /tmp/seed.rc' \
  </dev/null >/tmp/seed.log 2>&1 &
```

이렇게 바꾼 뒤 3,000만 건 INSERT를 통과하고 golden 22GB를 `IS_TEMPLATE`으로 동결했습니다. 참고로 `ServerAliveInterval` keepalive만으로는 부족했습니다. 유휴 터널은 살려도 실제 네트워크 드롭 앞에서는 무력합니다.

### 검증 숫자가 불가능한 값을 말했다

시드가 끝나고 검증 로그를 보니 포모도로 테이블 건수가 상위 개념인 `focus_sessions`보다 크게 찍혀 있었습니다(둘 다 4,700만대). 포모도로는 focus_sessions의 부분집합이므로 **더 많을 수가 없습니다.**

원인은 검증 쿼리였습니다. `count(*)`가 아니라 `pg_stat_user_tables.n_live_tup`을 읽고 있었는데, 이 값은 추정치입니다. 대량 적재 직후에는 크게 부풀 수 있고 테이블 간 일관성도 보장되지 않습니다.

교차검증은 볼륨으로 했습니다. 실측 `pg_database_size`가 22GB였고 이는 설계 볼륨(focus_sessions 3,000만)과 맞습니다. 정말 4,800만 건이었다면 22GB로는 불가능합니다. 즉 **실제 건수는 정상이고 추정만 부풀어 있었습니다.**

대량 적재 후 볼륨 검증은 추정치가 아니라 `count(*)`로 하고, 최소한 db_size로 교차검증합니다.

## 재현 가능한 생성 — 내 로컬에만 있던 yml

대시보드가 때릴 타겟을 손으로 4개 하드코딩하던 것을 백엔드 `openapi.json` 기반 자동 목록화로 넓히려 했습니다(GROMO-750). openapi.json은 springdoc gradle 플러그인의 부산물입니다. 앱을 부팅해서 api-docs 경로를 덤프하는 방식입니다.

그런데 `generateOpenApiDocs`가 `Unable to connect to http://localhost:8080/v0/api-docs waited for 180 seconds`로 끝났습니다. 컴파일은 3분 걸려 정상 완료되는데 **포크된 앱이 8080에 뜨지 않습니다.** 플러그인이 포크 앱의 startup 로그를 삼켜서 원인을 볼 수도 없었습니다.

추적 순서는 이랬습니다.

1. `local` 프로파일에 datasource를 시스템 프로퍼티로 넘겨 재시도 — 실패, 로그가 없어 깜깜.
2. 한 단계 내려가 `bootRun`을 직접 띄워 startup 로그 확보 — 앱이 부팅 중 죽는 것을 확인.
3. 핵심 원인: base `application.yml`과 `application-local.yml`이 **gitignored**라 fresh checkout 워크트리에 아예 없습니다. datasource·dialect·springdoc path 등 부팅에 필요한 config가 통째로 비어 크래시한 것입니다.
4. 결정적 단서: 같은 생성을 하는 CI 워크플로는 **매번 성공**합니다. CI가 뭘 다르게 하나 보니, 자기완결적인 `ci` 프로파일을 쓰고 있었습니다. datasource·`ddl-auto: create-drop`·flyway off·외부 서비스 URL·서명키까지 전부 명시돼 gitignored 로컬 파일에 의존하지 않도록 설계돼 있었습니다.

그대로 따랐습니다. `SPRING_PROFILES_ACTIVE=ci` + 일회용 DB로 datasource만 override했습니다(dev DB는 `create-drop`이 스키마를 지우므로 절대 붙이지 않습니다). 앱이 **3.2초** 만에 떴고 api-docs에서 **93개 operation**을 덤프했습니다.

이 덤프가 그다음 자동화의 입력이 됩니다. openapi가 스키마와 enum을 주니 엔드포인트별 입력 전략(recipe)을 생성할 수 있었고, 커버리지는 **86/93(92%)**였습니다. 못 채운 건 시드에 없는 path ID 7개(태그·챌린지·공지 등)뿐이라, **자동화의 경계가 곧 "데이터에 없는 식별자"**라는 사실이 깔끔하게 드러났습니다.

교훈은 두 줄입니다. 로컬 편의 config에 기대는 생성은 fresh checkout과 CI에서 조용히 깨집니다. 재현 가능한 생성은 CI가 쓰는 자기완결 프로파일을 그대로 따르는 것이 정답입니다. 그리고 gradle 플러그인이 포크 프로세스 로그를 삼킬 때는 한 단계 내려가 직접 띄웁니다.

## 조용히 사라지는 브랜치 — squash 머지와 스택 PR

recipe 작업은 앞선 PR 위에 스택으로 쌓아뒀습니다. 후속 draft PR을 열려는데 이렇게 거절당했습니다.

```text
No commits between ... / Base ref must be a branch
```

base로 지정한 부모 브랜치가 원격에 없습니다. 부모 PR(#190)이 **squash 머지**되면서 (a) head 브랜치가 자동 삭제되고, (b) squash라서 부모의 커밋 SHA 자체가 main에 존재하지 않게 됐기 때문입니다. 스택의 바닥이 통째로 증발한 셈입니다.

복구는 간단했습니다. main에서 새 브랜치를 따고 내 커밋만 `cherry-pick`했습니다. 부모 내용은 이미 main에 squash로 반영돼 있어 충돌은 0이었고, base=main으로 PR을 다시 열었습니다.

정리하면 base가 "없어진" 게 아니라 **squash가 커밋의 정체성을 바꾼 것**입니다. squash 머지를 쓰는 팀에서는 스택 PR을 만들지 않고, 부득이 만들었다면 부모 머지 직후 main 기준으로 rebase 또는 cherry-pick합니다. 같은 계열로 한 번 더 데었습니다. 리뷰 반영 커밋을 푸시하는 동안 PR이 머지되면, 이후 푸시는 이미 닫힌 브랜치로 가고 squash는 그 이력을 main에 남기지 않아 **반영했다고 믿은 픽스가 조용히 유실**됩니다. 그래서 "머지는 반영 완료 보고 후에"를 규칙으로 박았습니다.

## 조용히 오염되는 측정 — 직렬 디스패치와 주석 치환

### 배치는 순차, 부하는 동시

첫 설계에서 대시보드는 선택한 N개 API를 **직렬로 N번 디스패치**했습니다. 워크플로 concurrency가 알아서 직렬화해주니 구현이 쉬웠습니다.

그런데 스팟 부하 VM을 API 하나마다 올렸다 내리는 건 인프라 사이클 낭비이고, 실제 트래픽은 여러 API가 동시에 옵니다. 부하 생성기를 띄우는 이유 자체가 병렬 부하인데 설계가 그것을 못 쓰고 있었습니다.

교정: **선택 N개 = 단일 run.** 하나의 arrival-rate 시나리오에서 매 iteration마다 랜덤으로 엔드포인트를 골라 실행하고, 총 rate를 선택분에 분산합니다. 동시 VU가 서로 다른 엔드포인트를 때리므로 병렬입니다.

잃는 것이 없는지 확인했습니다. 엔드포인트별 지표는 k6 `endpoint` 태그로 그대로 분리됩니다. 유일하게 잃는 것은 `pg_stat_statements` 델타 격리인데, 그건 그 API 하나만 단독 선택하면 자동으로 회복됩니다. 결과적으로 **단독 선택 = 쿼리 프로필 격리, 다중 선택 = 결합 병렬 부하**로 한 UI가 둘을 커버합니다.

리소스를 왜 띄우는지 되물으면 설계 오류가 드러납니다.

### 25분 유료 run을 태운 주석 한 줄

또 한 번은 run이 끝나고 나서야 문제를 알았습니다. verdict가 INVALID였고, 이유를 파보니 관측 VM의 Prometheus가 run 내내 죽어 있었습니다(9090 connection refused). k6 remote-write는 전멸했고 collect 단계의 조회 2건도 실패했습니다. **25분짜리 유료 run을 다 태운 뒤에 간접적으로 발견한 것입니다.**

원인은 prometheus 설정 템플릿의 **주석**이었습니다. sync 단계에서 envsubst로 렌더하는데, 주석 안에 남아 있던 달러-중괄호 변수 표기까지 치환 대상이 됐습니다. 값이 호스트명 한 줄이던 시절에는 주석 안에서 무해했지만, 멀티-VM 전환으로 값이 6줄 멀티라인이 되자 치환된 개행이 주석을 뚫고 나와 렌더된 YAML 구조를 부쉈습니다. 로컬 재현으로 파싱 에러 위치까지 일치시켜 확정했습니다.

고침의 핵심은 표기 제거가 아니라 게이트였습니다.

```bash
# 렌더 직후, obs와 동일한 이미지의 promtool로 스키마까지 검증한다
envsubst '$SUT_HOST $LOADGEN_TARGETS' < prometheus.yml.tmpl > "$rendered"
docker run --rm -v "$rendered:/c.yml" prom/prometheus:$TAG \
  promtool check config /c.yml || exit 1
```

정상 렌더는 통과하고 사고 렌더는 exit 1로 막히는 것을 양방향으로 실증했습니다. envsubst에는 치환 대상 변수를 명시적으로 제한하는 습관도 함께 넣었습니다. 같은 계열의 권한 함정도 있었습니다. `mktemp`(기본 0600)로 렌더한 파일을 그대로 scp하면 non-root(nobody)로 도는 컨테이너가 읽지 못해 crash-loop에 빠집니다. scp 직후 배포 스크립트가 가독 권한을 확정하도록 바꿨습니다. "우연히 안전"은 안전이 아닙니다.

**조용한 설정 파괴 → 한참 뒤 간접 발견**이라는 실패 클래스는 개별 버그로 잡는 게 아니라 배포 전 검증 게이트로 통째로 닫습니다.

## 재고는 조회할 수 없다 — 존 소진 3연속과 프로브 VM

하네스는 평시 비용 0을 위해 VM을 중지 상태로 둡니다. 그런데 딸깍을 눌렀더니 SUT VM start가 `ZONE_RESOURCE_POOL_EXHAUSTED`로 실패했습니다. 1.5시간 간격 재시도도 같았습니다.

**중지된 VM은 용량을 예약하지 않습니다.** start마다 GCP가 호스트를 새로 배정하는데 그 존에 해당 인텔 머신 재고가 없었고, 세대 고정을 위해 걸어둔 min CPU platform exact-pin이 배치 가능한 호스트 풀을 더 좁혔습니다.

3연속 소진의 경과는 이렇습니다.

| 시점 | 시도 | 결과 |
| --- | --- | --- |
| 1일차 | n2(인텔) + 시작 재시도 3×60s | 소진 지속 → n2d(AMD)로 패밀리 이동 |
| 2일차 저녁 | n2d로 stress 2회 | n2d도 소진(reason: resource_availability), 25분 뒤 재실행도 동일 |
| 3일차 | b존으로 apply | b존도 소진 — sut만 생성 실패, obs·러너는 이동됨 |
| 3일차 | 일회용 프로브 VM으로 c존 재고 확인 | 재고 확인 후 c존으로 이동 완료 |

이틀 연속 **서로 다른 패밀리**가 품절이라는 것은 특정 패밀리 문제가 아니라 존 전체의 용량 압박이라는 뜻입니다. 머신 갈아타기 카드는 그 시점에 소진됐습니다. 그래서 apply로 시행착오하는 대신 **일회용 프로브 VM을 만들어 재고를 실증**한 뒤 존을 옮겼습니다. 존 재고를 미리 조회할 API는 없고, 프로브 생성이 유일한 사전 확인이며 apply 시행착오보다 훨씬 쌉니다.

여기서 파생된 함정 셋도 기록해 둡니다.

- **핀과 머신의 갱신 순서**: terraform provider가 min CPU platform을 machine_type보다 먼저 갱신해 "인텔 머신 + AMD 핀" 조합으로 400이 났습니다. 두 값을 원자적으로 적용해 우회했습니다.
- **각자 정상, 합치면 깨진다**: 한 PR이 부하 VM 템플릿에 SUT의 핀 변수를 공유했고(당시 값으로는 유효), 다른 PR이 그 변수를 AMD로 바꿨습니다. 파일이 달라 git 충돌도, 리뷰 diff도 걸리지 않았고, GCP는 템플릿 생성이 아니라 **인스턴스 생성 시점에** 조합을 검증하기 때문에 run에서만 드러났습니다(`required CPU platform of cascadelake ... but was milan`). 부하 VM용 핀 변수를 분리해 끊었습니다(PR #213 · GROMO-763). 변수 공유는 "두 소비자의 의미가 함께 움직여도 되는가"로 심사해야 합니다.
- **재생성된 VM의 암묵 의존**: c존 이동 후 첫 run에서 reset이 exit 127(`psql: command not found`)로 죽었습니다. sync가 운영 SQL은 올리면서 그것을 실행할 psql 바이너리는 보장하지 않았고, 기존 관측 VM에는 시드 실행이 설치해 둔 psql이 있어 잠복해 있었을 뿐입니다. 멱등 설치를 sync 경로에 넣어 소유권을 명시했습니다. 인프라를 부수고 다시 만드는 설계라면 "어쩌다 설치된" 의존까지 부트스트랩이 전부 소유해야 합니다.

단일 존 올인은 "아무 때나 눌러도 도는" 딸깍 컨셉과 태생적으로 상성이 나쁩니다. 장기 운영이라면 멀티존 폴백을 설계에 포함해야 합니다.

## 남은 것

하네스가 관통한 뒤 이 구조는 이렇게 정리됐습니다. 진입점 3개(대시보드 버튼·Actions UI·로컬 make)가 단일 파이프라인을 실행하고, golden을 `TEMPLATE`으로 복제해 매 run 동일 출발선을 만들고, 판정은 단일 모듈이 소관하며(INVALID 우선 → threshold → baseline 회귀), 리포트는 orphan 브랜치로 커밋해 대시보드가 서버 없이 읽습니다(PR #185). 자체 컨트롤플레인 서버는 0입니다.

만들면서 얻은 원칙은 하나로 수렴합니다. **자동화가 넓어질수록 실패는 조용하지 않게 만들어야 합니다.** 부하테스트에서 조용한 오류는 그대로 에러율·지연 왜곡이 되어 "정상인데 느림", "실패인데 통과"를 만들어냅니다. 그래서 실행 불가 recipe는 즉시 throw하고, path 파라미터 생성 실패는 문자열 `'null'`로 흘리지 않고 throw하며, 미구현 옵션은 조용히 기본값으로 처리하지 않고 실행 전에 차단합니다.
