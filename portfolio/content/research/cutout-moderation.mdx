## 0. 한눈에

**누끼**는 사진에서 피사체만 오려 내는 것이다. gromo 1.x의 누끼 캐릭터는 사진 속 물건을 오려 팔·다리·눈을 붙여 내 캐릭터로 쓰는 기능이고, 오리기는 기기 안에서(iOS 17 이상의 Vision 프레임워크) 한다. 만든 캐릭터는 기기에만 저장된다. 다만 **저장하기 직전에 서버 모더레이션을 한 번 통과해야** 한다. 모더레이션은 이미지가 유해한지 판정하는 검사이고, 서버는 판정만 하고 이미지를 저장하지 않는다.

이 관문을 두는 결정 자체는 [ADR-028](/adr/adr-028-cutout-moderation-gate)에 있다. 이 문서는 그 관문을 만들고 검증하면서 부러졌던 자리들이다.

| # | 무엇 | 언제 | 티켓 · PR |
| --- | --- | --- | --- |
| A | 검사 쪽 장애가 "사진이 잘못됐다"로 표시됐다 | 08-06 | GROMO-1197 · #491 |
| B | 모더레이션 회귀 테스트가 0건이었다 → 3건 | 08-06 | GROMO-1197 · #491 |
| C | 본문 크기 검사가 본문을 다 읽은 뒤에야 돌았다 | 08-02 | GROMO-1044 · #436 |
| D | 온디바이스 선필터(NSFW.js)를 설치조차 못 해 쓰지 않기로 했다 | 08-02 | — |

| 값 | 무엇 |
| --- | --- |
| **1곳** | 캐릭터를 저장하는 호출부 — 우회 경로 없음 |
| **0 → 3건** | 모더레이션 회귀 테스트 |
| **12MiB / 10MiB** | 본문 와이어 한도(413) / 이미지 문자열 한도(400) |
| **13초 · 15초** | 서버 판정 대기 상한 · 앱 요청 타임아웃 |
| **4,168ms** | 누끼 저장 시 모더레이션 앱 왕복 p99 |

<Callout label='핵심 한 줄: "막았다"와 "왜 막았는지"는 다른 축이다'>

fail-closed(검사를 못 하면 막는다)는 옳은 방향이었다. 틀린 것은 **막은 이유를 응답이 말하지 않았다**는 것이다. 차단 여부만 있고 사유가 없는 응답은, 받는 쪽에서 "판정 결과 유해"로밖에 읽을 수 없다.

</Callout>

## 1. 설계

### 1.1 흐름

```text
[앱]  사진 선택(갤러리·카메라)
      → 기기 안에서 누끼 (iOS 17+ Vision. 실패하면 throw 없이 원본으로 폴백)
      → 90도 회전 · 팔다리·눈 합성
      → 캐릭터 뷰를 PNG로 캡처
      → POST /api/v1/character/moderation   ← 저장 전 관문, 딱 한 번
[서버] 인증 확인 → 본문 크기 확인 → 판정 → 결과만 응답 (이미지 미저장)
[앱]  통과하면 기기에 저장 · 차단이면 저장하지 않고 사유별 안내
```

누끼 자체가 실패해도 오류를 내지 않고 원본 사진으로 계속 간다. iOS 16이나 시뮬레이터처럼 오리기가 안 되는 환경에서도 "원본으로라도 만들기"가 되게 하려는 선택이다. 그래서 모더레이션이 받는 이미지는 오려진 것일 수도, 원본 그대로일 수도 있다.

### 1.2 관문은 하나다

코드로 끝까지 따라가 확인한 것이다.

- 캐릭터를 저장하는 `saveCustomCharacter`의 호출부는 **`CharacterCreator` 한 곳뿐**이고, 그 바로 앞에서 모더레이션을 부른다. 통과해야만 저장한다.
- 온보딩의 누끼 체험(`CutoutStep`)도 같은 `CharacterCreator`를 모달로 재사용하므로 같은 관문을 지난다.
- 온보딩에는 이 스텝을 넘어가는 경로가 둘 있다 — 누끼를 만들 수 없는 기기(또는 E2E 테스트), 그리고 생성 창을 X로 닫고 포기한 경우. 둘 다 **이미지를 저장하지 않으므로** 우회가 아니다.
- 서버 엔드포인트는 인증 필터의 화이트리스트에 없어 로그인하지 않은 요청은 401이다.

### 1.3 검사를 못 하면 막는다 — fail-closed

**fail-closed**는 판단에 필요한 것이 고장 나면 "허용"이 아니라 "차단" 쪽으로 넘어지게 만드는 설계다. 유해 이미지를 한 번 통과시키는 비용이 정상 사진을 잠깐 막는 비용보다 크다고 봤다.

| 상황 | 서버 처리 |
| --- | --- |
| 검사 설정 누락 | 예외 → 차단 |
| 검사 호출이 오류로 끝남 | 예외 → 차단 |
| 빈 결과 | 예외 → 차단 |
| 판정 결과 필드가 빠짐(null) | 예외 → 차단 (통과로 해석하지 않는다) |
| 시간 초과 | 예외 → 차단 |

서버의 판정 대기 상한은 약 **13초**로, 앱 공용 요청 타임아웃 **15초**보다 짧게 잡았다. 그래야 서버가 "검사 불가"라고 판단한 결과가 앱의 타임아웃보다 먼저 도착한다. 순서가 뒤집히면 앱은 서버의 답을 못 듣고 자기 타임아웃으로 끝난다.

앱도 같은 방향이다. 응답을 아예 못 받으면(네트워크 오류·타임아웃·비2xx) `allowed:false, unavailable:true`로 취급한다. 응답이 없는 것을 "통과"로 읽지 않는다.

### 1.4 같은 화면의 다른 관문은 반대로 넘어진다 — fail-open

누끼 생성에는 관문이 하나 더 있다. 일정 기간에 만들 수 있는 횟수를 세는 **쿼터**다(GROMO-1045 #431, GROMO-1047 #432). 이쪽은 일부러 반대로 만들었다.

| 관문 | 조회 실패 시 | 이유 | 타임아웃 |
| --- | --- | --- | --- |
| 모더레이션 | **차단** (fail-closed) | 안전 장치다. 못 봤으면 통과시키지 않는다 | 공용 15초 |
| 쿼터 | **허용** (fail-open) | 제한 장치다. 인프라 문제로 생성을 막을 이유가 없다 | 전용 **4초** |

쿼터 조회는 로딩 스피너를 잡고 있는 UI 게이트라, 공용 15초까지 기다리면 fail-open이어도 사용자가 최대 15초 갇힌다. 그래서 짧은 전용 타임아웃으로 일찍 포기하고 생성을 허용한다. **넘어지는 방향은 관문의 목적이 정한다.** 한 화면에 두 관문이 반대 방향으로 서 있는 것은 모순이 아니다.

## 2. 결함 기록

### A. 검사 쪽 장애가 "사진이 잘못됐다"로 보였다 — GROMO-1197 · #491 · 08-06

**어떻게 발견했나** — 사용자 신고가 아니라, 모더레이션이 제대로 막는지를 코드 근거로 끝까지 검증하는 티켓(GROMO-1197)에서 나왔다. 배선·fail-closed·크기 제한은 모두 정상이었고, 결함은 안내 문구 한 곳에 있었다.

**증상** — 서버가 검사를 못 해서 막은 경우에도 앱은 "이 사진으로는 캐릭터를 만들 수 없어요."를 띄웠다. 사용자는 사진 탓이라고 생각하고 다른 사진으로 다시 시도한다. 검사 쪽이 죽어 있으니 몇 번을 바꿔도 같은 문구가 뜬다.

**원인** — 서버의 fail-closed가 **HTTP 200 + `allowed:false`**를 돌려줬다.

```text
검사 쪽 장애 → 서버 200 { allowed: false } → 앱: "이 사진으로는 캐릭터를 만들 수 없어요."
```

앱에는 `unavailable` 분기와 "지금은 확인이 어려워요. 잠시 후 다시 시도해 주세요." 문구가 **이미 있었다.** 하지만 그 분기는 앱이 응답 자체를 못 받았을 때만 탈 수 있었다. 서버가 200으로 정상 응답하면서 사유를 알려주지 않았으니, 앱 입장에서 그 응답은 "판정했고 유해함"과 구별할 방법이 없었다.

온보딩에서는 피해가 한 겹 더 있었다. 온보딩의 누끼 스텝은 만들기를 끝내야 "다음"이 열리고, **"검사 불가"일 때만** 예외로 "다음"을 열어 사용자가 갇히지 않게 해 두었다. 그런데 장애가 "유해 판정"으로 들어오니 그 예외도 타지 못했다. 빠져나갈 길은 생성 창을 X로 닫는 것(#452)뿐이었다.

**해결** — 서버 응답에 `unavailable` 필드를 추가했다. 응답 객체에 의도를 드러내는 생성 함수 둘을 두고(`judged()` = 판정함, `failClosed()` = 검사 못 해서 막음), fail-closed catch가 `failClosed()`를 반환하게 했다. 앱의 API 래퍼는 서버가 준 값을 그대로 `unavailable`로 옮긴다. 필드가 없는 구 서버는 `undefined`가 `false`로 읽혀 기존 동작이 그대로 유지된다(하위 호환).

**화면 코드(`CharacterCreator`)는 한 줄도 고치지 않았다.** 이미 있던 분기가 이제야 제대로 동작한다.

| 상황 | 문구 | 저장 | 온보딩 "다음" |
| --- | --- | --- | --- |
| 유해 판정 (`allowed=false`, `unavailable=false`) | 이 사진으로는 캐릭터를 만들 수 없어요. | 안 함 | 안 열림 |
| 검사 불가 (`unavailable=true`) | 지금은 확인이 어려워요. 잠시 후 다시 시도해 주세요. | 안 함 | **열림** — "나중에 홈에서 만들 수 있어요" 안내 |
| 저장 자체 실패 | 캐릭터를 저장하지 못했어요. 다시 시도해 주세요. | 실패 | — |

<Callout label="200 + false는 판정 결과로 읽힌다" tone="warn">

"실패하면 안전하게 막는다"를 구현할 때 가장 쉬운 방법은 catch에서 `allowed:false`를 돌려주는 것이다. 동작은 맞다. 하지만 받는 쪽은 그 응답을 **판정의 결과**로 읽는다. 차단 여부와 차단 사유는 별개의 축이고, 사유가 다르면 사용자에게 할 말도 다르다 — 한쪽은 "다른 사진을 고르세요", 다른 쪽은 "잠시 후 다시". fail-closed 응답에는 **"왜 막았는지"를 실어야** 한다.

</Callout>

### B. 모더레이션 테스트가 0건이었다

관문을 만들 때 모더레이션을 겨냥한 테스트는 서버에도 앱에도 **한 건도 없었다.** A의 결함이 컴파일도 CI도 통과한 채로 남아 있던 이유다. #491에서 서비스 테스트 3건을 추가했다.

1. 유해하지 않으면 통과 — `allowed=true`, 검사 불가 아님
2. 유해 판정이면 차단 — 카테고리를 실어 보내고, 검사 불가는 아님
3. **검사 실패(설정 누락·시간 초과·오류)는 차단하되 '검사 불가'로 표시** — fail-closed의 핵심

세 번째가 A를 다시 깨뜨리지 못하게 막는 테스트다. 같은 PR에서 백엔드 Checkstyle·SpotBugs·전체 테스트, 앱 타입 검사·린트·포맷·테스트 747개가 통과했다.

### C. 본문 크기를 역직렬화 전에 끊는다 — GROMO-1044 · #436 · 08-02

**증상** — 모더레이션 API가 머지된 직후(#426) 코드 리뷰(codex, P2)에서 지적이 나왔다. 요청 DTO의 `@Size(max = 10MiB)`는 **Jackson이 본문 전체를 힙에 읽어 객체로 만든 뒤에야** 검사한다. **역직렬화**(JSON 문자열을 자바 객체로 바꾸는 것)가 이미 끝난 다음이다. 인증된 클라이언트가 초대형 본문을 반복해서 보내면 400을 돌려주기 전에 서버 메모리를 태울 수 있다.

**해결** — `Content-Length` 헤더를 역직렬화 전에 보는 필터를 이 경로 전용으로 달았다.

- 한도를 넘으면 **413**(`PAYLOAD_TOO_LARGE`)으로 즉시 끊는다.
- 필터 순서는 0번으로, 인증 필터(1)와 추적 ID 필터(2)보다 **앞**이다. 본문을 읽기 전에 끊는 게 목적이기 때문이다.
- `Content-Length`가 없는 **chunked** 전송(길이를 미리 알리지 않고 조각으로 보내는 방식)은 미리 판정할 수 없으므로 통과시키고 뒤단 `@Size`(400)에 맡긴다. 이중 방어다.

**한도가 둘인 이유** — 이미지 문자열 한도는 10MiB인데 필터의 와이어 한도는 **12MiB**다. `@Size`는 base64 **문자열 길이**를 재지만 필터가 보는 `Content-Length`는 **전송되는 바이트**다. JSON 직렬화가 base64의 `/`를 `\/`로 이스케이프하면 와이어 쪽이 더 커진다(`/`가 base64 문자 중 약 1.6%라 최대 수백 KB). 두 한도를 같게 두면 `@Size`는 통과할 정상 요청이 필터에서 413을 맞는다. 그래서 와이어 한도를 넉넉히 뒀다.

**부작용 하나** — 필터가 인증보다 먼저 돌기 때문에, 로그인하지 않은 대용량 요청은 401이 아니라 413을 받는다. 수동 테스트에서 401을 기대하면 어긋난다. 의도한 순서의 결과지만 문서에 남겨 두지 않으면 버그로 오해받는다. 필터 순서가 동작을 바꾸는 다른 사례는 [로깅 함정 노트](/research/logging-traps)에 있다.

**영향** — 일주일 뒤 집중 세션 저장 경로(GROMO-1252, #539, 08-09)가 같은 필터를 8KiB 한도로 가져다 썼다. 지금은 경로별 한도를 받는 필터 하나(`RequestSizeLimitFilter`)가 두 경로를 맡는다.

### D. 온디바이스 선필터를 쓰지 않았다 — 08-02

서버 관문 앞에 기기 안에서 먼저 거르는 선필터로 NSFW.js를 붙이려 했다. 선필터가 걸러 주면 서버 호출이 줄고 사용자는 더 빨리 답을 받는다.

설치 단계에서 막혔다. NSFW.js가 기대는 `tfjs-react-native@1.0.0`의 **peer 의존성**(앱에 함께 깔려 있어야 하는 패키지와 버전 범위)이 Expo SDK 57 스택과 메이저 버전으로 충돌했다 — async-storage는 `^1.13.0`을 요구하는데 앱은 2.2.0, `expo-gl`은 `^13.0.1`을 요구하는데 SDK 57은 16.x다. 자세한 표와 `--force` 설치를 하지 않은 이유는 [Expo 네이티브 빌드 노트 §3](/research/expo-native-build-traps)에 있다.

**결정 — 선필터를 아예 쓰지 않는다.** 작업 중이던 스텁까지 지웠다. 근거는 선필터가 잡으려던 성적 이미지가 **서버 모더레이션의 판정 범주와 겹친다**는 것이다. 선필터는 서버 호출을 줄이는 최적화일 뿐이고, 빼도 안전에 구멍이 나지 않는다. 호환되는 경로(새 버전이나 대체 라이브러리)가 확인되면 네이티브 재빌드와 함께 후속으로 붙일 수 있다.

## 3. 숫자 — 관문의 대가

선필터 없이 서버 관문 하나로 가는 대가는 대기 시간이다. 08-25 기준 prod 실사용자 29일치를 앱 쪽 측정(RUM, 기기에서 잰 왕복 시간)과 서버 쪽 측정(APM, 서버가 요청 하나를 처리한 시간)으로 나란히 놓았다.

| 모더레이션 요청 | p75 | p95 | p99 |
| --- | ---: | ---: | ---: |
| 앱 왕복 | — | 3,214ms | **4,168ms** |
| 서버 처리 | 1,836ms | 2,198ms | **2,242ms** |

p99 기준 왕복의 **54%가 서버 몫**이다. 일반 조회 API는 서버 몫이 1–5%라 네트워크가 지배하는데, 이 경로만은 서버의 판정 시간이 절반을 차지한다. 누끼를 저장할 때 사용자는 꼬리에서 약 4초를 기다린다. 저장은 생성 한 번에 한 번뿐이고 쿼터로 횟수도 제한되므로 감수했다. 다른 엔드포인트와의 비교는 [API 응답 지연 노트](/research/api-latency-tail)에 있다.

## 4. 남은 천장

| 천장 | 지금 괜찮은 이유 | 넘어가면 할 일 |
| --- | --- | --- |
| 서버에 별도 임계값이 없다 | 판정 결과의 유해 여부 하나로 결정한다. 걸린 카테고리는 앱에 알려 주는 보고용이다 | 어떤 이미지가 걸리는지는 코드로 확인할 수 없다. 실제 이미지로 수동 확인해야 한다(유해 차단 · 검사 불가 안내 · 정상 통과 · 413) |
| 검사 설정이 비면 모든 사진이 막힌다 | fail-closed의 의도된 결과다. 이제는 "지금은 확인이 어려워요"로 보인다 | 배포 환경의 설정 주입 여부는 저장소 밖이라 코드 검증으로 확인할 수 없다 |
| 누끼 저장 시 4초 꼬리 | 생성당 한 번, 횟수 제한이 있다 | 선필터를 붙이면 명백한 경우를 기기에서 먼저 거를 수 있다. 호환 경로 확인이 선행 |
| 내 누끼는 나만 본다 | 로컬 저장이라 남에게 노출되지 않는다 | 서버에 올려 남에게 보이게 할 때는 업로드될 바이트를 다시 검사하기로 설계만 해 두었다(08-30, [ADR-028](/adr/adr-028-cutout-moderation-gate)). 서버 저장은 아직 착수되지 않았다 |

## 5. 용어

| 용어 | 뜻 |
| --- | --- |
| 누끼 | 사진에서 피사체만 오려 내는 것. 배경 제거 |
| 모더레이션 | 콘텐츠가 유해한지 판정해 걸러 내는 검사 |
| fail-closed | 판단에 필요한 것이 고장 나면 "차단"으로 넘어지는 설계. 안전 장치에 쓴다 |
| fail-open | 고장 나면 "허용"으로 넘어지는 설계. 제한 장치처럼 막을 이유가 약한 곳에 쓴다 |
| fail-safe | 실패해도 위험하지 않은 상태로 끝나게 하는 것. 여기서는 앱이 응답을 못 받으면 저장하지 않는 것 |
| 역직렬화 | JSON 같은 문자열을 프로그램 안의 객체로 바꾸는 것. 이 과정에서 본문 전체가 메모리에 올라간다 |
| `Content-Length` | 요청 본문이 몇 바이트인지 미리 알리는 HTTP 헤더. 본문을 읽기 전에 크기를 판단할 수 있다 |
| chunked 전송 | 전체 길이를 알리지 않고 본문을 조각으로 보내는 방식. 미리 크기를 판단할 수 없다 |
| 413 | "요청 본문이 너무 크다"는 HTTP 상태 코드 |
| peer 의존성 | 라이브러리가 직접 설치하지 않고 앱에 이미 깔려 있기를 기대하는 패키지와 버전 범위 |
| p95 / p99 | 요청을 느린 순으로 줄 세웠을 때 상위 5% / 1% 경계의 값. 사용자가 가끔 겪는 느림을 본다 |
