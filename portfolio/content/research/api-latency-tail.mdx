"앱이 느리다"는 말을 들으면 먼저 서버 쿼리를 의심하게 된다. 그런데 1.x 앱(`app/legacy/app-dev`)의 주요 화면을 운영 환경에서 재 보니, 일반 조회에서 서버가 쓰는 시간은 앱이 기다린 시간의 **1~5%**였다. 나머지 95% 이상은 서버 밖에서 흘렀다. 이 노트는 그 측정과, 거기서 나온 결론 셋 — **꼬리로 봐야 한다, 요청 개수보다 직렬 단계 수가 문제다, 앱이 원본을 받아 조립하는 자리가 느림과 틀림을 같이 만든다** — 그리고 제안 중 실제로 반영된 것과 아닌 것이다.

## 0. 한눈에

| 값 | 무엇 |
| --- | --- |
| **1~5%** | 일반 조회에서 앱 왕복 p99 중 서버 처리 몫 |
| **20~60ms** | 일반 조회의 서버 처리 p99 |
| **3,209ms** | 리그·홈 화면 p99 (세션 3페이지, 직렬 3단계) |
| **1,049ms** | 통계 화면 p99 (요청 5개 병렬, 1단계) |
| **2,684ms → 34ms** | 그룹방 p99를 혼자 만드는 호출의 앱 왕복 대 서버 처리 |
| **상위 100명** | "전체 평균"의 실제 모수 — GROMO-1632(#706)에서 정정 |

<Callout label="무엇으로 쟀나">

- **RUM** (Real User Monitoring, 실사용자 모니터링) — 사용자 기기에서 요청을 보낸 순간부터 응답이 도착할 때까지를 잰 **앱 왕복 시간**. 무선망·TLS 연결·기기 상태가 전부 들어간다.
- **APM** (Application Performance Monitoring) — 서버가 요청 하나를 받아 응답을 내보낼 때까지 쓴 **서버 처리 시간**. 네트워크는 빠져 있다.

둘 다 Datadog에서 운영 환경 29일치(2026-08-25 기준)를 뽑았다. 같은 엔드포인트의 두 값을 나란히 놓으면 왕복 중 서버 몫과 서버 밖 몫이 갈린다. **화면 단위 시간은 엔드포인트 실측을 코드의 호출 구조에 맞춰 조합한 추정**이다 — 직렬이면 더하고, 병렬이면 가장 느린 하나를 쓴다.

</Callout>

## 1. 왜 중앙값이 아니라 꼬리로 보나

중앙값은 "보통은 괜찮다"만 말해 준다. 사용자가 "이 앱 못 쓰겠다"고 느끼는 순간은 느린 쪽에서 벌어진다.

```text
p75  네 번에 한 번은 이보다 느리다
p95  스무 번에 한 번        ← 하루 한 번 쓰면 3주에 한 번은 겪는다
p99  백 번에 한 번          ← 하루에도 여러 번 여는 사람은 매주 겪는다
```

p95는 요청 100개 중 가장 느린 5개가 시작되는 경계, p99는 가장 느린 1개가 시작되는 경계다. 이 앱은 한 화면에 요청을 여러 개 쏘기 때문에, 화면 하나를 열 때마다 **여러 번 주사위를 굴리는 셈**이라 꼬리를 만날 확률이 요청 하나일 때보다 높다.

꼬리로 본 주요 화면은 이랬다.

| 화면 | p95 | p99 |
| --- | ---: | ---: |
| 집중 세션 | 1.50초 | **2.16초** |
| 그룹방 | 1.11초 | **2.68초** |
| 리그 · 홈 (세션 1페이지) | 1.05초 | 1.69초 |
| 리그 · 홈 (세션 3페이지) | **2.33초** | **3.21초** |
| 친구 프로필 | 0.99초 | 1.69초 |
| 통계 | 0.82초 | 1.05초 |
| 집중 결과 | 0.78초 | 1.31초 |

**주요 화면이 p99에서 전부 1초를 넘고 절반은 2초를 넘는다.** 로딩 스피너를 2초 보는 화면은 고장 난 것처럼 느껴진다.

## 2. 서버는 왕복의 1~5%였다

같은 엔드포인트를 앱 왕복(RUM)과 서버 처리(APM)로 나란히 놓은 p99 값이다.

| 엔드포인트 | 앱 왕복 | 서버 처리 | 서버 비중 |
| --- | ---: | ---: | ---: |
| `GET /api/v1/me/bet-sessions` | 2,684ms | 34ms | **1%** |
| `GET /api/v1/groups` | 1,661ms | 32ms | **2%** |
| `GET /api/v1/users/me` | 1,360ms | 28ms | **2%** |
| `GET /api/v1/league/me/ranking` | 1,695ms | 53ms | **3%** |
| `GET /api/v1/pins` | 1,695ms | 44ms | **3%** |
| `GET /api/v1/friends` | 1,307ms | 62ms | **5%** |
| `GET /api/v1/stats/by-category` | 623ms | 173ms | 28% |
| `GET /api/v1/stats/screen-time` | 675ms | 216ms | 32% |
| `POST /api/v1/auth/google` | 462ms | 151ms | 33% |
| `POST /api/v1/character/moderation` | 4,168ms | 2,242ms | 54% |
| `POST /api/v1/auth/apple` | 1,091ms | 689ms | 63% |

위쪽 여섯 줄이 일반 조회다. 서버는 p99에서도 20~60ms만 쓴다. `league/me/ranking`을 예로 들면, 쿼리를 아무리 다듬어도 왕복 1,695ms 중 줄일 수 있는 건 53ms다. **왕복 횟수를 줄이는 것만이 답**이다.

<Callout label="서버 몫이 큰 예외 셋">

- **소셜 로그인** — 서버가 외부 인증 서버를 다녀온다. 애플 로그인은 서버에서만 p99 689ms를 쓴다.
- **누끼 캐릭터 검사** — 사진을 서버 모더레이션에 보내는 호출이라 서버가 p99 2.2초를 쓰고, 앱은 4.2초를 기다린다. 이 대가를 치르고도 서버 검사를 둔 이유는 [누끼 모더레이션 노트](/research/cutout-moderation)에 있다.
- **통계 일부** — `stats/screen-time` 216ms, `stats/by-category` 173ms. 서버 p75는 16ms대로 다른 조회와 같은데 **p99에서만 튄다.** 중앙값으로 보면 영영 안 보이는 자리이고, 서버 쿼리 최적화가 실제로 값을 하는 몇 안 되는 곳이다.

</Callout>

서버 쪽 렌즈로 본 같은 질문 — 부하를 걸었을 때 서버 안에서 무엇이 꼬리를 만드는가 — 는 [부하 테스트 노트](/research/loadtest-error96)가 다룬다. 이 노트는 그 반대편, **실사용자의 기기에서 본 시간**이다.

## 3. 요청 개수보다 직렬 단계 수가 문제다

앱은 거의 모든 화면에서 요청을 `Promise.all`로 한꺼번에 병렬 발사한다. 병렬이면 5개를 쏘든 9개를 쏘든 기다리는 시간은 **가장 느린 하나**다. 반면 앞 응답을 받아야 다음 요청을 보낼 수 있는 **직렬 단계**는 단계마다 느린 주사위를 다시 굴린다. 꼬리에서는 이 차이가 더 벌어진다.

```text
병렬 5개   = 왕복 1번  →  p99 1,049ms   (통계 화면)
직렬 3단계 = 왕복 3번  →  p99 3,209ms   (리그·홈, 세션 3페이지)
```

직렬 단계가 생긴 곳은 두 군데였다.

**① 주간 집중 시간 합산 (리그·홈).** 화면에 필요한 건 "내 이번 주 집중 초" **숫자 하나**다. 그걸 얻으려고 세션 원본을 100건씩 커서 페이징(앞 페이지의 마지막 위치를 받아 다음 페이지를 요청하는 방식)으로 **순차** 조회해 앱에서 더했다. 최대 50페이지까지 돈다. 세션이 많을수록 느려지는 구조라, **가장 열심히 쓰는 사용자가 가장 느린 화면을 본다.**

| 세션 페이지 수 | p95 | p99 |
| ---: | ---: | ---: |
| 1 | 1,049ms | 1,695ms |
| 2 | 1,554ms | 2,139ms |
| 3 | 2,330ms | 3,209ms |
| 5 | 3,884ms | 5,349ms |

게다가 홈 화면이 리그와 같은 훅을 직접 써서, 이 무거운 조회가 **홈에서 한 번 더** 돈다. 서버에는 이미 주간 집계가 있었다 — 앱 코드 주석에 "서버 주간 집계는 종료 시각 날짜 버킷"이라고 적혀 있다.

**② 그룹 상세 (집중 세션 화면).** 그룹 목록을 받아야 그룹 id를 알고, 그 id로 그룹마다 상세를 받는 2단계다(N+1 — 목록 1번 + 그룹 수만큼 N번). 앱 전체에서 유일한 직렬 2단계라 집중 세션 화면이 가장 느리다. 여기에 **60초 폴링**이 붙어 있어, 30분 세션을 하는 동안 이 2단계가 30번 반복된다. 폴링을 둔 이유는 [집중 세션 동기화](/research/focus-session-sync)에 있다.

```text
1단계  GET /api/v1/groups              p99 1,661ms
          ↓  그룹 id 를 받아야 다음이 나감
2단계  GET /api/v1/groups/{groupId}    p99   500ms   × 그룹 수 (병렬)
─────────────────────────────────────────────────
       합계                            p99 2,161ms
```

그리고 **모든 화면이 `useFocusEffect`**(화면이 다시 보일 때마다 실행되는 React Navigation 훅)로 조회한다. 탭을 갔다 올 때마다 전부 다시 나간다. 통계 화면은 기간 탭(주·월·년)을 바꿀 때마다 요청 다섯 개가 다시 나가, 세 탭을 훑으면 꼬리를 뽑을 기회가 세 배가 된다. 통계는 다섯 개를 하나로 묶어도 p99가 약 15% 줄 뿐이라, 묶기보다 탭 캐시가 효과가 크다.

앱 부팅도 직렬이다. `users/me`를 받은 뒤 화면 조회가 이어지므로, 홈으로 콜드 스타트하면 p99 기준 `1,360 + 1,695`, 약 3초가 서버 대기다.

## 4. 성능 조사가 찾은 것은 값의 오류였다

화면별로 "무엇을 그리려고 무엇을 몇 번 부르는지"를 코드로 따라가다가, 느림보다 급한 것이 나왔다.

### 4.1 "전체 평균"은 랭킹 상위 100명의 평균이었다

통계 화면의 비교 카드는 "나 / 전체 평균 / 같은 시험 준비생 평균"을 보여 준다. 그런데 전체 평균을 내는 코드는 **리그 랭킹 상위 100명**을 받아 앱에서 평균을 내고 있었다. 같은 시험 평균도 같은 방식이었다.

- **선발 편향** — 상위 100명만의 평균이라 실제 평균보다 높게 나온다.
- **패딩** — 랭킹에 100명이 다 차지 않으면 빈자리를 0분으로 채워 반대로 낮게 나온다.

성능 이전에 값이 틀린 문제였다. 서버에는 평균 집계 API(`stats/focus/average`)가 이미 있었고 친구 축만 그걸 쓰고 있었다. 같은 파일 상단 주석이 친구 축을 서버 API로 옮기면서 "전체·같은 카테고리는 기존 방식 유지"라고 적어 두고 있었다 — 알고 남긴 구멍이었다.

측정 당일(08-25) 조재영이 GROMO-1632(#706)로 주간 탭 평균을 서버 집계로 옮겼다. 서버 작업은 없었고(3축 × 3기간이 이미 있었다), 앱에서 랭킹 호출 두 개가 사라졌다. PR은 **표시값이 의도적으로 바뀐다**고 적었다 — 랭킹이 꽉 찬 경우엔 평균이 내려가고(선발 편향 제거), 덜 찬 경우엔 올라갈 수 있다(0분 패딩 제거). 빈 상태 문구에 빠져 있던 "이번 주" 분기도 함께 넣고, 구현을 되돌리면 테스트가 정확히 2건 실패하는 것까지 확인했다.

<Callout label="앱이 원본을 받아 조립하면 느림과 틀림이 같이 온다" tone="warn">

상위 100명 평균은 "앱이 가진 데이터로 대충 계산한다"의 결과다. 숫자 하나를 얻으려고 원본을 통째로 받는 구조는 느릴 뿐 아니라, 앱이 받은 원본이 **모수 전체가 아닐 때** 값까지 틀린다. 그래서 이 조사의 제안은 대부분 "서버가 완성된 값을 준다"였다.

</Callout>

### 4.2 장비 조회는 한 번도 성공하지 않았다

APM에서 `GET /api/v1/equipment/{userId}`의 서버 처리 p99가 **1.2ms**였다. 다른 조회의 수십 분의 일이다. 빨라서가 아니라 **매칭되는 핸들러가 없어 즉시 405를 돌려준** 것이었다. 앱은 `/equipment/{userId}`를 부르는데 서버에는 `/equipment`만 있었다.

앱은 이 실패를 `.catch(() => {})`로 삼켜서 화면에는 아무것도 드러나지 않았다. 사용자는 실패하는 요청에 p75 기준 0.7초를 기다렸고, 서버에서 장비 착용 상태를 한 번도 읽어 오지 못했다. 장비 해제 경로도 서버 스펙과 어긋나 있었지만, 조회가 늘 비어 있으니 해제 분기를 탈 일이 없어 RUM에 잡히지도 않았다. **조회를 고치면 해제 실패가 드러날 것**이라 둘을 함께 고쳐야 한다고 적었다.

<Callout label="너무 빠른 응답도 신호다">

p99가 1ms대인 조회는 성능이 좋은 게 아니라 **일을 안 한 것**일 수 있다. [초록인데 깨졌다](/research/green-but-broken)의 "너무 빠른 초록"과 같은 결이다. 1.x 코드에는 이 경로 불일치가 지금도 그대로 있다 — 1.x가 동결되며 종결 없이 남았다.

</Callout>

### 4.3 토큰 만료 뒤의 401이 성공보다 느렸다

토큰이 만료된 뒤 갱신 전에 나간 요청들이 401을 받았는데, 이 실패 요청의 앱 p95가 약 1.2초로 **성공 요청보다 느렸다.** 실패를 1초 넘게 기다린 뒤 갱신하고 다시 쏘는 셈이다. 갱신 시점을 앞당기면 이 대기가 통째로 사라진다.

## 5. 서버가 조립하면 — 제안과 반영

같은 날 화면별로 "앱이 원본을 받아 직접 계산·조립하는 자리"를 일곱 군데 찾고, 서버가 완성된 형태로 주면 무엇이 사라지는지 정리했다. 눈에 띈 것은 **서버가 이미 절반을 주고 있었다**는 점이다.

- 리그 랭킹 응답(`LeagueMemberResponse`)은 `isPinned`는 주면서 `isFriend`는 안 줬다. 그래서 랭킹 행에 친구 배지 하나 붙이려고 친구 목록을 통째로 받아 앱에서 대조했다.
- 친구 **검색** 응답에는 관계(`relation`) 필드가 있는데 **프로필** 응답에는 없었다. 그래서 친구 프로필은 한 사람과의 관계 셋(친구인가·핀인가·요청 보냈나)을 알려고 목록 세 개를 통째로 받아 각각 훑었다. 화면의 주인공인 프로필 본체(p99 444ms)보다 관계 표시용 목록(`pins` p99 1,695ms)이 화면을 더 오래 붙잡았다.

반영 상태를 코드와 커밋으로 확인한 결과다.

| 제안 | 기대 효과 (p99, 구조 계산) | 상태 |
| --- | --- | --- |
| 리그 랭킹 응답에 `isFriend` | 리그 진입에서 `friends`(1,307ms) 제거 | **반영** — GROMO-1630 (#702 서버 · #703 앱, 08-25) |
| 공개 프로필 응답에 `relation` | 친구 프로필에서 목록 3개 제거 | **반영** — GROMO-1631 (#704 서버 · #705 앱, 08-25) |
| 비교 카드 평균을 서버 평균 API로 | 랭킹 2회 제거 + **값 정정** | **반영** — GROMO-1632 (#706, 08-25) |
| 서버가 주간 집중 초 합계를 준다 | 리그·홈 세션 3페이지 기준 3,209 → 1,695ms | 미반영 — 1.x 코드는 지금도 세션 페이징 후 앱에서 합산 |
| 그룹 목록에 멤버 라이브 상태 포함 | 집중 세션 2,161 → 1,695ms, 폴링 부하 4분의 1 | 미반영 — 1.x 코드는 지금도 목록 → 상세 2단계 |
| 목표 달성 스트릭을 서버 필드로 | 홈의 히트맵 순차 조회 체인 제거 | 미반영 — 1.x 코드는 지금도 히트맵을 거슬러 순차 조회 |
| 그룹방의 결과 모달 큐 조회를 첫 렌더 뒤로 | 그룹방 2,684 → 1,360ms (서버 처리는 34ms) | (확인 필요) |
| 통계 타임테이블 집계 API 신설 | 통계 화면 세션 순차 페이징 4곳 제거 | 미반영 — 서버에 해당 엔드포인트 없음 |
| 장비 조회·해제 경로 수정 | 기능 복구 | 미반영 — 4.2 |

필드 추가만으로 끝나는 앞의 셋은 측정 당일 조재영이 서버와 앱을 모두 반영했다. 주간 합계·그룹 라이브 상태처럼 **p99 개선폭이 가장 큰 항목**은 그 뒤 1.x가 동결되면서 착수되지 않았다.

<Callout label="화면 단위 조립 — 1.x에선 제안으로 끝났다">

같은 날 한 걸음 더 나간 안도 적었다. 앱이 데이터 API를 여러 번 부르는 대신, 화면 단위 응답을 조립하는 서버(비즈니스 API)가 데이터 API를 **병렬로** 불러 한 번에 내려주는 구조다. 홈·리그·통계·집중 세션·친구 프로필·그룹방·집중 결과 7개 화면에 `…/overview` 형태의 신규 엔드포인트 8개를 초안으로 그렸다. 이 엔드포인트들은 서버 코드에 없다 — 1.x에서는 제안으로 끝났다.

이후 서버는 화면 조합을 공개 계층(Business)에, 정본과 원자 명령을 데이터 계층(Data)에 두는 경계를 택했다([ADR-022](/adr/adr-022-business-data-boundary)). 이 실측이 그 결정의 근거로 쓰였는지는 (확인 필요). 둘을 나란히 놓으면 비용의 위치가 보인다 — 이 노트가 줄이려 한 것은 **무선망을 건너는 앱→서버 왕복**이고, ADR-022가 비용으로 적은 것은 **서버 안에서 늘어나는 홉**이다. 앞의 것이 p99에서 초 단위, 서버 처리가 수십 ms라는 게 이 측정이 준 비율이다.

</Callout>

## 6. 이 측정의 한계

- **화면 단위 시간은 추정이다.** 엔드포인트별 실측을 호출 구조에 맞춰 조합했다. p95·p99를 조합할 때 각 요청이 **독립적으로** 느려진다고 가정했지만, 실제로는 같은 순간 네트워크가 나쁘면 여러 요청이 함께 느려진다. 병렬 화면의 실제 꼬리는 표의 값보다 조금 낮을 수 있다.
- **표본이 얇은 엔드포인트의 p99는 사실상 최댓값 한두 건이다.** `stats/focus/average`는 p95 587ms → p99 3,150ms로 5배 넘게 튀는데, 추세로 보면 안 되고 개별 확인이 필요하다.
- **집중 결과 화면에서만 느린 호출이 있다.** 이 화면에서 잰 `league/me/ranking`의 p99가 4,426ms로 앱 전체 값(1,695ms)의 2.6배다. 직전 화면(집중 세션, 60초 폴링 중)에서 시작된 요청이 화면 전환 뒤 이 화면에 귀속됐을 가능성이 있지만 **확인되지 않았다.** 합치기 전에 이것부터 봐야 한다고 적었다.
- **세션 페이지 수·그룹 수는 사용자마다 다르다.** 한 주 세션이 100건 미만이면 페이지가 1이라 페이징 개선의 이득이 없다. 이득은 헤비 유저에게 몰린다 — 다만 그쪽이 정확히 지켜야 할 사용자다.
- **렌더·이미지 로딩은 포함하지 않았다.** 네트워크 대기만 다룬다.

## 7. 용어

| 용어 | 뜻 |
| --- | --- |
| RUM | Real User Monitoring. 실사용자 기기에서 잰 성능. 여기서는 요청의 앱 왕복 시간 |
| APM | Application Performance Monitoring. 서버 안에서 잰 요청 처리 시간. 네트워크는 빠진다 |
| p95 / p99 | 값을 작은 순으로 세웠을 때 95% · 99% 지점. "스무 번에 한 번 / 백 번에 한 번은 이보다 느리다" |
| 꼬리 지연 (tail latency) | 분포의 느린 끝. 평균·중앙값에는 안 보이지만 사용자가 체감하는 느림은 여기서 온다 |
| 왕복 (round trip) | 앱이 요청을 보내고 응답을 받기까지. 서버 처리 + 네트워크 + 연결 수립이 모두 들어간다 |
| 직렬 단계 | 앞 응답을 받아야 다음 요청을 보낼 수 있는 단계. 단계마다 왕복 시간이 더해진다 |
| 커서 페이징 | 앞 페이지의 마지막 위치를 받아 다음 페이지를 요청하는 방식. 본질적으로 순차다 |
| N+1 | 목록 1번 + 항목마다 1번씩 N번 조회하는 패턴 |
| `useFocusEffect` | 화면이 다시 보일 때마다 실행되는 React Navigation 훅. 탭 복귀마다 조회가 다시 나간다 |
| 서버 조립 | 앱이 원본을 받아 계산하던 것을 서버가 완성된 값으로 내려주는 것 |
