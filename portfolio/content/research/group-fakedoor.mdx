7월 6일, 그룹 API 10개를 이미 쌓아둔 상태에서 하단 '그룹' 탭을 준비중 안내로 되돌렸습니다. 6월 16일부터 21일까지 엿새 동안 생성·조회·검색·참가·공지·챌린지 API를 몰아 쌓았는데, 정작 붙일 화면이 없었습니다. 26일 뒤에야 백엔드를 다시 손봐 실기능으로 열었고, 6월 16일부터 8월 1일까지 한 달 반 사이에 참가 코드와 비밀번호라는 개념 두 개가 사라졌으며 '유저는 그룹 하나에만 속한다'는 전제도 깨졌습니다. **API가 있다는 것은 기능이 있다는 뜻이 아닙니다.**

하루에 다섯 개씩 병합된 날도 있습니다. 이때 우리가 전제로 깔았던 것은 지금 보면 전부 검증되지 않은 가정이었습니다. 참가는 **참가 코드**(당시 API 명칭은 초대코드)와 그룹 비밀번호로 하고, 검색은 코드 매칭으로 하고, 그룹장이 있고, 유저는 그룹 하나에 속한다. 이 가정들이 API 스펙에 그대로 굳어 있었습니다.

하단 탭에는 `Placeholder` 컴포넌트가 걸려 있었고, 유저가 그룹 탭을 누르면 아무것도 없는 화면이 나왔습니다.

## 7월: 되돌리기로 결정했다 (#145)

7월 6일, 실기능을 붙이는 대신 **탭을 통째로 준비중 안내로 되돌려 수요만 측정하는 Fakedoor**를 택했습니다.

`GroupComingSoonScreen`을 새로 만들어 `RootNavigator`의 그룹 탭을 `Placeholder`에서 이 화면으로 갈아 끼웠습니다. 화면 구성은 캐릭터 하나, 앞으로 만들 기능 3줄(그룹 만들기·참가 / 함께 집중·랭킹 / 콕 찌르기), '아직 준비 중이에요' 배지, 그리고 '출시되면 알림 받기' CTA였습니다. 앱만 바꾼 측정 전용 PR이라 백엔드는 한 줄도 건드리지 않았습니다.

계측은 두 가지를 신경 써 설계했고, 전환 결정에는 쓰이지 않았습니다.

첫째, 이벤트 이름을 기존 `group_viewed`와 분리해 `group_fakedoor_viewed`(탭 진입, `useFocusEffect`)와 `group_notify_requested`('알림 받기' 탭)를 새로 뒀습니다. 기존 이름을 재사용했다면 실기능이 열린 뒤 Fakedoor 시절 진입 수와 실기능 조회 수가 한 지표에 섞여, "그룹 수요가 있었나"라는 질문에 답할 수 없게 됩니다.

둘째, '알림 받기'는 최초 1회만 발사되게 했습니다. `AsyncStorage`에 `groupNotifyRequested` 키를 두고, 이미 있으면 이벤트를 쏘지 않고 '신청 완료' 표시만 유지합니다.

```ts
// 개념 코드 — 1회 가드
const already = await storage.get('groupNotifyRequested');
if (!already) {
  track('group_notify_requested');
  await storage.set('groupNotifyRequested', true);
}
setRequested(true); // 재진입 시에도 완료 상태 유지
```

가드가 없으면 관심 있는 유저 한 명이 버튼을 다섯 번 누른 것과, 유저 다섯 명이 한 번씩 누른 것이 같은 숫자로 보입니다.

이 PR의 핵심 결정은 **레거시 그룹 코드를 지우지 않은 것**입니다. `src/screens/group/*`는 dormant 상태로 남겼습니다. 표면만 닫아두면 되돌리는 비용은 라우트 한 줄이고, 26일 뒤 그 코드를 되살릴지 새로 쓸지는 여는 시점에 정하면 됩니다. 다만 사용처가 사라진 `Placeholder`와 그 때문에 미사용이 된 import들은 함께 정리했습니다.

부수 효과로 JS만 바뀌었기 때문에 OTA로 나갈 수 있었습니다. 기능을 내리는 데 네이티브 빌드와 스토어 심사를 기다릴 필요가 없다는 것도, 되돌리기를 쉽게 고를 수 있었던 이유 중 하나입니다.

## 8월 1일: 백엔드를 먼저 깔았다 (#379)

26일 뒤 실기능 전환에 들어갔습니다. 앱보다 백엔드가 먼저였습니다.

가장 큰 변경은 참여 경로를 2트랙으로 갈랐다는 것입니다.

| 트랙 | 발견 경로 | 참여 방법 |
| --- | --- | --- |
| 공개 그룹 | 이름 검색에 노출 | 검색 후 참여 |
| 비공개 그룹 | 검색에서 제외 | 초대 링크 전용 |

`groups.is_private` 컬럼(V17, `DEFAULT false`)을 넣고, 검색을 다시 썼습니다. 6월에 만든 검색은 코드 매칭이었는데, 이걸 **pg_trgm 유사도 검색**으로 교체했습니다. 이미 닉네임 검색에서 같은 방식을 쓰고 있었으므로 임계값 기본 0.3과 동형 구조를 그대로 맞췄고, 비공개 그룹은 제외하고 `LIMIT 20`을 걸었습니다. 인덱스는 V18에서 `groups.name`에 GIN trgm으로 붙였습니다.

이 지점에서 마이그레이션 하나를 일부러 쪼갰습니다. `ADD COLUMN`의 락과 GIN 인덱스 빌드를 한 파일에 넣지 않고 V17/V18로 분리했습니다. 짧고 강한 락과 길고 무거운 빌드는 성질이 다릅니다. 둘을 한 트랜잭션에 묶으면 실패했을 때 어디까지 적용됐는지가 불투명해집니다.

리뷰가 3라운드(자체·Codex) 돌면서 나온 수정들이 오히려 이 PR의 본체에 가깝습니다.

- **N+1 제거**: `getMyGroups`와 검색이 멤버 수를 그룹마다 따로 세고 있었습니다. count 집계로 접었습니다.
- **직렬화 키 고정**: `isMember`, `isPrivate`가 Jackson 기본 규칙 때문에 이중 키로 나가거나 앱이 기대하는 이름과 어긋날 수 있었습니다. `@JsonProperty`로 못박았습니다.
- **명시적 null 거절**: primitive `boolean` 필드에 명시적 null이 오면 조용히 기본값이 되는 대신 400을 던지게 했습니다. 기본값으로 흘려보내면 유저가 비공개로 만들려던 그룹이 공개로 생성됩니다.
- **실 DB 검증**: 검색 SQL은 `TestPostgres`로 실제 DB에 붙여 테스트했습니다. trgm 유사도는 모킹으로 대체되지 않습니다.
- **dead code 표시**: 참가 코드와 `group_invites`는 이제 안 쓰이므로 주석으로 명시했습니다.

배포 노트에 이 문장을 남겼습니다. "이 배포 시점부터 검색이 코드로는 동작하지 않음(현 앱은 Fakedoor라 실사용 영향 없음)." **탭이 닫혀 있으니 API 계약을 깨는 변경을 유저 영향 0으로 낼 수 있었습니다.** 탭이 열려 있었다면 검색 방식 교체는 OTA 반영 지연과 스토어 심사까지 계산해 앱 릴리스와 시점을 맞춰야 하는 작업이었을 겁니다.

## 같은 날: Fakedoor 철거와 화면 5종 (#382)

백엔드 병합 7시간 뒤에 앱을 올렸습니다. 커밋 순서를 배관 → 진입점 → 화면 → 마감으로 잡았습니다.

```text
da55a8d1  배관 — DTO·groupApi·초대링크 유틸
aecea8ca  진입점·라우트·링크 수신 골격 + 화면 스켈레톤
903a4c6c  그룹 찾기 시트 — 이름 검색·참여
c0bb08d2  그룹 공지 화면 — 목록·작성·수정·삭제
1acdc2df  초대 링크 프리뷰·참여 시트
59b09cd5  그룹 생성 화면 — 공개/비공개 세그먼트
17f34896  그룹방 화면 — 초대 카드·멤버 그리드·나가기
b1ad7de6~49b6af9c  리뷰 반영 8건
```

화면은 `GroupScreen`(분기)·`GroupCreateScreen`·`GroupRoomScreen`·`NoticeScreen`에 시트 3종(`GroupFindSheet`·`GroupInviteSheet`·`NoticeComposeSheet`)입니다. 딥링크는 `RootNavigator`에서 콜드 스타트와 실행 중 두 경로를 모두 받고, 기존 `pendingLink` 버퍼를 재사용했습니다. 초대 링크 생성과 파싱은 `utils/inviteLink` 한 곳으로 단일화했습니다. 링크 포맷이 앱과 서버 양쪽에 흩어지면 어긋나기 때문입니다.

이 배치에서 6월 스펙 두 개를 버렸습니다. **6월 참가 API가 받던 그룹 비밀번호와 참가 코드입니다.** 2트랙 모델에서 공개 그룹은 검색으로 들어오고 비공개 그룹은 링크로 들어오므로, 코드나 비번을 사람이 옮겨 적을 자리가 없습니다. 마감 기준으로 `password` 전송 0건, 하드코딩 색 0건, `@/legacy` import 0건을 확인했습니다.

기능 동작은 배포 순서에 걸려 있었습니다.

- 비공개방 실동작은 백엔드 #379 배포가 선행 조건이었습니다. 그 전에는 `isPrivate`가 무시돼 전부 공개방이 됩니다.
- 초대 링크 랜딩 페이지는 아직 없어서, 실기기 검증은 `gromo://` 스킴을 직접 열어서 했습니다. 랜딩이 404를 가리키던 문제는 별도 작업으로 넘어갔습니다 (→ [초대 링크와 미설치 유저 복원](/research/invite-links)).

## 그리고 '그룹 1개 전제'가 깨졌다 (#383)

10분 뒤 병합된 스택 후속에서 6월의 마지막 전제를 걷어냈습니다. 유저가 그룹 하나에만 속한다는 가정이었습니다.

`GroupListScreen`을 새로 만들되 **가입 그룹이 2개 이상일 때만** 보여주기로 했습니다. 1개인 유저는 기존 UX를 그대로 씁니다. 목록 화면을 항상 끼우면 대다수 유저에게 탭 하나가 더 생기고, 안 끼우면 다중 소속 유저가 갇힙니다. 분기 조건을 데이터에 두는 쪽을 골랐습니다. `GroupRoom`을 라우트로 승격하고 원형 백버튼을 붙였으며, `⋯` 메뉴에 '그룹 전환·추가'를 넣어 초대와 검색 양쪽에서 추가 참여를 열었습니다.

그룹방에는 챌린지 섹션이 붙었습니다. `ChallengeCard`의 진행 3상에서 **'—'와 0분을 구분한 것**이 핵심입니다. 아직 데이터가 없는 것과 0분을 기록한 것은 다른 사실인데, 둘을 같은 `0`으로 그리면 유저는 남이 안 했다고 읽습니다. 상한과 중복은 서버 에러 코드로 분기했습니다.

```text
GROUP_LIMIT_EXCEEDED       # 가입 그룹 상한 초과
ACTIVE_CHALLENGE_EXISTS    # 같은 카테고리 진행 중 챌린지 존재
```

그런데 코드·UI 리뷰 2종에서 **HIGH 5건을 포함해 25건 이상**이 나왔습니다. 반영 커밋 3개로 정리한 내용이 전환 일원화·백버튼·문구·status 계약·중복 챌린지 차단 등입니다. 같은 배치의 앞선 PR(#382)이 리뷰 8건이었던 것과 비교하면 3배 넘습니다. #382는 **없던 것을 새로 만드는** PR이었고, #383은 **이미 있는 전제를 바꾸는** PR이었습니다. 전제를 바꾸면 그 전제를 깔고 만든 모든 화면이 검토 대상이 됩니다. jest는 264개 전체 그린(신규 약 80개)으로 마감했습니다.

## 배운 것

**1. Fakedoor로 얻는 자유는 두 개인데, 우리가 실제로 쓴 것은 하나입니다.** 하나는 수요를 숫자로 확인할 자유, 다른 하나는 백엔드 계약을 유저 영향 0으로 깨뜨릴 자유입니다. 회수한 것은 두 번째입니다. 계측은 설계까지 해놓고도 전환 판단에 쓰이지 않았습니다.

**2. 되돌리기와 삭제를 가르는 기준은 "다시 쓸 것인가" 하나입니다.** 유저에게 보이는 표면은 닫되, 화면 코드는 dormant로 남기고 사용처가 사라진 것만 그 자리에서 지웠습니다. 26일 뒤 재작성에서 레거시 화면을 그대로 쓰지는 않았지만(#382 마감 기준 `@/legacy` import 0건), 되돌리기를 커밋 한 줄로 유지한 덕에 되살릴지 새로 쓸지를 전환 시점에 고를 수 있었습니다.

**3. 새로 만드는 PR보다 전제를 바꾸는 PR이 비싸고, API를 먼저 쌓으면 그 비용을 나중에 냅니다.** 6월의 참가 코드·그룹 비밀번호·코드 매칭 검색·그룹 1개 전제는 검증 없이 스펙으로 굳었다가 8월에 전부 폐기됐고, 그 값을 #383의 리뷰 분량으로 냈습니다. 백엔드(#379) → 실기능 전환(#382) → 멀티 그룹(#383) 순으로 스택을 쌓아 각 단계를 squash 머지하고 base를 옮긴 덕에, 이 비용이 한 PR에 몰리지는 않았습니다.
