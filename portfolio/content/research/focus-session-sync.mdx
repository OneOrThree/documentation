집중 세션을 서버와 어떻게 동기화할지 검토하면서 "실시간이니까 WebSocket"이라는 직관을 먼저 검증했고, 반대 결론이 나왔습니다. 이 노트는 그 판정 과정과, WS 없이 신뢰성을 올리기 위해 무엇을 쟀고 무엇을 바꿨는지의 기록입니다. 결론부터 적으면 이렇습니다.

- 이 앱의 정상 시나리오는 "폰을 내려놓고 집중"입니다. iOS는 백그라운드에서 앱을 suspend하고 소켓을 끊습니다. 그래서 **연결 생존을 세션 생존의 증거로 쓸 수 없습니다.**
- 우리가 실제로 가진 문제는 전송 방식 문제가 아니라 신뢰성 문제(생존 증명·멱등·내구 큐)와 표시 문제(폴링 팬아웃)였습니다. 둘 다 HTTP 안에서 풀립니다.
- 생존 증명은 전송 채널이 아니라 **임대 계약(lease)** 으로 해결했습니다. 하트비트로 갱신되는 TTL입니다.

## 판정: 세 축을 먼저 재고 방식을 골랐습니다

전송 방식(폴링·롱폴링·SSE·WebSocket)은 "서버가 클라에게 먼저 말을 걸 수 없다"는 HTTP의 제약을 각기 다른 비용으로 우회한 것입니다. 그래서 방식을 먼저 고르는 대신, 선택을 결정하는 세 축을 먼저 측정했습니다.

| 축 | 일반 계보가 WS로 가는 전제 | 우리 서비스의 실제 값 |
| --- | --- | --- |
| 이벤트 빈도 | 이벤트가 잦다(초 단위) | 집중 start/stop, **분 단위** |
| 지연 허용치 | 지연이 곧 UX 손해 | 60초 지연도 사용자가 인지 못 함 |
| 클라 생존 패턴 | 클라가 계속 떠 있다 | **suspend가 정상 동작** |

세 전제가 전부 뒤집혀 있었습니다. 여기서 파생되는 결론이 세 개였습니다.

1. 이벤트가 분 단위면 푸시가 절약하는 것은 "변화 없는 응답"뿐입니다. 그건 조건부 요청(ETag/304)으로도 거의 같은 크기까지 줄어듭니다.
2. 필요한 순간이 foreground 한정이면, WS의 백그라운드 재연결·재동기화 상태 기계가 결국 "복귀 시 폴링 1회"와 같은 코드로 수렴합니다. SSE의 `Last-Event-ID`, WS의 수동 스냅샷 재동기화, 폴링 1회가 셋 다 같은 자리로 모입니다.
3. 그래서 계보를 역방향으로 걸어(WS → 폴링) **20~30초 조건부 요청 폴링**이 우리 조건의 최적점이 됩니다.

남은 문제가 하나 있었고, 그게 이 노트의 본론입니다. 폴링으로는 **세션이 아직 살아 있다는 증명**을 얻을 수 없습니다. 그런데 WS로도 얻을 수 없습니다. 소켓이 살아 있어도 집중이 아닐 수 있고(앱만 켜둔 상태), 소켓이 죽어도 집중일 수 있습니다(폰을 뒤집어 놓은 상태 — 이게 우리의 정상 시나리오입니다). presence와 session liveness는 다른 개념이었습니다.

## 12시간 유령, 그리고 유령이 잡아먹은 정산

가동 중이던 구조는 표시용 마커와 실제 기록을 분리해 두고, 하트비트가 없었습니다.

```text
① POST /focus-session/start   → 표시 전용 마커. 실패해도 묵살(남에게 안 보일 뿐 세션은 진행)
② 블록마다 PATCH cancel + 완료분 통짜 POST → 실제 시간은 클라가 startedAt/endedAt로 제출
③ 60초 폴링 × 3계열(친구·리그·그룹)  → isFocusing은 "열린 세션 행"에서 파생
④ 매시 정각 sweeper            → 12시간을 넘긴 열린 세션만 정리
```

여기서 앱이 강제 종료되면 이렇게 됩니다.

```text
앱 강제종료 → cancel 미전송 → ended_at IS NULL 행 잔존
→ 친구·리그 그리드에 최대 12시간 "집중 중" 유령
→ 라이브 집중시간 표시값은 그동안 계속 증가 (base + (now − focusStartedAt))
```

`ended_at IS NULL`이 곧 "집중 중"이라는 파생 규칙 자체는 값이 쌉니다. 조회 시점마다 계산되니 종료 PATCH가 들어오면 즉시 `isFocusing=false`로 뒤집힙니다(GROMO-610). 문제는 종료 PATCH가 **안 들어오는 경우**의 상한이 sweeper의 12시간이었다는 점입니다.

그리고 이 유령은 표시만 더럽히는 게 아니었습니다. 유저당 라이브 마커가 1개라는 불변식이 서버에 없어서 열린 마커가 여러 개 쌓일 수 있었고, 정산 대기 가드가 "열린 마커가 있으면 기다린다"로 작성돼 있었습니다. 고아 마커 하나가 그 회차 정산을 **12시간까지 붙잡고**, 최악의 경우 자동 환불 시한에 걸려 내기를 무효화했습니다. 이걸 고치면서 가드 대상을 "도는 마커"에서 "반영이 확정되지 않은 세션"으로 넓히고 유예를 5분으로 잡았습니다. 고아 마커가 정산을 붙잡는 시간이 **12시간에서 5분으로** 줄었습니다(GROMO-1287).

측정 없이 얻은 교훈이 아니라, 유령을 사람이 눈으로 보고 티켓을 열어서 얻은 교훈입니다. 그리고 그 원인 어디에도 "WebSocket이 없어서"는 없었습니다.

## 하트비트는 전송이 아니라 임대 계약입니다

해법은 연결 감시가 아니라 리스입니다. 리스는 "일정 시간 유효한 임대 계약, 갱신 없으면 자동 소멸"이고, 분산 시스템에서 반복해 나오는 패턴입니다. GFS 청크 리스, ZooKeeper ephemeral node, DHCP lease, TCP keepalive, Redis TTL presence가 전부 같은 형태입니다. 우리는 세션 행에 마지막 하트비트 시각 컬럼을 추가하고, 값을 이렇게 잡았습니다.

| 파라미터 | 값 | 이유 |
| --- | --- | --- |
| 하트비트 주기 | 3분 | foreground일 때만 전송 |
| 리스 TTL | 10분 | 하트비트 2회 유실까지 허용 + 네트워크 지터 여유 |
| sweeper 주기 | 10분 | 매시 정각 → 10분 주기로 단축 |
| 시계 오차 허용 | 2분 | 클라 시각 클램프의 상한 여유 |

관계식은 `TTL ≥ 주기 × N + 지터`이고, N이 "몇 번의 하트비트 유실을 이탈로 보지 않을 것인가"입니다. TTL을 줄이면 유령이 빨리 사라지지만 두 가지가 나빠집니다. 일시적 오프라인을 이탈로 오탐하고, 하트비트가 **신규 최고빈도 쓰기 경로**가 되면서 row 단위 UPDATE 부하가 늘어납니다. 그래서 TTL은 "유령 소멸 속도"가 아니라 "오탐 허용치"로 정했습니다.

중요한 건 sweeper가 만료 세션의 종료 시각을 무엇으로 잡는지입니다. 기존 sweeper는 `시작 + 12시간`으로 채웠고, 그건 사실이 아닌 값이었습니다(그래서 통계에 반영하지 않는 예외 처리가 붙어 있었습니다). 리스 기반 sweeper는 `마지막 하트비트 + grace`로 채웁니다. 이건 근거가 있는 값이라서 예외 처리가 필요 없습니다.

한 가지는 의도적으로 하지 않기로 했습니다. **백그라운드에서 하트비트를 보내려고 시도하지 않는 것**입니다. iOS suspend 타이밍은 비결정적이라 "보내려고 했는데 못 보낸" 상태와 "보낼 필요가 없던" 상태를 구분할 수 없습니다. 대신 AppState가 active로 복귀할 때 즉시 1회 보냅니다. 하트비트 중단은 버그가 아니라 계약입니다.

## 표시 상태와 정산을 분리했습니다

리스를 도입하면서 가장 오래 붙잡은 질문이 이것이었습니다. 리스가 만료되면 그 시간을 몰수하는가?

아니라고 정했습니다. **리스 만료는 "표시 상태"의 소멸이지 "사실"의 소멸이 아닙니다.** 만료는 그리드에서 사라진다는 뜻이고, 집중 시간 정산은 별도 규칙(away-credit)으로 처리합니다. 이 분리를 하지 않으면 "완전한 서버 권위"와 "폰을 내려놓아도 인정되는 집중"이 정면으로 충돌합니다. 완전 검증은 포기하고 **bounding**으로 타협했습니다.

시간은 클라가 주장하고 서버가 세 항으로 클램프합니다.

```text
endedAt ≤ min( 클라 주장, last_heartbeat_at + grace, now + 시계오차 )
```

각 항이 막는 게 다릅니다.

| 항 | 막는 것 |
| --- | --- |
| 클라 주장 | 정상 케이스. 서버가 사용자 기록을 부풀리지 않음 |
| `last_heartbeat_at + grace` | 앱이 죽은 뒤 구간을 소급 주장하는 것 |
| `now + 시계오차` | 미래 시각 제출, 기기 시계 조작 |

여기에 세션 겹침 금지를 더합니다. 클램프가 완전한 위조 방어는 아니지만, **지급 계층만이라도** 상한을 갖는다는 게 중요합니다.

재전송 중복 적립은 멱등키로 막습니다. 클라가 블록마다 `client_key`를 붙여 at-least-once로 보내고, 서버는 DB의 partial unique 제약으로 중복을 걸러냅니다. 휴리스틱 dedup을 제약으로 승격시킨 것입니다. 여기서 얻은 교훈이 하나 더 있었습니다. 재전송(같은 블록)과 역순 도착(다른 블록)을 서버가 구분할 수 없는데 마커 id를 재사용하면서 "멱등"이라고 부른 구간이 있었고, 그건 멱등이 아니라 적립 유실이었습니다. 구분할 수 없다면 재사용하지 않는 게 답이었습니다.

오프라인·강제 종료 시 유실은 클라이언트 아웃박스로 막습니다. 완료 블록만 큐에 넣는 게 아니라 **cancel 의도까지** 스토리지에 영속화한 뒤 foreground 복귀 시 flush합니다. 기존 업로드 큐는 상한이 50건이고 초과분을 버리는 정책이었는데, 버리는 대신 합산 보존하는 쪽을 검토 중입니다.

## 전송을 바꾸기 전에 팬아웃을 없앴습니다

표시 문제는 별도 트랙으로 처리했습니다. 라이브 정보 조회 자체는 이미 배치로 정리돼 있었습니다. 친구 목록에 라이브 필드를 붙일 때 `userId → 라이브정보` 맵을 1회 배치로 도출하는 공통 헬퍼를 만들고(GROMO-822), 리그 랭킹이 그대로 재사용했습니다(GROMO-824). 진행 중 세션의 태그명은 LEFT JOIN FETCH로 N+1을 막았습니다.

문제는 남아 있던 **클라 쪽 팬아웃**이었습니다. 친구·리그·그룹 세 계열이 각자 60초 주기로 폴링하고, 화면마다 겹치는 유저를 중복 조회했습니다. 분당 요청이 고정 4~5건 + 계열별 N이었습니다. 바꾼 방향은 전송 전환이 아니라 요청 합치기입니다.

| 항목 | 이전 | 이후 |
| --- | --- | --- |
| 요청 계열 | 친구·리그·그룹 3계열 | 소셜 요약 단일 배치 엔드포인트 |
| 주기 | 60초 고정 | 20~30초 + AppState 게이팅 |
| 변화 없을 때 | 전체 페이로드 재전송 | `If-None-Match` → 304, 본문 0바이트 |

주기를 60초에서 20~30초로 **줄이면서도** 트래픽이 내려갑니다. 대부분의 응답이 304이기 때문입니다. 조건부 요청은 HTTP 캐싱과 같은 메커니즘의 다른 용도일 뿐인데, "실시간 체감"을 사는 데 가장 값이 싼 수단이었습니다.

부수적으로 정리한 것도 있습니다. 빌드 스크립트에 `spring-boot-starter-websocket`이 들어 있었는데 쓰는 코드가 없었습니다. WS를 안 쓰기로 판정한 뒤에도 남아 있던 팬텀 의존성이라 걷어냈습니다.

## WebSocket이 정당해지는 조건, 그리고 남은 트레이드오프

"안 쓴다"가 "영원히 안 쓴다"는 아닙니다. 판정을 재검토할 트리거를 미리 명문화해 뒀습니다.

- **양방향이 필요해질 때** — 채팅, 공동 집중방
- **초 단위 UX가 필요해질 때** — 베팅 틱
- **10초 미만 주기 요구가 생길 때** — 그 지점에서 폴링은 더 이상 싸지 않습니다

그때는 SSE가 아니라 WS입니다. React Native에 WebSocket이 내장돼 있고 SSE는 폴리필이 필요하다는, 아키텍처 선택에 실제로 무게를 갖는 이유가 있습니다. 그리고 그때 넘어야 할 벽도 미리 적어 뒀습니다. 서블릿 필터는 핸드셰이크를 지키지 못하므로 인증이 이원화됩니다(HandshakeInterceptor 또는 CONNECT 프레임 인증으로 필터 로직을 공유 컴포넌트로 뽑아야 합니다). 그리고 단일 인스턴스 simple broker는 스케일아웃되지 않으므로 Redis pub/sub 릴레이로 넘어가는 전환점이 필요합니다.

정직하게 남겨 둘 것도 있습니다.

- **away-credit 사용자의 실종** — 방해 차단 실드를 켜고 장시간 폰을 놓아둔 사용자는 리스가 만료돼 그리드에서 사라집니다. 정산은 되지만 남에게 안 보입니다. 이걸 그냥 수용할지, 실드 구간에만 TTL을 연장할지 아직 답이 없습니다. 표시와 정산을 분리한 대가입니다.
- **종료 경로 전환 범위** — 마지막 블록만 PATCH로 바꿀지, 블록 회전 전체를 대체할지. 마커 회전(GROMO-873)은 "구 마커 마감 전에 신 마커 오픈"을 정상 흐름으로 쓰기 때문에 여기를 잘못 건드리면 정상 동작이 500이 됩니다.
- **죽은 필드** — 방해 횟수·방해 시간 필드가 스키마에는 있고 실측 배선이 없습니다. 배선할지 폐기할지 결정이 남았습니다.

가장 크게 배운 건 방법론입니다. "실시간처럼 보이는 문제"를 신뢰성 문제와 표시 문제로 쪼개고 나면, 남는 질문에 전송 방식이 거의 등장하지 않습니다. 전송 방식은 세 축(이벤트 빈도 × 지연 허용치 × 클라 생존 패턴)을 잰 뒤의 종속 변수였습니다.
