고아 라이브 마커 하나가 그 회차 정산을 최대 12시간 붙잡았고, 최악의 경우 자동 환불 시한에 걸려 내기가 무효화됐습니다. 원인 어디에도 "WebSocket이 없어서"는 없었습니다. 하트비트/리스(TTL 10분·갱신 3분)와 20~30초 조건부 요청 폴링으로 유령 "집중 중"의 상한을 12시간에서 분 단위로, 정산 가드를 12시간에서 5분으로 줄였습니다. iOS suspend가 이 앱의 정상 시나리오("폰을 내려놓고 집중")인 이상 남는 문제는 신뢰성(생존 증명·멱등·내구 큐)과 표시(폴링 팬아웃)였고, 둘 다 HTTP 안에서 풀렸습니다. 리스 TTL·하트비트 주기와 sweeper 교체는 반영됐고, grace 값 고정과 아웃박스 초과분 처리는 미반영입니다.

## 12시간 유령, 그리고 유령이 잡아먹은 정산

모니터링이 아니라 사람이 그리드에 떠 있는 유령을 눈으로 보고 티켓을 열었습니다. 당시 가동 중이던 구조는 표시용 마커와 실제 기록을 분리해 두고, 하트비트가 없었습니다.

```text
① POST /focus-session/start   → 표시 축 라이브 마커. 전송 실패해도 세션은 진행
② 블록마다 PATCH cancel + 완료분 통짜 POST → 실제 시간은 클라가 startedAt/endedAt로 제출
③ 60초 폴링 × 3계열(친구·리그·그룹)  → isFocusing은 ended_at IS NULL인 라이브 마커에서 파생
④ 매시 정각 sweeper            → 12시간을 넘긴 열린 마커만 정리
```

여기서 앱이 강제 종료되면 이렇게 됩니다.

```text
앱 강제종료 → cancel 미전송 → ended_at IS NULL 라이브 마커 잔존
→ 친구·리그 그리드에 최대 12시간 "집중 중" 유령
→ 라이브 집중시간 표시값은 그동안 계속 증가 (base + (now − focusStartedAt))
```

라이브 마커의 `ended_at IS NULL`을 곧 "집중 중"으로 읽는 파생 규칙 자체는 값이 쌉니다. 조회 시점마다 계산되니 종료 PATCH가 들어오면 즉시 `isFocusing=false`로 뒤집힙니다(GROMO-610). 문제는 종료 PATCH가 **안 들어오는 경우**의 상한이 sweeper의 12시간이었다는 점입니다.

표시 전용이라고 믿었던 이 마커가 정산 대기 가드에 물려 있었습니다. 가드는 "열린 마커가 있으면 기다린다"였으니, 그 12시간이 그대로 정산 대기 시간이 됐습니다. 고아 마커 하나로 그 회차 정산이 **최대 12시간 지연**됐고, 자동 환불 시한을 넘기면 내기가 무효 처리됐습니다.

고치면서 유저당 라이브 마커 1개 불변식을 서버에 세웠습니다. 마커 회전 구간(구 마커 마감 직전의 짧은 겹침)은 예외로 두고, 그 밖의 시점에 열린 마커가 2개 이상이면 위반으로 봅니다. 가드 대상도 "도는 마커"에서 "반영이 확정되지 않은 세션"으로 넓히고 유예를 5분으로 잡았습니다. 고아 마커가 정산을 붙잡는 시간이 **12시간에서 5분으로** 줄었습니다(GROMO-1287).

## 판정: 세 축을 먼저 재고 방식을 골랐습니다

이 사건을 고치기 전에, 실시간 계보가 WS로 향하는 전제 세 개를 우리 서비스의 실제 값으로 다시 쟀습니다.

| 축 | 일반 계보가 WS로 가는 전제 | 우리 서비스의 실제 값 |
| --- | --- | --- |
| 이벤트 빈도 | 이벤트가 잦다(초 단위) | 집중 start/stop, **분 단위** |
| 지연 허용치 | 지연이 곧 UX 손해 | 60초 지연도 사용자가 인지 못 함 |
| 클라 생존 패턴 | 클라가 계속 떠 있다 | **suspend가 정상 동작** |

세 전제가 전부 뒤집혀 있었고, 여기서 결론 세 개가 나왔습니다.

1. 푸시가 절약하는 것은 "변화 없는 응답"뿐이고, 그건 조건부 요청(ETag/304)으로도 거의 같은 크기까지 줄어듭니다.
2. 필요한 순간이 foreground 한정이면, WS의 백그라운드 재연결·재동기화 상태 기계가 결국 "복귀 시 폴링 1회"와 같은 코드로 수렴합니다. SSE의 `Last-Event-ID`, WS의 수동 스냅샷 재동기화, 폴링 1회가 도착하는 자리가 같습니다.
3. 그래서 계보를 역방향으로 걸어(WS → 폴링) **20~30초 조건부 요청 폴링**이 우리 조건의 최적점이 됩니다.

남은 문제는 하나였습니다. 폴링으로는 **세션이 아직 살아 있다는 증명**을 얻을 수 없습니다. 그런데 WS로도 얻을 수 없습니다. 소켓이 살아 있어도 집중이 아닐 수 있고(앱만 켜둔 상태), 소켓이 죽어도 집중일 수 있습니다(폰을 뒤집어 놓은 상태, 곧 우리의 정상 시나리오입니다). presence와 session liveness는 다른 개념이었습니다.

## 하트비트는 전송이 아니라 임대 계약입니다

리스는 일정 시간만 유효한 임대 계약으로, 갱신이 없으면 자동 소멸합니다. 분산 시스템에서 반복해 나오는 패턴입니다. GFS 청크 리스, ZooKeeper ephemeral node, DHCP lease, TCP keepalive, Redis TTL presence가 전부 같은 형태입니다. 우리는 세션 행에 마지막 하트비트 시각 컬럼을 추가하고, 값을 이렇게 잡았습니다.

| 파라미터 | 값 | 이유 |
| --- | --- | --- |
| 하트비트 주기 | 3분 | foreground일 때만 전송 |
| 리스 TTL | 10분 | 하트비트 2회 유실까지 허용 + 네트워크 지터 여유 |
| sweeper 주기 | 10분 | 매시 정각 → 10분 주기로 단축 |

관계식은 `TTL ≥ 주기 × N + 지터`이고, N이 "몇 번의 하트비트 유실을 이탈로 보지 않을 것인가"입니다. TTL을 줄이면 유령이 빨리 사라지지만 두 가지가 나빠집니다. 일시적 오프라인을 이탈로 오탐하고, 하트비트가 **신규 최고빈도 쓰기 경로**가 되면서 row 단위 UPDATE 부하가 늘어납니다. 그래서 TTL은 오탐 허용치를 기준으로 정했습니다.

sweeper가 만료 세션의 종료 시각을 무엇으로 잡느냐도 함께 바꿨습니다. 기존 sweeper는 `시작 + 12시간`으로 채웠고, 그건 사실이 아닌 값이었습니다(그래서 통계에 반영하지 않는 예외 처리가 붙어 있었습니다). 리스 기반 sweeper는 `마지막 하트비트 + grace`로 채웁니다. 이건 근거가 있는 값이라서 예외 처리가 필요 없습니다.

한 가지는 의도적으로 하지 않기로 했습니다. **백그라운드에서 하트비트를 보내려고 시도하지 않는 것**입니다. iOS suspend 타이밍은 비결정적이라 "보내려고 했는데 못 보낸" 상태와 "보낼 필요가 없던" 상태를 구분할 수 없습니다. 대신 AppState가 active로 복귀할 때 즉시 1회 보내고, 그 사이 하트비트가 끊기는 것은 계약대로 허용합니다.

## 표시 상태와 정산을 분리했습니다

리스를 도입하면서 가장 오래 붙잡은 질문이 이것이었습니다. 리스가 만료되면 그 시간을 몰수하는가?

아니라고 정했습니다. **리스 만료는 "표시 상태"만 소멸시키고 "사실"은 그대로 남깁니다.** 만료는 그리드에서 사라진다는 뜻이고, 집중 시간 정산은 별도 규칙(away-credit)으로 처리합니다. 이 분리를 하지 않으면 "완전한 서버 권위"와 "폰을 내려놓아도 인정되는 집중"이 정면으로 충돌합니다. 완전 검증은 포기하고 **bounding**으로 타협했습니다.

시간은 클라가 주장하고 서버가 세 항으로 클램프합니다.

```text
endedAt ≤ min( 클라 주장, last_heartbeat_at + grace, now + 시계오차 )
```

`grace`는 아직 값을 고정하지 않았고, 리스 TTL과 같은 축에서 정합니다. 각 항이 막는 게 다릅니다.

| 항 | 막는 것 |
| --- | --- |
| 클라 주장 | 정상 케이스. 서버가 사용자 기록을 부풀리지 않음 |
| `last_heartbeat_at + grace` | 앱이 죽은 뒤 구간을 소급 주장하는 것 |
| `now + 시계오차`(2분) | 미래 시각 제출, 기기 시계 조작 |

여기에 기록 세션 축의 겹침 금지를 더합니다(시간이 적립되는 기록 세션끼리 구간이 겹칠 수 없다는 제약이고, 표시용 마커에는 걸지 않습니다). 클램프가 완전한 위조 방어는 아니지만, **지급 계층만이라도** 상한을 갖게 됩니다.

재전송 중복 적립은 멱등키로 막습니다. 클라가 블록마다 `client_key`를 붙여 at-least-once로 보내고, 서버는 DB의 partial unique 제약으로 중복을 걸러냅니다. 휴리스틱 dedup을 제약으로 승격시킨 것입니다. 그전에는 재전송(같은 블록)과 역순 도착(다른 블록)을 서버가 구분할 수 없는데도 마커 id를 재사용하면서 "멱등"이라고 부른 구간이 있었고, 그 구간에서 적립을 유실했습니다. 같은 형태의 선점 유니크를 알림 파이프라인에서도 씁니다([알림 파이프라인 재편](/research/notification-pipeline)).

오프라인·강제 종료 시 유실은 클라이언트 아웃박스로 **50건까지** 막습니다. 완료 블록과 **cancel 의도**를 함께 스토리지에 영속화한 뒤 foreground 복귀 시 flush합니다. 큐 상한 50건을 넘는 분량은 지금도 버려지고, 버리는 대신 합산 보존하는 쪽을 검토 중입니다.

## 전송을 바꾸기 전에 팬아웃을 없앴습니다

표시 문제는 별도 트랙으로 처리했습니다. 라이브 정보 조회 자체는 이미 배치로 정리돼 있었습니다. 친구 목록에 라이브 필드를 붙일 때 `userId → 라이브정보` 맵을 1회 배치로 도출하는 공통 헬퍼를 만들고(GROMO-822), 리그 랭킹이 그대로 재사용했습니다(GROMO-824). 진행 중 세션의 태그명은 LEFT JOIN FETCH로 N+1을 막았습니다.

문제는 남아 있던 **클라 쪽 팬아웃**이었습니다. 친구·리그·그룹 세 계열이 각자 60초 주기로 폴링하니 고정 요청만 분당 3건, 여기에 화면마다 겹치는 유저를 중복 조회하는 계열별 N이 붙었습니다. 바꾼 방향은 요청 합치기입니다.

| 항목 | 이전 | 이후 |
| --- | --- | --- |
| 요청 계열 | 친구·리그·그룹 3계열 | 소셜 요약 단일 배치 엔드포인트 |
| 주기 | 60초 고정 | 20~30초 + AppState 게이팅 |
| 변화 없을 때 | 전체 페이로드 재전송 | `If-None-Match` → 304, 본문 0바이트 |

주기를 60초에서 20~30초로 **줄이면서도** 트래픽이 내려갑니다. 대부분의 응답이 304이기 때문입니다. 조건부 요청은 HTTP 캐싱과 같은 메커니즘이고, "실시간 체감"을 사는 데 드는 비용이 가장 낮았습니다.

부수적으로 정리한 것도 있습니다. 빌드 스크립트에 `spring-boot-starter-websocket`이 들어 있었는데 쓰는 코드가 없었습니다. WS를 안 쓰기로 판정한 뒤에도 남아 있던 팬텀 의존성이라 걷어냈습니다.

## WebSocket이 정당해지는 조건, 그리고 남은 트레이드오프

판정을 재검토할 트리거는 미리 명문화해 뒀습니다.

- **양방향이 필요해질 때** — 채팅, 공동 집중방
- **초 단위 UX가 필요해질 때** — 베팅 틱
- **10초 미만 주기 요구가 생길 때** — 그 지점에서 폴링은 더 이상 싸지 않습니다

그때 고를 것은 WS입니다. React Native에 WebSocket이 내장돼 있고 SSE는 폴리필이 필요하다는 점이 선택을 갈랐습니다. 넘어야 할 벽도 함께 적어 뒀습니다. 인증이 핸드셰이크와 CONNECT 두 층으로 갈리고, 단일 인스턴스 브로커는 스케일아웃되지 않습니다. 두 층 인증과 cross-instance 릴레이의 배선 수준 기록은 [채팅 서버 팬아웃 설계](/research/chat-fanout)에 있습니다.

아직 답을 못 낸 것들은 이렇습니다.

- **away-credit 사용자의 실종** — 방해 차단 실드를 켜고 장시간 폰을 놓아둔 사용자는 리스가 만료돼 그리드에서 사라집니다. 정산은 되지만 남에게 안 보입니다. 이걸 그냥 수용할지, 실드 구간에만 TTL을 연장할지 아직 답이 없습니다. 표시와 정산을 분리한 대가입니다.
- **종료 경로 전환 범위** — 마지막 블록만 PATCH로 바꿀지, 블록 회전 전체를 대체할지. 마커 회전(GROMO-873)은 "구 마커 마감 전에 신 마커 오픈"을 정상 흐름으로 쓰기 때문에 여기를 잘못 건드리면 정상 동작이 500이 됩니다.
- **죽은 필드** — 방해 횟수·방해 시간 필드가 스키마에는 있고 실측 배선이 없습니다. 배선할지 폐기할지 결정이 남았습니다.

가장 크게 배운 건 방법론입니다. "실시간처럼 보이는 문제"를 신뢰성 문제와 표시 문제로 쪼개고 나면 남는 질문에 전송 방식이 거의 등장하지 않고, 전송 방식은 세 축(이벤트 빈도 × 지연 허용치 × 클라 생존 패턴)을 재고 나서 따라오는 결정이 됩니다.
