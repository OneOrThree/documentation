## 1. 09-08 — "느리니까"를 증명하려다 근거를 바꿨다

분리를 정당화하는 첫 문장은 "크론이 느리다"였습니다. 그래서 Datadog APM 의 `scheduled.call` 스팬(dd-java-agent 자동 계측, 샘플 20%)으로 prod 7일(09-01~09-08)을 셌습니다.

| 잡 | 소요 | 비고 |
| --- | --- | --- |
| `sendFinalDeadlineReminders` (일 22:00) | **53.2s** | 대상 384명 → 139ms/명 |
| `sendWeeklyResultNotifications` (월 07:00) | **50.3s** | 대상 384명 → 131ms/명 |
| `sendRankOvertakeNotifications` (매일 19:00) | max **46.0s** | 다른 날은 0.34s, "발송 대상 없음" — 계산 비용 |
| `sendInactiveReturnNotifications` (매일 10:00) | 7.5s | |
| 매 5분 잡 6종 | avg 200~500ms | `BotScheduler` 가 avg 498ms 로 제일 무거움 |
| `rescanBetEventNotifications` (매 15분) | 672회 **전부 대상 0건** | 15분마다 빈손으로 도는 잡 |

큐잉은 일 22:00 KST 버스트(공용 풀 수요 8이 스레드 6을 넘는 틱)에서 최대 **0.44s**, 크론 에러는 dev·prod 7일 **0건**이었습니다. 팬아웃 53s 는 6스레드 중 1개를 1분 점유할 뿐입니다. 이 숫자로는 "느리니까 분리"를 쓸 수 없었습니다. 그래서 근거를 실측이 뒷받침하는 네 가지로 바꿨습니다.

- **가시성.** 크론 23잡 / 26개 표현식이 5파일에 흩어져 있고, 일 09:00 에는 13개가 동시에 발화합니다. 잡 시작·종료 표준 로그가 없고 `elapsedMillis` 는 3개 잡에만 있어서, 대시보드가 읽을 수 있는 건 샘플 20% 스팬뿐입니다.
- **문구.** 푸시 문구 생성 지점 23곳 중 **16곳이 문자열 `+` 연결**입니다. 어순이 코드에 박혀 영어·일본어로 재배열이 안 됩니다.
- **다국어.** 앱은 4개 언어(`ko` `en` `ja` `zh-Hant`)를 지원하는데 서버 `users` 에는 locale 컬럼이 **없습니다**(V1~V49 에 0건).
- **구도.** `notification` 패키지가 **리포지토리 18개 / 8도메인**에 직결돼 있고, data-api 는 DB 서빙만 남긴다는 TO-BE 와 어긋납니다.

같은 실측이 결정 두 개를 냈습니다. **순위 추월 알림(RankOvertake)은 폐기** — 매일 19:00 에 46s 를 스캔하고 prod 실발송은 0건이었습니다. 18개 리포지토리는 알림 소유 3·도메인 15 로 갈라 알림 서버는 도메인 테이블 직결 0, 판정 재료는 Business API 가 발행하는 이벤트와 스냅샷으로 받기로 했습니다. 이 결정 조건표(팬아웃 5분 초과·대상 2,000명 초과·큐잉 5s 초과·주 1건 에러면 재검토)는 `doc/architecture/notification-cron-measurement-2026-09-08.md` 에 그대로 남겼습니다.

### 코드 발견이 설계를 바꾼 자리

HLD §5 스키마(14테이블, 원칙 "큐 = 이력", V45 `notification_sent_logs` 일반화)와 §6 템플릿 규칙(ICU MessageFormat, 폴백 ko, 변환표 23곳 → 22 kind)을 쓰던 중 하나를 더 찾았습니다. **티어명 5종("뽀시래기"…"집중 정복자")과 `formatShortfall`("2시간 30분")도 Java 에 박혀 있었습니다.** 그래서 규칙 하나가 핵심이 됐습니다 — **params 는 원시값(초·티어 레벨·개수)만 담고, 포맷은 렌더러가 locale 별로 한다.** 이 규칙이 없으면 템플릿을 콘솔로 옮겨도 번역할 수 없는 문자열이 봉투에 실립니다.

### 콘솔 인증 D18 — "하드코딩"을 env 로 바꾼 한 가지

콘솔은 link 대시보드에 동거시키기로 했고(D17), 처음 설계는 NextAuth Google + 허용 목록이었습니다. 저는 팀 3명 내부 콘솔에 개인 인증은 과하니 **비밀번호 3개를 하드코딩**하자고 했습니다. 받아들여진 것은 구조(1차 입장 비밀번호 3개 = 팀원별 슬롯이 actor 기록을 대신, 알림 **쓰기**에 2차 비밀번호 1개 10분 유효, 읽기는 1차만)이고, 바뀐 것은 저장 위치 하나입니다 — **코드가 아니라 env(해시)**. 코드에 박으면 깃에 남고, 별도 레포라도 한 번 유출되면 회전이 곧 커밋입니다. 32자 랜덤·실패 5회/10분 잠금도 같이 붙였습니다. 이 결정은 링크 장부의 Q5("Google + 허용목록")를 뒤집는 것이라 그쪽 §7 에도 후속을 적었습니다.

### D19 와 D20 — 하루 만에 뒤집힌 것과 동결한 것

§9 이행 순서를 쓰려고 compose·gradle·워크플로를 실측하니 `redis|kafka|rabbit|sqs` 가 **0건**이었습니다. 1658(브로커)은 미선정, 1661(Business API)은 미착수. "MQ 선행"을 두면 알림 서버가 두 티켓 뒤에 줄을 섭니다. 그래서 **D19(잠정)** — 이벤트 입구는 브로커 무관 어댑터로 두고 첫 단계는 `POST /internal/events`(HTTP, 서비스 토큰)로 시작. 이 결정은 다음날 저녁 브로커가 확정되면서 뒤집혔습니다(§2).

같은 밤 저는 "기존 리팩토링부터 쳐내는 게 낫지 않냐"고 물었고, 근거가 구체적이라 **D20** 으로 박았습니다. 1656(도메인 방향 확정) PR #721 이 열려 있었고, 알림 서버 P2·P4 가 옮길 리스너·정산·리포지토리 배선이 정확히 1656 이 손대는 자리였으며, `notification` 의 리포지토리 직결이 아직 17개 남아 있었습니다. 레이어가 움직이는 동안 옮기면 두 번 옮깁니다. 알림 서버는 설계 동결, 병행은 P0 `users.locale` 과 1658 브로커 조사뿐. [리팩토링 에픽 1643](/research/backend-layering-refactor)이 그렇게 먼저 갔습니다.

## 2. 09-09 — SQS 를 추천받았고 Kafka 도커로 확정했다

1658 범위 1 의 실측은 이렇습니다.

| 항목 | 실측 |
| --- | --- |
| 이벤트 타입 | 6종 (`FriendRequestSent` `FriendRequestAccepted` `GroupChallengeCreated` `GroupBetWon` `GroupBetSessionClosed` `BetResultAcknowledged`) |
| 발행처 | 8곳 |
| MQ 로 갈 수 있는 소비자 | 알림 리스너 5개 — 전부 `AFTER_COMMIT + @Async` |
| **MQ 로 가면 안 되는 소비자** | 2 — `GroupBetEarlySettlementListener`(group 도메인 내부 반응) · `BetResultAckSuppressionListener`(동기·발행 TX 안이어야 함, 1656 에서 못박음) |
| 인프라 | prod EC2 1대, compose = app·nginx·datadog-agent, **브로커·Redis 0** |

비교표의 추천은 **SQS 표준 큐**였습니다. 근거는 두 행 — 운영 부담 0(관리형), 순서 불필요(알림 5종은 유저별 독립 사건이고 멱등 키로 dedup) — 에 1660 링크 서버(Vercel)와 공유 가능이 더해졌습니다. 그 조건에서 RabbitMQ·Kafka 는 "내가 관리할 것을 하나 더 만드는" 선택이라는 판단이었습니다.

저는 Kafka 를 도커로 올리자고 했고, 조건 3개를 듣고 확정했습니다. ① prod t4g 사양은 실측이 필요하다(SSO 만료로 그날은 못 쟀고, 이틀 뒤 t4g.medium 2vCPU·4GB 로 확인돼 A14 사이즈업 권장이 붙었습니다) ② SQS 에 내장된 retention·재시도·DLQ 를 Spring Kafka `DefaultErrorHandler` + `DeadLetterPublishingRecoverer` 로 우리가 구현한다 ③ Vercel 링크 서버는 EC2 브로커에 붙기 어려우니 브로커를 공유하지 않는다. 추천의 근거였던 "운영 인력 0"은 **감수**로 닫혔고, 얻는 것은 리플레이·스트림·벤더 비종속, 서버 분리 시 소비자를 어디 둬도 같은 클라이언트였습니다. 비교표의 Kafka 열이 MSK(관리형 2~3 브로커) 기준이라 단일 노드 컨테이너는 다른 셈이었다는 것도 이때 적었습니다. 메모리가 문제면 Redpanda 로 이미지만 바꾸는 대안을 남겼습니다.

세 가지가 따라 바뀌었습니다. **D19 는 "브로커 확정 뒤 브로커로 바로"** — HTTP 입구는 폴백·수동 재전송·리컨실용으로만 남고, 1659 P1 은 1658 완료 후입니다. 조건 ③의 문구 "클릭 적재는 HTTP 로 data-api 에" 는 다른 세션이 링크 단방향(link → 코어 금지) 위반이라고 지적해 지웠습니다 — 클릭은 link 가 Neon 에 직접 적재하므로 불필요합니다. 그리고 결정 직후 착수는 보류했습니다. 목표 아키텍처 정본이 다른 세션에서 진행 중이라 그것이 확정될 때까지 data-api 수정 티켓부터 처리하기로 했고, 브랜치 `bfeat/GROMO-1658-kafka-events` 는 커밋 0 으로 남았습니다.

## 3. 09-11 — Orca 워커들이 outbox 기반을 깔았다

착수는 이틀 뒤, 코디네이터가 워커를 dispatch 하는 Orca 멀티에이전트 구조로 갔습니다. `bfeat-GROMO-1659-notification-foundation` 워크스페이스 한 곳에서 워커들이 소유 파일만 만지고 `worker_done` 으로 넘겼습니다.

| 워커 | 만든 것 | 로그가 남긴 결함·판정 |
| --- | --- | --- |
| C1 | V51 마이그레이션 4테이블(`event_outbox` `event_outbox_deliveries` `aggregate_versions` `command_idempotency`), `OutboxCommandPort.append` 는 `Propagation.MANDATORY` 로 같은 TX 강제, `allocateVersion` 은 aggregate 행 배타 락, relay 는 선점(TX)→전달(TX 밖)→표시(TX) 3구간 + lease 펜싱, `apache/kafka` KRaft compose 오버레이 | 같은 워크트리에서 소유 아닌 `FilterConfig` 변경으로 `compileTestJava` 가 깨져 escalation |
| C2 | `server/business-api` 무상태 위성 서비스(소스 74·테스트 18·109파일), 계약 yaml 1,484줄 | 컨테이너 실측에서 **필수 시크릿이 없어도 Spring 이 `${...}` 리터럴을 남기고 부팅 성공** → `RequiredConfig` 로 거절. claim 이 큐 commit 후 202 를 주는데 재개 주체가 없어 영구 대기 → 재개 CLI |
| N2 | 기존 알림 크론 17 `@Scheduled` 를 지우지 않고 `notification.dispatch.mode` 스위치(LEGACY 또는 OUTBOX)로 출력만 분기, kind 19종(RANK_OVERTAKE·bot 제외), 요청형 5종은 `BEFORE_COMMIT + MANDATORY` 리스너로 AFTER_COMMIT 유실 차단 | eligibility 는 모르는 kind fail-closed |
| N3 | 알림 서버 콘솔·이관 표면(643/852/757줄), 계약 14 path·18 schema | Docker VM 디스크 포화로 Testcontainers PG 가 exit 1 |
| 리뷰어 r5 | — | P1: 재개 CLI 가 **성공할 때마다 실패로 집계** — `intent.consume()` 이 `completedByLeaseToken=null` 을 박고 직후 `completeClaimIntent` 의 토큰 비교가 `T.equals(null)` → 409 → `failed++` → 컷오버 gate 통과 불가 |

## 남은 규칙 다섯 줄

1. **"느리다"는 분리 근거가 아니라 실측 대상이다.** 큐잉·에러·최장 소요를 먼저 세고, 재검토 트리거를 숫자로 적는다.
2. **params 는 원시값만.** 포맷·어순은 렌더러가 locale 별로 한다. 티어명도 예외가 아니다.
3. **추천과 결정이 다르면 조건을 적는다.** 감수하는 것·얻는 것·되돌리는 길(Redpanda)을 한 줄씩.
4. **읽고 쓰는 행은 처음부터 배타 락으로, 부분 갱신은 `@DynamicUpdate` 로.** Hibernate 는 스냅샷이 같으면 UPDATE 를 생략하고, 다르면 전 컬럼을 쓴다 — 둘 다 예외 없이 조용히 어긋난다.
5. **푸시 전 로컬 게이트 전부, 👍는 신호일 뿐.** squash 머지 뒤 스택은 부모부터 다시 세운다.
