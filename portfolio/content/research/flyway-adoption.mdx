1. `flyway-core`(엔진)만 넣으면 **Flyway 쪽 로그도 에러도 한 줄 없이** 마이그레이션이 미적용되고, 실패는 뒤이은 Hibernate `validate` 단계에서야 드러납니다. 원인은 Spring Boot 4가 오토컨피그를 기술별 모듈로 쪼갠 것이고, 여기에 Flyway 10의 DB별 모듈 분리가 겹쳐 필요한 의존성이 3종으로 늘었습니다.
2. 이미 데이터가 찬 DB에 Flyway를 뒤늦게 붙이는 것은 `baseline` 문제이고, 같은 설정 한 벌이 기존 DB에서는 마킹만, 빈 DB에서는 실제 실행이라는 두 갈래로 동작해야 합니다.
3. dbml에 없다고 드롭 목록에 넣은 `version` 컬럼 2개가 `@Version` 낙관적 락이었습니다. 한쪽은 동시성 테스트가 깨지며 드러났고, 다른 한쪽은 이후 전수 감사에서 걸렀습니다.

## 셸 스크립트 v15~v30이 남긴 문제

전환 전 우리 팀의 DB 스키마 변경 수단은 `docker exec` 로 `psql` 히어독을 밀어넣는 로컬 전용 셸 스크립트였습니다.

```bash
# run-migration-v30.sh — 로컬 전용, gitignore 대상
docker exec -i phone-db psql -U <user> -d dev <<'EOF'
ALTER TABLE focus_sessions ADD COLUMN IF NOT EXISTS local_date date;
EOF
```

`run-migration-v15.sh` 부터 `v30.sh` 까지 쌓이는 동안 세 가지가 걸렸습니다. 스크립트가 로컬 전용이라 지금 dev/prod DB가 몇 번까지 적용됐는지 아무도 몰랐고, 배포마다 사람이 `psql` 을 손으로 때려야 했으며, 빠뜨리면 앱이 죽었습니다. 거기에 `ddl-auto: update`(Hibernate 자동 변경)와 수동 스크립트가 섞이면서 스키마 문서(dbml)와 실 DB가 조금씩 어긋났습니다. `ddl-auto: update` 는 컬럼 삭제·리네임을 못 하고 변경 이력도 남기지 않으니, 남은 선택은 버전 넘버링된 마이그레이션을 코드로 남기고 앱 기동 시 툴이 순서대로 한 번만 적용하게 하는 것뿐이었습니다.

## baseline — 이미 찬 DB에 뒤늦게 붙이기

Flyway의 기본 전제는 "빈 DB에서 V1, V2, V3를 순서대로 다 실행하면 현재 스키마가 완성된다"입니다. 그런데 우리 dev/prod는 이미 손으로 v30까지 적용된 상태입니다. 여기에 Flyway를 그냥 켜면 다음 순서로 기동을 거부합니다.

> 테이블이 잔뜩 있는데 내 이력 테이블(`flyway_schema_history`)은 비어 있다 → 내가 관리하지 않은 스키마다 → 위험하니 기동 거부.

이 충돌을 푸는 게 `baseline` 입니다. `git init` 을 뒤늦게 하면서 "지금 상태를 최초 커밋으로 찍는" 것과 같습니다.

```yaml
# application-dev.yml
spring:
  flyway:
    enabled: true
    baseline-on-migrate: true   # 비어있지 않은 DB면 baseline부터
    baseline-version: 1         # V1을 '기준선'으로 마킹(재실행 안 함)
```

설정은 한 벌인데 동작이 두 갈래로 갈립니다.

| 대상 DB | baseline 동작 | `V1__baseline.sql` |
| --- | --- | --- |
| 기존 dev/prod (스키마 있음) | V1을 "적용됨"으로 마킹만 | 실행 안 됨 (무중단) |
| 빈 DB (신규 환경·CI) | 마킹 불필요 | V1부터 전부 실행 |

그래서 `V1__baseline.sql` 은 반드시 **현재 실 DB의 스냅샷**(`pg_dump --schema-only`)이어야 합니다. 기존 DB에서는 안 돌지만, 새 환경에서는 이 V1이 실제로 돌아 지금과 똑같은 스키마를 재현해야 하니까요. 우리 베이스라인은 33개 테이블 + `pg_trgm` 확장 + 닉네임 trgm GIN 인덱스로 떨어졌습니다. 이후 스키마 변경은 이 파일을 V1으로 두고 V2부터 번호를 이어 붙였습니다.

프로필별로는 이렇게 나눴습니다.

| 프로필 | Flyway | `ddl-auto` | 의도 |
| --- | --- | --- | --- |
| `local` | OFF | `update` | 현행 동작 불변 — 로컬 실험을 막지 않는다 |
| `ci` | OFF | `create-drop` | 테스트는 매번 빈 스키마에서 시작 |
| `dev`·`staging` | ON + baseline | `validate` | 배포 경로와 validate 기동을 먼저 여기서 확인 |
| `prod` | ON + baseline | `update` → `validate` | 드리프트를 기동 시 조기 탐지 |

prod의 `ddl-auto` 를 `validate` 로 올린 건 의도된 위험 감수였습니다. 그간 `update` 로 운영돼 엔티티와 실 DB가 어긋나 있을 수 있고, 그러면 기동이 실패합니다. 드리프트가 나오면 후속 마이그레이션으로 해소한 뒤 prod에 올리는 순서를 못박았습니다. 배포된 베이스라인 파일을 수정 금지로 둔 이유는 Flyway가 체크섬으로 검증하기 때문이고, 이 규칙을 어겼을 때 무슨 일이 생기는지는 [실패한 배포도 DB는 이미 바꿔놨다](/research/migration-incidents)에 있습니다.

## Flyway 로그가 한 줄도 없었다

설정을 다 넣고 빈 컨테이너로 배포 경로를 검증했습니다. `V1__baseline.sql` 을 Flyway로 적용하고 `ddl-auto: validate` 로 앱을 띄우는 시나리오입니다.

앱은 기동을 거부했습니다.

```text
ERROR o.s.o.j.LocalContainerEntityManagerFactoryBean - Failed to initialize JPA EntityManagerFactory:
  ... SchemaManagementException: Schema validation: missing table [character_equipment]
```

Hibernate는 빈 스키마에서 엔티티에 대응하는 테이블을 찾지 못해 validate에 실패했습니다. 즉 Flyway가 마이그레이션을 적용하지 않았다는 뜻입니다.

이상한 건 그다음이었습니다. 로그에 Flyway 관련 줄이 단 한 줄도 없었습니다. `flyway_schema_history` 테이블도 생기지 않았습니다. Flyway가 돌면 보통 `Migrating schema "public" to version ...` 같은 로그가 찍히는데, 그게 아예 없다는 건 마이그레이션이 실패한 게 아니라 오토컨피그 빈 자체가 생성되지 않았다는 신호입니다.

- `flyway-core` 는 클래스패스에 있다 — 확인.
- `spring.flyway.enabled=true`, 오토컨피그 제외 설정 없음 — 확인.

결정적 단서는 엉뚱한 로그의 패키지 이름이었습니다. Hibernate 설정 클래스가 `org.springframework.boot.hibernate.autoconfigure.HibernateJpaConfiguration` 로 찍혀 있었습니다. Boot 3.x에서 익숙한 경로는 `org.springframework.boot.autoconfigure.orm.jpa...` 였습니다. 패키지가 `org.springframework.boot.hibernate.autoconfigure` 로 바뀌었다는 건, 기술별로 오토컨피그가 별도 모듈로 쪼개졌다는 뜻입니다. 그 눈으로 클래스패스를 다시 훑었습니다.

```text
org.springframework.boot:spring-boot-hibernate    있음
org.springframework.boot:spring-boot-jpa          있음
org.springframework.boot:spring-boot-jdbc         있음
org.springframework.boot:spring-boot-flyway       없음   ← 여기
```

Spring Boot 4는 거대한 `spring-boot-autoconfigure` 하나에 몰려 있던 오토컨피그를 기술별 모듈로 분리했고, Flyway 오토컨피그는 `spring-boot-flyway` 에 들어 있습니다. 그리고 **엔진인 `flyway-core` 는 이 모듈을 전이 의존성으로 끌어오지 않습니다.** 엔진은 있는데 그것을 부팅에 연결하는 배선이 없으니 아무 일도 일어나지 않은 것입니다.

의존성 3종을 모두 선언하는 것으로 풀렸습니다.

```gradle
// build.gradle
implementation 'org.springframework.boot:spring-boot-flyway'   // Boot 4: 오토컨피그 — 이게 핵심
implementation 'org.flywaydb:flyway-core'                      // 엔진
runtimeOnly    'org.flywaydb:flyway-database-postgresql'        // Flyway 10+: DB별 지원 분리
```

세 번째 줄도 같은 종류의 함정입니다. Flyway 10부터 PostgreSQL 지원마저 별도 모듈로 갈라져서, 이게 없으면 기동 시 `No database found to handle jdbc:postgresql://...` 로 죽습니다. 프레임워크와 라이브러리가 같은 시기에 각자 모듈을 쪼갠 탓에, 밟을 자리가 둘로 늘어난 셈입니다.

`spring-boot-flyway` 를 넣고 다시 띄우니 그제야 로그가 찍혔습니다.

```text
INFO FlywayExecutor - Database: jdbc:postgresql://.../<db> (PostgreSQL 16.14)
INFO DbMigrate - Migrating schema "public" to version "1 - baseline"
INFO DbMigrate - Successfully applied 1 migration to schema "public", now at version v1
INFO PhoneApplication - Started PhoneApplication in 2.7 seconds
```

**재현·판정 방법으로 남길 것**: 어떤 오토컨피그가 실패 로그조차 없이 로그에서 아예 빠져 있다면, `enabled` 값을 의심하기 전에 그 오토컨피그 모듈이 클래스패스에 있는지부터 봅니다. 단서는 로그에 찍히는 새 패키지 이름(`org.springframework.boot.<기술>.autoconfigure`)입니다. 같은 구조 변화에서 나온 다른 사고들은 [Spring Boot 4로 먼저 넘어간 팀의 마이그레이션 노트](/research/springboot4-migration)에 모아 뒀습니다.

## dbml에 없던 컬럼을 지웠더니 동시성 테스트가 깨졌다

Flyway를 켠 뒤, 스키마 문서(dbml)를 권위로 삼아 공통 테이블을 정합했습니다. dbml과 실 DB에 함께 존재하는 공통 테이블 27개 중 컬럼 차이가 있던 20개를 리네임·추가·의미변경·기능제거로 맞추고, 그 결과를 `V2__align_common_columns.sql`(147줄)로 내려 빈 PostgreSQL 16에 `V1 + V2` 를 적용한 뒤 validate 기동으로 검증하는 흐름이었습니다.

이때 dbml에 없는 `version` 컬럼이 둘 걸렸습니다. `user_wallets.version` 과 `groups.version` 입니다. "안 쓰는 낙관락 컬럼인가 보다" 하고 둘 다 드롭 목록에 넣었습니다. 그러자 동시성 테스트가 깨졌습니다.

```text
InGameCurrencyConcurrencyTest > 잔액 100에서 80 차감을 동시에 2회 → 1건만 성공
  expected: 1  but was: 2
```

`version` 은 JPA `@Version` 이 붙은 낙관적 락 컬럼이었습니다. 드롭하면 잔액 100에 대한 80 차감 2건이 모두 성공해 이중 차감이 됩니다.

dbml에 이 안전장치가 빠져 있었습니다. 대체 동시성 전략(비관락 등)이 정해지기 전까지 두 컬럼을 유지하기로 하고, 근거를 코드에 남겼습니다.

```java
// GROMO-671: dbml 은 version 을 누락했으나 낙관락(동시성)이 필요해 유지.
@Version
@Builder.Default
private Long version = 0L;
```

이 정합 PR은 CI 게이트(Checkstyle + SpotBugs + 테스트 606건)까지 그린으로 통과했습니다. 컬럼 드롭을 막은 근거는 **동시성 테스트 한 건**이었습니다. 스키마 "정리"에서 지우려는 컬럼이 단순 데이터인지 락·인덱스·제약처럼 동작을 지탱하는 것인지, 우리는 테스트를 돌려 보고서야 구분했습니다. 단, `groups.version` 이 실제로 발동하는지는 이때 확인하지 않았고, 이후 동시성 전수 감사에서 따로 드러났습니다([낙관적 락은 있는데 작동하지 않는다](/research/concurrency-defense)).

## 최종 배선 — 실행할 명령이 없다

전환을 마치고 가장 많이 받은 질문은 "그래서 Flyway 적용 명령을 어디서 실행하나"였습니다. 답은 실행할 명령이 없다는 것입니다. Flyway는 앱에 내장돼 기동 시 JPA 초기화 직전에 자동 적용됩니다. 알아야 할 건 파일 위치뿐입니다.

| 파일 | 역할 |
| --- | --- |
| `build.gradle` | 의존성 3종 (오토컨피그 + 엔진 + PostgreSQL) |
| `application-dev.yml` 등 프로필 설정 | `spring.flyway.enabled` · `baseline-on-migrate` · `baseline-version` — 여기서 켜고 끈다 |
| `application.yml`(base)·`application-ci.yml` | `flyway.enabled: false` — local/CI 미개입 |
| `src/main/resources/db/migration/` | `V1__baseline.sql`, `V2__align_common_columns.sql` … 실제 SQL |

그래서 흐름은 **머지 = 배포 = Flyway 자동 적용**이고, 사람은 배포 로그에서 `Successfully applied N migration` 한 줄만 확인하면 됩니다. 새 스키마 변경은 `V<N>__<설명>.sql` 을 추가하는 것으로 끝나고, 이력은 `flyway_schema_history` 에 남습니다. 레거시 `run-migration-v*.sh` 는 아카이브했습니다.

남은 리스크는 둘입니다. 하나는 배포 환경의 설정 파일 일부가 저장소에 없어서(gitignore) Flyway 설정 주입을 환경 쪽에서 따로 확인해야 한다는 점, 다른 하나는 Flyway가 rollback을 자동 지원하지 않는다는 점입니다. 후자에 대해서는 마이그레이션과 짝이 되는 되돌리기 SQL을 함께 준비해 두는 방식을 검토했습니다. 그리고 실제로 이후 순서·체크섬 쪽 사고를 겪었습니다([실패한 배포도 DB는 이미 바꿔놨다](/research/migration-incidents)).
