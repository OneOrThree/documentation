PR #574(V45)에서 `notification_sent_logs` 에 `(user_id, kind, subject_id)` 유니크를 걸고, 발송보다 먼저 행을 만드는 `선점 → 발송 → 확정` 으로 순서를 뒤집었습니다. 같은 PR에서 `BET_RESULT` 배치 크론 2회(08:00·13:00)를 폐지하고 정산 커밋 후 이벤트 + 15분 재훑기로 교체했으며, 죽은 선점은 10분 리스로 회수합니다. 결과 알림 도착은 하루 2회 배치 창에서 정산 커밋 직후 몇 초로 바뀌었고, 새는 건은 15분 재훑기가 다시 발송합니다.

## 발송 후 기록은 중복도 유실도 못 막는다

2026-07-20 시점의 구조를 감사하며 실측한 한계는 두 가지입니다. 발송 실패 건은 재시도도 이력도 없어 그대로 유실됐고 catch-up도 불가능했습니다(GROMO-622). 중복 방지는 `sent_log` 쿨다운(추월 48h·주 2회)뿐이라, 같은 사건 두 번과 다른 사건 두 번을 구분하지 못하는 시간 축 dedup이었습니다.

크론 전체가 스케줄러 스레드 1개에 직렬로 묶여 있고, 알림 서비스 4종이 `@Transactional(isolation = REPEATABLE_READ)` 루프 안에서 유저당 동기 REST POST를 보내고 있었습니다. 이런 배치 층의 한계는 [배치 처리의 함정들](/research/batch-traps)에 정리했습니다(GROMO-893·900). 헥사고날 포트/어댑터 구조는 유지돼 있었고 `ScreenTimeNotificationPort` 만 NoOp(GROMO-902)이었으니, 도메인은 깨끗했고 문제는 전부 발송 파이프라인에 있었습니다.

아팠던 건 두 번째, 중복 방지 쪽입니다. 기록이 발송 **뒤에** 남으므로, 기록은 "보냈다"의 증거일 뿐 "보내도 되는가"의 판단 근거가 못 됩니다. 그리고 dedup 키가 사건을 식별하지 못하면 같은 종류의 사건이 연달아 일어날 때 나중 사건이 앞 사건과 중복으로 판정돼 조용히 사라집니다. 사용자에게는 "알림이 안 왔다"로, 로그에는 "정상 dedup"으로 보입니다.

## 선점 후 발송으로 뒤집기 (PR #574, V45)

8월 10일 재편에서 순서를 바꿨습니다. `notification_sent_logs` 를 사건 축으로 확장하고, 발송보다 **먼저** 행을 만듭니다.

```sql
-- 사건 축 유니크: 같은 유저의 같은 사건은 한 행만 존재할 수 있다
-- V45: notification_claim_pipeline_shedlock
ALTER TABLE notification_sent_logs
  ADD COLUMN kind       text,
  ADD COLUMN subject_id uuid,
  ADD COLUMN status     text,       -- PENDING / DEFERRED / SENT
  ADD COLUMN claimed_at timestamptz,
  ADD COLUMN group_id   uuid,       -- 묶음 메타
  ADD COLUMN slot_at    timestamptz;

CREATE UNIQUE INDEX ON notification_sent_logs (user_id, kind, subject_id);
CREATE INDEX ON notification_sent_logs (...) WHERE status <> 'SENT';
```

발송 경로는 세 단계가 됩니다.

```text
INSERT ... ON CONFLICT DO NOTHING   -- 선점: 0건이면 남이 이미 잡았다 → 나는 보내지 않는다
      ↓ 1건
FCM 발송
      ↓ 성공                          ↓ 실패
status = SENT                       선점 즉시 반납 (리스 만료를 기다리지 않는다)
```

"최초 1회" 판정은 동기적으로 즉시 반영되는 값에 걸어야 합니다. 렌더 사이클처럼 나중에 반영되는 값에 걸면 두 번째 시도가 그 사이를 통과하고, 서버에서는 이 유니크 인덱스가 그 즉시 반영되는 값입니다. 그 위에 세 가지를 결정했습니다.

**죽은 선점은 10분 리스로 회수합니다.** 선점만 하고 프로세스가 죽으면 그 사건은 영원히 아무도 못 잡습니다. `claimed_at` 기준 10분이 지난 `PENDING` 은 회수 대상이고, 이 만료 규칙 덕에 선점이 영구 점유로 굳지 않습니다.

**발송 실패는 리스를 기다리지 않고 즉시 반납합니다.** 실패를 아는 주체가 실패한 그 프로세스라면, 10분을 기다릴 이유가 없습니다. 즉시 반납하면 다음 재훑기 주기에서 그 사건이 곧바로 다시 발송됩니다.

**묶음 키와 dedup 키를 분리했습니다.** "묶어서 한 번 보내기"와 "같은 사건 두 번 금지"를 한 키로 처리하려니 둘 중 하나는 늘 어긋났습니다. 묶음 메타(`group_id`, `slot_at`)를 따로 두고, 묶음 슬롯은 사건 시각(`settled_at`) 기준으로 계산합니다. 재훑기나 이월이 언제 돌아도 같은 사건이면 같은 묶음에 들어가야 하기 때문입니다. 발송 시각 기준이면 재훑기가 돌 때마다 묶음 경계가 흔들립니다.

조용한 시간에 발생한 사건은 버리지 않고 `DEFERRED` 로 이월해 07:00에 보냅니다. 다만 지나간 모집을 아침에 알려 봐야 소음만 남으므로, 모집 알림은 이월 대상에서 빼고 버립니다.

## 크론을 없애고 이벤트로, 그리고 ShedLock

폐지한 `BET_RESULT` 크론의 자리는 두 경로로 나눴습니다. 정상 경로는 정산 커밋 후 이벤트로 몇 초 안에 도착하고, 15분 재훑기가 이벤트 유실 건, 발송 실패로 반납된 건, 리스 만료로 회수된 건을 훑어 다시 내보냅니다.

이 조합이 성립하는 근거는 선점 dedup입니다. 두 경로가 같은 사건에 동시에 도달해도 유니크 인덱스가 한쪽을 튕겨내므로 이중 발송이 나올 수 없습니다.

멀티 인스턴스 문제도 여기서 닫았습니다. 미접속 복귀 escalation(PR #127) 시점에는 "멀티 인스턴스 배포 시 스케줄 분산 락 필요"가 주의사항으로만 적혀 있었습니다(GROMO-565). 이번에 ShedLock을 JDBC provider + `usingDbTime()` 으로 넣고 전 크론에 고유 락 이름을 붙였습니다. 그리고 다음에 크론이 추가될 때 애노테이션을 빼먹는 걸 사람이 기억하지 않도록, 리플렉션으로 스케줄 메서드를 훑어 락 애노테이션 누락을 잡는 테스트를 함께 넣었습니다.

사일런트 푸시(data-only)도 이때 붙였습니다. `notification` 없이 `content-available: 1`, `apns-push-type: background`, priority 5로 보냅니다. 표시 알림용 필터(조용한 시간·설정 필터)를 타면 안 되므로 전용 경로로 분리했습니다.

## 배선이 세 층에서 각각 새고 있었다

재편 앞 한 달 동안, 알림 로직 밖에서 난 배선 실패 3종이 모두 "알림이 안 온다"라는 같은 증상으로 보였습니다.

**① 프로퍼티 키가 env 변수명을 그대로 정한다 (GROMO-528, PR #107).** GROMO-528은 푸시 파이프라인 전반을 묶은 티켓이라 [배치 처리의 함정들](/research/batch-traps)의 리그 알림 크론 2종도 같은 키를 답니다. `application.yml` 이 gitignore라 배포 이미지에 없고 시크릿은 env로만 주입하는 구성이었습니다. 코드의 키는 `fcm.service-account-json-base64` 였는데 주입한 env는 `FCM_SERVICE_ACCOUNT_JSON` 이었습니다. Spring은 프로퍼티 키를 기계적으로 변환해 env 이름을 만들기 때문에, 그 키가 찾는 이름은 `FCM_SERVICE_ACCOUNT_JSON_BASE64` 였고 값은 비어 있었습니다. 기동은 플레이스홀더 미해석으로 멈췄습니다.

| 프로퍼티 키 | Spring이 찾는 env 이름 |
| --- | --- |
| `fcm.service-account-json-base64` | `FCM_SERVICE_ACCOUNT_JSON_BASE64` |
| `fcm.service-account-json` | `FCM_SERVICE_ACCOUNT_JSON` |
| `fcm.project-id` | `FCM_PROJECT_ID` |

키를 env 변환 결과에 맞춰 정렬하고, 시크릿류 `@Value` 에는 기본값 `:` 을 줘서 생성자의 blank 검증으로 넘겼습니다. 이제는 미해석 placeholder 대신, 어떤 값이 비었는지 찍는 fail-fast 메시지와 함께 기동이 멈춥니다.

**② 네이티브 await에 예외 처리가 없으면 부가 기능이 본 흐름을 막는다 (GROMO-393).** Firebase 미구성 환경(네이티브 모듈 미준비, plist 부재)에서 푸시 권한 요청과 토큰 발급이 unhandled rejection으로 터져 앱 흐름 자체가 멈췄고, `registerPushToken`·`onMessage`·`handleInitialNotification` 세 진입점을 try-catch로 감싸 실패를 경계에서 흡수했습니다(등록 실패는 `null` 반환, 로컬 표시 실패는 무시). 같은 티켓에서 `getInitialNotification()` 을 앱 실행당 1회만 소비하도록 모듈 스코프 플래그로 가드해, 재로그인마다 이미 소비한 딥링크로 또 이동하는 문제도 닫았습니다.

**③ 계측이 부풀어 수요 측정을 망친다 (GROMO-597, PR #145).** 그룹 탭을 Fakedoor로 되돌리고 '출시되면 알림 받기' 클릭만 세던 화면에서, 한 유저에게 이벤트가 여러 번 기록됐습니다. 신청 여부를 AsyncStorage에서 비동기 로드하는 동안 버튼이 활성 상태라 이미 신청한 유저가 로드 완료 전에 누르면 재발사했고, `requested` state 기반 가드는 setState가 즉시 반영되지 않아 더블탭을 못 막았습니다. `loaded` state로 로드 완료까지 버튼을 비활성화하고, `useRef` 기반 `firedRef` 로 동기적 1회 발사 가드를 걸었습니다.

## 발송 대상을 정하는 쪽이 더 비쌀 수 있다

발송 앞단, 그러니까 "누구에게 보낼지"를 계산하는 비용과 "언제 보낼지"를 정하는 정책에서 비용과 회귀가 난 사례가 두 개 있습니다.

**미접속 복귀 escalation (PR #127, GROMO-578).** `last_active_at` 기준 KST date diff가 정확히 3/7/14일째인 유저에게 단계별 문구를 보냅니다. 대상 산정에는 `last_active_at` 이 필요하고, 그건 인증되는 모든 요청에서 갱신돼야 하는 값입니다. 요청마다 UPDATE를 걸면 인증 hot path에 쓰기가 붙습니다. 그래서 갱신을 `JwtFilter` 의 인증 통과 지점에 두고, WHERE 절에 `last_active_at < 오늘 0시 KST` 스로틀을 넣어 오늘 이미 갱신된 유저는 0건 매치로 무쓰기가 되게 했습니다.

엔티티 로드 없이 UPDATE 하나, 유저당 하루 최대 1 write입니다. 복귀 푸시 정확도를 위해 로그인을 막을 수는 없으니, 갱신이 실패해도 요청은 그대로 진행합니다(예외 격리). 부수 효과로 대상 조회 로직도 단순해졌습니다. 재접속하면 `last_active_at` 이 최신화되면서 D+3/7/14 경계를 자연히 벗어나므로 별도 카운터가 필요 없습니다. 14일 초과는 대상이 아닙니다.

이 PR의 dedup은 아직 스코프 밖이었습니다. PR 본문에 "같은 날 수동 재트리거 시 중복 발송될 수 있어 발송 이력 기반 dedup은 후속 티켓"이라고 남겼는데, 그 후속이 결과적으로 위의 #574였습니다.

**조용한 시간 창 (PR #255, GROMO-840).** 기본값을 21:00–09:00에서 23:00–07:00으로 좁혔습니다. 07:00 결과 발표(GROMO-839)와 21·22시 발송을 통과시키려면 창을 좁혀야 했습니다. 기존 발송 시각(09/10/19/20시)에는 회귀가 없음을 확인했습니다. 이 변경은 카탈로그 전체의 공용 전제라, 이 티켓이 후속 2개를 blocks하는 stacked PR 구조가 됐습니다. 같은 PR에서 일요일 위기 시퀀스를 넣으면서 유저당 1건만 나가도록 우선순위를 명시했습니다: 강등 위험(`tier>1` 이고 누적 미달) `>` 승급 미달 D-1 `>` 안전권 무발송.

## 표시 1회 보장을 서버로 올리기 (PR #671·#672, GROMO-1577, V49)

8월 중순에 결과 모달의 1회 노출 가드를 앱 로컬 마커에서 서버 쪽 확인(ack)·표시 선점(claim)으로 올렸습니다. 이 파이프라인이 거기서 두 번 쓰였습니다.

첫째, 세션 종료 알림 리스너가 `AFTER_COMMIT` + `@Async` 라 ack가 리스너보다 먼저 끝날 수 있었고, 그 창에서 사용자가 이미 본 결과의 푸시가 뒤늦게 나갔습니다. 메커니즘 쪽은 이 파이프라인으로 막았습니다. ack가 #574의 사건 유니크를 `SENT` 로 미리 점유하는 tombstone을 남기면, 리스너가 나중에 실행하는 `INSERT ... ON CONFLICT DO NOTHING` 이 그 행에 부딪혀 튕기고 발송할 `PENDING` 이 아예 생기지 않습니다.

둘째, 표시 선점의 리스 시각은 애플리케이션 시계가 아니라 DB 시계로 읽습니다. 인스턴스 시계가 어긋난 환경에서는 빠른 인스턴스가 느린 인스턴스의 방금 만든 선점을 만료로 보고 즉시 회수하기 때문입니다. ShedLock의 `usingDbTime()` 과 같은 축입니다.

정책 판단과 V49 스키마, 앱 쪽 실패 처리는 [결과 모달 사거리 회수](/research/result-modal)에 있습니다.

## 남은 것과 다음

- 큐/워커 분리는 아직 TO-BE입니다. 지금은 알림 서버 없이 스케줄러와 이벤트가 직접 FCM을 호출합니다. 다음 단계는 알림 소스 → 알림 서버(인증·전송률 제한·중복 제거) → 큐 → 워커 구조인데, at-least-once 중복이 따라오므로 지금 만든 사건 축 유니크가 그때 그대로 멱등 키 역할을 해야 합니다.
