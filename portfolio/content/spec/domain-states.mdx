이 문서는 서버가 소유하는 상태와 그 전이를 도메인별로 고정한다. 식별자는 출처의 코드·문서 표기를 그대로 쓴다. 챌린지·내기의 정본은 phone 레포 `docs/prd/challenge/policy.md`(최종 갱신 2026-08-14)이고, 리그·재화는 각 PRD(2026-08-08~09 기준), 나머지는 연구 노트다. 출처가 전이를 명시하지 않은 자리는 "출처에 명시 없음"으로 남겼다. 전이 표의 "누가"는 전이를 확정하는 주체다. 앱은 의도를 보내고 서버가 상태를 바꾼다.

## 집중 세션 — 라이브 마커와 리스

집중 세션은 **표시 축**(라이브 마커)과 **기록 축**(시간이 적립되는 세션)으로 나뉜다. 상태 enum이 아니라 컬럼값에서 파생된다. 표시 축의 "집중 중"(`isFocusing=true`)은 라이브 마커 `ended_at IS NULL` + 리스 생존이고, 기록 축은 `client_key`로 적립된 "반영 확정"과 창형 FOCUS 정산이 기다리는 "창과 겹치는 ACTIVE 세션"으로 나타난다.

| 파라미터 | 값 (2026-08-05 기준) |
| --- | --- |
| 하트비트 주기 | 3분 · foreground일 때만 전송, 백그라운드 전송 시도 없음 |
| 리스 TTL | 10분 · 하트비트 2회 유실 허용 + 지터 |
| sweeper 주기 | 10분 (종전 매시 정각, GROMO-610) |
| sweeper가 채우는 종료 시각 | `마지막 하트비트 + grace` (종전 `시작 + 12시간`) |
| 정산 가드 유예 | 5분 (종전 12시간, GROMO-1287) |

| from → to | 트리거 | 누가 |
| --- | --- | --- |
| (없음) → 집중 중 | `POST /focus-session/start` | 앱 요청, 서버 기록 |
| 집중 중 → 집중 중 (리스 갱신) | 하트비트 3분 주기, AppState active 복귀 시 즉시 1회 | 앱 전송, 서버가 마지막 하트비트 시각 갱신 |
| 집중 중 → 종료 | `PATCH cancel` 도착 | 서버, 조회 시점에 즉시 `isFocusing=false` |
| 집중 중 → 종료 (리스 만료) | 마지막 하트비트 + TTL 경과 후 sweeper | 서버 sweeper |
| 완료 블록 → 반영 확정 | 통짜 POST, 서버가 `endedAt`을 세 항으로 클램프 | 서버 |
| 정산 대기 → 정산 진행 | 반영 미확정 세션이 없거나 유예 5분 경과 | 서버 정산 가드 |

불변 규칙:

- **유저당 라이브 마커 1개.** 마커 회전 구간(GROMO-873)의 짧은 겹침만 예외이고, 그 밖에 열린 마커 2개 이상은 위반이다.
- **리스 만료는 표시 상태만 소멸시킨다.** 시간(사실)은 몰수하지 않고 별도 규칙(away-credit)으로 정산한다.
- **클램프**: `endedAt ≤ min(클라 주장, last_heartbeat_at + grace, now + 시계오차 2분)`. `grace` 값은 미확정이며 리스 TTL과 같은 축에서 정한다. 기록 세션끼리 구간이 겹칠 수 없고, 표시용 마커에는 이 제약을 걸지 않는다.
- 재전송 중복 적립은 `client_key` partial unique 제약으로 막는다. 클라 아웃박스는 50건 상한이고 초과분은 현재 버려진다.

## 챌린지 — `group_challenges`

상태: `ACTIVE` · `ENDED` · `DELETED`. 구앱 호환을 위해 레거시 응답 직렬화 시점에만 `ENDED → "INACTIVE"`로 다운맵하며, DB·enum·내부 로직의 정본은 `ENDED`다(B1, #567).

| from → to | 조건 | 결과 | 누가 |
| --- | --- | --- | --- |
| (없음) → ACTIVE | 생성 검증 통과: repeatDays 유효 → 그룹당 활성 4개 상한 → 하루형 중복 → 창 유효성 → 목표 규칙 → 창 겹침 | 활성 요일마다 회차가 자동으로 선다 | 그룹장 요청, 서버 검증 |
| ACTIVE → ENDED | OPEN 회차가 하나도 없을 때만(예약된 미래 회차도 OPEN). 있으면 `CHALLENGE_END_BLOCKED` 409 | 카드에서 내려감, 판정·알림·회차 중단. 환불 의무 없음 | 그룹장 요청, 서버 판정 |
| ACTIVE → DELETED | 언제든. 진행 중이면 경고 확인 1단계 추가(날짜·참여 인원·적립금을 수치로) | OPEN 회차 전부(미래 예약분 포함) `VOIDED`(사유 `CHALLENGE_DELETED`) + 전원 환불 후 soft delete | 그룹장 |
| ENDED → DELETED | 일반 확인 1단계 | 카드에서 사라짐 | 그룹장 |

불변 규칙:

- **수정 없음(FR-10).** 카테고리·방식·요일·시간대·목표분·내기 여부·참가비 전부 불변. 내기를 나중에 끄는 경로도 없다.
- **정산 끝난 회차는 삭제로 되돌리지 않는다(FR-13).** 환불 대상은 OPEN 회차의 에스크로뿐이다.
- **이력은 그룹이 소유한다(FR-14).** 회차 행에 미션 스냅샷(카테고리·방식·목표분·창 시각)을 박제하고, 판정은 스냅샷에서 읽는다(#575).
- 역전이는 없다. `DELETED → ACTIVE`, `ENDED → ACTIVE`는 출처에 없다. 창은 `time(6)` 벽시계 두 개이고 `CHECK (window_start < window_end)`로 자정을 넘는 창을 막는다.

## 회차 — `bet_sessions` (판정·정산 단위)

상태: `OPEN` · `SETTLED` · `FORFEITED` · `VOIDED` · `REFUNDED` · `UNUSED`. 종료 사유 `void_reason`: `INSUFFICIENT_PARTICIPANTS` · `CHALLENGE_DELETED` · `REFUND_DEADLINE`(N55, 2026-08-10).

```text
                 ┌─ 달성자 ≥ 1 ───────────────→ SETTLED    (팟 분배)
                 ├─ 달성자 0 ─────────────────→ FORFEITED  (팟 소멸, 이월 없음)
OPEN ────────────┼─ 참가 마감 시 1명 / 삭제 ──→ VOIDED     (전원 환불)
                 ├─ 정산 실패 24h 초과 ───────→ REFUNDED   (전원 환불)
                 └─ 참가자 0명 ──────────────→ UNUSED     (결과 아님)
```

| from → to | 트리거 | 누가 |
| --- | --- | --- |
| (없음) → OPEN | `ensureSession` 크론 매시 :05가 활성 요일 회차 개설. 마감 지난 창형은 스킵 | 서버 |
| OPEN → SETTLED / FORFEITED | `settle(sessionId, trigger)`, `trigger ∈ CRON \| EARLY \| MANUAL`. 회차를 `FOR UPDATE`로 선점, OPEN이 아니면 즉시 반환 | 서버 단일 진입점(B4, #571) |
| OPEN → VOIDED | `INSUFFICIENT_PARTICIPANTS`: 참가 마감 시 참가자 정확히 1명(무산 크론 5분) · `CHALLENGE_DELETED`: 챌린지 삭제 | 서버 |
| OPEN → REFUNDED (`REFUND_DEADLINE`) | 정산 실패 백오프 5m/15m/1h/4h 재시도 후 24h 초과. `next_attempt_at` 기준 settle 스캔 5분 | 서버 |
| OPEN → UNUSED | 참가자 0명. 결과 큐·내역·알림에서 제외 | 서버 무산 크론 |

| 조합 | 정산 시점 (회차 종료가 트리거, 크론은 안전망 — FR-26) | 그레이스 | 관용치 |
| --- | --- | --- | --- |
| FOCUS × DURATION | KST 자정 즉시 | 0분 | 0분 |
| FOCUS × TIME_WINDOW | 창 종료 + 30분 | 30분 | 5분 (달성 플래그에만, 표시값은 실측) |
| SCREEN_TIME × TIME_WINDOW | 창 종료 + 30분 | 30분 | 0분, 목표분을 15분 배수로 강제 |
| SCREEN_TIME × DURATION | 익일 12:00 | — | 0분 |

판정 규칙(§B1~B8):

- FOCUS는 `회차 내 집중분 ≥ 목표분`, SCREEN_TIME은 `회차 내 사용분 ≤ 목표분`. 판정은 `GroupBetJudge` 커널 1벌이며 카드와 정산이 같은 답을 낸다.
- **개인 승리는 즉시 확정하고 되돌리지 않는다(FR-23).** 세션 POST가 목표를 채우는 순간 박제한다. 조기 팟 분배(EARLY)는 참가 마감 이후 + 전원 확정일 때만이라 창형에서만 발동한다.
- **0분과 미집계는 다르다(§B7).** FOCUS는 데이터 없음을 0분으로 접고, SCREEN_TIME은 `progressMinutes = null`로 남긴다. 0으로 접으면 미보고가 "0분 사용 = 달성"이 된다.
- **미도착 = 미달성 확정(§B4).** 판정 제외+환불은 기각했다. SCREEN_TIME 권한 철회도 미계측 = 미달성이다.
- **정산은 되돌리지 않는다(§B8).** 마감 이후 도착한 기록은 반영하지 않는다. 24h 자동 환불(§E1)은 정산된 건을 되돌리는 게 아니라 정산이 불가능한 건을 닫는 것이며, 24h 검사는 정산 시도보다 먼저 온다.
- 창형 FOCUS는 창과 겹치는 ACTIVE 세션이 남아 있으면 정산 틱을 스킵한다(SCREEN_TIME은 대기 없음). 사일런트 푸시는 `settle_after − 15분`에 참가자에게만 보낸다.

## 내기 참가 — 참가 행과 환불

내기는 챌린지와 1:1인 설정(`group_challenge_bets`)이고, 돈이 움직이는 단위는 회차(`group_challenge_bet_sessions`, 유니크 `(bet_id, session_date)`)다. 참가 행은 참가마다 새로 만들어지는 UUID v7이다. 참가 마감은 창형이 창 시작 전(창이 열리는 순간 회차를 잠근다), 하루형이 회차 종료까지다.

| from → to | 조건 | 누가 |
| --- | --- | --- |
| (없음) → 참여 | 참가비(1~3,000 코인 정수) 즉시 차감, 에스크로. 주간 예약도 예약분 전액 즉시 에스크로 | 앱 요청, 서버 차감 |
| 참여 차단 | FOCUS 이미 달성 `BET_ALREADY_ACHIEVED` · SCREEN_TIME 이미 초과 `BET_ALREADY_FAILED`. 남은 시간 부족은 경고만 하고 막지 않는다 | 서버 |
| 참여 → 참여 취소 (전액 환불) | 시작 전 참가: `now < 회차 시작`. 시작 후 참가(하루형만 성립): `now < min(참가시각 + 5분, 회차 종료)` | 앱 요청, 서버 판정 |
| 참여 → 그룹 탈퇴 | 취소와 같은 창 안이면 전액 환불. 회차 시작 후면 정산 대상 유지 — 참가 행과 판돈을 보존하고 "탈퇴한 사용자"로 표기 | 서버, 예외 대신 스킵 |
| 참여 → 정산 | 회차 종료. `팟 = 참가비 × 참가자 수`, 달성자끼리 균등 분배 + 잔여는 성과 1위(동률은 `userId` 오름차순) | 서버 |

| 멱등키 | 시점 | 키 |
| --- | --- | --- |
| 참가비 차감 | 구 → P0 수정 | `bet:{betId}:stake:{userId}`(유저 축, 철회 후 재참여가 참가비 0원 — GROMO-1112) → `bet:{betId}:stake:{participantId}` |
| 환불 | P0 수정 | 경로별로 갈리던 키를 `bet:{betId}:refund:{participantId}` 하나로 통일(취소·철회·탈퇴·무산 공용) |
| 환불 (현행) | B3 #568 | `session:{sid}:refund:{participantId}` — 회차 축. 회차 id는 구 내기 행 id를 승계 |

불변 규칙:

- **환불은 정확히 한 번(§C9).** 차감 키와 환불 키가 1:1이라 "한 번 걷힌 참가 행은 어떤 경로로든 정확히 한 번 돌아온다"를 원장 유니크가 보장한다. 잠금 순서는 유저 → 멤버십 → 회차 → 지갑이고, 잠금 후 참가 행 실재를 재검증한다.
- **시작한 회차에서는 어떤 경로로도 참가비를 뺄 수 없다(§C8).** 그룹 탈퇴 포함. 목표 해석에 실패하면 "시작됨"으로 판정해 에스크로에 남긴다.
- **내기는 코인을 만들지 않는다.** 달성자 0명의 팟은 `FORFEITED`로 소멸하며 회수 계정이 없다. 원장에는 `BET_STAKE` 차감과 몰수 기입만 남는다.
- 참가비 차감 함수의 `false` 반환은 트랜잭션 전체 롤백이다. 5분마다 참가·취소를 반복하는 어뷰징은 수용한다.

## 알림 — 사건 선점과 리스

`notification_sent_logs`가 사건 축이다. 유니크 `(user_id, kind, subject_id)`, `status ∈ PENDING / DEFERRED / SENT`, `claimed_at`, 묶음 메타 `group_id`·`slot_at`(V45, PR #574, 2026-08-10).

| from → to | 트리거 | 누가 |
| --- | --- | --- |
| (없음) → PENDING | `INSERT ... ON CONFLICT DO NOTHING`. 0건이면 남이 이미 잡았으므로 보내지 않는다 | 정산 커밋 후 이벤트 또는 15분 재훑기 |
| PENDING → SENT | FCM 발송 성공 | 발송한 프로세스 |
| PENDING → (선점 반납) | FCM 발송 실패. 리스 만료를 기다리지 않고 즉시 반납, 다음 재훑기가 재발송 | 실패한 프로세스 |
| PENDING → (회수) | `claimed_at` 기준 10분 경과. 시각은 DB 시계로 읽는다 | 재훑기 |
| (없음) → DEFERRED → SENT | 조용한 시간(23:00–07:00)에 발생한 사건은 이월해 07:00에 발송. 모집 알림은 이월하지 않고 버린다 | 서버 |
| (없음) → SENT (tombstone) | 결과 모달 ack가 사건 행을 `SENT`로 선점. 이후 리스너의 INSERT가 튕겨 `PENDING`이 생기지 않는다 (V49, GROMO-1577) | 서버 ack |

불변 규칙:

- 같은 유저의 같은 사건은 행 하나만 존재한다. 이벤트 경로와 재훑기가 동시에 도달해도 유니크가 한쪽을 튕긴다. 묶음 키(`group_id`·`slot_at`, 사건 시각 `settled_at` 기준)는 dedup 키와 분리한다.
- 전 크론에 ShedLock(JDBC provider, `usingDbTime()`)과 고유 락 이름을 붙인다. 반납·회수 시 행을 삭제하는지 status를 되돌리는지는 출처에 명시 없음.

출처: [알림 파이프라인 재편](/research/notification-pipeline) · [결과 모달 사거리 회수](/research/result-modal).

## 리그 — 주간 정산과 티어

티어는 1~5 단계이고 승강은 순위가 아니라 **절대 주간 집중 시간**으로 결정된다(league/prd.md 2026-08-09, 현재 구현 기준).

| 티어 | 이름 | 승급 기준(주간) | 강등 기준(주간) | 승급 보너스 |
| --- | --- | --- | --- | --- |
| 1 | 뽀시래기 | 14시간 이상 → T2 | 없음 | — |
| 2 | 예열 모드 | 28시간 이상 → T3 | 14시간 미만 → T1 | 50 시간조각 |
| 3 | 초집중 모드 | 42시간 이상 → T4 | 28시간 미만 → T2 | 100 시간조각 |
| 4 | 갓생러 | 56시간 이상 → T5 | 42시간 미만 → T3 | 200 시간조각 |
| 5 | 집중 정복자 | 없음 | 56시간 미만 → T4 | 500 시간조각 |

판정식 `LeagueUserSettler.decideResult`: `tier < 5 && focusSeconds >= promotionTime → PROMOTED`, `tier > 1 && focusSeconds < relegationTime → RELEGATED`, 그 외 `STAY`. 한 번의 정산에서 최대 한 단계만 움직인다(R8).

| 단계 | 트리거 | 결과 |
| --- | --- | --- |
| 주간 정산 | `0 0 0 * * MON` KST (R12, GROMO-412) | 유저 1명 = 트랜잭션 1개(R15). anchor 선커밋 후 유저별 `settle(user, week)` |
| `settle(user, week)` | 유저 행 배타 락 → 락 안에서 `existsByUserIdAndWeekStartAt` 재확인 | `SETTLED` / `SKIPPED_WITHDRAWN` / `ALREADY_SETTLED` (`SettleOutcome`) |
| 완료 마커 | `league_weekly_results` 행 존재 = 그 주차 정산 완료. STAY도 INSERT, 유저·주차 UNIQUE | 신규 테이블 0개 (#534) |
| 재실행 | `POST /league/batch/resume` (프로파일 제한 + `X-Batch-Admin-Key`), 선택적 `userIds`. 기존 `/league/batch/run`은 anchor 409 가드 `BATCH_ALREADY_RUN`으로 주차당 1회 | 실패 유저만 정산, 성공 유저는 불변 |
| 결과 푸시 | 정산과 별도 스케줄 월 07:00 KST (R17). [배치 처리의 함정들](/research/batch-traps)의 2026-07-20 크론 표는 월 09:00이며 이 문서는 PRD를 따른다 | 앱은 응답의 `weekStartAt`을 ack 키로 사용 |

불변 규칙:

- 승급 보너스는 승급한 새 티어 기준 금액이고 서버가 결과 응답에 실제 지급액을 싣는다(R9). 앱은 금액을 계산하지 않는다(R10).
- 동시 재실행에도 정확히 한 번만 정산된다. 정본은 락 안 단건 재확인이고, 페이지(100명)당 마커 선조회는 그 앞의 빠른 경로다.
- `GET /league/me/last-result`는 "최신" 결과 1건이라 resume 후에는 직전 주가 아닐 수 있다. 아레나 상태 `ACTIVE`·`ENDED`는 크론 표에 등장하지만 전이 조건은 출처에 명시 없음.

출처: league/prd.md §4.2·§4.3, [리그 배치 4종 실패와 멱등 재실행](/research/league-batch) #517·#534.

## 재화(시간조각) — 획득·소비의 소유권

재화는 상태 머신보다 **누가 금액과 시점을 정하는가**로 규정된다(currency/prd.md, 2026-08-08 `main` 기준).

획득 이벤트([S] 서버 MP 소유 2종)는 금액·시점을 서버가 결정한다. 내기 정산·리그 승급은 앱이 꺼진 새벽 배치에서 지급되므로 클라가 쏘면 영원히 누락된다. 조작 이벤트([C] 클라 소유 4종)는 화면 노출·탭·좌절 지점처럼 서버가 알 수 없는 것만이다. 원장 `currency_transactions`에는 차감·지급·몰수 기입이 남는다.

| 확정 정책 | 내용 |
| --- | --- |
| 금액은 서버만 정한다 | P1 클라 적립 폐쇄(`POST /currency/earn`은 no-op 204) · P2 `isServerOnly()` 가드로 서버 전용 6종 타입 거절 · P6 선지급 금지, 확정 후에만 지급하며 지급은 되돌릴 수 없다(§9.1 R1) · P7 금액을 지어내는 폴백 금지, 미도착 = 배지 미표시 |
| 화면은 표시만 한다 | P4 낙관 가산 금지(응답 전 잔액을 올리지 않음) · P5 잔액 0 ≠ 모름 |
| 보상 구성 | P3 목표 달성 보상 = 스트릭 + 코인. 스크린타임 목표는 스트릭 미배선(비대칭) |

정정 수단인 역분개는 설계 단계라, 잘못 나간 지급을 원장에서 되돌릴 방법은 아직 없다([돈 경로 정본](/research/money-integrity)).
