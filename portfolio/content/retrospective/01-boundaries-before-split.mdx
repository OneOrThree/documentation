이 회고는 회의록을 대신 만들거나 팀의 감정을 추정한 글이 아니다. [9일간의 구현 기록](/research/backend-layering-refactor)과 PR #711~#730에서 확인되는 선택을 KPT로 다시 정리했다.

## 목표

알림·링크·Business API를 프로세스로 분리하기 전에 `data-api` 내부 경계를 실제로 자를 수 있는 상태로 만든다. 기능 변경은 뒤 단계로 미루고, 패키지 배치 → 조회 계층 → 도메인 방향 → 에러 계약 순서로 진행한다.

## Keep — 유지할 것

- **변경 전에 수치를 잰다.** 도메인 순환은 추정 2개가 아니라 238개였고, 서비스 44개가 다른 도메인의 리포지토리를 약 120번 직접 주입하고 있었다. 분해 순서를 이 측정에 맞췄다.
- **규칙을 빌드 실패로 만든다.** 역행 참조 15쌍·49건과 순환 238개를 0으로 만든 뒤 ArchUnit 규칙으로 고정했다. 새 도메인이 레이어 표에서 빠지는 경우도 실패시킨다.
- **PR 하나에 검증 가능한 한 단계만 둔다.** 패키지 배치, 조회 계층, 의존 방향, 에러 계약을 분리해 회귀의 원인을 좁혔다.
- **계약 변경은 앱 배포 순서와 함께 기록한다.** 404 코드 세분화처럼 구버전 앱에 영향을 주는 변경은 호환 분기와 배포 순서를 설계에 포함했다.

## Problem — 문제가 된 것

- 패키지 이동 뒤 JPQL 문자열의 FQCN 39건이 남아 컴파일은 통과했지만 ApplicationContext가 뜨지 않았다. 컴파일러가 보지 못하는 문자열 경로가 검증 사각지대였다.
- 최초 측정 스크립트가 레이어 표에 없는 새 도메인을 건너뛰어 위반 0건을 잘못 보고했다. 검사 대상 누락 자체를 실패시키는 규칙이 없었다.
- 리포지토리의 `@Transactional`을 일괄 정리하자 테스트가 덮어주던 호출과 스케줄러가 실제로 필요로 하던 호출이 섞여 있었다. 전체 테스트가 초록이어도 실패 기록 경로 하나는 검증되지 않았다.
- `userId`라는 이름만 보고 요청자와 대상을 구분한 분석이 여러 번 틀렸다. 컨트롤러 입력까지 추적하지 않은 grep은 권한 축을 설명하지 못했다.

## Try — 다음에 시도할 것

1. 패키지 이동 체크에 JPQL, `@Value`, `@ComponentScan`, logback, YAML 문자열 검색을 포함한다.
2. 아키텍처 검사에서 “등록되지 않은 도메인 0개”를 독립 조건으로 유지한다.
3. 트랜잭션 경계를 바꿀 때 정상 경로뿐 아니라 catch 블록·스케줄러·재시도 상태 전진을 별도 시나리오로 검증한다.
4. 서버 분리는 해당 모듈의 데이터 소유권, 내부 호출 계약, 장애 격리 이유가 문서에 함께 있을 때 진행한다.
