첫 12일 동안 저희가 만든 것은 제품이 아니라 **파이프라인**이었습니다. 2026-04-29 에 지라 첫 티켓 `GROMO-36` 「지라 공부하기」가 올라갔고, 2026-05-10 에 릴리스 `0.0.1` 이 41건으로 닫혔습니다. 그 41건을 도메인별로 세어 보면 인프라·배포 17건, 개발환경·워크플로 11건, 설정 6건입니다. **제품 기능은 0건이었습니다.** 저희는 그걸 알고도 그렇게 했고, 담당 멘토도 05-10 멘토링에서 "배포 사이클까지 돌려야 돼 (릴리즈X)"라고 같은 말을 했습니다.

동시에 이 시기는 정한 것보다 **비워 둔 것**이 더 많이 남은 시기이기도 합니다. 05-03 하루에 만든 위키 페이지 11개 중 여섯 개는 지금도 본문이 비어 있고, DoD 티켓은 2026-09 현재까지 '해야 할 일'입니다.

## 04-29 ~ 05-03 · 멘토 과제 스프린트

지라 보드의 첫 스프린트는 이름부터 `SCRUM Sprint N` 규칙 밖에 있습니다. 이름이 「담당 멘토 과제」이고, 기간은 2026-04-29~05-03, 목표는 "과제 완수를 통해 프로젝트 기반 다지기", 붙어 있는 이슈는 단 하나 — `GROMO-36` 「지라 공부하기」입니다. 담당은 저였고 04-29 22:33 에 만들어 05-01 에 닫았습니다. 티켓 본문은 스크럼 강의 영상 9편의 목록입니다: 비전 설정 → 로드맵·프로덕트 백로그 → 유저 스토리 → 플래닝 포커 → 릴리즈 플래닝 → 스프린트 개요 → 스프린트 플래닝·백로그 → 데일리 스크럼 → 리뷰·회고.

과제의 **제출물**은 05-03 에 만든 `GROMO-47` 「0.0.1 빌드 아키텍처 설계」 본문에 두 안의 비교로 남아 있습니다.

| 안 | 장점 | 단점 | 결과 |
| --- | --- | --- | --- |
| 1. 슬랙 커스텀 봇 | "지라를 연습용으로 사용할 수 있다" | "백 + 인프라 → 다양한 환경 구축 실패" | 기각 |
| 2. 빌드 0.0.1 | "다양한 환경 구축 실습" | "프로젝트 로그에 쭉 남아있다…" | **채택** |

같은 티켓 마지막 줄이 이 시기 전체의 요약입니다 — "프,백,인 (개발) → 뭔가 파이프라인 구축(배포, api 명세, 빌드, 테스트, 뭔가) → 배포완". 연습용 장난감 대신 **실제 프로젝트 저장소에 흔적이 남는 릴리스**를 과제 결과물로 고른 선택이고, 그래서 저희 지라 로그는 `GROMO-36` 부터 끊기지 않고 이어집니다.

## 05-03 · 위키 개설과 첫 팀 회의

05-03 저녁, 컨플루언스 스페이스 「나빼고놀지마 Space」와 페이지 10개가 **10분 안에** 만들어졌습니다: 스페이스 홈 → 「Personas」·「Vision & Roadmap」·「Competitor Analysis」 → 「Definition of Done」·「Git Flow」·「코드 리뷰 가이드」·「배포 절차」 → 「05-03 회의록」 → 「Jira & Slack & GitHub」. 세 시간 뒤 「AWS Secrets Manager 활용 가이드 - 개발자용」이 붙었습니다.

<Callout label="빈 문서 여섯 개" tone="warn">
이 중 「Personas」, 「Vision & Roadmap」, 「Definition of Done」, 「Git Flow」, 「코드 리뷰 가이드」, 「배포 절차」는 **v1 이후 한 번도 수정되지 않았고 본문이 비어 있습니다**. 제목만 만들어 두면 내용이 따라올 줄 알았는데, 따라오지 않았습니다. 나중에 실제로 굴러간 규약은 이 페이지들이 아니라 저장소의 `docs/conventions/` 와 지라 티켓 본문이었습니다.
</Callout>

같은 날 「05-03 회의록」에서 정한 것은 셋입니다.

1. **멘토 매칭** — 후보 9명을 포지션(백/프/풀/AI)과 수락 여부로 표에 정리하고, 1·2순위와 "A가 되고 B가 안 되면 C" 식 분기까지 미리 적어 두었습니다. 실명은 옮기지 않습니다.
2. **워킹 아워** — 10~18시(월~일), 이후 자율. 휴가는 월 2회(급한 일이 없고 전원 동의 시), 토요일 자율·재택 가능, 센터 외 작업은 2명 이상 동의 시. 회의록 자신이 "언제든 변경될 수 있다"고 단서를 달아 두었습니다.
3. **기획 시간 고정** — 월요일(정규 멘토링 직후)과 화요일 오전 10시.

회의록 맨 끝 한 줄은 "회고 때 칭찬 타임 추가"였습니다.

## 05-04 ~ 05-05 · 스프린트 플래닝과 기술 결정

`SCRUM Sprint 1`(05-03~05-10)의 목표는 지라에 **"워크 프로세스 세팅 + 0.0.1 릴리즈"** 로 적혀 있습니다. 05-04 하루에만 이슈 48건이 생성됐습니다. 전체 기간(04-29~05-10) 생성 이슈는 64건(작업 26 · 하위 작업 38)입니다.

기술 스택은 이날 대부분 확정됐고, 근거가 티켓 본문에 남아 있습니다.

| 결정 | 티켓 | 근거 (티켓 본문) |
| --- | --- | --- |
| 모바일 = React Native | `GROMO-54` (05-04 생성·완료) | "사용해야 하는 API(ScreenTimeAPI, Health.API) 특성상 모두 각 OS별로 상이하게 만들어야 함 / 전체 코드의 50\~60%가 native라 사실상 RN의 이점이 작아진다" → 그럼에도 "팀원들의 모바일 개발 참여 의사 확인 후 RN으로 결정" |
| 백엔드 = Spring Boot | `GROMO-63` (05-04) | Spring Boot 4.0.6 · Java 17 · Gradle(Groovy) · Jar. "빠른 MVP 개발 이후 유저 데이터를 통해 확장 예정 → 확장에 용이한 Spring Boot" |
| 인프라 = Terraform + AWS | `GROMO-69` · `GROMO-84` · `GROMO-97` | Secrets Manager·IAM·EC2·ECR·SSM·GitHub OIDC 까지 하위 작업 단위로 쪼갬 |
| 디자인 = Design.md 사이클 | `GROMO-60` · `GROMO-82` · `GROMO-83` | 「Design.md 양식」(05-04) — YAML 토큰(기계용) + 마크다운(이유와 사용법) 이중 구조 |

RN 결정은 특히 정직하게 적혀 있습니다. 이점이 작아진다는 것을 알면서도, **한 사람이 iOS·Android 를 다 만들 수 없다**는 이유가 이겼습니다. 이 판단의 대가는 이후 스크린타임 네이티브 모듈 작업에서 치릅니다.

「05-04 회의록」에는 0.0.1 의 범위가 목록으로 있습니다 — 아키텍처 설계, 깃헙 세팅(CI/CD·PR 슬랙 알림, 지라 연동), API 명세 문서(`Swagger` ↔ GitHub Pages ↔ 컨플루언스), 디자인(Figma ↔ 지라), Secrets, 기능 명세를 릴리스에 연결. 그리고 **DoD 초안 5개**가 같은 회의록과 `GROMO-116` 「DoD 설정」 양쪽에 똑같이 적혀 있습니다.

- Acceptance Criteria 모두 충족
- 코드 리뷰
- 테스트 통과
- 스테이징 환경 동작 확인 "(흉내라도..)"
- 문서 업데이트 (Confluence)

05-05 회의에서는 0.0.1 의 개인별 몫을 나눴습니다. 권태화는 Secrets Manager 기반 비밀 관리와 GitHub Actions 배포 자동화, 안수빈은 `figma → design.md → Claude Design` 사이클과 Expo 빌드·Firebase 연결, 저는 서버 개발 환경(docker-compose)·Swagger·CI 파이프라인·GitHub↔지라 동기화(commit/PR/branch)를 맡았습니다. 이 삼분할은 이후 넉 달 동안 거의 그대로 갑니다([역할 분담과 경계 계약](/team/roles)).

## 05-06 ~ 05-09 · 기획이 흔들리기 시작하다

파이프라인이 굴러가는 동안 기획은 아직 고정되지 않았습니다. 05-06 에 `GROMO-140` 「클로드 디자인으로 기획 시각화 및 공유」가 붙었고, 05-08 에 「기능 명세 (Ver.1)」이 만들어졌습니다(이후 06-13 까지 13차 개정). 초판의 골자는 '남은 인생 시간으로 스크린타임을 재해석하고, 되찾은 시간으로 캐릭터와 세계를 복구한다'였습니다. 제품 이름과 콘셉트가 확정되는 과정은 [다음 시기 기록](/history/02-idea-and-plan)에서 다룹니다.

「05-09 회의록」에 정리된 멘토 피드백은 첫 기획안의 약점을 정확히 찍었습니다.

- **온보딩** — "'시간이 유한하다'라는 온보딩은 나이가 들수록 와닿는다. 청소년들에겐 와닿지 않을 것임" → 수능·시험 같은 단기 목표로 대체 제안
- **보상** — "보상 주는 방법이 너무 많음", 메인 재화 필요. "핸드폰 안보기 → 아무것도 안 했는데 보상받는 느낌" → 성취 후 보상으로
- **실패** — "실패하고 있구나에 대해 피드백이 즉각적으로 느껴져야 함"
- **그룹** — "그룹의 목표보다는 개인의 목표로 사용하는 사람들이 우선이어야 한다"
- **BM** — "광고, 구독 제외 약하다"

## 05-10 · 0.0.1 릴리스와 첫 정규 멘토링

05-10 에 릴리스 `0.0.1` 을 41건으로 닫았습니다. 같은 날 「SCRUM Sprint 1 회고」와 정규 멘토링 첫 회차 노트가 함께 작성됐습니다.

첫 회고는 칸 세 개짜리 템플릿에 딱 세 줄이 들어갔습니다 — 실행 시작 "회고 전에 생각해오기 (월요일)", **실행 중지 "방향성이 자주 바뀐다"**, 계속 실행 "데일리 스크럼 긱봇 자동화". 개설 일주일 만에 팀이 스스로 잡아낸 문제가 '방향성이 자주 바뀐다'였다는 사실은, 이후 기획 심의까지 이어지는 흔들림의 첫 기록입니다.

같은 날 멘토링에서 다음 두 주의 숙제가 나왔습니다.

- **테크니컬 테스트** — "코어 피처들이 되는지 안 되는지 빌드": 스크린타임 API, 화면 on/off 이벤트 훅, 캐릭터 동작, 아이템 ID 전달, 로그인·회원가입. 앞의 둘은 **애플 디벨로퍼 인증이 선행**이라고 못 박혀 있습니다.
- **일정** — "기획심의 5/30까지", "개발 체계화(?) 뭔가 시작은 해야 돼 이건 인정 → 배포 사이클까지 돌려야 돼 (릴리즈X)"
- **버전 로드맵 초안** — `V0.0.1` 로그인/회원가입 → `V0.1.1` 포커싱 모드 → `V0.2.1` 스크린타임 목표 달성 → `V0.3.1` 상점·마이페이지 → `V0.4.1` 그룹·그룹 챌린지 → `V1.0.0` 릴리스 → 이후 랭킹·AI 회고·업적

그리고 05-10 에 티켓 네 건이 새로 생깁니다: `GROMO-143` 경쟁사 분석, `GROMO-145` 3D 캐릭터 동작, `GROMO-146` 캐릭터 소품 변경 및 적용, **`GROMO-147` 프로젝트 이름 정하기**. 다음 시기의 시작입니다.
