10월 18일 조사는 여러 데이터 규모에서 현재 병목을 찾는 As-Is 측정이었다. 테스트 발생기와 관측·프록시 설정을 고쳤고 SQL 후보 두 개를 비교했지만, 이날 운영 배포나 영구 인덱스 변경은 하지 않았다. 처리량이 높은 조회, 전달이 밀리는 쓰기, 실패한 후보 실험을 모두 남겼다.

원본은 `phone/loadtest/reports/survey-20261018/`, `matrix-20261018/`이며, 당시 정리본은 `phone/loadtest/survey/results/2026-10-18/`다. 2026-10-22 원시 대조에서 k6 HTTP 본측정 539개, 워밍업 272개, WS 측정 59개와 별도 paced HTTP 생산자 실행 2개를 확인했다. paced 원장마다 start·finish 200요청과 전후 조회 200요청을 구분했다. 공유용 evidence 복사본과 압축본은 별도 실행으로 세지 않았다.

## 어떤 환경에서 무엇을 쟀나

최초 survey는 **04:52:12–04:57:10 UTC(13:52:12–13:57:10 KST)**다. 이후 matrix와 후속·후보 실험은 같은 날 이어졌고 최종 확인 marker는 **10:05:34 UTC(19:05:34 KST)**다. 아래 세부 시각은 UTC로 표시한다.

| 조건 | 기록 |
|---|---|
| 환경 | macOS arm64의 격리 Docker 스택. 기존 개발 컨테이너와 VM 자원 공유 |
| 호스트 예산 | Docker VM CPU 8개·메모리 약 7.65GiB |
| 앱 예산 | 앱당 CPU 2개·힙 512MiB·컨테이너 메모리 1GiB |
| 구성 | Data·Business·Notification, Realtime 2대, PostgreSQL 16, Redis 2대, Kafka |
| 기준 코드 | `2cca31b7582c8a73751321ede75f4c0482f1eb1c` 및 실행별 `dirtyDiffHash`·이미지 ID |
| 등록 fixture | 100 → 1,000 → 10,000명, 섬당 10명 |
| 부가 데이터 | 사용자당 90일 통계·집중 기록 270건·편지 100건, 섬당 채팅 이력 1,000건 |
| 부하 | 짧은 API 탐색 10초, 상승 단계 20초, 대표 조건 60초 확인, 혼합 약 5분 |

등록 fixture 수는 동시 사용자 수가 아니다. 10,000명 단계의 사전 스냅샷에는 별도 봇·준비 계정을 포함해 사용자 10,191행, 집중 상세 약 271만 행, 채팅 약 104만 행이 있었다. 앞선 쓰기와 캐시·Outbox 상태가 다음 단계에 남을 수 있다. 등록자 수만 다른 완벽한 독립 A/B로 읽지 않는다.

당시 자체 기준은 오류율·미발신율 각각 1% 이하, 단일 조회 p95 200ms 이하, 홈·집중 여정 p95 500ms 이하였다. 운영 SLO 합의값은 아니다. k6에는 미발신 0건 기준도 있어 `exitCode=99`와 자체 조사 기준 통과가 함께 나타날 수 있다. WS `valid=true`도 수신 완결성 판정이며 지연 기준 통과를 대신하지 않는다.

## HTTP는 성공했지만 사건 전달은 밀렸다

10,000명 데이터에서 집중 50수명주기/s를 60초 재확인해 3,001회를 완료했다. main 구간 focus/rest 원장 사건은 24,008건이었고 REALTIME Outbox 대기 샘플은 최대 21,972건이었다. 이후 잔여 대기 21,798건이 0이 되는 데 **849.59초, 약 14분 10초**가 걸렸다. HTTP 통과와 Kafka로의 발행 회복을 앱 수신 완료로 합치지 않는다.

앞선 상승 부하와 100수명주기/s 확인 뒤에는 91,474건이 남았다. 관측 중단·재개 간격까지 포함해 약 31분 45초 뒤 0이 됐다. 앞선 단계의 사건이 섞였으므로 이 시간을 100 TPS·60초 한 번의 회복 시간이라고 쓰지 않는다.

회복 중 `pg_stat_statements` 차분에서는 선점 UPDATE 49회가 합계 59,329ms를 사용했다. 여러 target이 공유하는 normalized SQL의 합계다. 이 근거는 Kafka lag만으로 전체 전달 상태를 판단하거나 poll 간격만 줄이면 해결된다고 단정할 수 없음을 보여 준다. 원시 근거는 `users-10000/diagnostic-outbox-recovery/query-delta.json`, `drain-results.jsonl`, 정리본 `outbox-audit.csv`다.

## 측정 도중 바뀐 것

| UTC 경계 | 변경 | 바꾸지 않은 결론 |
|---|---|---|
| 08:08:20.764부터 | VU별 전체 fixture 복사를 줄이는 SharedArray 처리 | 발생기 수정이다. 서버 처리량 개선 A/B가 아님 |
| 09:29경 이후 새 Node 실행 | `valid=false`인데 OS exit 0이 될 수 있던 종료 코드 기록 수정 | 이전 raw의 수신 수·미확인 수는 유지. exit 0만으로 성공 판정 금지 |
| 09:39경 | 테스트 nginx 유휴 read timeout 120→3,600초 | 운영 프록시 변경 아님. 연결 유지 수정과 사건 적체를 별도로 판정 |

마지막 비교의 양쪽 원장 사건은 1,408건, 기대 수신은 14,080건이었다. 생산자 10명에서는 340건 미확인·도착분 p95 13,566ms, 100명에서는 미확인 0·p95 2,833ms였다. 이는 aggregate별 순서와 호출 분포의 영향이며 relay 최적화 후 개선율이 아니다.

변경 기록은 `harness-change.json`, `ws-exit-change.json`, `proxy-timeout-change.json`, `final-checks/events-{10,100}-producers/ws-events.json`으로 남아 있다. 최초 API 탐색 뒤 Business 계측을 추가한 재기동도 있었으므로 전체 날을 동일 바이너리·동일 캐시의 한 기준선으로 합치지 않는다.

## 얼마나 좋아졌나: SQL 후보 실험의 범위

독립 부하와 Outbox 회복 뒤 같은 SQL·DB에서 기존 계획 3회, 트랜잭션 안의 후보 인덱스 3회, ROLLBACK 뒤 기존 계획 3회를 실행했다. 아래는 `EXPLAIN ANALYZE` 실행시간 중앙값이다. 순차 실행이므로 캐시·실행 순서의 영향은 남는다.

| SQL 후보 | 기존 | 후보 적용 | 원복 후 | 확인한 변화 |
|---|---:|---:|---:|---|
| 망원경: 활성 `group_members(group_id,user_id)` 부분 인덱스 | 359.707ms | 7.525ms | 339.283ms | 같은 SQL의 후보 중앙값이 기존보다 약 97.91% 짧음. 시간 비율 약 47.8배 |
| 랭킹: 활성 구간 `focus_session_intervals(ended_at,started_at) INCLUDE(session_id)` | 221.393ms | 357.052ms | 158.178ms | 후보 중앙값이 기존보다 약 61.28% 길어짐 |

망원경의 반복 멤버 순차 읽기는 Index Only Scan으로 바뀌었다. 랭킹은 상세 테이블 전체 순차 읽기와 Hash Join을 사용하는 계획으로 바뀌어 이번 조건에서는 악화됐다. 두 후보 모두 `candidateIndexRemaining=0`으로 원복을 확인했다.

이것이 이날 수치로 비교한 개선·악화 범위다. **47.8배는 SQL 실행시간의 비율이며 API RPS 증가율이 아니다.** 후보를 적용한 API 재부하, 쓰기 비용, 운영 적용성은 이 실험에 없다. 원시 근거는 `final-checks/{telescope,ranking}-plan/{baseline,candidate-rolled-back,baseline-after-rollback}.json`과 `restored.json`이다.

## 다음 구현으로 넘긴 과제

Outbox는 순서를 보존하면서 선점 비용과 전송 대기를 줄이고, HTTP 완료·원장·실수신을 함께 재검증해야 했다. 이동은 인스턴스 간 동일 섬 상태와 소유권을 다뤄야 했으며, 채팅은 outbound 대기와 느린 수신자 예산을 별도로 확인해야 했다. SQL 후보는 쓰기 비용과 실제 API까지 연결한 검증이 필요했다.

이 페이지는 10월 18일 당시의 관측과 제안을 보존한다. 이후 구현·로컬 재시험·실제 AWS 부하는 [전체 타임라인](/performance/01-loadtest-timeline)에서 별도 단계로 연결한다. 환경과 데이터, 부하 모델이 다른 실행의 숫자를 나눠 전체 개선 배수를 만들지 않는다.
