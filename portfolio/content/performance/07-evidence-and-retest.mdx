이 기록은 현재 보관된 파일의 범위를 명시한 스냅샷이다. 보고서 한 장의 최댓값만 가져오지 않고 원시 집계, 실패한 실행, 준비 오류, 정리 검증과 후속 구현을 함께 대조했다. 원본 파일 수에는 복사본·압축 묶음·로그·그림·스크립트가 포함되므로 실험 횟수로 해석하지 않는다.

## 어디까지 확인했나

2026-10-22 11:36:48 UTC 기준으로 **7,083개 파일·835,069,288바이트**의 목록과 SHA-256을 확보했다. 해시를 계산하는 동안 크기·수정 시각이 바뀐 파일은 없었다. `.gitignore`, `.DS_Store`, JAR 바이너리는 목록에서 제외했고 실행의 시작·종료·종료 코드 표식은 포함했다.

| 공개 목록의 collection | 대응하는 보관 위치·범위 |
| --- | --- |
| `phone-reports` | phone의 `loadtest/reports`: 7월 실행, 10월 18일 조사·매트릭스, 10월 20일 6개 재시험 묶음, 10월 22일 AWS 자료 |
| `survey-20261018` | `loadtest/survey/results/2026-10-18`의 정리 자료·근거 108개. reports와 중복된 원본도 포함 |
| `implementation-20261022` | 후속 통합 구현 작업의 `loadtest/reports/implementation-20261022`, 14개 |
| `memory-trials` | GROMO-2417 진단 작업의 `server/realtime/build/diagnose`, 초기·반복·실패·압축·힙 대조 자료 |
| `memory-final` | 통합 구현의 `server/realtime/build/diagnose/final-1000-40-uncompressed`, 최종 7개 |

[전체 원본 목록·SHA-256](/performance/evidence/source-manifest.json)과 [폴더별 개수·크기](/performance/evidence/collections.json)로 보관 범위를 확인할 수 있다. `collection`과 상대 `path`를 함께 사용하면 같은 이름의 파일을 구분할 수 있다. 해시는 추후 원본과의 동일성을 확인하는 값이며, 측정 내용이 참이라는 독립 인증은 아니다.

AWS 폴더는 후기 진단·정리 자료까지 **818개 파일**을 포함한다. 초기 347파일 ZIP은 당시의 별도 스냅샷이어서 최신 전체 자료를 대신하지 않는다. 전송용 아카이브와 풀어 놓은 파일은 별개 실험으로 더하지 않았다.

추가 수치도 원본과 연결했다.

- [메모리 비교 차트 수치 JSON](/performance/evidence/memory-comparison-data.json), [SVG](/performance/memory-recovery.svg), [PNG](/performance/memory-recovery.png): 대조 구성의 반복 OOM과 최종 통합 구성의 완주를 상대 시간축으로 표시한다.

공개 파일에는 지표와 판정에 필요한 값만 옮겼다. 원시 인증 토큰, 사용자별 fixture, 응답 본문, 내부 접속 정보, 실행 스크립트와 전체 로그는 다운로드 자료에 포함하지 않는다. 원본의 상대 경로는 근거 위치를 가리키며 공개 사이트에서 그 원본을 직접 내려받는 URL은 아니다.

메모리 CSV의 `trialOomObserved`는 실험 전체에서 OOM을 관측했는지 나타낸다. 각 회차의 `serverPassed`와 범위가 다르다. 예를 들어 첫 회차가 통과하고 두 번째 회차에서 OOM이 난 실험은 첫 회차 행에도 실험 전체 OOM이 `true`로 표시된다.

## 지표를 읽을 때 지키는 구분

| 항목 | 해석 |
| --- | --- |
| 목표 rate와 실제 처리량 | 도착률 설정은 계획이다. 실제 HTTP RPS, 완료 여정 TPS, 드롭을 따로 읽는다 |
| iteration과 완료 여정 | k6 iteration은 실패한 흐름도 포함할 수 있다. 명시적 완료 카운터의 정의를 확인한다 |
| HTTP 계약과 데이터 정합성 | 성공 응답이 DB 정산·보상·Outbox 전달까지 증명하지 않는다 |
| 등록 데이터와 동시 사용자 | 10,000명 fixture는 DB 데이터 규모다. 동시에 연결된 10,000명이 아니다 |
| 발신과 수신 | 채팅 한 건이 섬의 구독자에게 여러 번 전달된다. fanout 수신량을 사용자 발신 TPS로 표시하지 않는다 |
| 원래 판정과 현재 해석 | k6 종료 코드, 당시 보고서 판정, 서버 회복을 포함한 최종 판정이 다를 수 있다. AWS 1,000 연결은 클라이언트가 성공해도 서버 OOM으로 실패다 |
| p95·p99·시간 구간 | 서버와 부하기, HTTP와 여정, 워밍업과 본 측정은 모집단이 다르다. 같은 열처럼 합치지 않는다 |
| 표본 최대와 커널 최대 | 간격 관측의 최대값은 순간 피크를 놓칠 수 있다. cgroup `memory.peak`와 별도로 기록한다 |

## 전후 비교를 허용하는 조건

환경·인스턴스와 자원 한도, 데이터 규모와 fixture 분포, API 계약과 여정 구성, 부하기 위치, 워밍업·유지 시간, 도착률과 사용자 행동 빈도, 판정 기준, 앱·Infra·하네스 버전을 함께 맞춰야 한다. 백로그·캐시·배치 중첩 상태도 기록한다.

7월 GCP, 10월 로컬 공유 Docker, 10월 22일 AWS 운영은 이 조건이 같지 않다. 10월 18일과 20일의 보고서에서도 검증된 자동 비교쌍은 없었다. 따라서 이 기록은 기간 전체의 TPS 향상 배수나 최대 사용자 증가율을 제시하지 않는다.

제한된 대조에서 확인한 수치는 남긴다. 망원경 SQL 후보는 같은 SQL·DB에서 조건별 3회 중앙값이 359.707→7.525ms로 줄었고 원복 뒤 339.283ms였다. 반대로 랭킹 후보는 더 느렸다. 순차 실행과 캐시 영향이 남아 있으며 두 인덱스 모두 원복했다. 로컬 무압축·같은 코드의 힙 65%→40% 대조에서는 표본 최대 cgroup이 767.87→715.04 MiB로 6.88% 줄었다. 모두 제한된 실험 결과이며 운영 개선률이 아니다.

## 다음 운영 시험에서 확정할 To-be

1. **배포 기준 동결:** 반영한 앱·Infra SHA, 이미지, 설정, Realtime 768 MiB 한도와 실제 JVM 옵션을 기록한다. Redis ACL 반영과 낮은 부하의 이동·바다·집중 계약부터 확인한다.
2. **회복 우선 확인:** 유휴 유지, 정상 종료, 강제 종료, 재접속을 반복하고 OOM·재시작·readiness·잔여 서버 세션·작업 큐를 함께 판정한다.
3. **단독 부하 재현:** 기존 AWS의 계정·도서관·홈·집중·채팅을 같은 데이터 조건과 부하 속도·유지 시간으로 다시 측정한다. 집중의 기본 1초와 탐색용 5초 기준을 섞지 않는다.
4. **섬 수로 확장:** 섬당 15명 한도를 지키고 비교용으로 10명을 고정한다. 섬을 늘리면서 사용자당 메시지 빈도를 동일하게 유지한다.
5. **혼합 공통 구간 확보:** 조회·집중 쓰기·채팅이 실제로 겹치는 구간을 측정한다. 조기 종료, 중단 자식, 미확인 여정과 전달 누락을 실패 판정에 포함한다.
6. **쓰기와 종료 검증:** 실행 소유 원장과 DB·정산·Outbox를 대조하고 전용 데이터·접근 권한·임시 자원을 정리한다. 성공 처리량·지연·오류·회복을 모두 통과한 단계만 비교한다.

이 조건으로 운영 재시험을 마친 뒤에야 “동일 조건에서 얼마만큼 좋아졌는가”를 운영 수치로 갱신할 수 있다. 현재 다섯 개선은 구현과 로컬 검증이 완료된 상태이며, 이 문서를 게시하는 작업이 운영 앱 배포나 새 부하 실행을 뜻하지는 않는다.
