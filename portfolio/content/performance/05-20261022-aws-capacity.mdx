2026년 10월 22일의 시험은 **당시 운영 버전의 기준 측정**이다. 읽기 API, 집중 쓰기, 채팅, 유휴 연결을 실제 AWS 운영 경로에서 실행했다. 이후 구현한 개선은 이 시험에 포함되지 않는다.

확인된 숫자는 특정 작업과 유지 시간에 붙는다. 계정 조회 175 RPS, 도서관 조회 40 RPS, 홈 방문 8회/초를 더해서 서비스 전체 TPS로 만들 수 없고, 채팅 연결 300개를 앱 전체 동시 사용자 300명으로 바꿔 읽을 수도 없다.

## 어느 기준으로 통과시켰나

HTTP는 k6의 도착률 지정 방식으로 실행했다. 단일 API의 p95는 500ms, 홈·집중 여정의 p95는 1,000ms, 오류율과 미실행 도착 비율은 각각 1% 이하를 기본 기준으로 삼았다. 탐색 과정에서는 10초 이후 오류율 5% 초과, HTTP p95 2초 초과 등의 중단 조건도 적용했다.

집중 후반 시험에는 **별도의 완화 기준인 여정 p95 5초**를 사용했다. 이 기준의 PASS는 원래 1초 기준을 통과했다는 뜻이 아니다. 모두 이번 탐색을 위한 기준이며 서비스가 합의한 장기 SLO를 대신하지 않는다.

| 수치 | 뜻 |
| --- | --- |
| 목표 RPS | 초당 시작하도록 예약한 HTTP 요청 또는 시나리오 도착 수 |
| 실제 HTTP RPS | 실제 요청 수를 측정 시간으로 나눈 값 |
| 완료 TPS | 명시적 `completed_journeys` 카운터를 측정 시간으로 나눈 값. 하네스가 HTTP 계약 성공을 확인한 여정 |
| WebSocket 요청 연결 수 | CSV의 `connections`는 연결을 시도하도록 지정한 수다. 활동 중인 앱 사용자 수와는 다르다 |
| WebSocket 준비 완료 수 | CSV의 `ready`는 연결·인증·준비 단계를 마친 수다. 파일럿처럼 요청 10개·준비 0개일 수도 있다 |
| 채팅 발신량 | 초당 보낸 메시지 수 |
| 채팅 수신량 | 방 안 수신자에게 전달된 메시지 수. 10명 방의 fanout을 포함한다 |

완료 TPS는 k6 `iterations`를 그대로 대입한 값이 아니다. 예를 들어 최초 집중 8회/초 실행은 iteration 481개 중 완료 카운터가 446개였다. 다만 HTTP 계약 성공은 DB 정산·Outbox 종단 처리를 보증하지 않는다. 여정 p95는 실패한 여정도 포함하는 `iteration_duration`에서 가져왔다.

## HTTP: 20초 통과가 60초 통과를 보장하지 않았다

| 작업 | 20초 탐색 | 60초 확인 | 여기까지 말할 수 있는 결과 |
| --- | --- | --- | --- |
| 계정 `GET /me` | 200 RPS에서 p95 385.2ms | 200에서 627.7ms로 미달; 175에서 136.8ms, 실제 174.940 RPS | **175 RPS·60초 통과**. 오류·미실행 도착 0 |
| 도서관 화면 | 50 RPS에서 p95 227.3ms | 50에서 1,353.2ms로 미달; 40에서 101.0ms, 실제 39.976 RPS | **40 RPS·60초 통과** |
| 신규 계정 홈 5경로 | 10회/초에서 여정 p95 317.9ms | 10에서 1,049.7ms로 미달; 8에서 914.2ms | **8회/초 목표·60초 통과**, 완료 7.921 TPS·HTTP 39.606 RPS |
| 집중 4단계 쓰기 | 1회/초는 p95 848.0ms; 5회/초는 1,672.6ms로 기본 기준 미달 | 5회/초에서 2,643.1ms·오류 0 | **5초 완화 기준만 통과**. 완료 4.874 TPS |
| 집중 8회/초 재시험 | 해당 없음 | p95 3,040.7ms·오류 0, 완료 7.757 TPS | **진단 재시험 결과**. 기본 1초 기준의 안정 한계로 채택하지 않음 |

홈 6경로와 5경로는 서로 다른 작업이다. 신규 계정이 사용할 수 없는 `/screens/board`를 제거한 결과를 기존 홈이 빨라진 것으로 표시하지 않는다. 집중은 시작→일시정지→재개→종료의 쓰기와 정리 조회를 포함하고 단계 사이 간격이 짧다. 실제 사용자의 장시간 집중 행동과도 다르다.

상위 단계에서 Business의 Tomcat 16개와 Data 호출 풀 4개가 모두 사용 중이었다. 홈 조합 실행기 4개와 그 큐의 증가도 관측됐다. 반면 해당 구간 Hikari 대기는 0이었고 기존 연결 시간 초과 카운터는 증가하지 않았다. 따라서 HTTP 호출 풀·화면 조합 경로는 후속 조사 대상으로 남겼다. 설정을 바꾼 운영 대조 시험까지 수행한 결과는 아니다.

## WebSocket: 유지·처리·종료를 따로 판정했다

| 시나리오 | 발신·수신 | 지연·완결성 | 최종 판정 |
| --- | --- | --- | --- |
| 채팅 100명, 10개 섬, 1Hz, 30초 | 발신 2,900건 | p95 6,682.0ms, 수신자 기준 누락 3,820건 | 실패 |
| 채팅 70명, 7개 섬, 1Hz, 60초 | 68.833 발신/초, 688.33 수신/초 | p95 310.7ms, 누락 0 | 이번 p95 기준 통과 |
| 채팅 80명, 8개 섬, 1Hz, 60초 | 발신 4,720건 | p95 5,002.6ms | 지연 기준 미달 |
| 유휴 1,000개, 60초 | 메시지 처리량 측정 없음 | 유지 성공 뒤 종료 시 768 MiB OOM, 재시작 1회 | **서버 실패** |
| 유휴 500개, 60초 | 메시지 처리량 측정 없음 | 종료 후 30초 관측, 추가 OOM·재시작 없음 | 해당 유지·회복 조건 통과 |
| 채팅 300명, 30개 섬, 0.1Hz, 150초 | 28.006 발신/초, 280.065 수신/초 | p95 24.4ms, 4,201건·42,010회 수신, 누락 0 | 낮은 빈도 채팅 단독 통과 |

100명 채팅은 DB에 2,900건이 모두 저장됐다. 마지막 저장은 클라이언트 집계 종료 뒤까지 이어졌다. 따라서 수신 창 안의 누락을 메시지 영구 유실로 단정하지 않는다. 70명 시험도 p99 499.7ms, 최댓값 약 5.96초가 있어 p95 통과가 모든 메시지의 즉시 도착을 뜻하지 않는다.

채팅 지연 구간의 inbound 실행기와 heartbeat 실행기는 9개 표본의 5개 지표가 모두 같았고, inbound 작업자는 1개·큐는 300개까지 관측됐다. 배포 소스의 자동 설정 경로와 함께 보면 실행기 공유가 유력했다. 운영에서 객체 동일성을 직접 조회하지는 않았으며, 후속 로컬 Boot 컨텍스트에서 실제 공유를 재현했다. 구현과 검증은 [후속 개선 글](/performance/06-20261022-remediation)에 분리했다.

1,000개 유휴 연결은 유지 중 약 714.1 MiB를 사용했고, 종료 창인 08:47 무렵 컨테이너 한도에 도달했다. 커널의 메모리 제한 OOM 기록과 `OOMKilled`, 재시작 증가가 일치했다. 08:47:52에 healthy로 돌아왔고 이후 추가 재시작은 없었다. 운영 계측만으로 힙·네이티브 메모리 중 하나를 단일 원인으로 확정하지 않았다.

## 혼합 부하와 집중 오류에 남은 질문

300명 혼합 시험은 채팅 0.1Hz, 홈 5회/초, 집중 1회/초를 함께 실행했다. HTTP 계획 구간은 120초, 채팅은 150초였다. 채팅 측정 약 123.9초에 조기 종료 1건이 발생해 전체 시험을 중단했다. 발신 3,416건, 수신 34,097회, 누락 63회였으며 실제 공통 측정 구간을 확정할 수 없었다.

당시 원장에는 최초 close code·reason이 없었다. 표본상 추가 OOM·재시작이나 지속적인 풀 포화는 없었지만, 그것만으로 순간적인 서버 문제나 네트워크 원인을 배제할 수 없다. 잔여 연결 42개는 09:22:16에 0개로 회복됐다. 이후 300명 저빈도 **채팅 단독** 시험의 통과를 이 혼합 시험의 성공으로 대체하지 않는다.

집중 8회/초 최초 실행에서는 요청 2,285개 중 37개가 실패했다. 운영 접근 로그에서 23개는 HTTP 409, 나머지 14개는 대응하는 요청을 찾지 못했다. 최초 하네스가 응답 오류 정보를 충분히 남기지 않아 14개의 실패 지점을 확정하지 못했다. 후속 진단 정보를 추가한 같은 목표 부하에서 오류가 0으로 바뀌었지만, 서버 개선을 적용한 대조 시험이 아니므로 이를 오류율 개선 효과로 계산하지 않는다.

## 제외한 결과도 기록의 일부다

- 초기 읽기 하네스는 `Array.map`의 index가 검증 함수 인자로 전달돼 정상 HTTP 200을 API 오류로 잘못 셌다. 이 실행은 서버 용량 실패에서 제외했다.
- 공개 `/ws/chat`의 404는 운영 공개 경로가 `/ws/realtime`인 계약 차이였다. 내부 엔드포인트 존재와 공개 라우팅을 구분했다.
- 이동은 STOMP 인증 10명 뒤 `FullState`가 0건이라 측정 구간 자체가 시작되지 않았다. `movement:*` 관련 키와 Redis `TIME` 권한 누락을 확인했다. **이동 0 TPS가 아니라 기능 선행 조건 실패**다.
- 기존 `user.withdrawn` 전달에도 LINK 404와 Realtime의 `sea:*` 권한 오류가 있었다. 시험 전 실패와 시험이 만든 실패를 나눠 확인했다.

## 종료 조건에는 데이터와 비용 정리도 포함했다

대량 탈퇴 이벤트가 기존 위성 서비스 실패를 증폭할 수 있어 공개 탈퇴 API를 1,000번 호출하는 경로는 사용하지 않았다. 정리 직전 정확한 전용 계정·세션·섬·통계 범위를 동결한 뒤, Data와 Realtime 각각의 ROLLBACK 시험 및 독립 복원 검증을 거쳐 COMMIT했다.

| 정리 대상 | 확인 결과 |
| --- | --- |
| 계정·인증·섬 | 전용 계정 1,000개 비활성화, 세션 1,000개 폐기, 멤버십 1,000개 이탈, 섬 100개 종료 |
| 쓰기 차단 | Realtime tombstone 1,000개, 전용 세션 Redis 차단 키 1,000개. 키는 토큰 만료+60초에 자연 만료 |
| 접근 확인 | 아직 만료되지 않은 기존 토큰 1,000개로 `GET /me` 접근 거부. 공개/합성 × 호스트/멤버 4표본의 STOMP CONNECT도 거부 |
| 집중·통계 | 전용 활성 집중·열린 구간 0. 일별 집중 통계 100행의 사용자 참조만 익명화 |
| 기존 데이터 보존 | 정리 직전·직후 기존 사용자 218명의 지정 필드, 망원경 4행, 지정 통계·이벤트의 해시 불변 |
| 남겨 둔 시험 이력 | 집중 1,806건, 채팅 24,147건, Outbox 이벤트 15,553건, 설정·지갑 등. 미지원 SCORE 가입 전달 10건도 보존 |
| 최종 상태 | 09:44:20 앱 전체 healthy, WS 0, 전용 활성 집중 0. 기존 사용자의 활성 집중 1건은 유지 |
| 임시 발생기 | 09:45:41 EC2 종료와 전용 EBS·보안 그룹·IAM 역할·프로파일 제거 확인. 잔여 임시 자원 0 |

새 `user.withdrawn` 이벤트는 0건이었다. 기존 망원경 배열에 시험 섬 UUID가 들어간 외부 행은 보존했고, 정상 조회가 종료된 섬을 걸러내는 계약을 확인했다. 이 검증은 **정리 직전과 직후의 지정 범위 보존**을 입증한다. 부하 시작 전부터 모든 기존 데이터가 전혀 바뀌지 않았다는 증명은 아니다.

시험 데이터는 물리 삭제하지 않았고 최종 DB는 약 72.7 MiB였다. 저장 용량을 시험 전으로 되돌렸다고 표현하지 않는다. 운영 앱·ACL 설정도 이번 측정·정리 과정에서 변경하지 않았다.

## 이 결과를 다음 시험에 사용하는 방법

이번 숫자는 해당 버전·작은 운영 데이터·공개 네트워크 경로·짧은 유지 시간에서 얻은 기준이다. 5초 간격 표본은 순간 피크를 놓칠 수 있고, Realtime 재시작 전후의 누적 카운터는 이어서 차감할 수 없다. 기존 사용자와 외부 이벤트도 있었으므로 완전 격리 시험으로 부르지 않는다.

원본 818개 파일, 22개 전송 아카이브의 추출 일치, 후기 진단·정리 자료까지 확인했다. 예전 347파일 공개 ZIP만으로 범위를 제한하지 않았다. 원시 토큰·계정 식별자·운영 실행 스크립트를 복사하는 대신 수치와 판정에 필요한 공개 집계를 별도로 제공한다.

근거의 연결은 [공개 근거와 재시험 조건](/performance/07-evidence-and-retest), 이후의 코드 변경과 로컬 실험은 [다섯 후속 개선](/performance/06-20261022-remediation)에서 이어진다.
