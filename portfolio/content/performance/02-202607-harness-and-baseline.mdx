7월에는 부하 발생기와 결과 판정기를 만들고, 큰 합성 데이터에서 요청이 실패하는 경로를 조사했다. 보존된 실행 12개 중 10개에 결과가 있으며, 판정은 모두 FAIL 또는 INVALID다. 나머지 2개는 시작·종료 시각과 종료 코드만 남았다. 이 기록이 보여 주는 것은 첫 실패 기준선과 진단 과정이다. 성능 개선을 적용한 뒤 같은 조건으로 통과한 결과는 이 묶음에 없다.

2026-10-22에 숨김 실행 marker까지 포함해 원시 파일을 다시 대조했다. 실행 수와 파일 수는 다르다. `summary.json`, `summary-0.json`, 엔드포인트 표는 한 실행의 다른 표현이다. [12개 실행 CSV](/performance/evidence/july-runs.csv)에 누락 상태까지 남겼다.

## 날짜와 환경

첫 묶음의 폴더 이름은 `20260710T15…Z`지만 한국 시각으로는 **7월 11일 00시대**다. 원시 시작 시각은 7월 10일 15:06:06 UTC와 15:23:49 UTC다. 7월 31일 실행은 06:01:39–08:37:48 UTC, 즉 15:01:39–17:37:48 KST에 걸쳐 있다. 아래 표의 시각은 UTC로 통일했다.

| 항목 | 7월 초 묶음 | 7월 31일 묶음 |
|---|---|---|
| SUT 메타데이터 | GCP `n2-standard-2`, Intel Ice Lake | GCP `n2d-standard-2`, AMD Milan |
| 애플리케이션 | loadtest 프로파일, `-Xmx2g` | 같은 프로파일·힙 기록 |
| DB | Cloud SQL `db-custom-2-8192`, PostgreSQL 16 | 같은 사양 기록 |
| 발생기 | `c2-standard-4` | `n2-highcpu-4` 1대, Intel Cascade Lake |
| 기록된 코드 SHA | `8d25ece6` | `36ec6e53`, `2a5b1785`, `55001b21`, `4f448e9e` |
| 시드·믹스 표기 | `seed-v1`, `assumed-v1` | 같은 표기이나 실제 엔드포인트 집합은 변경됨 |

`local073*`라는 폴더 이름을 로컬 Docker 환경이라는 뜻으로 읽지 않는다. 위 사양은 각 `meta.json`에 기록된 값이다. 일부 짧은 SHA는 현재 로컬 Git 객체에 없으므로 당시 배포 소스 전체까지 복원됐다고 주장하지 않는다. 과거 설계 노트의 10만 사용자·집중 세션 3,000만 행은 데이터 설계·진단 문맥이며, 각 run 폴더가 행 수 스냅샷을 전부 갖고 있는 것은 아니다.

원시 경로의 공통 접두사는 `phone/loadtest/reports/`다. 인증·DB reset·요청 계약을 정리한 과정은 [하네스 구축기](/research/loadtest-harness)와 [설계 결정](/research/loadtest-design)에 보존한다.

## 무엇을 알게 됐나

당시 진단 노트는 시드 JWT 계약, DB reset 뒤 앱 재기동, 요청 계약 불일치를 먼저 확인하고, 이후 `focus_sessions` 관련 고비용 SQL을 주요 병목으로 좁혔다. 각 run의 `pg_top20.csv`에는 호출 수·평균 실행시간·총 실행시간을 남겼다. 이는 SQL 관측 근거이고, API 지연의 한 지점과 같거나 같은 시간창의 원인별 분해는 아니다.

7개 경로, 24개 경로, 23개 경로를 달리한 격리 결과는 특정 조회가 공유 자원을 오래 사용하는 가설을 지지한다. 하지만 요청 집합이 달라진 비교다. 마지막 run도 오류 8.08%, HTTP p95 4.845초로 실패했다. 이 결과만으로 단일 원인, 전체 장애 해소 또는 인덱스 적용 효과를 확정할 수 없다.

| 격리 세 번으로 단일 원인 실증 | 주요 병목을 좁힌 비교다. 동일 믹스에서 인덱스를 적용·원복한 대조 실험은 보존 자료에 없다. |

이 정정은 당시 조사 과정을 지우지 않는다. 관측값, 당시 해석, 이후 재검증을 분리한다. [기존 진단 글](/research/loadtest-error96)에도 같은 정정을 반영했다.

## 얼마나 좋아졌나

이 묶음에서 **서버 성능 개선율은 계산하지 않는다.** 83.86%와 8.08%의 오류율을 나눠 개선 배수로 쓰면, 달라진 요청 집합과 남은 실패를 숨기게 된다. 인덱스 추가는 당시 후속 과제였으며, 이 run 폴더에는 적용 전후 같은 부하·데이터·코드 조건을 고정한 통과 결과가 없다.

이후 비교를 위한 요구는 명확하다. 같은 데이터 스냅샷, 성공 가능한 동일 요청 집합, 같은 도착률·지속 시간·워밍업과 복구 조건을 고정하고, 변경 하나를 적용한 뒤 HTTP·DB·오류 분류를 함께 다시 측정해야 한다. 10월의 로컬 Docker와 AWS 결과는 이 7월 GCP 결과에 곧바로 이어 붙인 개선 배수가 아니다.
