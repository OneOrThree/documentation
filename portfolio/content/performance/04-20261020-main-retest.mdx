이 시험에서 확인한 것은 **조건별 처리량과 실패 지점**이다. fixture 10,000명을 만들었다고 10,000명이 동시에 앱을 사용한 것은 아니며, 개별 API의 60초 통과가 앱 전체의 운영 용량을 뜻하지도 않는다. 혼합 부하는 두 종류 모두 실패했다.

당일 재시험 중 새 애플리케이션 성능 수정이나 인덱스 추가는 없었다. V129 인덱스와 V130 읽기 모델 등은 이미 main에 포함돼 있었다. 과거 결과와 달라진 숫자를 이번 시험의 코드 개선 효과로 계산하지 않는다.

## 환경과 판정 기준

메타데이터의 대상은 `localhost:18088`, 발생기 호스트는 macOS arm64, 서버는 **로컬 Docker 조사 환경**이다. Docker VM은 8 CPU와 메모리 8,217,145,344바이트를 공유했고 기존 개발 컨테이너도 함께 있었다. 클라우드 운영 서버의 측정값으로 분류하지 않는다.

초기 시험의 서버 SHA는 `6e48579502831f552d6129987631e41a869f7f25`, 확장과 후속 시험은 `971061dc679dbe1d5d96690c3cb3f218d03f67fd`다. 확장 시 Realtime은 최신 main으로 다시 빌드했고 Data·Business·Notification은 코드·설정·마이그레이션 동등성을 확인해 기존 이미지를 사용했다. 실행별 이미지와 하네스 해시는 원본 메타데이터에 남아 있다.

새 조사 DB·Kafka로 시작한 뒤, 초기 100명 fixture를 이어받아 1,000명과 10,000명으로 늘렸다. 사용자별 90일 합성 집중 이력이 있으며 실제 90일간의 정산·보상·과거 멤버십을 재현한 것은 아니다. 뒤로 갈수록 쓰기 이력과 캐시가 누적됐다.

| 항목 | 이번 연구용 기준·측정 방식 |
| --- | --- |
| 개별 읽기 HTTP | p99 200ms 이하 |
| 홈 진입·집중 여정 | 여정 p99 500ms 이하 |

이 기준은 운영 SLO가 아니다. 원본 k6에는 미발신 1건에도 실패하는 threshold 등이 있어, **k6 종료 코드 99와 연구 기준의 실패는 일치하지 않을 수 있다**. CSV는 원문 종료 코드와 연구 판정을 둘 다 보존한다. 사건 전달·유휴 연결·paced HTTP의 지연 한도가 정해지지 않은 경우에는 통과를 임의로 채우지 않았다.

HTTP RPS는 요청 완료 수/초다. 홈 진입은 한 여정에서 HTTP 6개, 집중 수명주기는 5개를 호출하므로 성공 여정 TPS와 구분한다. 일반 조회 API의 여정 TPS는 미계측이다. WS의 연결 수, 발신률, 수신자별 전달률도 서로 다른 값이며, 수신 p99에는 관측 창 안에 도착한 표본만 포함된다.

## 초기 실패와 확장 시험

초기 100명 fixture에서 `stats_focus_history` 25 RPS 목표는 실제 10.74 RPS, HTTP p99 8,891.34ms, 오류율 33.78%, 미발신 103건이었다. 오류·미발신이 커서 다음 100 RPS 단계를 생략했다. 홈 진입 100여정/초 목표도 실제 HTTP 475.62 RPS, 여정 p99 788.37ms, 미발신 177건과 최대 50 VU 경고를 남겼다. 서버 용량과 발생기 제한을 분리해야 하는 결과다.

확장 시험의 같은 이름의 이력 조회는 100명 fixture·25 RPS·10초에서 p99 15.27ms, 오류·미발신 0으로 관측됐다. **초기 8.9초 지연이 재현되지 않았다는 뜻이며, 원인을 고쳤거나 그 비율만큼 빨라졌다는 증거는 아니다.** 1,000명 fixture의 25 RPS에서는 p99 375.07ms, 10,000명 fixture의 100 RPS에서는 p99 1,001.82ms와 미발신 276건이 다시 관측됐다.

확장 카탈로그는 61개 시나리오였고, `settings`의 준비 실패를 제외한 60개 HTTP 시나리오에서 측정 행이 남았다. 저장된 OpenAPI 128개 operation이나 최신 API 전체를 모두 검증한 범위로 읽지 않는다. 읽기 외에 집중 시작·상태 전환·종료 쓰기, 채팅 저장·전달, 이동, Outbox 전달, 혼합 부하를 포함했다. 실제 순서는 읽기 → 집중 쓰기 → 집중 이력 조회여서 뒤의 이력 조회에는 앞선 쓰기와 회복 과정의 영향이 섞인다.

## 혼합 실패와 후속 시험의 의미

### 혼합 두 종류는 전체 통과가 아니다

`mixed-fast`와 `mixed-paced`는 각각 300초를 계획했다. 구성상 고유 사용자 200명, 소켓 300개였으나 준비 성공 연결의 합계는 각각 300개와 66개였다. 이 합계를 동일 시각의 생존 연결 수나 실제 고유 활성 사용자 수로 바꾸지 않는다.

`mixed-fast`는 홈·집중의 필수 HTTP 측정 결과가 없고 채팅·이동·사건 watcher도 실패했다. `mixed-paced` 역시 홈 결과가 없고 WS 연결 준비가 실패했다. 원본 완료 기록은 Realtime 컨테이너의 OOM 1회도 보고한다. 따라서 단일 API 통과 값을 더해 혼합 사용자 용량을 제시할 수 없다.

paced 집중은 시작 요청 100개와 종료 요청 100개를 따로 관측했다. 각각 약 5.05·5.04 HTTP RPS, p99 75.31·160.35ms, HTTP 오류 0이지만, 이 두 짧은 구간의 RPS를 300초 전체 여정 TPS로 쓰지 않는다. 나중에 DB 저장 수가 늘어난 경우도 WS 전달 성공이나 종단 간 내구성의 증명과 구분한다.

### 최신 읽기 3개 확인, 3개는 준비 조건 부족

`current-reads`는 매거진 자산·오늘 매거진·매거진 목록을 각각 100 RPS로 60초 확인했다. 실제 RPS는 99.91 / 100.00 / 99.98, HTTP p99는 19.15 / 18.15 / 9.85ms였다. 상품 상세·프로모션 편집기·매거진 상세는 필요한 데이터·인증 조건을 갖추지 못해 미측정으로 남겼다. 이 세 항목을 성능 0이나 통과로 채우지 않는다.

### 주간 배치의 직접 blocking은 관측했지만 대조군도 실패했다

`batch-overlap`은 fixture 10,000명, 집중 25여정/초를 각 60초 실행하면서 A1(배치 없음) → B(주간 집계 SQL 1회 겹침) → A2(배치 없음)를 비교했다.

| 지표 | A1 | B | A2 |
| --- | ---: | ---: | ---: |
| 완료 TPS | 24.65 | 16.04 | 24.73 |
| 여정 p99, ms | 1,253.74 | 3,693.40 | 729.53 |
| HTTP p99, ms | 154.53 | 687.49 | 109.93 |
| HTTP 오류율 | 0% | 9.42% | 0% |
| 미발신 | 16 | 47 | 10 |

B에서 배치 backend가 직접 blocking한 표본 4개를 관측했고, 원장 불변 조건과 겹침 절차는 확인했다. 다만 A1·A2도 여정 p99 500ms 기준에 실패해 `controlQualified=false`다. 한 번의 A1/B/A2 결과를 통제된 인과 효과나 개선 폭으로 확정하지 않는다. 특히 종료 요청의 p99는 B에서 오히려 낮았고 최대 지연만 3,009.46ms로 커졌으므로, 여정 p99와 특정 요청의 p99를 섞어 설명하지 않는다.

### 비어 있지 않은 목록과 회복은 별도 조건이다

`joinable30`은 기존 1,000개 섬 중 30개의 정원만 10→15명으로 바꿔 입장 가능한 목록을 만들었다. 실제 거주 인원은 섬당 10명으로 유지했다. 목록·망원경 조회는 각각 100 RPS × 60초에서 실제 100.00 RPS, HTTP p99 **114.15 / 40.24ms**, 오류·미발신 0으로 통과했다. 종료 후 정원 원복을 확인했으며 변경에 따른 명령·이벤트 이력은 남았다.

`recovery`는 앞서 준비 단계에서 막힌 목록·망원경 조회를 25 RPS × 20초로 한 번씩 수행했다. 실제 25.04 RPS와 p99 **11.64 / 49.27ms**로 연구 기준을 통과했다. 이동 10연결·20Hz 정책 초과 시험은 p99 71.98ms였지만 전달 유효성은 실패했고 일반 용량 판정에서 제외했다. DB·캐시·backlog와 실행 시점이 달라진 후속 확인이므로 원래 실패를 삭제하지 않는다.

## 개선 폭을 계산하지 않은 이유

확장 요약은 당일 초기 관측 19건과 10월 18일 과거 관측 646건을 비교 후보로 조사했으나 **검증된 전후 비교쌍은 0건**으로 남겼다. fixture 해시, 하네스, VU 상한·사전 할당·사용자 선택 조건이 달랐고 캐시·동거 부하·초기 backlog의 동등성도 확인되지 않았다. 10월 18일의 p95와 이번 p99 판정도 같지 않다.

따라서 이 묶음에서 공개할 동일 조건 API 개선 배수는 없다. 공개할 수 있는 것은 명시한 조건에서 관측한 실제 처리량·지연·오류, 어떤 초기 문제가 재현됐는지, 어떤 후속 시험이 여전히 실패했는지다. 장기 운영 최대 사용자 수와 TPS는 별도 재시험 과제로 남는다.

## 공개 데이터와 원본 연결

[HTTP 관측 586행 CSV](/performance/evidence/oct20-http.csv)와 [WebSocket 결과 56행 CSV](/performance/evidence/oct20-websocket.csv)는 실행 시각, fixture 크기, 목표와 실제 부하, 지연, 오류, 원문 종료 코드·연구 판정 및 원본 상대 경로를 제공한다. HTTP 중 k6 CSV 584행의 요청 수·실제 RPS·p99·HTTP 오류율을 저장된 k6 summary와 대조했으며, CSV 반올림을 제외한 불일치는 없었다. 일반 API의 TPS와 미측정 항목은 빈 값으로 유지했다.
