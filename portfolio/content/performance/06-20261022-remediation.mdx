운영 측정은 문제를 드러냈고, 후속 작업은 재현 가능한 수정과 검증을 남겼다. **이 글의 결과는 운영 미배포 상태의 로컬 검증**이다. 운영 최대 TPS가 높아졌다거나 OOM이 해결됐다고 확정하는 전후 측정은 아직 없다.

## 출발점을 분리했다

운영 측정의 phone SHA는 `6a22c3d30a972b94fc97791898e5ab8a24eae622`였다. 구현은 그 뒤 병합된 PR #1245·#1246을 포함하는 `a94e72c0402d97a1a647a6aaa745cb8973e93a38`에서 시작했다. Infra 출발점은 `71bae814f343a5f75a6505ed935b5fc7a8a72dc4`였다.

따라서 운영과 최종 로컬 결과 사이에는 환경뿐 아니라 소스 차이도 있다. 최종 통합 JAR는 `2e185d2fcb47d7ce50c6114b47af89341eaadb555ba99ade728193daa5a960ce`로 고정했다. 보고서 생성 시점에는 변경을 commit·운영 배포하지 않았다. 별도 GROMO-2421 작업은 이 구현 근거에 포함하지 않는다.

## 메모리는 한 번 통과한 뒤 다시 실패했다

처음에는 종료 순간 Tomcat 작업자 증가를 의심했다. 같은 768 MiB·2 CPU 조건에서 1,000개를 연결하고 닫자 기본 최대치에서는 작업자가 200개까지 늘었고, 최대 32 설정에서는 32개에 머물렀다. `baseline65-deny-tracing`과 `bounded32-deny-tracing` 단발 대조의 종료 전후 RSS 증가는 각각 약 63.05 MiB와 18.13 MiB였다. 이름에 `tracing`이 없는 앞선 `baseline65-deny` 탐색은 이 수치의 대조 쌍이 아니다.

하지만 단발 실험의 힙 committed 시작 상태부터 달랐고 관측도 짧았다. 이 차이를 곧바로 안정성 개선률로 쓰지 않았다. **32개로 제한한 채 60초 유지·60초 회복을 반복하자 두 번째 접속 증가 중 OOM이 재현됐다.** 스레드 제한만으로 수정 완료를 선언할 수 없었다.

모든 비교는 로컬 ARM Docker의 768 MiB 컨테이너, CPU 제한 2, Datadog agent를 포함한 환경에서 진행했다. JRE는 Temurin 17.0.20.1+1이고, 의존 서비스는 로컬 PostgreSQL·Redis였다. CPU 제한과 별개로 Docker 호스트에는 8개 CPU가 보였다. 기존 바다 ACL 실패를 재현하는 조건도 유지했다.

초기 진단 JAR는 `2444ffff4c17e753870621fcf72f64c3f75b475f5d259eb24307aa62ab4e5e62`다. 최종 JAR에는 실행기 분리와 진단 변경도 함께 들어갔다. 초기 JAR와 최종 JAR의 차이를 압축 하나의 효과로 환산하지 않는다.

### 무엇을 원인으로 볼 수 있나

NMT 진단에서는 힙 committed가 약 304.5 MiB인 상태에서 JVM 비힙·스레드·코드·메타데이터와 NMT에 완전히 잡히지 않는 프로세스 메모리가 함께 컸다. 직접 버퍼는 수 MiB 수준이어서 그것만으로 전체 사용량을 설명할 수 없었다. GC 뒤 힙 used가 줄어도 committed와 RSS가 같은 속도로 돌아오지는 않았다.

압축을 끈 로컬 대조에서 반복 실패가 사라졌다는 사실은 중요하지만, 운영 OOM의 유일 원인이 압축이라고 입증한 것은 아니다. 운영 당시 실제 확장 협상 응답을 남기지 않았고, 클라이언트의 송신 압축 동작도 달랐다.

Node 22.23.4는 `permessage-deflate`를 제안하지만 송신 프레임은 압축하지 않고 수신 압축 해제를 지원한다. Python `websockets`는 협상 뒤 CONNECT 같은 데이터 프레임도 압축한다. Tomcat의 압축기는 연결마다 native 자원을 만들지만 정상 종료에서 해제하는 코드도 있다. 따라서 이번 자료만으로 특정 해제 누락이나 네이티브 누수를 확정하지 않는다.

### 같은 조건에서 계산할 수 있는 차이

짧은 **클라이언트 무압축** 두 실험은 JAR·probe SHA가 같고, 768 MiB·2 CPU·Tomcat 32·1,000개·초당 40연결·10초 유지·5초 회복·정상/강제/정상 순서를 공유한다. 바꾼 설정은 힙 비율 65%→40%였다.

| 최대 관측값 | 65% | 40% | 차이와 계산 |
| --- | --- | --- | --- |
| cgroup | 767.87 MiB | 715.04 MiB | 52.83 MiB 감소. `(767.87 - 715.04) / 767.87 × 100 = 6.88%` |
| 프로세스 RSS | 737.70 MiB | 643.95 MiB | 93.75 MiB 감소. `(737.70 - 643.95) / 737.70 × 100 = 12.71%` |

각 설정에서 3회로 이뤄진 실험을 한 번씩 실행한 결과다. 무작위 반복·신뢰구간이 없고 호스트를 완전히 격리하지 않았으므로 반복 가능한 운영 개선률로 일반화하지 않는다. 표본 최댓값이며 커널 `memory.peak` 값과도 구분한다.

## 최종 변경은 연결 경로와 메모리 예산을 함께 제한했다

Tomcat 작업자는 최대 32개로 제한했다. Realtime에만 명령행 `MaxRAMPercentage=40.0`을 넣어 컨테이너 768 MiB 안에서 비힙·추적 agent·native 메모리가 쓸 여유를 확보했다. 공통 `JAVA_TOOL_OPTIONS=65`는 다른 서비스에 그대로 남는다. 실제 JVM 확인에서 명령행 40%가 우선했고 최대 힙은 322,961,408바이트였다.

WebSocket은 `/ws/chat`과 `/ws/realtime`의 handshake에서 확장 제안을 제거한다. Spring의 선택 목록만 비우면 Tomcat이 기본 확장을 다시 협상할 수 있어 실제 요청 경로에서 차단했다. 현재 정책은 모든 WebSocket 확장 협상을 끄며, 다른 확장 보존을 약속하지 않는다. Origin·STOMP 하위 프로토콜·인증 계약은 유지한다.

실제 Tomcat 소켓 테스트로 정상 압축 제안, 미제안, 잘못 닫힌 따옴표 형태의 우회 입력을 두 경로에서 확인했다. 101 응답에 확장이 없고 `v12.stomp`, text·binary CONNECT/receipt와 정상 종료가 동작했다. 허용하지 않은 Origin은 403이었다. 서버를 고쳤다는 확인을 위해 최종 부하 클라이언트도 **압축을 계속 제안**하도록 했다.

## 최종 1,000개 × 3회 회귀

![동일 768MiB 로컬 반복 연결 시험: 스레드32만 적용한 대조군은 두 번째 회차 OOM, 최종 통합 변경은 세 회차 완료](/performance/memory-recovery.svg)

같은 JRE·768 MiB·2 CPU·1,000개·60초 유지·60초 회복 조건의 시간축이다. 최종 시험은 JAR 통합 변경·힙 예산·압축 정책이 함께 달라 단일 변경 효과나 운영 전후 개선률을 보여주는 차트는 아니다.

| 회차 | 종료 방식 | 최대 관측 cgroup | 최대 관측 RSS | 서버 세션·큐 회복 | 결과 |
| --- | --- | --- | --- | --- | --- |
| 1 | 정상 close | 648.43 MiB | 605.23 MiB | 세션 0, 작업 큐 회복, drain 0.193초 | 통과 |
| 2 | 강제 TCP 종료 | 672.89 MiB | 656.73 MiB | 세션 0, 작업 큐 회복, drain 1.095초 | 통과 |
| 3 | 정상 close | 661.51 MiB | 657.96 MiB | 세션 0, 작업 큐 회복, drain 0.554초 | 통과 |

매 회 1,000개를 초당 40개씩 연결하고 60초 유지한 뒤 닫고 60초 관측했다. 압축 협상 응답은 모두 비어 있었고, 정상 종료 2,000개는 peer close code 1000을 확인했다. 강제 종료는 정상 close handshake 성공으로 세지 않았다. OOM·재시작·조기 종료는 없었다.

클라이언트의 `close()` 반환만으로 통과시키지 않았다. cgroup의 현재 메모리·OOM 카운터 조회 성공, 컨테이너 생존·health, 실제 서버 세션과 STOMP 세션 0, 작업 큐 회복을 따로 판정했다. 메모리 파일 조회 실패나 정리 조회 오류도 성공으로 바뀌지 않도록 했다. heartbeat 같은 주기 스케줄 작업의 예약 항목은 작업 backlog와 구분했다.

표의 최대 cgroup 관측값은 672.89 MiB다. 별도 live 기록의 커널 `memory.peak`는 약 674.41 MiB로, 표본이 놓친 피크를 포함하므로 서로 다른 값으로 남겼다. 사용한 컨테이너·네트워크는 삭제했고 독립 확인에서 잔여 수는 0이었다.

최종 실행 전에는 다른 작업의 Gradle worker가 있었고 GROMO-2421 작업도 포함됐다. before/after 호스트 상태를 보존했다. 이 시험은 **로컬 cgroup 메모리·회복 회귀**이며 처리량 벤치마크나 운영 환경 완전 복제가 아니다.

## 진단과 복구도 회귀 대상으로 삼았다

혼합 시험은 구성요소별 성공만으로 전체 성공을 만들지 않는다. 중단된 자식 프로세스의 부분 결과를 남기고, 실제 공통 측정 구간이 목표보다 짧으면 실패로 판단한다. 종료 코드나 클라이언트 힌트는 원인 조사 단서로 남기며 서버 원인 확정으로 승격하지 않는다.

집중 복구는 실패했다는 이유만으로 현재 세션을 종료하지 않는다. 같은 실행의 fixture 지문·start intent·현재 세션의 소유 근거가 일치할 때만 쓰기를 허용한다. `current=null`, 불완전 응답, 유실된 원장은 미확인으로 유지하고 성공 판정을 막는다. HTTP 종료 확인이 DB 정산·보상·Outbox 검증을 대신하지도 않는다.

## 운영에서 확인할 일은 남아 있다

운영 반영 시에는 새 버전·설정·자원 한도를 다시 동결해야 한다. Redis ACL은 일반 앱 배포만으로 적용되는 변경이 아니므로 기존 bootstrap 경로의 반영 여부부터 확인한다. 낮은 부하에서 인증·이동·바다·집중 계약을 확인한 뒤 유휴 유지·정상 종료·강제 종료·재접속을 거친다.

그다음 섬당 10명을 고정하고 섬 수를 늘리며 채팅·조회·집중 단독 시험과 혼합 시험을 다시 수행한다. 오류·지연·완료량뿐 아니라 실제 공통 구간, 종료 뒤 서버 회복, 실행 소유 원장과 DB의 일치를 함께 확인해야 한다. 구체적인 공개 근거와 판정 조건은 [근거·재시험 문서](/performance/07-evidence-and-retest)에 모았다.
