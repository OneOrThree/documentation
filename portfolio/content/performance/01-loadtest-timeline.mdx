부하테스트의 변화는 **측정 가능한 상태를 만드는 작업 → 기능별 병목 탐색 → 운영 한계 확인 → 병목 수정과 재검증**으로 이어졌다. 서로 다른 환경의 숫자를 한 줄로 연결하면 실제로 확인하지 않은 개선률을 만들게 된다. 여기서는 실행 조건과 실패한 실험까지 함께 남긴다.

이 문서는 2026년 10월 22일에 보유한 원본 보고서, 정리 자료, 구현 검증을 대조한 기록이다. 과거 실험일과 오늘 문서를 정리한 날은 다르다. 상세 문서에서는 폴더의 날짜, 메타데이터의 실행 시각, UTC/KST를 구분한다.

## 현재 운영에서 확인한 경계

아래는 **개선 전 AWS 운영 기준선**이다. 서로 다른 시나리오의 숫자를 합쳐 전체 앱의 동시 사용자 수로 계산하지 않는다. 상세한 유지 시간·오류·다음 실패 단계는 [운영 시험 기록](/performance/05-20261022-aws-capacity)에 있다.

| 시나리오 | 확인한 기준선 | 해석 |
| --- | --- | --- |
| 계정 읽기 | 175 RPS 단계 통과 | 해당 읽기 API의 단독 부하 |
| 도감 읽기 | 40 RPS 단계 통과 | 계정 API와 비용이 다른 경로 |
| 신규 사용자 홈 | 목표 8여정/초, 관측 약 39.6 HTTP RPS | 완료 7.921 TPS. 한 여정이 HTTP 요청 5개를 포함한다 |
| 집중 수명주기 | 목표 5cycle/s에서 p95 약 2.64초 | 완료 4.874 TPS. 완화한 5초 탐색 기준 통과이며, 1초 목표 통과가 아니다 |
| 다중 섬 채팅 | 7개 섬 × 10명, 사용자당 초당 1메시지 | 70명 조건의 60초 단독 시험. 읽기·쓰기 혼합 수용량과 다르다 |
| 유휴 연결 | 500개 유지 시험 통과 | 1,000개는 종료 부근 서버 OOM이 있어 서버 기준 실패 |
| 읽기·집중·채팅 혼합 | 공통 성공 구간 미확보 | 300명 저빈도 채팅 단독 통과를 혼합 시험 통과로 대체할 수 없다 |

섬당 정원은 **15명**이다. 채팅 수용량 탐색에서는 섬당 10명으로 고정하고 섬 수를 늘린다. 한 섬에 정원 이상을 몰아넣어 만든 결과를 실제 서비스 수용량으로 사용하지 않는다.

## 숫자를 읽는 단위

- **HTTP RPS**는 초당 HTTP 요청 수다. 성공한 요청 수와 전체 시도 수를 따로 본다.
- **여정/초 또는 cycle/s**는 시작부터 종료까지 하나의 사용자 흐름을 뜻한다. 여러 HTTP 요청이 들어갈 수 있고, 완료 카운터가 없으면 완료 TPS를 추정하지 않는다.
- **채팅 전송/초**와 **수신 전달/초**는 다르다. 섬의 구독자 수만큼 전달이 늘어나므로 전달 수를 사용자가 보낸 메시지 수로 표시하지 않는다.
- **유휴 연결 수**는 연결을 유지하는 능력이다. 채팅·이동·집중·조회·쓰기를 수행하는 활성 사용자 수와 다르다.
- **p95/p99**는 측정 주체와 구간을 함께 읽는다. k6 HTTP 지연, 서버 측 지연, WebSocket 종단 지연을 같은 열에서 섞지 않는다.

## 다음에 운영 개선 폭을 확정하는 방법

1. 운영에 반영한 앱 SHA·이미지·Infra 구성 SHA를 고정하고 Redis 권한 및 낮은 부하의 기능 동작을 확인한다.
2. 기존과 같은 데이터·fixture·워밍업·부하 속도·유지 시간·SLO로 단독 시나리오를 다시 실행한다. 먼저 유휴 유지·종료·재접속의 서버 회복을 확인한다.
3. 섬당 10명을 유지하며 섬 수를 늘리고, 홈·집중·채팅의 실제 공통 측정 구간을 확보한다. 중간 종료와 미확인 진행 중 쓰기는 누락하지 않는다.
4. 성공 처리량, p95/p99, 오류율, 드롭·전달 누락, OOM·재시작, 세션·큐 회복, 정산·Outbox 상태가 함께 충족될 때 개선 폭을 계산한다.

이전 보고서에서 “통과”한 값도 그때의 조건에서만 유효하다. 이후 더 엄격한 하네스를 만들었다고 과거 실행을 소급해 통과 또는 실패로 바꾸지 않고, 원래 판정과 현재 해석을 함께 남긴다.
