## 맥락

앱이 강제 종료되면 cancel PATCH가 전송되지 않아 `ended_at IS NULL`인 라이브 마커가 남았다. 친구·리그 그리드에 최대 12시간 "집중 중" 유령이 떴고, 라이브 집중시간 표시값은 그동안 계속 증가했다. sweeper는 매시 정각에 12시간을 넘긴 마커만 정리했다(GROMO-610). 하트비트는 없었다.

표시 전용이라 믿었던 이 마커가 정산 대기 가드에 물려 있었다. 가드가 "열린 마커가 있으면 기다린다"였으므로 고아 마커 하나로 그 회차 정산이 최대 12시간 지연됐고, 자동 환불 시한을 넘기면 내기가 무효 처리됐다.

## 선택지

실시간 계보가 WS로 향하는 전제 세 개를 이 서비스의 실제 값으로 다시 쟀다.

| 축 | 일반 계보의 전제 | 실제 값 |
| --- | --- | --- |
| 이벤트 빈도 | 초 단위 | 집중 start/stop, 분 단위 |
| 지연 허용치 | 지연이 곧 UX 손해 | 60초 지연도 사용자가 인지 못 함 |
| 클라 생존 패턴 | 클라가 계속 떠 있다 | suspend가 정상 동작 |

| 선택지 | 판단 |
| --- | --- |
| WebSocket 연결 생존 = 세션 생존 | 소켓이 살아도 집중이 아닐 수 있고(앱만 켜둔 상태), 죽어도 집중일 수 있다(폰을 뒤집어 놓은 상태). presence와 session liveness는 다른 개념이라 기각 |
| SSE | 복귀 시 `Last-Event-ID` 재동기화가 "폴링 1회"와 같은 자리에 도착한다. React Native에 폴리필이 필요해 기각 |
| 기존 유지 — 60초 × 3계열 폴링 + 12시간 sweeper | 유령 상한이 12시간. 기각 |
| 하트비트/리스 + 조건부 요청 폴링 | 채택 |

## 결정

**세션 생존은 리스(마지막 하트비트 시각 + TTL)로 판정하고, 표시는 20~30초 조건부 요청 폴링으로 갱신한다. WebSocket은 판정에서 제외한다.**

| 파라미터 | 값 | 이유 |
| --- | --- | --- |
| 하트비트 주기 | 3분 | foreground일 때만 전송 |
| 리스 TTL | 10분 | 하트비트 2회 유실까지 허용 + 네트워크 지터 여유 |
| sweeper 주기 | 10분 | 매시 정각에서 단축 |
| 폴링 주기 | 20~30초 + AppState 게이팅 | 변화 없으면 `If-None-Match` → 304, 본문 0바이트 |

관계식은 `TTL ≥ 주기 × N + 지터`이고, N은 몇 번의 하트비트 유실을 이탈로 보지 않을 것인가다. 백그라운드에서 하트비트를 보내려고 시도하지 않는다. iOS suspend 타이밍은 비결정적이라 "보내려고 했는데 못 보낸" 상태와 "보낼 필요가 없던" 상태를 구분할 수 없다. AppState가 active로 복귀할 때 1회 보낸다.

리스 만료는 표시 상태만 소멸시키고 사실은 남긴다. 시간은 클라가 주장하고 서버가 세 항으로 클램프한다.

```text
endedAt ≤ min( 클라 주장, last_heartbeat_at + grace, now + 시계오차(2분) )
```

정산 가드 대상은 "도는 마커"에서 "반영이 확정되지 않은 세션"으로 넓히고 유예를 5분으로 잡았다. 유저당 라이브 마커 1개 불변식을 서버에 세웠다(GROMO-1287). 재전송 중복 적립은 블록마다 붙는 `client_key`와 DB partial unique 제약으로 막고, 오프라인·강제 종료 시 유실은 클라이언트 아웃박스 50건으로 막는다.

## 근거

- 원인 어디에도 "WebSocket이 없어서"는 없었다. 남은 문제는 신뢰성(생존 증명·멱등·내구 큐)과 표시(폴링 팬아웃)였고 둘 다 HTTP 안에서 풀렸다.
- 푸시가 절약하는 것은 "변화 없는 응답"뿐이고, 조건부 요청(ETag/304)으로 거의 같은 크기까지 줄어든다. 친구·리그·그룹 3계열을 소셜 요약 단일 배치 엔드포인트로 합치고 주기를 60초에서 20~30초로 줄였는데도 대부분의 응답이 304라 트래픽이 내려갔다.
- 기존 sweeper는 종료 시각을 `시작 + 12시간`으로 채웠고 그건 사실이 아닌 값이라 통계 예외 처리가 붙어 있었다. 리스 기반 sweeper는 `마지막 하트비트 + grace`로 채우므로 예외 처리가 필요 없다.
- 고아 마커가 정산을 붙잡는 시간이 12시간에서 5분으로 줄었다.

WebSocket이 필요한 곳과의 대비: 채팅은 양방향이라 STOMP WebSocket을 쓰고, 채팅 전용 서비스(`:8081`)로 분리해 persist-first와 Redpanda 팬아웃을 깔았다. 그 경로의 두 층 인증과 cross-instance 릴레이는 [채팅 서버 팬아웃 설계](/research/chat-fanout)에 있다. 이 ADR은 집중 세션의 생존 판정에만 적용된다.

## 영향

- 재검토 트리거를 명문화했다. 양방향이 필요해질 때(채팅, 공동 집중방), 초 단위 UX가 필요해질 때(베팅 틱), 10초 미만 주기 요구가 생길 때. 그때 고를 것은 WS다.
- 쓰는 코드가 없던 `spring-boot-starter-websocket` 의존성을 걷어냈다.
- 미반영: `grace` 값 고정(리스 TTL과 같은 축에서 정한다), 아웃박스 50건 초과분 처리(버리는 대신 합산 보존 검토 중).
- 열린 문제: 방해 차단 실드를 켜고 장시간 폰을 놓아둔 사용자는 리스가 만료돼 그리드에서 사라진다. 정산은 되지만 남에게 안 보인다. 표시와 정산을 분리한 대가다.

<Callout label="전제" tone="warn">
리스 만료를 시간 몰수로 쓰지 않는다. 만료는 그리드에서 사라진다는 뜻이고, 집중 시간 정산은 away-credit 규칙과 위 클램프로 따로 처리한다. 이 분리를 없애면 "완전한 서버 권위"와 "폰을 내려놓아도 인정되는 집중"이 정면으로 충돌한다.
</Callout>
