## 맥락

6월 16일부터 21일까지 엿새 동안 그룹 생성·조회·검색·참가·공지·챌린지 API 10개(#26~#44)를 몰아 쌓았다. 하루에 다섯 개씩 병합된 날도 있다. 이때 깔린 전제는 검증되지 않은 가정이었다. 참가는 참가 코드(당시 API 명칭은 초대코드)와 그룹 비밀번호로 하고, 검색은 코드 매칭으로 하고, 그룹장이 있고, 유저는 그룹 하나에 속한다. 이 가정이 API 스펙에 그대로 굳어 있었다.

하단 탭에는 `Placeholder` 컴포넌트가 걸려 있어 유저가 그룹 탭을 누르면 아무것도 없는 화면이 나왔다. API가 있다는 것은 기능이 있다는 뜻이 아니었다.

상위 PRD는 그룹의 목적을 "함께 집중할 사람과 맥락을 얻고, 그 맥락에서 행동한 뒤 다시 돌아올 이유를 만드는 것"으로 정하고, 카드 덱은 그 생애주기 안의 하위 기능으로 둔다(prd §0).

## 선택지

7월 6일, 빈 탭 처리:

| 선택지 | 판정 | 이유 |
| --- | --- | --- |
| 쌓인 API 위에 실기능을 바로 붙인다 | 기각 | 전제가 검증되지 않았고 붙일 화면이 없다 |
| `Placeholder` 빈 화면 유지 | 기각 | 수요 신호가 없다 |
| 준비중 안내 화면 + 계측만 두는 Fakedoor | 채택 | 앱만 바꾸는 측정 전용 PR, OTA 가능 |
| 레거시 그룹 화면 코드 삭제 | 기각 | 되살릴지 새로 쓸지를 여는 시점에 정한다 |

8월 1일, 실기능 전환 순서:

- 앱을 먼저 올리고 백엔드를 맞춘다 — 기각. 탭이 열린 뒤에는 검색 방식 교체가 OTA 지연과 스토어 심사를 계산해야 하는 작업이 된다.
- 백엔드(#379) → 실기능 전환(#382) → 멀티 그룹(#383) 순으로 스택을 쌓는다 — 채택.
- 그룹 목록 화면을 항상 끼운다 — 기각. 대다수 유저에게 탭이 하나 더 생긴다. 가입 그룹 2개 이상일 때만 보여준다 — 채택.

## 결정

**7월 6일 그룹 탭을 `GroupComingSoonScreen`으로 되돌려 수요만 측정하고(#145), 26일 뒤 백엔드를 먼저 배포한 뒤 앱을 얹어 실기능으로 전환한다(#379 → #382 → #383). 참가 코드·그룹 비밀번호·코드 매칭 검색·'그룹 1개 전제'는 폐기한다.**

- Fakedoor 계측은 기존 `group_viewed`와 분리해 `group_fakedoor_viewed`(탭 진입)와 `group_notify_requested`('알림 받기')를 새로 둔다. '알림 받기'는 `AsyncStorage`의 `groupNotifyRequested` 키로 최초 1회만 발사한다. `src/screens/group/*`는 dormant로 남기고, 사용처가 사라진 `Placeholder`와 미사용 import만 정리한다.
- 백엔드(#379)는 참여 경로를 2트랙으로 가른다. 공개 그룹은 이름 검색에 노출되고 검색 후 참여, 비공개 그룹은 검색에서 제외되고 초대 링크 전용이다. `groups.is_private`(V17, `DEFAULT false`)를 넣고, 검색을 코드 매칭에서 pg_trgm 유사도 검색으로 바꾼다(임계값 기본 0.3, 비공개 제외, `LIMIT 20`). GIN trgm 인덱스는 V18로 분리한다. 참가 코드와 `group_invites`는 dead code로 표시한다.
- 앱(#382)은 `GroupScreen`·`GroupCreateScreen`·`GroupRoomScreen`·`NoticeScreen`과 시트 3종(`GroupFindSheet`·`GroupInviteSheet`·`NoticeComposeSheet`)이다. 초대 링크 생성·파싱은 `utils/inviteLink` 한 곳으로 단일화한다. 마감 기준 `password` 전송 0건, `@/legacy` import 0건.
- 멀티 그룹(#383)은 `GroupListScreen`을 가입 그룹 2개 이상일 때만 보여주고, `GroupRoom`을 라우트로 승격하며, `⋯` 메뉴에 '그룹 전환·추가'를 넣는다. 상한과 중복은 `GROUP_LIMIT_EXCEEDED`·`ACTIVE_CHALLENGE_EXISTS` 서버 에러 코드로 분기한다.

## 근거

- 계측 이름을 분리하지 않으면 실기능이 열린 뒤 Fakedoor 시절 진입 수와 실기능 조회 수가 한 지표에 섞여 "그룹 수요가 있었나"에 답할 수 없다. 1회 가드가 없으면 한 명이 다섯 번 누른 것과 다섯 명이 한 번씩 누른 것이 같은 숫자로 보인다.
- 표면만 닫아두면 되돌리는 비용은 라우트 한 줄이다. JS만 바뀌므로 OTA로 나가고, 네이티브 빌드와 스토어 심사를 기다릴 필요가 없다.
- 백엔드를 먼저 깐 이유는 탭이 닫혀 있어 API 계약을 깨는 변경을 유저 영향 0으로 낼 수 있었기 때문이다. 배포 노트에 "이 배포 시점부터 검색이 코드로는 동작하지 않음(현 앱은 Fakedoor라 실사용 영향 없음)"을 남겼다.
- 2트랙 모델에서 공개 그룹은 검색으로, 비공개 그룹은 링크로 들어오므로 코드나 비밀번호를 사람이 옮겨 적을 자리가 없다.
- `ADD COLUMN`의 짧고 강한 락과 GIN 인덱스 빌드의 길고 무거운 작업은 성질이 다르다. 한 트랜잭션에 묶으면 실패 시 어디까지 적용됐는지가 불투명해진다.
- pg_trgm은 이미 닉네임 검색에서 쓰던 방식이라 동형 구조를 그대로 맞췄다. 검색 SQL은 `TestPostgres`로 실제 DB에 붙여 테스트했다. trgm 유사도는 모킹으로 대체되지 않는다.
- primitive `boolean`에 명시적 null이 오면 조용히 기본값이 되는 대신 400을 던진다. 기본값으로 흘리면 유저가 비공개로 만들려던 그룹이 공개로 생성된다.

<Callout label="회수한 자유는 하나" tone="primary">
Fakedoor로 얻는 자유는 수요를 숫자로 확인할 자유와 백엔드 계약을 유저 영향 0으로 깨뜨릴 자유 두 개다. 계측은 설계까지 해놓고도 전환 판단에 쓰이지 않았고, 실제로 쓴 것은 두 번째뿐이다.
</Callout>

## 영향

- 새로 만드는 PR보다 전제를 바꾸는 PR이 비싸다. #382는 리뷰 8건이었고, 전제를 바꾼 #383은 코드·UI 리뷰 2종에서 HIGH 5건 포함 25건 이상이 나왔다. 6월에 검증 없이 굳은 스펙의 값을 여기서 냈다. 스택을 단계별로 squash 머지하고 base를 옮긴 덕에 한 PR에 몰리지는 않았다.
- 비공개방 실동작은 백엔드 #379 배포가 선행 조건이다. 그 전에는 `isPrivate`가 무시돼 전부 공개방이 된다.
- 초대 링크 랜딩 페이지가 없어 실기기 검증은 `gromo://` 스킴을 직접 열어서 했다. 랜딩 404는 별도 작업으로 넘겼다([초대 링크와 미설치 유저 복원](/research/invite-links)).
- `ChallengeCard`의 진행 3상에서 '—'(데이터 없음)와 0분을 구분한다. 같은 `0`으로 그리면 유저는 남이 안 했다고 읽는다.
- jest는 264개 전체 그린(신규 약 80개)으로 마감했다.
- 상위 PRD의 비목표(prd §6): 실시간 그룹 채팅·소셜 피드, 모든 그룹 자동 추천·랭킹, 새 알림 체계, 개인 카드 설정의 서버·다기기 동기화는 만들지 않는다. 챌린지 상세 정책은 챌린지 PRD로 이관한다.
