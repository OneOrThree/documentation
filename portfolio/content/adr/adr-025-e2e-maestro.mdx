## 맥락

E2E(End-to-End) 테스트는 실제 앱을 띄워 사용자처럼 화면을 누르며 처음부터 끝까지 흐름을 검증하는 테스트다. gromo 앱의 테스트는 순서대로 쌓아 왔다. GROMO-944(Expo SDK 57 업그레이드) → 945(유닛 테스트) → 946(컴포넌트 테스트). 다음 단계가 화면을 관통하는 E2E(GROMO-947)였다.

목표는 배포 전마다 사람이 손으로 도는 수동 QA 46개 시나리오의 반복 노동을 줄이는 것이었다. 같은 날(07-25) 안드로이드 출시 준비가 로드맵에 들어왔다. 그래서 한 번 쓴 대본을 iOS와 안드로이드에 같이 쓸 수 있는지가 선택 기준이 됐다.

## 선택지

GROMO-947 본문의 비교표다. WDA(WebDriverAgent)는 Appium이 iOS를 조작하려고 기기에 설치하는 보조 앱이고, 설치하려면 코드 서명이 필요하다. flaky 테스트는 코드가 그대로인데 통과와 실패가 오락가락하는 테스트다.

| 기준 | Maestro | Appium |
| --- | --- | --- |
| 셋업 | 분 단위(단일 바이너리) | 몇 시간~반나절(서버 + 드라이버 + WDA 서명) |
| 대본 | YAML 선언형, 자동 대기 내장 | 코드 작성, 대기를 수동으로 관리(flaky의 주원인) |
| iOS 실기기 | 사실상 불가 | 가능(유일한 강점) |
| Android | 에뮬레이터·실기기 지원 | 지원 |
| 유지 비용 | 낮음 | 높음(방치하면 도구 자체가 깨짐) |

| 선택지 | 판정 | 이유 |
| --- | --- | --- |
| Maestro | 채택 | 소규모 팀에 맞는 유지비. 같은 YAML 플로를 iOS 시뮬레이터와 안드로이드(에뮬레이터·실기기)에 재사용하고, React Native 단일 코드베이스라 testID도 양 플랫폼이 공유한다 |
| Appium | 조건부 보류 | 강점(iOS 실기기, 클라우드 기기팜, 범용성)이 전부 규모의 장점이라 지금은 쓸 곳이 없다 |
| 평소 Maestro + 릴리즈 때 Appium | 기각 | 유지비가 두 배인데 실익이 없다. 릴리즈 직전 층은 도구를 늘리지 않고 실기기 수동 QA로 한다 |
| Detox | 기각 사유 기록 없음 | 07-25 결정기록에 후보로 이름만 있고, GROMO-947 비교표와 선정 이유 어디에도 등장하지 않는다 |
| 스크린타임을 실기기 자동화로 검증 | 불가 | 아래 |

스크린타임을 뺀 이유는 도구의 한계가 아니라 Apple의 설계다. 시뮬레이터에서는 Screen Time API가 아예 동작하지 않는다. 실기기 자동화(Appium·XCUITest)로 가도 다음 넷에 막힌다.

1. **권한 팝업** — gromo가 아니라 시스템 프로세스가 띄운다. iOS 버전마다 구조가 바뀌어 자동화가 자주 깨진다.
2. **측정 대상 picker** — 프라이버시 보호 때문에 별도 시스템 프로세스가 그린다. 앱도 테스트 도구도 안쪽 요소를 읽을 수 없어 "특정 앱 선택"을 믿을 수 있게 자동화하지 못한다.
3. **리포트 숫자** — 홈의 사용 시간 표시는 격리된 익스텐션이 그리는 불투명 뷰다. "N분이 표시된다"를 단언(assert)할 수 없다.
4. **데이터 주입 불가(결정적)** — 사용 시간을 가짜로 심을 방법이 없다. "어제 3시간 사용" 상태를 만들려면 실제로 써야 하고, 목표 초과 판정도 실시간으로만 발화한다. "알려진 입력 → 기대 출력"이라는 검증의 전제가 성립하지 않는다.

그래서 실기기 자동화로 확인할 수 있는 것은 "버튼이 눌린다"까지다. 측정값·실드 차단·목표 판정 같은 기능 정합은 검증하지 못한다.

## 결정

**앱 E2E 도구는 Maestro다. 대본은 testID로만 요소를 찾고 화면 문구로 찾지 않는다. 스크린타임 전 영역·Apple 로그인·위젯/Live Activity·햅틱은 실기기 수동 QA로 남긴다. Appium은 ① 실기기에서만 재현되는 버그가 반복해서 회귀하거나 ② 안드로이드 출시 뒤 제조사별 기기 파편화에 대응해야 할 때 다시 검토한다.**

## 근거

도입 PR #352의 결과다.

- 티켓 원안은 P0 흐름 5개였고, 실제로 옮긴 것은 3개다: 01 온보딩 + 게스트 로그인, 02 집중 시작 → 정지 → 결과 → 홈, 03 통계 일/주/월 탭 전환. 상점 구매 → 장비 착용은 당시 라이브 코드에 상점 화면이 없어 뺐다.
- 01은 원안("스크린타임 스텝 전까지")보다 넓어졌다. iOS 26 시뮬레이터는 권한 시스템 알럿을 실제로 띄웠고, '허용 안 함'을 눌러 거부 경로로 닉네임까지 결정적으로 완주할 수 있었다. 수동 QA 문서의 "시뮬레이터에서는 권한 API가 안 돈다"는 전제는 구버전 기준이었다.
- 플로를 01 → 02 → 03으로 이었다. 01이 게스트 계정을 만들고, 02가 집중 기록을 만들고, 03이 그 기록을 조회한다. dev 서버 테스트 계정과 시드 데이터를 따로 맞출 필요가 없어졌다. 실행이 끝나면 성공·실패와 무관하게 그 실행이 만든 게스트 계정을 탈퇴 API로 지운다.
- testID 33개를 `영역.요소` 표기로 붙였다(`login.guest`, `focus.stop`, `stats.tab.week`). 문구 매칭 예외는 시스템 권한 알럿 2곳뿐이다. 문구를 고쳐도 대본이 깨지지 않는다.
- 비결정성 두 가지를 없앴다. E2E 빌드 플래그로 OTA 게이트를 건너뛰어, 실행 중 예전 번들이 내려와 testID 없는 구 JS로 바뀌는 오염을 막았다. 푸시 권한 요청도 건너뛰어, 시스템 알럿이 아무 때나 떠서 플로가 깨지는 문제를 없앴다.
- `scripts/e2e.sh` 한 번으로 Release 시뮬레이터 빌드 → 번들의 API 주소 검증 → 삭제 후 설치 → 전체 플로 → junit 리포트까지 돈다. 빌드를 포함한 한 번 실행이 2회 연속 3/3 통과했고 1분 28초가 걸렸다. 기존 jest 99케이스·lint·tsc에는 영향이 없었다.

## 영향

- E2E는 로컬에서 배포 전에 돌리는 관문이고 CI에는 연결하지 않았다(시뮬레이터가 필요하다). 스크린타임은 CI에도 E2E에도 보호가 없고, 실기기가 유일한 관문이다. [스크린타임 연구 노트](/research/screentime)의 "시뮬레이터에서 안 돈다"와 같은 축이다.
- 게스트에게는 앱 UI에 탈퇴 경로가 없어서, 정리는 API를 직접 호출해 한다. 이 점은 제품·심사 관점의 별도 논의거리로 기록만 했다.
- 1.x 앱의 `.maestro/` 플로 3종은 `app/legacy/`로 옮겨진 채 남아 있다. 2.0 앱에는 아직 E2E가 없다.
