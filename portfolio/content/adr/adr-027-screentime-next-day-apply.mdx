## 맥락

iOS는 스크린타임 사용 시간을 앱이 직접 읽게 해 주지 않는다. gromo는 이것을 두 개의 익스텐션으로 우회한다. 익스텐션은 앱과 따로 iOS가 실행하는 작은 프로그램이다. 전체 구조는 [스크린타임 연구 노트](/research/screentime)에 있고, 이 결정에 필요한 것은 둘의 비대칭이다.

| | 리포트 익스텐션 | 모니터 익스텐션 |
| --- | --- | --- |
| 하는 일 | 홈 화면의 사용 시간을 그린다 | 사용량이 눈금(threshold)에 닿거나 하루 구간이 바뀔 때 iOS가 깨운다. 앱이 꺼져 있어도 돈다 |
| 과거 소급 계산 | 하루 전체를 현재 측정 대상 기준으로 다시 계산 | 등록한 시점부터 앞으로만 센다 |
| 결과 내보내기 | 막혀 있다(App Group 쓰기가 실측 항상 0) | 가능 |

서버로 가는 값은 모니터 익스텐션이 15분 간격 눈금 60개로 기록하는 "버킷" 사용시간이다.

**문제 1 — 측정 대상을 바꾼 날이 섞였다.** 측정 대상(앱·카테고리)을 하루 중간에 바꾸면 모니터를 새 대상으로 다시 등록해야 한다. 그러면 그날 서버 값이 "옛 기준 오전 + 새 기준 이후"로 섞이고 목표 판정도 흔들렸다. 하루 전체를 새 기준으로 다시 보내려 해도 그 값은 출력이 막힌 리포트 익스텐션 안에만 있다. 그러니 하루가 하나의 기준이려면 계산을 바꿀 수는 없고, **바꾸는 시점을 자정으로 옮기는 수밖에 없다.**

**문제 2 — 목표 판정용 모니터가 따로 있었다.** 목표 달성은 별도 모니터(`gromo.daily`)가 판정했다. 측정 대상을 바꿀 때 이 모니터의 재등록 타이밍에 틈이 생긴다는 코드리뷰 지적이 있었고, 한낮에 자정 콜백이 불려 판정이 오염되는 백로그도 있었다.

**전제(07-17)** — 목표 판정과 서버 기록에 쓰는 threshold 이벤트는 picker로 받은 토큰이 있어야 발화한다. 토큰이 비어 있으면 절대 발화하지 않는다. 그래서 "온보딩에서 picker를 빼자"는 제안은 기각됐고, 측정 대상 변경은 곧 모니터 재등록을 뜻한다.

## 선택지

측정 대상 변경. pending은 "적용 대기 중인 값"이다.

| 안 | 방법 | 결과 | 리스크 | 판정 |
| --- | --- | --- | --- | --- |
| A. 자정 네이티브 승격 | picker 결과를 pending에만 저장하고 적용일을 기록 → 모니터 익스텐션의 자정 콜백(`intervalDidStart`)이 앱 없이 승격하고 모니터를 재등록 | 0시에 전환, 섞이는 날이 없다 | 익스텐션 안에서 `startMonitoring` 재등록이 되는지 전례가 없다 | 채택(스파이크 통과 조건) |
| B. 앱 실행 시 승격 | 다음날 이후 첫 앱 실행 때 승격 | 변경 당일은 보호되지만 승격일 하루가 섞인다. 문제가 하루 밀릴 뿐이다 | 낮음(기존 패턴 재사용) | 기각(A 실패 시 폴백) |
| C. 즉시 적용(현행) | — | 변경 당일이 섞인다 | 없음 | 기각 |
| 새 기준으로 하루 전체를 서버에 재전송 | — | — | 리포트 익스텐션 출력이 막혀 있다 | 불가 |

목표 판정.

| 안 | 판정 | 이유 |
| --- | --- | --- |
| 목표 모니터 유지 + 적용일에 강제 재등록 | 기각 | 재등록 틈이 남고, 판정만 "다음날 첫 앱 실행" 시점에 바뀌어 그날 판정이 조금 섞인다 |
| 앱이 "버킷 사용시간 ≤ 그날 유효했던 목표"로 판정 | 채택 | 별도 모니터가 필요 없다. 버킷 모니터가 새 대상으로 살아 있으면 판정도 자연히 새 대상 기준이 된다 |

판단 기준이 결론을 갈랐다. "바꿔도 **오늘** 목표·기록이 안 흔들리면 된다"면 B로 충분했다. 안수빈의 기준은 "서버 일별 데이터가 **항상** 단일 기준이어야 한다"였고, 이걸 만족하는 안은 A뿐이다. 07-27에 "스파이크가 통과하면 무조건 A, 실패할 때만 B"로 정했다.

## 결정

**측정 대상 변경은 pending에 저장하고, 모니터 익스텐션이 자정에 앱 없이 승격·재등록한다. 목표 달성은 앱이 어제분을 마감할 때 "버킷 사용시간 ≤ 그날 유효했던 목표"로 판정해 서버에 보고하고, `gromo.daily` 목표 모니터는 폐지한다.**

| 경로 | 동작 |
| --- | --- |
| 설정에서 이미 측정 중인 대상을 바꿈(주 경로) | pending 저장 + 적용일 = 내일. 당일은 옛 기준으로 계속 측정 |
| 자정 — 익스텐션 `promotePendingSelectionIfDue` | 적용일이 됐으면 승격하고 버킷 모니터만 새 대상으로 재등록. 성공하면 `selectionPromotedOkDate`를 기록 |
| 앱 포그라운드 | 자정을 놓쳤을 때의 백업 승격만. 자정 승격 성공이 기록돼 있으면 재등록하지 않는다. 재등록은 iOS 누적을 0부터 다시 세게 해 자정 이후 자투리(최대 14분)를 잃게 하기 때문이다 |
| 최초 설정·대상 비우기·온보딩 | 즉시 적용. 기존 측정이 없거나 끝나는 경우라 섞일 것이 없다 |
| OTA로 새 JS만 받은 구 바이너리 | 자정 승격 코드가 바이너리에 없으므로 즉시 적용으로 폴백 |
| 기존 설치에 남은 `gromo.daily` | `stopGoalMonitoring`으로 1회 정리 |

## 근거

A안의 유일한 리스크는 "익스텐션이 자기 콜백 안에서 모니터를 재등록할 수 있는가"였다. GROMO-942 스파이크로 실기기에서 세 조건을 확인했다.

| 실험 | 조건 | 결과 |
| --- | --- | --- |
| A | 한낮에 유발한 콜백 안에서 별도 활동 등록 | 등록 성공, 1·2·3분 눈금이 실제로 발화 (07-27) |
| B | 콜백 안에서 버킷 모니터 **자기 자신**을 재등록 | 재등록 뒤에도 15분 눈금 정상 발화 (07-27) |
| 자정 실측 | 폰이 잠긴 **진짜 자정 00:00:02** | 익스텐션이 스스로 깨어나 콜백 안 등록 성공, 아침 사용 때 눈금 발화 (07-31) |

세 조건을 모두 통과해 07-31 A안을 확정했고, 같은 날 구현(PR #356)을 머지했다.

구현 도중 한 발 더 나갔다. 처음 구현안은 적용일 첫 포그라운드에서 목표 모니터를 강제 재등록했고, 그러면 그날 판정이 조금 섞인다. 그런데 서버는 이미 앱이 보낸 달성 여부(achieved)를 믿고 있었고, 앱은 버킷 사용시간을 이미 갖고 있었다. 그러니 목표 모니터 없이 버킷과 목표를 비교하면 된다. 이렇게 바꾸자 재등록 타이밍 틈과 한낮 콜백 오염 백로그가 통째로 사라졌다. 서버 API와 스키마는 그대로라 백엔드 변경이 0이다.

## 영향

- 버킷이 15분 단위라 경계에서 최대 약 15분 후하게 판정된다. 대신 서버에 올라가 통계 화면에 그려지는 버킷 숫자와 판정이 일치한다. 15분 해상도 자체의 한계는 [15분 양자화 반례](/research/screentime-quantization)에 있다.
- 버킷 0분은 "측정이 켜져 있고 15분 미만 사용 = 달성"으로 본다. "데이터 없음"과는 측정 등록 여부로 구분한다.
- 서버는 앱이 보낸 판정을 믿는다. 스크린타임 PRD의 원칙 P2(서버는 과거 시점의 목표를 모르므로 앱의 판정을 쓴다)와 P5(측정값 위조 리스크는 수용한 정책)를 따른다.
- 목표 **시간** 변경은 여전히 "날짜가 바뀐 뒤 첫 앱 실행" 때 적용된다. 자정 네이티브 승격은 측정 **대상**에만 해당한다. [스크린타임 연구 노트](/research/screentime) §1.6의 "다음날 적용은 날짜가 바뀐 뒤 앱을 처음 여는 순간"이라는 서술은 목표 시간 기준으로 읽어야 한다.
- 계속 필요한 가드: 익스텐션 메모리 제한(눈금 이벤트 수와 RAM 6MB의 교환), iOS가 자정 콜백을 가끔 빼먹는 경우(새 날 첫 이벤트에서의 자가 리셋, 앱의 백업 승격).
