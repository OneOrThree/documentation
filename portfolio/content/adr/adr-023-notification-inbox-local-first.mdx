## 맥락

GROMO-661은 홈 오른쪽 위 종 아이콘과 알림 화면을 만드는 티켓이었다. 출시 범위에 들어 있었고, 안 읽은 알림이 있으면 종에 빨간 점을 띄워야 했다.

그런데 서버에는 "이 유저에게 무엇을 보냈는지"가 없었다. 백엔드는 푸시 4종(리그 승급·강등, 리그 마감, 순위 추월, 미접속 복귀)을 보내기만 했다. 유저별 발송 이력 테이블도, 그것을 조회하는 API도 없었다. 남아 있는 기록은 순위 추월 알림이 중복 발송되지 않게 막는 로그뿐이었다.

앱이 받은 푸시를 직접 적어 두는 방법에는 iOS의 구멍이 있다. 앱이 백그라운드에 있거나 꺼진 상태에서 도착만 한 푸시는 OS가 알림 센터에 띄울 뿐, 앱 코드를 실행하지 않는다. 앱이 푸시를 기록할 수 있는 순간은 앱이 켜져 있을 때 도착했거나, 사용자가 알림을 눌러 앱이 열렸을 때뿐이다. 누르지 않고 지운 알림은 앱이 존재조차 모른다.

## 선택지

AsyncStorage는 React Native 앱이 기기 안에 키-값을 저장하는 로컬 저장소다. 앱을 지우면 함께 지워진다.

| 선택지 | 얻는 것 | 대가 | 판정 |
| --- | --- | --- | --- |
| 서버 발송 이력 API를 먼저 만들고 화면은 그 뒤 | 빠짐없는 이력, 기기 간 동기화 | 알림 화면·빨간 점 출시가 백엔드 일정에 묶인다 | 기각 |
| 받은 푸시를 AsyncStorage에 저장하고, 원천을 바꿀 지점을 모듈 하나로 모은다 | 화면·뱃지를 앱 단독으로 지금 완성 | 누르지 않은 백그라운드 푸시 누락, 기기에 귀속 | 채택 |
| iOS 알림 서비스 익스텐션으로 도착 시점에 기록 | 백그라운드 도착분 누락을 줄일 여지 | 네이티브 타깃 추가 | 미검토 — 07-13 기록에 검토 흔적 없음 |

## 결정

**알림 보관함은 기기에 저장한 푸시로 먼저 완성하고, 서버 이력 API가 생기면 보관함 모듈의 데이터 원천만 바꾼다. 무엇을 저장할지의 정책은 상수 하나에 모은다.**

| 항목 | 값 |
| --- | --- |
| 모듈 | `services/notificationInbox.ts` 하나. 알림 화면과 홈 뱃지는 이 모듈만 본다 |
| 저장 키 | `gromo:notifications` |
| 상한 | 50건. 넘치면 오래된 것부터 버린다 |
| 중복 방지 | FCM `messageId`를 id로 쓴다. 같은 id는 다시 저장하지 않는다 |
| 저장 경로 3개 | 앱이 켜져 있을 때 수신 · 백그라운드에서 알림 탭 · 꺼진 앱을 알림 탭으로 실행(콜드 스타트) |
| 읽음 처리 | 알림 화면에 들어가면 전부 읽음 |
| 저장 정책 | `STORED_TYPES` 상수. 지금은 `'all'`이고, 타입 목록으로 바꾸면 그 타입만 저장한다 |

FCM(Firebase Cloud Messaging)은 푸시를 기기로 전달하는 서비스이고, `messageId`는 메시지마다 붙는 고유 번호다.

## 근거

- 화면과 뱃지를 서버 없이 완성할 수 있었다. 서버 이력이 생겨도 바뀌는 곳은 모듈 안쪽뿐이다. 홈 뱃지는 변경 구독(`subscribeInbox`)과 목록 조회만 쓰므로 원천이 바뀌어도 그대로다.
- 어떤 알림을 보관할지는 07-13에 정해지지 않았다. 결정을 기다리는 대신 정책을 상수 하나로 몰아 두고, 판정은 `shouldStore` 한 곳에서만 하게 했다. 나중에 정책이 정해지면 한 줄만 바뀐다.
- 로컬 저장의 경쟁 조건 두 개가 리뷰에서 잡혔고, 둘 다 모듈 안에서 닫혔다.
  - PR #224 리뷰: 푸시 2건이 거의 동시에 오면 둘 다 같은 목록을 읽고, 나중에 쓴 쪽이 먼저 쓴 알림을 덮어써 하나가 사라진다. → 읽기·고치기·쓰기를 한 번에 하나씩 실행하는 쓰기 큐를 두었다. 로그아웃 때 보관함을 비우는 작업도 같은 큐를 타서, 비운 직후 이전 계정의 알림이 되살아나지 않는다.
  - PR #226 리뷰: 몇 시간 전에 발송된 알림을 뒤늦게 눌러 저장하면, 맨 앞에 끼워 넣는 방식으로는 더 새 알림 위로 올라간다. → 저장할 때마다 발송 시각 기준 내림차순으로 다시 정렬한다.

## 영향

- 한계(수용): iOS에서 누르지 않은 백그라운드 푸시는 보관함에 없다. 저장소가 기기라서 재설치·기기 변경 때 보관함이 비고, 로그아웃·계정 전환 때도 비운다.
- 원천 교체는 일어나지 않았다. 09-19 기준 data-api에는 사용자용 알림 이력 조회 API가 없고, 알림 관련 엔드포인트는 배치 발송·테스트·내부 호출용뿐이다. 1.x 앱에서 보관함의 원천은 끝까지 로컬 하나다.
- 2.0 앱에는 이 보관함 모듈이 옮겨지지 않았다.
- 서버가 알림을 어떻게 보내고 중복을 어떻게 막는지는 [ADR-008](/adr/adr-008-notification-claim-first)과 [알림 파이프라인 재편](/research/notification-pipeline)에 있다. 이 ADR은 받는 쪽의 기록만 다룬다.
