## 맥락

07-20, 1.0.0 첫 심사 제출을 앞두고 팀이 두 가지를 전제로 확정했다. 앱 코드는 여러 명이 작업한다. 그리고 이미 나간 버전의 핫픽스(긴급 수정)와 다음 버전 개발을 동시에 한다.

그러려면 "스토어에 나가 있는 바이너리가 정확히 어느 코드인가"를 가리킬 수 있어야 한다. 핫픽스와 OTA는 그 코드 위에서만 만들어야 한다. 다음 버전용 네이티브 변경이 이미 들어간 `main`에서 OTA를 내면, 새 JS가 구 바이너리에 없는 네이티브 모듈을 불러 앱이 죽는다([ADR-023](/adr/adr-023-ota-hot-updater)). 그때까지의 방식인 `main` 하나와 태그 없음으로는 이 구분이 불가능했다.

배포도 한 종류가 아니었다.

| 단계 | 무엇 | 빈도 |
| --- | --- | --- |
| ① TestFlight 업로드 | 내부 테스터용 빌드 (TestFlight = 애플의 베타 배포 채널) | 잦음, 월 20회 이상 |
| ② 심사 제출 | 고른 빌드를 버전에 붙여 애플 심사에 제출 | 가끔 |
| ③ 출시 | 심사 통과 후 스토어 공개 | 드묾 |

## 선택지

| 선택지 | 판정 | 이유 |
| --- | --- | --- |
| `main` 단일 + 태그 없음 (기존) | 기각 | 배포된 바이너리의 코드 계열을 가리킬 수 없다 |
| 유지보수 브랜치 `release/app-1.0` | 기각 | 백엔드의 단독 `release` 브랜치와 git ref가 충돌한다. push가 "directory file conflict"로 거절됐다(07-20 실측) |
| 유지보수 브랜치 `arelease/1.0` | 채택 | 충돌이 없고, 앱 브랜치 접두 컨벤션(`afeat/`·`afix/`)과 맞는다 |
| TestFlight 업로드마다 태그 | 기각 | 월 20회가 넘는 테스트 빌드 태그에 릴리즈 태그의 의미가 묻힌다 |
| 핫픽스를 `main`으로 체리픽 | 기각 | 반영했는지를 PR 목록으로 추적할 수 없다 |
| GitHub 브랜치 룰셋으로 규칙을 강제 | 불가 | 조직이 무료 플랜 + 비공개 저장소라 기능이 잠겨 있다. GitHub Team 플랜이 필요하다 |

ref 충돌은 git이 브랜치를 저장하는 방식에서 나온다. git은 브랜치 이름을 파일 경로처럼 저장한다. `release`라는 브랜치가 이미 "파일"로 있으면, `release/app-1.0`을 담을 같은 이름의 "폴더"를 만들 수 없다.

## 결정

**`main`은 다음 버전 개발, `arelease/<major.minor>`는 그 버전의 유지보수 라인이다. 핫픽스 PR의 base, OTA 배포, 심사 빌드는 전부 `arelease`에서 하고, 핫픽스 뒤에는 `main`으로 머지백 PR을 반드시 올린다. 태그는 심사 제출 빌드에만 단다.**

| 규칙 | 내용 |
| --- | --- |
| 브랜치 | `main` = 신기능 PR의 base. `arelease/1.0` = 1.0.x 유지보수, 그 버전 지원이 끝날 때까지 유지 |
| 핫픽스 | `arelease/1.0`에서 `afix/…` 브랜치를 따고 PR base도 `arelease/1.0`. JS만 바뀌면 OTA, 네이티브가 섞이면 재빌드·재제출·새 태그 |
| 머지백 | 핫픽스가 들어갈 때마다(최소 주 1회) `arelease/1.0` → `main` PR. 방향만 반대인 평범한 PR이다. 빼먹으면 다음 버전에서 고친 버그가 되살아난다. 충돌은 핫픽스 작성자가 푼다 |
| 태그 | `app-<마케팅버전>-<빌드번호>`, 설명을 담은 어노테이티드 태그. 심사 제출 빌드에만 달고, push한 태그는 옮기지 않는다 |
| 빌드번호 | 1.0.0은 유닉스 타임스탬프를 유지한다(같은 버전 안에서는 빌드번호를 줄일 수 없는 애플 규칙). 다음 마케팅 버전부터 버전별 순차(1, 2, 3…) |

심사 제출은 fastlane `release` 레인이 한다(GROMO-911, PR #330). fastlane은 iOS 빌드·업로드를 자동화하는 도구이고, 레인은 그 안의 작업 묶음이다.

1. 시작 가드: 커밋하지 않은 변경이 있으면 거부한다(태그가 실제로 빌드한 코드를 가리키게). 현재 브랜치가 `arelease/*`가 아니면 실패한다.
2. 빌드하고 TestFlight에 올린다.
3. 성공하면 빌드번호를 커밋하고, 버전·빌드번호·직전 태그 이후 커밋 요약을 담은 태그를 만들어 브랜치와 함께 push한다.

## 근거

- 백엔드 `release`는 [ADR-021](/adr/adr-021-release-fast-forward)에서 `main`과 같은 SHA로 fast-forward 승격되는 단독 브랜치다. 앱 브랜치 이름은 그 결정의 부수 제약을 받았다. 이 ADR은 ADR-021을 바꾸지 않고, 그 옆에 앱 유지보수 라인을 따로 둔다.
- 규칙이 지켜지는 수준을 세 단계로 나눠 봤다. 1단계는 사람이 문서를 기억하는 것, 2단계는 기계가 규칙을 수행하는 것, 3단계는 플랫폼이 위반을 거부하는 것이다. `release` 레인이 2단계이고, 3단계(브랜치 룰셋)는 플랜 제약으로 열지 못했다.
- 07-20 적용: `main`의 `3bf3aaf`에서 `arelease/1.0`을 따고, 재빌드한 1784550135를 올린 뒤 빌드번호 커밋과 첫 태그 `app-1.0.0-1784550135`를 push했다. 원격에는 `arelease/1.0`·`arelease/1.1`이, 태그는 `app-1.0.0-1784550135`·`app-1.1.0-1`·`app-1.1.0-7`이 남아 있다. 1.1.0 태그의 작은 빌드번호가 버전별 순차 정책이 실제로 적용된 모습이다.

## 영향

- 검증 공백: 당시 앱 lint CI는 `main` 대상 PR만 검사했다. `arelease/*`로 가는 핫픽스 PR은 lint·typecheck 없이 머지될 수 있었고, 이 공백은 티켓 대상으로만 기록됐다.
- 09-08 멘토링 지적: `main`에 머지할 때 iOS·Android·OTA 변경이 섞여 들어가 체리픽이 안 된다. 커밋에 `[ios]`·`[android]`·`[ota]` 마크를 붙이라는 제안이었다([멘토링 기록](/history/07-mentoring)).
- 1.x 앱은 09-16 `app/legacy/`로 옮겨 동결됐다. 이 경로에는 CI가 없어서 1.x 핫픽스는 로컬에서 lint·typecheck·테스트를 직접 돌려 검증한다.
- 2.0 앱에 이 브랜치 규칙을 적용할지는 정해지지 않았다.
