## 맥락

그룹 참여는 6월에 참가 코드(당시 초대코드)와 그룹 비밀번호로 설계됐다. 8월 1일 공개/비공개 2트랙(#379)으로 바뀌면서 공개 그룹은 검색, 비공개 그룹은 초대 링크 전용이 됐고, 코드나 비번을 사람이 옮겨 적을 자리가 없어져 두 개념은 폐기됐다.

그런데 앱이 공유하던 초대 링크는 `oneorthree.github.io/phone/join.html`이라는 만들어진 적 없는 페이지를 가리켜 누르면 404였다. 발급·랜딩·deferred 매치·claim·AASA 다섯 구간이 비어 있었다. 앱이 깔려 있으면 Universal Links가 슬러그를 넘겨주지만, 앱이 없으면 스토어를 다녀오는 사이에 어떤 초대였는지가 사라진다. 서버가 붙일 수 있는 단서는 클릭 시점의 흔적뿐이다.

## 선택지

| 갈래 | 선택지 | 결과 |
| --- | --- | --- |
| 참여 경로 | 참가 코드·비밀번호 입력 | 기각 — 2트랙 모델에 자리가 없음 |
| 미설치 복원 | 복원 없음 (설치 후 재검색) | 기각 |
| 미설치 복원 | 클릭 지문(IP해시·OS·시간창) 확률적 매칭 | 채택 |
| 매치 후 동작 | 자동 가입 | 기각 — 100%가 아닌 신호로 계정 상태를 바꾸지 않음 |
| 매치 후 동작 | 초대 시트에서 그룹명 확인 후 참여 | 채택 |
| 소진 락 | 락 없음 / `PESSIMISTIC_WRITE`만 | 기각 (아래 근거) |
| 소진 락 | `PESSIMISTIC_WRITE` + `SKIP LOCKED` | 채택 |

## 결정

**클릭을 지문으로 남기고, 설치 후 첫 실행의 `POST /l/match`가 같은 지문의 미소진 클릭을 최신순으로 하나 골라 원자적으로 소진한다. claim은 최초 1회 + 셀프 초대 제외이며 같은 락 조합을 쓴다.**

```text
invite_link_clicks
  link_id, ip_hash, os, user_agent, clicked_at,
  matched / matched_at / matched_device_id / app_instance_id,
  claimed_user_id / claimed_at

  idx_invite_clicks_match  (ip_hash, os, clicked_at DESC) WHERE matched = FALSE
  idx_invite_clicks_device (matched_device_id, matched_at DESC) WHERE matched = TRUE
```

```sql
-- 실제 생성된 SQL (Hibernate)
... order by clicked_at desc
    fetch first ? rows only
    for no key update of ilc1_0 skip locked
```

원본 IP는 어떤 컬럼·로그·이벤트 파라미터에도 남기지 않고 `SHA-256(ip + LINK_IP_SALT)`의 hex만 저장한다. prod는 salt를 Secrets Manager에서 필수 주입받고, 미설정이면 기동을 실패한다.

엔드포인트 계약은 코드보다 먼저 표로 동결했다. `POST /api/v1/groups/{groupId}/invite-link`는 (그룹, 초대자)당 1링크 멱등 재사용, `GET /l/{slug}`는 만료·미존재·그룹 삭제도 항상 200 HTML(302 금지), `POST /l/match`는 매칭 실패도 200, `POST /api/v1/invite-links/claim`은 멱등 no-op이다.

## 근거

- 락이 없으면 동시 요청 둘이 한 클릭을 같이 소진해 한 클릭이 두 기기에 매치된다. `PESSIMISTIC_WRITE`가 이를 막는다.
- `SKIP LOCKED`는 별개의 이유다. PostgreSQL은 `FOR UPDATE`와 `LIMIT`을 함께 쓸 때 잠금이 풀린 뒤 조건에서 탈락한 행을 만나면 다음 후보를 다시 찾지 않고 빈 결과를 돌려준다. 공유 Wi-Fi처럼 같은 지문의 후보가 여러 개 쌓인 상황이 정확히 그 조건이라, 없으면 후보가 많을수록 복원이 더 안 된다.
- 지문이 IP 해시와 OS와 시간창이므로 같은 카페의 다른 사람이 겹칠 수 있다. 정확도가 100%가 아닌 신호로는 계정 상태를 바꾸지 않기로 했다.
- IPv4 주소 공간은 40억 개 남짓이라 salt 없는 해시는 전수 계산으로 되돌릴 수 있다.
- 검증은 통합 31건 + 단위 18건 = 신규 49건이다. 코어 PR(#412)의 핵심 주장 둘은 동시 매치 2건 중 정확히 1건만 성공, 동시 claim 중 정확히 1명만 기록이다.

<Callout label="CI는 이 SQL을 실행하지 않는다" tone="warn">
`ci` 프로파일은 `flyway.enabled: false` + `ddl-auto: create-drop`이라 스키마를 엔티티에서 만든다. 그래서 `postgres:16-alpine` 컨테이너에 V1부터 순서대로 직접 적용하고 `\d`로 부분 인덱스·유니크·FK를 대조했다. dev 기동이 이 SQL의 첫 실전 검증이다. 병렬 워크스트림과 번호가 겹쳐 V20에서 V21로 개번했다.
</Callout>

## 영향

- 매치는 재시도에 멱등하다. 응답이 유실돼 앱이 재시도해도 같은 기기의 창 내 기존 매치를 재반환하고 클릭을 추가로 소진하지 않는다.
- 봇은 클릭으로 세지 않는다. 스크레이퍼 IP의 미소진 클릭이 매치 후보가 되면 엉뚱한 설치에 붙는다. 반대로 카톡 인앱브라우저는 주 유입 경로라 봇으로 걸러선 안 되며, 이 구분을 UA 분류에 넣었다.
- 종료된 그룹(`status=ENDED`)은 만료로 취급하고, 발급·랜딩·매치 세 곳이 `deletedAt`과 `ENDED`를 같은 기준으로 본다.
- 무인증 경로 `/l/*`·`/.well-known/*`는 `JwtFilter`·`TraceIdFilter`가 `addUrlPatterns("/api/*")`로만 등록돼 있어 화이트리스트 없이 필터 밖이다.
- 남은 항목: 프록시 신뢰 헤더 전제(비우면 `remoteAddr`만 사용), claim이 슬러그만 받아 여러 기기 매치 시 기기 필드와 유저 결합이 어긋날 수 있는 문제, `/l/{slug}`·`/l/match` 스로틀(엣지 전제), 안드로이드 `intent://` 대응.
