## 맥락

2026-07-23 동시성 위험 API 전수 감사에서 가장 자신 있던 그룹 정원(`POST /groups/{id}/join`)은 `Group` 엔티티의 `@Version`과 `OptimisticLockException` → `ROOM_FULL` 매핑이 다 있는데, 그 예외를 던지는 지점이 없었다. `joinGroup`이 멤버 수를 `count`로 세어 통과시킨 뒤 멤버 행을 INSERT할 뿐 `Group` 행을 UPDATE하지 않아, 낙관적 락이 충돌을 감지할 방아쇠 자체가 없었다. `group_members(user_id, group_id)` 유니크는 같은 유저의 중복 가입만 막고, 서로 다른 두 사람이 마지막 1자리를 동시에 차지하는 것은 통과시킨다.

반대로 기대하지 않던 4곳은 서로 다른 기법으로 이미 막고 있었다. 방어선 문서가 가리키던 그룹 참가 동시성 전략 파일은 이미 사라진 상태였다.

## 선택지

| 선택지 | 문제 | 결과 |
| --- | --- | --- |
| 부품 존재로 검증 — `@Version`·예외 매핑을 센다 | 예외가 실제로 던져지는지 알 수 없다 | 기각 |
| 패턴만 보고 일괄 처방 — check-then-act 전부에 락 | 덮어쓰기 의미론에는 불필요한 대기, 누적에는 필요한 락을 빠뜨림 | 기각 |
| Mockito 단위 테스트로 동시성 검증 | 서비스를 두 번 호출해도 순차 실행이라 레이스가 안 난다 | 기각 |
| 실패 모드 분류 → API별 기법 명시 + 실제 DB·스레드 재현 테스트 | 비용이 크다 | 채택 (돈 경로 기본, 예외 조건부) |

## 결정

**실패 모드를 먼저 분류하고 API마다 기법을 명시한다. 낙관적 락은 발동 경로(쓰기 지점)까지 확인하고, 동시성 수정은 재현 테스트와 같은 PR에 둔다.**

| 실패 모드 | 대표 사례 | 처방 |
| --- | --- | --- |
| 가드 우회 | 소셜 연동 해제(GROMO-527), 그룹 정원 | 잠금 또는 원자적 쓰기로 check와 act 직렬화 |
| lost update | 일별 집중 집계 `+=`(GROMO-568) | 비관적 락 또는 원자적 UPDATE |
| 중복 삽입 | 소셜 첫 로그인(GROMO-581), 스크린타임 저장(GROMO-560) | 유니크 제약 + 재시도 |

층위는 이렇게 갈린다. INSERT 레이스는 유니크 제약이 막고, 이미 있는 행의 레이스는 락이나 조건절을 품은 원자적 UPDATE가 막는다. 아직 없는 행은 잠글 대상이 없어 비관적 락이 통하지 않는다.

테스트 표준은 Testcontainers 실제 DB + `newFixedThreadPool` + `startGate`/`doneGate` 두 래치다. 트랜잭션 없는 통합 테스트 베이스를 상속하고, 예외 타입이 아니라 결과 상태(성공 1건·실패 1건·재조회 잔액 일치)로 단정하며, `doneGate.await`에는 타임아웃을 주고 반환값을 단정한다.

<Callout label="수정 전 실패를 먼저 본다" tone="warn">
돈 경로 P0 결함(#544)에서는 `CyclicBarrier`로 취소×탈퇴를 강제 인터리빙하는 테스트를 쓰고, 옛 동작을 임시로 복원해 3회 중 3회 실패(`expected: 1L but was: 2L`)를 확인한 뒤 되돌렸다. 이 순서를 밟지 않으면 테스트가 그린인 이유가 "고쳤기 때문"인지 "그 경로를 안 타기 때문"인지 구별할 수 없다.
</Callout>

## 근거

- `@Transactional`은 원자성을 줄 뿐 두 트랜잭션의 인터리빙을 직렬화하지 않는다. READ COMMITTED에서 평범한 SELECT는 아무것도 잠그지 않으므로 둘 다 "조건 통과"를 본다.
- 겉보기가 같은 check-then-act여도 안전성이 다르다. 스크린타임 저장은 last-write-wins라 lost update가 없어 락을 걸지 않았고, 집중 집계는 `+=` 누적이라 걸었다. GROMO-560의 3안 비교에서는 네이티브 `ON CONFLICT`가 알림 side-effect 경로를 태우기 어렵고, 비관적 락은 막을 게 없는데 대기 비용만 내므로, 유니크 제약 + 새 트랜잭션 1회 재시도를 택했다.
- 애플리케이션 레벨 사전 검사는 방어선이 아니다. 친구 핀 API(GROMO-454)의 `existsBy` + `save`는 버튼 연타만으로 500이 나는 경로였고, 멱등 API에서 이 조합을 금지했다. 최종 방어선은 DB 제약이고 설계할 것은 제약 위반 시의 응답 형태다.
- 재현 테스트가 없으면 다음 리팩터링에서 방어를 걷어내도 CI가 걸러 주지 못한다. GROMO-560 수정에는 N=2와 N=10 동시 저장 테스트를 붙여 예외 0건·행 1개·최종값 일관을 확인했다.

## 영향

- 동시성 테스트는 비싸므로 돈 경로에만 붙이는 것이 기본이고, 유니크 위반이 500으로 새거나 계정 정합성이 깨지는 경로에는 예외로 붙인다.
- 잠금 조회 메서드는 쓰기 경로 전용으로 분리하고 이름에 `ForUpdate`를 붙여 일반 조회가 불필요하게 경합하지 않게 한다.
- 그룹 정원은 감사 시점에 미수정이다. 수리 방향은 참가 시 `Group` 행 버전을 실제로 올리거나(인기 그룹에서 재시도 폭증 위험), 카운트 검사와 INSERT를 원자화하는 것이며, 그룹 규모로 분기하는 안을 열어 두었다.
- 잔액 차감의 낙관적 락은 버전 컬럼이 있지만 재시도 로직이 없어 동시 요청 시 하나는 예외로 실패한다. 낙관·비관·유니크를 같은 부하 프로파일에서 재보고 변곡점을 숫자로 남기는 것이 다음 목표다.
