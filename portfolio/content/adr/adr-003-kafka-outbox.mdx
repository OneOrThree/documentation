## 맥락

Data가 확정한 사건을 Notification과 Realtime으로 전달해야 한다. 요구는 장애나 재시도에도 원장과 화면이 서로 다른 사실을 만들지 않는 것이다. 발행 성공 여부와 무관하게 사건의 원본이 남아야 하고, 같은 사건이 두 번 도착하거나 오래된 사건이 늦게 도착해도 소비자 DB가 틀리지 않아야 한다.

이전 대조는 main `875a9fd8`와 통합 PR의 `c015b2aa`를 각각 고정했다. **2026-09-17 정정:** PR #745는 2026-09-13 12:45 KST에 병합됐으며 main `59790ce49`에 Kafka overlay·outbox relay·Notification 소비가 포함돼 있다. “main에는 없다”는 설명은 현재 상태가 아니다. relay·소비·스케줄의 활성화 기본값은 OFF이고 호스트 운영 활성화 여부는 이번에 실측하지 않았다. 개발용 브로커는 `apache/kafka:3.8.1` KRaft 단일 노드, replication factor 1이다.

## 선택지

- **SQS 표준 큐.** 기각. 2026-09-09 브로커 비교(GROMO-1658)는 운영 부담 0(관리형)·순서 불필요(알림 5종은 유저별 독립 사건이고 멱등 키로 dedup)·MQ로 못 가는 리스너 2종(`GroupBetEarlySettlementListener` 도메인 내부, `BetResultAckSuppressionListener` 동기 필수)을 근거로 SQS를 추천했다. 같은 날 저녁 Kafka 도커(KRaft 단일 노드)로 확정하며 철회했고, 조건은 prod t4g 사양 실측, retention·재시도·DLQ를 직접 구현, Vercel 링크 서버는 브로커를 공유하지 않음 세 가지였다.
- **Business가 명령 처리 직후 별도 시각·새 eventId로 사건을 발행한다.** 기각. Business의 즉시 발행도 Data가 커밋한 봉투를 재사용한다. 사건을 다시 만들면 Data 커밋과 다른 사실이 생긴다.
- **DB sequence 할당 순서를 커밋 순서로 쓴다.** 기각. aggregate version은 상태와 같은 잠금 아래 증가시키며 sequence 순서를 커밋 순서로 사용하지 않는다.
- **파티션 키로 순서 보장을 끝낸다.** 기각. `notification-events`는 userId 키·3 partitions로 같은 유저의 브로커 도착 순서를 모으지만, DB 커밋 순서를 대신 보장하지 않는다.
- **브로커 장애 시 HTTP 자동 폴백.** 미결(A18). outbox의 목적지 상태를 남겨 relay가 재시도하는 것까지만 확정했다.
- **같은 TX의 outbox + relay + eventId·version으로 멱등한 소비자.** 채택.

## 결정

**Data는 상태 변경·원장·version·명령 receipt·outbox를 같은 TX에 저장하고, relay가 미전달 outbox를 lease로 선점해 Kafka로 보낸다. 소비자는 eventId로 중복을 접고 aggregate version으로 오래된 적용을 거부한다. Kafka overlay·relay·Notification 소비/스케줄의 활성화 기본값은 OFF다.**

| 항목 | 계약 |
| --- | --- |
| 알림 토픽 | `notification-events`, 3 partitions, 키 `userId` |
| 소비자 | `notification-v1`, ACK 모드 RECORD. 수신 서비스의 DB 커밋 뒤 반환 |
| 소비 실패 | 1초 간격 추가 재시도 3회 후 `notification-events.DLT`. 원본 파티션 번호를 유지하므로 DLT도 3 partitions |
| DLT 발행 실패 | recoverer가 실패를 예외로 돌려주고 복구 실패를 성공 처리하지 않음 |
| 발행 실패 | outbox의 목적지 상태를 남겨 relay가 재시도 |
| 봉투 축 | `eventId` 중복 제거 · `version` 상태 적용 순서 · `schemaVersion` 스키마 호환성 |

relay는 전송이 확인된 목적지만 완료 처리한다. Kafka ACK 후 완료 표시 전에 죽으면 같은 eventId가 다시 갈 수 있으며, 그래서 소비자가 멱등해야 한다. 실패한 위성 HTTP 전달도 같은 relay가 이어받는다.

## 근거

- outbox가 같은 TX에 있으면 발행 성공 여부와 무관하게 사건의 원본이 남고 relay가 재시도할 수 있다.
- 중복과 순서는 다른 축으로 다룬다. `eventId`는 중복 제거, aggregate `version`은 오래된 적용 거부, `schemaVersion`은 호환성이다.
- HTTP 시도별 requestId와 비즈니스 eventId는 별개다. 응답 유실 시 재생은 명령 receipt(동일 `Idempotency-Key`·동일 fingerprint·유효한 재생 권한)가 맡고, 사건 재전달은 outbox가 맡는다.
- 기존 결정 장부는 `.DLT`를 프레임워크 기본값으로 설명하지만, 확인한 Notification 코드는 resolver에서 `.DLT` 접미사를 명시적으로 고정한다. 버전별 기본 접미사에 기대지 않는다.
- 코드가 존재한다는 사실과 운영 전환 완료는 다른 상태다. 활성화 전에 consumer lag, DLT 유입률, outbox oldest-pending, relay 실패율의 기준선을 잰다.

<Callout label="내구성 범위" tone="warn">
개발용 Kafka는 단일 KRaft 브로커·replication factor 1이며 내부 토픽도 1이다. 영속 볼륨과 7일 보존을 쓰지만 다중 브로커 장애 내성은 제공하지 않는다. 파티션 수만 적으면 순서 보장이 끝난 것처럼 보일 수 있다.
</Callout>

## 영향

- 수신에 성공했다는 사실은 모든 기기의 화면 표시가 끝났다는 뜻이 아니다. Realtime 신규 이벤트를 기존 `notification-events`에 얹는 연결은 확정하지 않았다.
- 링크·어트리뷰션은 별도 서버가 아니다(A23). 공개 표면은 business-api, 원장은 data-api의 코어 DB이므로 발급·claim·폐기가 같은 트랜잭션에서 끝나고 Kafka도 위성 HTTP 전달도 쓰지 않는다.
- 이벤트 스키마 변경은 호환 소비자를 먼저 준비한다. 서비스별 Datadog에 HTTP requestId와 eventId를 연결하고 Kafka lag, outbox 재시도, DLT, 알림 지연을 별도 관측한다.
- 관리형 Kafka 이관 조건은 브로커 장애로 30분 이상 발송 지연이 월 1회 이상, 또는 디스크·업그레이드 수작업이 월 1회 이상이다. 이관 시 기존 토픽과 DLT의 backlog를 drain·처리 또는 보존하고, 랭킹 스트림 도입 후에는 `score-events`와 그 DLT도 같은 절차에 넣는다.
- 후속: DLT 재처리에서 같은 `eventId`가 다시 들어와도 소비자 DB가 중복을 접는지 장애 주입으로 확인한다. 2026-09-13 기준 실증 결과가 없다.
