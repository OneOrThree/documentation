## 맥락과 실제 근거

GROMO-1661은 하나의 Data API가 앱 요청과 데이터 적재·통계 집계·배치를 함께 맡아, 한쪽 변경이 다른 쪽 재배포를 강제하고 스케줄러가 API 스케일아웃을 제약한다는 문제에서 시작했다. 티켓은 요청 동시성과 적재 처리량의 다른 확장 축, 설정·커넥션 풀·CI·관측 분리를 작업 범위로 정했다. 이것은 **분리를 추진한 문제의식**이며, 실제 운영 병목을 측정해 입증한 결과는 아니다.

이후 ADR-002와 API 플랫폼 HLD는 공개 인증·DTO·BFF를 Business로, 권한·정산·원장·receipt·outbox와 PostgreSQL 정본을 Data로 배치했다. 초기 티켓의 “배치·집계부터 분리”와 현재의 “공개 조합 계층/원자 명령 계층”은 같은 설명이 아니다. 이 ADR은 현재 경계의 근거와 비용을 보완하며 새 서비스 분리나 운영 전환을 결정하지 않는다.

## 결정

**Business는 영속 DB 없이 공개 계약과 화면 조합을 맡고, Data는 코어 정본과 쓰기 불변식을 단일 트랜잭션에서 확정한다.** Business→Data는 검증 주체·서비스 자격·requestId·전체 deadline을 전달하는 내부 HTTP 계약이다. 화면 계약 변화와 원장 로직 변화의 배포 경계를 분리하고, 정본에 직접 접근하는 서비스를 늘리지 않는 것이 이 경계를 선택한 이유다.

## 감수하는 비용과 한계

| 비용 | 경계와 대응 |
| --- | --- |
| 추가 HTTP 홉 | Business가 Data를 경유하는 조회는 네트워크·직렬화·실패 경로가 추가된다. 화면별 호출 수·상류 지연·전체 deadline을 측정해야 하며 지연 개선을 주장하지 않는다 |
| HTTP 위의 호출 증폭 | 여러 조각을 조합하면 다중 호출이 생긴다. HLD는 필수/선택 조각과 전체 예산을 구분하고, 반드시 일치해야 하는 값은 Data의 단일 snapshot 조회로 묶는다. 호출 수·중복 조회 비용은 후속 측정 대상 |
| 원자성 범위 | Business가 Data 명령 두 번을 호출하는 것은 하나의 TX가 아니다. 전부 성공해야 하는 불변식은 Data의 단일 원자 명령에서 처리한다. 별도 명령의 부분 성공을 자동으로 롤백한다고 표현하지 않는다 |
| Data·DB 병목 | Business만 늘려도 Data CPU·DB 연결 풀·잠금 병목은 남는다. 배포와 공개 계층의 자원 경계를 나눈 것이며 전체 처리량 확장 효과는 미실증 |
| 장애 의존성 | Data가 멈추면 Data가 필요한 공개 API도 실패한다. Business 분리가 Data 장애를 차단하는 것은 아니다. timeout·취소·선택 조각 폴백은 계약에 맞춰 검증해야 한다 |

## 대안 기록

- **단일 서버 유지:** GROMO-1661의 출발 구조다. 내부 호출이 간단하고 네트워크 홉이 없지만 요청·배치·집계의 배포와 자원이 묶인다. 현재 경계는 이 결합을 줄이는 방향을 선택했다.
- **Business가 코어 DB에 직접 접근:** ADR-002의 Data 단일 정본 소유 규칙과 맞지 않아 채택하지 않는다. 읽기 복제본을 Business에 제공하려면 허용 지연·snapshot·자격·운영 책임을 별도 결정해야 한다.
- **읽기 복제본 또는 GraphQL 게이트웨이:** 이번 검토가 제안한 재검토 후보다. 당시 비교·기각한 기록은 확인하지 못했으므로 과거 기각안으로 꾸미지 않는다. 게이트웨이를 추가해도 Data의 원자성이나 DB 병목이 자동 해결되지는 않는다.

## 후속 검증과 재검토

2026-09-17 기준 이 문서 보완에서는 분리 전후 운영 성능을 실측하지 않았다. 같은 워크로드로 화면별 p95·Business→Data 호출 수·Data CPU·Hikari pending·잠금 대기를 함께 측정한다. 시스템 정본의 Business 다중 인스턴스 시작 조건(API p95 1초 초과 일 3회 이상 또는 CPU 70% 이상 10분 지속)을 만족해도 Data 병목을 먼저 구분한다.

추가 홉과 호출 증폭이 지연을 지배하거나, 독립 배포의 이점이 확인되지 않으면 Data 조회 계약을 묶는 안과 모듈 경계를 유지한 단일 프로세스 운영을 재검토한다. 수치는 성능 결과를 확인한 뒤 정하며 측정하지 않은 개선율은 적지 않는다.
