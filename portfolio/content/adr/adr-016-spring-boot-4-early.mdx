## 맥락

백엔드는 Spring Boot 4 계열로 시작했다. 최초에 Boot 4를 고른 사유는 출처 문서에 기록돼 있지 않다. 이 ADR은 조기 채택의 대가를 치른 뒤 그 선택을 유지하기로 한 결정과, 그 대가를 규약으로 흡수한 내용을 적는다.

참고한 예제와 물려온 코드는 전부 Boot 3 세대였고, 같은 모양의 사고를 세 번 겪었다.

| 증상 | 처음 의심한 것 | 실제 원인 |
| --- | --- | --- |
| `Cannot resolve symbol 'DataJpaTest'` | 테스트 의존성 누락 | Boot 4가 테스트 슬라이스를 모듈별 패키지로 재편 |
| `package com.fasterxml.jackson.datatype.jsr310 does not exist` | Jackson 모듈 의존성 누락 | Boot 4 = Jackson 3, 패키지 좌표가 `tools.jackson.*`로 이동 |
| Flyway 마이그레이션이 로그 한 줄 없이 미적용 | 설정값 오타 | 오토컨피그가 기술별 모듈로 분리돼 `flyway-core`만으론 부족 |

세 번 다 빌드 스크립트가 아니라 Boot 4가 바꾼 구조가 원인이었다. 4.0.6 jar를 직접 grep하니 30초 만에 좌표가 나왔는데, 그 30초를 몰라 의존성 트리를 한참 붙잡았다. 별도로 채팅 서비스를 Boot 4.1.0 + Testcontainers 2.0.5로 올리려다 Testcontainers 모듈 좌표가 맞지 않아 의존성 해결 자체가 실패했다.

## 선택지

| 선택지 | 판정 | 근거 |
| --- | --- | --- |
| Boot 3 세대로 되돌린다 | 기각 | 출처: "같은 선택을 다시 한다 해도 Boot 4로 갔을 것입니다" |
| Boot 4 유지, 서비스마다 최신 조합을 자유롭게 올린다 | 기각 | 채팅 서비스의 4.1.0 + Testcontainers 2.0.5 조합이 의존성 해결에 실패 |
| Boot 4 유지, 서비스 간 조합을 하나로 고정하고 구조 차이를 규약으로 흡수한다 | 채택 | 아래 |

## 결정

**Spring Boot 4 조기 채택을 유지한다. 서비스 간 조합은 메인 백엔드와 동일한 Boot 4.0.6 + Testcontainers 1.20.1 하나로 고정하고, 모듈형 구조에서 오는 차이는 아래 규약으로 흡수한다.**

- 오토컨피그 모듈을 명시한다. Flyway는 의존성 3종이 전부 있어야 켜진다.

```gradle
implementation 'org.springframework.boot:spring-boot-flyway'   // Boot 4: 오토컨피그
implementation 'org.flywaydb:flyway-core'                      // 엔진
runtimeOnly    'org.flywaydb:flyway-database-postgresql'        // Flyway 10+: DB별 지원
```

- 테스트 슬라이스는 `org.springframework.boot.MODULE.test.autoconfigure.ANNOTATION` 규칙을 따른다. 4.0.6 기준 `@DataJpaTest`는 `spring-boot-data-jpa-test`, `@AutoConfigureTestDatabase`는 `spring-boot-jdbc-test`, `@WebMvcTest`·`@AutoConfigureMockMvc`는 `spring-boot-webmvc-test`다. `@SpringBootTest`만 `org.springframework.boot.test.context`에 그대로 있다.
- Jackson 3를 쓴다. `com.fasterxml.jackson.databind` → `tools.jackson.databind`, java.time은 코어에 통합돼 `JavaTimeModule` 등록 코드를 지운다. 컨버터는 `MappingJackson2MessageConverter` → `JacksonJsonMessageConverter`, `MappingJackson2HttpMessageConverter` → `JacksonJsonHttpMessageConverter`. 서버와 테스트 클라이언트는 같은 세대 컨버터를 쓴다.
- 막혔을 때의 첫 행동을 고정한다.

| 상황 | 첫 행동 |
| --- | --- |
| import가 안 잡힌다 | 의존성 트리 대신 `jar tf "$JAR"` 출력에서 클래스 이름 검색 |
| 기능이 조용히 안 켜진다 | `--debug`의 CONDITIONS EVALUATION REPORT에서 오토컨피그 이름 검색 |
| 통합 테스트가 아무것도 못 받는다 | 서버와 테스트 클라이언트의 컨버터 세대 확인 |
| DTO 필드를 클라이언트가 못 읽는다 | 응답 본문의 실제 키를 확인한 뒤 `jsonPath`로 그 키를 고정 |
| 새 조합을 올리고 싶다 | 프레임워크와 테스트 인프라를 동시에 올리지 않는다 |

## 근거

- 메이저 버전이 앞선 환경에서는 import가 안 잡히면 좌표 이동을, 기능이 로그 한 줄 없이 안 켜지면 오토컨피그 모듈 누락을 먼저 의심한다. 의존성 누락으로 단정하고 빌드 스크립트를 다시 들여다본 시간이 통째로 낭비였다.
- Flyway 사례의 단서는 로그의 패키지 이름이었다. Hibernate 설정 클래스가 `org.springframework.boot.hibernate.autoconfigure.HibernateJpaConfiguration`로 찍혀, 클래스패스를 다시 훑으니 `spring-boot-flyway`만 없었다. `flyway-core`는 이 모듈을 전이 의존성으로 끌어오지 않는다. 넣고 다시 띄우자 `Successfully applied 1 migration`이 찍혔다.
- Jackson 세대 불일치는 예외 없이 실패한다. 서버는 Jackson 3로 `Instant` 페이로드를 직렬화했고, 테스트 STOMP 클라이언트는 Boot 3 예제를 따라 `MappingJackson2MessageConverter`(Jackson 2)를 썼다. 테스트는 예외도 실패 로그도 없이 메시지를 수신하지 못했다.
- 모듈형 오토컨피그는 방향 자체는 좋다고 판단했다. 전환기에 치르는 비용은 필요 의존성이 늘고 스타터 이름이 겹치는 것이다(리뷰에서 `starter-web`과 `starter-webmvc` 동시 선언을 지적받았다).
- 앞서 쓰는 것들끼리 조합하면 비용이 곱해진다. 새 프레임워크와 새 테스트 인프라를 동시에 최신으로 밀지 않고, 서비스 간에 하나의 조합으로 고정하는 쪽이 훨씬 저렴했다.

<Callout label="조기 채택의 비용은 간격에서 나온다" tone="primary">
프레임워크는 앞서 나가도 그것을 검증할 테스트 인프라와 참고할 예제는 같은 속도로 따라오지 않는다. 다음 버전을 고를 때는 숫자보다 그 간격의 폭을 먼저 잰다.
</Callout>

## 영향

- 검색 결과가 구 버전 정보로 오염돼 있으므로, 좌표는 문서보다 클래스패스에서 직접 확인한다.
- STOMP 테스트는 타입 역직렬화 이슈가 남아 페이로드를 `Map`으로 받아 키 단위로 검증하는 우회를 썼다. 테스트가 실제 클라이언트(React Native)와 다른 경로로 역직렬화한다는 사실 자체가 리스크로 남아 있다.
- boolean `is`-프리픽스 필드(`isFocusing`, `isPinned`)는 Lombok getter와 Jackson 규칙이 겹쳐 JSON 키가 `focusing`·`pinned`로 나간다. `@JsonProperty`로 키를 고정하거나 필드에서 `is`를 빼는 두 방법 중 하나를 프로젝트 차원에서 정해 통일하고, 선택한 키를 `jsonPath`로 검증한다. 어느 쪽인지는 출처에 확정돼 있지 않다.
- 요청 역직렬화가 같은 키 규칙을 타는지, 박싱 `Boolean`의 getter 이름과 JSON 키가 무엇인지는 미확인으로 열려 있다.
