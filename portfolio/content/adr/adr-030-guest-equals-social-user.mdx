## 맥락

게스트는 소셜 로그인 없이 "로그인 없이 시작하기"로 만든 계정이다. 서버에는 `is_guest = true`인 실제 `users` 행이 생기고, 그 계정을 되찾을 열쇠는 기기에 저장된 토큰뿐이다.

리그 모수(리그 랭킹과 주간 정산에 들어가는 유저 집합)는 `is_guest = false` 한 조건으로 판정하고 있었다. 이 조건은 두 방향으로 틀렸다.

- 게스트는 온보딩을 끝까지 마치고 닉네임과 준비 시험까지 등록해도 리그에 들어가지 못했다.
- 소셜 로그인만 하고 온보딩 중간에 떠난 유저(`nickname IS NULL`)는 모수에 들어갔다. 그래서 이름 없는 행으로 랭킹에 떴고, 주간 정산에서 0초 STAY(잔류) 결과까지 받았다.

온보딩 흐름을 보면 이유가 드러난다. 계정은 로그인 시점에 먼저 생기고, 프로필 등록(`POST /users/me`)은 마지막 닉네임 스텝에서만 나간다. 게스트도 같은 경로를 탄다. 그러니 **서버가 가진 온보딩 완주 신호는 닉네임 존재가 유일하다.** `is_guest`는 "어떻게 로그인했나"를 말할 뿐 "온보딩을 마쳤나"를 말하지 않는다.

그룹 쪽도 같은 문제를 안고 있었다. 그룹 도메인은 게스트를 `GUEST_FORBIDDEN`으로 막고 있었는데, 게스트도 가입할 때 지갑·스크린타임·집중·알림 설정 행이 똑같이 만들어진다. 기능상 막을 근거가 없었다.

게스트를 열면 새 구멍이 생긴다. `POST /auth/guest`에는 인증도 레이트리밋(단위 시간당 호출 횟수 제한)도 없었고, 호출 한 번에 `users` 행이 하나 생긴다. 게스트를 리그와 그룹에 넣는 순간 계정을 무한히 찍어 랭킹과 그룹 내기(코인)를 흔들 수 있게 된다.

## 선택지

| 선택지 | 문제 | 판정 |
| --- | --- | --- |
| `is_guest` 기준 유지 | 완주한 게스트는 빠지고, 미완주 소셜 유저는 들어가는 두 방향 오류가 그대로 남는다 | 기각 |
| 리그 게이트를 `nickname IS NOT NULL`로 | 서버가 가진 유일한 완주 신호. 게스트와 소셜을 같은 기준으로 가른다 | 채택 |
| 게스트 가드만 풀고 레이트리밋 없이 배포 | 게스트 무한 생성으로 랭킹·내기가 오염된다 | 기각 |
| 티켓에 적힌 그룹 가드 10곳만 해제 | 내기 참가는 되는데 진행분 보고만 403이 된다. 판정이 미달로 굳어 판돈만 잃는 반쪽 상태 | 기각 |
| 레이트리밋 축을 기기 식별자로 | 클라이언트가 보내는 값이라 헤더만 바꾸면 우회된다. 대량 생성 방어력이 0 | 기각 — IP 축 채택 |
| refresh 토큰 30일 고정 수명 유지 | 소셜 연결을 안 한 게스트는 매일 앱을 써도 30일이면 계정을 잃는다. 게스트가 방장인 그룹은 확정 고아가 되어 개방 자체가 성립하지 않는다 | 기각 |

## 결정

**게스트를 소셜 유저와 똑같이 취급한다. 리그 참가 자격은 `is_guest`가 아니라 온보딩 완주의 유일한 서버 신호인 닉네임 존재로 가르고, 게스트 개방은 `POST /auth/guest` 레이트리밋과 같은 배포로 묶는다.**

| # | 변경 | 티켓 · PR |
| --- | --- | --- |
| 1 | 리그 게이트를 `nickname IS NOT NULL`로. 빈 문자열·공백만 있는 값도 거른다 | GROMO-1508 · #620 |
| 2 | 그룹 게스트 가드 12곳 해제. 티켓 명시 10곳에 누락 2곳(내기 상세 조회, 창 사용분 보고)을 더했다 | GROMO-1509 · #644 |
| 3 | `POST /auth/guest`에 IP 단위 레이트리밋. 기본 1시간 10회, 초과 시 `429` | GROMO-1510 · #621 |
| 4 | refresh 토큰 회전(갱신할 때마다 새 refresh 토큰 발급) + 게스트 refresh 수명 90일. 소셜은 30일 유지 | GROMO-1509 · #644 |
| 5 | 앱의 게스트 사전 차단 UI와 `GUEST_FORBIDDEN` 분기 제거 | GROMO-1511 · #624 |
| 6 | 게스트 계정이 사라질 수 있다는 고지와 소셜 로그인 유도 | GROMO-1509 · #645 |
| 7 | (09-07) 앱의 기존 계정 판정 = `isNewUser === false` **그리고** 닉네임 존재 | GROMO-1637 · #714 |

1~3은 같은 배포로 나간다. 5는 서버 개방이 배포된 뒤에만 앱 빌드에 실을 수 있다. 서버가 아직 403을 주는데 앱의 사전 차단만 사라지면, 게스트는 "로그인하세요"라는 정확한 안내 대신 영원히 풀리지 않는 "잠시 후 다시 시도해 주세요"를 보게 된다.

## 근거

- **게이트 한 줄로 두 방향이 같이 고쳐진다.** 리그 정산 배치의 조회 3경로가 모두 같은 주간 합계 SQL 조각을 조립해 쓴다. 그래서 유령 유저의 0초 STAY 행 생성도 게이트 한 줄로 함께 사라졌다.
- **술어는 NULL만 거르지 않는다.** `btrim(u.nickname) <> ''`까지 본다. 닉네임 검증(GROMO-1215)이 들어오기 전에는 PATCH가 빈 문자열을 그대로 저장했고, 그 레거시 행을 정리한 마이그레이션이 없었다.
- **개방과 가드는 짝이다.** IP 한 축만 쓴 이유는 기기 식별자가 클라이언트 소유 값이라 우회가 쉽기 때문이다. 한도는 코드에 박지 않고 프로퍼티로 뺐다. 통신사 CGNAT(여러 가입자가 공인 IP 하나를 나눠 쓰는 방식)이나 학교·카페 와이파이에서는 실사용자 여럿이 IP 하나를 공유한다. 정상 신규 유저의 온보딩이 막히는 것이 가장 비싼 오탐이라, 배포 없이 값만 올릴 수 있게 했다.
- **refresh 회전은 개방의 전제였다.** 기존 `refreshToken()`은 access 토큰만 재발급해서 refresh 수명이 로그인 시점부터 고정이었다. 게스트 로그인은 언제나 새 User를 만들어 복구 경로가 없으므로, 게스트에게는 만료가 곧 계정 소실이다. 코드 리뷰(코덱스)가 이 문제를 찾았다. dev는 access 토큰도 30일이라 refresh를 거의 쓰지 않는다. dev 테스트로는 절대 재현되지 않는 종류다.
- **고지 문구에 만료 일수를 박지 않았다.** 만료 기간은 서버 refresh 수명이 정하는데 앱은 심사를 거쳐 나간다. 숫자를 박으면 서버 값이 바뀌는 순간 앱이 거짓을 말한다. 회전이 들어가면 미접속 만료는 대부분 유저에게 걸리지 않고, 실제 소실 경로는 앱 삭제·기기 변경이다. 그래서 그쪽을 앞세웠다.
- **09-07, 같은 원리를 앱에도 적용했다.** 온보딩 중간에 로그인만 하고 프로필 등록 전에 떠난 계정이 다시 로그인하면, 서버는 소셜 계정이 있으니 `isNewUser = false`를 준다. 서버 관점에서는 맞는 값이다. 앱은 그것만 보고 남은 온보딩을 건너뛰었고, 닉네임 없는 '유령 계정'이 영구히 고착됐다. `isNewUser` 하나가 "계정이 새로 생겼나"와 "프로필을 등록했나" 두 의미를 겸한 탓이다. 판정 재료를 의미별로 나눠 `isExistingAccount(login)` 헬퍼로 모았다. 서버 변경은 없다. `setupProfile`에 "이미 등록됨" 검사가 없어 유령 계정이 온보딩을 다시 완주해도 정상 처리된다.

<Callout label="플래그 하나가 두 의미를 겸하면 그 틈이 유령이 된다" tone="warn">
`is_guest`는 로그인 방식을, `isNewUser`는 계정 생성 시점을 말한다. 둘 다 "온보딩을 마쳤나"를 대신 답할 수 없다. 계정 생성과 프로필 등록 사이에서 이탈한 계정은 어느 플래그로 봐도 정상처럼 보이고, 랭킹·친구 목록에는 드러나지 않은 채 지표의 분모만 오염시킨다.
</Callout>

## 영향

- 배포 시점에 랭킹 인원수와 정산 대상 수가 한 번 움직였다. 닉네임 있는 게스트가 편입되고 닉네임 없는 유저가 빠졌다.
- 알려진 한계: 과거 Apple 로그인이 이름(`fullName`)을 닉네임에 미리 채우던 시기의 계정은 온보딩을 이탈했어도 유효한 닉네임을 갖고 있어 모수에 남는다. 이전에도 모수였으므로 이 변경의 회귀는 아니고, 별도 후속으로 뺐다.
- 서버 `setupProfile`의 조건부 가드는 BE 후속 과제로 남았다.
- 앱을 다시 켜지 않는 유령 계정은 자가 치유되지 않는다. 그래서 활성화 지표를 셀 때는 닉네임 없는 계정을 분모에서 뺀다 — [ADR-034](/adr/adr-034-activation-metric), [지표 함정 노트](/research/metric-pitfalls).
- 게스트 승격(게스트 → 소셜 연결)은 같은 User 행에 소셜 연동을 붙이는 구조라 코인·집중 기록·그룹이 그대로 유지된다. 고지 문구의 "기록 그대로 옮겨가요"는 이 서버 코드를 확인하고 넣었다. 승격 경로의 동시 로그인 레이스는 [인증 하드닝](/research/auth-hardening)에 있다.
- 2.0도 게스트 로그인과 refresh 경로를 그대로 유지하고, 게스트에게 열린 쓰기에 계정당 시간 한도를 짝으로 붙이는 같은 방식을 이었다(GROMO-1934).
