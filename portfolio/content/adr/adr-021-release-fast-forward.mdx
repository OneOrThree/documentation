## 맥락

브랜치는 두 개다. `main`에 머지되면 dev에 배포되고, `release`에 올라가면 prod-ci가 돌아 prod에 배포된다. 기능 PR은 전부 `main`으로 가고, 팀은 squash 머지를 쓴다. 레포 설정도 그렇게 잠겨 있다. 07-23에 확인한 값이다.

```
gh api repos/OneOrThree/phone --jq '{squash: .allow_squash_merge, merge_commit: .allow_merge_commit, rebase: .allow_rebase_merge}'
→ squash: true, merge_commit: false, rebase: false
```

첫 prod 배포는 07-20 00:24였다. `git log --oneline origin/main..origin/release`로 release에만 있는 커밋이 없는지, `git merge-tree`로 충돌 마커(`<<<<<<<`)가 0건인지 확인한 뒤 00:32에 `git push origin main:release`로 올렸다. PR을 만들자고 시작한 대화였지만 실제 승격은 push였다.

문제가 드러난 것은 07-23이다. 17:52에 release PR #325를 올려 두고 18:07에 "나는 squash merge밖에 안 되는데 대신 머지해 줄 수 있냐"는 요청이 왔다. 확인해 보니 release HEAD `01def29a`가 main에도 같은 SHA로 있고, release는 main의 직계 조상(선형)이었다. 즉 이 팀의 release 승격은 지금까지 squash PR이 아니라 fast-forward push로 이뤄져 온 것이고, #325를 버튼으로 밀면 그 규칙이 깨진다.

## 선택지

| 선택지 | release와 main의 관계 | 이후 승격 | 판정 |
| --- | --- | --- | --- |
| release PR을 squash 버튼으로 머지 | release에 main에 없는 새 커밋이 생겨 갈라짐 | FF가 영영 불가능, 릴리즈마다 꼬임 | 기각 |
| 레포 설정을 바꿔 merge commit 허용 | 머지 커밋 역시 main에 없는 커밋이라 SHA가 갈라짐 | 같은 문제 | 미검토 — 07-23 로그에 검토 흔적 없음 |
| `origin/main`을 release로 fast-forward push | 같은 SHA, release는 main의 직계 조상 유지 | 다음에도 FF 가능 | 채택 |

squash 기각 이유는 한 줄이다. squash는 브랜치의 변경을 새 커밋 하나로 다시 쓰기 때문에, release에 생기는 그 커밋은 main 어디에도 없다. 그 순간부터 release는 main의 조상이 아니게 되고, 다음 배포에서 `main:release` FF push는 거부된다.

## 결정

**release 승격은 `git push origin origin/main:release`로 하고, 열어 둔 release PR은 머지하지 않고 닫는다. push 전에 release가 main의 조상인지와 충돌 0건을 반드시 확인한다.**

| 단계 | 명령 | 확인할 것 |
| --- | --- | --- |
| 1. release에만 있는 커밋 | `git log --oneline origin/main..origin/release` | 출력 0줄 |
| 2. FF 가능 여부 | `git merge-base --is-ancestor origin/release origin/main` | 종료 코드 0 |
| 3. 충돌 | `git merge-tree $(git merge-base origin/release origin/main) origin/release origin/main \| grep -c '<<<<<<<'` | 0 |
| 4. 승격 | `git push origin origin/main:release` | release SHA = main SHA |
| 5. 파이프라인 | prod-ci 실행 확인 | 같은 SHA로 `in_progress` |
| 6. 정리 | release PR에 코멘트 후 close | — |

release PR 자체는 계속 만든다. 무엇이 prod로 나가는지 리뷰어가 볼 diff와 배포 기록으로서의 역할이 있고, 08-18에도 "main 빌드를 prod에 배포하려 하니 draft PR을 올려 달라"로 시작했다. 다만 버튼으로 머지하지 않는다.

## 근거

- 07-23 18:10 실행 결과: push 전 `git rev-parse origin/release`와 `origin/main`을 나란히 찍고 FF push → release가 main과 정확히 같은 SHA `429a0999`로 갱신됐고, prod-ci가 그 SHA로 곧바로 `in_progress`에 들어갔다. 18:12에 #325에 상황 설명 코멘트를 달고 close했다.
- 같은 날 20:58, #326이 main에 squash 머지돼 main이 `010c3052`가 됐고 release는 `429a099`였다. 배포할 커밋 1개, release는 여전히 main의 직계 조상이라 FF 가능 → 다시 release PR을 만들었다. 절차가 두 번째 배포에서도 그대로 통했다.
- 08-18 16:50 재확인: `git rev-list --count origin/main..origin/release`(release-only 커밋 수)와 `merge-base --is-ancestor origin/release origin/main`으로 FF 가능을 확인하고, 이전 release 지점 `429a09993`·`010c3052f`가 둘 다 main의 조상인지, `merge-base(main, release)`가 어디인지, `gh pr list --base release --state all`로 과거 release PR 이력이 어떤지까지 본 뒤 draft PR 본문을 썼다. 07-23의 판단이 한 달 뒤에도 유효했다.
- squash가 얼마나 쉽게 오해를 만드는지는 07-31 15:15가 보여 준다. 기능 PR을 squash 머지한 뒤 "잘못 머지한 것 같다"는 요청이 왔고, 브랜치 `36ec6e53`의 `^{tree}`와 `origin/main^{tree}`를 비교하고 `merge-base --is-ancestor 69ced87d origin/main`으로 조상 관계를 검증했다. squash 뒤에는 커밋 해시로는 "같은 변경"을 알 수 없고 트리 해시로 봐야 한다. release에서 이 상태를 만들면 매 배포마다 이 검증을 해야 한다.

<Callout label="PR을 만들었다고 PR을 머지하는 것은 아니다" tone="warn">
07-20도 07-23도 "PR 만들어 줘"로 시작해서 push로 끝났다. release PR은 기록이고, 승격은 push다. 이 둘을 섞어서 버튼을 누르면 되돌리기 어렵다. release를 다시 main과 같은 SHA로 맞추려면 force push가 필요한데 그것은 아래 훅 정책이 막는다.
</Callout>

## 영향

- release 컷이 배포 순서를 조절하는 도구가 됐다. 09-10 01:37 #729 머지 때 "main 머지 = dev 배포까지, prod(release) 컷은 앱 1726 배포 뒤"로 가정을 명시했다. 서버가 앱보다 먼저 prod에 나가면 안 되는 계약 변경을 main에는 넣되 release FF는 미루는 식이다. [/research/backend-layering-refactor](/research/backend-layering-refactor) 마지막 두 PR이 이 경우다.
- 07-20·07-23의 FF push는 에이전트가 직접 실행했다. 지금은 아니다. 전역 `settings.json`의 PreToolUse 훅이 `git push`를 검사해 "오케스트레이션 정책: main/release·강제 push 금지 (feature 브랜치만 허용)"으로 거부한다. 그래서 08-18처럼 에이전트는 FF 가능 확인과 draft PR까지만 하고, `origin/main:release` push는 사람이 한다. 09-09에도 리베이스 후 force push는 사람 몫으로 남겼고, 대신 `origin/main`을 브랜치에 머지해 force push 없이 충돌을 푸는 우회를 택했다.
- 훅은 명령 문자열을 보기 때문에 오탐이 있다. 09-09에 `git worktree remove --force`가 push와 같은 명령줄에 있자 "강제 push"로 막혀 명령을 분리해야 했다.
- release PR을 close하는 절차라 GitHub의 "merged" 표시는 남지 않는다. 배포 기록은 PR 코멘트와 prod-ci 실행 이력에 의존한다.
- 브랜치 보호가 없는 레포(free plan)라 이 규칙을 강제하는 것은 설정이 아니라 사람과 훅이다. 누군가 버튼을 누르면 그 자리에서 갈라진다.
